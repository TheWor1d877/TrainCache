# S3 合并回源⽹关
## 目标
设计一个网关在 Agent 和 MinIO 中间，实现更加高效与节能的传输方式，降低回源次数
所有源站都挂网关。源站在集群外、走公网、按 GB 计费的桶收益最大；同机房自搭 MinIO 照样挂，允许与 MinIO 落在同一个节点，必须是两个独立 Pod

重复块来源主要是： preheatFanout；同一 DataSet 上并发多个 WarmupTask，shuffle seed 不同导致不同节点要同一块

降低回源的两条手段各管一段：在途合并管同时到达的请求，源站只看到一次字节传输；缓存层管错峰到达的重复，一个块只在第一次回源时付一份出口流量。

## 缓存开关
缓存是一个开关，开则有一层磁盘缓存，关则只做在途合并。值写在 ConfigMap `traincache-config` 的 `gatewayCache`，Agent 侧不引用。

关闭态的口径是不命中不返回、不落盘、不管容量和淘汰。本文以下凡是写「出口 = 源站带宽 × N」「付整份字节」的地方，说的都是关闭态；开启态多出来的取数路径、出口带宽、磁盘配额与计量，在对应节里逐条交代。

清单不因开关分叉：卷常挂，开关只控制读不读写。带缓存与不带缓存两个实验臂除这个开关外装置完全相同，否则两臂对照不成立。

##  定位
关闭开关时只做在途合并，开启时在途合并之外加一层磁盘缓存。关闭态不命中不返回、不落盘、不管容量和淘汰。合并机制与节点内 Agent 的 in-flight 表相同，作用范围从单节点扩到集群内所有 Agent；缓存的作用范围也是集群内所有 Agent，一份字节留在网关盘上给所有节点复用。

窗口外「集群里某个节点已经有这块」的重复，原本交给分布式缓存组。缓存组不做，这一段由网关的缓存层承接。

## 位置与形态
位置：集群侧，在 Agent 和源站之间。所有节点的 Agent 通过同一个 Service 访问它。Agent 侧加一个网关地址配置项 `TRAINCACHE_GATEWAY_ENDPOINT`，值写在 ConfigMap `traincache-config` 的 `gatewayEndpoint`，与已有的源站地址配成一对，非空即启用、空则直连；凭证照旧从挂进 Pod 的 Secret 取，不经任何下发。DataSet.spec.endpoint 只归 Controller 用，是它校验 DataSet 时读 CURRENT 与 manifest 的地址，从不下发给 Agent。
- 不紧贴源站：贴源站时 N 份字节照样从存储节点网卡出去，省下的只是源站的 CPU 和磁盘读，带宽一分没省。网关与源站同 Pod 时两侧共享网络命名空间，那 1 份字节走 lo，挂在 eth0 上的 tbf 管不到，实验做不成；同节点不同 Pod 没这个问题。
- 不放到控制平面： 数据面流量挤占 etcd 和 apiserver 的 CPU 与网卡，控制面还是集群级故障域。
形态：独立进程，集中式。一个 Kubernetes Deployment，不是 DaemonSet——每节点一个等于回到节点内合并，跨节点没有效果。

如果S3在本地，S3与网关没必要分开到不同节点。只要是两个独立的Pod即可
生产环境下一般都是算存分离的，这一点不用考虑

#### 问题： 网关需要与Agent同节点还是分开单独节点？
不必独占。默认跟 Agent 混部，用 requests/limits 保住它自己那部分资源，而不是靠一整台机器隔离
出口 = 源站带宽 × N。按桶给 1Gbps、N=fanout 2–3 估，出口 2–3Gbps是 25Gbps 网卡的一到两成；
CPU 只有到源站那一段 TLS 加用户态拷贝，2核量级的
内存是扇出缓冲，在途块数 × 每个缓冲区大小，准入 64 × 10MiB = 640MiB，两态相同；热池另留 32 块
磁盘在关闭态是零，它不落盘；开启态是宿主盘上的缓存配额，等于单 dataset 上限 × dataset 数，另留全局总上限的余量
不值当作为一台单独的机器。盘的选择看命中侧要付的读带宽：宿主盘是 HDD（顺序读低于 300MB/s）或者同节点邻居写盘活跃，再给网关单独一块盘

## 容量计算
网关出口 = 源站出口带宽 × N
单副本能扛的 N = 网关节点网卡带宽 ÷ 源站出口带宽
N为节点数

开启缓存后出口分两段：命中侧的字节从网关盘上出，等于各节点取速率之和，4 节点 @1000 档是 500MB/s 即 4Gbps；未命中侧还是源站那一份 1Gbps。合计仍是 25Gbps 网卡的不到两成。

## 传输加密/信任边界
Agent 到网关走集群内网明文 HTTP(开关，能做成也走加密的，默认不加密)
TLS 只在网关到源站那一段终止，全集群加解密量从 N 降到 1
默认集群全部走内网，集群一半在外面的混合拓扑明确不管

源站的 accessKey 与 secretKey 两把，网关与 Agent 都需要有。Agent 发给网关的请求带的是按网关这个 host 算好的 SigV4 签名，转给源站前要用网关自己那份凭证重签，所以只有 AccessKey 不够。Agent 到网关不需要认证。

## 失败语义
网关不在训练 Pod 的读路径上（hostPath 只读直读本地盘）的情况下：
网关失效，Agent检测到网关失效将“取数据的后端”改成源站
不需要开新的健康检查通道，而是将下一次回源请求当作探针，降级后 Agent 保留「这个 endpoint 不可用」的标记和下次重试时间(初始10s间隔)，
到时间之后的取数前先试网关一次，成功就恢复正常路径，失败就继续直连并把下次探测间隔按退避拉长(上限到2min)

- 失败的判定条件要具体：连不上、TLS 握手失败、超时算
- 只有网关自己那一跳的 5xx 算，源站透传上来的 5xx 不算：直连同样会失败，切过去只是把源站的问题盖成网关的问题。网关回自己的失败时带一个自有响应头（x-traincache-gateway: unavailable），判据认这个头
- 403 429 这两个不算，需要开特例
- 准入到顶、缓冲到顶把请求拒回直连不算失效：那是容量信号，一次性，不写进降级状态

后端开关是 Agent 进程里的两个量：现在走哪个后端（网关还是源站），以及下次什么时候允许再试网关。同一节点上所有 dataset 的取数在发起前都问同一句「现在走哪个后端」，问的是同一个量，所以降级与恢复都是整个节点一起。

谁撞见这一跳失败（判据见上）谁就把后端改成源站，并记下 10s 后重试。之后任意一次取数先试网关一次，成功就把后端改回网关，这个节点的取数一起切回。

这个状态只活在 Agent 进程内存里，不写回任何 CRD：DataSet 对象不变，Controller 不知道哪个节点在降级。Agent 重启后回到配置默认，网关地址非空即启用。

正在下载的请求不切换，降级只影响新发起的取数

开启缓存后多一种冷启动：网关重启，盘是空的，之后的请求逐个回源、逐个回填。回源成功走的是正常路径，不触发降级，也不写进上面那个状态。

## 部署与更新
网关是单副本 Deployment。收到 SIGTERM 后，readiness 立即转 false 让 Service 摘流，停止接受新请求，等在途 GET 结束或满 30s 再退出。Agent 的在途下载因此看到的是正常收尾而不是连接重置；30s 内未结束的请求按普通失败处理，由 core/fetch 重试。

## QoS
不做分级。分层预取在上游已经做完，而且是两条轴：
agent/prefetch 按 P0–P3 四个优先级队列出队，
进 core/fetch 时折叠成两档准入，在读（需求读补块与坏块修复，按全场额度接入，不受折半额度与让路门约束）与预铺（预取与显式预热，任务槽与在途字节各折半，在读有下载在途时先让路）。
S3 GET 不携带档位标记，折叠之后的请求面上游分级透传不过来，网关再分一套只会跟上游打架。

做公平调度，分片粒度是S3中的dataset，当一个网关实例上同时挂着多个 dataset的时候(多个WarmupTask)，防止一个WarmupTask将另一个饿死。
并发下载额度按活跃 dataset 均分，每份额保底 1、封顶总额度的 1/2，空闲份额让给还在排队的。不做加权、不做抢占

做准入，网关到桶的并发下载数限制在 64 个（参数可以调节），实际要按照桶的 QPS 做参数调整
不做总缓存区大小配置，而是设置每个块的缓冲区大小配置（默认 10MiB，`TRAINCACHE_GATEWAY_BLOCK_BUFFER_BYTES`）

补充点：owner从源站拉取数据推动游标，等待者落后超过缓冲就踢出、让它直连。这防的是慢消费者占住整个扇出（head-of-line blocking）。

使用bench装置测试实验的时候注意： 网关的并发额度必须明显高于被测的 tc 档位，也高于集群内 Agent 的合计下载并发，否则串联两个瓶颈。Agent 每进程 16 个下载任务(core/fetch 默认)，bench 的 warmup fanout 默认 2，warmup 阶段两个 Agent 合计 32 条连接；放行后落点节点若不在预热集合里再起 16 条需求读，峰值约 48。每桶默认额度 64。

## singleflight合并
按对象键合并并发请求，只在途的整对象 GET 进合并表。Agent 对不小于 `fetchRangeThresholdBytes`（默认 64MiB）的块拆成 4 条 Range GET 并行取，拼成完整块后算指纹写盘。网关收到的带 Range 请求既不查在途表也不查缓存，直接透传源站，字节不写盘。

合并只认 <dataset>/blocks/ 前缀的键，缓存也只认这个前缀。CURRENT 与 manifest 是快照指针，内容每 5s 变一次，Agent 每 5s 跟随一次，把旧快照的指针返给迟到的请求会让跟随停在旧快照上。这两类 GET 与 Put、List 一起直接转发给源站，既不进在途表也不进缓存。

关于谁来服务一个迟到的请求：

| 层 | 条件                               | 由谁服务                        |
|----|------------------------------------|-------------------------------|
| 1  | 同一 key 在途                      | 网关扇出，0 次额外回源        |
| 2  | 窗口外，但网关盘上已经有这块 | 网关读盘扇出，0 次回源        |
| 3  | 盘上没有                       | 回源，付整份字节，字节同时写进盘              |

关闭开关时第 2 行没有承接者：节点之间不传数据，同一块每个节点各付一份字节。这一行要接的量就是缓存层的收益。

## 缓存层
省的是源站出口字节。一次错峰重复读省一个整块，64MiB 块是 0.0625GiB。请求数的单价比字节低几个数量级，不为它做设计。

命中来源三条：节点本地盘被水位淘汰之后重下、新 Pod 冷启动、错峰迟到者。
节点盘没满、块还在本地盘上是零收益：同一份字节在集群里多一份，取数还多一跳。数据集大于节点盘时缓存才有收益。

#### 缓存层数：只做磁盘一层
bench 三档数据集 2GiB、8GiB、32GiB，内存装不下后两档。
内存层要接的是环形缓冲窗口关闭之后仍被重复读的块。实验块 8MiB 整块落在 10MiB 缓冲内，@100 档实测 11.95 MB/s 下窗口 0.67s，@300 档 35.6 MB/s 下 0.225s。这一段有多大，看实验的到达间隔分布再定。

#### 取数与回填
块 GET 的取数顺序：先看有没有在途条目，有就挂上去扇出；没有就查盘，命中就从盘读出来扇出；盘上也没有才回源，回源的字节一边扇出一边写进盘。
缓存里写不进字节只影响下一次命中率，请求照原路返回。

#### 缓存淘汰
配额按 dataset 定：每个 dataset 一个上限，另有一个全局总上限，两个值都进 `traincache-config`。
活跃 dataset 之间均分不做。dataset 从 2 个变 4 个时配额从 1/2 掉到 1/4，立刻淘汰掉还能用的数据，触发条件是别的 dataset 来请求，跑分时算不出这一步。QoS 那节的额度均分作用在短期占用上，一个槽几秒就还回去；缓存配额作用在长期驻写上，两条规则不同形。

落盘布局用对象键当相对路径，dataset 是第一层目录，回收单位就是这一层目录。
淘汰按三步：该 dataset 超自己的上限，删这个 dataset 里 mtime 最老的块；全局仍超总上限，删最久没出现的 dataset 整个目录；仍然放不下，本次不写盘。
每个 dataset 的最后出现时间记在进程内存的一张表里，读命中就更新。Linux 上目录 mtime 只在条目增删时变，一轮实验读 20 分钟全命中时 mtime 不动，按目录 mtime 判空闲会误删。启动时扫一遍目录 mtime 填这张表。

#### 缓存的计量
60s 汇总加一列 `cache_hit`。`merged/gets` 是在途合并的命中率，缓存命中单独一列，两列相加才是网关接住的字节占比。
错峰也能命中，扇出同时发起这个前提只约束合并那一列，不再约束整个实验。

##  流式扇出
对于大对象使用io.Pipe边拉边分发给所有等待者，禁⽌整块缓冲完再分发，否则单请求的内存占用达到整个对象大小
使用环形缓冲区： 缓冲区大小设置成较小的空间，不跟主Agent抢占内存

读盘扇出与读源站扇出是同一条流式路径，只是 owner 一侧从盘上读、不从 minio-go 的 reader 读，订阅者、游标与踢出规则都不变。

## 内存复用
缓冲区不反复分配，而是用sync.Pool复用块级buffer。
规则：
1. 池化之后稳态持有量 = 并发准入数 × 10MiB = 64 × 10MiB = 640MiB，分配一次，之后全是复用。
store.Get 的 reader 里每收一段，写进`buf[w%cap:]`（越过尾就绕回 0），推进 w，然后唤醒所有订阅者每个订阅者从自己 pos 拷走、写自己的 sink。owner 只看自己的 w，不看谁读完了。
2. 需要踢人的时候： w - sub.pos > cap(buf) 就把这个 sub 摘掉、关 kicked，它自己直连源站。
3. 归还：key 下载结束、最后一个订阅者取走或被踢，调用 `Registry.PutBuffer`。`PutBuffer` 先把缓冲放进 `hotLimit` 长度的热缓存表，表满才交给 `sync.Pool`；用 `*[]byte` 装池，避免 Get 返回值装箱逃逸一次。

注意：提交给用户的是[0, written)。复用的缓冲里留着上一个 dataset 的字节，任何「还没写满就返回」的分支都会把上一个 dataset 的字节混进本对象的响应。池不限容量，内存上限由并发准入（32）定

缓冲是按 key 生命周期归还的在途内存，缓存是按配额淘汰的盘上字节，两笔账不重叠。

## 其他决策(不做什么)
不做AIMD背压：网关把回源次数从 N 降到 1，这个降幅比已经非常大了
MinIO的P99在云S3中不好得到实时数据，MinIO 的 P99 主要由它自己的磁盘状态和 page cache 冷热决定，跟请求频率关系很弱

不做零拷贝： 只能一端到一端。网关是 1 份源字节扇出 N 路，还要给迟到者从头重放，必须有用户态环形缓冲。路径上有 TLS 就失效。

不做缓存内存层：要新建一套块级访问簿记和重启恢复语义，能接的量与在途环形缓冲重叠。
不做活跃 dataset 均分缓存配额：dataset 数一变就触发一轮淘汰。
传输压缩默认关闭：Agent 与网关各有一个开关，取值都来自 ConfigMap 的 `objstoreCompression`（默认 `"false"`），环境变量 `TRAINCACHE_OBJSTORE_COMPRESSION`。关闭时 S3 客户端设置 `DisableCompression`，不发 `Accept-Encoding`。打开后传输层协商 gzip 并自动解压，指纹仍对解压后的原始字节计算；带 Range 的请求不参与协商。训练数据在存储侧基本都是已压缩格式（JPEG/PNG/WebP/MP4、Parquet、gzip/zstd 归档），再压一遍收益接近 0；bench 的 JPEG tar 实测 0.7%，所以默认关闭。
