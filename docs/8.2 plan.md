# 日志与可观测性 · Plan

> 落地契约与字段定义见 `8.1 design.md`，选型与取舍理由见 `8.3 decisions.md`。本文回答：日志与监控还缺什么、按什么顺序补、每补完一块怎么算过关。

术语一次说清：slog 是 Go 标准库的结构化日志包，JSON 是它的一种输出格式；fluent-bit 是跑在每台节点上的日志采集器；Loki 存日志，Prometheus 存指标，Grafana 把两者画成图；kind 是用容器在本机模拟 K8s 集群的工具；DaemonSet 是 K8s 里"每台节点各跑一个副本"的部署方式。

## 1. 背景

三层（控制平面、Agent、DataLoader）各自的日志现状：

- 控制平面（controller-manager、webhook、scheduler 这些组件）：基线已经能用。slog JSON 输出、context logger（带上下文的 logger，打日志时自动附上 `request_id` 这类字段）、7.1 §9.3 规定的十六个日志点、M12 的日志断言测试（断言关键路径确实打了日志），都齐了。
- Agent：`agent/internal/logging` 已建立，`component/version/level/context` 统一注入；逐块下载与缓存命中的汇总日志、采样限流仍缺。
- DataLoader：既没有生产实现，也没有日志实现，只有已冻结的契约（8.1 §4.3）。三层贯通（同一次请求的日志能在控制平面、Agent、DataLoader 三段里串起来查）真正的断点在这里。

采集与保留这一头已经建成：fluent-bit 按 DaemonSet 把节点日志送进 Loki，Prometheus 抓指标进 Grafana；容器日志轮转（`containerLogMaxSize: 50Mi`、`containerLogMaxFiles: 3`）已写入 kind 配置。链路与标签细节见 8.1 §6。

所以现在最该补的是四件事：公共字段接线、关联 ID 贯通、采样限流、DataLoader 契约落地。日志数量本身够用，缺的是"查得到、串得起、撑得住"。

概述：控制平面能用，Agent 缺汇总日志，DataLoader 是空白，三层贯通的断点在 DataLoader。

## 2. 缺口清单

剩余缺口按四类：

- 契约缺：DataLoader 无生产实现，日志契约只停在文档里；Agent 的逐块下载/校验、缓存命中/未命中只有指标没有汇总日志（字段表本身已冻结）。
- 关联缺：控制平面的 `request_id`（一次请求的追踪编号）目前不出进程；Agent 没有 `request_id`；钩子帧（训练进程发给 Agent 的通知消息）不带任务身份。同一次任务在三处留下的日志对不上号。
- 保护缺：采样（按比例丢）和限流（超速率丢）未实现，Debug 一开逐块、逐帧都打日志，量可以打满节点磁盘；脱敏函数已有，controller 与 Agent 的调用点还没接上，日志里的凭证还没有代码级保证。
- 消费缺：告警规则与三层看板还没有，出问题只能人肉查。

概述：四个未通——契约、关联、保护、消费；采集与保留已建成。

## 3. 落地清单（P0 -> P3）

P0 到 P3 是优先级，P0 最急。各阶段做什么是范围，验收是过关判据；已完成部分的事实见 8.1 §2。

| 阶段           | 内容                                                                                                                                                                                  | 验收标准                                                                                                                                 |
|----------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------|
| P0 契约与字段补齐 | 冻结 8.1 §3.1 字段表和 §3.2 级别约定；`agentd` 统一 `err`；脱敏函数（把 Secret 这类敏感值抹掉）配哨兵测试（故意打一个假 Secret，断言它不出现在任何日志里）；DataLoader 日志契约成文 | 7.1 §9.3 十六点逐行有测试；`go test ./controller/... ./agent/svc/...` 全绿；哨兵 Secret 在全部日志中零出现；同一事件字段名唯一           |
| P1 采集链路    | fluent-bit 节点采集 DaemonSet；Loki 3.6.9 + Grafana 12.4.13；Loki 标签固定六个（`cluster/namespace/component/level/node/stream`）与保留期（默认 720h，`level="DEBUG"` 流 168h，`retention_stream`）；Prometheus 单实例按 15s 抓取 controller-manager(:9412)、agentd(:9411)、webhook、scheduler 的 `/metrics`，覆盖 `traincache` 与 `kube-system`；Grafana 接入 Loki 与 Prometheus 两个数据源；容器日志轮转（kind KubeletConfiguration patch：`containerLogMaxSize: 50Mi`、`containerLogMaxFiles: 3`，下次 `kind create cluster` 生效）；observability 独立 kustomize 根与 `controller/e2e/observability.sh` | 任一节点 `kubectl logs` 为合法 JSON；Loki 能按 `namespace/component/node` 查询；标签基数在预算内（恰为六个有界维度）；节点故障前日志已入中心；Prometheus 各 target 为 up；Grafana 两个数据源均可查询；`controller/e2e/observability.sh verify` 通过 |
| P2 DataLoader 与关联 ID | DataLoader 库写入上下文与分位日志；webhook 注入 env；钩子帧增量字段；Controller 注入 gRPC metadata（gRPC 请求自带的键值对，用来跨进程传数据）；Agent 拦截器（gRPC 请求的统一入口钩子）建 context logger 并生成/继承 `request_id`；采样限流落地 | 给定 `warmup_task + pod_index` 能一次查出 controller -> Agent -> DataLoader 三段；钩子缺字段时旧路径不回归；采样开启后 Warn/Error 零丢失 |
| P3 告警与看板  | 门控 Hold 超时、Agent 不可达、读 stall 超阈值、磁盘危险线、日志采集断流；Grafana 三层看板；runbook（故障处置手册）链接                                                               | 每条告警有对应指标与 runbook；预发环境注入故障可触发并恢复；看板覆盖控制平面、Agent、DataLoader 三层                                     |

概述：P0 定契约、P1 通链路、P2 串三层、P3 能告警。四步走完，日志从"有日志"变成"可观测"。

> 字段编号沿用 `8.1 design.md` §3.1 / §3.2；runbook 见 `8.1 design.md` 附录 A。
