## 1. 实验目的与判据

阶段0 第一部分的目的是用最小装置证明**实验方法论成立**:装置能造出可信的冷热差异(探针A)、stall 指标能被打出来(探针B)。三个月后才发现装置不可信,成本是整个项目重来,所以先用 2-3 天验证。任一红灯,停止开工,修装置,不碰 kind、不碰 Fluid。

**绿灯标准(文档原文)**:

- 探针A:① 冷/热中位延迟差 ≥5×(或中位吞吐差一个数量级);② 两组 bootstrap 95% CI 不重叠;③ 组内变异系数 CV ≤ 15%。冷/热各 ≥7 次取中位数。
- 探针B:① 冷态 stall 占比稳定 >40%;② 热态 stall 占比 <15%;③ 增加 workers 冷态 stall 单调下降。

## 2. 装置与执行:每一步在干什么

### 2.1 总览

数据流两用:同一批 tar 分片同时服务探针A(字节吞吐)与探针B(解码+打点),避免两套数据带来的差异解释负担。

### 2.2 步骤1:合成 2GB 训练数据(`setup/01_synth_data.py`)

**干什么**:生成 16 个 webdataset 风格 tar 分片,每个含 800 张 512×512 JPEG(约 126MB/tar,合计 1.97GiB)。文档指出 2026 年训练数据主流是"百 MB 分片 + 确定性 shuffle 流式读取",装置数据按此形态构造。

**合成图为什么不是纯色块**:纯色块会被 JPEG 过度压缩(体积失真、解码成本失真)。每张图 = 双色渐变底 + 随机圆形/矩形 + 高斯噪声,噪声强度 σ 自动校准到目标体积 ~160KB/张(实测校准到 σ 后单张 158KB)。全部随机源由固定种子(20261006)派生,重跑得到逐字节一致的数据,结果可完全复现。

**执行中的问题与修复**:首跑因 numpy `RandomState` 种子超过 2³² 上限报错,修复为取模后重跑成功(合成耗时约 6 分钟)。

### 2.3 步骤2:源站(`setup/02_source_up.sh`)

**干什么**:起一个"远程数据源"容器,以 HTTP 字节流提供 tar 分片(公开读,无签名逻辑)。原设计为容器 MinIO(文档层3 指定:kind 集群里用 MinIO 模拟 S3/OSS)。

**降级实录**:MinIO 镜像在所有可达镜像源均拉取失败——docker hub 直连超时(网络受限,已知)、玄源加速站(回源失败)、DaoCloud(denied)、1ms.run 与 hub.rat.dev(manifest not found)、1panel(denied)、quay.io(unauthorized)、阿里云(仓库不存在)。降级为本地已有的 `nginx:latest` 镜像做静态文件服务,tar 目录只读挂载到 URL 前缀目录下。

**为什么读路径语义等价**:探针中 MinIO 只承担"远程 HTTP 字节流源"角色(公开读、http 直取,不用 S3 API)。nginx 静态服务在该读路径上与 MinIO 公开读行为一致(HTTP GET 字节流);URL 结构 `/train-data/shard-*.tar` 与 MinIO bucket 前缀一致,下游脚本完全复用。**kind 现勘阶段仍按文档部署真 MinIO**(届时另解镜像)。

### 2.4 步骤3:tc 限速(`probe_a/tc_setup.sh`)—— 本次执行的核心踩坑

**干什么**:在下载路径上制造"远端网络"的真实代价:tbf 令牌桶整形到 100mbit(12.5MB/s)+ netem 20ms 时延,与文档装置一致(burst≈1s 令牌量)。

**三次踩坑的完整实证过程**(这是本次执行最有价值的发现,已写入 `design.md` 与长期备忘):

1. **挂 docker0 主设备 → 无效**。首轮冷读 3.5 秒跑完 2GB(565MB/s),而 tc 计数只涨 12MB。排查确认:Linux bridge 的二层转发(br_dev_xmit → veth)不经过桥主设备(docker0)的 egress qdisc。
2. **挂 veth host 侧 root(egress)→ 无效**。tcpdump 实证数据包确实经过 veth,但 tc 计数不动。原因是下载的数据方向是 容器→host(nginx 发出响应),在 host 侧 veth 上是 **ingress** 方向,egress qdisc 管不到。排查中另有收获:veth 匹配不能用 ethtool peer_ifindex(不同 netns 里 ifindex 都是 2,会误匹配到别的容器),要用 `ip -o link show master docker0` 的从属关系。
3. **挂容器 netns 内 eth0 的 egress(源站出站方向)→ 生效**。验证:下载 132MB 实测 11.04s(≈12MB/s),tc 计数涨 138MB,overlimits 计数在涨(整形器在工作)。

**意义**:这个坑花掉了执行中相当一部分时间,但它在 kind 现勘阶段(对训练 Pod/Agent 做网络波动实验)会再次出现,现在把它实锤并写成可复用脚本是值得的。

### 2.5 步骤4/5:冷读与热读(`run_cold.sh` / `run_hot.sh` / `fetch.py`)

**冷读定义**(每轮):`rm -rf` Agent 缓存目录 → `sync` → `echo 3 > /proc/sys/vm/drop_caches`(清全 host 的 page cache,含源站容器进程的,杜绝"假冷读")→ 走 tc 从源站下载 16 个 tar 到缓存目录。`fetch.py` 模拟层2 Agent 的三条抓取指令中的"有界并发"(线程池并发 4、按分片下载、落本地缓存目录)。共 7 轮。

**热读定义**(每轮):数据已在缓存目录,顺序直读文件(模拟训练 Pod 的 hostPath 读路径),不 drop_caches(真实训练里"热"含 OS page cache)。每轮并行采样 9000 端口 established 连接数做零网络验证。共 7 轮。

**执行中的问题**:首轮冷读因 tc 挂点错误跑出 565MB/s 的作废数据,已在 §2.4 修复后清空重跑;另有一次 results 目录因 root 创建导致普通用户无法写入,chown 后解决,并在 `run.sh` 里加了提示。

### 2.6 步骤6:探针A 判定(`probe_a/judge.py`)

**干什么**:读 7+7 轮原始 JSON,计算中位耗时/吞吐、百分位 bootstrap 95% CI(2000 次重采样)、组内 CV,按三条绿灯判据输出。

### 2.7 步骤7/8:探针B 装置与判定(`probe_b/train.py` / `run.sh` / `judge.py`)

**打点口径(主进程视角)**:每步 `t0`=上一步计算结束 → `next(batch)` 到手 `t1` → compute 完成 `t2`。`wait=t1-t0`(DataLoader 等待数据的时间),`step=t2-t0`,`stall=wait/step`。解码在 worker 进程并行(workers>0 时),主进程 wait 只含排队与管线补货——这是文档要求"真 JPEG(真实解码成本)"的意义。

**装置**:webdataset 流式读 tar;冷态从 `http://127.0.0.1:9000/...`(经 tc),热态读本地 tar 目录;workers 0/4/8 三档 × 冷热 = 六组,每组 60 步(warmup 10 步不计);compute = 单线程 1024² matmul × 8(校准后,见下);batch=32(≈5MB/批)。

**compute 量级的两次校准(如实记录)**:

1. 首跑发现 1024² matmul 被多核 BLAS 跑成 ~3ms,stall 对 wait 的微小变化极敏感(热态 wait 0.6ms 与 13ms 的差异就把 stall 从 17% 推到 81%),装置判别力差。限单线程后 ~25ms,热态仍 ~35%,压不到 15%。
2. 改为单线程 ×8 次 ≈200ms/步。这是"模拟真实 step 的 compute 量级"与"判据灵敏度"之间的落点——相对真实模型仍是"极小矩阵乘"(文档允许),同时让 stall 有判别力。

**判定口径与实测机制的对应**(详述见 §4.2):条件1 判 w0 无管线档(冷态),条件2 判 w4/w8 至少一档(热态),条件3 按 mean 口径(时间加权)判单调。口径依据全部来自本次实测的 wait 结构数据,非预设。

## 4. 结果分析

### 4.1 探针A:冷热差是稳定、可复现、且悬殊的

- **817× 的差距远超 5× 判据**。冷读被 tbf 整形钉在 11.4MB/s(100mbit 理论值 12.5MB/s 扣除 20ms 时延与 TCP 开销后的实际值);热读是 NVMe page cache 直读(~9.3GB/s)。
- **冷读 7 轮极差只有 46ms(CV≈0)**。原因:tbf 令牌桶整形是确定性的——每轮数据量相同(2GB)、限速器状态在每轮间被 drop_caches 与固定起始条件重置,波动只来自 TCP 慢启动的微小差异。热读 CV 0.4% 同样稳定。两组 CI 自然不重叠。
- **红灯排查清单逐条验证过**:tc 计数在涨(overlimits 24959)、热读零网络(连接峰值 0)、盘不是瓶颈(9.3GB/s 远高于限速)、无假冷读(每轮 drop_caches 全清)。

**结论:装置能造出可信的冷热差异,且重复测量高度稳定。**

### 4.2 探针B:stall 指标打得出,且数据揭示了三个机制

**机制1:无管线档(w0)直接暴露数据源速度。** 冷 w0 每步 wait 318ms(网络下载 5MB/批 + 主进程内解码),stall 71.7%——数据加载确实是瓶颈;热 w0 wait 177ms(只剩本地读+解码),stall 58.1% 仍高,因为解码发生在主进程(w0 无并行管线),这是装置结构使然,真实训练必开 workers,故条件1/2 分别按无管线/有管线档判定。

**机制2:管线化后,冷热差异转移到 wait 尾部。** w4/w8 的中位 wait 都落在 ~12-14ms 的 DataLoader 基座上(预取队列缓冲抹平数据源差异),但冷态的 p90 wait 是 ~0.9-1.0s(每 4-8 批撞一次 100mbit 共享带宽的网络排队),热态 p90 只有 ~13ms(本地读无排队)。这是"块级就绪度"问题在数据加载上的第一个可见签名:共享瓶颈会把等待集中成周期性的长尾。

**机制3:条件③的单调下降是真实 I/O 饥饿的证据。** mean 口径下 70.4% → 27.3% → 17.6%:w0→w4 的大降来自管线并行化(真实 I/O 等待被预取吸收),w4→w8 的缓降来自带宽已饱和(共享 100mbit,加 worker 不再加速)——这正是文档要求的"证明测到的是真实 I/O 饥饿,而非打点噪声"的签名:如果是打点噪声,w0→w4 应该不变。

### 4.3 装置 artifact 与真实机制的区分(诚实性说明)

- ~12-14ms 的 DataLoader 基座 wait 是本装置的固定开销(多 worker 队列与批次传递),不是数据源属性;它决定热态 stall 的"地板"约为 wait/(wait+compute)。compute 200ms 校准后地板 ≈6%。
- compute 量级是装置参数而非测量对象:3ms 时装置失去判别力,200ms 是"极小 compute 替身"与判据灵敏度之间的落点。换机器/换数据时需按 design.md 旋钮重新校准。
- 合成 JPEG 的像素内容不真实(解码成本真实);对 stall 打点无影响,现勘阶段如需与公开基线对齐可换数据源而不动装置骨架。

### 4.4 源站降级对结论的影响

MinIO→nginx 降级改变了"对象存储语义"(S3 API、元数据层),但探针只测量 HTTP 字节流读路径上的冷热差与 stall,该路径两者等价。此项差异如实记录,kind 现勘阶段将以真 MinIO 部署复核(届时镜像问题需另行解决)。

## 5. 闸门结论与下一步

**A/B 双绿灯,方法论成立,按闸门制进入阶段0 第二部分(现勘)**。

现勘阶段可直接复用的装置资产与经验:

1. **tc 限速经验**(已写入脚本与长期备忘):容器流量限速挂容器 netns 内 eth0 egress;veth 匹配用 bridge 从属关系;kind 里对 Pod/Agent 做网络波动实验时同样适用。
2. **数据合成管线**:种子固定,2GB 数据 6 分钟可复现;现勘的 JuiceFS/Fluid 对照组可直接用同一批 tar。
3. **stall 打点装置**:主进程 wait/step 口径 + compute 校准流程,可直接搬到 kind 里的真实训练 Pod。
4. **待解决事项**:MinIO 镜像的获取(现勘部署必须)、kind ≥1.26 集群搭建。

## 6. 探针C:多 epoch 全程 stall 存在性(2026-10-13 增补)

### 6.1 目的与判据

**目的**:证明"全程 data stall 真实存在"——连续多 epoch 训练循环中,stall 在每个 epoch 内持续存在、epoch 切换后回升,而不是只出现在启动预热的一次性瞬态。若 stall 仅是启动瞬态,"缓存收益"叙事将收缩;本探针的绿灯/红灯直接决定该叙事是否成立(红灯按实报,不作装置外解释)。

## 7. D 轨勘测:多 epoch 欠配场景的 stall 重复形态(2026-10-13 增补)

### 7.1 目的与判据

**目的**:为 v4"全程收益"提供专用场景数据——单 Job 连续 **10 个 epoch**、每 epoch 换 seed 重排读取顺序、缓存只能覆盖一半工作集(**欠配 50%**:源站侧容器 cgroup 限 1GiB = 2GB 数据集的 50%)。测量对象:欠配下 stall 是否**逐 epoch 重复出现**(重复形态);数据口径移交 bench 阶段(见 §7.5)。

**判据**:

- **前置门(欠配真实生效)**:内存采样中源站容器 file(缓存)峰值 ≥0.9×1GiB,且 memory.current 全程 ≤ 上限、无 OOM kill/breach;不满足判"**无效**"而非红灯(数据不用于红/绿判定)。
- **绿灯判据①(形态重复)**:每 epoch 400 步切 20 步窗口(20 窗/epoch,值=窗口内 stall 均值)→ 长度 20 的逐 epoch 曲线;对 epoch 1..9 的 8 个相邻对算 Pearson r,要求 **≥6 对 r≥0.5**。
- **绿灯判据②(幅度稳定)**:epoch 2..9 逐 epoch 中位 stall 的 **CV ≤30%**。
- **报告项③(不参与绿/红)**:epoch0 中位 stall 与 epoch1..9 中位 stall 中位数的比值(旧阈值 >1.2)。**降级裁决理由(主对话,2026-10-13)**:恒定 tc 限速(100mbit+20ms)下链路瓶颈掩盖 epoch0 冷态差异(实测比值 0.99,低于旧阈值),与探针B 已确立机制一致——w4 冷态签名只在 wait 尾部、中位 stall 对冷态不敏感;故仅报告数值,并补记"epoch1 首窗切换峰值"作为切换瞬间冷读集中的证据。
- 绿灯 = 前置门 + 判据①②全满足(verdict 记"重复形态确认");否则红灯照实报,不作装置外解释。

**移交 bench 阶段的口径说明**:

1. `track_d_windows.json` 是 bench 阶段欠配场景的**对照基线**(10 epoch × 20 窗口的 stall 曲线;窗口=20 步、值为窗口内 stall 均值、epoch0 前 10 步 warmup 不计入、余数步不在窗口内)——bench 装置若复现同构场景,可与该曲线逐窗对齐;
2. per_step 全量留档 `track_d_w4.json`(4000 步)支持更细粒度复核;判定脚本 `judge_track_d.py` 的判据参数(≥6/8 对 r≥0.5、CV≤30%)已 CLI 化,bench 阶段更换数据/容量后可直接重跑;
3. 装置限制(如实):恒定 tc 限速掩盖 epoch0 中位级冷态差异(与探针B 机制一致),epoch0 证据只在尾/首窗维度;内存限制以 128GiB 等效记档(容器未重建)。

## 8. 消费顺序探针:OrderSource 输入可得性(2026-10-13 增补)

### 8.1 验证点

验证"消费顺序是否由可复现的输入元组决定"(即 OrderSource 的现实输入 =(分片列表, seed, epoch) 是否可构造),7 个验证点:

1. 分片顺序(`shardshuffle=False` + 显式 URL 列表);
2. 分片置换(同 (seed, epoch) 确定性,三条实现路径);
3. 样本级洗牌(`.shuffle(bufsize, seed=S)` 的确定性与有效种子);
4. `shardshuffle=True` 的 seed 通道(有 seed 注入点?缺省是否确定);
5. PyTorch `RandomSampler(generator=...)`;
6. PyTorch `DistributedSampler(seed)+set_epoch(e)`;
7. 端到端重建:仅凭 (分片列表, seed, epoch) 复现消费序列。

### 8.2 装置

`probes/probe_d/`:`verify_wds.py`(点1-4,webdataset 1.0.2)、`verify_torch.py`(点5-6,torch 2.14.1+cpu)、`reconstruct.py`(点7,不经框架、仅凭 tar 文件名 + 源码语义的独立复现)、`judge.py`(按序跑三脚本并汇总)。全部**单进程(num_workers=0)**;数据用合成 16 分片;总耗时 6.63s;输出 `wds_results.json`/`torch_results.json`/`reconstruct_results.json`/`verdict.json`。

### 8.3 结果(7/7 通过)

| # | 验证点 | 判据/断言 | 结果 |
|---|---|---|---|
| 1 | 分片顺序 | `shardshuffle=False` + 显式 URL 列表:一 pass 内消费分片序=列表序(16×800=12800 样本);置换列表后跟随 | 过(断言)|
| 2 | 分片置换 | 同 (seed, epoch) 逐位相同、异 seed/epoch 不同;`SimpleShardList` / `MultiShardSample.set_epoch`+`get_shards_for_epoch` / `filters.detshuffle` 三路径 | 过(断言)|
| 3 | 样本级洗牌 | `.shuffle(100, seed=S)` 同 S 复跑 400 步 `__key__` 逐位相同、异 S 不同;**有效种子 = S 本身**(无 epoch 项) | 过(断言)|
| 4 | `shardshuffle=True` 的 seed 通道 | 1.0.2 有注入点(`seed=` 参数 / `WDS_SEED` 环境变量);缺省走 `random.randint(0,1e6)` → **非确定**;无 seed 的是 `FluidInterface.shuffle(size)` | 过(记录)|
| 5 | RandomSampler | `generator=torch.Generator().manual_seed(S)`:同 seed 索引序列逐位相同;generator **有状态**,不重建复跑第二次序列不同 | 过(断言)|
| 6 | DistributedSampler | `(seed, epoch, world_size, rank)` 固定则序列确定(world_size=1 覆盖全数据集) | 过(断言)|
| 7 | 端到端重建 | 仅凭 (16 分片列表, seed, epoch) 复现分片置换与全量 12800 样本消费序列,与框架采集逐位一致(3 个 epoch) | 过(断言)|

### 8.4 结论

- **OrderSource 输入可构造**:分片置换(`detshuffle`/`SimpleShardList`/`MultiShardSample` 三选一)+ 样本级洗牌(`.shuffle(buffer, seed)`)都由 (分片列表, seed, epoch) 决定;`reconstruct.py` 仅凭该三元组 + tar 文件名(不经框架运行)即复现 400 步消费序列,与框架采集逐位一致。
- **实测 seed 语义(如实记录)**:(a) `.shuffle(100, seed=S)` 无 epoch 项——同 S 的所有轮次序列完全相同,OrderSource 若要求样本级顺序随 epoch 变化,须把 epoch 显式混入 seed;(b) `detshuffle` 的有效种子 = S + epoch(首迭 = S+0、第 k 次 run 的 epoch=k-1),任务书所述"首迭有效种子 = S+1"在本安装(1.0.2)未复现;(c) `shardshuffle=True` 缺省 seed 非确定,须显式注入 `seed=` 或 `WDS_SEED` 才可复现;(d) `RandomSampler` 的显式 generator 有状态,复用同一对象不重建会得到不同序列,必须每 epoch 重建/重播种。
- **局限(明确留待 bench)**:`num_workers>0` 时 worker 切分模型(`split_by_worker` 交错)与到达时序语义未覆盖——主进程看到的顺序取决于 prefetch/worker 时序,重建需另加 worker 切分模型;该差异作为 bench 阶段的输入假设记录。
