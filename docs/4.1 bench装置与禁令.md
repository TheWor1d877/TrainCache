# bench 装置与禁令

## 1. 装置构成

32 核 / 30 GiB 的宿主机上跑 kind 集群 `traincache`：1 个 control-plane + 4 个 worker。tc 挂在 MinIO 的出站路径上（D 轨挂本地源站 `traincache-source-d`），把回源带宽限到档位值；本地缓存命中绕开这条路，于是同一次读在两个组态下走出完全不同的耗时。有效带宽 = min(名义 rate, 源站实测上限 674 MB/s)。

带宽是实验自变量，rate 取 100 / 300 / 1000 mbit，burst 按 rate 推导（100→1250k、300→3750k、1000→12500k）。netem 只挂固定 `delay 20ms`，不加随机抖动：逐包重抽时延会把包序打乱，300mbit 档实测吞吐从 35.6 MB/s（95% 线速）掉到 0.6 MB/s 以下，档位差异被装置掩盖。

四轨数据都用固定种子生成，逐字节可复现：

| 轨 | 内容 | 规模 |
|---|---|---|
| A | 小文件元数据 | 100 万 × 4KB，100 个子目录 |
| B | webdataset tar 分片 | 32 个 tars，约 256MB/个；MinIO 桶 `bench-b` 现有 128 个对象，够 L 档取用 |
| C | 倾斜访问清单 | 热分片占 10%，复用 B 轨数据 |
| D | 连续 epoch 负载 | 16 × 约 128MB ≈ 2GiB，落宿主机本地源，不上传 MinIO |

档位一次决定数据规模、epoch 数、每点次数与本档参跑组：

| 档 | 数据 | epoch | 每点次数 | 参跑组 |
|---|---|---|---|---|
| S | 8 × 256MiB = 2GiB | 3 | 3 | 七组态 |
| M | 32 × 256MiB = 8GiB | 1 | 3 | direct、fluid-cold、traincache-cold |
| L | 128 × 256MiB = 32GiB | 1 | 1 | traincache-cold、fluid-cold（产物标 `exploratory`） |

七组态 = direct、juicefs-cold/warm、fluid-cold/warm、traincache-cold/warm，合计四个装置目录。每组只有一个训练 Pod（`train-job-0`），测量体与调度体合一；`t_submit` 取创建该 Pod 之前的时刻，七组态同尺。

```text
bench/
├── Makefile          # 装置起停、自检、D 轨、quick
├── config.py         # 唯一参数源：python3 config.py --sh KEY
├── scripts/          # 造数、tc、冷态、verify、上传、trainpublish
├── k8s/              # kind 集群配置与 MinIO 清单
├── compare/          # 七组态装置、run_bench.py、汇总
├── exp.py            # 实验族统一入口
└── experiments/      # COND 契约、COND 集、统计、lock、出图
```

## 2. 文件作用

### 2.1 TrainCache 侧

| 文件 | 作用 |
|---|---|
| `scripts/ctrl_up.sh` / `ctrl_down.sh` | 控制面与 agentd 起停。up 建命名空间与两个 Secret、注入 webhook caBundle、apply `controller/deploy`、等五个工作负载就绪（开网关时含网关）；清单哈希记在命名空间注解，未变化时不 apply、不滚动重启 |
| `scripts/trainpublish` | 发布 TrainCache 块快照。Go 二进制，源码在 `core/cmd/trainpublish`；`-chunk-size 8388608`，`-work-dir` 必须放数据层（`/tmp` 是 16 GiB tmpfs，全量发布会写爆） |
| `compare/traincache/up.sh` | traincache 组四步：打节点标签、发布快照、起控制面、写 `traincache-config` 并建 DataSet/WarmupTask，最后挂 tc。cold 以 `TRAINCACHE_WARMUP_K=0` 跳过 WarmupTask |
| `compare/run_bench.py` | 跑分编排器，所有实验的底层执行体。决定档位、组态、rep 次数与产物列；`--selftest` 离线自检模板与字节账 |
| `experiments/cond.py` + `conds/*.json` | COND 契约 v1：一个 JSON = 一个实验点，校验字段并翻译成环境变量 |
| `exp.py` | 实验族统一入口：列完成度、按族跑分、回填 4.6 的最后一行 |
| `experiments/lock.py` | 每个 run 目录落一份 `lock.json`：镜像 digest、kubectl 版本、tc 档位、块大小、种子 |
| `experiments/collect.py` / `stats.py` / `plot.py` | 离线汇总出 `metrics.csv`、bootstrap 置信区间与六个出图族的 PNG |
| `compare/summarize.py` | 七组态对照的汇总与判定：14 个指标分档列均值与 CI，组间差值判 5% |

### 2.2 非 TrainCache 侧

| 文件 | 作用 |
|---|---|
| `scripts/synth_track_{a,b,c,d}.py` | 四轨数据生成，参数全在 `config.py`，已存在即跳过 |
| `scripts/bench_track_d.py` | D 轨负载器与 verify 判据；模块级依赖 numpy / torch / webdataset |
| `scripts/tc_apply.sh` / `tc_teardown.sh` | 挂拆限速。`<rate> <delay> [burst] [--target minio\|source-d] [--dry-run] [--self-test]`，burst 不给时按 rate 推导 |
| `scripts/cold_reset.sh` | 主实验冷态：sync + drop_caches + 重启 MinIO + 重挂 tc。对照层不用它，用 `run_bench.py` 自带的 `cold_reset()` |
| `scripts/verify_cold.sh` | 装置可信性：两轮冷读相对差 ≤10% |
| `scripts/upload_bench.py` | B 轨灌 MinIO，只追加不覆盖；`UPLOAD_FORCE=1` 才重传 |
| `compare/direct/` | 组 1：HTTP 直读 MinIO，零缓存 |
| `compare/juicefs/` | 组 2/3：JuiceFS 冷热，缓存走节点 hostPath `/var/cache/jfs` |
| `compare/fluid/` | 组 4/5：Fluid 冷热，tieredstore 走 `/tmp/juicefs-cache` |
| `compare/trace.py` | 按 (分片数, shuffle, epochs) 生成统一请求轨迹并算 sha256 |
| `k8s/kind-config.yaml`、`k8s/minio.yaml` | kind 5 节点配置与源站基座。MinIO 带 30Gi PVC，`kind delete` 后源数据仍在宿主机；metrics 端点匿名只读，端口 30090 |

## 3. 参数总表

| 旋钮 | 现值 | 写在哪 | 影响 |
|---|---|---|---|
| `--rate` / `TC_DELAY` | 100 / 300 / 1000 mbit，delay 20ms | `run_bench.py --rate` 与环境变量 `TC_RATE`/`TC_DELAY` 下发给 up.sh；`make bench-tc` 走同一套 `tc_apply` | 回源管道粗细 |
| `TC_BURST` | 按 rate 推导 | `config.burst_for_rate()`；`tc_apply.sh` 自己算；四个 up.sh 只传 rate 与 delay | 突发窗口必须跟着 rate 走 |
| `TRACK_B_N_TARS` | 32（约 8GiB） | `config.py` | 源数据生成规模 |
| `--tier` / `CAPACITY_RATIO` | S | `run_bench.py` 旗标 / 环境变量；档位常量在 `experiments/cond.py` 的 `CAPACITY_TIER_*` | 一次决定 `N_TARS`、`EPOCHS`、每点次数与本档参跑组；非法值退回 S 并告警 |
| `N_TARS` | S=8、M=32、L=128 | `run_bench.py` 环境变量，缺省按档位取 | 每组读的分片数；快照覆盖全部 128 片，档位只收窄轨迹消费范围 |
| `-chunk-size` | 8MiB（生产默认 64MiB） | 空桶首次发布 `trainpublish -chunk-size 8388608`，写入 `bench-b/_traincache/format.json` | 缓存与预取的最小单位；1GiB 缓存 = 128 块。桶里已有声明后该参数不再生效 |
| `cacheCapacityBytes` | 缺省 1GiB（`1073741824`） | `ctrl_up.sh` 与 `run_bench.py` 各自对齐 `traincache-config`；值变化时重启 controller-manager | Agent 按它触发淘汰，Controller 按它算自动 K 的 `K_cache` |
| `startupWindowBytes` / `maxFillFraction` | 512MiB / 0.125 | `ctrl_up.sh` 的 `ensure_agent_config`；Controller 读 `TRAINCACHE_STARTUP_WINDOW_BYTES` / `TRAINCACHE_MAX_FILL_FRACTION` | 自动 K 的两个输入：`K_window = ceil(窗口 / chunkSize)`，`K_cache = floor(容量 × maxFillFraction / (Pod 数 × chunkSize))` |
| `TRAINCACHE_WARMUP_K` | warm=128，cold=0（哨兵） | `run_bench.py` → `traincache/up.sh` → WarmupTask `podDetails[0].k` | 预热量 = k × chunk-size × fanout；只覆盖数据集开头 1GiB。cold 的 0 不写进 CRD，创建前跳过 WarmupTask |
| `TRAINCACHE_PREHEAT_FANOUT` | 2 | `run_bench.py` → `traincache/up.sh` 的 `preheatFanout` | 每个 Pod 的预热节点数上限 |
| `TRAINCACHE_PREFETCH_LOOKAHEAD` | 对照 16；pareto-sustained 8/16/32 | `traincache-config` 的 `prefetchLookahead`：`run_bench.py` 起跑前写一次，`ctrl_up.sh` 在 `apply -k` 之后按同名环境变量再对齐一次并滚动重启 agentd | Agent 侧持续预取窗口，与训练侧消费窗口互不联动。只写前一次会被 apply 盖回清单默认 16，扫点就没有自变量（4.4 §C4 字段与消费方对照） |
| `TRAINCACHE_PREFETCH_K` | 16 | 测量 Pod 的消费窗口 | 训练侧消费深度 |
| `TRAINCACHE_EVICT_POLICY` | heat / lru / lfu | `traincache-config` 的 `evictPolicy`，DaemonSet 用 `configMapKeyRef` 注入；非法名拒绝启动；对齐时机与上一行相同 | 淘汰策略；对照实验一律 heat，4.4 §5.3 淘汰矩阵按它取 heat/lru/lfu |
| `TRAINCACHE_GATEWAY` / `GATEWAY_PORT` | 0（关）/ 1（开）；9413 | `ctrl_up.sh` 按开关写 `traincache-config` 的 `gatewayEndpoint`、把 `deployment/traincache-gateway` 缩到 0/1 副本；`run_bench.py` 透传给 `traincache/up.sh`，每行 `summary.csv` 落 `gateway` 列 | 合并回源网关总开关，只影响 traincache 组的块 GET 路径，direct/juicefs/fluid 不读网关；开关口径见 4.3 §3.1 |
| `COMPUTE_MS` / `READ_WORKERS` / `READ_QUEUE_DEPTH` / `READ_TIMEOUT_S` | 200 / 2 / 2 / 300 | `run_bench.py` 下发进 measure 模板 | 每步计算的墙钟预算（每步跑满 200ms，决定 stall_ratio 有没有判别力）与异步预取队列深度 |
| `TRAINCACHE_TILT` / `TILT_STAGGER_S` / `TILT_SEED` / `TILT_A_STEPS` | 1 / 5s / 20261015 / `EPOCHS × STEPS_PER_EPOCH`（C 轨 1200） | `run_policy.py`、`exp.py` 置 `TRAINCACHE_TILT=1`；其余三个由 `run_bench.py` 的 TILT 分支读自身环境再下发进测量 Pod | C 轨倾斜双 Job：B 的延迟启动秒数、A 的热分片乱序种子、A 的步预算（常量，完成步数是响应变量；挤占计数口径同见 4.4 §C3） |
| `JFS_CACHE_MB` / `FLUID_CACHE_GI` | 1024 MiB / 1 Gi | juicefs / fluid 的 `up.sh` | 两类对照组的缓存上限，与 1GiB 对齐 |
| `datasetMetricsWhitelist` / `TRAINCACHE_OBJSTORE_BUCKET` | compare-data-8m / bench-b | `traincache-config` ConfigMap 与 agentd 环境变量 | 白名单只控制指标 `dataset` 标签；桶决定 Agent 读哪个 MinIO 桶 |

## 4. 数据与产物落点

数据与产物一律落在 `~/tcd/`（等于 `~/Project/TrainCache/traincachedata`），repo 内只存脚本与清单，不放软链接。

| 层 | 路径 | 装什么 |
|---|---|---|
| 容器层 | `~/Project/TrainCache/` | 空壳，隔开上下两层 |
| 代码层 | `~/Project/TrainCache/traincache/` | 源码、脚本、清单、docs、`.git` |
| 数据层 | `~/Project/TrainCache/traincachedata/` | 四轨数据、运行结果、探针结论 |

```text
~/tcd/bench/results/
├── scores/<格>/              # 七组态对照跑分：summary.csv、version、runs/、lock.json；格名如 S-100、M-1000
├── baselines/<格>/           # 非 TrainCache 组的历史基线，只读，汇总层按组态补入
├── figures/<点>/             # 曲面与启动字节族逐点产物，目录名是完整 COND 名（fig1-*、fig2-*、fig3-*、pareto1-*）
├── policy/<点>/<run>/        # 倾斜两族产物，每次运行一个 run 子目录（pareto2-*、policy-*）
├── summary/                  # 汇总视图：baseline.md/csv、verdict.csv
├── track_d/                  # D 轨负载与扫点
├── quick/<run_id>/           # 新版本自跑，首次 bench-quick 后出现
└── cold-verify.txt           # 冷读可信性
```

族到分区的对应表在 `bench/exp.py` 的 `results_root()`，分区路径常量在 `bench/config.py:21-24`。

每个点目录下的 `runs/<组态>-r<NN>/` 装 `run.json` 与逐步打点：单线程形态一份 `per_step_1_w1.jsonl`，`track=C` 倾斜双 Job 两份 `per_step_a.jsonl`/`per_step_b.jsonl`（字段见 4.4 §C3 末段）。切换回落判据只读单线程形态。

数据层留在家目录之外，起因是 inotify 配额按 UID 计算：百万级数据文件放在 repo 内会吃光整个 UID 的 watch 预算，之后任何程序调 `inotify_add_watch` 都返回 `No space left on device`。搬出 repo 后整个 UID 只用 1.9% 的配额。

## 5. 禁令

1. 不删 MinIO `bench-b/shard-*.tar` 与旧 `bench-b/compare-data/` 快照。前者是五组共同源数据，后者保留供历史产物复现。
2. 不执行 `kind delete`。清理脚本只拆控制面与工作负载，kind 集群与 MinIO PVC 一律保留。
3. 不删 `~/tcd/bench/data/` 与 `~/tcd/probes/results/`。四轨数据重生成很贵，探针结论是常量口径的出处。
4. `results/` 下的产物只追加：不覆盖、不删、不改历史行，void 行也保留。`baselines/` 只读。
5. `bench/.sudo-pass` 的内容不出现在文档、日志、提交与回复里。
6. 跑分期间不执行 `bench-up` 或 `ctrl-up`。清单一变就滚动重启 agentd，正在跑的任务中断，该轮作废。
7. 手工重启 MinIO 后必须重挂 tc。不重挂，整轮跑在无限速链路上，所有 makespan 失真。
8. 数据层不进 repo、不建软链接；产物不落 repo 根目录与家目录。
9. 不为省磁盘删 void 行或旧轮次。判定用 `void` 列过滤，不靠删数据。

## 6. 装置级故障

组态特有的问题写在 4.2、4.3 各自文档里。

| 现象 | 根因 | 处理 |
|---|---|---|
| 训练 Pod ImagePullBackOff | 离线环境拉不到 docker hub；containerd 不读 daemon.json 的镜像加速 | 宿主机 `docker pull` 后 `kind load docker-image <img> --name traincache`；训练镜像用 `python:3.12-alpine` |
| 冷读结果忽快忽慢 | MinIO 或源站重启后 tc qdisc 丢失 | 冷态规程重挂 tc；不重挂该轮作废 |
| 全 API 401、Service 不通 | 宿主机时钟回拨，SA token 的 nbf 在未来 | 重启 Deployment 重签；坏透就 `kind delete cluster` 后 `make bench-up`，数据在宿主机，重传约 8 秒 |
| DataSet SnapshotNotFound | 快照没发布过，`CURRENT` 缺失 | `traincache/up.sh` 的 `publish_snapshot` 调 `trainpublish`；块大小 8MiB |
| NoAccessibleNodes | worker 缺 `traincache.io/s3-access=true` 标签 | `ctrl_up.sh` 的 `label_s3_nodes` 自动打；重建集群后重跑 |
| preheat 全部失败 | agentd 的桶与 DataSet 的桶不一致 | `ctrl_up.sh` 的 `ensure_agent_config` 改 DaemonSet 环境变量；桶名以 DataSet `spec.bucket` 为准 |
| drop_caches 或 tc 卡在 sudo | 交互式 sudo 不可用 | `bench/.sudo-pass`（gitignore，600 权限） |
| python 依赖找不到 | 直接调系统 `python3` 没加载项目根 `.venv` | 统一用 Makefile 入口（`PY`/`PYTHONPATH` 已设好）；分析层依赖按 `bench/requirements.txt` 装进 `.venv` |
| `pkill` 把 shell 自己杀了；`pgrep` 判「有没有在跑」永远为真 | 模式串出现在自己那条命令行里，自己匹配自己 | `pgrep -f 'run_bench\.py'`；判在跑用 `ps -eo cmd \| grep -E '^(bash\|/bin/bash) .*up\.sh'` |

## 7. 实测基准

- 100mbit / 20ms 档冷读 8GiB：两轮 710s / 710s，相对差 0.0%，理论传输 640s。产物 `results/cold-verify.txt`。只有这一档有对账记录，@300 与 @1000 跨档引用前先各跑一遍 `make bench-verify`。
- 源站吞吐上限 674 MB/s（9 次测量，区间 629~755，约 5.4 Gbit/s）。采法与 train-job 同路径：worker 节点上的临时 Pod 经 `nodeIP:30090` 读 `mc cat`，全程无 tc。
- stall_ratio 口径：measure 脚本用 `COMPUTE_MS=200` 控制每步计算，读与计算并行。预取正常时 wait_s≈0，stall_ratio≈0；预取失效时 wait_s 占满 step_s，stall_ratio≈1。
- 以上数字绑定本机。换机器或换 kind 版本后重测，不直接引用。
