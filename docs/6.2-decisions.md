### D1 文档体系

**结论**:6.0 的下游三件套(design/decisions/test),文件名和内部标题都不带编号。**为什么**:文件内部编号与外文件名已不一致,不再制造第二层映射混乱;三件套与核心库三件套 5.1/5.2/5.3 平行。

### D2 模块落位

**结论**:`agent/` 独立 Go module(`traincache/agent`),并入根 go.work(use ./core ./agent),go.mod 不写 replace。**为什么**:沿用 core D1/D16 的独立 module 口径:module 独立、免 replace、workspace 统一解析;根 go.work 已提交且 agent/ 在其目录树下,不在 use 列表时 go build 直接报错。

### D3 三个可执行产物

**结论**:产出 `traincache-agentd`(Go,DaemonSet)、`traincache-ordersrc`(Python sidecar)、`traincache`(Go CLI)。**为什么**:sidecar 的顺序语义必须与真实 loader 的 shuffle 一致,直接复用 torch / webdataset 的 RNG;Go 复刻 RNG 风险高;共享内存协议语言中立(design §6.2)。

### D4 包结构与依赖方向

**结论**:目录树按 cmd → svc → 子模块 → core 单向无环(design §4)。**为什么**:与 core「单向无环」同风格;子模块互不依赖可并行实现;ordersource 不依赖 core。

### D5 端口

**结论**:gRPC 用 9410,指标用 9411,都可用 env 改。**为什么**:9410/9411 是非特权端口,固定默认值保证 CLI / 探针 / 抓取一致。

### D6 gRPC 服务划分

**结论**:先做南向 PreheatService + NodeService;北向 ReportService(ReportBlocks 流)proto 随本设计冻结,服务端实现推迟至 Controller 就绪。**为什么**:6.0 验收只含南向;北向方向性(谁拨号)依赖 Controller 设计(Q1),先冻结契约不阻塞。

### D7 任务寻址与状态机

**结论**:任务引用 =(dataset, snapshot_id, prefixes, chunks);chunk 复用 core (path, chunk int64);状态机 QUEUED / RUNNING / DONE / ERROR。**为什么**:6.0 CLI 状态只列「进行中/等待/错误」,补齐 DONE 才完备;寻址复用 core,不发明第二套。

### D8 节点标识

**结论**:以 env `NODE_NAME`(Downward API fieldRef spec.nodeName)为权威,启动校验非空,所有状态与指标带 node。**为什么**:6.0 要求「唯一确定自身所在 K8s 节点并在状态上报中携带节点标识」;Downward API 是标准做法。

### D9 共享内存协议

**结论**:单写单读 ring,64B 头加槽位,读端落后就跳最新。**为什么**:多 Pod 并发写同一文件需要锁,单写单读免锁;阶段切换只关心最新顺序,允许丢旧。

**约束与影响**:`/run/traincache/orders/<pod-uid>.ring`;代际检测;slot 1 MiB×64 可配;布局见 design §6.2。

### D10 阶段切换三源归一

**结论**:epoch / shuffle / curriculum 三种阶段切换统一为 sidecar 推送一条新 ConsumeOrder;Agent 不区分三源。**为什么**:归一后 Agent 只剩一种切换语义(design §5.3),curriculum 检测复杂性隔离在 sidecar;curriculum 事件源的做法是 sidecar 获训练进程通知后重算顺序。

### D11 钩子通道

**结论**:单向 Unix datagram 钩子(`/run/traincache/agent.sock`,行分隔 JSON,不回复);顺序主源 = sidecar,钩子只报位点与打开块。**为什么**:6.0 要求钩子调用 PersistentPrefetcher 方法;单向 datagram 免连接管理,丢帧靠 inotify 旁路兜底。

**约束与影响**:帧集合共五种 advance / stage_switch / open_report / read_miss / read_stall(read_miss 见 D44,read_stall 见 D47)。

### D12 core 增量(cas Quarantine)

**结论**:坏块隔离落进 core,core 侧按决策文档登记。**为什么**:6.0 明示「需要增加标记位」;坏块状态属于存储层职责,服务化层不重复实现存储逻辑。契约见 design §5.7;core 侧决策在 5.2 从现有最大号顺延登记。

### D13 重扫描流程

**结论**:启动 = 枚举 + 1% 抽样(全过先服务)→ 后台全量(修复队列优先)→ 读时坏块 repair 回源(single-flight);readiness = 服务 up + 抽样完成,全量不拦。**为什么**:6.0 部署约束「缓存尚未完成全量扫描不应直接导致 Agent 无法提供服务」;CAS 读时自校验兜底。

### D14 热度参数默认值

**结论**:N=24h、DumpInterval=30min、T=24h(因子 0.5)、k=80%、Δ=5%、M=90%;全部 env 可配。**为什么**:6.0 只给示例值;先取可实现默认,校准留 bench 装置。dump 间隔记号用 DumpInterval,与危险线 M 区分(D24)。

### D15 交叉校准口径

**结论**:滑动窗口 100 次打开,实际顺序与 OrderSource 期望匹配率 < 0.8 即重对齐 cursor(即 6.0「默认 20% 偏差」的精确口径)。**为什么**:把「20% 偏差」落成可测试的匹配率定义;inotify 与钩子双源,钩子为主。

### D16 预取参数

**结论**:lookahead=16(6.0 默认);K = ConsumeOrder.prefetch_chunks;P0>P1>P2>P3,在途不取消。**为什么**:6.0 原文约定;ETA 口径显式化便于测试:ETA = 新窗口剩余字节 ÷ EMA(α=0.3) 吞吐。

### D17 指标清单与命名

**结论**:指标按七条线列清单(design §5.8 family 表,含磁盘淘汰线),靠标签控制基数。**为什么**:6.0 基数控制三原则;清单化便于验收 7 逐项核对。

**约束与影响**:dataset / node / result / endpoint / priority 进标签;dataset 白名单外记 other;固定 bucket;高基数进日志。

### D18 依赖引入

**结论**:引入的依赖只有 grpc + protobuf、prometheus/client_golang 两项;inotify 不用 fsnotify,以标准库 syscall 实现(见 D37);其余沿用 core 依赖链。**为什么**:现成库已覆盖需求,与 core D10 的依赖引入口径一致。

### D19 部署

**结论**:DaemonSet 部署(design §8 要点),升级不删有效块。**为什么**:6.0 部署约束原文;节点筛选调度是 Controller 职责,节点选择 label 留待 Controller,不在本设计。

### D20 CLI 细节

**结论**:`--endpoint` 默认 127.0.0.1:9410;`--node` 仅校验不做地址解析(Q2);`--chunks` 是逗号分隔 `path:chunk`,每项直接构造 `ChunkRef`;`--files` 是逗号分隔 tar 分片名,给出时必须同时给 `--dataset`,经 `ListSnapshot` 展开为块;两者互斥且至少给一个。`ls` 默认按文件聚合,`--chunks` 展开到块。**为什么**:CLI 是纯 gRPC 客户端,不能本地读 manifest。

### D21 验收口径

**结论**:bench 装置为唯一数字来源;11 条验收映射写进验收标准。**为什么**:与项目既有流程一致——关键流程可重复执行(验收 11)。

### D22 ring 发现机制与写端实现协议

**结论**:发现 = svc 目录轮询(1s 扫 `*.ring`,新文件构造 Reader)+ Reader 内 200ms poll;写端只增不缩,seq 最后写。**为什么**:design §6.2 未写明这些实现细节,开工前冻结。

**约束与影响**:写端 ftruncate 至 max(现长, 64+slot_size),防读端 mmap SIGBUS;commit = 头 write_seq 最后写,reader 只读 seq ≤ 头 write_seq 的槽;槽索引 =(seq-1) mod slot_count;write_seq 跨代际续增;几何上限 slot_size∈[16, 64MiB]、slot_count∈[1, 1024]。代际只表示「写端会话换了」:`ordersrc.py` 默认每次调用即新会话(gen +1),`--same-generation` 表示同一会话内的续写(载荷不变、只推进 write_seq),用于保活心跳;ring 不存在或旧头非法时 `--same-generation` 退化成新会话首写(gen=1)并 stderr 提示,不报错退出,保证一次心跳写入失败不影响写端进程存活。

### D23 格式错误指标

**结论**:格式错误单独计数:family `traincache_ordersource_format_errors_total`(counter,labels=["reason"]∈{magic,version}),只按 magic/version 分因。**为什么**:§6.2 要求「计入错误指标」但 §5.8 指标表无对应项,本条建立该 family 并登记进清单。

**约束与影响**:不带 dataset 标签(坏文件读不出 dataset,防基数膨胀);ordersource 包级 atomic 计数,svc 每 tick 以 Set 绝对值同步。

### D24 磁盘淘汰策略(热度驱动)

**结论**:淘汰与回收分两层:core Sweep 只做引用回收(语义不变);Agent 淘汰循环(默认 30s 周期)经 core `cas.Evict`(core D28)删除活块本地副本,按 `S = max(h, R)` 升序选块。**为什么**:淘汰发生在「逻辑上还需要」的块里,Sweep 删不了活块(5.0 §7 只回收不引用数据),必须分层;算子取 max:单一权重无法同时保护「刚预取未读」(h=0 靠 R 保)与「历史热久未读」(R 低靠 h 保),max 按各自较强的信号保住两类块。

**约束与影响**:OPEN 合并后 `h ← h+(1−h)·β`(β=0.15),每 T 乘 0.5、超 N 直接衰减;`R = 0.5^(Δt/T_R)`(T_R=6h);t_touch 取最后打开 / 预取写入 / 新 ConsumeOrder 刷新三者最大值。触发线:利用率超 k 按 S 升序 Evict 至 k-Δ;危险线:超 M 时 R 清零按 h 升序激进淘汰 + 告警至 k-2Δ。cursor + lookahead(16 块)任何情况不淘汰;消费窗口保护 = 新订单刷新 t_touch,不设独立机制;索引与引用不动,回源时不重复 Acquire;新增指标线 `traincache_evict_*`(D17 七线)。周期与阈值细节见 design §7.6。

### D25 数据块对象键布局

**结论**:数据块源站对象键 = `<dataset>/blocks/<path>#<chunk>`(path 约定不含 `#`)。**为什么**:core 与 7.x 均未定义下载键;Entry.Node 仅是「块实际落盘的节点名」标签,不可作键;由 (dataset, path, chunk) 直接构造、无需解析。

**约束与影响**:与 core 索引键 `dataset/<name>/...` 同风格;fetch.Fetch 的 key 为 opaque,core 无感知,由数据写入方与 Agent 共同遵守。

### D26 对象存储接入配置

**结论**:对象存储五个 env:`TRAINCACHE_OBJSTORE_ENDPOINT`(默认 127.0.0.1:9000,开发演练连本地 MinIO,真实环境换成 COS/OSS/S3 endpoint)、`TRAINCACHE_OBJSTORE_ACCESS_KEY`、`TRAINCACHE_OBJSTORE_SECRET_KEY`、`TRAINCACHE_OBJSTORE_BUCKET`(默认 traincache)、`TRAINCACHE_OBJSTORE_SECURE`(默认 false),MinIO/COS/OSS/S3 通吃。**为什么**:design §8 env 表补这五个配置项,真实下载链路必需。

**约束与影响**:经 core objectstore.NewS3Store 构造;集成测试用 objectstore.Mock 注入,不依赖 env。

### D27 显式预热入队接口

**结论**:prefetch 增 `EnqueueP0(ctx, refs []ChunkRef) error`(P0 严格最高优先级入队,在途不取消,空列表返回 nil,ctx 取消返回 ctx.Err());Config 增 `OnP0Done func(ref ChunkRef, err error)`(仅 P0 触发,调度协程内同步调用不得阻塞)。**为什么**:§5.2 冻结四方法无显式预热入队口,svc 预热任务状态机(completed/failed 进度)需要完成通知;回调进 Config 不破坏 New 冻结签名。

### D28 prefetch 通用完成回调

**结论**:Config 再增 `OnDone func(ref ChunkRef, err error)`:所有优先级队列块完成(就绪或下载成败)触发,与 OnP0Done 同触发点、调度协程内同步调用不得阻塞;OnP0Done 保留(仅 P0)。**为什么**:collector t_touch 三源之一「预取写入」需要块级完成通知,仅 OnP0Done 覆盖不了其他队列。

### D29 Reader 序推进观测

**结论**:ordersource.Reader 暴露 `LastAdvance() time.Time`:最近一次观察到 write_seq 推进的本地时间(锁下),新代际视为推进,零值 = 从未推进;另有 `Generation() int64`(契约见 D63):代际变化时读端清当前订单、重置载荷去重基线,把新订单重放一次。**为什么**:降级检测(30s 停滞)需要观测 ring 写入序推进;sidecar 重启后不重放,会话会停在上一个阶段。

### D30 HEAT env 拼法与配置扩充

**结论**:svc.HeatConfig 增 HeatOpenBeta(0.15)/HeatTouchHalfLife(6h)/CalibrateWindow(100)/CalibrateThreshold(0.8);env 11 个拼法固定:`TRAINCACHE_HEAT_DECAY_AGE`/`DUMP_INTERVAL`/`DECAY_INTERVAL`/`DECAY_FACTOR`/`OPEN_BETA`/`TOUCH_HALF_LIFE`/`CALIBRATE_WINDOW`/`CALIBRATE_THRESHOLD`/`DISK_TRIGGER_PERCENT`/`DISK_DELTA_PERCENT`/`DISK_CRITICAL_PERCENT`(duration 用 time.ParseDuration,percent 用 0..100)。**为什么**:§5.5 参数 env 拼法文档未定义,开工冻结。

### D31 collector 消费接口

**结论**:淘汰循环以同签名窄接口消费 collector,不直接 import:`EvictionEntry{FP cas.Fingerprint; Heat float64; LastTouch time.Time}`、`ListForEviction() []EvictionEntry`(全量快照,调用方排序)、`Touch(fp cas.Fingerprint, t time.Time)`(幂等,不存在则建 h=0)、`HitRate() float64`。**为什么**:淘汰循环消费热度数据,接口先行冻结解耦并行。

### D32 GC 触发语义

**结论**:淘汰循环先 Sweep 再 Evict,分两条触发线:30s 周期查磁盘利用率;超 k 先 Sweep(全部已知 dataset,失败仅日志)再按 S 升序 Evict 至 k-Δ;超 M 先 Sweep 再 R 清零按 h 升序激进淘汰至 k-2Δ;告警 = ERROR 日志 + evict 计数,不引入新 family。**为什么**:Sweep 如今只回收无引用的快照对象,无引用的本地块由 `LocalGC` 按节点周期清扫(D65);触发时先跑一轮对象回收开销小,淘汰照常。周期与阈值默认值同 6.1 §7.6。

### D33 钩子帧错误计数与收端分发

**结论**:钩子坏帧单独计数:family `traincache_hook_format_errors_total`(counter,labels=["reason"]∈{parse,size}),与 D23 同风格;svc 收端 `HookSock`:`New(path string, m *metrics.Registry, h HookHandlers)`;`HookHandlers{Advance func(ChunkRef); StageSwitch func(stageID string, seed int64); Open func(ChunkRef)}`。**为什么**:§5.4 要求非法帧丢弃计数但 metric 名未定义;分发走注入 handler 保证接线阶段不改 hooksock.go。

**约束与影响**:钩子 stage_switch 仅作信号,接线层结合 CurrentOrder 构造;Miss/Stall 见 D44/D47。

### D34 Agent 组件暴露

**结论**:svc.Agent 增导出字段 `CS *cas.Store`、`Fetcher *fetch.Fetcher`、`ObjectStore objectstore.Store`、`Rescan`、`Collector`、`Evictor`、`HookSock`。**为什么**:重扫描与淘汰需触达 cas/fetch/objectstore,现埋于 PrefetchManager 私有字段。

### D35 rescan 包接口

**结论**:rescan 的构造、启动、状态和单块修复接口冻结。**为什么**:§7.1 启动序列无组件接口,并行开工前冻结。

**约束与影响**:`New(cs *cas.Store, fetcher *fetch.Fetcher, obj objectstore.Store, catalogFor func(ctx context.Context, dataset string) (*index.Catalog, error), m Metrics)`(Metrics = rescan 自定义窄接口);`Start(ctx)` 非阻塞(内部:1% 抽样全过先服务 → 后台全量,修复队列优先);`Status() Status{Phase, Sampled, Verified, Quarantined, RepairQueue int64}`;`RepairOne(ctx, dataset, ref ChunkRef) (cas.Fingerprint, error)`(读时坏块路径复用;键用 D25;Quarantine→fetch→Put→校验→RemoveQuarantined);dataset 枚举经 objectstore.List("") 首段。

### D36 指标标签词汇表

**结论**:指标标签取值全部冻结成一张词汇表。**为什么**:§5.8 冻结了 family 名与部分取值,标签取值的完整词汇表要单独固定,实现侧与查询侧才不会出现两套写法(design §5.8 的「全集另见」指向本条)。

**约束与影响**:result∈{success,error} 全局二元;refetched 仅 cache_misses_total;normal/danger 仅 evict_* 两 family;无 result 参数者固定 success;endpoint∈四南向 RPC 方法名(不带服务前缀);钩子/ordersource 帧错误 reason∈{parse,size};回源 reason∈{prefetch,demand,repair,other}(三词术语冻结口径见 design §5.8);priority∈{P0,P1,P2,P3};phase∈{startup,steady,switch,unknown};source∈{prefetch,cache,unknown}(命中)/{hook,inotify}(消费推进);cause∈{local_slow,prefetch_lag,origin_slow,unknown};集合外取值忽略该次打点,不产生新标签取值;构造预置(dataset 类预置 other 子指标、request_duration 预置 4 endpoint×{success,error}、agent_up 预置 1);index_refresh_duration_seconds 复用延迟线固定 bucket;Add*/Inc* 非正增量忽略。

### D37 inotify 实现选型

**结论**:collector 的 inotify 用标准库 syscall(InotifyInit1/InotifyAddWatch)直接实现,不用 fsnotify。**为什么**:fsnotify v1.9/v1.10 把 IN_OPEN 映射到未导出常量,外部包无法观测打开事件,需求在其上不可实现。**约束与影响**:不引入新依赖,与 ordersource 的 syscall.Mmap 同风格。

### D38 缓存根 env 覆盖

**结论**:svc 配置增 env `TRAINCACHE_CACHE_ROOT`(默认 `/var/cache/traincache`),覆盖 Config.CacheRoot。**为什么**:非 root 进程写不了 `/var/cache`,进程级演练与 agentd 动态判据验收都被这条卡住,「动态判据环境受限」需闭合。

**约束与影响**:DaemonSet 部署仍用默认值(§8 hostPath 固定不变),env 供本机进程级演练与非标准缓存根场景;env 表见 6.1 §8。

### D39 探针判据实现

**结论**:liveness = CLI `traincache node status --node "$NODE_NAME" --item agent` 退出码 0;readiness = `--item rescan` 成功且输出含 `RESCAN_PHASE` 行、该行不含 `SAMPLING`(DONE/FULL_SCAN 计 Ready)。**为什么**:grpcurl 不在装机的默认工具里,CLI 又无 health 子命令,以 GetNodeStatus 承载 health 语义;判据符合 §7.1「抽样完成先服务,后台全量不阻 ready」。

### D40 部署镜像构建口径

**结论**:多阶段 `golang:1.26-alpine → alpine:3.24`,`CGO_ENABLED=0` 静态构建;构建上下文须含 go.work/go.work.sum + core/ + agent/,Dockerfile 用「仓库根上下文 + COPY 子树」写法。**为什么**:§8 已定镜像口径;agent 与 core 无 require/replace,构建上下文必须从仓库根来。

**约束与影响**:`ARG GOPROXY`(本机 `https://goproxy.cn,direct`);sidecar 镜像 `python:3.12-alpine` 仅标准库依赖。

### D41 sidecar 节奏与调度

**结论**:ordersrc 循环写 ring(10s 间隔)而非一次性写完退出;循环内的重写是同一写端会话的续写,首轮之后一律带 `--same-generation`(见 D22、D57);DaemonSet 不加 toleration。**为什么**:保持容器 Running(验收 2)且避免周期 <30s 触发停滞降级(orderStallThreshold=30s);control-plane 的 NoSchedule 污点使 DS 自然只落 worker(每节点一个 Agent 的正确语义),故不加 nodeSelector。适用范围含所有 ring 写端(见 D57)。

### D43 CLI prefetch 幂等键必填 + 无对象存储 GAP 口径

**结论**:① `traincache prefetch` 增 `--task-id` 必填(与 `status` 对称):SubmitPreheatRequest.task_id 为幂等键,未填则 svc 拒 InvalidArgument;② 验收:进程或集群里没有对象存储时 svc SubmitPreheat 同步 resolveRefs 读 CURRENT 失败 → prefetch/status 标 [GAP-环境](与验收 1/5/9 同口径),非缺陷;e2e-local.sh 4.2/4.3 复用 kind 集群内 MinIO(port-forward 后由 trainpublish 播种),此两项为硬断言,失败不记 GAP。

### D44 读 miss 上报与 Agent 侧 demand 按需补块

**结论**:钩子加 read_miss 帧,Agent 按需异步补块。

**为什么**:inotify 只能观测已存在文件的 IN_OPEN,缺块对 Agent 不可观测;open_report 语义是「已打开」,不能承载 miss。补块必须留在 Agent 进程内才能复用 fetch 的 inflight 合并并回填 CAS——训练侧直连对象存储既与预取分属不同 single-flight 域,又因只读挂载无法回填。read_miss 是事后信号,作用是把缺块交给补取,单次读仍可能出现 stall。

**约束与影响**:帧字段与 svc 接线见 design §5.4(含归属解析不要求 Catalog 命中、P0 入队、single-flight 域、补不及则本次读仍失败的正确性契约);fetch reason 按首个入队触发者记账,后续 P0 提升不改已有 task 的 reason。训练 Pod 保持只读 hostPath、不接对象存储、不持凭证。指标 `traincache_hook_read_miss_total{reason}` 不带 dataset(family 清单见 design §5.8)。

### D45 prefetch 跨队列去重与优先级提升

**结论**:PersistentPrefetcher 维护 pending 表跨队列去重,P0 到了就提优先级。

**为什么**:入队处无去重会使同一块在 P0/P2(及 P1/P3)并存;fetch.Fetch 下载前拿不到指纹,无法按 key 复查 CAS,且 inflight entry 在 close(done) 后立即删除,single-flight 覆盖不了「本地检查→Fetch」间隙。源头去重消除重复下载、重复完成回调、重复吞吐采样与重复 collector.Touch;优先级提升保证 P0 语义不被先到的 P2 任务降级。

**约束与影响**:键 `blockKey(dataset,ChunkRef)=<dataset>/blocks/<path>#<chunk>`(与 fetch key 一致),覆盖 P0–P3 与运行中 task;入队 / 提升 / 忽略三规则与计数口径见 design §5.2(完成或终止移除键、失败重试保留;OnDone/OnP0Done 每 task 恰好一次;QueueDepth 与 SubmitPreheat total/completed 按去重后计数)。

### D46 分阶段命中率与命中来源

**结论**:命中率按 phase 和 source 拆标签,新增预取命中率。

**为什么**:6.0 要求分阶段观察命中率与预取收益,D17 仅按 dataset/result 聚合无法区分切换期与稳定期;100 样本窗口沿用 D30 CalibrateWindow 口径,保证 prefetch_hit_ratio 可解释。

**约束与影响**:phase 状态机与 source 判定定义见 design §5.2;四个 family 及标签见 §5.8(`cache_hits_total{dataset,result,source,phase}` result 固定 success、`cache_misses_total{dataset,result,phase}`、`cache_hit_ratio{dataset,phase}`、新增 `traincache_prefetch_hit_ratio{dataset}` gauge)。

### D47 实测 stall 与归因

**结论**:钩子加 read_stall 帧,按 ts±5s 关联归因。

**为什么**:6.0 只有 ETA 预估,无实测读等待;read_stall 提供训练侧真实等待,ts±5s 窗口容忍钩子与 Agent 的时钟/调度偏差;单次读仍可能 stall 的口径沿用 D44,read_stall 只做观测,读路径行为保持不变。

**约束与影响**:字段与归因规则、buckets 见 design §5.4/§5.8;`HookHandlers` 增 `Stall`;`traincache_read_stall_seconds{dataset,phase,cause}` 仅记录 ≥100ms 等待(阈值默认 100ms,env `TRAINCACHE_READ_STALL_MIN_WAIT_MS` 可配)。ETA 记预估,实测等待记入 `read_stall_seconds{phase="switch"}`。

### D48 证据类指标

**结论**:补 6 个证据 family,fetch 指标增 reason 标签(family 总数见 design §5.8)。

**为什么**:6.0 六条线路的预取收益、修复压力、消费推进与带宽上限缺少可观测证据;singleflight 在 core/fetch 内部无法从 Agent 侧观测,调用包装器是改动面最小的落法(不改 core/fetch 契约);reason 区分 prefetch、demand、repair 三类回源,便于验收与容量分析。

**约束与影响**:6 个新 family(`fetch_singleflight_merged_total`、`repair_queue_depth`、`prefetch_task_duration_seconds`、`prefetch_lead_blocks`、`consumption_advance_total`、`fetch_bandwidth_limit_bytes`)与 `fetch_bytes_total`/`fetch_requests_total` 的标签变更清单见 design §5.8;reason 分桶同 D44 口径。

### D49 Status 双游标口径收口与 inotify 兜底

**结论**:`Status` 拆纯消费位点与预取前沿,落实 inotify 兜底。

**为什么**:两者混用会让 inotify 兜底把「块已完成」误当「已消费」,并使 lead 失去负值语义;inotify 事件本身无位点,只能凭指纹反查,代际缓存把逐 OPEN 的全订单 Lookup 降为同代际 O(1)。

**约束与影响**:双游标契约(`Cursor` 仅由 advance/inotify 推进、`PrefetchFrontier` 不要求连续、`lead = frontier − cursor` 可为负、调度游标不进 `Status`)与兜底去重、门控见 design §5.2/§5.8/§7.4。实现口径:
- ① fp 反查无 Catalog 接口,只能遍历当前订单 Chunks 逐个 Lookup;按订单代际(stageID、Chunk 数、首尾 ref)缓存反向索引,同内容多路径返回候选逐个尝试;已知限制:反查仅覆盖当前订单;
- ② `traincache_prefetch_cursor` 指标记录调度游标,help 文本明示「调度进度,非 Status.Cursor」,与 `Status.Cursor` 无关;
- ③ self-open guard:Agent 自身读打开本地块(预取本地命中、下载读回校验、ETA 探测、rescan 扫描/修复读回、backfill/stall 归因探测)同样产生 IN_OPEN,钩子沉默/降级期会被 inotify 兜底误判为训练消费;新增 `prefetch.SelfOpenGuard`(`Mark`/`SelfOpened`,并发安全、惰性清理、条目上限 8192,超出先清过期再淘汰最旧;nil 安全)在打开前登记指纹;TTL 默认 3s(装配处传入),覆盖 inotify 轮询与处理延迟;已知偏差:TTL 内训练恰好打开同一 fp 会漏计一次消费推进(宁可少计不可虚增);
- ④ Mark 覆盖:prefetch 本地命中 / 修复重开 / `reportFetchSuccess` / `estimateETA`、core fetch Put 成功后读回(经通用 `fetch.Options.OnLocalOpen` 钩子,core 不依赖 prefetch 类型)、rescan `verify`/`reportRepairFetch`(经 `SetSelfOpenMarker` 注入)、svc `backfill` 本地命中探测与 `stallLocalExists`;
- ⑤ 过滤位置:collector `SetOpenFilter`,仅在 `fireOpen` 调用兜底 open 回调前判断,true 则跳过(不推进 consume、不计数),`noteOpen` 的热度/命中率逻辑不受影响;nil filter 不过滤。

### D50 快照发布 vs 快照跟随边界与自开观测

**结论**:快照发布 = 写入方调用 core/index `(*Writer).Commit`;快照跟随 = Agent 经 `index.Catalog.Start`/`Refresh` 只读,不调用 `Commit`;自开观测防护 = `cas.SetOpenObserver(guard.Mark)`,装配期最先安装(契约见 design §5.9)。

**为什么**:两种角色分离,避免 Agent 误承担发布职责;Commit 的 checksum 读回会打开本地块文件,进程内 observer 在 `Store.Open` 处统一登记,覆盖未来任何写入方内嵌调用 Commit 的自开读,使其不污染消费侧信号(inotify 热度、Cursor);observer 按 Store 实例划分,进程内多个 Store 与测试互不干扰。发布调用方是 `traincache trainpublish`;Controller 现有职责不产生新索引。

### D51 前缀感知快照跟随(R1)

**结论**:Catalog 支持按前缀、按周期跟随 CURRENT;Agent 侧 Follow 在订单前缀 hint 写入之后才启动,`RefreshManifest` 在 snapID 未变且 entries 非空时为空操作(不清空)。**为什么**:Catalog 加载由订单/预热触发,无订单时快照保持陈旧;前缀感知跟随在无活跃前缀时退化为整 manifest 跟随,并以 Catalog 内部互斥保证与 `ForOrder` 不并发切换。完整冻结契约见 design §5.9。

### D52 快照读者登记、心跳与撤销(R2)

**结论**:读者登记快照、定期心跳,退出时撤销。**为什么**:GC 需要知道哪些快照仍被读者使用;心跳过期即可判死,`PreviousSnapID` 覆盖切换宽限期,撤销后不再误保护。完整冻结契约见 design §5.10。

### D53 GC 按读者确认删除(R3)

**结论**:GC 以有效读者 claim 为保护集,保留窗口降为兜底。**为什么**:保留窗口只提供时间维度的兜底,读者可能在窗口外仍持有旧快照;以有效 claim 为保护集并用 `PreviousSnapID` 覆盖切换宽限期,manifest 缺失时 fail-safe、该数据集本轮一个对象都不删。完整冻结契约见 design §5.11 七条 Sweep 规则。本地块副本的清扫归 `LocalGC`(D65)。

### D54 Commit 孤儿清理与条件写探测(R4)

**结论**:失败提交清理孤儿对象,并探测后端条件写。**为什么**:失败提交留下的新分片/manifest 无引用,不清理会成孤儿对象;条件写在 mock 上无法证明真实后端支持,需真实 S3 兼容后端探测与集成测试。完整冻结契约见 design §5.12。

### D55 Agent 预热任务增量(7.x)

**结论**:扩展 `traincache.agent.v1.PreheatService`(契约全文见 design 附录 A):新增 `UpdatePreheat`/`CancelPreheat`;`PreheatStatus` 追加 `generation=12`、`seq=13`、`ready_bitmap=14`、`canceled=15`,`SubmitPreheatRequest` 追加 `generation=8`;进度查询复用 `GetPreheatStatus`;`UpdatePreheat` 全量替换;`CancelPreheat` 标记取消并撤回该任务未完成的下载(D62),任务仍留在任务表内并由 `canceled` 回报;低 generation 返回 `FailedPrecondition`;同 generation 的 Cancel 后再 `SubmitPreheat` 视为新任务;`ReportBlocks` 为 Unimplemented,7.x 不使用。

**为什么**:7.x GWAA 需要按 `(pod,node)` 改派/停止并读取窗口位图;复用 `GetPreheatStatus`,不引入额外查询 RPC,两个动作 RPC 覆盖改派/取消;拉取方向与现有 RPC 一致,避免 Agent→Controller 反向连接(详见 `docs/7.2-decisions.md` D28)。

### D56 位序定义(7.x)

**结论**:`ready_bitmap` 第 `i` 位对应请求 `chunks` 第 `i` 项;`UpdatePreheat` 全量替换 `chunks` 后位序重定义、旧位图失效并重置;7.x 必须显式 `chunks`,空列表视为清空窗口。**为什么**:位序若按块全局编号会随窗口变化漂移;绑定请求顺序使 Controller 与 Agent 无需共享全局映射,位图长度可推导(`ceil(len(chunks)/8)`)。

### D57 ring 写端保活扩展到 bench reader

**结论**:D41 的 10s 重写节奏从 `traincache-ordersrc` sidecar 扩展到所有 ring 写端;`bench/compare/run_bench.py` 的 traincache 组 reader 加 heartbeat 线程,每 10s 按当前 epoch 的载荷同代际续写一次订单。

**为什么**:D41 只约束了 manifest 里的 sidecar,而 bench 的 traincache 组由 `run_bench.py` 内联写 ring:订单每 epoch 只写一次、epoch 内静止,`LastAdvance`(D29)停滞 30s 后 collector 进 degraded 切 inotify 兜底,热度和命中率统计中途换源,跑分数据口径不一致、不可比。本条调整的对象是写端的续写节奏;D22 的写契约与 collector 的 30s 降级阈值保持不变。

**约束与影响**:
- `run_bench.py` traincache reader 的心跳线程每 10s 调一次 `_write_order(当前 epoch 载荷, heartbeat=True)`,写入异常忽略,不中断训练读取;epoch 主循环的首写不带 heartbeat,即新起代际;心跳线程在 `epoch == 0` 时以 daemon 线程拉起,循环结束置停止标志收尾;心跳与 epoch 首写共用同一把写锁,同一时刻只有一个写端在动 ring。
- 心跳必须同代际续写(`--same-generation`,契约见 D22 与 design §6.2):读端的载荷去重(`lastEmitted`)按 `(generation, payload)` 判,新代际同载荷也重放一次(design §7.4),所以「内容相同不推送」只在同代际成立。每次心跳另起一个 `ordersrc.py` 进程等于每 10s 一次代际 bump → 每 10s 一次 `OnStageSwitch` → 预取队列整段重铺(M5 前置探针:每 10s `chunks=1024` 重铺一次,字节上限生效后演变成无界回源)。
- 保活判据:跑分产物所在轮次要求 `traincache_agent_degraded` 全程为 0;出现过 1 则该轮命中率/热度曲线标 `degraded`,不参与组间对比。
- 新的自研 ring 写端(探针、临时脚本)按同一条约束实现,不得只写一次就静止;静止前的重写一律同代际。

### D58 缓存字节上限与淘汰双维度触发

**结论**:evictor 新增 env `TRAINCACHE_CACHE_CAPACITY_BYTES`(默认 0=关闭),开启后淘汰循环同时查磁盘利用率和字节占用,哪个先到阈值就按哪个维度触发;两个维度共享得分模型 `S = max(h, R)` 和硬保护(cursor+lookahead 不淘汰)。

**为什么**:磁盘百分比水位(80%/90%)是间接约束:节点上还有其他 Pod 占用磁盘时,Agent 可能在磁盘还没到 80% 时就已经预取了大量数据,或者磁盘到了 80% 但 Agent 其实没写多少块。字节上限直接约束本节点 Agent 最多占用多少 GB,满足 bench 公平实验「所有组统一 1GB 缓存」的要求(归入 D19 部署约束)。

**约束与影响**:
- 默认 0 关闭时字节维度不生效,只按磁盘水位触发淘汰。
- 触发线(超上限 → S 升序淘汰到 85%)与危险线(超上限 95% → R 清零按 h 升序淘汰到 80%)及磁盘维度沿用 D32 的 k/Δ/M,两维度各自判定互不依赖;细节见 design §7.6。
- 记账:evictor 维护本地块字节累计,口径固定为块文件 size = 数据长度 + 128B 块头(`cas.HeaderSize`)。三个来源必须同源:`cas.Put` 后置观察者按 `n + HeaderSize` 加、`cas.Open` 首次打开且块文件已存在时按文件大小加、`cas.Evict` 成功后按同一文件大小减。只统计 Agent 自己写的块,系统文件不计入。启动时预扫 `blocks/` 目录,把已有块的 size 播种累计,同时把这些指纹播种去重表 `seenFPs`:只播种累计的话,已有块被本进程首次打开会再加一次(8GiB 目录读成 16GiB),淘汰每块只减一次,清空目录后累计停在正的残值上,危险判定无法解除。
- `seenFPs` 的语义是「这个块的字节已进累计」:`cas.Open` 前置观察者对缺失块同样触发(预取就绪探测、ETA、回填都是先 Open 再判命中),此时 stat 取不到 size(0),不得占用去重槽;若占,随后本进程 `cas.Put` 同一块会被当成「已累计」跳过。冷缓存下几乎每个块都先被探测一遍,漏记覆盖全部写入,累计停在播种值、字节维度到不了触发线。M5 探针复现现象:`capacity_bytes{bytes}` 恒等于播种值、目录越涨淘汰增量越为 0。
- 指标:`traincache_cache_capacity_bytes_total{source}`(gauge,source∈{disk,bytes})暴露当前触发维度(family 总数见 design §5.8)。
- bench 装置:所有组统一设 1GB,保证公平对比。

### D59 淘汰策略抽象与运行时选择

**结论**:淘汰时谁先被换出抽象成 `Policy` 接口(`agent/evictor/policy.go`),接口只有 `Rank(blocks []Block, danger bool) []Block` 一个方法;三档 `heat`(现有热度打分,作回归基准)/`lru`/`lfu`,运行时经 env `TRAINCACHE_EVICT_POLICY` 选择(默认 heat,启动校验,未知值拒绝启动并打印合法清单);lookahead 同步 env 化为 `TRAINCACHE_PREFETCH_LOOKAHEAD`(默认 16)。W-TinyLFU 档不实现(权威口径见 4.5 D9):无准入(`Admit`)层、无 `admit_rejections` 指标与频率减半动作。

**为什么**:9.0 要求多策略同台,用哪种淘汰是运行时选项,同一份代码按 env 换档。接口落在 `agent/evictor`:core 不该知道训练语义与访问历史(4.5 D7),`cas.Evict` 原语不动。扫点靠 env 注入,不改 CRD(4.5 D10)。实验块大小取 8MiB(4.5 D20)后 1GiB 缓存有 128 块,各档排序结果才有判别力。撤档理由(4.5 D9):① bench 主场景是单 Job 顺序读,准入(拦截一次性块)的收益不明确;② window + 两段 SLRU + count-min + doorkeeper 的实现与验证成本高;③ 已写出的 `tinylfu.go` 只是频率排序代理(window 与两段 SLRU 缺失、`Admit()` 从未被淘汰循环调用),留着会让策略同台对比失真。

**约束与影响**:触发线、危险线、字节上限维度(D58)、硬保护(cursor+lookahead)与策略无关,三档共用;策略只替换「谁先被淘汰」这一层。`heat` 档回归判据:同一访问序列下与 D24/D32/D58 的行为逐块一致(4.5 D8)。淘汰指标沿用 D17 的 `traincache_evict_*` 三线,策略切换没有计数(4.5 D29:策略只在启动时选定,运行期无切换路径,计数恒为 0)。bench 装置:对照实验一律 `heat`;淘汰矩阵与 `pareto-sustained` 由 `experiments/run_policy.py` 注入策略与 lookahead,矩阵覆盖 3 个策略(4.5 D9)。

### D60 Follow 启动时序与 demand 索引解绑

**结论**:svc 在 bundle 构造内先写入当前订单的路径前缀 hint,再启动 `Catalog.Follow`;hint 由 `bundleFor` 的调用方传入。`RefreshManifest` 在 snapID 未变且现有 entries 非空时为空操作:不切换、不清空、不触发 `OnSnapshotChange`。read_miss 的 demand 归属解析与索引命中解绑:dataset 已知、条目未命中时,仍按 D25 键入 P0;dataset 未知才丢弃该帧。契约见 design §5.4/§5.9。

**为什么**:`Follow` 启动即执行首轮检查。先启动、后写 hint,首轮会读到空前缀,`RefreshManifest` 清掉刚由 `LoadPrefixes` 装入的映射;snapID 未变,后续各轮全部跳过,空映射从此固化,demand 再也入不了队,因此同快照非空映射的 `RefreshManifest` 定为空操作。P0 demand 的回源键由 `(dataset,path,chunk)` 直接拼出,归属判断只依赖 dataset 是否已知,索引为空时已知 dataset 的块照样能回源。

**约束与影响**:首次构造 bundle 时随参数装入 hint 并启动 Follow;既有 bundle 的前缀 hint 不随无订单入口改写。空前缀(无订单)的轻量跟随仍可切换空映射,受保护的是同快照的非空映射。demand 与 prefetch 共用同一 Fetcher、同处一个 single-flight 域的口径不变(D44),准入档位按 D61 分级。

### D61 fetch 在读/预铺分级准入

**结论**:`core/fetch` 增加准入档位 `Admission`(`AdmissionReading` 在读 / `AdmissionSpeculative` 预铺)与 `FetchWithAdmission`,`Fetch` 等价于在读。在读是需求读补块与坏块修复,发起时已经有人在等这次下载;预铺是预取(含显式预热),暂时没有等待者。预铺额度固定取全场的一半:任务槽 `MaxTasks/2`、在途字节 `MaxInflightBytes/2`,各自至少 1;预铺先占半额、再占全场额度,在读按全场额度随时接入。在读有下载在途时,预铺停在让路门外,等到在读在途数归零再放行。已在途的预铺下载不取消;在读请求合并进同 key 的预铺下载时,该次下载改按在读准入(代码名 `promote`)。准入档位与队列优先级是两个维度:`Admission` 决定这次下载拿多少额度、能不能排队进入,`P0~P3` 决定出队顺序,prefetch 侧按任务 reason 分档,demand 走在读,其余(含显式预热)走预铺。契约见 5.1 §5.3、6.1 §5.2/§5.4。

**为什么**:cold 探针给出三组数字。启动耗时 80.0 s,其中第一片 252 MiB 的串行块读占 76.6 s;整轮取数 2.12 GB 里有 1.96 GB(92%)归因 `reason=prefetch`。预取与需求读共用同一条 12.5 MB/s 出口,预取能占满全部 8 个任务槽。P0 只约束出队顺序,挡不住已经在途的预取,需求读只能排队,首片读因此被拉长三倍多。

**约束与影响**:在读永远保有一半任务槽与一半在途字节,需求读与预取各用一份额度。额度不构成吞吐瓶颈:12.5 MB/s 的出口上两块并发就能打满,预取让出一半槽位不降低回源吞吐。训练读持续不断时预取会让路,预取进度可能后移;命中率与 stall 归因口径不变。让路门只数在读在途、不数合并等待者,否则预铺持有者会被自己的合并等待者挡住。

### D62 宽预热落选窗口的 P0 撤回

**结论**:撤回的作用点是每块绑定的下载 ctx。每个预热任务受理时结一个下载作用域(`PrefetchManager.PreheatScope`,派生自管理器 `baseCtx`),窗口里的块入队时逐个结上它;`CancelPreheat`(以及任务出表、D55 的 TTL 过期)取消该作用域,块就在下一个 ctx 边界退出:`core/fetch` 的准入排队、源站读、写盘三处本来就 ctx-aware,无需额外的门。已在途的块同样中途退出,部分写的临时文件丢弃——落选节点搬完半块和搬完整块消耗同样多的回源带宽。入队准入仍按请求 ctx 判,`docs/6.1` §`CancelPreheat` 的受理口径不变。

**撤回点为什么选在下载 ctx**:预取队列层没有准入门,调度协程出队即取走,`EnqueueP0` 一次性把整窗推进 P0 后队列几毫秒就排空,队列级摘块(摘 P0 队列 + 删 `pending` 键)在生产路径上摘到的块数为 0;积压真正停在 `core/fetch` 准入层(D61 预铺额度 `MaxTasks/2`,fixture 4 → 2 块),只有 ctx 边界能覆盖仍在排队下载的块。

**为什么**:宽预热是「四家同下一份、留下两家」的竞速,落选两家各下一整份就是纯消耗回源带宽。`canceled` 标记在取块路径上没有读者,只用于 `Submit`/`Update` 的入参校验与 `Status` 回报,光靠它停不住调度。探针实测(`results/m7/_probe-fand45-20261029T0857`,fanout=2、100 mbit):`Submit`/`Cancel` 已止于首轮广播的 4/2 次、成对「取消/重提」归零、325 s 放行,`startup_warmup_bytes` 仍为 3 827 130 368 B,模型 2 147 483 648 B,多出 1.68 GB;四节点各存满 1 059 559 424 B,worker3/worker4 在 00:59:11 被取消,两节点最老的缓存文件是 00:59:21/00:59:22,整个窗口都落在取消之后。

**约束与影响**:落选节点在取消后停止下载剩余窗口,宽预热的回源成本从 `候选数 × K × chunk` 降到 `fanout × K × chunk + 取消前已完成的块`。四条口径:
- 撤走的块按失败计入回调,任务落 `ERROR` 终态(`completed` 保留取消前已完成的块数,`ready_block_bitmap` 不变),控制器按 D55 的终态处理,不发紧急重提;
- D45 去重表按块跨任务共享:同键的真实需求读会合并进预热里的同一个 task,取消预热任务连带打断它。代价是那次下载重头来过,读路径自己会重新排队并有超时保护,不会挂住消费者,不影响正确性;
- 作用域只在出表时释放(`drop`、TTL 过期、`CancelPreheat`),`finish()`(DONE)里不取消——DONE 后仍可能收到 `UpdatePreheat` 续窗,作用域若已死则续窗直接失败。
- 结果回投调度协程的 `select` 用调度 ctx:被撤块的结果要照常完成记账与 P0 回调,任务才能收敛到终态。

### D63 订单通道降级的观测语义

**结论**:降级信号观测的是订单通道还剩几路在推进;读服务与订单投递按订单本身走,Agent 的运行模式与该标志无关。每路 ring 按 `(pod_uid, generation, dataset)` 记 `discovered/healthy/stalled/ended`;`OrderDiscovery` 单写者每 1s 聚合 `none/healthy/partial/all_stalled`,`traincache_agent_degraded` 只在 all_stalled 时为 1。Collector 不写 gauge、不绑 ring,订单上下文由 svc provider 注入。订单投递与降级解耦,forward 删除降级闸门,按 `(generation, payload)` 去重;代际变化时读端清当前订单并重放新订单(契约见 D29)。missing 满 5min 回收 Reader(取消转发、关读端、移出表),mtime 超 5min 的陈旧 ring 不建 Reader;启动 5s 宽限内不判 stalled。inotify 只做统计和消费提示。

**为什么**:订单通道的存活、读服务的可用、降级期数据的正确性,三者生命周期不同,折成一个 bool 后,触发没有身份、恢复只是翻标志、两个写者互相覆盖、测量侧不读 gauge。订单是提示,丢单只损失预取效率,因此降级只作观测信号。

**约束与影响**:
- `traincache_agent_degraded` 形状不变(0/1,`{node}`),新增 `agent_ordersources{node,state}`、`agent_ordersource_ended_total{node,reason}`、`orders_dropped_total{reason}` 三个 family(family 总数见 design §5.8)。
- `ordersource.Reader` 增 `Generation()`,读端清 `cur`、重置去重基线、同内容重放一次的契约见 D29;resync / 损坏槽 / 空订单计 `orders_dropped_total{reason}`。
- 多训练 Pod 同时段切换时,`stage_switch` 帧不带 dataset,归属仍取最近安装订单;精确归属由钩子帧的可选任务身份字段(`warmup_task`/`pod`/`pod_index`)给出,见 6.1 §5.4。
- 不做重放/ACK/游标持久化,不做独立的 fail-fast 配置项。

### D64 块 GET 走合并回源网关

**结论**:Agent 只让块 `Get` 走网关,`Put`/`Delete`/`GetETag`/`PutIfMatch`/`List` 一律直连源站。`gatewayEndpoint` 非空即启用;`gatewaySecure` 单独控制 Agent 到网关的 TLS,与 `objstoreSecure` 无关,源站与网关两侧的加密可以各自成立。网关失败的判据走双通道:响应头 `x-traincache-gateway: unavailable` 与 XML 错误码 `XTraincacheGatewayUnavailable`。minio-go 不透出响应头,这一路由 `NewS3StoreWithOptions` 安装的 `RoundTripper` 探针在每次请求的 ctx 里记录。降级状态(mode、代际、下次探测时刻、退避)只存在进程内存,Agent 重启回到配置默认。网关客户端固定 `Region="us-east-1"` 与 `MaxRetries=1`。

**为什么**:块数据是唯一需要合并的读路径,写入、列举、ETag 与条件写留在源站,网关的职责与故障面都收窄;若把写也送进网关,网关一坏就同时打断读者心跳与 GC。响应头是网关区分「自己坏了」与「源站坏了」的直接信号,而 SDK 只透出 XML `Code`,两路都要认,缺一路就会把可降级的 503 当成普通源站错误。TLS 分开是因为源站常是云端 HTTPS,网关在集群内默认明文,复用同一个开关会让 Agent 用 TLS 拨一个不监听 TLS 的地址。`MaxRetries=1` 是因为网关的 503 是控制信号(准入拒绝或降级触发),SDK 默认的 10 次退避重试会把它放大成十次请求,还会拖住调用方的超时预算。固定 `Region` 则省掉 minio-go 先发 `GET /<bucket>?location=`,网关只需处理 GET 与 HEAD。

**约束与影响**:
- 选择器包住 `objectstore.Store`,只有 `Get` 读降级状态;其余五个方法直接转源站。降级退避 10s→20s→40s→80s→120s→120s,探测窗口 5s,同一时刻最多一个请求发到网关。同一次 `Get` 仅在已写 0 字节时改走源站,已写出的字节不重试。
- 降级状态不进 CRD、不落盘;进程重启后按 `gatewayEndpoint` 重新从直连或网关起步。
- 新增 `traincache_source_mode`(gauge,0=直连/1=网关)与 `traincache_gateway_fallback_total{reason}`(counter,reason∈{unavailable,timeout,transport})两个 family(family 总数见 design §5.8)。
- 验证:`core/objectstore/gateway_test.go` 覆盖响应头与 XML 两个判据、`MaxRetries` 不被 SDK 全局值放大;`agent/svc/backend_test.go` 覆盖只 `Get` 走网关、已写字节为 0 的同次回退与退避序列。详细契约见 9.1 design §4.3/§4.4,取舍见 9.2 decisions。

### D65 本地孤儿块副本的周期清扫归 Agent

**结论**:Agent 新增独立周期任务,默认 10 分钟,env `TRAINCACHE_LOCAL_GC_INTERVAL`(`agent/svc/config.go` 的 `LocalGCInterval`),按节点清扫本地 CAS 孤儿块副本。每轮先取数据集全集(对象存储枚举 ∪ 本地已知),枚举失败整轮放弃、不调 core `LocalGC.Sweep`;删除的本地块数复用 `traincache_gc_blocks_removed_total` 上报,dataset 标签传空串、经白名单归 `other`,不新增 family。core 侧的分工见 5.2 D35:`Collector.Sweep` 只回收对象存储里的快照对象。契约与机制见 design §7.6、§5.11 和 5.1 §5.4 / §11.5。

**为什么**:活块集合 = 各数据集 CURRENT 引用的块 ∪ 有效 claim 保护的快照引用的块,这个集合只有按节点算才对——本地 CAS 是节点级全局、内容寻址,块不按数据集分区。Agent 同时持有本节点 `cas.Store`、对象存储访问和数据集全集视图,是唯一体;`traincacheds gc` 是单点运维工具,看不到各节点本地状态,不该由它删块。固定周期加集合差覆盖全部删除形态(条目删除、数据集删除、无 CURRENT),不需要删除事件通道。

**约束与影响**:
- fail-safe:任一数据集索引读不到(确定不存在除外)或损坏,整轮不删任何块;被 pin 住的块经 `cas.Evict` 返回 `ErrInUse`,跳过留待下轮。生产路径不调 `Pin`,所以块副本被删时若正有读在跑,unlink 不影响已打开的句柄读完,下一轮 fetch 才回源重拉。
- 淘汰边界不变(D24/Q5):GC 与本地清扫 = 引用回收,淘汰 = 容量管理;`evictor.Config.Sweep` 仍只在越过触发线时跑,跑的是对象回收那部分。
- `traincache_gc_blocks_removed_total` 从此只计 `LocalGC` 删除的本地副本数;`traincacheds gc` 不再输出 `local_blocks=`(5.1 §11.3)。
- 每轮读全部数据集的 CURRENT、manifest 与分片,请求量与节点本地是否有活块无关;周期默认 10 分钟,把预算调低即增大该流量。
