## 缓存淘汰实验
构造倾斜场景（C轨）：
WarmupTask A 反复读10%的热分⽚（模拟多轮微调和重复 epoch），WarmupTask B 顺序扫全量数据（流寇式扫描），缓存只给数据集的 30%
记录A的命中率和等待占⽐，以及B把热数据挤出去的次数
随后将缓存淘汰策略设为 heat（现有热度策略）、LRU、LFU，三种策略同台测试，给出数据

W-TinyLFU 撤档，不实现（2026-10-24 裁决）：单 Job 顺序读下它的准入收益不明确，
而 window + 两段 SLRU + count-min + doorkeeper 的实现与验证成本高；
现有实现只是频率排序代理，缺 window 与两段 SLRU，留场会让策略同台对比失真。

与持续预取的协同实验：
lookahead（取 8/16/32 三档）× 排序策略（heat/LRU/LFU 三档）⼆维命中率曲⾯。
说明两者如何相互影响

允许的阴性结论：如果顺序场景下三种策略没差异、倾斜场景下才有差异，就如实写”淘汰策略对单Job的顺序训练并不关键，真正关键的是预取调度与跨租⼾保护”

# 与Fluid基准框架一起上秤测试
把五组对照实验⾃动化，让”跟对⼿同台跑分”变成⼀条命令的事，这⼀步就是给项⽬装秤。
每组实验都要分别报启动阶段指标和全程阶段指标，不能只报全程 makespan ⽽隐藏持续预取的字节成本

七组对照：
1. 直读 MinIO，是完全不缓存的零缓存基线
2. JuiceFS 冷读，是对⼿⾸次访问，缓存是空的
3. JuiceFS 预热后热读，是对⼿预热完成后的效果
4. Fluid完整流程(冷读 + 热读),是按官⽅姿势部署 Dataset+DataLoad+亲和调度，最强⼯业基线 
5. TrainCache⾃⼰(冷读 + 热读)


指标：

| 指标       | 启动阶段（Pod 落地前）               | 全程阶段（Pod 落地后到训练结束）                 |
|------------|--------------------------------------|--------------------------------------------------|
| makespan   | Job 提交 → 第一个 step 开始          | Job 提交 → 最后一个 epoch 结束                   |
| stall 占比 | 第一个 step 的 wait_time / step_time | 全程所有 step 的 stall 时间序列                  |
| 缓存命中率 | 启动窗口内的缓存命中率               | 分阶段曲线：启动期 / 稳态期 / 阶段切换期         |
| 字节成本   | 启动预取字节 × fanout                | 启动预取 + 持续预取 + 阶段切换重预取，分三笔统计 |

具体做法：
1. 写实验编排脚本，保证五组实验吃同⼀份固定随机种⼦的请求轨迹⽂件；
2. 每组⾄少跑 3 次取平均数，并报告 bootstrap 95% 置信区间——只跑 3 次取中位数的结果不许进报
   告，这是硬纪律；
3. 环境全部锁定⼊库（镜像 digest、软件版本、tc 参数、随机种⼦），做到 make bench COND=xxx ⼀键
   复现任何⼀组。

## 缓存容量档位

真实训练⾥数据集通常是节点缓存的⼏⼗倍以上，只在⼀个容量⽐下跑分，结论⽆法外推。
五个受试者（即上文的七个组态）按容量⽐分三档：

| 档 | 数据 | 缓存 | 容量⽐ | 参跑组 | 每点次数 | 定位 |
|----|------|------|--------|--------|----------|------|
| S | 2GiB | 1GiB | 1:2 | 全部七组态 | 3+3（@100 与 @1000 各 3 次，符号翻转格补到 5）；@300 抖动格只跑 direct/fluid-cold/traincache-cold 各 3 次 | 正式结果，现状口径 |
| M | 8GiB | 1GiB | 1:8 | direct、fluid-cold、traincache-cold | 3 | 正式结果，欠配校验 |
| L | 32GiB | 1GiB | 1:32 | traincache-cold、fluid-cold | 1 | 探点：只看收益符号，不报置信区间，不进正式表 |

参跑组的「fluid 化」（2026-10-24 裁决，10.1 D30）：M 档与 L 档的 `juicefs-cold` 一律换成 `fluid-cold`。
欠配校验必须压在最强工业基线上，只比 JuiceFS CE 会被质疑「绕过 Fluid」。
JuiceFS 没有退出实验：`juicefs-cold` 与 `juicefs-warm` 仍留在 S 档的全部七组态里。
替补条款：Fluid 若触发 Q6 的两次环境性失败（`fluid-unavailable-on-kind`），
M/L 档该组自动落回 `juicefs-cold` 补跑，产物记 `baseline_substituted`，机时只花在失败路径上。

每点次数按带宽分区（2026-10-24 裁决，10.1 D31/D32）：S 档在链路受限区（@100）与预取有效区（@1000）
各跑 3 次，符号翻转的格子补到 5 次。依据是「至少 3 次取平均数 + bootstrap 95% 置信区间」
这条硬纪律——3 次只报中位数才是违规形态，3 次报均值 + CI 合规；
汇总列必须同时给 mean / median / p90 / CI。
临界区（BW/r ∈ [1,2]）只有 S@300（1.40）与 M@1000（1.16）两格，这两格加 netem 抖动；
抖动只改方差不改均值（10ms 标准差叠在 20ms 固定延时上），所以不额外占机时。

预注册假设：容量⽐越⼤，各组命中率越低、回源占⽐越⾼，TrainCache 相对基线的收益应增⼤；
增⼤不了甚⾄反转，如实记录。更⼤范围的⽐例扫点由图⼀（数据集/缓存容量⽐⾃变量）负责。
warm 组只出现在 S 档：1:8 及以下预热⾄多覆盖数据的 1/8，优势缩⼩是算术事实，不陪跑。
L 档的单点次数低于"⾄少 3 次"的硬纪律，因此产物标 exploratory，只⽤于回答
"M ⽅向是否延续"，不⽀持任何正式结论。

## 块⼤⼩与限速⼝径

- 块是 TrainCache 缓存与预取的最小单位。⽣产默认 64MiB 不变；实验环境通过
  trainpublish 的 `-chunk-size` 配置为 8MiB。原因：1GiB 缓存按 64MiB 切只有 16 块，
  预取保护窗⼝（lookahead 16 块）会覆盖整个缓存，淘汰策略的排序统计失真；
  按 8MiB 切有 128 块，窗⼝占缓存 1/8。该参数写在配置⽂件⾥，随产物⼊库、可复现。
- tc 限速与块大小无关，但**带宽本身是实验自变量**（2026-10-24 裁决，10.1 D31）：
  tc 的 rate 取 {100, 300, 1000} mbit（= 12.5 / 37.5 / 125 MB/s），随 COND 的
  `network.rate_mbit` 落盘。块大小只改请求次数与单请求时长，不改变链路带宽；tc 作用在
  节点网络层，对七个组态一视同仁。8MiB 块的单请求延迟开销约占传输时间 3%
  （20ms RTT / 0.64s 传输 @100mbit），可忽略。
- 带宽档按「链路带宽 ÷ 每步读量」（BW/r）分三类。每步读量 r = 数据集字节 ÷
  （每 epoch 400 步 × 每步 200ms 计算）——一个 epoch 恰好 80 秒过完全量，得
  S≈26.8、M≈107.4、L≈429.5 MB/s。比值 < 1 是链路受限区（S@100=0.47，
  L 档三个带宽档 0.03/0.09/0.29 全在此区）；比值 > 2 是预取有效区（S@1000=4.66）；
  [1, 2] 是临界区，全表只有 S@300（1.40）与 M@1000（1.16）两格，只有这两格启用
  netem 抖动（`delay 20ms 10ms distribution normal`）。开关由
  `config.jitter_enabled(tier, rate)` 从档位与 rate 推导，不是 COND 字段，避免出现
  两个互相矛盾的真相。抖动是方差来源，抬不动均值比值，不能替代带宽档。
- burst 与 rate 联动：取「≈ 0.1 秒的传输量」= 1250k / 3750k / 12500k
  （`config.burst_for_rate`）。旧固定 1600k 在 100mbit 下是 128ms 突发窗口，
  沿用到 1000mbit 只剩 13ms，禁止跨档复用。
- 跑分第一格先做前置探针：无 tc 状态下测 MinIO 实际吞吐上限 C。每格的有效带宽取
  min(名义 rate, C)：C < 125MB/s 时 @1000 不再是一个独立档位；若 @300（37.5MB/s）也一起被 C
  封顶，这几格塌缩成同一个「源站封顶档」，只保留一个并标 `ceiling`。BW/r 分区与抖动格
  按有效带宽重算，实测 C 与重算结果一起回写 D31 与 10.1 §12 的机时表。
