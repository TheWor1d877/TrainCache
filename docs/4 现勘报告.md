## 0. 摘要与闸门判定

现勘验证了三个问题,结论如下(第 3 条为 2026-10-13 补强):

1. **Fluid 是否真的没做"预热—调度"联动?** 成立,且比 P1 笔记的预期更强:开源 Fluid 1.1.0-alpha.9 在 JuiceFSRuntime 上**连 webhook 粗粒度注入都消失了**(实测注入前后 diff 为零,见 §2.2),预热(DataLoad)与调度(Pod 创建即被调度,时间戳同秒)完全独立。
2. **JuiceFS 社区版的能力边界?** 确认:CE 只有本地缓存;分布式缓存组、IORPC、RDMA 均为企业版(5.2/5.3+)能力,且有官方文档佐证。
3. **对手是否具备"阶段感知/按消费顺序持续预取"能力?** **判定:无阶段感知**(2026-10-13 补强,见 §5):三 epoch 换序读实验在三个切换点 × 三个观测点(客户端块级日志、Dataset cached 抬升、UFS 流量)全部被动,零超前于读取的自动预取动作;手动 DataLoad 预热可行但需外部显式触发。

**闸门判定:缺口成立 → 核心1 按"闭环"叙事推进**(P1 现勘闸门 ①)。

**v4 第一步闸门判定:对手"无阶段感知"成立(§5)→ "阶段感知/按消费顺序持续预取"列为缺口项,证据已纳入 §4 边界表。**

## 2. 官方 demo 与证据抓取(动作2)

### 2.1 链路与数据导入

Dataset `jfsdemo` + JuiceFSRuntime(同名绑定)→ format(元数据进 redis,数据块落 MinIO)→ **数据导入**(裸对象→JuiceFS 文件系统)→ DataLoad(warmup)→ 训练 Pod。

导入方式(踩坑后定稿):`juicefs sync` 以 `jfs://` 协议直写文件系统,源 URI 为路径式 `minio://AK:SK@endpoint/bucket`。该镜像客户端(ce-v1.3.0)已移除 `juicefs import` 命令;Fluid 的 PVC 只读,挂载写不可行。

### 2.2 发现一:webhook 注入前后 diff 为零

dry-run(绕过 webhook)与实际创建(经过 webhook)的 Pod spec 对比(`evidence/pod-before-injection.yaml` vs `pod-after-injection.yaml`):

| 观察项 | 结果 |
|---|---|
| FUSE sidecar 容器注入 | **无**——容器列表只有用户的 busybox。FUSE 由 Fluid CSI(node plugin)+ `jfsdemo-fuse` Pod(每节点一个)在 kubelet 层完成挂载,Pod 内只见普通 volumeMount |
| nodeAffinity / nodeSelector 注入 | **无**——P1 笔记描述的"webhook 注入亲和"在此版本+Runtime 组合下不复现 |
| 其他注入 | 仅 k8s 默认字段(serviceaccount projected volume、默认 tolerations) |

而 `JuiceFSRuntime.status` 里 Fluid 维护着 `cacheAffinity`(`evidence/runtime-status.txt`):
worker 节点被打上 `fluid.io/f-default-jfsdemo=true` 标签,亲和策略为 `preferredDuringSchedulingIgnoredDuringExecution`(weight 100),**required 项为空,且未注入到任何 Pod**。

**解读**:Fluid 1.1 把 JuiceFS 访问全面 CSI 化后,传统 webhook sidecar 注入路径不再使用;缓存亲和退化为 runtime status 里的"软偏好+节点标签",既不强制也不自动。这与 P1 笔记的外部事实"粗粒度二进制+事后注入"相比,注入环节已弱化,但"二进制(有无缓存 worker)而非块级进度"的粒度问题依旧。

### 2.3 发现二:Pod 不等 DataLoad(时序证据)

`evidence/timeline-notes.txt`(全部同一秒,来自 `kubectl get pod -o jsonpath`):

| 时刻(UTC) | 事件 |
|---|---|
| 08:33:39 | train-demo creationTimestamp |
| 08:33:39 | PodScheduled 条件生效 |
| 08:33:39 | startTime(容器启动) |

Pod 从创建到被调度到 `traincache-worker` 到启动,**同一秒完成,零等待**。DataLoad 是之后手动创建的独立资源(10:00 与 16:26 各运行一次),**没有任何机制让 Pod 等待预热完成**——"先被调度、再等数据"的 P1 论断成立(且在本装置上数据已在文件系统里,连"等数据"都由 FUSE 冷读承担,调度器一无所知)。

### 2.4 发现三:两次 warmup 的结果差异与 3.9G 污染事件

DataLoad 的 loader Job 在 worker Pod 里执行 `juicefs warmup <worker挂载点>`,两次运行结果不同:

| 时间(UTC) | warmup 结果 | 证据 |
|---|---|---|
| 02:00:12(10:00 CST) | **0 files (0 B)** | `evidence/loader-jfs-load.log`、`dataload-timing.txt` |
| 08:26:55(16:26 CST) | **548 files (3.9 GiB)** | 执行时终端日志(用户记录) |

10:00 那次 warmup 为 0 files,但同一脚本里 `ls` 挂载点能看到 shard-00000/00001.tar——两次差异的机制与 worker 生命周期相关(jfsdemo-worker-0 于 12:38 重启,16:26 的 warmup 在重启后的 worker 上成功),**结论按实记录:warmup 行为依赖 worker 挂载状态,失败时 DataLoad 仍会以 Complete 结束**(10:00 那次 DataLoad PHASE=Complete、DURATION 6s,`evidence/dataload-status.txt`)。

**3.9G 污染事件(装置侧教训,如实记录)**:导入时源 URI 拼重(`train-data//train-data/`)导致 sync 把 JuiceFS 自己的数据块对象镜像进了文件系统本身,文件系统 = 16 tar(1.97GiB)+ `traincache-demo/chunks/` 垃圾镜像(1.97GiB)≈ 3.9G(`evidence/import-pod.log`)。这直接导致 warmup 3.9GiB 超过 3Gi 缓存配额、热读被 LRU 淘汰打折——**恰好是"预热成本无人记账"的装置侧缩影:多拉 2 倍数据,系统毫无提示**。垃圾目录的清理状态见 §7 遗留事项(2026-10-13 已随元数据重建消解)。

### 2.5 训练 Pod 读数据(端到端成立)

`evidence/train-pod.log`:经 Fluid 挂载的 `/data` 可见 16 个 shard-*.tar,`du -sh` 3.9G(含垃圾),读 tar 前 1MB 成功——Fluid 链路端到端可用。

不经过 Fluid,用挂载镜像直接裸挂载同一文件系统(`../survey/manifests/jfs-standalone.yaml`),装置与结果(`evidence/standalone-baseline.txt`):

| 项 | 记录 |
|---|---|
| 客户端版本 | juicefs **1.3.0**+2025-07-03.30190ca1 |
| 挂载参数 | `metaurl=redis://redis.default.svc.cluster.local:6379/0`,`--cache-dir /cache --cache-size 3072`(本地缓存模式) |

### 5.2 集群修复与重装记录(轻修 vs 重建)

**现象与根因**:kind 节点容器重启后,containerd 残留旧容器条目造成 name reservation 冲突(kubelet 日志:"check if another CreateContainer request is in progress: name ... is reserved for ..."),kube-system 与 minio 命名空间多个 Pod(修复前约 10 个)报 CreateContainerError,Fluid 整体不存在(无 fluid-system ns、无 CRD、helm list 为空)。

**修复选择**:采用**第一档轻修**——逐节点删除 Exited 容器条目并重启 kubelet:

```
for n in traincache-control-plane traincache-worker traincache-worker2; do
  docker exec $n bash -c "crictl ps -a | grep Exited | cut -d' ' -f1 | xargs -r crictl rm -f"
  docker exec $n systemctl restart kubelet
done
```

共删除 12 个残留条目(control-plane 7 + worker 2 + worker2 3),修复后 `kubectl get pods -A` = 23/23 Running。**未采用第二档重建**:重建需先恢复 kindest/node:v1.37.0 的镜像 tag(宿主机仅剩 dangling 状态,见 §7),存在 docker hub 拉取不可达风险。

**镜像**:docker hub 不可达,全部 `kind load`(redis:7-alpine、busybox:latest,以及 9 个 Fluid/JuiceFS 镜像:7 个 fluidcloudnative:v1.1.0-36f0467 全套 + juicefs-csi-driver:v0.32.0 + mount:ce-v1.3.0)。

**Fluid 重装**:官方 helm repo index 未收录 alpha 版本(/tmp/fluid 残留也已不存在),改从 GitHub release 直下离线 tgz(`helm-chart-fluid-1.1.0-alpha.9`),`helm install` 到 fluid-system(带 `--set runtime.juicefs.enabled=true`);chart appVersion 1.1.0-36f0467 与本地镜像 tag 一致,`helm list` 状态 deployed(`evidence/fluid-install-helm.txt`)。

**数据恢复**:MinIO 内 train-data bucket 缺失(非重建引起,minio Pod 自 3d20h 前持续存在),经 `kubectl port-forward` 通道重传 16 分片共 1.97GiB(耗时 5s);随后照序 apply(redis → jfs-secret → dataset → juicefsruntime),JuiceFSRuntime Worker/FUSE Ready、Dataset Bound、PVC Bound。

**装置改动:quota 3Gi→1Gi**。将 Runtime 缓存配额自 3Gi 下调为 1Gi(低于数据集总量≈2GB),设计意图是**欠配使每次 epoch 切换必然产生缓存 miss**,给"主动预取"制造可观测的发挥空间。该改动的装置副作用见 §5.5(节点 /dev/shm 仅 64MB,配额名存实亡)。

### 5.3 三 epoch 换序读实验装置

- **读序构造**:`train-demo` 对挂载点内 16 个 `shard-*.tar` 逐一 `dd`(每分片≈126MiB,每 epoch 合计≈2.0GiB)。E0 升序;E1 按 `random.Random(17).sample(range(16),16)` 置换;E2 按 `random.Random(42)` 置换;两个置换离线生成后**字面量嵌入** Pod 脚本(经 `sh -n` 校验)。本报告复核:E1/E2 实际读序与上述种子置换逐一一致(`evidence/train-pod-3epoch.log`)。
- **观测窗口**:13:26:15Z ~ 13:29:20Z(E2 完成 +2min)。
- **三个切换点**:A = 窗口起点(E0 冷启动;消费端 fuse 客户端为新挂载、缓存空);B = E0→E1(13:27:19.704Z);C = E1→E2(13:27:19.894Z)。
- **三个观测点**(采样:Dataset status 与 Runtime/控制器日志 10s 一轮;MinIO netns 计数与客户端 metrics 3s,更细以对齐切换点):
  1. **客户端块级/预热日志**:Runtime/FUSE/CSI 日志的 warmup/prefetch 关键词与消费端 fuse 客户端(:15506)的缓存 miss 增量;
  2. **Dataset status `cached` 抬升**:是否超前于 Pod 读取;
  3. **UFS 流量**:MinIO Pod netns eth0 的 tx 计数(≈ JuiceFS 自对象存储拉取字节)。
- **判读标准**:任一切换点出现任何超前于读取的预热/块获取动作 → 主动;三者全无 → 被动。

### 5.5 判定

**判定:无阶段感知。** 三个切换点 × 三个观测点全部为被动(§5.4.2),观测窗口内预热/预取零动作;预热只能由外部显式触发(手动 DataLoad,§5.4.2)。结论:开源 Fluid(1.1.0-alpha.9)+ JuiceFS CE 1.3.0 组合**不存在任何"按训练阶段/读序切换自动预取下一批数据"的机制**,更谈不上"按消费顺序持续预取"。

**装置混杂与证据强度限定(如实记录)**:

1. **页缓存吸收,切换点"无可预热的缺失"**:E1/E2 每 epoch 仅 ≈0.19s / ≈0.18s、分片瞬时 11-15GB/s,零 UFS 流量——数据全部命中内核页缓存,消费端在 JuiceFS 层没有产生任何 miss(消费端 fuse `read` ops≈16207 ≈ E0 一次全量读取在 128KB 粒度下的次数,E1/E2 基本未经 FUSE)。因此观测点③在切换点的区分力受限:即便存在"按 miss 触发"的预取,切换点也没有可被激励的 miss。E0 冷读仅 0.90s(分片 1.7-2.7GB/s)亦因 kind 内网直连 MinIO,冷热差被压缩。
2. **/dev/shm 仅 64MB**:kind 节点 /dev/shm 为 64MB,JuiceFS 客户端按 freeratio 将 1GiB 声明配额再压至 **60,397,976B(≈57.6MB)**——"quota 3Gi→1Gi 欠配"的设计名存实亡(容量小到连单分片 126MiB 也存不下);证据:`evidence/fluid-runtime-log-3epoch.txt`(Adjusted cache capacity 行)。
3. **证据强度分级**:日志级证据(窗口内零自动预热动作、零 warmup/prefetch 关键词;fuse 客户端 miss 全部由 E0 读取同步产生且其后不增长)为**强**;"UFS 流量在切换点被动"一条因页缓存混杂而**削弱**(且手动预热对照暴露了流量观测口径的盲区);Dataset `cached` 首次非空晚于读取完成仅作**弱佐证**(Fluid 统计刷新滞后,基线时该字段甚至为空串)。
4. **(可选)补测方向**:放大 /dev/shm 或改用 O_DIRECT 绕过页缓存,做一次"切换级纯 UFS 缺失"实验,可把观测点③在切换点的区分力补满。

**实验后装置状态**:train-demo、手动 DataLoad(及其 loader Job)、import pod 均已清理;PVC/Dataset/Runtime 完好;未回收的 fuse pod 与节点标签、镜像 dangling 等见 §7。
