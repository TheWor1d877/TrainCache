# eBPF 观测工具

目标：补上内核侧观测。用户态的 inotify 与 dataloader 打点只能说明文件发生了什么、数据什么时候被用到，块设备 I/O 延迟、major fault 的次数与耗时、预读是否产生无效 I/O，都要从内核侧取。
交付: 一个只读 eBPF 工具集，块 I/O、major fault、预读三类观测在同一轮读数据负载中出数。

## 部署形态

工具是单机二进制，不依赖任何实验装置，装到任何一台跑 Linux 的机器上都能开始采数。部署位置选在被观测负载所在节点内，输出结构化数据文件，数据文件落在本台机器上的指定位置(能选择文件夹)。并且在终端中直接输出该次结果指标。

节点上只放这一个二进制，采集、事件配对、指标计算与结果输出都在里面完成，不要求节点上有 Python 环境，本工具全程不依赖 Python。工具输出结构化指标文件与终端摘要，指标文件的字段与指标清单一一对应。

独立进程，与 TrainCache 并行运行，通过时间戳对齐，不写入 TrainCache 内部日志。

部署范围是单机场景，不做集群聚合

kind 节点是特权容器，与宿主共享同一个内核。eBPF 程序从节点内加载，挂到的仍是这个共享内核，观测范围覆盖内核上所有进程的块 I/O 与缺页事件，与从宿主加载看到的事实相同。

eBPF 事件携带宿主级 PID 编号，节点容器内的进程编号是另一套命名空间，两者不一致。进程归因用 comm 与 cgroup id，cgroup id 与命名空间无关。

## 范围与约束

- 只读观测，不修改被观测对象。
- 不写内核模块，不改缓存核心代码。

## 观测项
### 块 I/O 延迟

挂载 `block:block_rq_issue` 与 `block:block_rq_complete`，按 request 指针配对，配对表放 per-CPU map 或 hash map。内核侧按 log2 桶累加直方图，用户态周期拉取。issue 后没有 complete 的请求走超时清理路径，否则配对表持续增长。bpftrace 验证阶段没有超时清理能力，泄漏的条目靠重启探针清掉，正式工具必须实现这条路径。

### major fault

kretprobe 挂 `handle_mm_fault`，读返回值标志位，`VM_FAULT_MAJOR` 为 `0x4`，置位即 major fault。major fault 才需要从块设备取数据，minor fault 不产生块 I/O。计数与同时间窗 `/proc/vmstat` 的 `pgmajfault` 增量对照，两者一致说明探针读对了标志位。major fault 次数强依赖被观测进程有没有关预读：fault-around 开着时，一次冷 mmap 的相邻页被内核顺带映射、后续访问算 minor fault，major 计数会摊薄到个位，报数要连同这个前提一起给。

`exceptions:page_fault_user` tracepoint 在宿主机上可用，但它不区分 major/minor，不作为分类依据。

### 预读归因

内核提供三个 filemap tracepoint，都携带 `s_dev`、`i_ino`、`index` 字段；`mm_filemap_add_to_page_cache` 另带 `order`，`mm_filemap_get_pages` 另带 `last_index`：

| tracepoint | 触发时机 |
|---|---|
| `filemap:mm_filemap_add_to_page_cache` | folio 进入页缓存，含预读带入的页；`order` 表示本次进的是从 `index` 起的连续 `2^order` 个页 |
| `filemap:mm_filemap_fault` | 缺页路径消费页缓存中的页 |
| `filemap:mm_filemap_get_pages` | read() 路径消费页，命中与未命中均触发，另带 `last_index`，一条事件覆盖一段页区间 |

按（设备、inode、页索引）配对进缓存事件与两个消费事件，判定预读页是否被消费，进缓存后从未被消费的页计入无效预读。进缓存事件按多页 folio 触发，一个事件覆盖从 `index` 起的连续 `2^order` 个页，换算页数要按 `2^order` 累加，直接数事件条数会把页数低估几十倍。

eBPF 侧只记录事实：页面访问事件、块 I/O 事件、major fault 事件及其进程信息。归因逻辑放用户态配对阶段。预读产生的 major fault 可能记不到消费者进程名下，fault 与 I/O 时间接近但发起者不一致时，标注为「疑似预读归因偏移」，eBPF 层不做猜测性归因。

### 时钟对齐

bpftrace 的 `nsecs` 是单调时钟，跨进程对齐用 epoch。每轮开始记录一对偏移：同时读 `/proc/uptime` 与 `date +%s%N`，写进 run 目录，内核侧事件时间戳经偏移换算成 epoch，与负载运行的起始时间对齐。

## 指标清单

| 指标 | 单位 | 维度 | 采集点 |
|---|---|---|---|
| 块 I/O 延迟分布 | µs，log2 直方图 | 设备、读/写 | `block_rq_issue` 与 `block_rq_complete` 按 request 指针配对 |
| major fault 次数 | 次 | cgroup、pid、comm | kretprobe `handle_mm_fault`，返回值置 `VM_FAULT_MAJOR` 位 |
| major fault 耗时 | µs | cgroup、pid | kprobe 与 kretprobe 配对 `handle_mm_fault`，仅统计置 MAJOR 位的返回 |
| 预读进缓存页数 | 页 | 设备、inode | `mm_filemap_add_to_page_cache` 按 `Σ2^order` 累加（事件数不等于页数） |
| 预读页消费数 | 页 | 设备、inode、页索引 | `mm_filemap_fault` 每页计 1，`mm_filemap_get_pages` 按 `last_index − index + 1` 计，与进缓存事件按三元组配对 |
| 无效预读比例 | % | 设备、inode | （进缓存页数 − 消费数）÷ 进缓存页数 |

过滤口径：文件打开与缺页事件按消费者 Pod 的 cgroup id 过滤，覆盖 Pod 内全部进程；块 I/O 事件按缓存盘设备过滤，归因在用户态时间线阶段完成。


## 实现阶段

### 阶段一：bpftrace 观测可行性验证

用 bpftrace 验证四个问题：块 I/O 延迟直方图能否出数；kretprobe 能否读对 fault 标志位；filemap 事件能否配对；延迟量级是否合理。这一阶段的验证对象是观测点，不是交付最终工具。

bpftrace 有三件事做不到，而这三条正好是交付工具必须具备的。配对表的超时清理做不出来，脚本没有按时间淘汰表项的手段，泄漏的条目只能靠重启探针清掉。per-CPU map 与 ringbuf 的尺寸与采样策略由脚本间接决定，不好按负载调。探针逻辑写在脚本里，分发与版本管理没有 libbpf 那套骨架可用。

所以阶段一只回答观测点行不行，行了才进阶段二；阶段二用 libbpf 加 C 把这几件事补上。

### 阶段二：libbpf + C 正式工具集

用 libbpf 加 C 实现正式工具集，骨架由 `bpftool gen skeleton` 生成。工具集是一个二进制，从 ringbuf 收事件，周期拉取 per-CPU map，在用户态完成事件配对与指标计算，把事件、直方图与算出的指标写成数据文件落到指定目录，并在终端打印本轮摘要。per-CPU map、ringbuf、配对表清理路径与探针开销在这一阶段控制，这些环节在 bpftrace 里被抽象掉了。per-CPU map 与 ringbuf 的取舍以低开销与不丢事件为两端，选择理由和实测结果写进工具的报告输出。

配对与指标计算放在二进制里，是因为这部分逻辑在设计阶段就定死，运行时不改，而节点上只需要一个可执行文件。代价是预读页配对与 fault 归因要用 C 的哈希表自己维护，没有现成的容器可用。

本工具不出图，也不生成报告文档。它输出的指标文件是唯一的产物格式，后续怎么读这份文件不在本工具范围内。

### 分发方式

bpftrace 走官方静态二进制：取 v0.25.0 发布资产里的单文件 bpftrace，宿主下载后经 `docker cp` 传入节点，不构建镜像。

## 在 bench 装置里的接入

bench 在这份文档里只承担一个角色：提供被观测的读数据负载，并给出一次跑分的产物目录。工具本身在负载运行期间并行跑在旁边，产物和负载侧的指标放在同一轮 run 目录里。

一次跑分对应一个 COND，由 `bench/experiments/run.py` 编排，产物落在 `reps_dir/<run_id>/`。train 形态那一步用 `bench/scripts/load_train.py` 跑负载，负载结束后 `bench/experiments/collect.py` 采集指标。

接入方式：run.py 在 load 步骤前把工具进程拉起在消费者所在节点，指定产物目录为本次 run 目录，工具在终端输出本轮指标；load 结束后工具停止。探针开关不进 COND，由运行参数控制，同一个 COND 跑两遍，一遍开探针一遍关探针。

探针开销的算法用 bench 现成的产物算。`bench/scripts/load_train.py` 每步往 `per_step_<seed>_w<workers>.jsonl` 写一行，字段 `wait_s` 是取数等待时长（上一步 compute 结束到 batch 就绪，不含 compute），`step_s` 是含 compute 的整步时长。探针挂在块 I/O 与缺页路径上，代价落在 `wait_s` 上。

主口径取 `wait_s` 的 P99 差值，即开探针一遍的 P99 减关探针一遍的 P99，单位 ms。bench 现有的聚合只算了 `median_stall` 与 `mean_stall`（`stall = wait_s / step_s`，见 `load_train.py` 的 `stall` 函数），P99 没有现成输出，由 bench 侧从同一份 per_step 记录补一次分位数统计，load 侧不用改。这一步是 bench 自己的统计，与工具无关，工具不参与。

交叉核对用 `metrics.csv` 的 `full_makespan_s` 差值，加上 bench 现成的全轮 `median_stall` 差值。

不变量对照用 `total_fetch_bytes` 与 `hit_ratio_steady`。探针只读，这两项在两遍之间应当基本一致；这两项也变了，说明两遍不可比，开销数据作废。

### 工具开销评估

开销分两层，量法不同。

第一层是装置自身的开销：探针进程的 CPU 时间、事件速率、ringbuf 丢事件计数、per-CPU map 与配对表的内存占用。这一层不依赖负载，空载机器上也能测，工具跑一段固定时长后自己报出这些数。

第二层是挂上探针对被观测负载的影响。探针挂在块 I/O 与缺页这些热路径上，被观测负载的取数等待会变长。同一份负载配置跑两遍，一遍不启动工具，一遍启动工具并挂上探针，比较两遍的取数等待分布，差值就是这一层的代价。

这个对照只属于工具开销评估，是工具研发阶段的一次性实验。生产训练跑一遍就够，工具开着直接采数，不需要再跑一遍没有工具的对照。对照实验要的是同一份负载配置下的两遍数据，不要求完整训练一遍，跑几轮数据即可。

## 验收标准

1. 块 I/O、major fault、预读三类观测在同一轮读数据负载中出数，时间戳与该轮运行的起始时间对齐。
2. 预读收益与无效预读比例有数据支撑。
3. 探针自身开销有测量结果，含对被观测负载取数等待 P99 的影响。
