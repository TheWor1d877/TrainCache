# 8.4 controller 测试说明书

> 配套 design.md `8.1`、plan.md `8.2`、decisions.md `8.3`。读者懂 Go 和 K8s 基础就能跟下来，新名词第一次出现顺手解释。

## §1 这份文档在说什么

controller 是集群控制面组件（Kubernetes controller-manager 内跑），管预热生命周期 + Scheduler 打分，不直接碰数据面。当前共有 **52 个 `*_test.go` 文件**、**约 12,000 行测试代码**、**约 300 个 `Test` 函数**，覆盖 api/v1alpha1、internal/controller/{dataset,warmup}、internal/gwaa、internal/gate、internal/nodescore、internal/scorefmt、internal/webhook、internal/scheduler、internal/agentclient、internal/storage、internal/config/logging/metrics、cmd/{controller-manager,webhook,scheduler} 共 **19 个子包**。测试框架同 core/agent：`testing` + testify + controller-runtime 的 envtest（k8s API Server 本地进程）；GWAA、Gate、Filter、scorefmt 是纯函数，直接喂 struct 断言不碰 k8s。

一句话：覆盖了控制面的全部核心链路，纯函数层（GWAA / Gate / scorefmt）测试密度高、端到端靠 envtest 支撑 k8s 对象流转。

## §2 怎么跑

```bash
# 全量
cd controller && go test ./... -race -count=1
# 示例输出摘要
# ok   traincache/controller/api/v1alpha1       0.6s
# ok   traincache/controller/internal/config     0.3s
# ok   traincache/controller/internal/logging    0.3s
# ok   traincache/controller/internal/metrics    0.4s
# ok   traincache/controller/internal/gwaa       1.2s   # 纯函数，快
# ok   traincache/controller/internal/gate        0.5s   # 纯函数，快
# ok   traincache/controller/internal/nodescore   0.4s
# ok   traincache/controller/internal/scorefmt   0.4s
# ok   traincache/controller/internal/agentclient 0.8s   # bufconn gRPC
# ok   traincache/controller/internal/storage     0.5s
# ok   traincache/controller/internal/webhook     0.6s
# ok   traincache/controller/internal/scheduler   0.7s
# ok   traincache/controller/internal/controller/dataset  2.3s  # envtest
# ok   traincache/controller/internal/controller/warmup   4.1s  # envtest
# ok   traincache/controller/cmd/...             0.4s

# 只跑纯函数层（最快，不到 3 秒）
go test ./internal/gwaa/... ./internal/gate/... ./internal/scorefmt/... -v

# 跑 GWAA 全部 31 个测试
go test ./internal/gwaa -run 'TestCompute' -v

# 跑门控判定
go test ./internal/gate -v

# 跑 MinUnmet 端到端（M14 增量）
go test ./internal/controller/warmup -run 'MinUnmet' -v
```

controller 依赖 k8s.io/apimachinery + controller-runtime。envtest 需要先 `go install sigs.k8s.io/controller-runtime/tools/setup-envtest@latest`，再 `export KUBEBUILDER_ASSETS=$(setup-envtest use -p path)`。GWAA/Gate/scorefmt 三个纯函数包不依赖 envtest，跑起来最干净。

## §5 已知未覆盖的点

**(a) 低优先级不打算补**

| 未覆盖项 | 理由 |
|----------|------|
| `cmd/` 三个入口程序的集成启动测试（controller-manager + leader election、webhook + HTTP server、scheduler + framework 注册） | 三个 main 函数极薄，只装配依赖然后阻塞。已有单元测试覆盖配置加载和组件初始化。集成启动需要 kind 集群 + RBAC + kube-scheduler 自定义镜像，工程量大且对冻结接口覆盖无增益 |
| Scheduler 插件在真实 kube-scheduler 进程内的端到端 | 当前靠 envtest 测 Score/NormalizeScore 纯逻辑即可。真实 kube-scheduler 的调度循环是 framework 内部机制，plugin 只实现 ScorePlugin 接口方法。plugin_test.go 已经覆盖了全部冻结语义 |
| controller 与真实 Agent 进程的联调 | controller 侧 gRPC Pool 只实现 4 个 RPC 的客户端调用语义（超时、generation 幂等、错误映射），Agent 侧服务端实现已由 `agent/svc` 覆盖。两边通过 bufconn 做内存连接测试已经足够。 |

**(b) 暂时技术困难**

| 未覆盖项 | 困难在哪 |
|----------|----------|
| WarmupTask reconcile 与 Poll 的并发安全（MaxConcurrentReconciles=1 已串行，但 Poll 定时跑会不会和 reconcile 撞） | 两者共用 controller-runtime 的 manager 主循环 + 定时器。要精确构造 reconcile 执行到一半时 Poll 触发的竞态，需要注入可控的延迟钩子，侵入性大。当前靠 `race detector + Poll 每 100ms 调一次 + reconcile 串行` 间接覆盖 |
| GWAA 的 Rounds 边界（最多 len(Pods) 轮、未收敛保留首个贪心结果并 warn） | 要构造"GWAA 跑 len(Pods) 轮仍未收敛"的场景，需要精心编排每个 Pod 对每个节点的 c_ij 值矩阵，且随机种子恰好让冲突裁决交替让步。概率性场景，写 deterministic 测试困难 |
| DataSet controller 读真实对象存储（S3/MinIO）验证快照 | 当前 storage.Validate 用 core 的 mock Store，已经覆盖 CURRENT + manifest + 分片校验逻辑。真实 S3 集成测试需要 CI 预置凭证，同 core 的 s3_integration_test.go 问题一致 |

**(c) 打算以后补**

| 未覆盖项 | 什么时候补 | 验收标准 |
|----------|-----------|----------|
| Webhook 在 Pod 创建流程中的完整链路（PodMutator → schedulingGate → Scheduler ScorePlugin → 放行 → Gate 判定） | controller 8.5 里程碑 | kind 端到端：创建 WarmupTask + Training Pod → 验证 Pod schedulingGates 被注入 → Scheduler ScorePlugin 读取 annotation 打分 → 门控放行后 schedulingGates 被移除 → Pod 调度成功 |
| agentclient.Progress 在 Agent 真实返回部分位图损坏时的降级行为 | controller 8.4 里程碑 | 构造 Agent 返回的 bitmap 长度与请求 chunks 数不符 → controller 置该 PodNodeReadiness.State=Failed → Poll 下一轮重试 |
| GatePolicy 的 Gap/Slope 在 MinInterval 边界下的采样时序 | controller 8.4 里程碑 | 构造两个 Pod，第一个在 t=0 时 Ready（置 FirstReadyAt），第二个在 t=MinInterval+1s 时 Ready。在 t=MinInterval 时刻 Evalute：条件②不满足（第二个 Pod 间隔不足 MinInterval）→ Hold；在 t=MinInterval+Δt 时刻 Evalute：条件②满足 → Released |
