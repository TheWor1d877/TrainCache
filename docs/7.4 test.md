# 7.4 agent 测试说明书

> 配套 design.md `7.1`、plan.md `7.2`、decisions.md `7.3`。读者懂 Go 和 K8s/存储基础就能跟下来，新名词第一次出现顺手解释。

## §1 这份文档在说什么

agent 是缓存节点上的常驻服务（`traincache-agentd` DaemonSet Pod），把 core 库包装成带 gRPC 接口和自治能力的进程。当前共有 **43 个 `*_test.go` 文件**、**约 15,470 行测试代码**、**约 271 个 `Test` 函数**，覆盖 api/agentpb、svc、prefetch、collector、evictor、rescan、ordersource、metrics、nodeid、internal/logging 共 **10 个包**。测试框架同 core：`testing` + testify + mockey；gRPC 层用 bufconn 做内存连接（不启动真实端口）；对象存储和 CAS 沿用 core 的 mock/临时目录；Prefetcher 直接注入 mock Fetcher。

一句话：覆盖了从协议层到自治层的全部 10 个包，单元和端到端并重，冻结接口和自治逻辑都有对应测试。

## §2 怎么跑

```bash
# 全量（含竞态检测）
cd agent && go test ./... -race -count=1
# 示例输出摘要
# ok   traincache/agent/api/agentpb    0.3s
# ok   traincache/agent/svc            4.7s
# ok   traincache/agent/prefetch       2.8s
# ok   traincache/agent/collector      1.1s
# ok   traincache/agent/evictor        1.6s
# ok   traincache/agent/rescan         0.8s
# ok   traincache/agent/ordersource    0.9s
# ok   traincache/agent/metrics        0.4s
# ok   traincache/agent/nodeid         0.2s
# ok   traincache/agent/internal/logging 0.3s

# 只跑 gRPC server 相关
go test ./svc -run 'TestServer' -v

# 跑端到端场景（selfopen、e2e 结尾的文件名）
go test ./svc -run 'TestSelfopen|TestReadMiss|TestR1R3' -v
```

agent 的测试依赖 core 包（`replace traincache/core => ../core`），在 `go.work` 里统一管理，跑之前要在仓库根 `go work sync` 过一次。

## §5 已知未覆盖的点

**(a) 低优先级不打算补**

| 未覆盖项 | 理由 |
|----------|------|
| Agent gRPC server 与真实 k8s client-go 的集成（e.g. Service Discovery / EndpointSlice） | Agent 只做 Server，不做 Client；南向调用 Controller 的逻辑在 controller 模块的 agentclient 包里。agent 侧测试不需要碰 k8s 客户端 |
| ReportBlocks 北向服务端实现（Controller 侧） | 已登记为 decisions Q1，推迟到 Controller 里程碑。agent 侧当前只测消息结构 |
| CLI `cmd/traincache` 的命令行解析和表格输出 | CLI 是薄壳（纯 gRPC 客户端），解析逻辑 cobra 负责，输出逻辑独立。当前有 smoke 测试但不完整 |

**(b) 暂时技术困难**
