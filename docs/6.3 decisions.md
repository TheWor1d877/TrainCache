### D1 文档体系

**结论**:7.0 的下游三件套,文件名和内部标题都不带编号。**为什么**:6.x 文件内部编号与外文件名已不一致,不再制造第二层映射混乱;三件套与核心库三件套(6.1/6.2/6.3)平行。

### D2 模块落位

**结论**:`agent/` 独立 Go module(`traincache/agent`),并入根 go.work(use ./core ./agent),go.mod 不写 replace。**为什么**:延续 core D1/D16"独立 module"精神——module 独立、免 replace、workspace 统一解析;根 go.work 已提交且 agent/ 在其目录树下,不在 use 列表时 go build 直接报错。

### D3 三个可执行产物

**结论**:产出 `traincache-agentd`(Go,DaemonSet)、`traincache-ordersrc`(Python sidecar)、`traincache`(Go CLI)。**为什么**:sidecar 的顺序语义必须与真实 loader 的 shuffle 一致(torch / webdataset RNG),Python 直接复用训练生态,Go 复刻 RNG 风险高;共享内存协议语言中立(design §6.2)。

### D4 包结构与依赖方向

**结论**:目录树按 cmd → svc → 子模块 → core 单向无环(design §4)。**为什么**:与 core"单向无环"同风格;子模块互不依赖可并行派活;ordersource 不依赖 core。

### D5 端口

**结论**:gRPC 用 9410,指标用 9411,都可用 env 改。**为什么**:避免 root 端口;固定默认值保证 CLI / 探针 / 抓取一致(非特权端口)。

### D6 gRPC 服务划分

**结论**:先做南向 PreheatService + NodeService;北向 ReportService(ReportBlocks 流)proto 随本设计冻结,服务端实现推迟至 Controller 里程碑。**为什么**:7.0 验收只含南向;北向方向性(谁拨号)依赖 Controller 设计(Q1),先冻结契约不阻塞。

### D7 任务寻址与状态机

**结论**:任务引用 =(dataset, snapshot_id, prefixes, chunks);chunk 复用 core (path, chunk int64);状态机 QUEUED / RUNNING / DONE / ERROR。**为什么**:7.0 CLI 状态只列"进行中/等待/错误",补齐 DONE 才完备;寻址复用 core,不发明第二套。

### D8 节点标识

**结论**:以 env `NODE_NAME`(Downward API fieldRef spec.nodeName)为权威,启动校验非空,所有状态与指标带 node。**为什么**:7.0 要求"唯一确定自身所在 K8s 节点并在状态上报中携带节点标识";Downward API 是标准做法。

### D9 共享内存协议

**结论**:单写单读 ring,64B 头加槽位,读端落后就跳最新。**为什么**:多 Pod 并发写同一文件需要锁,单写单读免锁;阶段切换只关心最新顺序,允许丢旧。

**约束与影响**:`/run/traincache/orders/<pod-uid>.ring`;代际检测;slot 1 MiB×64 可配;布局见 design §6.2。

### D10 阶段切换三源归一

**结论**:epoch / shuffle / curriculum 三种阶段切换统一为 sidecar 推送一条新 ConsumeOrder;Agent 不区分三源。**为什么**:归一后 Agent 只剩一种切换语义(design §5.3),curriculum 检测复杂性隔离在 sidecar;7.0 留空的 curriculum 事件源 = sidecar 获训练进程通知后重算顺序。

### D11 钩子通道

**结论**:单向 Unix datagram 钩子(`/run/traincache/agent.sock`,行分隔 JSON,不回复);顺序主源 = sidecar,钩子只报位点与打开块。**为什么**:7.0 要求钩子调用 PersistentPrefetcher 方法;单向 datagram 免连接管理,丢帧靠 inotify 旁路兜底。

**约束与影响**:帧集合共五种 advance / stage_switch / open_report / read_miss / read_stall(read_miss 见 D44,read_stall 见 D47)。

### D12 core 增量(cas Quarantine)

**结论**:坏块隔离落进 core,按核心库文档流程排队。**为什么**:7.0 明示"需要增加标记位";归属 core 是职责边界——服务化层不重复实现存储逻辑。契约见 design §5.7;由核心库文档流程落地(6.3 新增决策,编号顺延),plan.md M0 引用。

### D13 重扫描流程

**结论**:启动 = 枚举 + 1% 抽样(全过先服务)→ 后台全量(修复队列优先)→ 读时坏块 repair 回源(single-flight);readiness = 服务 up + 抽样完成,全量不拦。**为什么**:7.0 部署约束"缓存尚未完成全量扫描不应直接导致 Agent 无法提供服务";CAS 读时自校验兜底。

### D14 热度参数默认值

**结论**:N=24h、DumpInterval=30min、T=24h(因子 0.5)、k=80%、Δ=5%、M=90%;全部 env 可配。**为什么**:7.0 只给示例值;先取可实现默认,校准留 bench 装置。dump 间隔记号用 DumpInterval,与危险线 M 区分(D24)。

### D15 交叉校准口径

**结论**:滑动窗口 100 次打开,实际顺序与 OrderSource 期望匹配率 < 0.8 即重对齐 cursor(即 7.0"默认 20% 偏差"的精确口径)。**为什么**:把"20% 偏差"落成可测试的匹配率定义;inotify 与钩子双源,钩子为主。

### D16 预取引擎参数

**结论**:lookahead=16(7.0 默认);K = ConsumeOrder.prefetch_chunks;P0>P1>P2>P3,在途不取消。**为什么**:7.0 原文约定;ETA 口径显式化便于测试:ETA = 新窗口剩余字节 ÷ EMA(α=0.3) 吞吐。

### D17 指标清单与命名

**结论**:指标按七条线列清单(design §5.8 family 表,含磁盘淘汰线),靠标签控制基数。**为什么**:7.0 基数控制三原则;清单化便于验收 7 逐项核对。

**约束与影响**:dataset / node / result / endpoint / priority 进标签;dataset 白名单外记 other;固定 bucket;高基数进日志。

### D18 依赖引入

**结论**:只新增 grpc + protobuf、prometheus/client_golang、fsnotify 三个依赖;其余沿用 core 依赖链;派活时声明。**为什么**:不自研轮子,与 core D10 精神一致。(fsnotify 的批准后被 D37 终止。)

### D19 部署

**结论**:DaemonSet 部署(design §8 要点),升级不删有效块。**为什么**:7.0 部署约束原文;节点筛选调度是 Controller 职责,节点选择 label 留待 Controller,不在本设计。

### D20 CLI 细节

**结论**:`--endpoint` 默认 127.0.0.1:9410;`--node` 仅校验不做地址解析(Q2);`--chunks` 是逗号分隔 `path:chunk`,每项直接构造 `ChunkRef`;`--files` 是逗号分隔 tar 分片名,给出时必须同时给 `--dataset`,经 `ListSnapshot` 展开为块;两者互斥且至少给一个。`ls` 默认按文件聚合,`--chunks` 展开到块。**为什么**:CLI 是纯 gRPC 客户端,不能本地读 manifest。

### D21 验收口径

**结论**:bench 装置为唯一数字来源;11 条验收映射写进 plan.md。**为什么**:与项目既有流程一致——关键流程可重复执行(验收 11);验收命令风格沿用 6.2。

### D22 ring 发现机制与写端实现协议

**结论**:发现 = svc 目录轮询(1s 扫 `*.ring`,新文件构造 Reader)+ Reader 内 200ms poll;写端只增不缩,seq 最后写。**为什么**:design §6.2 未明文这些落地细节,M2 开工前冻结。

**约束与影响**:写端 ftruncate 至 max(现长, 64+slot_size),防读端 mmap SIGBUS;commit = 头 write_seq 最后写,reader 只读 seq ≤ 头 write_seq 的槽;槽索引 =(seq-1) mod slot_count;write_seq 跨代际续增;几何上限 slot_size∈[16, 64MiB]、slot_count∈[1, 1024]。

### D23 格式错误指标

**结论**:格式错误单独计数:family `traincache_ordersource_format_errors_total`(counter,labels=["reason"]∈{magic,version}),只按 magic/version 分因。**为什么**:§6.2 要求"计入错误指标"但 §5.8 指标表无对应项,新增并登记。

**约束与影响**:不带 dataset 标签(坏文件读不出 dataset,防基数膨胀);ordersource 包级 atomic 计数,svc 每 tick 以 Set 绝对值同步。

### D24 磁盘淘汰策略(热度驱动)

**结论**:淘汰与回收分两层:core Sweep 只做引用回收(语义不变);Agent 淘汰循环(默认 30s 周期)经 core `cas.Evict`(core D28,5.2 M9)删除活块本地副本,按 `S = max(h, R)` 升序选块。**为什么**:淘汰发生在"逻辑上还需要"的块里,Sweep 删不了活块(5.0 §7 只回收不引用数据),必须分层;算子取 max 不取加权平均——单一权重无法同时保护"刚预取未读"(h=0 靠 R 保)与"历史热久未读"(R 低靠 h 保),max 是"谁强听谁"的最简形式。

**约束与影响**:OPEN 合并后 `h ← h+(1−h)·β`(β=0.15),每 T 乘 0.5、超 N 直接衰减;`R = 0.5^(Δt/T_R)`(T_R=6h);t_touch 取最后打开 / 预取写入 / 新 ConsumeOrder 刷新三者最大值。触发线:利用率超 k 按 S 升序 Evict 至 k-Δ;危险线:超 M 时 R 清零按 h 升序激进淘汰 + 告警至 k-2Δ。cursor + lookahead(16 块)任何情况不淘汰;消费窗口保护 = 新订单刷新 t_touch,不设独立机制;索引与引用不动,回源时不重复 Acquire;新增指标线 `traincache_evict_*`(D17 七线)。周期与阈值细节见 design §7.6。

### D25 数据块对象键布局

**结论**:数据块源站对象键 = `<dataset>/blocks/<path>#<chunk>`(path 约定不含 `#`)。**为什么**:core 与 7.x 均未定义下载键;Entry.Node 仅是"块实际落盘的节点名"标签,不可作键;由 (dataset, path, chunk) 直接构造、无需解析(M3 开工裁决)。

**约束与影响**:与 core 索引键 `dataset/<name>/...` 同风格;fetch.Fetch 的 key 为 opaque,core 无感知,由数据写入方与 Agent 共同遵守。

### D26 对象存储接入配置

**结论**:对象存储五个 env:`TRAINCACHE_OBJSTORE_ENDPOINT`(默认 127.0.0.1:9000,开发演练连本地 MinIO,真实环境换成 COS/OSS/S3 endpoint)、`TRAINCACHE_OBJSTORE_ACCESS_KEY`、`TRAINCACHE_OBJSTORE_SECRET_KEY`、`TRAINCACHE_OBJSTORE_BUCKET`(默认 traincache)、`TRAINCACHE_OBJSTORE_SECURE`(默认 false),MinIO/COS/OSS/S3 通吃。**为什么**:design §8 env 表此前无对象存储配置,M3 真实下载链路必需。

**约束与影响**:经 core objectstore.NewS3Store 构造;集成测试用 objectstore.Mock 注入,不依赖 env。

### D27 显式预热入队接口

**结论**:prefetch 增 `EnqueueP0(ctx, refs []ChunkRef) error`(P0 严格最高优先级入队,在途不取消,空列表返回 nil,ctx 取消返回 ctx.Err());Config 增 `OnP0Done func(ref ChunkRef, err error)`(仅 P0 触发,调度协程内同步调用不得阻塞)。**为什么**:§5.2 冻结四方法无显式预热入队口,svc 预热任务状态机(completed/failed 进度)需要完成通知;回调进 Config 不破坏 New 冻结签名。

### D28 prefetch 通用完成回调

**结论**:Config 再增 `OnDone func(ref ChunkRef, err error)`:所有优先级队列块完成(就绪或下载成败)触发,与 OnP0Done 同触发点、调度协程内同步调用不得阻塞;OnP0Done 保留(仅 P0)。**为什么**:collector t_touch 三源之一"预取写入"需要块级完成通知,仅 OnP0Done 覆盖不了其他队列(M4 开工裁决)。

### D29 Reader 序推进观测

### D44 读 miss 上报与 Agent 侧 demand 按需补块

**结论**:钩子加 read_miss 帧,Agent 按需异步补块。

**为什么**:inotify 只能观测已存在文件的 IN_OPEN,缺块对 Agent 不可观测;open_report 语义是"已打开",不能承载 miss。补块必须留在 Agent 进程内才能复用 fetch 的 inflight 合并并回填 CAS——训练侧直连对象存储既与预取分属不同 single-flight 域,又因只读挂载无法回填。read_miss 是事后信号,只消除"缺块无人补",不承诺零 stall。fetch reason 按首个入队触发者记账,后续 P0 提升不改已有 task 的 reason。

**约束与影响**:帧字段与 svc 接线见 design §5.4:`reason∈{absent,corrupt}`(corrupt→repair),分不清按 absent;单帧 ≤4 KiB;demand 的归属解析只确定 dataset、不要求 Catalog 命中,条目未命中仍按 D25 键以最高优先级 P0 入队、复用 `EnqueueP0`、与 prefetch 共用同一 Fetcher、同处一个 single-flight 域,补不及则本次读仍失败、正确性契约不变;训练 Pod 保持只读 hostPath、不接对象存储、不持凭证;指标 `traincache_hook_read_miss_total{reason}` 不带 dataset(family 25→26,design §5.8)。

### D45 prefetch 跨队列去重与优先级提升

**结论**:PersistentPrefetcher 维护 pending 表跨队列去重,P0 到了就提优先级。

**为什么**:入队处无去重会使同一块在 P0/P2(及 P1/P3)并存;fetch.Fetch 下载前拿不到指纹,无法按 key 复查 CAS,且 inflight entry 在 close(done) 后立即删除,single-flight 覆盖不了"本地检查→Fetch"间隙。源头去重消除重复下载、重复完成回调、重复吞吐采样与重复 collector.Touch;优先级提升保证 P0 语义不被先到的 P2 任务降级。

**约束与影响**:键 `blockKey(dataset,ChunkRef)=<dataset>/blocks/<path>#<chunk>`(与 fetch key 一致),覆盖 P0–P3 与运行中 task;入队 / 提升 / 忽略三规则与计数口径见 design §5.2(完成或终止移除键、失败重试保留;OnDone/OnP0Done 每 task 恰好一次;QueueDepth 与 SubmitPreheat total/completed 按去重后计数)。

### D46 分阶段命中率与命中来源

**结论**:命中率按 phase 和 source 拆标签,新增预取命中率。

**为什么**:7.0 要求分阶段观察命中率与预取收益,D17 仅按 dataset/result 聚合无法区分切换期与稳定期;100 样本窗口沿用 D30 CalibrateWindow 口径,保证 prefetch_hit_ratio 可解释。

**约束与影响**:phase 状态机与 source 判定定义见 design §5.2;四个 family 及标签见 §5.8(`cache_hits_total{dataset,result,source,phase}` result 固定 success、`cache_misses_total{dataset,result,phase}`、`cache_hit_ratio{dataset,phase}`、新增 `traincache_prefetch_hit_ratio{dataset}` gauge)。

### D47 实测 stall 与归因

**结论**:钩子加 read_stall 帧,按 ts±5s 关联归因。

**为什么**:7.0 只有 ETA 预估,无实测读等待;read_stall 提供训练侧真实等待,ts±5s 窗口容忍钩子与 Agent 的时钟/调度偏差;"不承诺零 stall"沿用 D44,read_stall 仅观测不改变读路径。

**约束与影响**:字段 `type,path,chunk,wait_ms,ts`(≤4 KiB)、`HookHandlers` 增 `Stall`、归因规则与 buckets 见 design §5.4/§5.8;`traincache_read_stall_seconds{dataset,phase,cause}` 仅记录 ≥100ms 等待(阈值默认可配);`traincache_stage_switch_eta_seconds` 仍是预估,实测以 `read_stall_seconds{phase="switch"}` 为准,两者不得混用。

### D48 证据类指标

**结论**:补 6 个证据 family,fetch 指标增 reason 标签;family 总数 26→34。

**为什么**:7.0 六条线路的预取收益、修复压力、消费推进与带宽上限缺少可观测证据;singleflight 在 core/fetch 内部无法从 Agent 侧观测,调用包装器是改动面最小的落法(不改 core/fetch 契约);reason 区分 prefetch、demand、repair 三类回源,便于验收与容量分析。

**约束与影响**:6 个新 family(`fetch_singleflight_merged_total`、`repair_queue_depth`、`prefetch_task_duration_seconds`、`prefetch_lead_blocks`、`consumption_advance_total`、`fetch_bandwidth_limit_bytes`)与 `fetch_bytes_total`/`fetch_requests_total` 的标签变更清单见 design §5.8;reason 分桶同 D44 口径。

### D49 Status 双游标口径收口与 inotify 兜底

**结论**:`Status` 拆纯消费位点与预取前沿,落实 inotify 兜底。

**为什么**:两者混用会让 inotify 兜底把"块已完成"误当"已消费",并使 lead 失去负值语义;inotify 事件本身无位点,只能凭指纹反查,代际缓存把逐 OPEN 的全订单 Lookup 降为同代际 O(1)。

**约束与影响**:双游标契约(`Cursor` 仅由 advance/inotify 推进、`PrefetchFrontier` 不要求连续、`lead = frontier − cursor` 可为负、不再暴露调度游标)与兜底去重、门控见 design §5.2/§5.8/§7.4。此处记实现增补:
- ① fp 反查无 Catalog 接口,只能遍历当前订单 Chunks 逐个 Lookup;按订单代际(stageID、Chunk 数、首尾 ref)缓存反向索引,同内容多路径返回候选逐个尝试;已知限制:反查仅覆盖当前订单;
- ② `traincache_prefetch_cursor` 指标仍是调度游标,未改(help 明示"调度进度,非 Status.Cursor");
- ③ self-open guard:Agent 自身读打开本地块(预取本地命中、下载读回校验、ETA 探测、rescan 扫描/修复读回、backfill/stall 归因探测)同样产生 IN_OPEN,钩子沉默/降级期会被 inotify 兜底误判为训练消费;新增 `prefetch.SelfOpenGuard`(`Mark`/`SelfOpened`,并发安全、惰性清理、条目上限 8192,超出先清过期再淘汰最旧;nil 安全)在打开前登记指纹;TTL 默认 3s(装配处传入),覆盖 inotify 轮询与处理延迟;已知偏差:TTL 内训练恰好打开同一 fp 会漏计一次消费推进(宁可少计不可虚增);
- ④ Mark 覆盖:prefetch 本地命中 / 修复重开 / `reportFetchSuccess` / `estimateETA`、core fetch Put 成功后读回(经通用 `fetch.Options.OnLocalOpen` 钩子,core 不依赖 prefetch 类型)、rescan `verify`/`reportRepairFetch`(经 `SetSelfOpenMarker` 注入)、svc `backfill` 本地命中探测与 `stallLocalExists`;
- ⑤ 过滤位置:collector `SetOpenFilter`,仅在 `fireOpen` 调用兜底 open 回调前判断,true 则跳过(不推进 consume、不计数),`noteOpen` 的热度/命中率逻辑不受影响;nil filter 不过滤;
- ⑥ 遗留项(`core/index` Writer.Commit 自开读未登记 guard)已登记 todo。

### D50 快照发布 vs 快照跟随边界与自开观测

**结论**:快照发布 = 写入方调用 core/index `(*Writer).Commit`;快照跟随 = Agent 经 `index.Catalog.Start`/`Refresh` 只读,不调用 `Commit`;自开观测防护 = `cas.SetOpenObserver(guard.Mark)`,装配期最先安装(契约见 design §5.9)。

**为什么**:两种角色分离,避免 Agent 误承担发布职责;Commit 的 checksum 读回会打开本地块文件(D49⑨),进程内 observer 在 `Store.Open` 处统一登记,覆盖未来任何写入方内嵌调用 Commit 的自开读,使其不污染消费侧信号(inotify 热度、Cursor);observer 实例级而非进程级,避免多 Store 与测试间串扰。发布调用方见 `TODO.md`（B）;Controller 现有职责不产生新索引。

### D51 前缀感知快照跟随(R1)

**结论**:Catalog 支持按前缀、按周期跟随 CURRENT;Agent 侧 Follow 在订单前缀 hint 写入之后才启动,`RefreshManifest` 在 snapID 未变且 entries 非空时为空操作(不清空)。**为什么**:Agent 此前仅由订单/预热触发加载,无订单时快照长期陈旧;前缀感知跟随在无活跃前缀时退化为整 manifest 跟随,并以 Catalog 内部互斥保证与 `ForOrder` 不并发切换。完整冻结契约见 design §5.9(`SnapID`/`RefreshManifest`/`Follow`、`OnSnapshotChange`/`OnSnapshotError`、`IndexRefreshInterval` 默认 5s、刷新指标复用 `index_refresh_total{dataset,result}`,失败不切换、不清空)。

### D52 快照读者登记、心跳与撤销(R2)

### D53 GC 按读者确认删除(R3)

**结论**:GC 以有效读者 claim 为保护集,保留窗口降为兜底。**为什么**:固定保留窗口不是安全边界,读者可能在窗口外仍持有旧快照;以有效 claim 为保护集并用 `PreviousSnapID` 覆盖切换宽限期,manifest 缺失时 fail-safe 防误删块。完整冻结契约见 design §5.11 七条 Sweep 规则(`ReaderGrace` 零值回退 `2*RefreshInterval`、默认 10s;protected = CURRENT ∪ 固定保留窗口 ∪ 有效 claim;`RetainSnapshots` 仅兜底;CURRENT 永不删;`OnSweepSkip(dataset,"manifest_unavailable")` 跳过本轮块删除但继续其他删除)。

### D54 Commit 孤儿清理与条件写探测(R4)

**结论**:失败提交清理孤儿对象,并探测后端条件写。**为什么**:失败提交留下的新分片/manifest 无引用,不清理会成孤儿对象;条件写在 mock 上无法证明真实后端支持,需真实 S3 兼容后端探测与集成测试。完整冻结契约见 design §5.12(`commitOnce` best-effort 逆序 Delete、`ErrConditionalWriteUnsupported` 与 `ProbeConditionalWrite`、`ObjstoreProbeConditionalWrite` 默认 false、`traincache_objectstore_conditional_write_supported` 0/1 预置 0、minio.yaml 与 TC_S3_* 集成测试)。

### D55 Agent 预热任务增量(8.x)

**结论**:扩展 `traincache.agent.v1.PreheatService`(契约全文见 design 附录 A):新增 `UpdatePreheat`/`CancelPreheat`;`PreheatStatus` 追加 `generation=12`、`seq=13`、`ready_bitmap=14`、`canceled=15`,`SubmitPreheatRequest` 追加 `generation=8`;不新增 `GetPreheatProgress`;`UpdatePreheat` 全量替换,`CancelPreheat` 仅标记且不保证停止在途 P0、任务仍留在任务表内并由 `canceled` 回报;低 generation 返回 `FailedPrecondition`;同 generation Cancel 后再 Submit 视为新任务;`ReportBlocks` 保持 Unimplemented、8.x 不使用。

**为什么**:8.x GWAA 需要按 `(pod,node)` 改派/停止并读取窗口位图;复用 `GetPreheatStatus` 避免新增查询 RPC,两个动作 RPC 覆盖改派/取消;拉取方向与现有 RPC 一致,避免 Agent→Controller 反向连接(详见 `docs/7.3 decisions.md` D28)。D43 结论"不设 CancelPreheat"是 8.x 增量之前的口径,现状以本条为准。

### D56 位序定义(8.x)

**结论**:`ready_bitmap` 第 `i` 位对应请求 `chunks` 第 `i` 项;`UpdatePreheat` 全量替换 `chunks` 后位序重定义、旧位图失效并重置;8.x 必须显式 `chunks`,空列表视为清空窗口。**为什么**:位序若按块全局编号会随窗口变化漂移;绑定请求顺序使 Controller 与 Agent 无需共享全局映射,位图长度可推导(`ceil(len(chunks)/8)`)。

### D57 ring 写端保活扩展到 bench reader

**结论**:D41 的 10s 重写节奏从 `traincache-ordersrc` sidecar 扩展到所有 ring 写端;`bench/compare/run_bench.py` 的 traincache 组 reader 加 heartbeat 线程,每 10s 重写当前 epoch 的订单。

**为什么**:D41 只约束了 manifest 里的 sidecar,而 bench 的 traincache 组由 `run_bench.py` 内联写 ring:订单每 epoch 只写一次、epoch 内静止,`LastAdvance`(D29)停滞 30s 后 collector 进 degraded 切 inotify 兜底——热度和命中率统计中途换源,跑分数据口径不一致、不可比。写端一次性写完退出是设计行为不是 bug,修的是写端节奏,不是降级阈值。

**约束与影响**:
- `run_bench.py` traincache reader 内:`_hb_stop = threading.Event()` + `_hb_epoch = [0]`;`_heartbeat_loop()` 每 10s 调 `_write_order(str(_hb_epoch[0]))`,异常吞掉不中断训练读取;epoch 主循环开头更新 `_hb_epoch[0] = epoch` 并照常 `_write_order`,`epoch == 0` 时拉起 daemon 线程,循环结束 `_hb_stop.set()` 收尾。
- 前提依赖读端 `ordersource.Reader` 的载荷字节去重(`lastEmitted`,代码内称"约定 7"):内容相同不推送、不触发 `OnStageSwitch`,所以心跳只推进 `write_seq`、刷新 `LastAdvance`,不会每 10s 把预取队列打回 P1。
- 保活判据:跑分产物所在轮次要求 `traincache_agent_degraded` 全程为 0;出现过 1 则该轮命中率/热度曲线标 `degraded`,不参与组间对比。
- 新的自研 ring 写端(探针、临时脚本)按同一条约束实现,不得只写一次就静止。

### D58 缓存字节上限与淘汰双维度触发

**结论**:evictor 新增 env `TRAINCACHE_CACHE_CAPACITY_BYTES`(默认 0=关闭),开启后淘汰循环同时查磁盘利用率和字节占用,哪个先到阈值就按哪个维度触发;两个维度共享得分模型 `S = max(h, R)` 和硬保护(cursor+lookahead 不淘汰)。

**为什么**:磁盘百分比水位(80%/90%)是间接约束:节点上还有其他 Pod 占用磁盘时,Agent 可能在磁盘还没到 80% 时就已经预取了大量数据,或者磁盘到了 80% 但 Agent 其实没写多少块。字节上限直接约束"这个节点 Agent 最多占多少 GB",和 bench 公平实验里"所有组统一 1GB 缓存"的要求对齐(归入 D19 部署约束)。

**约束与影响**:
- 默认 0 关闭时退化成原行为,零代码路径变化;磁盘水位仍生效。
- 触发线(超上限 → S 升序淘汰到 85%)与危险线(超上限 95% → R 清零按 h 升序淘汰到 80%)及磁盘维度沿用 D32 的 k/Δ/M,两维度各自判定互不依赖;细节见 design §7.6。
- 记账:evictor 维护累计本地块字节数(`cas.Open` 成功后查文件大小、Evict 成功后从累计减),只统计 Agent 自己写的块,系统文件不计入。
- 指标:`traincache_cache_capacity_bytes_total{source}`(gauge,source∈{disk,bytes})暴露当前触发维度(design §5.8 的 family 计数未回填,登记 todo)。
- bench 装置:所有组统一设 1GB,保证公平对比。

### D59 淘汰策略抽象与运行时选择(M4)

**结论**:淘汰"谁先被换出"抽象成 `Policy` 接口(`agent/evictor/policy.go`),只留 `Rank(blocks []Block, danger bool) []Block`;三档 `heat`(现有热度打分,行为与改动前逐字一致,作回归基准)/`lru`/`lfu`,运行时经 env `TRAINCACHE_EVICT_POLICY` 选择(默认 heat,启动校验,未知值拒绝启动并打印合法清单);lookahead 同步 env 化为 `TRAINCACHE_PREFETCH_LOOKAHEAD`(默认 16)。W-TinyLFU 档不实现(权威口径见 9.1 D9):`Admit` 准入方法连同接线一起删除,配套指标 `admit_rejections` 与频率减半次数随之取消,`agent/evictor/tinylfu.go` 与 `bench/experiments/conds/policy-wtinylfu.json` 已移除。

**为什么**:10.0 要求多策略同台,"用哪种淘汰"必须是运行时选项而不是代码分支。接口落在 `agent/evictor` 而不是 core——core 不该知道训练语义与访问历史(9.1 D7),`cas.Evict` 原语不动。扫点靠 env 注入,不改 CRD(9.1 D10)。实验块大小取 8MiB(9.1 D20)后 1GiB 缓存有 128 块,各档排序结果才有判别力。撤档理由(9.1 D9):① bench 主场景是单 Job 顺序读,准入(拦截一次性块)的收益不明确;② window + 两段 SLRU + count-min + doorkeeper 的实现与验证成本高;③ 核查确认已写的 `tinylfu.go` 只是频率排序代理(window 与两段 SLRU 缺失、`Admit()` 从未被淘汰循环调用),留着会让策略同台对比失真。

**约束与影响**:触发线、危险线、字节上限维度(D58)、硬保护(cursor+lookahead)与策略无关,三档共用;策略只替换"谁先被淘汰"这一层。`heat` 档回归判据:同一访问序列下与 D24/D32/D58 的旧行为逐块一致(9.1 M4 判据①)。新指标线只保留策略切换计数,标签只放策略名(10.1 4.9)。bench 装置:对照实验一律 `heat`;M5 淘汰矩阵与 Pareto 二由 `experiments/run_policy.py` 注入策略与 lookahead,矩阵从 4 策略缩到 3 策略(9.1 D9)。

### D60 Follow 启动时序与 demand 索引解绑

**结论**:svc 在 bundle 构造内先写入当前订单的路径前缀 hint,再启动 `Catalog.Follow`;hint 由 `bundleFor` 的调用方传入。`RefreshManifest` 在 snapID 未变且现有 entries 非空时为空操作:不切换、不清空、不触发 `OnSnapshotChange`。read_miss 的 demand 归属解析与索引命中解绑:dataset 已知、条目未命中时,仍按 D25 键入 P0。契约见 design §5.4/§5.9,D44/D51 同步。**为什么**:`Follow` 启动即执行首轮检查。先启动、后写 hint,首轮就会读到空前缀,走 `RefreshManifest` 清掉刚由 `LoadPrefixes` 装入的映射;snapID 未变,后续各轮全部跳过,空映射从此固化,demand 再也入不了队。RefreshManifest 的防线拦住这次误清空。P0 demand 的回源键由 (dataset,path,chunk) 直接拼出,不需要索引。旧实现把 dataset 归属绑在 Catalog 命中上,索引为空时已知 dataset 会被误判为未知,帧被丢弃。**约束与影响**:首次构造 bundle 时随参数装入 hint 并启动 Follow;既有 bundle 的前缀 hint 不随无订单入口改写。空前缀(无订单)的轻量跟随仍可切换空映射,只有同快照非空映射受保护。demand 与 prefetch 共用同一 Fetcher、同处一个 single-flight 域的口径不变(D44),准入等级按 D61 分级。

### D61 fetch 前台/后台分级准入

**结论**:`core/fetch` 增加准入等级 `Priority`(`PriorityForeground` / `PriorityBackground`)与 `FetchWithPriority`,`Fetch` 等价于前台。后台额度固定取全场的一半:任务槽 `MaxTasks/2`、在途字节 `MaxInflightBytes/2`,各自至少 1;后台先占半额、再占全场额度,前台按全场额度随时接入。前台有下载在途时,后台停在让路门外,等到前台在途数归零再放行。已在途的后台下载不取消;前台请求合并进同 key 的后台下载时,该次下载改按前台准入(代码名 `promote`)。prefetch 侧按任务 reason 分档:demand 走前台,其余(含显式预热)走后台。契约见 5.1 §5.3、6.1 §5.2/§5.4。

**为什么**:cold 探针给出三组数字。启动耗时 80.0 s,其中第一片 252 MiB 的串行块读占 76.6 s;整轮取数 2.12 GB 里有 1.96 GB(92%)归因 `reason=prefetch`。预取与需求读共用同一条 12.5 MB/s 出口,预取能占满全部 8 个任务槽。P0 只约束出队顺序,挡不住已经在途的预取,需求读只能排队,首片读因此被拉长三倍多。

**约束与影响**:前台永远保有一半任务槽与一半在途字节,需求读不再和预取抢同一份额度。额度不构成吞吐瓶颈:12.5 MB/s 的出口上两块并发就能打满,预取让出一半槽位不降低回源吞吐。训练读持续不断时预取会让路,预取进度可能后移;命中率与 stall 归因口径不变。让路门只数前台在途、不数合并等待者,否则后台持有者会被自己的合并等待者挡住。

## 3. 决策变更流程

与 core 6.3 一致,三步:

1. 实现子代理发现约定不可行、不合理,先回传 `BLOCKED`(带上理由、证据和建议),代码先别动;
2. 主对话裁决:采纳则更新 `docs/design.md` 和本文档——旧编号保留,新决策接着往后编号,再重新派活;否决则说明理由,子代理按原约定继续;
3. Q* 结案时在 §2 表格登记结论,必要时升级成 D* 或改 `docs/design.md`。
