# Agent 服务化设计(design)

## 定位

把核心库(纯 Go 库,无服务形态)包装成常驻服务 `traincache-agentd`,每台缓存节点一个实例,以节点为服务边界:一个 Agent 只认识本机的缓存目录和本机的块,没有全局视图;单机故障不扩散,Controller 不在线时训练照跑。

- 对外:gRPC(接收预热任务、上报块级任务、节点状态查询)与 Prometheus `/metrics`。
- 对内:调用核心库完成缓存索引、数据块存储、校验和回收,服务化层不重复实现其中任何一项。
- 缓存根 `/var/cache/traincache`,CAS 块统一存 `blocks/` 下,物理路径由块内容指纹确定。
- 训练 Pod 经 hostPath 只读挂载直读 CAS 块,读路径不经过 Agent 的 gRPC 读接口。
- 自治能力:训练中持续预取、阶段切换重预取、重启重扫描、坏块修复、热度统计,均无需 Controller 在场。

Agent 在本机做四件事:收任务、定顺序、下载数据、报状态。训练侧的 DataLoader 钩子由独立工程实现,本设计只冻结它与 Agent 的 socket 协议。

## 架构与依赖方向

Agent 的 DaemonSet Pod 与训练 Pod 跑在同一台机器上,靠 hostPath 与 Unix socket 通信,不走网络。Controller 在南向用 gRPC 与 Agent 交互,训练进程在数据面经 hostPath 直接读块,不经过 Agent;读 miss 时钩子发 `read_miss` 帧,Agent 收到后异步补块。sidecar 把消费顺序写进共享内存,Agent 从共享内存读出。

三个可执行产物:

| 产物 | 形态 | 职责 |
|---|---|---|
| `traincache-agentd` | Go,DaemonSet 常驻服务 | 本设计主体 |
| `traincache-ordersrc` | Python,训练 Pod 内 sidecar | 按 Job 配置算出每个阶段的消费顺序,写进共享内存;算出的顺序必须和真实 loader 一致 |
| `traincache` | Go,CLI | 纯 gRPC 客户端 |

依赖方向单向、不允许环:

- `cmd/agentd` 与 `cmd/traincache` 依赖 `svc`;
- `svc` 依赖 `prefetch`、`collector`、`rescan`、`metrics`、`nodeid`、`ordersource`,并依赖核心库;
- `api` 是 proto 生成代码,只被 `svc`、`cmd` 与 `ordersource` 引用;
- `ordersrc` 是独立小进程,不依赖核心库。

`svc` 是装配层:起服务、读配置、接探针,持有各子模块实例。子模块之间互不依赖,数据由 `svc` 编排,每个模块可单独测。`ordersource` 只读共享内存,不碰核心库;`ordersrc` 是另一个进程,连核心库都不依赖,可以跟着训练镜像走。

目录职责:`api/` 放 proto 定义与生成代码,`cmd/agentd` 是服务入口,`cmd/traincache` 是 CLI,`ordersrc/` 是 sidecar,`hooklib/` 是 DataLoader 适配器,`svc/` 是服务化层(gRPC server、生命周期、装配、探针、预热任务状态机、钩子 socket 收端),`prefetch/` 是预取主循环,`ordersource/` 是共享内存读端,`collector/` 是 inotify 旁路采集,`rescan/` 是重扫与修复队列,`nodeid/` 解析节点标识,`metrics/` 注册 Prometheus 指标。

## gRPC 接口

Agent 对外三个 gRPC 服务,按方向分:

- `PreheatService`:南向,Controller 或 CLI 下发预热任务、查询进度;
- `NodeService`:节点状态查询,CLI 和就绪探针都用它;
- `ReportService`:北向,Agent 往 Controller 报块级结果。proto 随本设计冻结,接收端实现在 Controller 侧。

```proto
syntax = "proto3";
package traincache.agent.v1;
option go_package = "traincache/agent/api/agentpb";

service PreheatService {
  rpc SubmitPreheat(SubmitPreheatRequest) returns (SubmitPreheatResponse);
  rpc GetPreheatStatus(GetPreheatStatusRequest) returns (PreheatStatus);
}

service NodeService {
  rpc GetNodeStatus(GetNodeStatusRequest) returns (NodeStatus);
  rpc ListSnapshot(ListSnapshotRequest) returns (ListSnapshotResponse);
}

service ReportService {
  rpc ReportBlocks(stream BlockReport) returns (ReportAck);
}
```

消息定义(字段名冻结):

| 消息 | 字段 |
|---|---|
| `SubmitPreheatRequest` | `task_id string`(幂等键);`node string`(须等于本节点);`dataset string`;`snapshot_id string`(空=当前 CURRENT,非空值不支持,返回 `InvalidArgument`);`prefixes []string`(路径前缀,语义同核心库 `Catalog.LoadPrefixes`:空=空映射,含空串=全量);`chunks []ChunkRef`(可选,块级精确指定);`priority PreheatPriority` |
| `ChunkRef` | `path string`;`chunk int64`(核心库 Entry 寻址) |
| `PreheatPriority` | 枚举 `P0=显式启动预取 / P1=阶段切换重预取 / P2=邻域预取 / P3=后台补全`(默认 P0) |
| `SubmitPreheatResponse` | `accepted bool`;`task_id string`;`message string` |
| `GetPreheatStatusRequest` | `task_id string` |
| `PreheatStatus` | `task_id`;`node`;`dataset`;`snapshot_id`;`paths []string`;`state`(枚举 `QUEUED / RUNNING / DONE / ERROR`);`total_blocks int64`(去重后的唯一块数);`completed_blocks int64`;`failed_blocks int64`;`started_at`、`updated_at`(google.protobuf.Timestamp);`window_blocks uint32`(当前窗口块数,等于 `chunks` 项数,含重复位置) |
| `GetNodeStatusRequest` | `node string`;`item NodeStatusItem`(枚举:全量 / agent / catalog / space / tasks / rescan) |
| `NodeStatus` | `node`;`agent_ok bool`;`cache_root string`;`cached_bytes int64`;`free_bytes int64`;`running_tasks int64`;`rescan RescanStatus`;`catalog []DatasetCatalog` |
| `RescanStatus` | `phase`(枚举 `SAMPLING / FULL_SCAN / DONE`);`sampled int64`;`verified int64`;`quarantined int64`;`repair_queue int64` |
| `DatasetCatalog` | `dataset string`;`snapshot_id string`;`shards int64`;`entries int64` |
| `ListSnapshotRequest` | `dataset string`;`snapshot_id string`(空=CURRENT);`prefix string` |
| `ListSnapshotResponse` | `entries []EntryRef`(`path`;`chunk`;`size`) |
| `BlockReport` | `node`;`task_id`;`ref ChunkRef`;`fp string`;`bytes int64`;`result`(枚举 `OK / CORRUPT / REFETCHED`) |
| `ReportAck` | 空 |

错误语义以 `task_id` 为幂等键:任务校验失败(节点不符、dataset 不存在)返回 `InvalidArgument`;同 `task_id` 内容不同返回 `AlreadyExists`,内容相同则返回现有任务。

RPC 一律带 context 超时,Agent 侧默认 10s;长时间任务靠 `GetPreheatStatus` 轮询,不做长连接流。

## 预取主循环

PersistentPrefetcher 是预取主循环:四个严格优先级队列(P0>P1>P2>P3),一个调度协程串行出队,并发下载受核心库 fetch 的分级额度约束。队列任务按块去重,同一块不排两次。

节点上只有一条抓取管线,任务按 P0 到 P3 四级排队。每个训练 Pod 有一个消费队列,队列上滑动着预取窗口;窗口中的块先查本地 CAS,已有的不管,没有的按任务来源定优先级入管线。sidecar 推送首份 ConsumeOrder 后 `ordersource.Reader` 发现 ring,`svc` 组装 PersistentPrefetcher 并 `Start`,从 cursor 起做 P2 邻域预取,范围是 cursor 到 cursor 加 lookahead,每完成一块推进调度游标并上报指标。

预取主循环对外五个动作:启动持续预取、推进消费位点、阶段切换、显式启动预取入队、查状态。

- 启动持续预取:从消费位点起按当前消费订单做邻域预取,每完成一块推进调度游标并上报指标。显式启动预取与阶段切换重预取可以打断这个循环:在途请求不取消,新请求按更高优先级入队。
- 推进消费位点:钩子每消费完一块调一次,预取提前量等于消费位点加邻域提前量(默认 16 块)。块不在当前订单、上下文已取消、尚无阶段,或位点没有前进(重复或回退事件)时返回未推进,且不产生任何副作用。
- 阶段切换:旧阶段消费位点之后未消费的块降级 P3(在途请求不取消);新阶段开头 K 块(K 取新订单的阶段首批块数)按 P1 高优先级入队,剩余块转 P2;返回切换时刻到新窗口就绪的预估时间。
- 显式启动预取入队:显式预热的块按顺序以 P0 严格最高优先级入队,在途不取消,每块完成后回调完成结果;需求补块的块同样进 P0,插在队首,排在任何预热块之前;空列表是空操作。
- 查状态:给出当前阶段、消费位点、预取前沿、四个队列各自长度与预取命中率。消费位点只由消费推进事件前进,预取前沿是已就绪的最远块(不要求连续),队列长度按去重后的任务计数,预取命中率是窗口内消费时块已就绪的比例,只作观测,不参与调度。

装配时注入六样东西:邻域提前量(默认 16 块);自打开登记表,Agent 自身打开本地块前先登记指纹,采集侧的 inotify 兜底据此跳过这些打开事件,免得把 Agent 自己的读判成训练消费;P0 块完成回调与全队列块完成回调,都在调度协程内同步调用且不得阻塞,P0 块先走前者再走后者,后者是采集侧"预取写入"这个触摸来源;校验失败回调,注入"隔离加修复"的组合,返回成功且随后按索引指纹重开成功视为就绪,无回调、返回错误或重开失败都按未命中走下载路径;逐块汇总器,只累加计数,窗口到期输出一条汇总,避免逐块写日志;阶段切换回调,安装新阶段后调一次并传入阶段标识,供服务层把阶段切到 switch。

订单预取降级:svc 安装订单前按索引累加订单块的数据集总字节,重复块只计一次,与 `TRAINCACHE_CACHE_CAPACITY_BYTES` 比较。容量大于 0 且总字节超过容量时,该订单的首批 K 置 0,预取器同时不开放邻域窗口,块只在 read_miss 钩子触发按需回源或显式预热时下载;降级时输出一条 Info 日志,带数据集总字节与容量。容量为 0 表示字节维度未启用,预取维持原样。判据随每份订单重算,总字节回落到容量以内的订单恢复首批与邻域预取。缓存装不下整个数据集时,提前取来的块会在消费前被淘汰,同一块回源两次;按需回源把回源字节限制在消费实际读到的块。

队列档位与准入档位是两条独立的轴。队列档位 P0 到 P3 只决定出队顺序;准入档位只决定这次下载拿多少额度、能不能排队进入,在读准入(需求读补块与坏块修复)占全场额度,预铺准入(预取与显式预热)先占半额、再占全场,在读有下载在途时预铺停在让路门外。已在途的预铺下载不取消,在读请求合并进同 key 的预铺下载时该次下载改按在读准入。显式预热的块也走预铺档位,训练进程有没有开始消费都不变,预热任务刚下发时只拿一半任务槽与一半在途字节。预取自己不管限速,额度全部由核心库 fetch 统一约束。

去重表以 `blockKey(dataset,ChunkRef)` 为键,取值 `<dataset>/blocks/<path>#<chunk>`,与 fetch 的 key 一致。键已存在且 task 未开始时按最高优先级提升,不新建 task;已在运行则忽略。pending 表覆盖 P0 到 P3 队列和运行中的 task,由 `mu` 保护,同一个键任一时刻最多一个 task;task 成功或终止后移除键,失败重试期间保留。完成回调对每个被接受的 task 恰好回调一次。预热任务的 total 与 completed 按去重后的块计数,重复提交不会让数字翻倍。

ETA 的口径是新窗口剩余未就绪字节除以最近 30s 滑动平均吞吐,EMA 系数 0.3,吞吐含回源与本地命中。已经在本地(索引命中且 `cas.Open` 成功)的块不产生下载,直接当就绪处理,避免每次阶段切换重复下载已有块。消费游标不落盘,只在内存里;Agent 重启后的恢复起点是共享内存里当前那份订单加上本地已就绪的块。

phase 状态机只有四个取值:`startup`(Agent 启动起到首个 ConsumeOrder 的首 K 块就绪,K 取订单里的 `prefetch_chunks`)、`switch`(`OnStageSwitch` 起到新窗口 K 块全部就绪)、`steady`(其余时间)、`unknown`(判定不了的情况,比如事件关联不到任何已知窗口)。两个窗口同时活跃时 `switch` 优先。

双游标口径:消费游标由钩子 `advance` 帧推进,降级期由 inotify 打开事件兜底,`Status.Cursor` 暴露的就是这个口径;预取前沿指已就绪的最远块,不要求连续,经 `Status.PrefetchFrontier` 暴露。`Status` 不暴露调度游标,`traincache_prefetch_cursor` 指标记的是调度游标。预取领先等于预取前沿减消费游标,按当前订单的 Chunks 序列计块数,可以是负值,负值表示消费跑在预取前面,要等数据。

任务耗时打点位置:task 被 pending 表接受并入队时记起点,同键去重提升不重置起点;进入终态(就绪或下载失败终止)时向 `traincache_prefetch_task_duration_seconds{dataset, priority}` 记一次。priority 取值 P0 到 P3,取 task 最终生效的最高优先级;CLI 的 `--priority` 用小写 p0 到 p3,映射到指标标签时统一大写。

`Status.HitRate` 以最近 100 个消费样本的滑动窗口计算,直接输出为 `traincache_prefetch_hit_ratio{dataset}`。

## 订单源与共享内存

消费顺序由训练 Pod 里的 sidecar 算出,写进共享内存 ring,Agent 侧读端读出。订单载荷是一个块引用列表加数据集名、快照名、阶段标识、洗牌种子、批大小与阶段首批块数,块引用是路径加分片号,载荷的字节格式见数据格式一节。

订单源对外两个动作:取当前阶段的消费顺序(没有订单时返回无)、订阅阶段切换事件(返回一个通道,每收到一次事件推一份新订单)。读端是 mmap 共享内存文件的实现,监视目录是 `/run/traincache/orders`,自动发现新 Pod 的 ring 文件。读端另外报最近一次观察到写入序号推进的本地时间(零值表示从未推进,新代际也算一次推进)与当前代际号。

代际变化时读端清掉当前订单、重置载荷去重基线,把新订单重放一次;sidecar 重启后不重放历史。

阶段切换的三种来源归一:epoch 边界、shuffle 重排、curriculum 切换统一为同一条语义,sidecar 重算并推一份新的 ConsumeOrder,Agent 不区分事件来源。

ring 单写(sidecar)单读(Agent)。写端重启靠代际计数检测;读端落后不阻塞写端,直接跳到最新,因为阶段切换只关心最新顺序。每路 ring 的写入序号推进就是它自己的 lease。Agent 按源记 `lastAdvance`,聚合出订单通道状态;30 秒没有推进的源计 stalled。

## 钩子 socket 协议

DataLoader 钩子(Python,训练 Pod 内)往 Agent 发消息:Unix datagram socket `/run/traincache/agent.sock`,行分隔 JSON,单向,Agent 不回帧。发送端实现在 `agent/hooklib/`,包装 torch 的 `Dataset` 与 `IterableDataset`,发送失败只计数、不抛给训练循环。选 datagram 是因为丢一帧不影响训练,不需要重传。帧共五种类型。

```json
{"type":"advance","path":"...","chunk":3}
{"type":"stage_switch","stage_id":"epoch-2","shuffle_seed":12345}
{"type":"open_report","path":"...","chunk":3}
{"type":"read_miss","path":"...","chunk":3,"reason":"absent","ts":"2026-10-18T10:00:00Z"}
{"type":"read_stall","path":"...","chunk":3,"wait_ms":250,"ts":"2026-10-18T10:00:00.123456789Z"}
```

五帧都可带同一组可选身份字段:`warmup_task`、`pod`、`pod_index`、`dataset`、`generation`。字段缺失时取零值,行为与不带身份字段的旧帧一致。Agent 用 `warmup_task` 反查自己的 `task_id`,不要求训练侧知道它。

各帧的去向:

- `advance` 推进消费位点,调用 `OnConsumeSideAdvance`。
- `stage_switch` 转交 `OnStageSwitch`。主通道是 sidecar 推送,钩子直报算双通道冗余,以先到者为准并去重。
- `open_report` 交给 collector 做命中率统计。它和 inotify 是两个来源,钩子为主,inotify 兜底。
- `read_miss` 交给钩子处理器补块。字段 `path`、`chunk`、`reason`(`absent` 或 `corrupt`)、`ts`;分不清 absent 和 corrupt 时按 `absent` 上报。svc 收到后先解析 dataset 归属,解析不要求索引命中,条目未命中不影响归属;缺失块按 `(dataset, path, chunk)` 拼出来源键,以最高优先级 P0 入队补块,复用 `EnqueueP0` 语义,回源 reason 是 `demand`;损坏走 repair,先 `Quarantine` 再 `RepairOne`。这帧是事后信号,best-effort:补不及则本次读仍失败,正确性契约不变。训练侧保持只读 hostPath、不拿凭证、不直连对象存储,Open 失败后只用这个单向异步通道把缺失块告诉 Agent。
- `read_stall` 在实际消费等块达到 100ms 时由钩子上报,阈值由 env `TRAINCACHE_READ_STALL_MIN_WAIT_MS` 配置,字段 `type`、`path`、`chunk`、`wait_ms`、`ts`(RFC3339Nano)。Agent 按 `ts` 加减窗口去关联该块的预取状态,窗口默认 5s,由 `TRAINCACHE_READ_STALL_WINDOW_MS` 配置,归因分四类:本地存在且不是当前窗口预取的记 `local_slow`;核心库 fetch 在途记 `origin_slow`;不在本地也不在途(pending 或未知)记 `prefetch_lag`;解析不了或超出时间窗记 `unknown`。归因结果写进 `traincache_read_stall_seconds{dataset, phase, cause}`,只有达到 100ms 的等待进直方图。

帧格式错误照旧计 `traincache_hook_format_errors_total{reason="parse|size"}`。

收端分三处装配:每帧先过一遍元数据回调(拿任务身份、pod 信息),再按帧类型分给五个处理槽;处理槽留空表示丢掉这一类帧。钩子 socket 绑定 Unix datagram 套接字后起读循环:父目录缺失就创建,上次崩溃残留的陈旧套接字文件先清掉,套接字权限放开到 0666 以便跨容器的钩子进程写。上下文取消自动关闭并删除套接字文件,每个实例只允许启动一次,关闭后再启动返回错误。

钩子 socket 和订单通道各自独立:sidecar 缺席只改变订单通道的观测状态,不改钩子帧的处理,也不改读路径。

## 热度与命中率

collector 用 inotify 旁路监听缓存目录的文件打开事件,不侵入训练进程,产出热度(给淘汰做决策输入)和命中率(判断缓存效果,供调参)。

collector 不持有 ring。订单上下文只用于命中标签和交叉校准,缺订单时统计照常,标签归 unknown;订单通道健不健康由 svc 聚合,采集层不判、不写 gauge。

采集侧要注入三样东西:订单上下文 provider(按块引用反查所属数据集与阶段,反查不到也能统计)、消费推进回调、以及打开事件的开销过滤。打开与触摸分两路:打开记一次访问,触摸只更新最近访问时刻。淘汰侧从采集侧取全量热度快照与单块淘汰得分。

热度参数有固定默认值:超过 24 小时的记录直接衰减,每 30 分钟 dump 一次,全体衰减周期 24 小时、因子 0.5,单次打开的热度增量系数 0.15,新鲜度半衰期 6 小时,交叉校准窗口 100 次打开、匹配率阈值 0.8。

热度映射的键是块指纹,值是热度与最近触摸时间两项,在内存里持有,定期 dump 成 `heatmap.json`。指纹是块的 xxh3 哈希,同一块换路径也认得。条目结构是 `FP`、`Heat`、`LastTouch`、`Accesses`,Collector 和 Evictor 两边各有一份定义但字段一致;`Accesses` 是累计打开次数,供 LFU 档策略消费。

每次 OPEN 合并后 `h ← h + (1−h)·β`,热度按比例逼近 1,越热的块涨得越慢。每隔 T 全体乘衰减因子,超过 N 的记录直接衰减并淘汰得分低于阈值的条目;`t_touch` 取最后打开、预取写入、新 ConsumeOrder 刷新三者的最大值。同一进程反复打开一个文件要合并,因为训练进程一个 epoch 里可能反复打开同一块,inotify 每次都报 OPEN。

淘汰得分是 `S = max(h, R)`,其中 `R = 0.5^(Δt/T_R)`,Δt 是 now 减 `t_touch`。双信号取强:刚预取还没被读过的块靠 R 保,历史热块久未读的靠 h 保。

命中率把消费者报告的打开块集合和本地块集合求交集,滚动窗口按分钟级统计,再按训练阶段聚合。不落长期历史,导出到监控,重启即丢。phase 取值 startup、steady、switch、unknown 四种,命中与未命中按事件发生时的 phase 打标。命中来源分三种:prefetch 是当前窗口内由 Agent 预取放置,cache 是本地已有且非当前窗口预取,unknown 是无来源信息。预取命中率与打开命中率是两个口径,不混用:dataloader 上报有精度上限,计划读到的不一定实际成功读到,这里的指标是观测口径,Agent 不声称在读路径上做了精确记账。

交叉校准:窗口内实际打开顺序和订单期望顺序的匹配率低于 0.8 时,调 `OnConsumeSideAdvance` 把消费游标重对齐到实际位点,防止 sidecar 算的顺序和真实 loader 长期漂移。热度只做决策输入,不参与正确性。

## CLI

CLI 是纯 gRPC 客户端:不直接操作缓存目录,不重复实现缓存索引、数据块下载或落盘,所有逻辑在 Agent 侧,线上线下行为一致。

```
traincache prefetch --task-id T --path /train-data --node worker-01 \
                    --chunks shard-000.tar:0,shard-000.tar:1 \
                    [--dataset NAME] [--snapshot-id ID] [--priority p0|p1|p2|p3]
traincache prefetch --task-id T --path /train-data --node worker-01 \
                    --files shard-000.tar,shard-001.tar --dataset NAME \
                    [--snapshot-id ID] [--priority p0|p1|p2|p3]
traincache ls --dataset NAME [--snapshot-id ID] [--prefix P] [--chunks]
traincache node status --node worker-01 [--item agent|catalog|space|tasks|rescan]
traincache status --node worker-01 --task-id <task-id>
```

地址解析顺序：显式 `--endpoint` 优先；否则进程所在节点的 `NODE_NAME` 等于 `--node` 时连 `127.0.0.1:9410`；否则向控制面查该节点的 Agent 候选地址（Pod IP 在前、节点地址在后），按顺序试连，第一个连上的就用；都不给时连 `127.0.0.1:9410`。控制面地址来自 `--controller`，缺省取环境变量 `TRAINCACHE_CONTROLLER_ENDPOINT`，再缺省取集群内 DNS `traincache-controller-manager.traincache.svc:9412`。`--node` 在连上之后仍作请求校验字段。`--priority` 接受小写 p0 到 p3,映射到指标标签时统一大写。

`--chunks` 是逗号分隔的 `path:chunk`,每项直接构造 `ChunkRef` 填入请求的 chunks 字段,此时 `--dataset` 可选。`--files` 是逗号分隔的 tar 分片名,必须同时给 `--dataset`;CLI 先调 `ListSnapshot`,把每个分片展开为该分片的全部块,再填入 chunks,分片名在快照中找不到时退出 1。两者互斥且至少给一个;`--path` 是请求 prefixes 的唯一元素。没写 `--dataset` 时 `--path` 必须能映射到已注册的 dataset,校验在 Agent 侧做。

路径预热:Agent 若没有存储该路径下的快照,去远端拉取,加载行为同核心库 `Catalog.LoadPrefixes`。

`traincache node status` 输出 Agent 是否可用、缓存目录内容、已缓存数据量、缓存剩余空间、运行中预热任务数、索引恢复与扫描状态,`--item` 只查其中一项。`traincache status` 输出任务 id、目标节点、数据路径、任务状态、总块数、已完成块数、失败块数、任务开始时间、最近更新时间。`traincache ls` 列出快照条目,默认按文件聚合输出 `FILE CHUNKS BYTES`,加 `--chunks` 展开到块并输出 `FILE CHUNK BYTES`;`--dataset` 必填,`--snapshot-id` 空表示当前 CURRENT,`--prefix` 过滤路径。输出默认人类可读表格。

## 坏块隔离

坏块物理移进 cas 根下的 `quarantine/` 目录,与 `blocks/` 平级,标记位就是块所在的目录,`List()` 自然看不到坏块。核心库提供三个动作:把坏块移进隔离目录(幂等)、列出隔离中的块、修复成功后清理隔离块。

Agent 侧读时遇到坏块走 repair,顺序是 `Quarantine`、入修复队列、`fetch.Fetch` 回源重下、`cas.Put`、校验通过、`RemoveQuarantined`。多个并发 repair 撞同一块时复用核心库既有的 single-flight,只下一次;后台全量扫描与异步 repair 同时碰到同一块时也合并成一次下载。`cas.Put` 对已存在同指纹块的行为是 rename 原子覆盖,幂等等价。修复成功后 `traincache_quarantined_blocks` 递减、`traincache_cache_misses_total{result="refetched"}` 计数,隔离数与队列长度由 `traincache_quarantined_blocks` 与 `traincache_repair_queue_depth` 暴露。补不及则本次读仍失败,Agent 只负责加速,不承诺读一定成功。

## 指标清单

指标服务于验证缓存价值,分七条线。所有指标默认带 `dataset` 基础标签,格式错误类和 hook_read_miss 线例外,不带 `dataset`;同一层级同一前缀,全部 `traincache_`。取值集合可枚举的低基数维度(dataset、node、result、endpoint、priority)进标签,取值数量随数据增长的高基数维度进日志;`dataset` 白名单外记 other。

语义与词汇冻结:

- phase 取 startup、steady、switch、unknown;命中来源取 prefetch、cache、unknown;stall 归因取 local_slow、prefetch_lag、origin_slow、unknown;消费推进来源取 hook、inotify;priority 取 P0 到 P3;订单通道状态取 discovered、healthy、stalled,聚合模式 none、healthy、partial、all_stalled 由状态计数派生、不进标签。
- 回源 reason 取 prefetch、demand、repair、other,四个术语固定:prefetch 是按 P0 到 P3 队列主动提前下载,demand 是训练侧 read_miss 钩子触发并复用预取队列补块,repair 是坏块隔离后重下,回源是这三者的总称。帧名 `read_miss`、处理函数 `handleReadMiss`、指标 `traincache_hook_read_miss_total` 保持不变,该指标统计帧,不区分回源路径。
- `traincache_cache_hits_total` 的 result 固定 success;`traincache_cache_misses_total` 的 result 取 success、error、refetched,refetched 对应 demand 补块成功。
- `traincache_fetch_singleflight_merged_total` 由 Agent 侧的 fetch 调用包装器统计:同一个 key 在途时第二个调用加一,不改核心库 fetch。`traincache_fetch_bandwidth_limit_bytes` 是配置的字节信号量上限、全场口径,预铺实际可用一半,与 `traincache_fetch_inflight_bytes` 求比值可判断限速是否打满。
- `traincache_read_stall_seconds` 只记达到 100ms 的消费等待,`_count` 是 stall 事件数,`_sum` 是 stall 总时长;`traincache_stage_switch_eta_seconds` 记阶段切换的预计等待,实测等待一律进 `read_stall` 且 phase 取 switch。`traincache_prefetch_hit_ratio` 来自 `Status.HitRate`,100 样本滑动窗口。
- `traincache_index_refresh_total` 的 result 取 success 或 error,失败不切换、不清空。`traincache_index_sweep_skipped_total` 的 reason 当前是 `manifest_unavailable`。
- `traincache_consumption_advance_total` 的 inotify 兜底路径是:inotify 收到 OPEN 后按指纹反查当前订单,再调 `OnConsumeSideAdvance`,单调去重后计 source 为 inotify。钩子活跃期 inotify 被 collector 门控抑制,不会和 hook 双计。已知限制:反查只覆盖当前订单的 Chunks。
- `traincache_index_refresh_total` 的 result 取 success 或 error,失败不切换、不清空。`traincache_index_sweep_skipped_total` 的 reason 当前是 `manifest_unavailable`。
- `traincache_gc_blocks_removed_total` 的计数来源是本地副本清扫:Agent 每轮删除的本地块数经 `AddGCBlocksRemoved` 累加,dataset 标签传空串、经白名单归 other。Collector 只回收对象存储对象,不产生块计数。

固定 bucket:

- `traincache_request_duration_seconds` 与 `traincache_index_refresh_duration_seconds`:`{.01,.05,.1,.5,1,5,10,30}` 秒;
- `traincache_read_stall_seconds`:`{0.1,0.25,0.5,1,2,5,10,30,60}` 秒;
- `traincache_prefetch_task_duration_seconds`:`{0.1,0.5,1,2,5,10,30,60,120}` 秒。

基数纪律:标签编译期固定,不引入用户输入,取值集合外的值直接忽略该次打点,时间序列集合不变;`dataset` 走配置文件白名单,白名单外记 other;`node` 是第二正交维度,为多节点聚合预留;高基数维度(path、chunk、fp、task_id)进日志;延迟用固定 bucket。

## 快照与回收

Agent 只读快照,不发布快照。

快照发布是写入方的事:产生新 entries 的组件调用核心库 `(*Writer).Commit`,由它合并快照并推进 CURRENT。发布由 `traincache trainpublish` 显式执行,切块上传后调 `Commit`。

快照跟随是 Agent 的只读职责:经 `index.Catalog.Start` 与 `Catalog.Refresh` 定时读 CURRENT,下载并校验 manifest 与引用分片,再用 `atomic.Pointer` 原子切换内存映射,读的人永远看到完整一份,失败保持旧映射。Agent 不调用 `Commit`。

自开观测防护由核心库 cas 提供 `SetOpenObserver(func(Fingerprint))`,在 `Store.Open` 内于 `os.Open` 之前回调,只登记本进程即将读打开该块,不改变 Open 行为。observer 挂在 Store 实例上,传 nil 清除,不做进程级全局。Agent 装配中创建 `cas.Store` 时调用 `cs.SetOpenObserver(guard.Mark)` 安装,位置必须在任何 prefetcher、rescan、backfill、fetch 构造之前;否则写入方内嵌调用 `Commit` 的自开读会污染消费侧信号。现有各调用点的显式 Mark 保留,幂等。

前缀感知跟随的冻结契约:

- `(*index.Catalog).SnapID() string` 原子读当前 snapID,没有则空串。
- `(*index.Catalog).RefreshManifest(ctx context.Context) error` 读 CURRENT 与 manifest,成功则原子切换 snapID 并换成空 entries,用于无活跃前缀时。当前 snapID 未变且现有 entries 非空时为空操作:不切换、不清空,也不触发 `OnSnapshotChange`。
- `(*index.Catalog).Follow(ctx context.Context, prefixes func() []string) error` 是阻塞循环,每 `Config.RefreshInterval` 检查一次 CURRENT,未变则跳过;`prefixes` 非空调 `LoadPrefixes`,为空调 `RefreshManifest`;失败保持旧映射并继续下一轮。
- `index.Config` 的 `OnSnapshotChange func(dataset, snapID string)` 字段由 `Refresh`、`LoadPrefixes`、`RefreshManifest`、`Follow` 在每次成功原子切换后、锁外触发,Follow 经其内部调用的加载方法触发;未发生切换的空操作不触发;不得阻塞,回调 panic 不得向调用方传播,nil 安全。
- `index.Config` 的 `OnSnapshotError func(dataset string, err error)` 字段只由 Follow 内部单轮加载失败触发,锁外调用,用于错误计数,同样 nil 安全且 panic 不外传。其他加载方法失败不触发该回调。
- Agent 侧的 `svc.Config` 有 `IndexRefreshInterval time.Duration` 字段,默认 5s。per-dataset 首次创建 Catalog 后启动一次 `go cat.Follow(ctx, prefixesFn)`,`prefixesFn` 返回该 dataset 最近订单的路径前缀。Follow 启动即执行首轮检查,所以启动时机在 bundle 构造内、当前订单的路径前缀 hint 写入之后,首轮 tick 不得读到空前缀;`ForOrder` 与 Follow 的加载必须串行,复用 Catalog 内部互斥。
- 刷新指标复用 `index_refresh_total{dataset,result}`,result 取 success 或 error,失败不切换、不清空。

读者登记的冻结契约:GC 删旧快照前需要知道还有没有节点在读,每个节点的 Agent 主动向对象存储登记本节点在读的快照。

- `core/index/readers.go` 定义 `ReaderClaim`,字段是 `NodeID`、`SnapID`、`PreviousSnapID`、`PreviousUntil`、`UpdatedAt`,JSON 字段名 `node_id`、`snap_id`、`previous_snap_id`、`previous_until`、`updated_at`。
- 对象键是 `dataset/<dataset>/readers/<url.PathEscape(nodeID)>.json`,一节点一 dataset 一文件。
- `func NewReaderRegistry(store objectstore.Store, nodeID string, grace time.Duration) *ReaderRegistry`,grace 小于等于 0 时回退 10s。`Declare(ctx, dataset, snapID) error`、`Withdraw(ctx, dataset) error`、`ReadReaderClaims(ctx, store, dataset) ([]ReaderClaim, error)`。
- `Declare` 在切换快照(本次 snapID 与上次不同)时写 `previous_snap_id` 为旧 snap、`PreviousUntil` 为 now 加 grace,给 GC 一个宽限期,刚切换完的旧快照不能立刻删;同一快照重复声明保留 previous 与 PreviousUntil,待 `now > PreviousUntil` 后清空;Put 覆盖,幂等,成功后更新内存里的 last。
- `Withdraw` 写空的 `snap_id`、`previous_snap_id` 为 last、`PreviousUntil` 为 now 加 grace、`updated_at` 为 now,之后停止心跳,best-effort。
- `ReadReaderClaims` 在没有对象时返回空集合,JSON 损坏返回错误,GC 需要 fail-safe。
- Agent 侧用 `nodeid.FromEnv()` 的 ID 构造 registry。心跳间隔是 `IndexRefreshInterval` 的一半,下限 1s;ctx 取消时对已知 dataset 调 `Withdraw`,超时 5s;`OnSnapshotChange` 立即 `Declare`。

回收规则:GC 删除快照前按有效读者 claim 判定保护集,固定保留数覆盖不到正在切快照的读者,因此只作兜底。`index.Config` 有 `ReaderGrace time.Duration` 字段(零值回退 `2*RefreshInterval`,默认 10s)与 `OnSweepSkip func(dataset, reason string)` 字段。`Collector.Sweep` 的规则是:

1. 读 claims,`UpdatedAt` 超过 `ReaderGrace` 的 claim 整体忽略,视为读者已死。
2. 有效 claim 的 `SnapID` 计入 protected,`PreviousSnapID` 只在 `now ≤ PreviousUntil` 时计入 protected,即切换与撤销宽限期。
3. protected 是 CURRENT 并上固定保留窗口(最近 `RetainSnapshots` 个)并上有效 claim 集合;`RetainSnapshots` 是兜底上限,安全边界由有效 claim 集合给出。
4. 快照对象(manifest 加分片)只在不在 protected 时删除,CURRENT 永不删除。
5. protected 快照的 manifest 缺失或损坏时调 `OnSweepSkip(dataset,"manifest_unavailable")`,该数据集本轮一个对象都不删,因为被复用分片是否仍被引用无法判定;不牵连其他 dataset,不整轮停摆。
6. `Sweep` 只删对象存储里的快照对象,返回删除对象数,不持 `*cas.Store`;本地块副本的删除面不在 Collector,按节点计算,归本地清扫。
7. 删除面里没有数据块,CURRENT 永不删,同一轮内不引入额外宽限。

提交失败要清掉本轮新写的对象:`(*index.Writer).commitOnce` 记录本次 attempt 新 Put 的分片键与 manifest 键,任何失败(含冲突重试前、验证失败)做 best-effort `Delete`,逆序、超时 5s、错误忽略、不覆盖原始错误;不复用键不删;`PutIfMatch` 成功提交后不清理。失败的尝试不在对象存储里留下无人引用的孤儿对象。

条件写探测提前告诉后端支不支持条件写,不必等真正提交时才失败:`objectstore` 包有 `ErrConditionalWriteUnsupported` 与 `func ProbeConditionalWrite(ctx context.Context, s Store) error`,做法是写临时键,用不匹配 ETag 调 `PutIfMatch`,期望 `ErrConflict`,若返回 nil 则返回 `ErrConditionalWriteUnsupported`,结束时删除临时键。Agent 的 `svc.Config` 有 `ObjstoreProbeConditionalWrite bool` 字段,默认 false,开启时装配期探测,指标 `traincache_objectstore_conditional_write_supported` 取值 0 或 1、预置 0,不支持时告警但不阻止启动。

开发演练用的本地 S3 兼容后端是 `bench/k8s/minio.yaml`,MinIO 镜像固定为 `pgsty/minio:RELEASE.2026-08-04T00-00-00Z`,manifest digest `sha256:b6bfe7239bfc83fb90d31612d9704d86039dd714f7904b3f1ad68f211e602372`;真实环境连 COS/OSS/S3 时不需要这个文件。真实后端条件写集成测试在环境变量 TC_S3_ENDPOINT、TC_S3_ACCESS_KEY、TC_S3_SECRET_KEY、TC_S3_BUCKET 任一缺失时 skip,存在时期望冲突返回 ErrConflict 或 412。

## 数据格式

字节层面的约定,实现逐字照做。JSON 字段顺序不影响解析,字段名和类型不能改。

ConsumeOrder 是共享内存载荷:

```json
{
  "dataset": "b-track", "snapshot_id": "snap-20261014",
  "stage_id": "epoch-2", "shuffle_seed": 20261015,
  "batch_size": 32, "prefetch_chunks": 256,
  "chunks": [ {"path": "shard-000.tar", "chunk": 0}, {"path": "shard-007.tar", "chunk": 0} ]
}
```

两条硬要求:`chunks` 必须按消费顺序排列,顺序错了预取就全错;`prefetch_chunks` 就是阶段首批块数。

共享内存环形缓冲的文件是 `/run/traincache/orders/<pod-uid>.ring`,小端字节序。sidecar 负责创建并 `ftruncate`,Agent 只读 mmap。文件头 64 字节:

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | magic `"TCO1"` |
| 4 | 2 | version=1 |
| 6 | 2 | 保留 |
| 8 | 8 | `writer_generation`(写端每次新会话启动加一,同一会话内续写不变) |
| 16 | 8 | `write_seq`(全局递增写入序号) |
| 24 | 4 | `slot_size`(默认 1 MiB) |
| 28 | 4 | `slot_count`(默认 64) |
| 32 | 32 | 保留 |

64 字节头之后是 slot 数组,每个 slot 布局是 `seq int64` 加 `len int32` 加 payload,也就是 ConsumeOrder 的 UTF-8 JSON。约定:

- 单写单读;写端只追加序号,不回收;读端按 `write_seq` 追读,落后超过 slot_count 时直接跳至最新,不阻塞写端;
- `writer_generation` 变化时读端丢弃旧状态重读最新,这样能识别 sidecar 重启,因为旧 ring 的序号可能和新的对不上;
- 代际的语义是写端会话换了。同一会话内的续写(包括保活心跳,载荷不变、只为推进 `write_seq`)必须续写当前代际。心跳若递增代际,会被读端判成 sidecar 重启,同载荷也重放一次,于是每次心跳都触发一次阶段切换与整段重预取;
- 读端发现格式不符时忽略该文件并计入错误指标,reason 取 magic(读不出或不是 "TCO1")或 version(version 与几何非法,slot_size 落在 16 字节到 64 MiB 之外、slot_count 落在 1 到 1024 之外);同一文件同一坏头状态只计一次,文件重开或代际变化后复验再失败才再计;
- 文件放在 tmpfs 上(hostPath `/run/traincache`,两侧 Pod 同路径挂载),宿主机重启自动清空,与重启丢弃长期历史的语义一致。

钩子帧约束:单帧不超过 4 KiB,解析失败就丢弃并计数,异常计数不带 dataset 标签以防基数膨胀。`read_stall` 的 `ts` 是 RFC3339Nano,`wait_ms` 只在达到 100ms 时上报。

`heatmap.json` 的路径是 `/var/cache/traincache/heatmap.json`,内容是 version、dumped_at 与 entries 三部分,entries 的键是 fp32hex,值含 heat、last_access、access_count:

```json
{
  "version": 1,
  "dumped_at": "2026-10-14T10:00:00Z",
  "entries": { "<fp32hex>": { "heat": 1.5, "last_access": 1763000000, "access_count": 3 } }
}
```

周期性原子写,临时文件再 rename,进程中途挂掉不留半个 JSON。重启恢复时读它;写入失败不影响服务,最多丢一段热度历史。

## 关键流程

### 启动与重启重扫描

Agent 重启后需要重建 CAS 索引,才能知道哪些块本地直接命中、哪些需要重新拉取;磁盘会静默损坏,所以要校验。启动后按顺序做五件事。

1. 读配置并校验 nodeid,初始化核心库(cas、fetch、objectstore、catalog)。
2. 枚举块目录(`cas.List`)重建内存索引,同时读取 heatmap.json。不读块内容,很快。
3. 抽样校验:随机挑 1% 的块全读校验,`cas.Open` 自带 xxh3 校验。全过就先把这批块视为没问题,把服务挂出来;发现损坏就 `Quarantine` 并投入修复队列,由后台全量按队列优先级处理。抽样让服务尽快可用,全量校验放后台低优先级。
4. 后台全量扫描:低优先级遍历所有块,维护一个需修复的队列,队列中已有的修复问题优先于剩余块的扫描。坏块在读时全量扫描还没修好的,直接从队列拿出来交给 Agent 从对象存储拉取,与修复下载共用核心库 single-flight,不会两边都下。扫描期间读 miss 的异步处理按 absent 走 demand、corrupt 走 repair,补不及则本次读仍失败。全量扫描没跑完也能正常服务,因为 CAS 读块时本身自校验,后台全量是提前发现。
5. 就绪探针的判断条件是 gRPC 服务可用且抽样阶段完成。全量扫描是否跑完不影响 ready。

重扫描包对外只暴露四个动作:启动扫描、查状态、注入自打开登记、按块修复。阶段取值三个:抽样阶段、后台全量扫描阶段、全部完成阶段。状态快照给出阶段、校验尝试累计数、通过数、累计隔离数、当前修复队列长度。构造时不做任何 IO,阶段与计数初值在启动与首次修复时装载。指标窄接口由接线层注入:一个写已校验块数占总块数的比例(完成态为一),一个写隔离目录里的坏块数(修复成功后递减);接口允许为空,打点静默跳过。

自打开登记钩子在装配期注入:扫描校验与修复后读回在打开块前先登记指纹,免得被 inotify 兜底当成训练消费。

### 预热任务生命周期

一次 `SubmitPreheat` 的完整路径:先校验 node 与 dataset,再解析快照(空 snapshot_id 用 CURRENT 兜底),然后 `Catalog.LoadPrefixes(prefixes)` 只加载所需 Manifest 分片,因为整份 manifest 在大数据集上加载慢到不可接受;由此得到块列表,与请求里的 chunks 求交,空表示全量;接着建任务置 QUEUED 并把块以 P0 入队;逐块处理时本地命中的直接跳过不下载,未命中的经核心库 fetch 下载,同键 single-flight 合并;每块推进 completed 或 failed;任务状态置 RUNNING、DONE 或 ERROR;`GetPreheatStatus` 全程可查。块级上报流随每块完成触发,Controller 缺席时直接丢弃,不阻塞。指定块预热只下选中的块。

### 订单通道降级

订单只是提示:训练正确性不依赖订单,丢单只损失预取效率,预取失效表现为消费停滞。降级描述的是订单通道还剩几路在推进;读服务、命中统计、钩子处理和订单投递在降级期保持不变。

每路 ring 是一路订单源,身份是 `(pod_uid, generation, dataset)`。状态有四种:discovered 是文件刚发现还没读到有效头,启动宽限 5 秒;healthy 是最近 30 秒内观察到 write_seq 推进,初始快照算推进,新代际算推进;stalled 是文件消失或超过 30 秒没推进;ended 是文件消失满 5 分钟回收,关 Reader、取消转发、移出表。mtime 超过 5 分钟的陈旧 ring 不建 Reader,计 `reason="stale_file"`。

聚合由 `OrderDiscovery` 单写者每秒算一次:没有 healthy 或 stalled 的源是 none,有活源且没有 stalled 是 healthy,同时有 stalled 和非 stalled 的活源是 partial,至少一路 stalled 且没有 healthy 或 discovered 是 all_stalled。`traincache_agent_degraded=1` 只在 all_stalled,其余为 0。每源计数进 `traincache_agent_ordersources{state}`,回收进 `traincache_agent_ordersource_ended_total{reason}`,读端跳读、损坏槽、空订单进 `traincache_orders_dropped_total{reason}`。启动后 5 秒宽限内不判 stalled,避免 Agent 重启瞬间被误判。

降级不影响订单投递:读端送来新订单就安装,去重按 `(generation, payload)`,新代际同内容也重放。sidecar 重启后读端先清当前订单,读到新订单即把会话追到当前阶段,不重放历史。

inotify 兜底只做统计和消费提示:钩子沉默时 inotify OPEN 计入热度与命中率,并可按当前订单反查推进消费游标;健康判定与恢复都不依赖它。已知限制是指纹反查只覆盖当前订单。实际 stall 由 `read_stall` 帧进 `traincache_read_stall_seconds`,phase 判不出时记 unknown。

### 回收与磁盘淘汰

回收和淘汰是两件事:引用回收删的是不再被引用的对象与副本,容量管理删的是仍被引用的块的本地副本。引用回收分两个删除面。

对象存储侧的回收复用核心库 `Collector.Sweep`,按上面的读者确认规则执行,删除面只有快照对象(manifest 加分片),不删任何节点的本地块。周期运行,热度不参与。

节点侧的本地副本清扫由 Agent 按节点周期跑核心库 `LocalGC.Sweep(ctx, datasets)`,默认 10 分钟,env `TRAINCACHE_LOCAL_GC_INTERVAL`。循环启动即跑首轮,重启积压的孤儿副本不用等一个周期。`datasets` 取全集,对象存储枚举并上本地已知,枚举失败整轮放弃;任一数据集的索引读不到(确定不存在除外)或损坏,整轮不删任何块,这是 fail-safe。活块集合是各数据集 CURRENT 引用的块并上有效读者 claim 保护的快照引用的块;删除走 `cas.Evict`,引用计数不挡,pin 大于 0 才返回 `ErrInUse` 并跳过留待下轮,生产路径不 Pin。删除的本地块数计 `traincache_gc_blocks_removed_total`,dataset 标签传空串、经白名单归 other。

磁盘淘汰是容量管理:缓存磁盘有限,可能被快照引用的块远大于盘容量;活数据淘汰是在逻辑上还需要 的块里决定哪些本地副本值得留。筛选活数据的条件是快照引用加无 pin 的本地块。淘汰动作只删本地副本,经核心库 `cas.Evict`,索引条目与引用关系不动,之后要用时经 fetch 重新下载,不重复 Acquire。淘汰得分由热度决定,与引用回收的删除判据无关。

淘汰循环的细节:

- 周期:Agent 层淘汰循环默认每 30 秒查磁盘利用率与字节占用两个维度,取先触发者。
- 与回收的接线:淘汰循环经 `evictor.Config.Sweep` 驱动对象存储侧回收,逐 dataset 调 `Collector.Sweep`,仍然只在越过触发线或危险线时跑;本地副本清扫走独立的周期,不经淘汰循环。
- 字节上限:env `TRAINCACHE_CACHE_CAPACITY_BYTES`,默认 0 表示关闭。开了之后 Agent 按块文件 size 累计本地块占用,块文件 size 是数据长度加 128 字节块头;累计值不能超这个值。三个记账来源必须同源:`cas.Put` 后置观察者按 `n + HeaderSize` 加,`cas.Open` 首次打开且块文件已存在时按文件大小加,`cas.Evict` 成功后按同一文件大小减。`cas.Open` 的前置观察者对缺失块同样触发,此时 stat 取不到 size 为 0,不得占用去重槽,否则随后本进程 `cas.Put` 同一块会被当成已累计而跳过记账。启动时预扫 `blocks/` 目录播种累计与去重表,只播种累计的话已有块被本进程首次打开会再加一次。关掉时只有磁盘利用率一个维度。
- 触发线:磁盘利用率超 k(默认 80%),或字节占用超上限,按淘汰得分 S 升序 Evict,降到 k 减 Δ(默认 85%)或字节上限的某个百分比。
- 危险线:磁盘利用率超 M(默认 90%),或字节占用超上限的 95%,此时 R 清零,按 h 升序激进淘汰,同时打告警指标与日志,降到 k 减 2Δ(默认 80%)或字节上限的某个百分比。激进指优先淘汰纯投机块,即预取了但还没被读过的块。
- 硬保护:cursor 加 lookahead(默认 16 块)覆盖的块在任何情况下都不淘汰,删了紧接着还要读等于多一次无谓回源。消费窗口不设独立保护机制,新 ConsumeOrder 到达时刷新订单内块的 `t_touch`,这些块自然拿到高 R。
- 热度只做淘汰的决策输入,簿记在 collector,核心库不感知热度。淘汰包不 import collector,只声明两个窄接口,由接线层适配:`HeatSource` 提供全量热度快照(指纹、热度、最近触摸时刻、累计打开次数),`ProtectedSource` 提供本轮硬保护指纹集合。
- 策略档位:「谁先被淘汰」抽象成 `Policy` 接口,放在 `agent/evictor/policy.go`,只有 `Rank` 一个方法;三档 heat、lru、lfu 运行时经 env `TRAINCACHE_EVICT_POLICY` 选择,默认 heat 与原行为逐字一致作为回归基准;未知值拒绝启动并打印合法清单。触发线、危险线、字节上限、硬保护与策略无关,三档共用;策略只替换选块这一层。

热度辅助预热:冷启动后读磁盘热度选出历史高频块,查本地 CAS 排除已有,对缺的块发起 fetch,低优先级、限流、可取消;也可手动触发。缓存淘汰看近期(内存),预热看历史(磁盘)。

## 部署与配置

Agent 以 DaemonSet 部署,每个缓存节点一份。部署清单只有一份:`controller/deploy/agent/daemonset.yaml`,由 `controller/deploy` 的 kustomize 渲染进发布包。Agent 必须能唯一确定自身所在 K8s 节点并在状态上报中携带节点标识。部署参数:

| 项 | 值 |
|---|---|
| 镜像入口 | `traincache-agentd` |
| hostPath 挂载 | `/var/cache/traincache`(rw,DirectoryOrCreate)、`/run/traincache`(rw,DirectoryOrCreate) |
| 探针 | liveness 用 gRPC health check 判进程活着;readiness 用 GetNodeStatus 且 `rescan.phase != SAMPLING` 判能否提供基本服务 |
| 资源 | request 100m/256Mi,limit 4Gi(内存) |
| 安全 | readOnlyRootFilesystem=true;缓存目录写权限经 hostPath 与安全上下文授予 |

环境变量:

- `NODE_NAME` 取自 fieldRef `spec.nodeName`,必填,启动校验非空。
- `TRAINCACHE_GRPC_ADDR` 默认 :9410,`TRAINCACHE_METRICS_ADDR` 默认 :9411。
- `TRAINCACHE_VERIFY` 取 xxh3 或 xxh3+sha256,透传核心库的校验档位。
- `TRAINCACHE_DATASET_WHITELIST` 是逗号分隔的白名单。
- `TRAINCACHE_CACHE_ROOT` 默认 /var/cache/traincache,本机演练与非标准根场景用。
- `TRAINCACHE_CACHE_CAPACITY_BYTES` 默认 0 表示关闭,开启后淘汰循环按字节阈值触发,磁盘百分比与字节两个维度取先到者;实验的公平对比需要统一设成 1GB。容量大于 0 时同时作为订单预取降级判据:订单数据集总字节超过容量,该订单只保留按需回源。
- `TRAINCACHE_EVICT_POLICY` 取 heat、lru、lfu,默认 heat,启动校验,未知值拒绝启动。
- `TRAINCACHE_LOCAL_GC_INTERVAL` 默认 10m,是 Agent 按节点清扫本地孤儿块副本的周期。
- `TRAINCACHE_PREFETCH_LOOKAHEAD` 默认 16,覆盖邻域预取提前量,扫点用环境变量注入,不加 CRD 字段。
- `TRAINCACHE_HEAT_*` 覆盖热度衰减阈值、dump 间隔、衰减周期与因子、增量系数、新鲜度半衰期和淘汰水位。
- `TRAINCACHE_OBJSTORE_*` 覆盖对象存储的 endpoint、access_key、secret_key、bucket、secure。
- `TRAINCACHE_GATEWAY_ENDPOINT` 默认空表示全部直连源站,非空时只有块 GET 走网关。
- `TRAINCACHE_GATEWAY_SECURE` 默认 false,是 Agent 到网关是否用 TLS,与 `TRAINCACHE_OBJSTORE_SECURE` 无关。

硬约束:

- Agent 必须具备访问本地缓存目录的权限,能执行缓存扫描、数据块读取、预热写入和垃圾回收;
- Agent 的退出、重启和升级不得破坏本地缓存数据的持久性,进程退出不应导致缓存目录中的有效数据块被主动删除;
- 后台扫描、校验和预取任务不得无界占用节点资源,CPU 与内存的请求与限制即为此设;
- 缓存未完成全量扫描不应直接导致 Agent 无法提供服务。

训练 Pod 侧三处配置:hostPath 只读挂载 `/var/cache/traincache/blocks/`;sidecar 容器挂载 `/run/traincache` 为 rw;训练容器也挂 `/run/traincache` 为 rw。DataLoader 适配器只往里写 `agent.sock`,订单 ring 仍由 sidecar 独占写入。

## 验收标准

前 11 条对应最初的服务化验收标准,第 12 条是补充验收。

1. 手动调用 gRPC 接口能够下发预热任务并查询进度。
2. Agent 通过 DaemonSet 部署在符合条件的缓存节点上,重启后本地缓存数据不丢失,索引能够自动恢复。
3. 训练 Pod 能通过 hostPath 只读挂载访问本地 CAS 数据块,直接读取数据,不经过 Agent 的 gRPC 读接口。
4. CLI 支持指定节点、快照路径和数据块进行手动预热,并支持查询预热进度和节点缓存状态。
5. 路径预热只加载所需的 Manifest 分片,不要求加载整个 Manifest;指定块预热不会意外下载未选中的数据块。
6. 磁盘损坏的块能够通过后台扫描或读时 repair 修复,且不会因并发 repair 产生重复下载。
7. Prometheus 指标能够被外部服务访问,覆盖命中率、回源量、索引刷新、GC、延迟和节点状态,并控制标签基数。
8. 启动最小训练 Pod 和 OrderSource sidecar 后,Agent 能够接收 ConsumeOrder 并启动 PersistentPrefetcher。
9. 阶段切换事件到达后,Agent 能够及时将新阶段开头 K 个块加入高优先级预取队列。
10. OrderSource sidecar 退出后,Agent 在 30 秒内把该源标为 stalled;全部源 stalled 时 `agent_degraded=1`,恢复推进后回 0,期间订单投递与钩子处理不中断。
11. 上述关键流程均有可重复执行的测试覆盖。
12. `/metrics` 出现 42 个 family,标签与指标清单一致。family 清单与构成见指标清单一节;验收命令用 `curl :9411/metrics`,断言所列 family 与标签集合出现,尤其 phase、source、cause、reason 的取值,`read_stall_seconds` 需有 `_count` 与 `_sum`。
demand 按需补块与预取去重、指标契约扩充、cursor 口径收口与 inotify 兜底、前缀感知跟随与读者登记及 GC 安全边界为补充验收,不在前 11 条内。
