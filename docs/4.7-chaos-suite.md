# 混沌套件规格

## 1. 套件目的与运行边界

混沌套件给运行中的 TrainCache 注入单点故障，逐档断言各部件的降级行为。注入点固定六个，网络劣化分两档，规格见第 2 节。

套件跑在开发机上，用 bench 用的 kind 集群 traincache（bench/Makefile 的 kind-up 目标）。控制面与 agentd 由 bench/scripts/ctrl_up.sh 拉起（`make -C bench ctrl-up`），命名空间 traincache，源站是命名空间 minio 里的 Deployment/minio（bench/k8s/minio.yaml）。集群里同时跑一个训练 Pod（agent/deploy/train-pod.yaml）：它带 ordersrc sidecar，并把节点缓存目录以只读方式挂到 /var/cache/traincache/blocks。

每档产物落在数据层 ~/tcd/chaos/<run-id>/。run-id 是一次运行的标识，由脚本按时间戳加四位随机后缀生成，一次运行一个目录，旧目录不覆盖。

bench 跑分测稳态下的吞吐与命中率，混沌套件测故障注入下的降级路径。两者共用同一个 kind 集群与同一套控制面清单，混沌档在跑分窗口之外发起。bench/scripts/tc_apply.sh 挂的 tbf 限速与混沌档的网络注入不同时生效。

注入与判定脚本在 bench/chaos/。仓库内只放脚本与清单，产物全部写到数据层。

本文用到的词：

- hostPath：节点上的目录，Pod 把它挂进容器。套件用到两个：/var/cache/traincache（块目录）与 /run/traincache（订单 ring 文件）。
- netem：内核的队列规则（qdisc），能加延迟、抖动与丢包。用 `tc qdisc add dev eth0 root netem ...` 挂在网卡上。
- rescan：Agent 启动时扫描本地块目录、重建块到数据集映射并逐块校验的过程，代码在 agent/rescan。
- 门控：Pod 的 `spec.schedulingGates` 上挂的调度闸门，不放行时 Pod 停在 Pending。
- 订单通道：ordersrc sidecar 与 Agent 之间的 ring 文件通道，写端是 sidecar，读端是 Agent。

## 2. 注入档规格

| 编号 | 注入点 | 注入命令或动作 | 期望表现 | 判据 | 档位 |
|------|--------|----------------|----------|------|------|
| 1 | Agent 进程崩溃 | `kubectl -n traincache delete pod <agentd-pod> --grace-period=0` | Agent 重启，rescan 重建块到 (dataset, path, chunk) 的映射；已落盘的块留在 hostPath 上不重下；训练侧按当前订单继续 | `traincache node status --item rescan` 输出的 RESCAN_PHASE 离开 SAMPLING；`traincache_fetch_bytes_total` 的窗口增量接近 0；`traincache_quarantined_blocks` 不增 | 必跑 |
| 2 | 网络劣化（档 2A：抖动与丢包） | 源站容器 eth0 egress 挂 netem（delay + jitter + loss） | 回源请求在字节信号量与任务槽前排队；读等待落在 60s 桶内；训练 Pod 存活 | `traincache_fetch_inflight_bytes` 的采样最大值记入产物作背压证据；`traincache_read_stall_seconds_bucket{le="60"}` 覆盖 `traincache_read_stall_seconds_count`；训练 Pod 不退出 | 必跑 |
| 2B | 网络劣化（档 2B：加限速） | 档 2A 的 qdisc 换成 tbf + netem（固定 delay + jitter + loss + 速率上限） | 带宽上限生效，在途字节不超过上限；读等待落在 60s 桶内；训练 Pod 存活 | `traincache_fetch_bandwidth_limit_bytes` 的取值等于生效上限（默认 1073741824 字节）；`traincache_read_stall_seconds_bucket{le="60"}` 覆盖 `traincache_read_stall_seconds_count`；训练 Pod 不退出 | 必跑 |
| 3 | 数据损坏 | 改 hostPath 上一个块文件的数据字节（/var/cache/traincache/blocks/<xx>/<fp>.blk） | 校验失败，块移入 quarantine/，进修复队列重拉 | `traincache_quarantined_blocks` 上升；`traincache_repair_queue_depth` 上升后回落；`traincache_fetch_requests_total{reason="repair"}` 上升 | 必跑 |
| 4 | 数据源宕机 | `kubectl -n minio scale deployment/minio --replicas=0` | 回源请求拿到 504 与错误码 XTraincacheGatewayOriginUnavailable；门控 TMax 到期后 WarmupTask 落 Degraded 并摘掉 Pod 的 schedulingGates，Job 离开 Pending；训练读路径取不到块，训练 Pod 退出或 Job 失败是本档的预期终态 | WarmupTask `status.phase` 出现 Degraded；`traincache_source_mode` 与 `traincache_gateway_fallback_total` 不动；训练 Pod 进入 Failed 或 Job 落 Failed；源站恢复后重新起训，`traincache_hook_read_miss_total{reason="absent"}` 上升且补块续上 | 必跑 |
| 5 | 订单通道停写 | 在 ordersrc 容器内给 PPid==1 的子进程发 SIGSTOP | 写端停止推进满 30s 后该路订单源标 stalled；只有一路订单源时 `traincache_agent_degraded` 置 1；写端恢复后回落 0 | `traincache_agent_ordersources{state="stalled"}` 计数不小于 1；`traincache_agent_degraded` 走 0→1→0 | 必跑 |
| 6 | 节点丢失 | `docker stop <kind 节点容器>` | 候选节点出列，控制器停止下发；门控仍由 TMax 兜底放行 | DataSet condition `NoAccessibleNodes` 为 True；WarmupTask `status.phase` 落 Degraded | 可选 |

## 3. 判据口径

### 3.1 采集口径

Agent 侧指标从 agentd 的 9411 端口取：`kubectl get --raw "/api/v1/namespaces/traincache/pods/<agentd-pod>:9411/proxy/metrics"`，与 bench 的取法一致（bench/compare/run_bench.py 的 `_agent_metrics_texts`）。控制面指标取 controller-manager 与 kube-scheduler 的 :9412/metrics/traincache（controller/cmd/controller-manager/main.go 的 `metricsPath`、controller/cmd/scheduler/main.go 的 `metricsPath`）。

每档取三个时点：注入前基线快照、注入窗口内的周期采样、注入结束后的终值。counter 判据一律取窗口差分，gauge 判据取终值。

### 3.2 rescan.phase 与就绪判据

rescan.phase 的取值是 SAMPLING、FULL_SCAN、DONE（agent/rescan/rescan.go 的 PhaseSampling、PhaseFullScan、PhaseDone），Agent 的节点状态查询把它们映射成同名枚举（agent/svc/server.go 的 `rescanPhase`）。

Agent DaemonSet 的 readinessProbe 执行 `traincache node status --node "$NODE_NAME" --item rescan`（controller/deploy/agent/daemonset.yaml）。该命令打印 RESCAN_PHASE 后以 0 退出（agent/cmd/traincache/main.go 的 `runNodeStatus`），探针本身不按阶段取值判失败。判据取命令输出里 RESCAN_PHASE 是否离开 SAMPLING，不取 Pod 的 Ready 位。

第 1 档不含 `traincache_orders_dropped_total{reason="resync"}` 判据。Agent 重启后 Reader 走首次接入路径（agent/ordersource/reader.go 的 `resyncLocked`，suppress 为真），历史序号不计入丢单；resync 计数在写端换代或 write_seq 回退时才涨。

### 3.3 在途数与带宽上限的量纲

`traincache_fetch_inflight_bytes` 记的是在途 Fetch 调用数：agent/prefetch/prefetcher.go 的 `reportFetchStart` 与 `reportFetchEnd` 在调用 core fetch 前后各加减 1。

`traincache_fetch_bandwidth_limit_bytes` 记的是 core fetch 的字节信号量上限：core/fetch/limiter.go 的 `defaultMaxInflightBytes`，默认 1 GiB；agent/svc/metricswiring.go 的 `reportBandwidthLimit` 上报该值。

两个数不同量纲，比值关系不成立。并发下载任务数由 core/fetch 的任务槽压住（core/fetch/limiter.go 的 `defaultMaxTasks` 为 8，预铺另占 `specTasks` 的一半 4 槽），字节在途总量由 byteSem 保证不超过上限，当前字节用量没有对应的指标族。第 2 档的有界性判据落在读等待分布与 Pod 存活上。

### 3.4 60s 与 30s 两个数字的出处

60s 是 `traincache_read_stall_seconds` 的桶上界：agent/metrics/families.go 的 `readStallBuckets` 为 {0.1, 0.25, 0.5, 1, 2, 5, 10, 30, 60} 秒，超过 60s 的等待只落 +Inf 桶。判据写成 `traincache_read_stall_seconds_bucket{le="60"}` 的计数等于 `traincache_read_stall_seconds_count`，差值为 0 表示全部读等待在 60s 内。

30s 是订单源的停滞阈值：agent/svc/orders.go 的 `orderStallThreshold` 为 30s，严格大于阈值才算停滞；同一文件的 `degradeTickInterval` 每 1s 聚合一次，`orderStartupGrace` 给 5s 启动宽限。冻结写端后判定落在停止推进满 30s 之后，聚合周期 1s，最迟再加不到 1s。

### 3.5 netem 挂点与丢包方向

挂点取出站方容器 netns 内 eth0 的 egress，做法是节点容器内 `crictl pods --state Ready --name <pod> -q` 取 sandbox 的 containerID，`crictl inspectp` 取 netns 路径，再 `nsenter --net=<netns>` 挂 qdisc（bench/scripts/tc_apply.sh 的挂载段）。

qdisc 挂在出站方向，只作用于源站到 Agent 的数据包，含重传段。Agent 到源站方向的 ACK 不经过该 qdisc，源站按 TCP 重传把数据补齐，读侧量到的是重传恢复后的完成耗时。

抖动会打乱包序。docs/4.1-bench-setup-and-rules.md §1 的 300mbit 记录里，逐包重抽时延把吞吐从 35.6 MB/s 打到 0.6 MB/s 以下。混沌档的吞吐读数带同样成分。

### 3.6 TRAINCACHE_VERIFY 档位与改字节的检出

默认档 xxh3 能发现改字节：core/cas/store.go 的 `Open` 流式重算数据 xxh3 并与块头比对，不符返回 ErrCorrupt。注入前无需切换 Agent 的 `TRAINCACHE_VERIFY`。

xxh3+sha256 的作用范围是切换之后新写的块。sha256 写进块头（core/cas/header.go 的 FlagHasSHA256），读时按块头标志双验（core/cas/store.go 的 `Open`），切换档位不改写已有块（docs/5.2-decisions.md D13）。要测 sha256 分支，注入目标块必须在切换之后新写。

sha256 针对的是构造性碰撞，随机改字节两类摘要都能发现（docs/5.2-decisions.md D10）。

改字节的动作要在节点上做，块文件路径由 core/cas/store.go 的 `blockPath` 决定，形如 <cache-root>/blocks/<fp 前两位十六进制>/<fp 十六进制>.blk。Agent 检测到损坏有两条路径：rescan 全量校验（agent/rescan/rescan.go 的 `verify`）与读时修复（agent/svc/wire.go 的 `repairCorrupt`）。第 3 档的注入后动作取其一：重启 agentd 触发 rescan，或让训练侧重读该块。

训练容器把块目录只读挂载，直接读文件。Agent 把坏块移入 quarantine/ 之后，训练侧的 open 拿到 ENOENT，钩子把这次读记成 read_miss 帧，Agent 走 demand 补块。

### 3.7 网关线两个指标与源站宕机的对应关系

`traincache_source_mode` 是二值 gauge，0 直连源站、1 走网关（agent/metrics/families.go 的 `SetSourceMode`）。`traincache_gateway_fallback_total` 的 reason 取 unavailable、timeout、transport 三个值。

三个 reason 都对应网关这一跳的失败：unavailable 来自网关自报不可用，transport 与 timeout 来自网关连接层失败（agent/svc/backend.go 的 `reportFailure` 分支与 core/objectstore/gateway.go 的 `classifyGetError`）。源站自身返回的错误由 `classifyGetError` 原样返回，不进降级计数。

源站宕机时网关这一跳仍然健康，两个指标不动。验网关降级动作时，注入点选网关这一跳；源站宕机不触发降级计数。

### 3.8 门控判据的落点

门控是 Pod 的 `spec.schedulingGates` 上挂的调度闸门，不放行时 Pod 停在 Pending。controller/internal/gate/gate.go 的 `Evaluate` 按 TMax 优先判定，条件③超时给出 state=Degraded、reason=tmax_exceeded。controller/internal/controller/warmup/gate.go 据此把 `status.phase` 写成 Degraded，并摘掉 Pod 的 schedulingGates。

Degraded 与 Released 是 WarmupTask 的 phase 取值（controller/api/v1alpha1/warmuptask_types.go 的 WarmupPhaseDegraded、WarmupPhaseReleased）。DataSet 的 condition 只有 Ready 与 NoAccessibleNodes（controller/internal/controller/dataset/controller.go 的 `ConditionNoAccessibleNodes`）。

## 4. 装置复用

### 4.1 控制面与 agentd

bench/scripts/ctrl_up.sh 幂等拉起 namespace、节点标签、Secret、webhook TLS、controller-manager、webhook、scheduler、agentd 与可选网关（TRAINCACHE_GATEWAY=1 时网关副本 1，否则 0）。套件直接调这个脚本，不另写 apply 步骤。脚本会断言 kubectl context 是 kind-traincache，context 不符时直接失败。

### 4.2 netem 挂点

挂点沿用 bench/scripts/tc_apply.sh 的路径：节点容器内 `crictl inspectp` 取 sandbox netns，再 `nsenter` 挂 eth0 egress。

混沌档的 netem 与 bench 的 tc_apply.sh 不同时生效。档 2A 只挂 netem；档 2B 在 netem 之外加 tbf 限速，把 tbf 挂在 root、netem 挂在子队列。bench 的 `netem_args` 只有固定 delay 一档，抖动与丢包由混沌脚本自己发。

### 4.3 qdisc 生命周期

qdisc 挂在容器 netns 内，容器重建后 netns 换新，qdisc 随之消失，套件不做清理命令。同一容器生命周期内换档时先 `tc qdisc del dev eth0 root` 再挂新的。

### 4.4 块目录与隔离目录

块目录是 hostPath /var/cache/traincache 下的 blocks/，隔离目录是同级的 quarantine/（core/cas/store.go 的 `quarantinePath`）。两者同两级分片，改字节与查隔离结果都在节点上做。

## 5. 观测通道

### 5.1 Agent

agentd 的 9411 端口提供 /metrics，指标族在 agent/metrics/families.go 注册。网关线的两个族也在 agentd 上：`traincache_source_mode` 与 `traincache_gateway_fallback_total`。

### 5.2 控制面

controller-manager 与 kube-scheduler 的项目指标在 :9412/metrics/traincache。webhook 不注册项目指标族。门控与调度相关的族取 `traincache_controller_gate_tasks`（state 分 hold、released、degraded）与 `traincache_controller_candidate_nodes`。

### 5.3 网关

网关不注册 prometheus 指标，也没有 /metrics 端点。网关的观测面是结构化日志（component=gateway）与 60s 汇总（gateway/internal/obs 的 Logger）。网关线的定量判据从 agentd 的两个族取。

### 5.4 checkpointd

checkpointd 不注册指标，也不写 Kubernetes Event，六档里没有以 checkpointd 为注入点的档。它的观测面只有日志字段表：公共字段见 docs/8.1-design.md §3.1，Loki 标签 component=checkpointd，查询式为 `{namespace="traincache", component="checkpointd"}`（docs/8.4-logging-and-monitoring-usage.md §二）。

### 5.5 core

core 是库，包内没有指标端点。core 侧的行为由 agentd 的指标族与 core 包日志字段覆盖。

## 6. 运行方式

### 6.1 前置条件

控制面在位（`make -C bench ctrl-up`），训练 Pod 已创建（agent/deploy/train-pod.yaml），源站桶里已有块数据。

### 6.2 必跑档

第 1、2A、2B、3、4、5 档由一条命令跑完：

```
bash bench/chaos/run_chaos.sh --suite required
```

### 6.3 可选档

第 6 档单独一条命令：

```
bash bench/chaos/run_chaos.sh --suite optional
```

### 6.4 产物落点

```
~/tcd/chaos/<run-id>/
  run.json            运行元信息：run-id、集群名、档位集合、起止时刻
  <tier-id>/          一档一个子目录
    metrics/          agentd 与控制面的 /metrics 原文快照
    events/           kubectl events 与 Pod 状态快照
    verdict.json      判据逐条结果：判据名、实测值、取值
```
