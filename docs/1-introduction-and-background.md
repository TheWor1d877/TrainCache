## TrainCache 介绍
面向k8s训练Job的全程数据流加速器,工业界将数据预热做成一次启动时候的临时操作，预热完成之后就手动不管
训练pod落到节点上面之后整个epoch中后期出现的data stall没有人兜底

TrainCache是负责将启动欲取拓展成贯穿训练全程的闭环，分为Pod调度阶段与Pod落地后两个阶段：
调度阶段按照Job实际消费的数据子集,以块粒度向候选节点提供数据，并按照细粒度的就绪度门控并且打分作业
如果节点准备超时就自动降级

Pod落地后由Agent按照消费顺序持续欲取后续块，epoch 切换或 shuﬄe重排时按新顺序重新预取

最后，我们⽤端到端 makespan 和真实部署起来的Fluid/JuiceFS 同台跑分，分别量化启动阶段收益与全程收益。

#### 定位
对标者：我们把 Fluid（Dataset/DataLoad/Runtime 加缓存亲和调度）和 JuiceFS 社区版当作⼀等对照组真实部署起来，在同样的负载下跑分，绝不打空⽓靶；

测量者：我们最看重的指标有四个——Job 从提交到跑起第⼀个 step 的时间、整个epoch的makespan、训练全程的 dataloader stall 占⽐、缓存命中率分阶段曲线；
预热时重复搬运的字节成本仍然计⼊分⺟；我们允许阴性结论，并且在实验开始之前就把假设预注册下来；

改进者：现勘证实的缺口以测量数据支撑，向 Fluid 提 issue/PR，而不是停在"我自己的仓库里有这个功能

#### 明确:
不是又一个分布式文件系统
不是缓存算法论文
不是需要 GPU 的项目——全项目在 CPU 训练循环上即可测
它不调度 epoch（epoch 是 Pod 内部循环，不触发 K8s 调度）阶段切换是节点内缓存⾏为，永远不进调度路径


## 外部事实
- Fluid实用的缓存亲和度是"粗粒度二进制 + 事后注入"
Fluid 的逻辑：Pod 引用了 Dataset A → 节点上装没装 A 的 Runtime？装了 → 加分；没装 → 不加分。
等Pod已经创建了,才去修改他的spec: 往里面增加nodeAffinity
若 Pod 自带 affinity/nodeSelector 则跳过注入: 
它回答的问题是”节点上有没有这个 Dataset 的 runtime/缓存”，不知道缓存了多少⽐例、哪些块

问题所在:
DataLoad不知道怎么调度: 手动拉取数据智能拉取全量,因为不知道接下来跑得Job需要哪些分片
调度不知道DataLoad: webhook 注入亲和的时候，它只检查"节点上有没有 Runtime"，不检查"这个 Dataset 的数据拉了多少、拉了哪几块"。所以它可能把一个 Job 派到一个"Runtime 开着但数据只拉了 10%"的节点上。

在工业方案中,预热是针对整个Dataset或者某个prefix的,不是针对某个具体Job要读取的那几个分片
- 预热是独⽴、⼿动创建的 CRD，与调度决策不闭环,调度也不按 DataLoad 的块级进度门控

- 本项目使用社区版:分布式缓存组（⼀致性哈希环、peer 间共享块）、
   IORPC、RDMA 均为企业版能⼒

- 2026 年训练数据加载的主流形态: 
  webdataset tar 分片 / Mosaic MDS 这类百 MB 级分片 + 确定性 shuffle 的流式读取数据打包成 100MB 级别的大分片（webdataset tar 或 Mosaic MDS），顺序流式读取，shuffle 是确定性的（用种子控制）。不再是百万小文件的元数据压力场景.
  训练中的主负载应该是"百 MB 分片 + 真实 DataLoader",而不是百万小文件

- 训练阶段切换的真实形态
一个训练Pod从启动到结束常驻同一个节点，从 epoch 0 跑到最后⼀轮，epoch 切换、shuﬄe重排、curriculum 阶段切换全部是 Pod 内部循环，根本不触发 K8s 调度。
如果要做阶段切换预热，必须做成节点内缓存欲取策略而不是重新调度Pod来预热

- 数据并行下分片对应关系
分布式训练的主流形态是数据并⾏，整份数据被所有 Pod 合起来跑⼀遍，每个 Pod 只跑⾃⼰的分⽚，Pod 之间不重复。
所以预热要按”Pod 分⽚”对应到候选节点，⽽不是每个候选节点都预热全量

## 仍然成⽴的问题（本项⽬的缝） 
1. 训练全程的数据流⽆⼈加速：⼯业⽅案把预热当成启动时的⼀个动作，预热完之后训练 Pod 就靠⾃⼰读 page cache 和回源拉数据。 
epoch 中后期 page cache 失效、shuffle 之后顺序被打乱、热⼦集被换出，这些都会再次造成 data stall，但这时候 Pod 已经在节点上跑着，没有任何组件再帮它把数据提前铺好。

2. 预热与调度不闭环：⼯业⽅案⾥”先⼿动 DataLoad、再靠⼆进制亲和碰运⽓”之间，没有”Job 即将调度 → 向哪⼏个候选节点预热它需要的那些块 → 块级就绪度决定何时放⾏/如何打分 → 超时如何降级”的控制回路；

3. 预热成本⽆⼈记账：向 2‒3 个候选节点重复预热有 2‒3 倍字节与带宽代价，什么情况下这笔代价值得，没有公开曲线。
