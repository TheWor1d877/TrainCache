# Controller
## 定义两个CRD，并实现Controller
两个CRD：DataSet与WarmupTask，并且实现他们的子资源（将status与主端点解耦，scale不开）
DataSet: 静态描述数据长什么样子，如何被消费。回答有哪些块、块在哪
WarmupTask: 一次预热的运行时载体，回答给谁预热、分别预热哪些块、分别现在预热到哪里了，现在准备到哪里了
用户只需要创建DataSet与WarmupTask两个CRD即可完成整套预热任务，Controller中没有Job这个概念，不需要用户写Job的yaml文件
#### DataSet：登记数据集
这里只描述关键字段，不做完整CRD的yaml文件描述
- 基本字段
group: traincache.io
name: datasets.traincache.io
scope: Namespaced
version: v1alpha1（storage: true）
subresources: 开status
schema: 只描述spec与status的字段结构，k8s使用schema做校验
- 关键语义
1. 数据源: 存储后端endpoint，bucket，数据集名(`dataset/<数据集名>/`这一层)，引用凭证(Secret),当前使用的快照id，哪些节点能访问数据源
2. 块结构: ChunkSize，一个三元组列表`[ (tar分片名称,块数,尾块大小) , ... ]`
3. 元数据: 这是给人或者上层工具看的业务描述，包括：样本数量、数据格式、内容说明、数据版本、来源、用途(默认留空即可，这些内容 只做登记 ，Controller 与 Agent 都不读它做决策)
这里面有spec字段也有status字段，需要自行分辨，此处只描述实现功能
不记录谁引用的Dataset
#### WarmupTask：登记一次预热


这里只描述关键字段，不做完整CRD的yaml文件描述
命名空间：namespaced
1. 预热的DataSet
2. 训练类型(枚举：epoch/shuffle/curriculum/static)，随机种子不进spec，放到DataLoader即可
3. 需要的训练Pod数量，Pod之间的亲和策略（v1 只登记，不参与分配；一个预热节点最多认领一个 Pod）
4. 筛选出来的候选节点列表(详细筛选方法见下面)
5. readinessTable：P×N 就绪表（窗口内就绪块数，不是比例），分配依据，也是观测入口。(P、N 几十到几百，表是 P×N 个整数，可控)
6. podNodeReadiness:每个 (Pod, 实际认领的预热节点) 配对一条，条数不超过 preheatFanout，至少记录一下内容，podName与PodDetail之间通过podNodeReadiness来关联
   - nodeName
   - podName
   - podDetails（是用户手动填写的，约定每个Pod如何使用资源与资源配置情况）
     - 实际消费的 tar 分片名清单 initialConsumeFiles（未指定、含未知分片、重复或覆盖不全时，整组按 Pod 数量默认切分），
     - 启动窗口K
     - 需要资源声明
   - readyBlockBitmap：块级就绪位图（只有“落盘 + 校验通过”才置 1）
   - startupWindowReady：窗口内就绪块数
   - startupWindowReadyRate：= startupWindowReady / K（仅用于观测；门控用整数判据 startupWindowReady ≥ floor(阈值 × K)）
   - globalDecayScore：全局衰减就绪度得分（取整，放行快照）
   - lastReportTime：最近上报时间，用于判“进度是否还在涨
7. gateDecision(门控状态机，记录门控状态与放行原因)
8. lastUpdated：最近一次 status 更新时间，用于观测“分数是否还在动”
9. observedGeneration：幂等必备，判断 status 是否已反映最新 spec


###### 候选节点筛选
资源条件：节点的 allocatable 能覆盖最大的 podDetails[].resources.requests 声明，ephemeral-storage 的 allocatable 不小于 candidate.minFreeDiskBytes。预热本身消耗节点资源（缓存、IO），给一个装不下的节点预热是浪费。
数据可达性：节点需带有人工维护的 `traincache.io/s3-access=true` 标签；Dataset 可声明可选 selector 进一步收窄。排除拿不到数据的节点。
节点健康状态：NotReady、带 NoExecute 污点的节点直接排除；NoSchedule 污点在 candidate.ignoreNoSchedule 为 false 时也排除。
Agent 条件：节点上要有 Ready 的 Agent Pod，控制器才能向它下发预热。

#### DataSet::Controller核心逻辑
- 概述
它是静态数据契约，不是运行时执行者
负责校验数据是否合法，固化块空间，探测入口，确认node节点是否可以访问数据源

- 核心逻辑
1. 接收到一个DataSet声明，先检验数据字段是否完整(如chunkSize>0)，
2. 检查后端格式是否正确，bucket,数据集名,Secret引用正确，三元组列表格式正确等
3. 入口是否能访问： 检查快照指针(不一定就是CURRENT指针，可能任务开始后数据变化)，快照清单是否存在，能否正常访问等
4. 检查节点标签 `traincache.io/s3-access=true`，判断哪些节点可以访问数据源；该标签由用户/集群管理员手工添加到 Node，任何组件不得自动写入
5. 展开块空间，固化编号规则：数据块号只在 DataSet Controller 推一次，写进 `blockLayout`，每个分片记 `startChunk`（该分片首块的全局编号）与 `count`
```text
totalChunks: 9
blockLayout:
  - shard: shard-000.tar, startChunk: 0, count: 3, lastChunkSize: 50MB
  - shard: shard-001.tar, startChunk: 3, count: 2, lastChunkSize: 30MB
  - shard: shard-002.tar, startChunk: 5, count: 4, lastChunkSize: 50MB
```
6. 写status
7. 不向引用方发通知：WarmupTask 不 watch DataSet，需要时在下一轮 reconcile 里重新读取 DataSet 的 status

- 幂等操作
  控制器重启，事件重放都不能产生重复操作informer的事件可能重复送达，reconcile 逻辑必须做到执⾏几次都结果⼀样

#### WarmupTask::Controller的核心逻辑
- 概述
WarmupTask::Controller是WarmupTask的唯一执行者，监听WarmupTask创建之后的行为
先筛选出值得预热的节点，向这些节点Agent下发块级别的预热任务(gRPC函数调用)
然后持续收集Agent上报的进度，算出各个节点的就绪度
当就绪度达标之后，摘除Pod上面的SchedulingGate，保存此时的分数快照，放行调度，
同时将算好的分数快照暴露给调度器，作为调度器选择节点的一个偏好
它管“数据备好没、能不能放行、哪个节点备得最好”，不管“Pod 最终坐哪”

- 名词声明
就绪度：指数据准备好了多少的度量
窗口内就绪度：只看启动窗口内那部分数据准备好了多少
全局衰减就绪度:看全程数据备好了多少，但按块离起点的距离加权：窗口内权重 1，窗口外指数衰减，衰减到阈值以下不计
全局衰减就绪度 = 窗口内就绪度 + 窗口外就绪度
预热节点集合（下文也称暖节点集合）：某个 Pod 在本次任务中被选中预热的那些节点，数量在 preheatFanoutMin 与 preheatFanout 之间，实际认领数可能低于下限
最终落点：调度器真正把 Pod 放到的那一个节点，正常情况下从该 Pod 的预热节点集合里选出，被抢占时也可能落到集合之外

- 具体逻辑
1. Controller盯着训练Pod的声明，筛选出候选节点，然后使用GWAA算出每个节点需要预热哪些Pod的窗口，以及每个Pod需要预热哪些节点（上限 preheatFanout、目标下限 preheatFanoutMin）
2. 通过gRPC调用向这些节点下发块粒度级别的预热任务
3. 接收Agent的进度汇报，更新 podNodeReadiness（配对级）：
4. 将就绪度填回到CRD的status里面
5. GangScheduling Gate(这不是在Scheduler里面的Permit hook上面的)，持续观察各预热节点的 startupWindowReady 计数，rate 只用于观测
6. 门控按三条判据裁定，优先级从高到低是超时、全达标、提前降级，都不满足时保持 Hold；门控仍为 Hold 时先做两条前置跳过判断，命中任一也放行
   1. 每个 Pod 的预热节点集合中至少有一个节点，其该 Pod 的 startupWindowReady ≥ floor(阈值 × K_i)（阈值大于 0 时结果不足 1 取 1、超过 K_i 取 K_i；例如 K=8、阈值=0.8 时 6 块即可）；预热节点集合就是该 Pod 实际认领的那些节点。全部 Pod 满足才放行
   2. 已经有一个pod达标、且距第一个 Pod 达标已不少于 min_interval 之后，未达标的Pod的提前降级条件必须同时满足“gap > gap_min”和“slope < slope_min”；
   ```text
   gap  = gateThreshold - rate          // 离阈值还差多少
   slope = (rate_now - rate_prev) / (t_now - t_prev)   // 就绪率变化速度，需上报间隔 >= min_interval
   
   if gap > gap_min  &&  slope < slope_min:
   触发提前降级放行
   ```
   3. 从 startedAt 起算已经到 t_max 时降级放行；t_max 不大于 0 时这条不启用
   4. 门控不值得挡：数据集总字节大于 0 且小于 cacheCapacityBytes / 20（整数除法；cacheCapacityBytes 未配置时不触发），或 agent 上报吞吐 > networkBandwidthBytes × 0.8 且数据集总字节 < 5GiB（networkBandwidthBytes 未配置时不触发）；两条都命中时记前者
7. 放行逻辑
   1. 对每个还没摘 gate 的 Pod 算出它在实际认领各预热节点上的全局衰减就绪度分数 S(node)；这份快照交给 Scheduler，从这往后预热的不算入分数
   2. 把该 Pod 的节点到分数表和“摘掉 SchedulingGate”放进同一次 Pod patch，Scheduler 在各 Pod 的暖节点集合中选择最终落点
   3. 全部 Pod 处理完再写 status

- 幂等操作
控制器重启，事件重放都不能产生重复操作informer的事件可能重复送达，reconcile 逻辑必须做到执⾏几次都结果⼀样

#### 就绪度得分逻辑
- 参数
K： 启动窗口大小（前K块权重均为1）
H： 半衰期（多少块后权重掉一半）
C： 截断距离（超过不计分）
- 公式
$$
w(i) =
\begin{cases}
1, & i < \min(K, C) \\
0.5^{\frac{i - K}{H}}, & \min(K, C) \leq i < C \\
0, & i \geq C
\end{cases}
$$
窗口内恒 1 ，窗口外按半衰期指数衰减：每过 H 块，权重减半，超过 C 直接 0，不计；K 不小于 C 时没有衰减段
窗口内与窗口外的贡献分开算，写进 Pod 注解的只有合成分数

#### GWAA：贪心窗口亲和分配（Greedy Window Affinity Assignment）
###### 定位
GWAA 是一个纯分配算法模块，只回答一个问题：在候选节点上，每个节点应该预热哪些 Pod 的窗口。
它给每个 Pod 选出不超过 preheatFanout 个预热节点；Pod 的最终落点不在此处决定，由 Scheduler 在放行后的分数快照中选择。
它不涉及门控、放行、调度与兜底，输入输出边界清晰，可独立实现与测试。
###### 输入
Pods（P 个）：每个 Pod 的启动窗口块数 K_i，以及各候选节点上该 Pod 的窗口就绪块数 c_ij。
Nodes（N 个候选节点）：已通过粗筛（资源余量、数据可达、健康均满足）的节点列表。
就绪表 cij：节点 j 上 Pod i 的窗口已就绪块数，由 Agent 上报增量更新。
preheatFanout：每 Pod 需要预热的节点数上限，默认 2，最小 1。preheatFanoutMin：目标下限，默认 1，最小 1。单节点候选时实际认领 1 个。
Pod 间亲和字段：
AffinityGroup / AntiAffinityGroup：Pod 间必须同节点 / 不可同节点的分组标签；WarmupTask 的 spec.affinity 只登记策略，控制器本期不传这两个标签；
allowMultiPodPerNode：默认 false（一节点一 Pod），控制器本期不打开；true 时允许多 Pod 同节点。
###### 约束判定
本模块只处理两类约束，均来自输入字段：
亲和性约束：若 Pod i 与 Pod k 反亲和，则二者不可分配到同一节点；若必须亲和，则须同节点成组分配。
一节点一 Pod / 多 Pod：allowMultiPodPerNode=false 时每节点最多 1 个 Pod；true 时同节点可放多个 Pod，但须满足亲和性约束。GWAA 按该字段判断每个节点还能认领几个 Pod。
资源是否足够已在粗筛保证，模块内不再重复判断。

###### 算法流程
亲和组合并：将“必须同节点”的 Pod 合并为超 Pod，按超 Pod 的窗口集合与就绪表参与分配；分配后组内共享节点。
目标集合：每个 Pod 先算 S_min = ceil(K_i / 4)。最优节点的 c_ij 不超过 S_min 时判低信号，目标数量取可行节点数与上限中的小者；否则只保留 c_ij 不小于最优节点一半的节点，目标数量是这些节点的数目。目标数量再夹在 preheatFanoutMin 与 preheatFanout 之间、并按可行节点数封顶。目标下限高于目标数量时按 c_ij 顺序补到目标数量；下限高于可行节点数时目标数量取可行节点数。
在册保留：本轮进度查询报持有、代际与本轮相同的节点只要仍可行并满足保留线（低信号时恒满足，否则 c_ij 不小于最优节点一半），就留在目标集合里；集合满了就替换排名最低且不在册的那个节点，目标数量不变。
贪心认领：按各 Pod（或超 Pod）的最大 cij 降序处理，每个 Pod 只在目标集合内按 cij 从大到小认领，直到达到目标数量；节点放不下就顺延到集合内下一个节点。
冲突裁决：多个 Pod 争同一节点且无法全部容纳时，比较各 Pod 的 (cij − 次优 cik) 差值，差值大者（更依赖该节点）保留，其余让步到集合内尚未认领的次优节点；差值相同或 cij 相同由注入的随机源决定。
集合外兜底：目标集合内一个都认领不到时，允许在集合外再认领至多一个节点，并标记集合外兜底。
未分配标记：目标集合与集合外兜底都放不下、或没有任何可行节点的 Pod 标记为 unassigned。

###### 输出
`assignment[i]`：Pod i 实际认领的预热节点（节点名列表，按 cij 降序），数量不超过 preheatFanout，可低于 preheatFanoutMin 并置下限未满足标记。
`targetSet[i]`：Pod i 的目标集合，实际认领除集合外兜底那一个外都在其中。
preheatSet：全量 (Pod i, 节点 j) 配对集合，覆盖每个 Pod 的实际认领节点；未分配的 (Pod, 节点) 组合不预热。
unassignedPods：没有任何可行节点、或目标集合与兜底都放不下的 Pod 列表。
输出直接作为“哪个节点预热哪个 Pod 的窗口”的执行依据；最终落点由 Scheduler 在放行后的分数快照里选择，不在 GWAA 输出里。

###### 复杂度
亲和组合并：O(P)
贪心认领：O(P×N×K)
冲突裁决：最坏 O(P×N×K)，实际远小于此
总计 O(P×N×K)，P、N 为几十至几百量级，K 是每 Pod 的目标数量（上限默认 2、下限默认 1），毫秒级，每轮拿到进度后重算也够用

## Scheduler
实现`Score`与`NormalizeScore`拓展点
- 编写程序
使用Go语言写一个TrainCacheScore程序，实现ScorePlugin接口，核心方法就是Score()
在里面读取 Controller 放行时写在本 Pod 注解上的节点分数表，按节点名取分，做Normalization，并返回（返回的是一个0~100之间的整数）
- 写配置文件
在 KubeSchedulerConfiguration 的 profile 里启用插件，只挂到 score 扩展点：
```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
   - schedulerName: default-scheduler
     plugins:
        score:
           enabled:
              - name: TrainCacheScore
                weight: x  # 权重值，可根据实际需求调整
```
注意：`KubeSchedulerConfiguration` v1 没有 `normalizeScore` 配置字段（strict decoding 会拒绝）。只要插件实现了 `ScoreExtensions`，framework 会在 score 阶段后自动调用其 `NormalizeScore`，无需也不能在配置里单独启用。

## 接入真实DataLoader
接入真实 DataLoader 不是搭一个假训练循环，而是让真实 tar 分片、真实块语义、真实消费顺序贯穿到测量里。
DataLoader 按 Dataset 固化的 chunkIndex 与 WarmupTask 的初始消费计划组织 sampler，
每个 worker 的读取序列与预热序列对齐；epoch/shuffle/curriculum 通过钩子上报事件给 Agent，触发运行时重预取
存未命中走回源并在打点中区分。打点记录每 step 的 step_time 与 wait_time（并拆出本地命中等待与回源等待），按窗口/切换点/全程聚合。
负载均衡必须在这一步接入：多 worker 的块分配要均衡、worker 序列要与本节点预热对齐、切换后要重新均衡——否则 wait_time 反映的是分配不均和跨节点回源，而非预热收益，后续“启动收益 vs 全程收益”的归因就失效。

完整跑完提交一个DataSet + WarmupTask到选出节点再到持续预取/阶段切换重预取的全流程训练流程，能完整运行全流程逻辑

## 补充： 一条Pod的完整路径
1. 先建 DataSet（描述 bucket/prefix 的块），再建 WarmupTask（引用 DataSet、写 podCount、预热扇出）。
2. controller-manager 算候选节点，通过 gRPC 让各节点 agentd 去拉块，把每对 (Pod, 节点) 的就绪块数持续写进 status.readinessTable。
3. 训练负载创建 Pod，带 traincache.io/warmup: enabled 标签——这是 webhook 的 objectSelector 条件，命名空间里还要有一个 TargetRef 命中该 Pod 且 Ready 的 WarmupTask
4. API server 回调 webhook：它先从 batch.kubernetes.io/job-completion-index 标签取 Pod 序号，没有就取 Pod 名最后一段序号，校验该序号落在 podCount 内且有对应 PodDetail，然后注入 gate 与任务引用注解，Pod 落库，Pending，未调度。
5. 控制器先对每个 Pod 算分数并把分数注解与摘 gate 放进同一次 patch，再写 status；所有 Pod 都至少在一个预热节点上达到整数门槛，或超时、提前降级、前置跳过命中时才放行，gate 一没，调度器立刻看见它，按注解里的分数绑到热好的节点，kubelet 起容器。
webhook 负责给 Pod 加上调度门，控制器负责放行，调度器在放行之后才开始打分。 没有匹配的 WarmupTask 或 webhook 不可用，Pod 就被直接放过去，只是不享受预热保护。
