# TrainCache 启动与实验

## 1. 构建与导入镜像

控制面五个镜像用同一套 Dockerfile 构建，标签统一 `dev`：

```bash
./hack/build-images.sh     # manager webhook scheduler agent gateway
```

产物：

```text
ghcr.io/thewor1d877/traincache/controller-manager:dev
ghcr.io/thewor1d877/traincache/webhook:dev
ghcr.io/thewor1d877/traincache/kube-scheduler:dev
ghcr.io/thewor1d877/traincache/traincache-agentd:dev
ghcr.io/thewor1d877/traincache/traincache-gateway:dev
```

`kind-up` 不预载这五个镜像，逐个导入 4 个 worker：

```bash
for c in controller-manager webhook kube-scheduler traincache-agentd traincache-gateway; do
  kind load docker-image "ghcr.io/thewor1d877/traincache/$c:dev" --name traincache
done
```

`ctrl_up.sh` 启动前对每个镜像探 3 次、间隔 2s，任一次缺失就退出并打印上面两条命令。刚 `kind load` 完 containerd 元数据可能还没同步，探 3 次是为了不误报。

缺失之外还要查新旧。`hack/build-images.sh` 构建时把源码指纹（进镜像的 `*.go`、`go.mod`/`go.sum`/`go.work`、Dockerfile 的内容哈希）打在镜像标签 `io.traincache.src-fp` 上，`ctrl_up.sh` 拿它和当前工作树比：不一致或没有标签就退出，打印重建与导入命令。同一台机器上并行的会话会共用 `~/.kube/config`，`kind create cluster` 会把 current-context 切到新集群，所以 `ctrl_up.sh` 开头还断言 context 就是 `kind-traincache`，不是则退出并打印用独立 kubeconfig 的办法。两处放行的开关是 `TRAINCACHE_ALLOW_STALE_IMAGE=1`（只在复现历史产物时用）与 `TRAINCACHE_ALLOW_CONTEXT_MISMATCH=1`。

## 2. 拉起装置

首次或换机器：

```bash
cd bench
make bench-up
```

依次执行 `kind-up`（5 节点集群）→ `k8s-up`（MinIO 带 30Gi PVC）→ `data-up`（四轨数据）→ `track-d-data` → `upload`（B 轨灌 MinIO）→ `ctrl-up`（控制面与 agentd）→ `tc-up`（默认 100mbit / 20ms）→ `bench-verify`（两轮冷读相对差 ≤10%）。首次约 1 小时，主要花在造数；已存在的步骤自动跳过。

`ctrl-up` 的保证：

- 清单内容哈希记在命名空间注解 `traincache.io/deploy-hash`。哈希未变且五个工作负载（manager、webhook、scheduler、agentd、gateway）都在时不 apply，连续两次 `make ctrl-up` 不滚动重启。
- context 必须是 `kind-traincache`（kubeconfig 里有这个 context 时才断言）；并行会话建自己的 kind 集群会把 current-context 切走，切走时直接退出。
- 五个控制面镜像的 `io.traincache.src-fp` 标签必须等于当前工作树的源码指纹；标签是 `:dev`、节点上已有同名镜像时 `imagePullPolicy: IfNotPresent` 不会重新拉取，旧二进制会被静默复用，读到的就是已经修掉的缺陷。
- webhook TLS Secret 缺失时自签生成，并把 CA 写进 MutatingWebhookConfiguration `traincache-pod-warmup` 的 caBundle。
- 凭证 Secret `traincache-objstore` 用 `config.py` 的 MinIO 凭证创建，已存在则跳过。
- worker 缺 `traincache.io/s3-access=true` 时自动补标签。
- 白名单、桶、缓存上限、自动 K 的两个输入、本轮的预取提前量与淘汰策略，再加网关端点 `gatewayEndpoint`（`TRAINCACHE_GATEWAY=1` 写 `traincache-gateway.traincache.svc:9413`，关网关写空串）共八项都写在 `traincache-config`，任一现值与期望不符就整体 merge patch 并滚动重启 agentd；DaemonSet 只留 `configMapKeyRef` 引用，改桶不再用 `kubectl set env` 动工作负载。这八项在 `apply -k` 之后才写：apply 会把整份 `data` 盖回清单默认，先写就会被抹掉。
跑分期间不执行 `bench-up` 或 `ctrl-up`。清单哈希一变就 apply，agentd 滚动重启，正在跑的任务中断。

`make bench-status` 只读打印集群、节点、MinIO、tc qdisc、数据目录与最近产物；`make bench-doctor` 逐项回报 PASS/FAIL/WARN。

## 3. traincache 组

```bash
cd bench
make -C compare compare-up GROUP=traincache-cold
make -C compare compare-up GROUP=traincache-warm
```

`up.sh` 四步，顺序固定，全部幂等：

| 步 | 动作 | 出问题先查 |
|---|---|---|
| 1 | 给所有 worker 打 `traincache.io/s3-access=true`，节点数动态枚举 | NoAccessibleNodes |
| 2 | `trainpublish -chunk-size 8388608` 把 `track_b/tars/shard-*.tar` 切成 8MiB 块，上传成 `bench-b/dataset/compare-data-8m/`；空桶首次发布同时写 `bench-b/_traincache/format.json`；`CURRENT` 已存在就跳过 | DataSet SnapshotNotFound |
| 3 | 起控制面：与 `bench-up` 共用 `ctrl_up.sh`，清单哈希变化或工作负载缺失才 apply | ImagePullBackOff |
| 4 | 写 `traincache-config`：`datasetMetricsWhitelist=compare-data-8m`、`objstoreBucket=bench-b`、`cacheCapacityBytes=1GiB`、`startupWindowBytes=512MiB`、`maxFillFraction=0.125`，再加本轮的 `prefetchLookahead`、`evictPolicy`（无 env 时取清单默认 16、heat）与 `gatewayEndpoint`（开关见 §3.1，未开关注空串），八项一次 merge patch；Controller 读中间三项算自动 K；建 DataSet 与 WarmupTask；最后挂 tc | preheat 全失败、缓存不生效、扫点参数没进 agentd |
cold 与 warm 只差 `TRAINCACHE_WARMUP_K`：warm 写 128（8MiB × 128 = 1GiB 前缀，fanout=2 时总传输 2GiB），cold 写 0。0 是 bench 哨兵，不写进 CRD，创建前跳过 WarmupTask，也不打 gate 标签，测量 Pod 普通调度。

预热 15 分钟硬超时，超时整轮作废。warm 组等 WarmupTask 进入 Released（gate 放行）才创建测量 Pod，预热时长单独记 `warmup_seconds`。

### 3.1 网关开关（有网关 / 无网关）

`TRAINCACHE_GATEWAY` 是装置级总开关，只影响 traincache 组：direct/juicefs/fluid 三组不读网关，行为与产物不变。

| 取值 | `traincache-config` 的 `gatewayEndpoint` | `deployment/traincache-gateway` | agentd |
|---|---|---|---|
| `1` | `traincache-gateway.traincache.svc:9413` | 副本 1，等 rollout 就绪 | `gatewayEndpoint` 变化才滚动重启 |
| 未设置 / `0` | 空串，块 GET 直连源站 | 副本 0（对象保留，不删 Deployment） | 只在 `gatewayEndpoint` 真的变化时重启 |

```bash
cd bench
TRAINCACHE_GATEWAY=1 make ctrl-up                      # 拉起网关，并把 agentd 切过去
TRAINCACHE_GATEWAY=1 python3 compare/run_bench.py ...  # 跑分：开关透传给 traincache/up.sh
```

- 开关只切副本数与 ConfigMap 键；两条分支各自幂等，连续两次执行同一分支不会滚动重启 agentd。
- `run_bench.py` 把开关透传给 `traincache/up.sh`，并给每行 `summary.csv` 落 `gateway` 列（`1`/`0`，紧随 `gate_mode`）。
- `bench/compare/summarize.py` 把 `gateway=1` 的行的格子名改成 `S-100+gw`，与无网关的同名格子分开统计；`+gw` 表示该格经合并回源网关。
- 合并效果看网关 Pod 的 60s 汇总日志（`msg="gateway: 60s 汇总"`）：`merged/gets` 是合并命中率，`owners` 是真实回源次数；不为它另建指标端点。
- 有网关与无网关必须分目录或分 `TAG` 跑，不能让两种装置状态的数据落在同一产物目录。4.4 的七个实验族全部在关网关下跑，网关不是任何一张图的自变量。

## 4. 新版本自跑

发布新版本、只验 TrainCache 自身，不重跑对照：

```bash
cd bench
make bench-quick TIER=S RATE=1000 REPS=3
```

只跑 `traincache-cold` 与 `traincache-warm`。`TIER` 只能是 S：M/L 档的参跑组不含 warm，凑不齐冷热两阶段。`RATE` 取 100 / 300 / 1000，`REPS` 取 3，`TAG=...` 给 run_id 加后缀。

产物落 `~/tcd/bench/results/quick/<run_id>/`，含 `summary.csv`、`run.json`、`lock.json`；存在上一次 quick 产物时另出 `vs_last.md`，对比两次的启动与全程 makespan、stall 占比、字节成本。

## 5. 实验族

七个实验族。族的 ID 是 `--family`/`--point` 的寻址名，产物落数据层的哪个分区由 `bench/exp.py` 的 `results_root()` 给出，图与判据的口径在 [4.4 实验协议](<4.4-experiment-protocol.md>)：

| 族 | 测什么 | 点数 | 每点次数 | 产物分区 | 4.4 章节 |
|---|---|---|---|---|---|
| compare-groups | TrainCache 与 direct/juicefs/fluid 同台跑分（对照行取只读的 `baselines/`，exp.py 只跑 TrainCache 组） | 5 格（S-100、S-300、S-1000、M-1000、L-1000） | S/M 3 次，L 1 次 | `scores/<格名>/` | §1.9 假设、§1.10 跑法 |
| startup-surface | 启动 makespan 随带宽、缓存比、fanout、门控变化 | 54（3 带宽 × 3 比 × 3 fanout × 2 门控） | 1 | `figures/fig1-*/` | §2 |
| total-makespan | 全程 makespan 随带宽与 epoch 数变化 | 9（3 带宽 × epoch 1/3/6） | 1 | `figures/fig2-*/` | §3 |
| switch-recovery | 阶段切换后的 stall 回落 | 9（fixed / per-epoch / curriculum × epoch 1/3/6） | 1 | `figures/fig3-*/` | §4 |
| pareto-startup | fanout 与门控的启动权衡 | 6（3 fanout × 2 门控） | 7 | `figures/pareto1-*/` | §5.1 |
| pareto-sustained | 预取窗口三档的淘汰与预取权衡（倾斜负载） | 3（lookahead 8/16/32） | 2 | `policy/pareto2-*/<run>/` | §5.2 |
| evict-policy | heat / lru / lfu 在倾斜负载下的挤占 | 3 | 1 | `policy/policy-*/<run>/` | §5.3 |

统一入口：

```bash
python3 bench/exp.py status                              # 各族完成度与产物分区
python3 bench/exp.py run startup-surface --dry-run      # 只打印将执行的命令
python3 bench/exp.py run total-makespan                 # 跑一族，已完成的点跳过
python3 bench/exp.py run all                            # 七族串行
python3 bench/exp.py run evict-policy --point lru      # 只跑一个点
python3 bench/exp.py record evict-policy                # 只按产物回填版本表，不跑
```

点名是 COND 名去掉族前缀，例如 `fig1-100-ratio2-fan2-gated` 在 `--point` 里写 `100-ratio2-fan2-gated`；`exp.py` 按 `FAMILY_COND_PREFIX` 把点名加回前缀当目录名，所以产物落在 `results/figures/fig1-100-ratio2-fan2-gated/`，和 `make bench COND=fig1-100-ratio2-fan2-gated` 手工复跑写的是同一个目录。倾斜两族（`pareto-sustained`/`evict-policy`）每个 rep 独占一个 run 目录 `results/policy/<COND 名>/<run ID>/`，产物不并成一份 `summary.csv`。

启动器只写 [4.6 实验版本记录](<4.6-experiment-version-log.md>)的最后一行。开跑前在表里新起一行，第一格写版本号，其余格留空。exp.py 跑完一族后回填该行对应的格：整族完成写产物路径，没完成写 `未完成`。没有版本行时 exp.py 报错退出，不自己加行。

每族的点产物目录里写一个 `version` 文件，记录产出它的版本。启动器按行数加版本判断完成：同版本跳过已完成的点，版本不同就重跑；`--force` 不管版本强制重跑。

同一时刻只允许一个 exp.py 实例，锁文件 `/tmp/traincache-exp.lock`。长跑脱离会话：

```bash
cd bench
nohup python3 exp.py run all \
  > ~/tcd/bench/logs/exp-$(date +%Y%m%dT%H%M).log 2>&1 &
```

进度：

```bash
find ~/tcd/bench/results/figures -name summary.csv | wc -l
tail -f ~/tcd/bench/logs/exp-*.log
kubectl get pods -A -l app=train-job -o wide
kubectl -n traincache get warmuptask
```

单点手工复跑只在排障时用，走同一个底层执行体：

```bash
cd bench
CAPACITY_RATIO=S DATASET_NAME=compare-data-8m python3 compare/run_bench.py \
  --tier S --rate 100mbit --reps 3 --groups traincache-cold \
  --out scores/S-100/summary.csv
```

`run_bench.py` 写 `--out` 时先读回既有行，按 `(group, rep)` 合并：本次有效行顶掉同样本点的旧有效行，其余历史行原样保留，作废行只追加。中断后重跑同一条命令即可续做。

## 6. 冒烟判据

装置改动后先跑受影响组的冒烟，再谈正式实验。低负载口径 `N_TARS=2 EPOCHS=1 STEPS_PER_EPOCH=4`。

```bash
cd bench
CAPACITY_RATIO=S DATASET_NAME=compare-data-8m \
python3 compare/run_bench.py --reps 1 --groups traincache-cold \
  --out quick/smoke-traincache.csv
```

| 组 | 通过判据 |
|---|---|
| traincache-cold | `TRAINCACHE_WARMUP_K=0`：不建 WarmupTask、不打 gate 标签，测量 Pod 普通调度，任务正常跑完 |
| traincache-warm | k=128：预热完成，gate 放行；agentd 命中指标非零；落点节点的 blocks 目录有数据 |

两组共判：`kubectl get events` 无 ImagePullBackOff 与 CrashLoop；产物含 run ID，能关联到 COND。

## 7. 排障

| 现象 | 根因 | 处理 |
|---|---|---|
| 测量 Pod 长时间 Pending | warm 组的 gate 卡在预热未完成 | `kubectl -n traincache get warmuptask`；超 15 分钟整轮作废 |
| 预热全部失败 | agentd 的桶与 DataSet 的桶不一致 | 跑 `ctrl_up.sh` 的 `ensure_agent_config`；桶名以 `spec.bucket` 为准 |
| 命中率全 0、预热看着成功 | `datasetMetricsWhitelist` 没写新数据集名，指标全归并到 `other` | 同步 `traincache-config` 白名单 |
| 行里 `agent_degraded_max=1` 且 `void=True` | 测量期间某个 agentd 降级 | run_bench 每 5s 采一次 `traincache_agent_degraded`，出现 1 就作废该轮，查 agentd 日志 |
| 行里 `reason=evict_not_engaged` | 目录峰值超容量而 `evict_blocks_run=0`：淘汰闸门没生效，多数是 `cacheCapacityBytes` 没进到 agentd 进程，其次是对照容量字节累计的修复还没进镜像 | `kubectl -n traincache exec <agentd Pod> -- printenv TRAINCACHE_CACHE_CAPACITY_BYTES` 对本次 COND 的 `cache.capacity_bytes`；一致就查 `ctrl_up.sh` 打印的镜像源码指纹是否等于当前工作树。配置不符则补 `traincache-config` 后重启 agentd，镜像不符则重建导入，再重跑该点（判据见 4.4 §1.7） |
| 改了 Go 代码但读数没变，或读数是已修缺陷的表现 | 节点上还是上一次构建的 `:dev` 镜像，`IfNotPresent` 不重新拉取 | `ctrl_up.sh` 的源码指纹门禁会退出；重建 `./hack/build-images.sh` 后逐个 `kind load`，再滚动重启工作负载 |
| 扫点各点读数几乎一样、或 `evictPolicy` 看着没换 | `apply -k` 把 `traincache-config` 整份 `data` 盖回清单默认（16、heat），起组前写的本轮值消失 | `ctrl_up.sh` 的 `ensure_agent_config` 在 apply 之后按 `TRAINCACHE_PREFETCH_LOOKAHEAD`/`TRAINCACHE_EVICT_POLICY` 再对齐；`make bench-doctor` 的 ConfigMap 与容器 env 两条断言会把它判成 FAIL |
| `agentd` 起不来、残留 `tmp-*` | 上一轮清缓存时 agentd 还在写块 | 按 `run_bench.py` 的顺序复位：先摘 Pod，再清目录，最后拉起并等 fetch 计数不增长 |
| 换块大小后预热块数不对 | `k` 是按 8MiB 写的 | 按「字节量 ÷ chunk-size」重算，重发快照 |

镜像、快照、节点标签、sudo、python 环境这几类与组态无关，见 [4.1 bench装置与禁令](<4.1-bench-setup-and-rules.md>)第 6 节。

## 8. 汇总与出图

分析层依赖装在项目根 `.venv`：

```bash
.venv/bin/pip install -r bench/requirements.txt
.venv/bin/python bench/experiments/collect.py    # 逐 run 汇总 metrics.csv
.venv/bin/python bench/compare/summarize.py      # 七组对照的正式表与胜负判定
.venv/bin/python bench/experiments/plot.py       # 九张图（零参自动扫描数据层）
```

`collect.py` 出 makespan 两边界、三笔字节成本、分阶段命中率；`stats.py` 给 bootstrap 95% 置信区间；`summarize.py` 读 `scores/` + `baselines/`，正式表与判定落 `results/summary/`（`baseline.md`、`verdict.csv`），不在格目录里。

`plot.py` 零参时扫 `~/tcd/bench/results/` 下所有含 `summary.csv` 的目录，按一级分区分流：`scores/`+`baselines/` 出七组态对照图，`figures/`（点目录名带 `fig1-`…`pareto1-` 前缀）与 `policy/pareto2-*` 出各族的收益图。图片统一落 `results/figures/`，图上用到的聚合值同目录 `data/` 下逐图一份 CSV：

| 图件 | 来自哪一族 | 画的是什么 |
|---|---|---|
| `compare_startup_v0.4.0.png`、`compare_total_v0.4.0.png`、`compare_stall_v0.4.0.png` | compare-groups | 七组态的启动/全程 makespan 与 stall 占比三张横向条形图，按格子（S-100…L-1000）分面，柱长越短越好 |
| `fig1_startup_surface_v0.4.0.png` | startup-surface | 启动 makespan 的门控盈亏：按 fanout 分三面，每行一个带宽 × 容量比，一根发散柱表示相对自由调度的变化（%），右蓝=门控更快、左橙=门控更慢 |
