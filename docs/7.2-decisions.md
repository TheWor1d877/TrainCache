# Controller & Scheduler decisions

## D4 块模型

结论：`spec.chunkSize int64` 字节加 `spec.shards[]{name,count,lastChunkSize}`；`totalChunks=Σcount`；全局块号按 spec 顺序累计，固化在 `status.blockLayout[].startChunk`。

原因：备选 `resource.Quantity` 每次计算都要解析，agent 与 core 全用 int64，避免引入第二套单位。

## D5 readinessTable 语义

结论：status 存 `[][]int32` 计数（窗口内就绪块数），比例一律现算 `rate=ready/K_i`；门控用整数判据 `required=floor(threshold*K_i)`，`rate` 只用于观测与展示。

原因：计数无损、可审计；比例随 K 变化不宜持久化，浮点 rate 不适合作放行裁决。

## D8 Pod 关联

结论：`spec.targetRef{apiVersion,kind,name,podLabelSelector}` 与 `PodDetail.Index`；Index 必须为 `0..PodCount-1` 连续；Pod 通过 ordinal 映射到 PodDetail。

原因：没有稳定的 Pod 与序号映射，readiness 无法按 Pod 归属。

## D9 Gate 注入

结论：新增 MutatingWebhook，匹配 `objectSelector: traincache.io/warmup=enabled`；注入固定 gate `traincache.io/warmup` 与 annotation `traincache.io/warmup-task`、`traincache.io/pod-index`；`failurePolicy: Ignore`。

原因：SchedulingGate 只能在创建时加入、事后只能摘；备选由用户模板自带 gate 把配置负担外推且易错。Ignore 的代价是静默降级，由 `GateInjectionDegraded` 条件兜底，换取 webhook 故障不阻塞训练。

## D10 Pod 序号推导

结论：优先 label `batch.kubernetes.io/job-completion-index`，其次 StatefulSet ordinal（Pod 名最后一段），都失败不注入并记事件 `WarmupTaskMappingFailed`。

原因：序号须由 webhook 独立、确定地算出；控制器回填会与创建竞争。

## D11 Agent 契约

结论：扩展 `traincache.agent.v1.PreheatService`：进度复用 `GetPreheatStatus`，`PreheatStatus` 追加 `generation=12`、`seq=13`、`ready_bitmap=14`、`canceled=15`，`SubmitPreheatRequest` 追加 `generation=8`；新增 `UpdatePreheat` 与 `CancelPreheat` 两个动作 RPC，不新增进度查询 RPC；位序等于请求 `chunks` 顺序，控制面一律显式传 `chunks`；`ReportBlocks` 保持 Unimplemented，保留占位不实现，理由见 Agent 侧 D67。

原因：备选新建 controlplane proto（双契约维护成本）、Agent 推送（需反向连接与服务发现）；拉取模型与现有 RPC 方向一致，状态查询已携带位图进度。

## D12 幂等与陈旧

结论：`task_id="<namespace>/<name>/p<index>"`；`generation=metadata.generation`；Agent 对低 generation 返回 `FailedPrecondition`；`UpdatePreheat` 全量替换 `chunks` 并重定义位序，`seq` 单调递增；`CancelPreheat` 仅标记、不保证停止在途 P0；Cancel 后同 generation 再 Submit 视为新任务。

原因：重复 reconcile、重启、乱序响应是常态；generation 单调性是唯一裁决依据，seq 解决同代际内位图新鲜度。

## D13 门控参数位置

结论：`spec.gate{threshold,gapMin,slopeMin,tMax,minInterval}` 与 `spec.score{halfLife,cutoff}`；示例默认 `threshold=0.9`、`gapMin=0.1`（比例）、`slopeMin=0`（比例/秒）、`tMax=10m`、`minInterval=10s`、`halfLife=2·K_i`、`cutoff=8·K_i`；没有 `window` 字段，K 是每 Pod 的 `K_i`。

原因：参数须可声明、可回滚，默认值只是示例，生产由用户覆盖；gapMin 与 slopeMin 单位显式化避免与块数混淆。

## D15 条件②采样

结论：`FirstReadyAt` 取首次出现任一 Pod 达标的时间，写入 `Condition FirstReady`；每个未达标 Pod 需两个间隔不小于 `minInterval` 的样本才计算 slope，样本不足视为不满足。条件②是边际收益判据：等待价值随 gap 增大、slope 降低而下降，`gap>gapMin && slope<slopeMin` 时提前放行（Released）；条件③ `tMax` 是绝对上限。

原因：首次达标的起点必须固定，避免交错达标反复重置；采样不足不误放行；②③分工，不把超时当收益判据。

## D18 缺分行为

结论：Scheduler 在 Pod 分数注解缺失、节点缺项、JSON 损坏、`task` 不匹配、超 TTL 时返回 0 且 `Status` 为 nil。

原因：备选返回 Unschedulable 会让 controller 故障演变为集群不可调度；返回 0 只影响落点偏好，读路径仍可回源。

## D19 分数公式

结论：`w(i)=1`（`i < min(K_i, C)`）、`0.5^((i-K_i)/H)`（`K_i <= i < C`）、`0`（`i >= C`）；`S=round(100*Σw·ready/Σw)`，`Σw=0` 时取 0；NormalizeScore 按最大分缩放至 100。

原因：0~100 与 NormalizeScore 约定一致；整数便于注解存储；`K_i` 是每 Pod 的启动窗口，窗口内权重取满、窗口外按半衰期衰减。

## D22 core 复用边界

结论：只读复用 `core/objectstore` 与 `core/index` 的导出符号；不新增 core 接口、不改 core 代码。

原因：快照与键布局已有唯一实现，重复实现会产生第二套事实。

## D23 选主

结论：`CONTROLLER_LEADER_ELECTION` 默认 `false`，生产建议开启；webhook 是独立进程，不参与选主。

原因：单副本开发简单；多副本时两个控制器同时下发会造成重复 RPC，幂等能兜底但浪费带宽。

## D25 K 单一窗口

结论：启动窗口与评分窗口统一为每 Pod 的 `K_i`（`PodDetail.K`）；删除 `ScorePolicy.Window`；门控与全局衰减评分都只用 `K_i`。

原因：双窗口的配置面与解释成本高；单窗口让"能否放行"和"落点偏好"共用同一事实。

## D26 整数门控与 required 的 0/1 钳制

结论：`required=floor(threshold*K_i)`；`threshold>0` 且结果为 0 时取 1；放行判据是 `ready>=required`。示例 K=8、threshold=0.8 时 required=6；浮点 `rate` 只用于观测。

原因：浮点比较受精度与采样抖动影响；整数门槛可审计、可复现；0 取 1 避免小窗口因向下取整永远无法放行。

## D29 默认消费顺序切分

结论：删除 `consumeOrderRef`；任一 Pod 的消费清单缺失或非法时忽略全部用户值，统一按 `[floor(i*T/P), floor((i+1)*T/P))` 升序切分，要求 `T>=P`；记事件 `ConsumeOrderDefaulted`，`status.consumeOrderSource=Default`。

原因：悬空引用无法解析且无生产者；确定性切分可测、无需额外对象；`T<P` 无合法切分，显式拒绝而非静默生成空窗口。

## D30 可达性标签人工维护

结论：`traincache.io/s3-access=true` 由人工维护，任何组件不得写入；`DataSet.spec.accessibleNodeSelector` 可选，未设置时默认等价于 `traincache.io/s3-access=true` 选择器。

原因：标签要求人为维护，selector 只作可选收窄；默认值让最小清单免配置，同时保留多数据集差异化能力。

## D31 固定 Pod 集与不可变字段

结论：不开 scale；`spec.podCount` 与 `spec.dataSetRef` 创建后不可变（CRD CEL `self == oldSelf`，webhook 兜底）；Controller 不创建与管理 Job、Pod，只通过 gate 与 status 协作。

原因：扩容会改变 P×N 表与窗口映射，v1 不支持；Pod 生命周期归训练侧，越权会引入竞态。

## D32 GWAA 贪心近似与随机并列

结论：GWAA 按 `c_ij` 贪心分配，属近似解；并列时随机选择，随机源由参数注入，固定种子可复现；WarmupTask 的注入种子按"任务 UID 加 generation"派生，同一代内每轮重算取同一序列，代际变化才重掷；不追求全局最优。

原因：精确分配是组合优化，P×N 规模下无必要；随机并列避免字典序裁决带来的系统性偏置，注入随机源保留可测试性。种子按代际固定，是因为冷启动时整张 `ReadinessTable` 全为 0、每个 `c_ij` 都并列，逐轮重掷会让目标集合反复翻转，每轮把上一轮刚提交的配对按 `target_shrink` 撤销，预热进度归零直到 `t_max` 降级。

## D33 GWAA 冲突裁决是否允许共享

结论：默认保留差值裁决，`c_ij - secondBest_i` 大者保留、其余让步。共享最优节点只是未启用的可选分支：仅当 `allowMultiPodPerNode=true`、无亲和冲突、粗容量允许，且 `|W_B \ W_A| < c_ij - c_ik` 时才允许次优 Pod 共享；前置条件是补 `count × maxPod` 粗资源记账，v1 不装箱。`allowMultiPodPerNode=false` 时共享违反用户声明的放置约束，不可作为默认行为。

原因：共享的真实代价是同节点多预热一个窗口（窗口重叠时便宜，不重叠接近双倍 IO）加资源争用；次优节点通常已预热，搬迁的补预热多为沉没成本；若次优节点差很多，搬迁代价才可能大于共享。

## D34 Controller 下发预热时的快照标识

结论：`SubmitPreheatRequest.snapshot_id` 恒为空字符串；Controller 不下发 `DataSet.status.snapshotID` 解析出的具体快照 ID，`Update` 路径同理。Agent 侧对非空值返回 `InvalidArgument`。

原因：Agent 经 `Catalog` 自行跟随 CURRENT、按前缀加载 manifest 分片；下发具体 ID 会把任务键 `(dataset,snapshot_id)` 钉在某一代，快照推进后位图失去意义，也可能指向 Agent 未加载的快照而令预热被永久拒绝。

## D35 指标标签口径

结论：全部指标只用有界标签：`controller`（3 值）、`result`（固定枚举）、`op`（3 值）、`state`（3 值）、`dataset`（值取 `<namespace>/<name>`，避免跨命名空间碰撞）。不设按任务、Pod、节点展开的 ready 明细与门控序列 family，门控状态用有界计数的 `gate_tasks{state}` 观测；family 清单共 11 项。

原因：无界身份标签无法聚合与告警；`err.Error()`、Pod 名、Node 名、task 名、UID 禁止进标签。

## D36 WarmupTask status 明细粒度

结论：候选节点粒度的就绪块数只由 `ReadinessTable`（P×N）承载；`PodNodeReadiness` 明细只记判定所需的预热节点配对，条数是实际 `Assignment` 数，门控、评分与落点判定只读这些配对。

原因：P=64、N=256 时"每 Pod 乘每候选节点一条"的明细为 4.18 MiB，超过 1 MiB 上限与 etcd 请求上限；收窄后 61,589 B 且不丢判定信息。上限是 P≤64、N≤256，超限拒绝。

## D37 取消 DataSet 到 WarmupTask 的反向引用

结论：删除 `DataSetStatus.WarmupTasks`；保留 `WarmupTaskSpec.DataSetRef` 单向引用；不设 OwnerReference、不建互相 watch。

原因：该字段全仓无写入点且无 namespace 与 UID，属无使用者的字段；一旦回写而任务侧又 watch DataSet，会形成 reconcile 回环。

## D38 预热分配 fanout

结论：`spec.preheatFanout` 声明每个 Pod 的预热节点数量上限，最小 1，0 与负数由 CRD 拒绝；GWAA 按各 Pod 最大 `c_ij` 降序贪心认领 top-K 可行节点；节点能放几个 Pod 由 `allowMultiPodPerNode` 与亲和字段声明；跨 Pod 争同一节点按 `(c_ij − 次优 c_ik)` 差值裁决，差值大者保留、其余让步到次优可行节点；GWAA 不决定最终落点，落点由 Scheduler 在放行后的分数快照中从该 Pod 的暖节点里选出；门控条件①用存在量词：预热节点中至少一个 `Ready ≥ floor(阈值 × K_i)` 即该 Pod 达标，全部 Pod 达标才放行，条件②③不变；放行时对全部预热节点写分数快照，沿用衰减加权公式，分数写在训练 Pod 注解上；`PodNodeReadiness` 每 Pod K 条（P×K 有界），候选粒度仍由 `ReadinessTable` 承载；预热节点数量按下限加上限执行，下限由 `spec.preheatFanoutMin` 声明；代价是预热 IO 与缓存占用最多 K 倍，窗口重叠时更低。

原因：单节点预热下条件①的存在量词没有实际意义；放行时每行只有一个非零值，`NormalizeScore` 把唯一非零节点归一到 100，其余节点为 0，衰减分数不参与节点比较，落点实际被单一节点定死；唯一预热节点被高优先级任务抢占后其余节点全 0 分，Pod 落到冷节点回源，预热收益归零。有界 fanout 用成本换调度鲁棒性；`fanout=1` 时行为与单节点预热一致，可平滑迁移。

## D39 fanout 上限、下限与自适应目标数量

结论：`spec.preheatFanout` 只作上限（最小 1），新增 `spec.preheatFanoutMin` 作目标下限（默认 1、最小 1、必须不大于 `preheatFanout`）。GWAA 对每个分配单元按块数计算目标数量：`S_min=ceil(0.25×K_i)` 判低信号；保留线 `c_ij >= 0.5×best` 定 band；`target=clamp(band, minFanout, maxFanout)` 再按可行节点数封顶；`minFanout > band` 置 `ForcedByMin` 强制补位；`minFanout > 可行节点数` 计划阶段置 `MinUnmet` 且 `target=可行节点数`。亲和合并单元 `unitMin=max(成员 min)`、`unitMax=min(成员 max)`，`unitMin > unitMax` 返回冲突错误，目标集合成员共享。输出新增 `TargetSet` 与 `Decisions`（`TargetFanout/LowSignal/ForcedByMin/MinUnmet/FallbackOutOfTarget`）；除集合外兜底 1 个外 `Assignment ⊆ TargetSet`，冲突裁决与补齐只在集合内进行；集合内放不下时集合外兜底 1 个并置 `FallbackOutOfTarget=true`，兜底始终最多 1 个；无任何可行节点才 unassigned；`PreheatSet` 覆盖实际 `Assignment`。`MinUnmet` 的最终定义：冲突裁决、top-up、集合外兜底全部结束后 `len(Assignment[pod]) < 归一后的 min`，输入 0 按 1 处理。status 条数等于实际 `Assignment`，正常在 `[min,max]`，可低于 min（`MinUnmet=true`），任何情况不超过 max；无可行节点写一条空 `NodeName` 汇总。门控条件①仍为存在量词，集合大小以实际 Assignment 为准；放行分数快照只覆盖实际 `Assignment` 的 P×actual 配对。日志新增 `fanout_min/fanout_max/fanout_target/fanout_actual/low_signal/forced_by_min/min_unmet/fallback_out_of_target/prune_reason`；`pods_per_node` 按实际配对计数。下限只是目标：冲突、容量与兜底都可能让实际认领更少。

原因：固定数量在缓存分布集中时多预热无收益节点，分布均匀时又缺区分度；0.25 作低信号下限、0.5 作保留线，让目标数量随分布伸缩——集中时只留最优节点，分散时保留多个暖备份；下限由用户显式声明，避免"算法认为 1 个就够"破坏调度鲁棒性；`TargetSet` 与 `Assignment` 分离使"允许预热范围"与"实际下发范围"可分别观测与裁剪。代价：低信号时目标取到上限，预热 IO 与缓存占用最多升到 max 倍，下限强制补位也增加成本；复杂度仍是 O(P×N×max)。

## D40 PodNodeReadiness 补齐 MinUnmet

结论：`PodNodeReadiness` 追加 `MinUnmet bool`（JSON tag `minUnmet,omitempty`，字段末尾），与 `gwaa.PodDecision.MinUnmet` 同步；Poll 构造条目时直接取该 Pod 的 `PodDecision.MinUnmet`（GWAA 规划结果，轮询不重算），同一 Pod 各条同值；`StartupWindowReady` 同时补注释，语义是窗口内就绪块数的原始计数。

原因：下限未满足事实原先只记在 `PodDecision`，status 明细层没有对应字段，Controller 重启后无法从旧 status 还原哪些 Pod 没分到足够预热节点。

## D41 StartupWindowReady 字段保留理由与语义

结论：`PodNodeReadiness.StartupWindowReady int32` 保留，定义为"窗口内就绪块数的原始计数"；当前实现中与 `ReadyInWindow` 由同一次就绪度计算赋值、值相同。语义分工：`ReadyInWindow` 是门控条件①判定读取的中间结果，`StartupWindowReady` 是 status 中给人直接读的窗口就绪快照，也是 `StartupWindowReadyRate` 的分子。字段与类型、JSON tag 均不变。

原因：门控口径若调整（例如 `ReadyInWindow` 改加权计数），`StartupWindowReady` 保持原始计数语义；实现层约束是两字段必须由同一次计算赋值，不得各用一种口径。

## D42 preheatFanout 默认值

结论：`spec.preheatFanout` 的 CRD 默认值是 2，最小值 1；`spec.preheatFanoutMin` 默认 1。`preheatFanout` 仍只是上限，单节点候选时实际 `Assignment` 为 1，`MinUnmet` 按归一后的 min（输入 0 视为 1）比较，所以单节点不触发 `MinUnmet`。需要严格单节点行为的用户显式写 `preheatFanout: 1`。

原因：默认 1 让暖备份语义在"不写字段"的默认用法下事实上失效——多数集群的候选节点数不止一个，用户不写 `preheatFanout` 就退回单节点预热，被抢占后仍会落到冷节点。默认 2 让双节点及以上的默认用法直接拿到一个暖备份；单节点集群的实际分配不变。

## D43 K 自动计算与文件级消费清单

结论：`PodDetail.K` 可选，CRD 下限 0，0 表示省略；省略时由 Controller 按 `K_i = clamp(min(W_i, K_window, K_cache), 1, W_i)` 计算并 patch 回 `spec.podDetails[].k`，立即 `Requeue`，发 Normal 事件 `KDefaulted`（日志 `startup window K defaulted`），其中 `K_window=ceil(startupWindowBytes/chunkSize)`、`K_cache=floor(cacheCapacityBytes×maxFillFraction/(podCount×chunkSize))`，`startupWindowBytes` 默认 536870912、`maxFillFraction` 默认 0.125、`cacheCapacityBytes` 默认 0。显式 K 的有效范围是 `1..W_i`，`K > W_i` 置 `Condition InvalidSpec=False` 拒绝，不截断、不钳制；全部 Pod 实际请求块数合计超过 `cacheCapacityBytes × maxFillFraction` 只发 Warning 事件 `KExceedsFillLimit`，任务照常执行。`PodDetail.InitialConsumeFiles []string` 填 tar 分片名，全部 Pod 合起来必须恰好覆盖全部分片且每个分片只出现一次；不满足时整组回退默认均分，置 `status.consumeOrderSource=Default` 并发 `ConsumeOrderDefaulted`；`totalChunks < podCount` 置 `Condition InvalidSpec=False` 拒绝，不回退。预热请求块数是 `min(max(K_i, score.cutoff), W_i)`，超过消费顺序长度时截断。

原因：用户按"启动阶段读多少字节"配置窗口，不自己换算块数；清单以分片为单位，与 `traincache ls` 看到的文件对齐，用户不需要知道全局块号。`min` 保证窗口不超过该 Pod 实际分到的数据，也不超过按 podCount 均摊的缓存预算；下界取 1 避免算出的 0 被误读成"省略"。`maxFillFraction=0.125` 让自动 K 下的多 Pod 预热不填满节点缓存。显式 K 超过 `W_i` 无法落到真实块上，只能拒绝；超过缓存预算仍可执行，但多出的块要回源。

## D44 放行快照终态冻结

结论：`gateDecision` 随 status 落库后，该 `(任务 UID, generation)` 的分配即冻结：不再重算 GWAA、不再发 `Submit`/`Update`/`Cancel`、不再重写 Pod 分数注解，`status.podNodeReadiness` 的配对就是放行快照。冻结判定记在进程内 `pollTracker` 的"任务 UID 到已提交终态的最高 generation"表里，与 status 缓存副本无关；`isTerminal` 的 status 判断保留，负责跨进程重启。落点兜底照常运行，只回填 `ActualNode` 并在实际落点提交 P0 预热。规格换代（`generation` 变化）与删除重建（新 UID）都重新开启循环。

原因：放行那次 status patch 自身会触发一次 watch 事件，紧随其后的 reconcile 可能读到还没收到该 patch 的缓存副本，`isTerminal` 判不出来，于是把整条预热流水线重跑一遍。同一代的并列裁决又共用一条随机源流，取到哪个配对取决于本轮各分配单元走的是 `LowSignal` 还是 `c_ij ≥ 0.5×best` 分支，块陆续落盘会让分支组合变化——于是互换的配对被写回 status，刚提交的热配对被 `Cancel`，门控从 `Released` 退回 `Hold`。e2e 实测（2 Pod / 2 候选节点 / `fanout=1`）100 ms 内出现 3 次配对与 6 次 Cancel/Submit，最终 status 配对还与放行写下的注解互相矛盾。把种子固定在 `(UID, generation)` 上不足够：随机源流的位置会随分支消耗量移动，必须由"终态不再重算"来停止重跑。

## D45 目标集合在册保留（迟滞）

结论：GWAA 的 `Input` 增加 `Held map[int32][]string`，取本轮 `GetPreheatStatus` 报持有（`canceled=false` 且非 `NotFound`）且代际等于本轮的配对。目标集合按块数口径算出后，`Held` 里仍可行、未停止且满足保留线（非低信号时 `c_ij ≥ 0.5 × best`，低信号时视为满足）的节点强制留在集合内：集合已满就换掉排名最低且不在 `Held` 中的那个，未满就直接加入，`target` 数量不变。掉出保留带、被判停止、Agent 报未持有（含换代）之后不保留，按排序自由重选。迟滞只做集合内替换，不消耗随机源，不动 `LowSignal`/`ForcedByMin`/`MinUnmet` 口径。

原因：宽预热把同一个窗口投给全部候选节点，各节点进度天然同步，而目标集合取严格 `c_ij` 排序——谁刚多落一块谁就是 `best`。e2e 实测（1 Pod / 4 候选节点 / `fanout=1`）10 分钟里 `p0` 在四个节点间翻了 50 次，每次翻动一发 `Submit` 一发 `Cancel`，四个节点各下满 1059969024 B（合计约 4 GiB，即 A 级问题的 3 到 4 倍字节放大）。终态冻结只覆盖放行之后，`Hold` 期的翻转仍在。把种子固定在 `(UID, generation)` 只保证同输入同输出，而输入（`ReadinessTable`）每轮都在动，所以同种子止不住翻转；要停止翻转必须把"已在册"本身作为保留依据。

## D46 重投后丢弃 seq 高水位

结论：`ApplyPlacement` 对某 `(pod,node)` 成功发出 `Submit` 或 `Update` 后，控制器立即删除 `pollTracker` 里该配对的 `seq` 高水位，下一轮起该节点从 `seq=1` 起的上报都算新鲜。`check` 的丢弃规则本身不变：同代 `seq ≤` 水位记 `stale`，低代际记 `old generation`。

原因：水位是配对级的、进程内长期保留，而 Agent 的任务实例是短命的：同名同代际的重投被当作新任务，`seq` 从 1 重启。两者一旦错配，重投之后该节点的全部进度对控制器不可见。e2e 实测：`traincache-worker2` 的任务被重新提交后，Agent 报 `state=DONE total_blocks=128 completed_blocks=128`，控制器侧 `ready` 全程停在 31、`rate` 停在 0.2422，`requiredReady=115` 永远够不到，最终以 `tmax_exceeded` 降级。

## D47 窗口变化判据改用窗口块数

结论：`PreheatStatus` 追加 `uint32 window_blocks = 16`，Agent 回显当前任务 `chunks` 项数（`UpdatePreheat` 全量替换后同步）；分配差异里的"未变化"判据改为 `generation` 相同且 `window_blocks` 等于本轮窗口块数。不去重、不用 `total_blocks`。

原因：原判据比 `ready_bitmap` 长度，分辨率是 `ceil(块数/8)`；同一字节区间内窗口从 7 块缩到 8 块或反之都不发 `Update`，Agent 按旧窗口预热，首 epoch 命中率下降而不报错。`total_blocks` 按去重后的唯一块计，与窗口位置数不等价，拿来比会在含重复块的窗口上误判。窗口指纹哈希能覆盖同块数换块，但 Controller 与 Agent 要重复实现同一哈希，当前窗口由控制器单侧生成，块数足以判定。

## D48 PodSetMismatch 只描述部分匹配

结论：`targetPodNames` 匹配数为 0 时不置 `Condition PodSetMismatch`、不发声、只记 Debug；匹配数大于 0 且不等于 `spec.podCount` 才置条件并发 Warning 事件；相等时摘条件。

原因：宽预热先于 Pod 创建，预热期 `pods=0` 是预期状态。把它当不一致会导致每轮重复输出 `Warn`、条件长期为真，淹没真正的部分不一致，也让告警口径对每个任务都报一遍。

## D49 Pod 分数注解

结论：分数快照写在训练 Pod 自己的注解上，键为 `CONTROLLER_SCORE_ANNOTATION`（默认 `traincache.io/node-scores`），值 `{"v":1,"task":"<ns>/<name>","g":<gen>,"t":"RFC3339","s":{"<node>":0..100}}`；`s` 只含该 Pod 实际 `Assignment` 的节点。写分数与移除 scheduling gate 在同一次 Pod patch 内完成，失败时两者都不变；Pod 的 gate 移除后不再改写它的注解。Scheduler 读本 Pod 注解、按节点名取分，不再读 Node，也不再依赖 `pod-index` 定位分数。

原因：原设计在放行时先写 Node 注解、几毫秒后摘 Pod 的 gate；Node 与 Pod 是两个对象、两条 watch 流，Scheduler 可能在看到 Pod 可调度时还没收到 Node 注解更新，取到 0 分（kind e2e 复现过该竞争）。在同一 Pod patch 内写分数，Scheduler 看到的 Pod 对象自带分数，顺序竞争消失；不引入等待或重试延迟，放行时间不变。分数按 Pod 独立存放后，每个 Pod 的写入失败只影响它自己：该 Pod 继续被 gate 拦住，不会出现"分数已写但 Pod 仍被卡住"或反之的中间态。

## D50 门控前置跳过条件

结论：门控仍为 `Hold` 时先做两条前置判断，命中即放行：数据集总字节大于 0 且小于 `cacheCapacityBytes / 20`（`cacheCapacityBytes` 未配置时为 0，该条不触发），原因 `dataset_too_small`；Agent 上报吞吐大于 `0.8 × TRAINCACHE_GATE_NETWORK_BANDWIDTH`（带宽上限未配置时该条不触发）且数据集总字节小于 5GiB，原因 `bandwidth_fast_enough`。两条同时命中时记 `dataset_too_small`。其余情形门控只认就绪度、提前降级与超时三条判据。带宽判断只从候选节点 Agent 的 `/metrics`（9411 端口）取 `traincache_fetch_bytes_total{result="success"}`，按两次采样的增量除以时间差算吞吐，各节点取最大值。

原因：条件①（全达标）、②（提前降级）、③（超时）判定的是"数据备好没有"，这两条前置判断判定的是"等下去有没有收益"。数据集总字节不到缓存容量的 5% 时，预热这批数据省下的回源字节有限，门控挡住训练 Pod 的代价大于收益；Agent 上报吞吐已超过带宽上限的 0.8 倍时，回源链路已被跑满，继续等就绪度不会加快训练进程启动，而此时训练 Pod 还没被调度，没有在读请求在途。预热只做了一小块就放行，剩下的块会在训练开始后继续拉，和训练读抢同一条链路，启动窗口里最该有数据的时候反而没有。就绪度判据要求预热到门槛，提前降级判据在补齐速度低于消费速度时放行，超时上限兜住 Agent 起不来的情形。候选节点只剩一个的情形不跳过：单节点下门控仍能让那台节点备好几块，只是节点分数白算。

## D51 CLI 按节点名拨号

结论：`traincache` 的 `--endpoint` 留空时按四步取地址：显式 `--endpoint` 优先；环境变量 `NODE_NAME` 等于 `--node` 时用 `127.0.0.1:9410`；`--node` 非空时向控制面发 `GET /resolve?node=<节点名>` 拿候选地址数组，按数组顺序逐个试连，取第一个连上的；`--node` 为空时用 `127.0.0.1:9410`。控制面在 metrics 服务器（9412）上暴露该端点，返回 `host:port` 的 JSON 数组，候选顺序是 Agent Pod 的 podIP 在前、节点 InternalIP 在后，Agent 端口取 `CONTROLLER_AGENT_PORT`（默认 9410）。CLI 新增 `--controller`（默认取环境变量 `TRAINCACHE_CONTROLLER_ENDPOINT`，未设置时为 `traincache-controller-manager.traincache.svc:9412`）与 `resolve` 子命令，后者按同一顺序打印候选地址，不发 gRPC、不试连。

原因：节点名到 Agent 地址的映射只存在于控制面，Agent Pod 的 podIP 与节点地址都由控制面从集群状态读出，CLI 侧没有这份信息，所以只知道节点名时连不上目标节点，只能手工给 `--endpoint` 配端口转发。映射放在控制面、CLI 按节点名查之后，两边都只认节点名这一件事：CLI 不维护节点清单，控制面不需要知道谁在用 CLI。端点返回候选数组而不是单个地址，是因为 podIP 与 hostPort 是两条不同的路由，实际通哪条由网络决定，客户端按顺序试连能自动落到通的那条上；显式 `--endpoint` 仍然可用，所以这条路径不取代直连。本机判断排在控制面查询之前，是因为 Agent DaemonSet 用 Downward API 把节点名注入 `NODE_NAME`，目标节点就是本机时不必绕控制面，也不依赖控制面可达。控制面端点复用 Controller 自己的解析器与 30 秒缓存，不新增一份节点名到地址的映射逻辑。
