# Agent 服务化
目标： 将`6.0 缓存核心库设计方法.md`中的库包装成一个常驻服务（Agent）,部署到每个缓存节点上面
别人能远程指挥它进行预热、查询进度，他也能自己主动汇报状态，
并且还能训练中持续预取跟阶段切换时候的重新预取
## 模型部署
Agent采用DaemonSet的方式部署，在每隔符合调度条件的缓存节点上面部署一个Agent实例
Agent 应设置合理的 CPU、内存资源请求与限制，避免后台扫描、校验和预取任务无界占用节点资源。
Agent 的存活探针用于判断进程是否正常运行；就绪探针用于判断服务是否具备提供基本服务的能力。
缓存尚未完成全量扫描不应直接导致 Agent 无法提供服务，具体行为遵循「重启重扫描」章节的设计
Agent 的退出、重启和升级不得破坏本地缓存数据的持久性。进程退出不应导致缓存目录中的有效数据块被主动删除

#### 部署原则
每个缓存节点运行一个Agent实例，负责本节点的缓存管理数据块预热，状态上报与持续预取
Agent 以节点为服务边界，对外提供 gRPC 接口和 Prometheus `/metrics` 端点。
Agent 必须能够唯一确定自身所在的K8s节点，并在状态上报中携带节点标识。

#### 运行约束
Agent 必须具备访问本地缓存目录的权限，能够执行缓存扫描、数据块读取、预热写入和垃圾回收等操作

## 本地缓存目录
Agent使用宿主机`/var/cache/traincache`作为本地缓存根目录
CAS 数据块统一存放在 `/var/cache/traincache/blocks/` 下，物理路径由块内容指纹确定。
Agent 负责调用现有缓存核心库管理本地缓存，不在服务化层重复实现缓存索引、数据块存储、校验和回收逻辑。

## gRPC接口
Agent对外提供了三个主要接口：
- 接收预热任务
- 上报块级任务
- 节点状态查询
控制器使用前两个接口与Agent对话

## /metrics 监控
暴露Prometheus的格式的指标，指标上面带上dataset标签，知道当前agent为使用的数据集是什么
标签的基数需要控制，标签组合不能将监控系统撑爆
#### 设计原则
1. 指标服务于验证缓存价值
2. `dataset` 是所有指标的基础标签
3. 低基数维度进标签，高基数维度进日志/追踪
4. 指标命名要规范，比如同一层级要同一前缀

#### 必须覆盖的六条线路

| 线           | 回答什么问题                            | 对应模块            |
|--------------|-----------------------------------------|---------------------|
| **命中率**   | 缓存到底省了多少回源                    | `cas`               |
| **回源量**   | 对象存储压力降了多少、限流打没打满      | `fetch`             |
| **索引刷新** | 快照传播及不及时、分片复用了没有        | `index` / `Catalog` |
| **GC**       | 回收有没有误删、pin 有没有挡住          | `Collector`         |
| **延迟**     | GPU 到底饿没饿死                        | 贯穿各层            |
| **节点状态** | 服务化后 Agent 活没活、跨节点交互多不多 | 服务化层            |

#### 标签分层
低基数进标签：dataset、node、结果状态、endpoint 这类。
dataset 是核心维度：多项目共用对象存储时，不带它就分不清是谁把缓存打爆了
node是第二个正交维度，为服务化后面的多节点聚合预留

#### 基数控制原则
标签编译期就固定，不引入用户输入（防止基数完全失控）
dataset设置白名单，重点监控白名单里面的，其余标签直接使用other就行
延迟类用固定 bucket，不动态生成

## 重启重扫描
当Agent重启之后，需要重新扫描缓存目录，把CAS索引重新建立起来
能让Agent知道那些块本地嫩直接命中，哪些块需要重新拉取

磁盘会静默损坏，所以需要做校验
对块头抽样校验 1%，全量校验放后台低优先级慢慢做
抽样1%的逻辑：
- 全过 → 大概率这批块没问题，先用起来
- 发现损坏 → 将块标记为坏块（需要增加标记位），交给全量扫描进程，由全量扫描进程慢慢修复

全量扫描： 维护一个需修复的队列，优先解决队列中已有的修复问题，次要解决剩下块的扫描问题
如果某个坏块读的时候全量扫描进程还没修好：
1. 将这个坏块进程从队列中拿出来
2. 读进程自行解决坏块，直接从对象存储拉取
这里要防止二者都在下载，需要复用核心库已有的single-flight机制

注意：全量没做完也能正常服务，因为 CAS 读块时本身会自校验，后台全量是提前发现

## 预取策略
#### 预取优先级排序
P0: 显示启动预取： Pod 落地/手动触发时，为了取得启动阶段要用的块，直接决定 makespan
P1: 阶段切换重预取： epoch/shuffle/curriculum切换时，为了按新消费顺序重新预取，防止切换后data stall
P2: 邻域预取： 训练中持续预取，为了消费游标附近的块，常态化防饿死
P3: 后台补全： 低优先级补缺，可慢慢来，不阻塞服务

#### 训练中持续预取 & 阶段切换重预取
新增⼀个 Agent 内部的预取编排器 PersistentPrefetcher ，它独⽴于 gRPC 预热接⼝，消费
OrderSource 推送的消费顺序

定义以下方法：
- start： 开始预取
从当前的消费位点（cursor）开始，按照consumerOrder的顺序，
将后续块以“邻域预取”的方式进行预取，每完成一块就推进cursor并且上报/metrics
启动预取（来⾃ gRPC Preheat接⼝）和阶段切换重预取可以打断本循环，
打断的时候在途请求不取消，而是新请求采用更高优先级入队

- OnConsumeSideAdvance：消费位点推进
DataLoader钩子每消费完一块数据就调用此方法，来推进cursor
预取提前量 = cursor + lookahead
默认lookahead = 8

- OnStageSwitch： 阶段切换
OrderSource调用阶段切换时把当前阶段未消费的块降级为后台补全优先级（不取消在途请求）
把新阶段的开头块序列作为新的启动窗口高优先级入队
返回切换时刻到新窗⼝就绪的预估时间，供Agent上报。

- Status： 返回当前状态
返回当前阶段、cursor位点、预取队列⻓度、预取命中率（⽤于⾃适应K调参）。

三种类型的切换事件源：
- epoch边界：DataLoader钩⼦检测到当前 epoch 即将结束（消费完最后⼀个分⽚），上报”下个
  epoch 的 seed 和顺序”
- shuffle重排：与epoch行为类似
- curriculum阶段切换：

阶段切换时做法(OnStageSwitch)： 
旧阶段在途预取请求：降级为后台补全优先级
旧阶段没有消费的块（cursor之后的）：从抓取队列中移除，腾出带宽给新阶段
新阶段的开头 K 块：作为新启动窗⼝，⾛”阶段切换重预取”优先级，送进抓取管线
新阶段的剩余块：新启动窗⼝就绪后，转⼊持续预取模式（邻域预取）
上报`traincache_stage_switch_stall_seconds`

#### OrderSource 抽象
OrderSource是消费顺序的来源抽象，Agent持有⼀个实例
部署方式：sidecar，在训练Pod里面跑一个轻量化的sidecar，按照Job的配置算出每个阶段的消费顺序
通过共享内存的方式传递给同节点的Agent
方法：
- CurrentOrder返回当前阶段的消费顺序（块引⽤列表）
里面包括：数据集名称、快照名称、阶段标识、ShuffleSeed、Chunks列表、batch_size、PrefetchChunk（启动窗口大小）

- SubscribeStageSwitch订阅阶段切换事件；返回channel每收到⼀个事件push⼀份新ConsumeOrder、

#### 整体模型
node上面有一条抓取管线，任务按照P0到P3分成四个优先级别
n个Pod执行训练任务，每个Pod有一个消费队列，每个队列上面有一个滑动的预取窗口
窗口中的块先查询本地CAS，已有的不管，没有的按照任务来源定优先级，加入node的抓取管线

Pod中发生阶段切换问题时候，更改他的消费队列，并且重新定位窗口，在途请求降级，未预取的旧块移除，新阶段开头K块高优先级入队

## inotify
#### 热度统计
用 inotify 旁路监听缓存目录的文件打开事件，反应那些块被读过
根据读写频率设置块的冷热等级（多级划分）
热度只做决策输入，而不是关键数据

在内存中维护`指纹->(热度，最近访问时间)`的映射（加权得分是由前两项算出来的），超过N小时的记录直接衰减热度
怎么加权：已定（2026-10-14）——双信号取强 `S = max(热度h, 新鲜度R)`，不用加权平均数（它保护不了「刚预取还没被读过」的块，详见 7.1 §5.5、7.3 D24）
然后每M分钟（如30min） 热度大于阈值的映射dump到磁盘(heatmap.json)持久化
热度衰减： 每隔T（如1天）就将所有条目热度乘以衰减因子，并且淘汰所有加权得分低于阈值的条目


用途： 统计块的使用热度，用于辅助缓存淘汰、辅助预热
缓存淘汰看近期（内存），预热看历史（磁盘）

- 辅助缓存淘汰
缓存磁盘有限，但是可能被快照引用的块远大于盘容量
活数据淘汰 = 在「逻辑上还需要」的块里，决定「哪些本地副本值得留」
筛选活数据： 快照引用 + 无 pin 的本地块
淘汰动作 = 只删本地副本（core 提供 cas.Evict），索引条目与引用关系不动，之后要用经 fetch 重新下载；这跟 core 回收旧快照/旧块的 Sweep 是两回事（Sweep 只删不再被引用的数据）

根据“加权得分”设置两条淘汰线： 
1. 触发线
当磁盘利用率超过阈值k的时候触发淘汰，将利用率降低至k-Δ
2. 危险线
当磁盘利用率暴增，达到很高的值M，激进淘汰+告警，将利用率降低至k-2Δ

- 辅助预热
1. 读磁盘热度 → 选出「历史高频」的块
2. 查本地 CAS → 排除已有的
3. 对缺的块发起 fetch（低优先级、限流，可取消）

预热触发的时机：
冷启动后依据磁盘热度预热历史热块
能手动触发预热

注意： 
同一进程 反复打开一个文件要合并
训练进程可能一个 epoch 里反复打开同一个块。 inotify 会每次都报 OPEN。
如果不合并，统计就变成「打开次数」而不是「有多少数据被读」。

#### 命中率统计
消费者确认：使用插了桩的dataloader（此时dataloader只完成相关接口，不写逻辑代码）
上报给Agent他打开的块集合，再和本地块求交集

用途： 判断缓存效果，出发扩容、预警

生命周期：导出到监控，Agent本地不留长期历史
过期策略是使用滚动窗口（分钟级），或者按照训练阶段聚合
重启数据自然丢弃，重新积累即可

dataloader上报，也不是完美精确，计划读到的不一定是实际成功读到的，不声称Agent在读路径上做了精确记账

#### 交叉校准
inotify观察到的实际打开顺序跟OrderSource推送的预期消费顺序做交叉校准，
如果实际打开顺序跟预期顺序超过某个阈值（默认20%），就将Persistent Prefetch重新对齐到cursor实际的位点
防止预想顺序跟实际顺序的长期漂移

## CLi命令行工具
提供命令行工具，用于手动指定数据集、数据块和目标节点，触发预热并查询执行进度。
CLI 是 Agent gRPC 接口的客户端，不直接操作缓存目录，也不重复实现缓存索引、数据块下载或落盘逻辑
命令包括：
- 手动预热
指定节点，选择快照路径（如果Agent没有存储这个路径下的快照，就要去远端拉取，详细见文档6）
还可以指定该目录下面的任意块
如：
```bash
traincache prefetch \
  --path /train-data \
  --node worker-01 \
  --chunks chunk-001,chunk-002,chunk-003
```

- 查询节点缓存状态
内容包括： Agent是否可用，缓存目录有什么，已缓存的数据量，缓存剩余空间，当前运行的预热任务数量，索引恢复与扫描状态
并且能根据命令的后缀参数 单独查询一项内容
```bash
traincache node status --node worker-01
```

- 查询预热进度
支持查询指定节点上某次预热任务的状态
包括： 任务id，目标节点，数据路径，任务状态（进行中，等待，错误），总块数，已完成块数，失败块数，任务开始时间，最近更新时间
```bash
traincache status \
  --node worker-01 \
  --task-id <task-id>
```

## 最终验收标准
- 手动调用 gRPC 接口能够下发预热任务并查询进度。
- Agent 通过 DaemonSet 部署在符合条件的缓存节点上，重启后本地缓存数据不丢失，索引能够自动恢复。
- 训练 Pod 能通过 hostPath 只读挂载访问本地 CAS 数据块，直接读取数据，不经过 Agent 的 gRPC 读接口。
- CLI 支持指定节点、快照路径和数据块进行手动预热，并支持查询预热进度和节点缓存状态。
- 路径预热只加载所需的 Manifest 分片，不要求加载整个 Manifest；指定块预热不会意外下载未选中的数据块。
- 磁盘损坏的块能够通过后台扫描或读时回源修复，且不会因并发修复产生重复下载。
- Prometheus 指标能够被外部服务访问，覆盖命中率、回源量、索引刷新、GC、延迟和节点状态，并控制标签基数。
- 启动最小训练 Pod 和 OrderSource sidecar 后，Agent 能够接收 ConsumeOrder 并启动 PersistentPrefetcher。
- 阶段切换事件到达后，Agent 能够及时将新阶段开头 K 个块加入高优先级预取队列。
- OrderSource sidecar 退出后，Agent 在 30 秒内进入降级模式，通过 inotify 兜底并上报相应指标。
- 上述关键流程均有可重复执行的测试覆盖。
