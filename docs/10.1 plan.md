术语先解释三个，后文不再重复：

- **COND**：一个实验点的全部条件（数据规模、缓存容量、带宽档位、策略名、种子……）写成一个 JSON 文件，跑分脚本只读它，不读散落在代码里的常量。一个 COND = 一个可复现的实验点。
- **fanout**：预热时把同一份数据同时复制到几个节点。复制 3 份，字节成本就是 3 倍。
- **门控（SchedulingGate）**：TrainCache 的 webhook 先把训练 Pod 卡在 Pending，等 WarmupTask 把数据准备好再放行。放行的判据是"这个 Pod 将要用的数据已经就位到什么程度"。

**预热与预取是两个东西，全文严格区分**：预热 = 训练 Pod 调度之前，Controller 驱动 WarmupTask 把数据拉进节点缓存。此时 Pod 还没落地，不知道会落在哪个节点，所以是"盲热"——`juicefs warmup` 和 Fluid DataLoad 也是同样语义。预取 = Pod 落地之后，Agent 跟着训练的消费顺序持续往后拉数据，epoch/shuffle 切换时重预取。

## 12. 机时预算

单点时长 = 冷态 + 负载 + 采集，按带宽档分别标定（D31）。每步读量 r 与 BW/r 的口径以 `bench/config.py` 为准：r = 数据集字节 ÷（400 步 × 200ms 计算）→ S≈26.8、M≈107.4、L≈429.5 MB/s；100/300/1000mbit 的链路带宽 = 12.5/37.5/125 MB/s。

- S 档单 rep（2GiB×3 epoch ≈ 6GiB 读量）：@100 传输主导 491s ≈ 8.2 分钟，加冷态与采集记 9 分钟；@1000 传输只需 49 秒，时长被计算下限（3×80s=4 分钟）盖住，记 4.5 分钟。

### Q11 L 档 32GiB 数据的磁盘预算

**已裁决（2026-10-24）**：预算上限 200GiB。按 D20 口径估算：shard tar 共 32GiB（现有 8 + 新增 24）、8MiB 块副本 ≤32GiB、旧 64MiB 块快照 ≈2GiB、生成暂存 ≈32GiB、agent 节点缓存 ≤4GiB，合计约 100GiB，预算内。跑 M7 前仍查一次 `df` 确认余量；真不足时 L 档顺延或砍掉（探点，不影响正式表）。

L 档新增分片的生成方式（2026-10-24 定）：`bench/scripts/synth_track_b.py` 增加 `--start-shard` / `--count` 两个参数，追加生成第 32~127 号分片：

```bash
python3 bench/scripts/synth_track_b.py --start-shard 32 --count 96
```

每个分片的随机种子只与自己的序号有关（`config.SEED × 1000003 + shard`），所以「先生成 32 份再追加 96 份」与「一次生成 128 份」逐字节一致。生成器遇到已存在的分片会跳过不重写——产物只追加不覆盖。

**实际数据量与声明值的偏差（2026-10-24 实测）**：生成器按「tar 体积 ≈ 256MiB」校准，但 tar 内是 JPEG 样本（内容不可压缩），实际每份约 252.6MiB。于是 L 档 128 份的真实数据量约 31GiB，比 COND 里声明的 32GiB 小约 3%，容量比相应变成约 1:31 而不是 1:32；S/M 档的偏差在 1% 量级。三档都用声明值参与缓存容量计算，偏差方向一致、不影响组间可比性，出表时注明即可。

### Q12 快照重发布与原数据的关系

**已裁决（2026-10-24）**：采纳并存方案。MinIO 里三类对象各司其职：① `bench-b/shard-*.tar` 是五组共同的源数据，只此一份，不删不动；② 旧 `compare-data/`（64MiB 切块 + 快照）保留，历史产物可按原样复现；③ 新快照发布为 `compare-data-8m`（trainpublish `-chunk-size 8388608`），正式实验一律用它。DataSet CRD 指向 `compare-data-8m`。
