# 缓存核心库设计（design）

核心库是无服务形态的 Go 库，module 名 `traincache/core`，编译进层2 Agent 常驻进程，Controller 侧组件同样按 module 路径导入，仓库根直接 `go build ./...` 会因工作区配置失败，验证一律先进 `core` 目录。它处理三件事：某个数据块在哪、块怎么落本地盘、块怎么从对象存储下载。接口签名与数据格式是冻结契约，改格式必须读写两侧同批改，不留只改一侧的兼容分支。

## 定位

三层各自负责一件事：

- 路径索引层：维护 `(path, chunkIndex)` 到块指纹的映射，以快照形式存进对象存储。指纹是块内容的哈希值，当键用；快照是一次提交后的完整索引版本，读侧只认 CURRENT 指向的那一份。
- CAS 存储层：用 xxh3-128 指纹当存储键，文件位置由内容决定，同内容只存一份，读回来要校验。
- 抓取编排层：按在途字节限并发、合并同键重复请求、校验失败重下。

交付形态是一个被导入的库：可执行面只有两个命令入口，其余能力由调用方在自己的进程里装配，训练语义靠调用参数传进来，core 自己不认识训练阶段。索引的去重只发生在 CAS 层：`(path, chunk)` 当键意味着两条路径指向相同内容时索引里仍是两条条目，磁盘上只存一份块文件。

## 术语

- 数据分片（tar）：上游训练数据集的打包文件，例如 `shard-00000.tar`，百 MB 级 webdataset，存在上游数据源，缓存的对象是它切出来的数据块，每条索引条目的 path 里带它的名字字符串。
- 数据块：把一个 tar 按 64 MiB 等分后的物理单元，是缓存、传输、去重的最小单位，存在对象存储。
- 索引分片：路径索引表的切片，回答某个 `(path, chunk)` 落在哪个块，存在对象存储。
- manifest：快照清单，记录这次快照由哪几个索引分片组成，存在对象存储。
- 快照：CURRENT 指针、manifest 与具体索引分片三部分的整体。

行文里的「分片」一律指索引分片。训练数据侧的 webdataset tar 分片是另一类东西，两类都存在对象存储上，名字容易看混，提到时写全名。

## 包与依赖方向

七个包各管一段：`objectstore` 把 S3 兼容对象存储收成一个接口，条件写在这层；`cas` 管本地磁盘上的块文件；`fetch` 管下载编排、限流、合并、重试；`index` 管路径索引的提交、加载、回收与读者登记；`publish` 编排多个 tar 发布成一个快照；`internal/digest` 封装两种摘要；`logging` 提供日志字段脱敏。命令入口两个，`cmd/trainpublish` 与 `cmd/traincacheds`，只解析参数、装配依赖。

依赖方向单向无环是硬约束：`index` 依赖 `cas` 与 `objectstore`；`fetch` 依赖 `objectstore` 与 `cas`；`publish` 依赖 `index`、`cas` 与 `objectstore`；`cas` 依赖 `internal/digest`。`index` 不反向依赖 `publish`，`logging` 与 core 其他包互不引用，`cas` 不认识 `objectstore`：下载得到的字节流由 `fetch` 喂给 `cas.Put`，本地存储与远端存储解耦，`cas` 能脱离对象存储单测。新文件放错包就会破坏这条方向。

哈希实现只在 `internal/digest` 出现，其他包都调它：xxh3-128 用 `github.com/zeebo/xxh3`，sha256 用标准库，各有一次性计算与流式构造两种用法。

`logging` 只依赖标准库，把 slog handler 包一层做字段脱敏，另带级别过滤与运行时改级、按级别取不同采样率并在去重窗口内折叠相同片段、错误归因标签、请求身份字段四类，供上层的两个独立 module 共用同一份口径，避免各写一份出现两种结果。

## 对象存储抽象

S3 兼容对象存储收成六个方法：

- `Get` 把对象内容完整写进 writer；对象不存在返回 `ErrNotFound`。
- `Put` 上传对象并返回服务端 ETag。相同内容必须返回相同 ETag，这是 S3 简单上传语义，内存 mock 的 ETag 取内容 MD5 的 hex；ETag 就是条件写比对的前置条件值。
- `Delete` 删除对象，对象不存在不算错误。
- `GetETag` 返回对象当前 ETag，不存在返回 `ErrNotFound`。
- `PutIfMatch` 是对象存储上的 compare-and-swap：期望 ETag 传空串时要求 key 不存在（`If-None-Match: *`），非空时要求当前 ETag 等于它（`If-Match`）；前置条件不满足返回 `ErrConflict` 且不写入。CURRENT 的原子提交靠它，同一时刻只有一个提交者能改成。minio-go 后端把 412 前置条件失败、409 冲突、以及 If-Match 指向不存在对象时的 404 都映射成 `ErrConflict`。
- `List` 返回匹配前缀的全部对象键，按字典序升序，无匹配返回空切片；回收方靠它枚举快照对象，读者登记靠它列举声明对象。

构造器两个：`NewMock()` 给单测装配，`NewS3Store(endpoint, accessKey, secretKey, bucket, secure)` 覆盖 COS、OSS、AWS S3、MinIO 等任何 S3 兼容后端，endpoint 形如 `127.0.0.1:9000` 或 `cos.ap-guangzhou.myqcloud.com`，secure 决定用不用 HTTPS。桶按单桶约定用：索引对象与数据块对象同在一个桶里，靠键前缀区分，数据集名写在键里。

支持区间读取的后端在 `Store` 之上实现 `RangeStore` 的 `GetRange(ctx, key, start, end, w)`，闭区间语义同 HTTP 的 `bytes=start-end`，长度等于 end-start+1。start 或 end 为负、end 小于 start、任一端不小于对象长度都返回 `ErrInvalidRange`；对象不存在返回 `ErrNotFound`；写目标失败返回写错误。下载编排层开并行开关时按它分片取数，未实现该接口的后端退回整对象 `Get`。真实 S3 对超出对象末尾的区间会截断返回，实现按读出字节数与请求长度是否相符统一报 `ErrInvalidRange`，短读绝不会被当成完整数据写盘。

带大小的列举是一个可选只读能力：`ListInfo(ctx, store, prefix)` 返回 `ObjectInfo{Key, Size, LastModified}`，给孤儿块清理提供对象年龄；后端不提供该能力时返回 `ErrListInfoUnsupported`，六个方法的语义不受影响。S3 后端用 `ListObjects` 实现，mock 允许测试改写对象的修改时间。

数据块对象的键由 `BlockKey(dataset, path, chunk)` 生成，格式 `<dataset>/blocks/<path>#<chunk>`，存裸数据。前置条件是 dataset 与 path 非空、path 不含 `#`：`#` 是块序号分隔符，键生成不做转义，带 `#` 的路径直接判非法。格式知识只维护这一处，读写两侧都调这个函数。

`ProbeConditionalWrite(ctx, store)` 提前判断后端是否真的执行条件写：写一个临时键（前缀 `traincache-probe/conditional-write-`），再用故意不匹配的 ETag 调 `PutIfMatch`，期望值取 32 个 0，万一当前 ETag 恰好就是这个值就改用 32 个 1。返回 `ErrConflict` 说明前置条件被服务端执行、探测通过；返回 nil 说明服务端忽略了条件、报 `ErrConditionalWriteUnsupported`；其他存储错误原样返回。探测对象尽力删除。各 S3 后端对条件写支持度不一，后端忽略前置条件时提交会静默覆盖 CURRENT，两个并发提交互相盖掉各自的快照且都不报错，所以装配期先探测，比等到真正提交时才失败更早暴露问题。

## 本地块存储

块文件路径 `<cas 根>/blocks/<fp 前 2 字节 hex>/<fp hex>.blk`，一个文件等于 128 字节块头加数据，文件名就是内容指纹的 32 字符小写 hex。xxh3 的计算吞吐远高于本地磁盘写入（单核 8 MiB 缓冲 85.8 GB/s，机型 AMD Ryzen 9 7940HX、Go 1.27.1、Linux amd64，基准在 `core/cas/hash_bench_test.go`），算指纹不额外占 I/O，所以指纹能直接当存储键。

块头是格式规格，v1 就是最终格式，字段与偏移逐字照做：

| 偏移 | 字节数 | 字段 |
|---|---|---|
| 0 | 4 | magic `TCBK` |
| 4 | 2 | version，恒为 1 |
| 6 | 2 | flags，bit0 置位表示块头内的 sha256 有效 |
| 8 | 4 | block_size，uint32 小端，数据字节数，不含块头 |
| 12 | 16 | xxh3_128，数据指纹，等于存储键与文件名 |
| 28 | 32 | sha256，flags bit0 置位时有效，否则全 0 |
| 60 | 68 | reserved，必须全 0，把块头补齐到 128 字节 |

校验信息写在块头里，磁盘上没有独立的校验文件。解析时长度不足 128 字节报错，超出的部分按前 128 字节解析；magic、版本号、reserved 区任一不符就判为坏块。同时维护 64 字节与 128 字节两种布局要维护两套解析，所以只做 128 字节一种。

`New(dir, verify)` 在 dir 下建 `blocks/` 与 `quarantine/` 两个目录（权限 0755），verify 是新写块的校验档位。两个目录必须在同一文件系统上，隔离与发布都靠一次 rename。

`Put(ctx, r)` 流式写入，返回指纹与数据字节数。先在 `blocks/` 目录内建 `tmp-` 前缀的临时文件并写 128 字节占位；再把数据边写盘边算 xxh3，档位要求双验时同时算 sha256；每次读之前检查上下文，取消就返回上下文错误并删掉临时文件。数据字节数超过 uint32 上限时报错，块头放不下长度。算完指纹后用 WriteAt 回填块头、关闭文件、建好两级分片目录、rename 到最终路径，发布成功后触发一次 Put 后置观察者并传入准确的数据字节数。临时文件写在块目录内是为了 rename 不跨文件系统；命名带不上指纹是因为指纹要读完整个流才算得出来，rename 之后别的进程才看得见这块。半成品块只在 rename 后可见，崩溃留下的 `tmp-*` 文件不影响 Open 也不影响后续 Put，枚举时忽略。不做逐块 fsync，掉电丢块的代价就是重拉。多协程同时写同一指纹各写各的临时文件，rename 原子覆盖，最后留下的文件必为完整块；指纹等于内容，覆盖的内容必然相同，所以 Put 里不加「已存在就跳过」的分支，同指纹重写等价于幂等跳过。坏块被隔离后重下再 Put，直接落在空位上。

`Open(fp)` 打开块并校验，通过后返回从数据区起读的句柄，句柄读完 block_size 字节就返回 EOF，`Size` 给出数据字节数。顺序是：先触发 Open 前置观察者（命中或缺失都触发，只表示本进程即将读打开该块，成败不影响这次触发，也不改变 Open 的返回值与错误语义；观察者挂在实例上、原子读取，传 nil 清除）；再打开文件，不存在返回 `ErrNotFound`，其他打开失败返回包装错误；然后读并解析块头，块头指纹与请求指纹不等、数据读出长度不足 block_size、xxh3 重算不符，都返回 `ErrCorrupt`；块头 flags bit0 置位时还要重算 sha256 比对。读时验什么只看块头 flags，与实例的 verify 档位无关，所以把档位从单验切到双验不会触发已有块的全量重算。调用方拿到 `ErrCorrupt` 负责删除后重拉。

`Remove(fp)` 删块：引用计数或 pin 大于 0 返回 `ErrInUse`，块不存在返回 `ErrNotFound`；检查与删除在同一把锁内完成，不会被并发的 Acquire 或 Pin 插进来。

`Evict(fp)` 只删块的本地副本，供磁盘淘汰用：引用计数不拦（引用是快照级逻辑簿记，与副本在不在本地无关），pin 大于 0 返回 `ErrInUse`，块已不存在返回 `ErrNotFound`；与 Remove、Put 同在一把锁内串行；只动 `blocks/` 下的正常块路径，不碰隔离目录。索引条目不受影响，之后 Lookup 命中而 Open 得 `ErrNotFound` 时由下载编排重下一次。回收与淘汰是两个维度：回收删不再被引用的数据，管正确性；淘汰删仍被引用块的本地副本，管磁盘容量，索引与引用关系都不动。

`Acquire(fp)` 与 `Release(fp)` 维护引用计数，引用计数统计的是已提交快照对物理块的逻辑引用，不是当前路径映射的计数；Release 减到零后块进入可回收状态，未 Acquire 过或已归零时是空操作，计数不会变负。读操作不占引用计数，`Pin` 与 `Unpin` 单独管读的生命周期，同样不会变负；pin 大于 0 时 Remove 必须失败。两张表都只在内存里、不落盘：持久化引用计数有崩溃一致性问题，进程重启后归零，所以回收判据以「保留快照可达 并上 有效读者登记」为准，引用计数只做快速过滤和冗余校验。读保护精度落在这里：库的调用方与 Agent 同进程，进程内 pin 够用，跨进程的读保护由对象存储上的读者登记承担。

`List()` 递归枚举 `blocks/` 下全部块指纹，忽略临时文件和解析不出 32 位 hex 的文件名，按指纹字节序升序返回，无块返回空切片。目录布局留在 cas 内部，回收侧只拿指纹列表，布局变化不外泄。

`Quarantine(fp)` 把 Open 校验失败的坏块物理移入 `quarantine/<fp 前 2 字节 hex>/<fp hex>.blk`，与 `blocks/` 并列同两级布局，移走后不再出现在 `List()` 里。幂等：源块不在 `blocks/`（已在隔离区或从未存在）返回 nil；目标已存在时 rename 原子覆盖。不检查引用计数与 pin：隔离是正确性动作，引用计数是索引层的逻辑关系，修好后同指纹块回到原位、引用不变。它与 Remove 及其他隔离操作在同一把锁内串行，只有真实 I/O 错误才报错。`ListQuarantined()` 按与 `List()` 相同的规则枚举隔离块，供修复队列与重扫描使用；`RemoveQuarantined()` 删除隔离块，目标不存在返回 nil。坏块要物理移走而不是打标记，因为留在 `blocks/` 里会让后续读持续失败，还会进 `List()` 枚举、进回收判定。

校验档位有 `xxh3` 与 `xxh3+sha256` 两个取值，默认前者。档位是实例参数、进程级取值：Agent 全进程只有一个 CAS 实例，档位由 `TRAINCACHE_VERIFY` 传入构造器，进程启动后不变。xxh3-128 抗随机损坏但不抗有意构造，能往桶里写对象的人可以让两个内容不同的块算出同一个指纹。当前 sha256 只写在本地块头里、跟数据在同一次读回里重算，索引里没有它的对照，所以这个档位排查的是本地盘有没有在改数据；要挡住构造出来的碰撞，得把 sha256 放进索引条目。

## 下载编排

`fetch` 把远端对象变成本地块。`New(store, cs, opts)` 补齐默认值，字段小于等于 0 一律视为未设置：

- `MaxInflightBytes` 是在途下载字节上限，默认 1 GiB，信号量口径而不是协程数；预铺档最多用一半。
- `MaxConnsPerHost` 是单个主机的连接数上限，默认 64。
- `MaxTasks` 是并发下载任务数上限，默认 16；预铺档最多用一半。
- `MaxRetries` 是校验失败后的重下次数，默认 3。
- `RangeParallel` 打开后每个块拆成 4 段 Range GET 并行取，关闭时走整对象 `Get`；库内默认关闭，Agent 侧由 `TRAINCACHE_FETCH_RANGE_PARALLEL` 控制且默认打开，块大小不参与该判定。
- `OnLocalOpen` 在 Put 成功之后、Open 读回校验之前以块指纹调用一次，可为 nil，实现不得阻塞，通常只做内存记账。

`MaxInflightBytes()` 返回补齐后的实际上限，供观测限速是否打满，是只读访问器，不改变下载语义。

限并发按在途字节而不是协程数：只按协程数限并发时，小文件会把协程数推高到不可用，大文件会把内存耗尽，在途字节对两类文件是同一个度量。字节信号量把超过整条上限的单次请求钳到上限值、独占全部预算，上下文取消时归还额度不泄漏；上限小于块大小时每个块都独占预算到自己结束，并发下载退化成串行。任务槽与主机连接各自计数，同主机的并发受 `MaxConnsPerHost` 约束、不同主机互不影响；主机名取对象键的第一段做稳定划分，对象键本身不含主机名，mock 场景下就是键前缀。

准入分两档。在读档对应需求读补块与坏块修复，已经有人等在这次下载上，按全场额度准入，不受预铺额度与让路门约束。预铺档对应预取与显式预热，先看让路门，再按折半的任务槽与折半的在途字节准入，折半至少留一个。已经在途的预铺下载不取消，数据照样进缓存，让路只拦新接入，所以最坏等一块下载的收尾时间。让路门只计在途的在读下载（含已排队等额度的），不计合并进来的等待者；预铺下载在让路期间被同键的在读请求合并时，那次下载立刻改按在读口径准入，需求读不会被自己的合并对象挡在门外。排队出队顺序是另一条轴，由调用方的优先级队列决定，与准入档位无关。

同一 key 的并发请求合并成一次实际下载：内存表按 key 登记，后来者登记为等待者、共享发起者的结果与错误，不占字节与任务额度；等待者的上下文取消只影响它自己，不取消正在跑的下载。合并钩子 `OnMerge` 由装配层在构造之后、并发使用之前设置，等待者登记时同步调用一次、发起者不触发，只用于计数。

`Fetch(ctx, key, expectSize)` 按在读档准入，`FetchWithAdmission` 多一个档位参数，两者都返回块指纹。命中检查是调用方职责：先经索引查表拿到指纹、用 `Open` 验存在，未命中才调这里，命中就不触及数据源。下载不做引用计数，调用方在首次写入时 Acquire 一次即可；副本被磁盘淘汰后重下不能再 Acquire，因为淘汰只删本地副本、引用计数不动，重复计数会让块永久落在不可回收状态。

一次实际下载最多跑 `MaxRetries + 1` 轮。每轮先拿额度，再取数：`RangeParallel` 打开、`expectSize` 大于 0、后端实现 `RangeStore` 三个条件同时成立时走并行分片，否则整对象 `Get` 流经 `cas.Put` 落盘。并行分片把块均分 4 段，用 `GetRange` 取到一个临时文件的各自偏移上，任何一段短读或出错就取消其余段并返回错误，四段齐了才把这个文件当完整数据喂给 Put 算指纹写盘，在途字节按整块计。分片聚合用的临时文件建在块目录内（`<缓存根>/blocks/`），与 Put 的临时文件同处一卷：不跨文件系统，后续 Put 的 rename 不跨卷；块目录可写这一点由部署保证，Agent 的容器根文件系统是只读的，`os.TempDir()` 指向的 `/tmp` 不可写，所以临时文件不能落在系统临时目录。取数成功并 Put 完成后调 `OnLocalOpen`，再 `Open` 读回校验；校验失败就 `Remove` 该块再重试，重试前退避 100ms 起指数翻倍、无抖动（抖动要跨多个调用方才有意义），退避受上下文控制。此刻的 `Remove` 一定成功：引用要等下载成功后由上层 Acquire，还没有引用也没有 pin。上下文出错立即返回上下文错误，不再重试。重试耗尽后，只有最后一轮的失败是 `ErrCorrupt` 才报 `ErrTooManyRetries`，否则把最后一轮的错误原样返回。

一次下载的完整样子：训练要 `shard-00000.tar` 的第 2 块，读侧先查索引拿到条目与指纹 e5f6…，本地 `blocks/e5/e5f6….blk` 在就 Open 校验后直接读，一次网络请求都不发；不在就按 `<数据集名>/blocks/shard-00000.tar#2` 从对象存储取，字节流经 Put 边写盘边算指纹，回填块头后 rename 原子发布，再 Open 读回校验块头与流式重算数据指纹，校验失败删块重下、退避到上限后报错，成功后按指纹提供读取。

## 索引条目与对象布局

一个数据集有几十万个块，`(path, chunk)` 到指纹的整表远超 etcd 单值 1.5 MB 的上限，所以整表落对象存储，并按条目数切成索引分片管理。角色分四个：写入方产生新条目，构建任务读当前快照并重切分片，对象存储保存一切，Agent 在内存里维护块到位置的映射并按周期去对象存储确认有没有新版本。

键布局是格式规格，逐字照做：

```text
<bucket>/
├── dataset/<数据集名>/CURRENT
├── dataset/<数据集名>/snapshots/<snapID>/manifest.json
├── dataset/<数据集名>/snapshots/<snapID>/shard-<fp8>.idx
└── <数据集名>/blocks/<path>#<chunk>
```

`fp8` 是分片内容 xxh3-128 前 8 字节的 hex，分片文件名只用这 8 字节，清单里存完整指纹。CURRENT 的内容是 `"<snapID> <manifestFP8>"`，空格分隔、无换行，manifestFP8 是 manifest 内容指纹的前 8 字节 hex；CURRENT 是唯一入口，改它等于切快照。snapID 是 16 位十六进制的 UTC 纳秒时间戳加 8 位随机后缀共 25 字符，字符集限于十六进制与连字符，字典序近似等于提交先后。键前缀、清单键、分片键、CURRENT 键四个函数是键布局的唯一来源，快照前缀函数的入参契约是有效 snapID，回收枚举快照根目录时把空 snapID 造成的重复分隔符折叠掉。

索引条目五格，JSON 字段名冻结：

| 字段 | 含义 |
|---|---|
| `path` | 数据分片名，索引寻址的第一半 |
| `chunk` | 块序号，块的字节范围是 `[chunk*ChunkSize, +Size)`，偏移由读侧乘出来、不落盘 |
| `size` | 数据字节数，末块可以不足一个 ChunkSize |
| `fp` | CAS 指纹，32 字符小写 hex |
| `node` | 块实际落盘的节点名，发布器不填，序列化时因空值整字段省略 |

条目先按 `(path, chunk)` 字典序排序，再按条目数切分，每片最多 `MaxEntriesPerShard` 条，默认 100_000。索引分片文件是一个 JSON 数组，元素就是上面这些条目；片内容的 xxh3-128 写进清单里的分片指纹，读侧下载后重算比对，不一致报 `ErrInvalidShard`。单片条目数超上限即违反契约。选 JSON 是为了可读、可调试、构建与合并逻辑简单，10 万条约 13 MB，索引分片在对象存储上对体积不敏感。

分片引用五格：`key` 是分片对象的完整键，`min_path` 与 `max_path` 是片内首末条目的 path，`entries` 是该片条目数，`fp` 是片内容的完整 32 字符 hex。快照清单三格：`snapshot_id`、`created_at`（UTC）、`shards` 引用列表。

```json
{"snapshot_id":"...","created_at":"...","shards":[{"key":"dataset/<数据集名>/snapshots/<snapID>/shard-<fp8>.idx","min_path":"/a/...","max_path":"/b/...","entries":100000,"fp":"<32 字符 hex>"}]}
```

清单只存引用与路径范围，真正的条目在分片里，条目级的总量清单里没有。分片是加载单元，一片内部的路径范围可以跨越前缀。

内容没变的分片不重传：新快照的清单直接引用首次创建它的那个对象键，键含内容指纹、跨快照不变，所以一份分片内容在对象存储里只有一个对象，快照逻辑上完整、物理上复用旧分片。代价有两处：删对象时必须先知道每个保留快照引用了哪些键，只看目录前缀会删掉仍被引用的分片；分片的对象键挂在创建它的那个快照目录下，读侧只能按清单里的 `key` 取对象，按当前快照前缀自己拼键会读不到复用分片，冷启动直接失败。

校验链逐级担保：CURRENT 里的 manifestFP8 担保 manifest.json，manifest 里每个分片引用的指纹担保索引分片内容，分片里每条条目的指纹担保数据块内容，落盘时算出的指纹必须等于它。manifest 损坏能被 CURRENT 查出来，代价只是 CURRENT 多带一个字段。写 CURRENT 之前必须先把 manifest 与全部新分片上传完、指纹算出，先指过去会让读侧下载到一个担保不过的清单；CURRENT 的内容本身不能带换行。

## 提交

`NewWriter(store, cs, cfg)` 构造提交方。`Commit(ctx, dataset, entries)` 与 `CommitChanges(ctx, dataset, puts, dels)` 是同一个事务的两个入口，前者等价于后者传空的 dels；条目参数是本次变更的增量 upsert，不是全表。

提交不覆盖旧数据：新建一套对象，最后用一次条件写把 CURRENT 指过去。一次尝试按七步做：

1. 新块在提交之前就已写好。调用方经下载编排或 `cas.Put` 把块落进本地 CAS 并把引用计数加一；CAS 键是内容指纹，新块不会盖掉旧块。
2. 读 CURRENT 拿它当前的 ETag 作为条件写的期望值；CURRENT 还不存在（空数据集首次提交）时期望值取空串，走 `If-None-Match: *`。
3. 读当前快照的 manifest 与它引用的全部分片，解析出现有条目。manifest 要和 CURRENT 里的 manifestFP8 以及自身的 snapshot_id 对上，每个分片要过键名、内容指纹、条目数三道校验，任何一道不过就是脏快照，直接报错、不写任何东西。
4. 合并：新表等于按 dels 过滤后的旧表并上 puts，同一 `(path, chunk)` 既删又放时 puts 赢；dels 指向不存在的条目是空操作、不报错。dels 本身的合法性在这一步之前校验，Path 为空或 Chunk 小于 -1 直接报错且不写任何对象。
5. 重排切分：内容指纹与某个旧分片相同的新分片直接复用旧的对象键与条目数、指纹照旧、路径范围重算；新分片用 `<dataset>/snapshots/<新 snapID>/shard-<fp8>.idx` 的键。新分片与 manifest 用独立键上传，提交前读侧看不到它们，读侧只认 CURRENT。
6. 提交前确认四件事：manifest 读回来的指纹与算出的一致；每个被引用的分片都能下载、内容指纹一致、条目数一致且不超过上限；每条 puts 的指纹在本地 CAS 能 Open 校验通过；以上全过才继续。
7. 用 `PutIfMatch` 把 CURRENT 改成 `"<新 snapID> <新 manifestFP8>"`。成功即新快照生效；返回 `ErrConflict` 说明别人先提交了，重读最新快照、重新合并构建再提交，最多 `CommitMaxAttempts` 次（默认 5），耗尽报「提交冲突重试耗尽」。

失败不留孤儿对象：每次尝试记下自己新上传的分片键与 manifest 键，任何失败（含冲突重试之前、验证失败）都逆序尽力删除、总超时 5 秒、错误忽略、不覆盖原始错误；复用的旧键绝不删；`PutIfMatch` 成功之后不清理。

删除语义由「每次提交重建全量」的模型直接给出：删除就是这次没带上它，索引里不出现 tombstone 或标记对象，不可变对象照旧。`Delete` 是删除描述，`Chunk` 非负只删该 path 的这一块，`-1` 删该 path 的全部块；目录级批量删除由调用方读旧快照展开成 path 列表再一次提交，库里的删除粒度保持到 `(path, chunk)`。改名就是放新条同时删旧条，一次提交完成。

## 读侧加载

`NewCatalog(store, dataset, cfg)` 绑定单个数据集：查表与刷新的签名里没有数据集参数，所以一个实例只服务一个数据集，换数据集要新建实例。内存映射因写入方提交而常变，所以要周期性地跟对象存储确认。

`Start(ctx)` 在调用方协程里跑循环（要后台执行就自己起协程调它），启动即刷新一次，每个 `RefreshInterval`（默认 5 秒）读一次 CURRENT，上下文取消即停；单轮失败记日志后继续下一轮，不影响原子切换语义。

`Refresh(ctx)` 手动执行一次：CURRENT 原文与上次读到的完全一样就跳过、不下载任何东西；变了就下载 manifest、逐个下载分片并校验、构建新映射、用原子指针一次性切换。绝不边加载新分片边改正在使用的旧映射，读的人永远看到完整一份；加载失败保持旧映射。校验规则与提交侧同一套：manifest 过指纹与 snapshot_id 两道，分片过键名、指纹长度、内容指纹、条目数四道。

`Lookup(ctx, path, chunk)` 是纯内存查表：当前快照里没有该条目返回未命中；还从来没有过快照返回 `ErrNoCurrent`。

`LoadPrefixes(ctx, prefixes)` 按前缀加载：读 CURRENT、下载 manifest（只有分片引用列表，几十 KB，全量下载），只下载校验加载与任一前缀相关的那些分片，构建局部映射原子切换。分片相关当且仅当该片的 `max_path` 不小于 prefix，且 `min_path` 不大于 prefix 或 `min_path` 以 prefix 开头。prefixes 为空不加载任何分片、映射为空；含空串元素匹配一切、等于全量。加载失败不动旧映射。全量索引分片加起来能到 GB 级，而训练往往只需要某些 path 的数据，所以按前缀加载是必要的；省掉的是无关分片的下载，manifest 仍然全量下载。与 `Refresh`、`Start` 是互斥的使用模式，宿主二选一；这个方法不起后台循环，前缀集变化时宿主再调一次。加载哪些前缀由上层服务决定，库只提供能力。

`List(ctx, prefix)` 是只读枚举：读 CURRENT 与 manifest，按同一套相关性判定只下载相关分片（无关分片零下载），片内再按 prefix 过滤，按 `(path, chunk)` 排序返回；prefix 为空是全量，无匹配返回空切片，无 CURRENT 报 `ErrNoCurrent`。它不触碰内存映射，Lookup 看到的既有映射不受影响，「失败不动旧映射」在这里恒成立，可与刷新循环并发调用。

`SnapID()` 原子读当前生效快照的 ID，还没有快照返回空串。`ShardsLoaded()` 返回当前生效快照清单里的分片数，从未成功加载过返回 0。两者都是纯读、不长持锁。

`RefreshManifest(ctx)` 是无活跃前缀时的轻量跟随：读 CURRENT 并下载校验 manifest，不下载分片，成功后原子切换 snapID 并把条目集换成空，旧映射整体作废；失败不动旧映射。当前 snapID 未变且现有条目非空时是空操作，不切换、不清空、也不触发切换通知。装配时先写入本轮订单的路径前缀、再启动跟随循环：跟随循环启动即做首轮检查，先启动后写前缀会让首轮读到空前缀、清掉刚装入的映射，此后快照号不变、每轮都跳过，空映射固化下来。

`Follow(ctx, prefixes func() []string)` 是阻塞式跟随循环：每个 `RefreshInterval` 做一次廉价的 CURRENT 检查，snapID 没变就跳过；变了就按 `prefixes()` 的返回值走 `LoadPrefixes`（非空）或 `RefreshManifest`（空）；单轮失败通知错误回调后继续下一轮、不清空旧映射，只在上下文取消时返回。

配置里有三个可选回调，nil 表示不回调，实现不得阻塞，回调 panic 不向调用方传播：`OnSnapshotChange(dataset, snapID)` 在每次成功原子切换之后、锁外调用，由 `Refresh`、`LoadPrefixes`、`RefreshManifest`、`Follow`（经其内部调用的加载方法）触发，未发生切换的空操作不触发；`OnSnapshotError(dataset, err)` 只由 `Follow` 的单轮加载失败触发；`OnSweepSkip(dataset, reason)` 由回收在受保护快照的清单不可用时触发。

按数据集加载是构造时绑定数据集、走 `Refresh` 或 `Start`；按路径前缀加载是走 `LoadPrefixes`，两种模式覆盖同一份索引数据的不同子集。

## 读者登记

回收旧快照前要知道还有没有节点在读它，每个节点把自己在读的快照登记到对象存储，不搞分布式租约。一节点一数据集一对象，键是 `dataset/<dataset>/readers/<url.PathEscape(nodeID)>.json`，内容是五个 JSON 字段：`node_id`、`snap_id`、`previous_snap_id`、`previous_until`、`updated_at`。

`NewReaderRegistry(store, nodeID, grace)` 的 grace 小于等于 0 回退 10 秒。

`Declare(ctx, dataset, snapID)` 幂等，覆盖同一个对象：本次 snapID 与上次不同才把旧值写进 `previous_snap_id`、把 `previous_until` 写成当前时间加宽限期，给刚切换完的旧快照一个宽限期；同一快照重复声明保留 previous 与其截止时间，等到当前时间超过它才清空。写入成功后才更新内存里的声明，失败不更新；上下文取消返回上下文错误。

`Withdraw(ctx, dataset)` 撤销声明：`snap_id` 写空、上次快照进宽限期，尽力而为，内存里的最近声明保留，之后停止心跳。

`ReadReaderClaims(ctx, store, dataset)` 先列举再逐个读；列举后对象消失就跳过；任一声明的 JSON 解析失败返回错误。回收方必须把这条错误当作整轮放弃，不能把读取失败当成「没有声明」继续删。

宽限期存在的原因：读者从加载旧快照到加载新快照之间有窗口，固定保留个数覆盖不到正在切快照的读者。

## 回收

删除面有两处，谁删什么由各自的可达性信息决定。

对象存储侧 `NewCollector(store, cfg)` 的 `Sweep(ctx, dataset)` 返回删除的对象数，删除面只有快照对象（manifest 与分片），不删任何节点的本地块，也不删数据块对象。构造参数里的 `RetainSnapshots` 至少按 1 处理。规则按顺序：

1. 枚举 `dataset/<数据集名>/snapshots/` 下的全部键，枚举空前缀时把重复分隔符折掉。快照根目录下的非规范首段（长度不是 25 或字符集不是十六进制加连字符）不进保留窗口，按垃圾回收。
2. 读并解析 CURRENT；还没有 CURRENT 就什么都不删。
3. 保护集 = CURRENT 指向的快照 并上 按 snapID 字典序最大的 `RetainSnapshots-1` 个候选 并上 有效读者登记声明的快照。`UpdatedAt` 超过 `ReaderGrace` 的登记整体忽略，视为读者已死；`previous_snap_id` 只在当前时间不晚于 `previous_until` 时计入。固定保留个数只是兜底上限，安全边界由有效登记集合给出。
4. 读登记失败整轮放弃。
5. 把保护集里每个快照的 manifest 与分片全部读出来组成存活键集，分片内容指纹重算比对，不符报 `ErrInvalidShard` 且一个对象都不删。
6. 删除列举结果里既不在保护快照集合中、也不在存活键集里的对象；CURRENT 永不删；被保留快照复用的分片保留。
7. 受保护快照的 manifest 缺失或损坏时，无法知道它复用了哪些分片对象（未变更分片跨快照共用同一对象键），该数据集本轮一个对象都不删，触发 `OnSweepSkip(dataset, "manifest_unavailable")` 后返回，不牵连其他数据集、不整轮停摆。

`Sweep` 不承诺与并发提交安全，调用方应串行调度，最坏情况是多一次提交冲突重试。库内不放定时器，回收由宿主按周期显式调用，提交路径不带回收。心跳过期即判读者已死并允许删，否则 Agent 崩溃后旧快照会永久留着。

远端数据块对象的回收另有一条：`FindOrphanBlocks(ctx, store, dataset, minAge)` 返回候选孤儿块列表（键、大小、最后修改时间）。活块集合按全部快照重建，范围比保留窗口更宽，正在被窗口外旧快照复用的块不算孤儿；窗口外快照没有 CURRENT 担保指纹，所以清单只校验存在性与 snapshot_id，分片仍按完整规则校验。候选等于不在活块集合内、最后修改时间非零、且不晚于当前时间减 minAge。任一清单或分片缺失、损坏直接报错，不给部分结果。

本地块副本的回收按节点算：`NewLocalGC(store, cs, cfg)` 的 `Sweep(ctx, datasets)` 返回删除数。本地 CAS 是节点级全局、内容寻址，块不按数据集分区，「这个副本还有没有数据集引用它」只能按节点回答；按单个数据集算会把同一节点上其他数据集的副本当孤儿删掉。所以：

- `datasets` 必须是本轮全集（远端枚举 并上 本地已知），漏掉一个数据集，它的块就会被当孤儿删掉；调用方枚举失败时应整轮放弃、不调用本方法。空数据集名跳过，每个数据集检查一次上下文。
- 每个数据集先读 CURRENT：确定不存在（`ErrNoCurrent`）不贡献活块、不算错误；读 manifest 或分片失败触发跳过回调并报错。然后读该数据集的读者登记，宽限期内、且与 CURRENT 不同的快照也标记为活，其中对象已经不在的跳过不算错——本节点自身的登记同样计入，多保护无害。
- 活块集合之外的本地副本走 `cas.Evict`，引用计数不挡；`ErrInUse`（pin 大于 0）与 `ErrNotFound` 当跳过、留待下轮，其他错误返回。生产路径不 Pin，这条实际不触发；已经打开该块的读进程不受影响，删的是目录项，已持有的句柄照样读完。
- fail-safe：任一数据集的索引读不到（确定不存在除外）或损坏，整轮不删任何块。凑不出活块集合却按集合差删除，仍被引用的副本可能整批进删除名单，代价是本节点这些块全部回源重下。
- 存储实例或 CAS 为 nil、本地一块都没有时返回 0 且不报错。

条目被删后新快照不再引用它的块，本节点那份副本在下一轮清扫里回收；其他节点上仍在读旧快照的 Agent，靠自己的登记把该快照的块留在该节点的活块集合里。数据集被删掉或从未提交时没有 CURRENT，它的本地副本被回收，不算错误。

## 多 tar 发布

`core/publish` 是写侧编排：把一批 tar 源按块切分粒度切开、逐块写本地 CAS 与对象存储、生成索引条目列表，最后只调一次 `Writer.Commit` 发布成一个快照。索引合并、分片构建、条件提交都在 `index` 包里，发布器不重复实现；写侧编排跨三个包，放进任何既有包都会造成反向依赖或环，所以单开一个包。

`Source` 三格：`Path` 是索引路径，同批次内必须唯一、不能含 `#`、不可变；`Reader` 提供数据，允许并发按偏移读；`Size` 是数据字节数，负数报错，0 字节不产生条目。`Options` 三格：`Dataset` 为空报错；`ChunkSize` 与 `Concurrency` 传零值回退 64 MiB 与 4。`Result` 四格：`SnapID`、`Entries`（只计本次发布生成的条目数，快照总条目数是另一个数，因为提交做 upsert 合并）、`Bytes`（各 Source 的 Size 之和）、`UniqueBlocks`（本次观察到的不同内容指纹数）。错误两个：`ErrNoSources`（没给源）、`ErrDuplicatePath`（Path 重复）。

流程：先校验数据集与每个源，再按切分粒度展开任务（每个 (源, 块号) 一个，末块取剩余字节），起 `min(并发度, 任务数)` 个协程上传，任一块失败就取消整轮、返回首个错误、不提交；全部成功后按 `(Path, Chunk)` 排序条目，调一次提交。每块的动作顺序是先 `cas.Put` 落本地拿指纹、再 `store.Put(BlockKey)` 上传远端，这个顺序不能颠倒：提交的完整性验证只看本地 CAS、不看远端块对象，块对象没传上去就会让新快照指向远端不存在的块。跨路径内容相同的块本地 CAS 只存一份，远端按各自 path 分别保留 `<path>#<chunk>` 键，两个口径不同。

失败语义：任一块上传失败就不提交，已上传的远端块留着成为孤儿，由孤儿块回收规则收；提交失败时 `Writer` 只尽力删除本次尝试上传的分片与清单，发布器不动远端块对象。同一 Path 不能对应不同内容，tar 文件名要带版本或哈希；重复发布同 Path 且内容一致，按 upsert 幂等处理。条目的 `node` 字段发布器恒不填，发布完成后本地工作目录可以清理。

上传示例：200 MB 的 `shard-00000.tar` 切成 4 块（3 个 64 MiB 加 8 MiB 末块），每块算出 xxh3-128 指纹，作为独立对象上传到 `<数据集名>/blocks/shard-00000.tar#0` 到 `#3`，索引留 4 条条目；条目按 `(path, chunk)` 排序、每 10 万条切一个索引分片上传，生成新 manifest，CURRENT 条件写入切到新快照。

块切分粒度在桶级别固定一次，记在桶根的 `_traincache/format.json` 里，内容是 `{"version":1,"chunkSize":N}`。这个键在 `dataset/` 前缀之外，所以快照枚举不会把它当成快照对象。空桶首次发布时用空期望值的条件写写入；桶里已有声明就按已有值发布，显式传不同值直接失败并说明改块大小需要清空桶或换桶；后端忽略条件写时不做静默覆盖、直接失败；条件写撞上并发就重读已有声明。读回来的声明要校验版本与 chunkSize 大于 0。

## 命令行入口

两个命令各管一段：`trainpublish` 覆盖增与改（切块、上传、一次提交），`traincacheds` 补上删除、查询、回收触发。名字按职责取，不带统一产品前缀，改名也不留别名；`tc` 这个名字不能用，它是 iproute2 的流量控制工具（`/usr/sbin/tc`），压测装置大量用真 `tc` 做限速，同名会歧义。

```text
trainpublish --dataset <name> [options] <tar> [<tar>...]
trainpublish --dataset <name> --check-dataset <path>

traincacheds rm    <ds> --path p.tar[,…] | --prefix p/  [--dry-run] [--yes]
traincacheds ls    datasets | snapshots <ds> | entries <ds> [--prefix p/] [--limit n]
traincacheds stat  <ds> [--path p.tar]
traincacheds gc    <ds> [--orphan-blocks] [--orphan-grace 24h] [--dry-run] [--yes]
```

trainpublish 的对象存储参数是 `--endpoint`、`--access-key`、`--secret-key`、`--bucket`、`--secure`，每个都有 `TRAINCACHE_OBJSTORE_` 同名环境变量兜底，endpoint 默认 `127.0.0.1:9000`、bucket 默认 `traincache`；布尔型环境变量接受 `1`、`true`、`yes`，忽略大小写。`--chunk-size` 以字节计、默认 64 MiB，只在显式设置且桶为空时生效。`--concurrency` 默认 4。`--work-dir` 指定 CAS 工作目录的父目录，没给就用系统临时目录，目录以 `trainpublish-` 为前缀创建，退出时删除，`--keep-work-dir` 保留。`--probe-conditional-write` 在发布前探测条件写。`--check-dataset` 只校验不发布：读桶级声明，比对 DataSet 文件的 `kind` 是 DataSet、`metadata.name` 非空、`spec.datasetName` 等于 `--dataset`、`spec.chunkSize` 等于桶声明的块大小，打印 `ok dataset=… chunk_size=… dataset_file=…`，不符退出 1。位置参数是 tar 文件，索引路径取文件名；同批次路径重复报 `ErrDuplicatePath`。成功打印 `snapID=… entries=… bytes=… unique_blocks=…`。退出码 0 成功、1 运行错误、2 参数错误。

traincacheds 的参数解析分两段：每个动词有自己的 flag 白名单，flag 与位置参数混排，`--` 之后的全部按位置参数处理；白名单外的 flag 打印用法并退出 2。四个动词都站在既有导出面上：索引变更只有 `CommitChanges` 一条路径，查询复用 `List` 与清单里的分片条目数，回收复用 `Sweep` 与孤儿块查找。

- `ls datasets` 每行一个数据集名，判据是存在 `dataset/<数据集名>/CURRENT` 这个键；`ls snapshots <ds>` 每行一个快照 ID，CURRENT 指向的那行行尾标 ` current`；`ls entries <ds>` 每行 `<path> <chunk> <size> <fp>`，`--prefix` 过滤、`--limit` 截断且必须不小于 0。
- `stat <ds>` 打印 `dataset=… snapshot=… shards=… entries=…`，只读 CURRENT 与 manifest，两次 GET 就出结果；`stat <ds> --path p` 才下载相关分片，并追加条目级的 `paths=… bytes=…`。条目级总量不在清单里，所以不带 `--path` 就不报这个数。
- `rm` 的 `--path` 删指定 tar 的全部块，`--prefix` 是目录级批量：读旧快照、按前缀过滤、展开成 `(path, chunk)` 粒度的删除描述、一次提交。没有命中时打印 `nothing to remove`。
- `gc` 手动跑一次对象存储侧回收，`--orphan-blocks` 附带清理远端孤儿块对象，宽限期由 `--orphan-grace` 给定、默认 24 小时、必须与该开关同时给且不小于 0。宽限期给「先传块后提交」的在途发布留窗口。孤儿候选在删快照对象之前就用删除前的快照集合算好，结果可复现；预览模式下用一个吞掉删除的存储包装跑回收，好数出「会删多少」。
- 安全阀：`rm` 与 `gc` 默认只预览，打印影响的条目数与字节数、行首标 `would remove`；预览优先于 `--yes`，非交互环境要真正执行必须带 `--yes`。CURRENT 与仍被读者登记的快照受回收规则既有保护。
- 输出错误统一以 `traincacheds: ` 开头，退出码与 trainpublish 同口径。

CLI 只动对象存储里的快照对象与块对象，只删已提交快照不再引用的，不碰任何节点的本地 CAS。删除的传播靠快照跟随，不加 RPC、不做删除事件通道：提交一个不含目标条目的新快照，节点跟到新快照后该条目从内存映射里消失，训练读到被删的 path 就是未命中，语义已经正确；旧快照对象由回收删，远端孤儿块由 `gc --orphan-blocks` 删，各节点本地副本由节点侧周期清扫删。

## 默认值

- 块切分粒度 `ChunkSize` 64 MiB，参数化可调，桶级声明固定后改大小要清空桶或换桶。
- 索引分片条目上限 `MaxEntriesPerShard` 100_000。
- 提交冲突重试上限 `CommitMaxAttempts` 5。
- 快照保留窗口 `RetainSnapshots` 3，即 CURRENT 加最近 2 个，构造时至少按 1 处理。
- 刷新周期 `RefreshInterval` 5 秒。
- 读者登记有效期 `ReaderGrace` 取零值时回退 2 倍刷新周期即默认 10 秒；登记表自身的 grace 小于等于 0 时回退 10 秒。
- 在途下载字节上限 `MaxInflightBytes` 1 GiB，预铺档折半使用。
- 单主机连接数 `MaxConnsPerHost` 64。
- 并发任务数 `MaxTasks` 16，预铺档折半使用。
- 校验失败重下次数 `MaxRetries` 3，退避 100ms 起指数翻倍。
- Range 并行 `RangeParallel` 库内默认关闭，Agent 侧默认打开。
- 校验档位默认 `xxh3`，另一档 `xxh3+sha256`。
- 发布的块大小与并发默认 64 MiB 与 4。
- 并行分片的段数固定 4。
- 索引配置的三个回调默认为 nil。

配置项的零值与负值都按未设置处理并取默认值，索引与下载两层口径相同。

## 规模边界

每次提交读全量旧条目重建分片，未变更分片只复用键不重传。低频批量的数据集级管理操作可接受；提交频率一高，先出问题的是写放大和冲突重试，管理平面的容量按提交频率算。库对提交频率不设上限，一次提交承载一批变更，批量聚合由调用方的调度策略决定。

单条命令或单次调用的开销口径：`stat <ds>` 两次 GET；`LoadPrefixes` 与 `List` 只付相关分片的钱；`LocalGC.Sweep` 每轮按数据集读 CURRENT、manifest 与相关分片；误删一个本地副本损失一次回源重下。

## 日志关键位置

库用标准库 `log` 打点，不引入日志框架，宿主自行接管输出。关键位置与必带字段：

- 快照切换：数据集名、新旧 snapID、分片数、本次加载耗时。前缀加载与清单跟随的每次成功切换都出，切换回调只用于宿主计数，不替代日志。
- 刷新与跟随的失败：数据集名、出错阶段（读 CURRENT、下载 manifest、下载分片、解析）、错误文本；跟随循环单轮失败只记一条，不刷屏。
- 提交：数据集名、新 snapID、条目数、分片数、复用分片数、冲突重试次数；冲突重试每轮一条，重试耗尽按错误级。
- 回收：数据集名、候选对象数、删除数、保护集大小；整轮放弃与 `OnSweepSkip` 各自一条，说明放弃原因（清单不可用、分片指纹不符、登记读取失败）。
- 本地清扫：数据集全集、活块数、删除数、因 pin 跳过的块数、整轮放弃的原因。
- 下载重试：key、期望大小、实际算出的指纹、第几次尝试、退避时长；`ErrCorrupt` 与重试耗尽错误级，其余失败按错误原样带出。
- 隔离与修复：块指纹、移动结果；幂等空操作不打日志，避免与并发修复循环互相刷屏。
- 坏块校验失败：请求指纹与块头指纹都要写出来，只有指纹对不上这一类才够定位磁盘问题。

字段一律用结构化键值，路径、块号、指纹、task 标识这类高基数维度只进日志不进指标；日志内容不得改变业务逻辑，也不得为了打点开额外的读。

## 验收标准

`cd core && go build ./... && go vet ./... && go test ./...` 全绿，格式检查 `gofmt -l core` 无输出。四条基本契约各自成一条用例并且必须过：

1. 多个 goroutine 并发 `Put` 同一份内容：最终文件完整、指纹正确、没有临时文件泄漏。
2. `Put` 中途终止或预置孤儿临时文件：重开后同内容的 `Put` 完成，`Open` 不受影响。
3. 同内容 `Put` 两次：指纹相同，磁盘上只有一份文件。
4. 篡改块内容：`Open` 报 `ErrCorrupt`，下载编排自动 `Remove` 重下后恢复可读。
