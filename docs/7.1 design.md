# Controller & Scheduler design
> 本文是实现契约：§5 接口签名、§6 数据格式、全文表格与枚举取值已冻结，字段名、类型、默认值照写，不得擅改；实现与签名不符时回传 `BLOCKED`，按 7.3 §3 流程裁决。需求基线是 `docs/7.0 Controller & Scheduler.md`（不改动）；fanout 的"上限 + 下限"语义（7.3 D39）未回写 7.0，以本文 §5.1、§5.5 为准。里程碑与验收命令见 `docs/7.2 plan.md`。

## 1. 模块定位与职责
Controller 管预热生命周期，Scheduler 管训练 Pod 落点；两者不互调，只经 Node annotation 传分数快照。新增 Go module `traincache/controller`：

| 组件 | 职责 |
|---|---|
| `DataSet` 控制器 | 校验数据契约、固化块编号与布局、解析可达节点、校验快照可访问性；只写 status，不触发预热 |
| `WarmupTask` 控制器 | 唯一执行者：筛候选节点、GWAA 分配、按块下发/更新/取消预热、轮询进度、门控判定、放行时冻结评分并写 Node annotation；管"数据备好没、能不能放行、哪个节点备得最好"，Pod 最终落点交给 Scheduler |
| MutatingWebhook | Pod 创建时注入 SchedulingGate、WarmupTask 引用与 Pod 序号注解，是门控链路的前置条件（基线缺口 G1） |
| Scheduler 插件 | 只读 Node annotation，实现 `Score` / `NormalizeScore`，返回 0~100 |

### 1.1 边界（非目标）
- 训练读路径不经过本模块：训练 Pod 经 hostPath 直读本地 CAS。
- 数据发布（tar 切块、快照提交）归 `core/publish` 与 `traincache trainpublish`。
- 运行时重预取（epoch/shuffle/curriculum 切换）归 Agent 的 `PersistentPrefetcher`，阶段切换永不进入调度路径。
- 不实现 DataLoader/sampler：训练侧只消费 `InitialConsumeFiles` 展开后的块序与固定 chunk 序号。7.0「接入真实 DataLoader」的块分配均衡、worker 序列与本节点预热对齐、切换后重新均衡，由 DataLoader/Agent 侧契约维护，钩子协议见 7.3 Q5（归 6.x）。
- 不实现 Agent 服务端：Agent 侧 gRPC 增量由 6.x 承接（见 §12）。

### 1.2 与已有模块的关系
依赖全部单向：Controller 是上层消费者，core 与 agent 是被依赖的下层。

| 已有模块 | 复用方式 | 依赖方向 |
|---|---|---|
| `core/objectstore` | `NewS3Store` / `Store.Get` 校验 CURRENT、manifest、shard 存在性 | controller → core |
| `core/index` | 复用 `Manifest`、`ShardRef`、`Entry`、键布局常量；只读 | controller → core |
| `agent/api/agentpb` | 扩展 `PreheatService`，Controller 作客户端 | controller → agent |
| `agent/metrics` | 只参考 family 命名纪律，独立 Registry | 不复用代码 |
| `agent/cmd/agentd` | 参考 slog 初始化、信号处理、优雅退出 | 不复用代码 |

## 2. 术语速查
| 术语 | 含义 |
|---|---|
| 幂等 | 同一动作重复执行结果不变：`Submit` 同一 `task_id` 两次，不会建出第二个任务 |
| best-effort | 尽力而为，失败不阻塞主流程 |
| 就绪度 | 数据已准备好的程度 |
| 窗口内就绪度 | 启动窗口（前 K_i 块）内已就绪的块数 |
| 全局衰减就绪度 | 全程就绪块按离起点距离加权：窗口内权重 1，窗口外按半衰期指数衰减，截断距离之外不计（§7.6） |
| 预热节点集合（暖节点集合） | 某 Pod 在本次任务中被选中预热的节点，数量由 preheatFanout 声明，通常多于一个 |
| 最终落点 | Scheduler 真正把 Pod 放到的节点；正常情况下从该 Pod 的暖节点集合中选出，被抢占时可能落在集合之外（§7.8） |

## 3. 总体架构与依赖方向
四个组件的部署拓扑（Controller 写分数快照进 Node annotation，Scheduler 只读该 annotation；controller-manager 管两个 CRD，经 gRPC 南向调用 Agent 下发预热任务；Webhook 在 Pod 创建时拦截，先于调度器运行）：

```
                    kube-apiserver
        ┌───────────────┼────────────────┬──────────────┐
        │               │                │              │
   controller-manager  webhook       kube-scheduler   Node
        │               │                │              │
   ┌────┴────┐          │           TrainCacheScore     │
   │ DataSet │          │           (读 Node annot.)    │
   │ Warmup  │          │                ▲              │
   └────┬────┘          │                │              │
        │  gRPC(南向)   │                │              │
        ▼               │                │              │
   Agent(DaemonSet) ────┴────────────────┴──────────────┘
        │
   S3 对象存储 / 本地 CAS
```

依赖方向固定为单向：

```
cmd/* → internal/{controller,webhook,scheduler}
internal/controller/* → {api/v1alpha1, gwaa, gate, nodescore, agentclient, storage, config, logging, metrics}
internal/{nodescore,agentclient,webhook,scheduler} → api/v1alpha1
internal/{nodescore,scheduler} → scorefmt
internal/agentclient → agent/api/agentpb
internal/storage → core/{objectstore,index}
api/v1alpha1 → k8s.io/apimachinery only
```

禁止 `api → internal`、`gwaa/gate/scorefmt → k8s 客户端或 core`、`scheduler → controller 内部包`、`internal → cmd`：底层不得反向依赖上层，避免小改动牵连大范围。

## 5. 核心接口（冻结约定）
### 5.1 CRD 类型
Group `traincache.io`，Version `v1alpha1`。两个 CRD 均 Namespaced，跨对象引用只允许同 namespace。只开 `status` 子资源，不定义 `scale`（基线缺口 G9）。`WarmupTaskSpec.podCount` 与 `dataSetRef` 不可变，由 CRD CEL 校验 `self == oldSelf`；Controller 不创建 Job/Pod、不扩缩容、不重建 Pod，用户也不需要写 Job yaml。`traincache.io/s3-access` 标签由用户/集群管理员手工维护，任何组件不得写入。

DataSet 描述"数据本身"（endpoint、bucket、数据集名、chunk 大小、shards 列表、可达节点选择器）；WarmupTask 描述"一次预热"（引用 DataSet、指明 Pod 集、定义门控与调度策略）。

| 枚举 | 取值 | 备注 |
|---|---|---|
| `TrainingType` | `epoch` / `shuffle` / `curriculum` / `static` | 随机种子不进 spec，归 DataLoader |

| `WarmupPhase` | `Pending` / `Filtering` / `Preheating` / `Gating` / `Released` / `Degraded` / `Failed` | |
| `GateState` | `Hold` / `Released` / `Degraded` | |
| `PreheatState` | `Preheating` / `Ready` / `Stopped` / `Failed` | |
| `AffinityPolicy` | `Any` / `Pack` / `Spread` | 仅记录，v1 不参与算法 |

#### 5.1.1 启动窗口 K_i
`PodDetail.K` 可省略（CRD 下限 0，0 表示省略）。省略时 Controller 按下表算出每个 Pod 的 `K_i`：

| 符号 | 计算 |
|---|---|
| `W_i` | Pod i 实际分到的块数：填文件清单时为所列分片的块数之和；默认均分时为 `[floor(i*T/P), floor((i+1)*T/P))` 的长度 |
| `K_window` | `ceil(startupWindowBytes / chunkSize)` |
| `K_cache` | `floor(cacheCapacityBytes × maxFillFraction / (podCount × chunkSize))`；`cacheCapacityBytes=0` 时不计算 |
| `K_i` | `clamp(min(W_i, K_window, K_cache), 1, W_i)` |

`startupWindowBytes` 默认 536870912（512MiB），`maxFillFraction` 默认 0.125，与 `cacheCapacityBytes` 同在 ConfigMap `traincache-config`（§8）。`maxFillFraction` 是自动 K 的缓存预算口径：全部 Pod 的自动 K 总量不超过缓存容量的这个比例，按 `podCount` 均摊；显式 K 超过该预算只发事件，不拒绝。

K 省略（0）时，Controller 把算出的值 patch 回 `spec.podDetails[].k`，立即 `Requeue`，并发 Normal 事件 `KDefaulted`（日志 `startup window K defaulted`）；后续门控与轮询只读 spec 中的持久化值。

用户显式填 `K` 时有效范围是 `1..W_i`；`K > W_i` 置 `Condition InvalidSpec=False` 并拒绝，不截断、不钳制。`cacheCapacityBytes > 0` 时，全部 Pod 实际请求块数（`min(max(K_i, score.cutoff), W_i)`）合计超过 `cacheCapacityBytes × maxFillFraction` 只发 Warning 事件 `KExceedsFillLimit`，任务照常执行，超出缓存预算的块由回源承担。

预热请求的块数是 `min(max(K_i, score.cutoff), W_i)`（§5.9），超过消费顺序长度时截断。启动阶段只想预热 `K_i` 块时，`score.cutoff` 不能大于 `K_i`；`cutoff` 调大可以覆盖全程评分，代价是预热块数与耗时增加。

### 5.2 DataSet 控制器
DataSet 是静态数据契约，不是运行时执行者：校验数据、固化块空间、探测入口、确认节点可达。

```go
type Reconciler struct {
    client.Client
    StoreFactory storage.Factory // secretRef -> objectstore.Store
    Recorder     record.EventRecorder
    Log          *slog.Logger
    Metrics      *metrics.Metrics
}
func (r *Reconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error)
```

前置条件：`chunkSize > 0`、`shards` 非空、`count > 0`、`0 < lastChunkSize <= chunkSize`、`0 <= snapshotID`、Secret 存在且含 `accessKey`/`secretKey`。

后置条件：`TotalChunks = Σ shards[i].Count`；`BlockLayout` 按 spec 顺序累计 `StartChunk`；`SnapshotID` 为解析后的具体值；`AccessibleNodes` 升序——默认选 `traincache.io/s3-access=true` 的 Node，`AccessibleNodeSelector` 非空时在该标签集合内收窄。有匹配节点时 `Condition Ready=True`；无匹配节点时置 `Condition NoAccessibleNodes=False` 并发事件，返回退避重试（节点标签可能随后补齐），WarmupTask 不得下发。

错误语义：可重试错误（存储不可达、API 冲突）返回 error，由 controller-runtime 退避；不可重试错误写 `Condition InvalidSpec/StorageUnreachable/SnapshotNotFound=False` 并返回 nil。幂等：每次 reconcile 从 spec 全量重算，不依赖上一次结果。

### 5.3 WarmupTask 控制器
WarmupTask 控制器是唯一执行者：筛节点、下发块级预热任务、收集进度算就绪度、达标后摘 Pod 的 SchedulingGate 并把分数快照暴露给 Scheduler。

```go
type Reconciler struct {
    client.Client
    Agents   agentclient.Pool
    Now      func() time.Time
    Recorder record.EventRecorder
    Log      *slog.Logger
    Metrics  *metrics.Metrics
    // K 自动计算参数，来自 TRAINCACHE_* 环境变量（§8）；零值回退包内默认值。
    CacheCapacityBytes int64
    StartupWindowBytes int64
    MaxFillFraction    float64
}
func (r *Reconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error)
func (r *Reconciler) Poll(ctx context.Context) // 定时器驱动，逐 task 拉取进度
```
两种驱动：`Reconcile` 响应 CR 变更，`Poll` 定时拉 Agent 进度。并发约定：每个 controller `MaxConcurrentReconciles = 1`，同一 WarmupTask 的 reconcile 串行。内存态仅两项：`rateHistory[taskUID+podIndex][]sample`（保留最近两次、间隔 ≥ MinInterval）与 `agentclient.Pool`；其余状态一律落 status。重启后 rateHistory 为空，门控条件②需重新积累两个采样点（§5.6）。

### 5.4 候选节点筛选
```go
func Filter(in FilterInput) ([]string, error)
type FilterInput struct { Nodes []corev1.Node; Accessible set.Set[string]; Pods []PodDetail; Policy CandidatePolicy }
```

一台 Node 要依次通过全部规则才是候选（先排除后保留）：`Ready=True` → 命中 DataSet `AccessibleNodes` → 无 `NoSchedule/NoExecute` 污点（`IgnoreNoSchedule=true` 时只排除 NoExecute）→ allocatable 减去已请求资源后满足最大 `PodDetail.Resources` → 该节点存在 Ready 的 agent Pod。返回节点名升序，作为 ReadinessTable 的列顺序；升序保证列位置稳定，排查时可用列下标定位节点。

预热阶段粗看资源的原因：预热本身消耗节点缓存与 IO，给资源已满的节点预热是浪费（数据可达性与健康口径来自 7.0 候选筛选，落点即本节与 §7.1 步骤 6）。

### 5.5 GWAA
GWAA（Greedy Weighted Allocation Algorithm）是纯分配算法：在候选节点上，给每个 Pod 挑一批预热节点。纯函数——不读 k8s、不写 status、不记 log，也不涉及门控、放行、调度与兜底；最终落点由 Scheduler 在放行后的分数快照中选择。

```go
func Compute(in Input) Placement
type Input struct {
    Pods      []PodState   // Index, K, ReadyCountByNode map[string]int32（块数）
    Nodes     []NodeState  // Name, Stopped bool
    FanoutMin int32        // 目标数量下限；0 视为 1（CRD 层已拒绝 0 与负数）
    Fanout    int32        // 目标数量上限；0 视为 1（CRD 层已拒绝 0 与负数）
    Rand      *rand.Rand   // 注入随机源；测试传固定种子，生产用时间种子
}
type Placement struct {
    TargetSet      map[int32][]string    // podIndex -> 目标节点集合，按 c_ij 降序、节点名升序
    Assignment     map[int32][]string    // podIndex -> 最终认领节点；除集合外兜底 1 个外，是 TargetSet 的子集
    PreheatSet     map[string][]int32    // nodeName -> podIndex，覆盖实际 Assignment 的配对
    Decisions      map[int32]PodDecision // podIndex -> 目标数量与异常标记
    UnassignedPods []int32
    Rounds         int
}
type PodDecision struct {
    TargetFanout        int32 // 目标数量
    LowSignal           bool  // best <= S_min，缓存分布不足以区分节点
    ForcedByMin         bool  // 下限高于保留线，强制补到目标数量
    MinUnmet            bool  // 最终实际 Assignment 少于下限（含冲突、容量、集合外兜底）
    FallbackOutOfTarget bool  // 目标集合内放不下，集合外兜底 1 个
}
```

全部按块数计算；输入若为比例，先按该 Pod 的 `K_i` 还原为块数。分配单元是普通 Pod 或亲和合并后的超 Pod：必须同节点的 Pod 先合并为超 Pod（`unitMin = max(各成员 minFanout)`，`unitMax = min(各成员 maxFanout)`，`unitMin > unitMax` 返回冲突错误），单元共享目标集合、组内共享节点。

目标数量算法（对每个分配单元独立执行）：

1. `K_i` = 该单元启动窗口的块数；`S_min = ceil(0.25 × K_i)`：最好的节点就绪不足窗口 25% 时，缓存分布无差异。
2. 可行节点按 `c_ij` 降序、节点名升序排序；`best = c_i1`。目标集合排序确定，不走随机。
3. `best <= S_min`：判低信号，`band = min(maxFanout, 可行节点数)`，置 `LowSignal=true`。
4. 否则 `band = min(maxFanout, 满足 c_ij >= 0.5 × best 的节点数)`，至少 1。0.5 是保留线：与最优节点差距过大的节点不进目标集合。
5. `target = clamp(band, minFanout, maxFanout)`，再按可行节点数封顶。
6. `minFanout > band`：置 `ForcedByMin=true`，按排序强制补到 `target` 以保留暖备份；`ForcedByMin` 只表示目标被下限抬高，不保证实际数量达到下限。
7. `minFanout > 可行节点数`：计划阶段置 `MinUnmet=true`，`target = 可行节点数`；无可行节点时目标集合为空，进 `UnassignedPods`。
8. 冲突裁决、top-up、集合外兜底全部结束后，按最终 `Assignment` 回算 `MinUnmet`：`len(Assignment[pod]) < 归一后的 min`（0 按 1 处理）为 true。
9. `Decisions[podIndex]` 记录 `TargetFanout`、`LowSignal`、`ForcedByMin`、`MinUnmet`、`FallbackOutOfTarget`。

贪心认领与冲突裁决：每个单元在目标集合内认领；节点能否放多个 Pod 由 `allowMultiPodPerNode` 与亲和约束声明（`podAffinity/podAntiAffinity` 必须同/不可同节点；`allowMultiPodPerNode=false` 一节点一 Pod，true 时同节点可放多个但须满足亲和），本模块按声明判断空位；资源余量已在粗筛（§5.4）保证。多 Pod 争同一节点且放不下时，比较 `c_ij − 次优 c_ik`，差值大者（更依赖该节点）保留，其余让步到集合内尚未认领的次优节点；并列（`c_ij` 相同或差值相同）用注入的 RNG 均匀随机决定（D32）。共享分支未启用（D33）。每轮结束后被让步单元只能改认尚未认领的目标节点；最多 `len(Pods)` 轮，仍未收敛则保留首个贪心结果并 `slog.Warn("gwaa: 未收敛，保留首个贪心结果")`。

目标集合与执行集合：`TargetSet` 表示"允许在哪里预热"，`Assignment` 是实际执行集合；除集合外兜底外 `Assignment ⊆ TargetSet`，冲突裁决与补齐只在集合内进行；集合内一个都放不下时为免完全未分配，允许集合外兜底 1 个并置 `FallbackOutOfTarget=true`（始终最多 1 个，不为补足下限把集合外节点扩成多个）；只有无任何可行节点才 unassigned。`PreheatSet` 覆盖实际 `Assignment` 的配对，未分配的目标节点不进入。冲突或容量限制让实际数量低于下限时照实写 status 并置 `MinUnmet`（条数规则见 §6.1）。

固定随机种子下可复现；不同种子下输出合法。复杂度 O(P×N×max)，max 为小常量（默认 2），P、N 几十至几百量级时为毫秒级，预热前单次计算；每轮 Poll 后的重算时机见 §7.4。

### 5.6 门控
Webhook 给 Pod 挂上门（§5.7），Controller 持续判定能不能开门。门控不在 Scheduler 的 Permit hook 上（D6，基线缺口对应 7.0 说明）。

```go
func Evaluate(in Input) Decision
type Input struct {
    Now         time.Time
    Policy      GatePolicy
    Pods        []PodGateState // Index, AssignedNodes []string, ReadyByNode map[string]int32, K, Rate, PrevRate, PrevAt, FirstSampleSeen
    FirstReadyAt time.Time     // 首个 Pod 达标的时刻，零值表示尚未出现
    StartedAt   time.Time
}
type Decision struct { State GateState; Reason string; Rates []PodRate }
```

整数门控（供放行判据与 status 记录）：

```text
required_i = floor(Threshold * K_i)
// Threshold > 0 且结果为 0 时取 1；Threshold == 0 时 required_i = 0
// 示例：K=8, Threshold=0.8 → required=6
```

判定顺序按固定优先级：

1. 条件③超时：`Now - StartedAt >= TMax` → `Degraded`（绝对上限，代表占用资源的机会成本）。
2. 条件①全达标：每个 Pod 的预热节点集合（记在 `AssignedNodes`，以实际 `Assignment` 为准）中至少有一个节点，其该 Pod 的 `ReadyByNode[node] >= required_i`；全部 Pod 满足 → `Released`。只在预热节点集合内判定，未被选为预热节点的候选节点不参与（D38）。
3. 条件②提前降级放行：`FirstReadyAt` 非零、`Now - FirstReadyAt >= MinInterval`，且每个未达标 Pod 同时满足 `Gap > GapMin` 和 `Slope < SlopeMin` → `Released`。等待价值是减少启动期回源，补齐速率低于消费速率时继续等待边际收益趋零，判据口径见 D15/D18（7.3）。
4. 都不满足 → `Hold`。

```text
gap   = gateThreshold - rate                     // 离阈值还差多少
slope = (rate_now - rate_prev) / (t_now - t_prev) // 就绪率变化速度，需上报间隔 >= min_interval
```

`Gap`/`Slope` 用连续 `Rate`（不取整），避免量化噪声；`Rate` 取集合内各节点 `Ready/K_i` 的最大值，仅供观测与条件②；`PrevAt` 为零或间隔 < MinInterval 时不参与条件②。

### 5.8 Scheduler 插件
```go
const Name = "TrainCacheScore"

type Plugin struct { handle framework.Handle; log *slog.Logger; ttl time.Duration }
var _ framework.ScorePlugin = (*Plugin)(nil)

func New(ctx context.Context, obj runtime.Object, h framework.Handle) (framework.Plugin, error)
func (p *Plugin) Name() string
func (p *Plugin) Score(ctx context.Context, state *framework.CycleState, pod *v1.Pod, nodeInfo *framework.NodeInfo) (int64, *framework.Status)
func (p *Plugin) NormalizeScore(ctx context.Context, state *framework.CycleState, pod *v1.Pod, scores framework.NodeScoreList) *framework.Status
```

插件只有一件事：给"Pod 该不该落到这台 Node"打 0~100 分，分数来自 Controller 放行时写入的 Node annotation（§6.2）。

`Score` 经 `nodeInfo.Node().Name` 取节点名（v0.37 的 Score 签名直接传 `*framework.NodeInfo`，不再传节点名字符串）。逻辑：读 Pod annotation `traincache.io/warmup-task`（值 `<ns>/<name>`）与 `traincache.io/pod-index`（十进制 `<i>`）→ `scorefmt.Key(ns, name)` 算出 Node annotation 键（§6.2，即 D27 的 `scores-<namePrefix32>-<hash12>`）→ 读该键 JSON 的 `p["<i>"]` → 未过期返回该分数。键缺失、条目缺失、`pod-index` 缺失、JSON 损坏、`task` 与 Pod 注解不匹配、超 TTL，一律返回 0 + nil status；任何错误都不得让 Pod 因插件失败被拒绝调度。

`NormalizeScore` 的映射公式：

```text
score' = round(score * 100 / max(1, maxScore))    // 全 0 时全部返回 0
```

`KubeSchedulerConfiguration` 只启用 `score` 扩展点（weight 由配置决定）；v1 没有 `normalizeScore` 配置字段（strict decoding 会拒绝），插件实现 `ScoreExtensions` 后 framework 在 score 阶段后自动调用 `NormalizeScore`，无需也不能单独启用。

### 5.9 Agent gRPC 客户端
Controller 是 Agent gRPC 的客户端，扩展 `agent/api/agent.proto` 的 `PreheatService`（增量见 §12.1 与 `docs/6.1 design.md` 附录 A；Controller 只使用增量后的消息，不自定义传输格式）：

```go
type Pool interface {
    Submit(ctx context.Context, node string, req *agentpb.SubmitPreheatRequest) error
    Update(ctx context.Context, node string, req *agentpb.UpdatePreheatRequest) error
    Cancel(ctx context.Context, node string, req *agentpb.CancelPreheatRequest) error
```

- `Progress` 复用 `GetPreheatStatus`，返回 `{Generation,Seq,ReadyBitmap,Completed,Failed,State,UpdatedAt,Total}`；不新增 `GetPreheatProgress`。
- 节点地址解析：列出 `app=traincache-agentd` 且 `spec.nodeName` 匹配的 Pod，取 `status.podIP:CONTROLLER_AGENT_PORT`；结果缓存 30s。

## 6. 数据格式
字节层面的约定：字段顺序不影响 JSON 解析，字段名、类型、默认值不得改。

### 6.1 CRD 状态布局
`ReadinessTable` 行下标 = `PodDetail.Index`，列下标 = `CandidateNodes` 顺序；值 = 该 Pod 在该节点启动窗口内"已落盘且校验通过"的块数，范围 `0..K_i`（每 Pod 用自己的 K）。候选节点粒度的就绪块数只由 `ReadinessTable` 承载。

`PodNodeReadiness` 按 `(PodDetail.Index, 预热节点)` 展开，条数 = 该 Pod 实际 `Assignment` 的节点数：正常在 `[preheatFanoutMin, preheatFanout]` 内，冲突、容量不足或集合外兜底可低于下限（`MinUnmet=true`，条数照实），任何情况不超过 `preheatFanout`，总条数 ≤ P×preheatFanout；无可行节点的 Pod 只写一条 `NodeName` 为空的汇总记录，`State` 取该 Pod 的汇总态。每条的位图、就绪数、速率与 `LastReportTime` 取该预热节点最近一次上报；`ActualNode` 同一 Pod 各条同值。比例一律现算：`Rate = ReadyInWindow / K_i`，`RequiredReady` 按 §5.6 整数公式按 Pod 算出后写入各条。体积：P≤64、N≤256、preheatFanout 典型 2 时序列化 < 1 MiB（M13 重新实测，数值记录见 7.2）。

### 6.2 Node annotation
每 WarmupTask 一个独立键，完整键 `<prefix>-<namePrefix>-<hash12>`，`<prefix>` 默认 `traincache.io/scores`（§8）。编码函数（输出注解键，Controller 与 Scheduler 用同一实现）：

```go
func Key(ns, name string) string
// namePrefix = strings.TrimRight(name[:min(len(name),32)], "-.")
// hash12     = sha256(ns + "/" + name) 的前 12 位小写十六进制
// prefix     = 配置项（默认 traincache.io/scores），Controller/Scheduler 取值一致
// return prefix + "-" + namePrefix + "-" + hash12
```

键名部分（`scores-` + ≤32 + `-` + 12）≤ 52 字符，满足 63 上限。

值为单行 JSON，UTF-8，无换行：

```json
{"v":1,"task":"default/train-1","g":12,"t":"2026-10-20T08:00:00Z","p":{"0":87,"1":73}}
```

| 字段 | 含义 |
|---|---|
| `v` | 格式版本，当前 1 |
| `task` | `<namespace>/<name>`，写入时校验与键的 hash 一致 |
| `g` | 写入时的 WarmupTask `generation` |
| `t` | RFC3339 UTC 写入时刻；超过 `CONTROLLER_SCORE_TTL` 视为过期 |
| `p` | 键为 podIndex 十进制字符串，值为 0~100 整数分数 |

每个 task 只读改写自己的键，多 task 共节点互不影响；一次 reconcile 内冲突时重读重试最多 5 次，不删除其他 task 的键。Scheduler 由 Pod annotation `traincache.io/warmup-task` 计算同一键，取分失败一律 0（分支枚举见 §5.8）。

固定小写 snake_case，禁止混用：`component`、`dataset`、`warmup_task`、`task_id`、`pod`、`pod_index`、`node`、`generation`、`seq`、`annotation_key`、`consume_order_source`、`phase`、`fanout`、`fanout_min`、`fanout_max`、`fanout_target`、`fanout_actual`、`low_signal`、`forced_by_min`、`min_unmet`、`fallback_out_of_target`、`prune_reason`、`warm_node_count`、`status_entries`、`state`、`reason`、`duration_ms`、`err`。不记录 Secret 内容、access key、完整对象路径（Info 级）；块级明细只在 Debug 级。

## 7. 关键流程
### 7.1 DataSet 校验与块布局
reconcile 七步，先读、再校验、再探测、最后写 status：

1. 读取 DataSet；`deletionTimestamp` 非空则直接返回。
2. 校验 spec 字段（§5.2 前置条件）；失败写 `InvalidSpec=False` + `Event` 记录原因，返回 nil。
3. 解析 Secret，构造 `objectstore.Store`；失败写 `StorageUnreachable=False`，返回 error 退避重试。
4. `snapshotID` 为空时读 `CURRENT` 解析具体快照；读 manifest 并校验 `snapshot_id` 一致、`shards` 非空。
5. 按 spec `Shards` 顺序累计 `StartChunk`，生成 `BlockLayout` 与 `TotalChunks`——全局块号在这里只固化一次，后续预热与门控都按全局块号。
6. 解析可达节点（§5.2 后置条件）；无匹配节点停止下发；标签只读。
7. 写 status（带 `ObservedGeneration`）；`Event` 提示引用它的 WarmupTask（spec 变化时通知所有引用者，DataSet 不记录被谁引用）。

### 7.2 候选节点筛选与预热下发
WarmupTask reconcile 前六步：

1. 读取 WarmupTask 与 DataSet；DataSet 非 `Ready` 时写 `Condition DataSetNotReady` 并返回。
2. 校验 `PodDetail.Index` 覆盖 `0..PodCount-1` 且不重复。解析消费清单：任一 Pod 的 `InitialConsumeFiles` 为空、含未知分片名，或全组内同一分片出现多次、全部 Pod 合起来未覆盖全部分片时，忽略全部用户值，按默认切分 `T=totalChunks`、Pod i 取 `[floor(i*T/P), floor((i+1)*T/P))` 升序，置 `ConsumeOrderSource=Default` 并发 `ConsumeOrderDefaulted` 事件；否则 `Spec`，每个 Pod 的块序为所列分片按列出顺序展开的全局块号。清单没有追加语义：本 Pod 的分片必须一次列全，只列前几个按非法处理。`totalChunks < podCount` 时不存在合法的默认切分，置 `Condition InvalidSpec=False` 并拒绝，不回退。随后按 §5.1.1 算出每个 Pod 的 `W_i` 与 `K_i`；显式 `K > W_i` 置 `InvalidSpec=False` 并拒绝，不截断。K 省略（0）时，把算出的 K patch 回 `spec.podDetails[].k`，发 `KDefaulted` 事件并立即 `Requeue` 结束本轮，下一轮从 API server 读取持久化值。`cacheCapacityBytes > 0` 时，全部 Pod 实际请求块数（`min(max(K_i, score.cutoff), W_i)`）合计超过 `cacheCapacityBytes × maxFillFraction` 只发 Warning `KExceedsFillLimit`，任务继续执行。
3. 列出 `TargetRef` 匹配的 Pod 与 Node；Pod 集合与 `PodCount` 不一致时只置 `Condition PodSetMismatch`，继续使用已有 Pod，不创建/重建/扩缩容。
4. 执行 `Filter`（§5.4）；DataSet 无可达节点时写 `NoAccessibleNodes` 并停止下发；结果为空写 `NoCandidates`，返回退避（节点状态可能变化）。
5. 对每个 `(pod,node)` 调 `Submit`（`task_id` 见 §5.9；`chunks` 为该 Pod 消费顺序前 `min(max(K_i, Cutoff), W_i)` 块）。发送失败记 `ErrAgentUnavailable`，节点标记 `Stopped` 下一轮重试；永久拒绝写 `Condition PreheatRejected=False`（reason=`AgentRejected`）发 Warning 事件，该节点不再重试（§7.9）。
6. 进入 `Preheating`，写 `CandidateNodes`、`StartedAt`（仅首次）。

### 7.3 进度拉取与就绪表
`Poll` 把 Agent 原始位图翻译成 Controller 侧状态表：

1. 每 `CONTROLLER_POLL_INTERVAL` 遍历所有 `Preheating/Gating` 的 task。
2. 对实际 `Assignment` 的每个 `(pod,node)` 调 `Progress`（内部 `GetPreheatStatus`）；位图按该配对请求的 `chunks` 顺序解码。
3. `ReadyInWindow = popcount(前 K_i 位)`；`RequiredReady` 按 §5.6 整数公式；`GlobalDecayScore` 按 §7.6 用该 Pod 的 `K_i` 与前 `C` 位计算。
4. 更新 `ReadinessTable[p][n]` 与该 Pod 各预热节点的 `PodNodeReadiness` 条目；`LastReportTime` 用 `UpdatedAt`，缺失时用本地时钟。
5. 低于当前 generation 的响应丢弃并记 Debug；同 generation 下 `Seq` 小于已记录值也丢弃。连续 3 次 `ErrAgentUnavailable` 将对应预热节点条目置 `Failed`——仅影响门控条件②的斜率计算，不阻塞超时降级。

### 7.4 GWAA 分配
输入为 `ReadinessTable`、已停止节点集合、`spec.preheatFanoutMin` 与 `spec.preheatFanout`；每轮 Poll 后重算。GWAA 按 §5.5 算出目标集合与实际 `Assignment`，不决定最终落点。分配变化时按差异调用：新增配对 `Submit`/`Update`，移除配对 `Cancel`，未变化配对不重复调用；被清理节点记 `prune_reason`（`out_of_target`、`low_signal`、`target_shrink`）。结果只写 status，不写 Node。

### 7.5 门控与放行
1. 组装 `PodGateState`：`AssignedNodes` 取该 Pod 实际预热节点集合（以 `Assignment` 为准），`ReadyByNode` 取各预热节点窗口就绪数，`Rate` 取集合内 `ReadyByNode[node]/K_i` 最大值；`FirstReadyAt` 取自 `Conditions` 中类型 `FirstReady` 的 `LastTransitionTime`——首次出现任一 Pod 在任一预热节点上达标时写入，之后不再更新。
2. `Evaluate`（§5.6）返回 `Hold`：不写 Node、不摘 Gate，`RequeueAfter = PollInterval`。
3. `Released`/`Degraded` 时，一次 reconcile 内完成三件事：
   a. 对每个预热节点，计算在本节点预热的本 task 各 Pod 的 `S(node)`（各 Pod 用各自 `K_i`），覆盖实际 `Assignment` 的 P×actual 配对；写本 task 自己的 Node annotation 键（§6.2），只读改写该键。放行之后继续回填的预热不算入分数——快照就此冻结，generation 不变则不再改写本 task 的 annotation。
   b. 逐个 Pod patch 移除 `traincache.io/warmup` gate（已移除则跳过）。
   c. 写 `GateDecision{State,Reason,DecidedAt,PodRates}` 与 `Phase=Released/Degraded`。
4. a 失败则整体重试、不摘 Gate；b 部分失败时已摘 Pod 不回滚，下一轮继续摘剩余 Pod（幂等）。

### 7.6 评分计算
按 `(pod,node)` 计算，使用该 Pod 的 `K_i`。S 是"窗口内加权就绪比例"，供 Scheduler 打分调权（对消费顺序位置 i，0 起）：

```text
w(i) = 1,                        i < min(K_i, C)
w(i) = 0.5^((i - K_i) / H),      K_i <= i < C
w(i) = 0,                        i >= C
S    = round(100 * Σ(w(i)*ready(i)) / Σw(i))    // Σw(i)=0 时 S=0
```

窗口内的块决定启动速度，给满权重；窗口外按半衰期衰减（每过 H 块权重减半），超过 C 不计。位图缺失的位按 0 计；`K_i >= C` 时平台段截到 C，无衰减段。status 中窗口内就绪度（`StartupWindowReady`）与全局衰减得分（`GlobalDecayScore`）分开记录，对应 8.0 的"窗口内外分开存储"。

### 7.7 调度
Scheduler 收到 `(Pod, Node)`：读 Pod 注解 `warmup-task` + `pod-index` → `scorefmt.Key(ns,name)` → 读 Node 上该键的 `p[podIndex]` 返回 `Score`，再由 `NormalizeScore` 归一化；任何读取失败给 0（§5.8）。算分在 Controller 放行时已完成，插件只查表取分。

### 7.8 落点兜底
分数只是调度偏好，不是硬约束，Pod 可能落在暖节点集合之外。Controller 监听 Pod 的 `spec.nodeName`：落在实际预热节点集合内时，只回填 `ActualNode` 到各条 `PodNodeReadiness`；落在集合外时写各条 `ActualNode`、发 `Event NodeDeviation`、对实际节点 `Submit` 同一 Pod 的窗口（优先级 P0），不取消原有预热节点，也不重新门控（Pod 已放行）。兜底失败只影响该 Pod 读路径命中率，由 Agent 回源兜底。

### 7.9 异常与降级
| 场景 | 行为 |
|---|---|
| Agent 不可达 | 节点标记 Stopped，退避重试；全部不可达且 `t >= TMax` → `Degraded` 放行 |
| Agent 永久拒绝 | `InvalidArgument/FailedPrecondition` 映射 `ErrPermanent`：写 `Condition PreheatRejected=False`（reason=`AgentRejected`）发 Warning 事件；该节点不再重试，其余继续；全部候选被拒时不推进门控，仍由 `TMax` 兜底降级 |
| DataSet 失效 | WarmupTask 停止下发，`Condition DataSetNotReady`，不推进门控 |
| 可达节点为空 | `Condition NoAccessibleNodes`，停止下发；已有任务可 `Cancel`，门控仍受 `TMax` 降级约束 |
| Pod 集合与 `podCount` 不一致 | 只置 `Condition PodSetMismatch`，不创建/重建/扩缩容，继续使用现有 Pod |
| 消费清单非法 | 任一分片未知、同一分片在全组内重复，或全部 Pod 未恰好覆盖全部分片时，忽略全部用户值，按默认均分并发 `ConsumeOrderDefaulted`；`T < P` 属规格错误，`Condition InvalidSpec=False` 并拒绝，不进入回退 |
| 显式 K 超过 W_i | `Condition InvalidSpec=False` 并拒绝；不截断、不钳制 |
| 实际请求块数合计超过填充上限 | `cacheCapacityBytes > 0` 时只发 Warning `KExceedsFillLimit`，任务照常执行；超出缓存预算的块由回源承担 |
| Webhook 未注入 | `Condition GateInjectionDegraded`，不阻塞其他 Pod；该 Pod 无 gate，直接调度 |
| Node annotation 写失败 | 不摘 Gate，退避重试（只重写本 task 的键） |
| Controller 重启 | 全部状态从 CRD/Node annotation 重建；rateHistory 丢失，条件②重新积累 |
| 重复 reconcile | 全量重算 + 幂等 patch；Submit/Cancel 幂等键保证不重复建任务 |

所有降级最终由 `TMax` 超时放行兜底，任务不会永远卡在 Hold。

### 7.10 初始化与配置加载
`cmd/controller-manager`：`config.Load()` → `logging.New()` → `metrics.New()` → `ctrl.NewManager` → 注册两个 Reconciler 与 Poll ticker → leader election（可选）→ `signal.NotifyContext(SIGINT,SIGTERM)` → `mgr.Start`。`cmd/webhook` 独立进程加载同一 `config`，只启动 webhook server。`cmd/scheduler` 走 kube-scheduler 的 `app.WithPlugin` 注册。

## 9. 日志与可观测性设计
### 9.1 硬性要求
> 新模块核心代码的每个关键位置必须记录结构化日志，并随对应里程碑一起验收；没有日志断言测试的里程碑不判通过（7.3 D21）。日志不得改变业务逻辑、接口、数据格式与运行行为。

### 9.2 基础设施
- 日志库：标准库 `log/slog`，`JSONHandler(os.Stderr)`，与 agent 一致；`cmd/*/main.go` 各初始化一次，不引入第三方。
- `internal/logging` 只有三个函数：`New(level) *slog.Logger`、`Into(ctx, l) context.Context`、`From(ctx) *slog.Logger`（缺失时返回 `slog.Default()`）。
- 每个 reconcile/HTTP 请求生成 `request_id`（`<uid>/<generation>/<unixnano>`）放入 context 与所有日志；无分布式 traceId，跨进程关联用 `task_id + node + generation`。
- 级别：Info = 状态迁移、放行、筛选结果、任务完成；Warn = 降级、重试、跳过、未收敛；Error = reconcile 返回 error、RPC 永久失败；Debug = 逐块/逐节点评分明细，默认关闭。
- 脱敏：禁止记录 Secret 内容、accessKey/secretKey、完整凭据 URL；`path`/`chunk`/`fp` 等高基数维度只进 Debug，Info 聚合到 dataset/task 维度；日志调用不得在锁内做格式化之外的 I/O，`From(ctx)` 缺失时退化为全局 logger，不 panic。

### 9.5 指标（Prometheus，独立 Registry）
controller-manager 使用独立 Registry，经 `metricsserver.Options.ExtraHandlers` 暴露在 `/metrics/traincache`（内置 `/metrics` 仍归 controller-runtime）；scheduler 独立进程，自建 Registry 并在 `CONTROLLER_METRICS_ADDR` 暴露同一路径。标签值必须来自固定枚举，禁止 `err.Error()`、Pod/Node/task 名、UID 等无界值（7.3 D35）。标签集合共 11 个 family：

| Family | 类型 | 标签 | 发射点 / 语义 |
|---|---|---|---|
| `traincache_controller_reconcile_total` | Counter | `controller` ∈ `dataset\|warmup\|warmup-degraded`；`result` ∈ `success\|error\|requeue` | 每个 Reconcile 退出时 +1；err≠nil → error，否则 RequeueAfter>0 → requeue，否则 success |
| `traincache_controller_reconcile_duration_seconds` | Histogram | `controller` | defer 覆盖所有返回路径（含 NotFound/DeletionTimestamp） |
| `traincache_controller_candidate_nodes` | Histogram | `dataset` = `<namespace>/<name>` | 候选节点筛选完成后观测 `len(candidates)` |
| `traincache_controller_preheat_rpc_total` | Counter | `op` ∈ `submit\|update\|cancel`；`result` ∈ `ok\|permanent\|unavailable` | 每次 Agent RPC 调用点 +1；`permanent` 对应 `ErrPermanent`，其余失败归 `unavailable` |
| `traincache_controller_gate_tasks` | Gauge | `state` ∈ `hold\|released\|degraded` | 首次门控评估起 Inc/Dec；任务删除或进入终态时 Dec，重复状态不重复计数 |
| `traincache_controller_gate_hold_duration_seconds` | Histogram | 无 | 仅在离开 Hold（Released/Degraded）时观测一次 |
| `traincache_controller_agent_poll_total` | Counter | `result` ∈ `ok\|unavailable\|stale\|error` | 每次 `GetPreheatStatus` 轮询 +1；generation/seq 回退被丢弃记 `stale`，响应解析失败记 `error` |
| `traincache_controller_pods_per_node` | Histogram | 无 | 每次 GWAA 计算后对 `PreheatSet` 每个 node 观测 `len(pods)`；按预热配对计数，fanout 接线后该值可大于 1 |
| `traincache_controller_gwaa_unassigned_pods` | Gauge | `dataset` | 每次 GWAA 计算后 Set 为 `len(UnassignedPods)` |
| `traincache_controller_gwaa_fallback_total` | Counter | 无 | GWAA 不收敛、回退到首个贪心结果时 +1 |
| `traincache_scheduler_score_total` | Counter | `result` ∈ `ok\|no_task_ref\|invalid_task_ref\|no_pod_index\|invalid_pod_index\|no_annotation\|invalid_value\|task_mismatch\|stale_generation\|expired\|no_pod_entry` | scheduler 进程 `Evaluate` 的固定分支枚举 |

### 9.6 排查路径
门控不放行 → `GateDecision.PodRates` 与 `PodNodeReadiness` → `controller_preheat_rpc_total` → Agent `GetPreheatStatus`（`generation/seq/ready_bitmap`）→ Agent 自身指标。落点偏离 → Pod 的 `ActualNode` 与 `NodeDeviation` 事件。

## 10. 风险与约束
- **R1 调度器依赖重量级**：自定义 kube-scheduler 镜像引入 `k8s.io/kubernetes`（或等价 framework runtime），版本必须与集群 minor 对齐，否则插件 ABI 不兼容（结案口径见 7.3 Q1）。
- **R2 Webhook 是关键路径**：未注入 gate 时门控失效但不阻塞训练；`failurePolicy=Ignore` 是有意选择，代价是静默降级，由 `GateInjectionDegraded` 条件兜底。
- **R3 workspace 依赖**：跨 module import 依赖 `go.work`，`GOWORK=off` 构建失败；与现有 agent→core 做法一致，不引入 replace。
- **R4 CRD status 体积**：`ReadinessTable` 随 P×N 增长，`PodNodeReadiness` 随 P×K 增长（K ≤ `preheatFanout`）；需在上限（P≤64、N≤256、K 小常量）内测试，超出时改为只存表不存明细。
- **R5 内存态丢失**：rateHistory 随重启清空，条件②重启后重新积累，可能推迟放行，但不会错误放行。
- **R6 Agent 增量依赖**：Controller 依赖 7.x 新增 RPC；集成测试用 fake server。
- **R7 时钟**：所有时间比较使用 `r.Now()` 注入的同一时钟；CRD 时间字段统一 UTC RFC3339。

## 11. 验收标准（总闸）
14 条全过才算完成；分里程碑的判据与命令见 8.2。8.0 的过关标准——DataSet + WarmupTask 提交 → 选出节点 → 持续预取/阶段切换重预取的完整训练流程可运行——其中控制面闭环由第 1 条与 7.2 M11 端到端验证，阶段切换重预取在 Agent 侧（本文 §1.1）。

1. `cd controller && go build ./... && go vet ./... && go test ./... -race -count=1` 全绿，gofmt 干净。
2. 两个 CRD 可由 `controller-gen` 从类型重新生成，产物与提交一致；只开 `status`、无 `scale`；`podCount`/`dataSetRef` CEL 不可变校验生效；Controller 不创建 Job/Pod。
3. 8.0 基线需求 D1–D8 每条在代码中有唯一落点，且 8.3 有对应 D 编号。
4. DataSet 校验（规格见 §5.2/§7.1）逐项测：字段非法、Secret 缺失、快照不存在、blockLayout 累计正确、`s3-access` 解析、selector 收窄、无匹配时 `NoAccessibleNodes` 且停止下发。
5. 门控边界按 §5.6 逐条测：required 整数化与 0/1 钳制、存在量词集合取实际 `Assignment`、条件②连续 rate、观测字段不参与判定、TMax 与全达标两种必放行。
6. GWAA 五情形均有测试（§5.5）：冲突、并列（含随机回退）、不收敛（保留首个贪心结果）、集合外兜底、无可行节点；固定种子可复现；status 条数 = 实际 `Assignment`、可低于 min（`MinUnmet`）但不超 max；除兜底外 `Assignment ⊆ TargetSet`。
7. Node annotation 编解码（§6.2）往返测：截断去尾、hash 稳定、键名 ≤ 52；两 task 共节点互不影响；过期/缺失/损坏/`task` 不匹配时 Scheduler 返回 0 且不拒绝调度。

10. 每个里程碑的日志点有断言测试（至少一条 slog 捕获），覆盖 §6.5 字段中的 `annotation_key`、`generation`、`seq`、`consume_order_source`，M14 起再加九个 fanout 字段。

## 12. 跨模块增量
### 12.1 Agent proto 增量（并入 7.1 附录 A）
`agent/api/agent.proto` 在现有 `traincache.agent.v1.PreheatService` 上做最小增量（进度复用 `GetPreheatStatus`）：

```proto
// 8.x 增量：在现有 traincache.agent.v1.PreheatService 上最小增量扩展。
// 进度查询复用 GetPreheatStatus；不新增 GetPreheatProgress。

message SubmitPreheatRequest {
  // 字段 1..7 保持现状
  uint64 generation = 8;  // 任务代际；0 表示未提供
}
message PreheatStatus {
  // 字段 1..11 保持现状
  uint64 generation = 12;   // 任务代际
  uint64 seq = 13;          // 位图变更序号，单调递增
  bytes ready_bitmap = 14;  // 位 i 对应请求 chunks 第 i 项；1=已落盘且校验通过
}
message UpdatePreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;         // 必须 >= Agent 当前代际
  repeated ChunkRef chunks = 4;  // 新的完整块列表，同时定义位序
  PreheatPriority priority = 5;
}
message UpdatePreheatResponse {
  bool accepted = 1;
  string message = 2;
}
message CancelPreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;
}
message CancelPreheatResponse {
  bool accepted = 1;
}
service PreheatService {
  // 已有
  rpc SubmitPreheat(SubmitPreheatRequest) returns (SubmitPreheatResponse);
  rpc GetPreheatStatus(GetPreheatStatusRequest) returns (PreheatStatus);
  // 新增
  rpc UpdatePreheat(UpdatePreheatRequest) returns (UpdatePreheatResponse);
  rpc CancelPreheat(CancelPreheatRequest) returns (CancelPreheatResponse);
}
```

`SubmitPreheatRequest.snapshot_id`（字段 4）恒为空：Controller 不得把 DataSet status 中解析出的具体快照 ID 下发，Submit 与 Update 两条路径均空（`UpdatePreheatRequest` 本身无该字段）。Agent 自行跟随 CURRENT 并按需加载 manifest 分片，避免任务键随快照推进漂移；非空值在 7.x M3 Agent 侧返回 `InvalidArgument`（7.3 D34）。

语义：`task_id` 幂等；Agent 对低于已接受 `generation` 的请求返回 `FailedPrecondition`；`Cancel` 后同名同 generation 再 `Submit` 视为新任务；位图长度必须恰好 `ceil(len(chunks)/8)`，位序由请求 `chunks` 定义；`ReportBlocks` 保持 `Unimplemented`，8.x 不使用推送模型。
