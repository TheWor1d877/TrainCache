# Agent 服务化设计(design)

> 本文档是 `docs/7.0 Agent服务化.md` 的下游设计文档,与核心库三件套(6.1 design / 6.2 plan / 6.3 decisions)平行。
> §5 接口签名与 §6 数据格式为冻结约定,实现子代理不得私改;发现问题回传 `BLOCKED`,由主对话裁决后更新本文档与 docs/decisions.md。

## 1. 定位

把核心库(core/,无服务形态 Go 库)包装为节点常驻服务,以 K8s DaemonSet 部署,每缓存节点一个实例,以节点为服务边界。

- 对外:gRPC(预热任务接收、块级任务上报、节点状态查询)+ Prometheus `/metrics`。
- 对内:调用 core 完成索引、下载、落盘、校验、回收;服务化层不重复实现其中任何一项。
- 训练 Pod 经 hostPath 只读挂载直读 CAS 块,读路径不经过 Agent(沿用 preheat 模型)。
- 自治:训练中持续预取、阶段切换重预取、重启重扫描、坏块修复、热度统计,均无需 Controller 在场。

非目标:

- 不是 Controller(筛选/门控/打分调度逻辑不在本设计);
- 不做读路径内联(FUSE read-through 是可选 stretch,本设计不含);
- 不做分布式缓存组(多节点协作留待后续文档);
- 不实现 Python DataLoader 钩子本体(仅冻结其与 Agent 的 socket 协议;钩子工程形态见 decisions Q10)。

## 3. 总体架构与依赖方向

部署拓扑(单节点视角):

```
┌─ control plane(未来)──────────────┐        ┌─ 训练 Pod ───────────────────────────┐
│ Controller                        │        │ DataLoader(钩子)                     │
└──────────┬────────────────────────┘        │  │ 位点/打开块(Unix Socket,§5.4)     │
           │ gRPC 南向(§5.1)                 │  ▼                                   │
┌──────────▼──────────────────────────┐      │ Agent(同节点)                        │
│ Agent DaemonSet Pod                 │      │  ordersrc sidecar(Python)            │
│  svc(gRPC + 生命周期 + 装配)        │      │    按 Job 配置重算 ConsumeOrder      │
│   ├─ prefetch(四优先级预取)         │ ◄────┼─── 共享内存 ring(§6.2)               │
│   ├─ ordersource(读 ring)           │      │                                      │
│   ├─ collector(inotify 旁路采集)    │      └──── 直读:hostPath 只读挂载           │
│   ├─ rescan(重扫 / 修复)            │      │   /var/cache/traincache/blocks/      │
│   └─ metrics / nodeid               │      ────────────────────────────────────────                                  
└───────┬─────────────────────────────┘                                            
        │ core 库(cas / fetch / index / objectstore)                                
        ▼                                                                          
   数据源(MinIO / 本地源站)                                                          
```

数据面:训练进程只读 hostPath 直接读块,读路径仍不经过 Agent;读 miss 经钩子 `read_miss` 上报,由 Agent 异步执行 demand 按需补块(§5.4、§7.5)。

进程模型:三个可执行产物——

- `traincache-agentd`:DaemonSet 常驻服务(本设计主体);
- `traincache-ordersrc`:训练 Pod 内 sidecar(Python,按 Job 配置计算每阶段消费顺序并写共享内存;顺序语义必须与真实 loader 一致,见 decisions D3);
- `traincache`:CLI(gRPC 客户端)。

依赖方向(单向无环):

```
cmd/{agentd,traincache}  →  svc  →  prefetch, collector, rescan, metrics, nodeid, ordersource  →  core
ordersrc(独立小进程,不依赖 core)        api(proto 生成,仅被 svc / cmd / ordersource 引用)
```

- `svc` 是装配层:起服务、读配置、接探针,持有各子模块实例;
- 子模块之间互不依赖,数据经 `svc` 编排(与 core"index 不依赖 fetch"同风格);
- `ordersource` 只读共享内存,不依赖 core。

## 5. 核心接口(冻结约定)

### 5.1 gRPC(api/agent.proto)

```proto
syntax = "proto3";
package traincache.agent.v1;
option go_package = "traincache/agent/api/agentpb";

// 南向:Controller/CLI → Agent(7.0 验收 1/4/5)
service PreheatService {
  rpc SubmitPreheat(SubmitPreheatRequest) returns (SubmitPreheatResponse);
  rpc GetPreheatStatus(GetPreheatStatusRequest) returns (PreheatStatus);
}

// 节点状态查询(CLI 与就绪探针)
service NodeService {
  rpc GetNodeStatus(GetNodeStatusRequest) returns (NodeStatus);
  rpc ListSnapshot(ListSnapshotRequest) returns (ListSnapshotResponse);
}

// 北向:Agent → Controller,块级任务上报。
// proto 随本设计冻结,服务端实现推迟至 Controller 里程碑(decisions Q1)。
service ReportService {
  rpc ReportBlocks(stream BlockReport) returns (ReportAck);
}
```

消息(字段名冻结):

| 消息 | 字段 |
|---|---|
| `SubmitPreheatRequest` | `task_id string`(幂等键);`node string`(须等于本节点);`dataset string`;`snapshot_id string`(空=当前 CURRENT);`prefixes []string`(路径前缀,语义同 core `Catalog.LoadPrefixes`:空=空映射,含空串=全量);`chunks []ChunkRef`(可选,块级精确指定);`priority PreheatPriority` |
| `ChunkRef` | `path string`;`chunk int64`(core Entry 寻址) |
| `PreheatPriority` | 枚举 `P0=显式启动预取 / P1=阶段切换重预取 / P2=邻域预取 / P3=后台补全`(默认 P0) |
| `SubmitPreheatResponse` | `accepted bool`;`task_id string`;`message string` |
| `GetPreheatStatusRequest` | `task_id string` |
| `PreheatStatus` | `task_id`;`node`;`dataset`;`snapshot_id`;`paths []string`;`state`(枚举 `QUEUED / RUNNING / DONE / ERROR`);`total_blocks int64`;`completed_blocks int64`;`failed_blocks int64`;`started_at`、`updated_at`(google.protobuf.Timestamp) |
| `GetNodeStatusRequest` | `node string`;`item NodeStatusItem`(枚举:全量 / agent / catalog / space / tasks / rescan) |
| `NodeStatus` | `node`;`agent_ok bool`;`cache_root string`;`cached_bytes int64`;`free_bytes int64`;`running_tasks int64`;`rescan RescanStatus`;`catalog []DatasetCatalog` |
| `RescanStatus` | `phase`(枚举 `SAMPLING / FULL_SCAN / DONE`);`sampled int64`;`verified int64`;`quarantined int64`;`repair_queue int64` |
| `DatasetCatalog` | `dataset string`;`snapshot_id string`;`shards int64`;`entries int64` |
| `ListSnapshotRequest` | `dataset string`;`snapshot_id string`(空=CURRENT);`prefix string` |
| `ListSnapshotResponse` | `entries []EntryRef`(`path`;`chunk`;`size`) |
| `BlockReport` | `node`;`task_id`;`ref ChunkRef`;`fp string`;`bytes int64`;`result`(枚举 `OK / CORRUPT / REFETCHED`) |
| `ReportAck` | 空 |

错误语义:任务校验失败(节点不符、dataset 不存在)→ `InvalidArgument`;同 `task_id` 内容不同 → `AlreadyExists`;同 `task_id` 内容相同 → 幂等返回现有任务。RPC 一律带 context 超时(Agent 侧默认 10s);长时间任务经 `GetPreheatStatus` 轮询,不做长连接流。

### 5.2 PersistentPrefetcher(prefetch 包)

```go
type PersistentPrefetcher struct{ /* ... */ }
func New(cat *index.Catalog, f *fetch.Fetcher, cs *cas.Store,
         m *metrics.Registry, cfg Config) *PersistentPrefetcher

type Config struct {
    Lookahead int // 邻域预取提前量,默认 8(≤0 取默认;D16)
    // OnP0Done:P0 块完成回调(ref=块引用,err=该块结果;err==nil 表示就绪或下载成功),
    // 在调度协程内同步调用,不得阻塞;nil 表示无回调(仅 P0 触发)。
    OnP0Done func(ref ChunkRef, err error)
}

// 开始持续预取:从 cursor 起按当前 ConsumeOrder 邻域预取,每完成一块推进 cursor 并上报 /metrics。
// 可被显式启动预取(P0)与阶段切换重预取(P1)打断:在途请求不取消,新请求按更高优先级入队。
func (p *PersistentPrefetcher) Start(ctx context.Context)

// DataLoader 钩子每消费完一块调用,推进 cursor;预取提前量 = cursor + lookahead(默认 8)。
func (p *PersistentPrefetcher) OnConsumeSideAdvance(ctx context.Context, ref ChunkRef) error

// 阶段切换:旧阶段 cursor 之后未消费块降级 P3(在途请求不取消);
// 新阶段开头 K 块(K = 新 ConsumeOrder.prefetch_chunks)作为 P1 高优先级入队,剩余块转 P2 邻域预取;
// 返回"切换时刻到新窗口就绪"的预估时间,供 Agent 上报 traincache_stage_switch_eta_seconds。
func (p *PersistentPrefetcher) OnStageSwitch(ctx context.Context, next ConsumeOrder) (eta time.Duration, err error)

// 显式启动预取(P0)入队:refs 按顺序以 P0 严格最高优先级入队,在途不取消;
// 每块完成(就绪或下载成败)经 Config.OnP0Done 回调(若有)。空列表返回 nil。
// 去重(D45):以 blockKey(dataset,ChunkRef)=<dataset>/blocks/<path>#<chunk>(与 fetch key 一致)维护 pending 表;
// 键已存在且 task 未开始 → 按最高优先级提升(不新建 task);已在运行 → 忽略。
func (p *PersistentPrefetcher) EnqueueP0(ctx context.Context, refs []ChunkRef) error

type Status struct {
    Stage            string   // 当前阶段标识
    Cursor           ChunkRef // 纯消费位点:仅由 advance/inotify 推进
    PrefetchFrontier ChunkRef // 预取前沿:已就绪的最远块(不要求连续)
    QueueDepth       [4]int   // P0..P3 各队列长度(按去重后的 task 计数,D45)
    HitRate          float64  // 预取命中率(窗口内消费时块已就绪的比例),供自适应 K 调参
}
func (p *PersistentPrefetcher) Status() Status
```

内部约定:四个严格优先级队列(P0>P1>P2>P3);调度协程串行出队,并发抓取受 core fetch 字节信号量统一约束;ETA = 新窗口剩余未就绪字节 ÷ 最近 30s 滑动平均吞吐(EMA α=0.3,口径含回源与本地命中);对已在本地(Catalog.Lookup 命中且 cas.Open 成功)的块不产生下载,直接视为就绪。

并发约定(D45):pending 表覆盖 P0–P3 队列与运行中 task,由 `mu` 保护;同一 blockKey 任一时刻至多一个 task;task 成功或终止后移除键(失败重试期间保留);OnDone / OnP0Done 对每个被接受的 task 恰好回调一次;SubmitPreheat 的 total / completed 按去重后的块计数。

阶段与打点约定(本次指标契约,§5.8):

- phase 状态机:`phase ∈ {startup, steady, switch, unknown}`。startup = Agent 启动起,至首个 ConsumeOrder 的首 K 块就绪(启动窗口 ready),K = §6.1 `prefetch_chunks`;switch = `OnStageSwitch` 起至新窗口 K 块全部就绪(与 ETA 同一完成点);steady = 其余时间;unknown = 无法判定(事件无法关联到任何已知窗口、降级后无法关联阶段等)。两个窗口同时活跃时 switch 优先。
- 双游标口径:消费游标由 `advance` 钩子推进(降级期由 inotify 打开事件兜底,§7.4),`Status.Cursor` 暴露该口径;预取前沿 = 已就绪的最远块(不要求连续),经 `Status.PrefetchFrontier` 暴露。`Status` 不再暴露调度游标(`traincache_prefetch_cursor` 指标仍是调度游标,未改)。`Start` 中"每完成一块推进 cursor"指预取前沿,不改变消费游标。
- 预取领先:`traincache_prefetch_lead_blocks` = 预取前沿 − 消费游标(按当前 ConsumeOrder.Chunks 序列计块数),即 `lead = frontier − cursor`,可为负;负值表示消费领先预取。
- 任务耗时打点位置:task 被 pending 表接受并入队时记起点(同 blockKey 去重提升不重置起点),进入终态(就绪或下载失败终止)时向 `traincache_prefetch_task_duration_seconds{dataset, priority}` observe 一次;priority ∈ {P0,P1,P2,P3}(取 task 最终生效的最高优先级;CLI `--priority` 用小写 p0..p3,映射到指标标签时统一大写 P0..P3)。
- `Status.HitRate` 以最近 100 个消费样本的滑动窗口计算,直接输出为 `traincache_prefetch_hit_ratio{dataset}`(§5.5)。

### 5.3 OrderSource 与共享内存(ordersource 包)

```go
type ChunkRef struct {
    Path  string `json:"path"`  // core Entry 寻址(§5.1 ChunkRef)
    Chunk int64  `json:"chunk"`
}

type ConsumeOrder struct {
    Dataset        string     `json:"dataset"`
    SnapshotID     string     `json:"snapshot_id"`
    StageID        string     `json:"stage_id"`
    ShuffleSeed    int64      `json:"shuffle_seed"`
    BatchSize      int64      `json:"batch_size"`
    PrefetchChunks int        `json:"prefetch_chunks"` // 启动窗口大小 K
    Chunks         []ChunkRef `json:"chunks"`          // 本阶段消费顺序(有序块引用列表)
}

type OrderSource interface {
    // 当前阶段的消费顺序;尚无任何推送时返回 false。
    CurrentOrder() (ConsumeOrder, bool)
    // 订阅阶段切换事件:channel 每收到一个事件 push 一份新 ConsumeOrder。
    SubscribeStageSwitch(ctx context.Context) (<-chan ConsumeOrder, error)
}

// 读端实现:mmap 共享内存文件(布局见 §6.2),由 svc 装配。
// watchDir = /run/traincache/orders,自动发现新 Pod 的 ring 文件。
func NewReader(ringPath string, watchDir string) *Reader
```

语义约定:

- 阶段切换三源归一(decisions D10):epoch 边界、shuffle 重排、curriculum 切换统一为 sidecar 重算并推送一份新 ConsumeOrder;Agent 不区分事件来源。
- ring 单写(sidecar)单读(Agent);writer 重启由代际计数检测;reader 落后不阻塞 writer,跳过至最新(阶段切换只关心最新顺序)。
- Agent 侧心跳 = ring 写入序号推进;30s 无推进 → 进入降级模式(§7.4,验收 10)。

### 5.4 钩子 Unix Socket 协议

DataLoader 钩子(Python,训练 Pod 内)→ Agent:Unix datagram socket `/run/traincache/agent.sock`,行分隔 JSON,单向(Agent 不回帧)。

```json
{"type":"advance","path":"...","chunk":3}
{"type":"stage_switch","stage_id":"epoch-2","shuffle_seed":12345}
{"type":"open_report","path":"...","chunk":3}
{"type":"read_miss","path":"...","chunk":3,"reason":"absent","ts":"2026-10-18T10:00:00Z"}
{"type":"read_stall","path":"...","chunk":3,"wait_ms":250,"ts":"2026-10-18T10:00:00.123456789Z"}
```

- `advance` → `OnConsumeSideAdvance`;`stage_switch` → 转交 `OnStageSwitch`(主通道是 sidecar 推送,钩子直报为双通道冗余,以先到者为准并去重);
- `open_report` → collector 命中率统计(与 inotify 双源,钩子为主,inotify 兜底);
- `read_miss`(D44)→ `HookHandlers.Miss(ref, reason)`:字段 `path`、`chunk`、`reason`(`absent`|`corrupt`)、`ts`;无法区分 absent / corrupt 时按 `absent` 上报。svc 收到后 `resolveRef → Catalog.Lookup → cas.Open`:缺失(ErrNotFound)走 demand(按需补块:以最高优先级 P0 入队,复用 `EnqueueP0` 语义,回源 reason=`demand`),损坏(ErrCorrupt)走 repair(`Quarantine` + `RepairOne`)。该帧是事后信号,best-effort,不保证本次读前补齐;demand 与 prefetch 共用同一 Fetcher、同处一个 single-flight 域;补不及则本次读仍失败,正确性契约不变。训练 Pod 保持只读 hostPath,不接对象存储、不持凭证;
- `read_stall`(D11 注记:钩子帧由四帧扩为五帧——advance / stage_switch / open_report / read_miss / read_stall)→ 实际消费等待块 ≥100ms(阈值可配)时由钩子上报,字段 `type`、`path`、`chunk`、`wait_ms`、`ts`(RFC3339Nano);`type` 为帧类型字段名(与既有四帧一致,取值 `read_stall`)。Agent 按 `ts` ±5s 关联该块的预取状态归因:本地存在且非当前窗口预取 → `local_slow`;在 core fetch 在途 → `origin_slow`;未本地且未在途(pending 或未知)→ `prefetch_lag`;无法解析/超窗 → `unknown`。归因结果进 `traincache_read_stall_seconds{dataset, phase, cause}`,仅 ≥100ms 的等待入直方图;帧格式错误仍记 `traincache_hook_format_errors_total{reason="parse|size"}`(D33);
- socket 不存在或 sidecar 缺席 → 降级模式,以 inotify 打开事件驱动(§7.4)。

### 5.5 热度与命中率(collector 包)

```go
// inotify 旁路监听缓存目录打开事件(不侵入训练进程)。
func NewCollector(blockDir string, ring *ordersource.Reader,
                  m *metrics.Registry, cfg CollectorConfig) *Collector
func (c *Collector) Start(ctx context.Context)

type CollectorConfig struct {
    HeatDecayAge       time.Duration // 超过 N 的记录直接衰减热度,默认 24h
    HeatDumpInterval   time.Duration // 每 DumpInterval 分钟 dump 一次,默认 30min
    HeatDecayInterval  time.Duration // 每隔 T 全体乘衰减因子,默认 24h
    HeatDecayFactor    float64       // 默认 0.5
    HeatOpenBeta       float64       // 单次打开的热度增量系数 β,默认 0.15(D24)
    HeatTouchHalfLife  time.Duration // 新鲜度 R 半衰期 T_R,默认 6h(D24)
    CalibrateWindow    int           // 交叉校准滑动窗口,默认 100 次打开
    CalibrateThreshold float64       // 匹配率低于该值重对齐,默认 0.8(即 7.0 默认 20% 偏差)
}
```

- 热度映射:`指纹 → (热度h, 最近触摸时间t_touch)`,内存持有,定期 dump `heatmap.json`(§6.4);
- 更新规则(D24):每次 OPEN 合并后 `h ← h + (1−h)·β`;每 T 全体乘衰减因子、超 N 直接衰减;`t_touch` 取最后打开 / 预取写入 / 新 ConsumeOrder 刷新三者的最大值;
- 淘汰得分:**`S = max(h, R)`**,其中 `R = 0.5^(Δt/T_R)`(Δt = now − t_touch)——加权平均被否决:它无法同时保护「刚预取还没被读过」(h=0 靠 R 保)与「历史热块久未读」(R 低靠 h 保)两类块(7.3 D24);淘汰序与两条线见 §7.6;
- 命中率:打开块集合与本地块求交集,滚动窗口(分钟级)+ 按训练阶段聚合,不落长期历史,重启丢弃。阶段与来源词汇(冻结):
  - `phase ∈ {startup, steady, switch, unknown}`(状态机见 §5.2);命中/未命中按事件发生时的 phase 打标。
  - 命中来源 `source ∈ {prefetch, cache, unknown}`:prefetch = 当前窗口内由 Agent 预取放置;cache = 本地已有且非当前窗口预取;unknown = 无来源信息。
  - 预取命中率口径:`Status.HitRate` = 最近 100 个消费样本中"消费时块已就绪"的比例,输出为 `traincache_prefetch_hit_ratio{dataset}`;它与 `cache_hit_ratio`(hits/(hits+misses))不同,后者是打开命中率。
  - 同 7.0:dataloader 上报并非完美精确,读到的不一定是实际成功读到的;本设计不声称 Agent 在读路径上做了精确记账,指标是观测口径而非账本;
- 交叉校准:窗口内实际打开顺序 vs OrderSource 期望顺序的匹配率 < 0.8 → 调 `OnConsumeSideAdvance` 把 cursor 重对齐到实际位点。

### 5.6 CLI(cmd/traincache)

纯 gRPC 客户端,不直接操作缓存目录,不重复实现缓存索引、数据块下载或落盘逻辑。

```

                    [--dataset NAME] [--snapshot-id ID] [--priority p0|p1|p2|p3]
```

- `--priority` 接受小写 `p0|p1|p2|p3`,映射到指标标签时统一为大写 `P0|P1|P2|P3`(与 §5.8 指标词汇一致);
- `--chunks` 名字解析:先 `NodeService.ListSnapshot` 取 `--path` 前缀下条目,`chunk-NNN` = 按 `(path, chunk)` 字典序第 NNN 个条目(1 起);
- `traincache node status` 输出字段(7.0):Agent 是否可用、缓存目录内容、已缓存数据量、缓存剩余空间、运行中预热任务数、索引恢复与扫描状态;`--item` 单独查一项;

- 未指明 `--dataset` 时,`--path` 需能映射到已注册 dataset(Agent 侧校验);输出格式默认人类可读表格(JSON 见 decisions Q9)。

语义与词汇(冻结):

- `phase ∈ {startup, steady, switch, unknown}`;命中来源 `source ∈ {prefetch, cache, unknown}`;stall 归因 `cause ∈ {local_slow, prefetch_lag, origin_slow, unknown}`;消费推进 `source ∈ {hook, inotify}`;priority ∈ {P0,P1,P2,P3}(CLI `--priority` 用小写 p0..p3,映射到指标标签时统一大写 P0..P3)。phase 状态机见 §5.2,归因规则见 §5.4。
- `traincache_cache_hits_total` 的 `result` 固定 `success`;`traincache_cache_misses_total` 的 `result ∈ {success, error, refetched}`(refetched 对应 demand 补块成功,§7.5)。
- 回源 `reason ∈ {prefetch, demand, repair, other}`:prefetch 为预取/预热下载,demand 为 `read_miss` 钩子触发的按需补块,repair 为坏块修复重下,other 为兜底。
- 术语冻结:prefetch(预取)= 按 P0–P3 队列主动提前下载;demand(按需补块)= 训练侧 `read_miss` 钩子触发、复用预取队列补块;repair(修复)= 坏块 `Quarantine` 后重下;回源(origin fetch)是三者总称,不是第四条路径。帧名 `read_miss`、`handleReadMiss`、`traincache_hook_read_miss_total` 保持不变(该指标统计帧,不区分回源路径)。
- `traincache_fetch_singleflight_merged_total` 由 Agent 侧 fetch 调用包装器统计:同 key 在途时第二个调用 +1,不修改 core/fetch。
- `traincache_fetch_bandwidth_limit_bytes` = 配置的字节信号量上限;与 `traincache_fetch_inflight_bytes` 求比值判断限速是否打满。
- `traincache_prefetch_hit_ratio` 来自 `Status.HitRate`(100 样本滑动窗口,§5.2/§5.5)。
- `traincache_read_stall_seconds` 只记录 ≥100ms 的消费等待(阈值可配);`_count` = stall 事件数,`_sum` = stall 总时长。
- `traincache_stage_switch_eta_seconds` 是「阶段切换预计 stall(ETA)」,不是实测 stall;实测值一律走 `traincache_read_stall_seconds`(phase=switch),两者不得混用或互相替代。
- `traincache_quarantined_blocks` 与 `traincache_repair_queue_depth` 归 GC 线(对齐 7.0「坏块隔离和修复队列」),不再列入节点状态线。
- `traincache_consumption_advance_total` 的 inotify 兜底已实现:inotify OPEN → 指纹反查当前订单 → `OnConsumeSideAdvance`,单调 consume 去重后计 source="inotify";钩子活跃期 inotify 被 collector 门控抑制,不与 source="hook" 双计。已知限制:反查仅覆盖当前订单 Chunks。
- `traincache_index_refresh_total` 的 `result ∈ {success,error}`(R1 快照跟随复用,沿用既有 metrics 契约);失败不切换、不清空。`traincache_index_sweep_skipped_total` 的 `reason` 当前为 `manifest_unavailable`。

固定 bucket:

- `traincache_request_duration_seconds` / `traincache_index_refresh_duration_seconds`:`{.01,.05,.1,.5,1,5,10,30}`s;
- `traincache_read_stall_seconds`:`{0.1,0.25,0.5,1,2,5,10,30,60}`s;
- `traincache_prefetch_task_duration_seconds`:`{0.1,0.5,1,2,5,10,30,60,120}`s。

family 计数:D44 后 26;本次新增 8 个 family(`traincache_prefetch_hit_ratio` / `traincache_read_stall_seconds` / `traincache_fetch_singleflight_merged_total` / `traincache_repair_queue_depth` / `traincache_prefetch_task_duration_seconds` / `traincache_prefetch_lead_blocks` / `traincache_consumption_advance_total` / `traincache_fetch_bandwidth_limit_bytes`),并调整 6 个既有 family:5 个标签变更,`traincache_stage_switch_eta_seconds` 完成改名并明确其为阶段切换预计 stall(ETA)(上表),合计 34;R3/R4 新增 `traincache_index_sweep_skipped_total` 与 `traincache_objectstore_conditional_write_supported` 后共 36。另有两条不带 `dataset` 的钩子/订单线 family:`traincache_hook_format_errors_total{reason}`(D33)与 `traincache_ordersource_format_errors_total{reason}`(D23),计入总数但不进七线表。

### 5.9 快照角色边界:快照发布 vs 快照跟随

- **快照发布(写入方)**:产生新 entries 的组件调用 core/index `(*Writer).Commit`,由它合并快照并推进 CURRENT。发布方当前待定:Controller 设计未完成,且其现有职责不产生新索引,因此不直接调用 `Commit`;Agent 不承担发布职责。
- **快照跟随(Agent,只读)**:经 `index.Catalog.Start` / `Catalog.Refresh` 定时读 CURRENT → 下载并校验 manifest 与引用分片 → `atomic.Pointer` 原子切换内存映射;失败保持旧映射。Agent 只读,不调用 `Commit`。
- **自开观测防护**:core/cas 已提供 `SetOpenObserver(func(Fingerprint))`,在 `Store.Open` 内于 `os.Open` 之前回调,仅登记“本进程即将读打开该块”,不改变 Open 行为;observer 挂在 Store 实例上,传 nil 清除,不做进程级全局。Agent 在装配中创建 `cas.Store` 时调用 `cs.SetOpenObserver(guard.Mark)` 安装,位置必须在任何 prefetcher / rescan / backfill / fetch 构造之前。目的:未来任何写入方内嵌调用 `Commit` 时,其自开读不会污染消费侧信号(inotify 热度、Cursor)。现有各调用点显式 Mark 保留,幂等。

**前缀感知快照跟随(R1,冻结契约)**

- `(*index.Catalog).SnapID() string`:原子读当前 snapID,无则空串。
- `(*index.Catalog).RefreshManifest(ctx context.Context) error`:读 CURRENT+manifest,成功则原子切换 snapID 与空 entries;用于无活跃前缀时。
- `(*index.Catalog).Follow(ctx context.Context, prefixes func() []string) error`:阻塞循环,每 `Config.RefreshInterval` 检查 CURRENT;未变则跳过;`prefixes` 非空调 `LoadPrefixes`,为空调 `RefreshManifest`;失败保持旧映射并继续下一轮。
- `index.Config` 新增 `OnSnapshotChange func(dataset, snapID string)`:由 `Refresh` / `LoadPrefixes` / `RefreshManifest` / `Follow` 在每次成功原子切换后、锁外触发(Follow 经其内部调用的加载方法触发);不得阻塞,回调 panic 不得向调用方传播,nil 安全。
- `index.Config` 新增 `OnSnapshotError func(dataset string, err error)`:仅由 `Follow` 内部单轮加载失败触发(锁外调用),用于错误计数;同样 nil 安全且 panic 不外传。其他加载方法失败不触发该回调。
- Agent 侧:`svc.Config` 新增 `IndexRefreshInterval time.Duration`(默认 5s);per-dataset 首次创建 Catalog 后启动一次 `go cat.Follow(ctx, prefixesFn)`,`prefixesFn` 返回该 dataset 最近订单的路径前缀;`ForOrder` 与 Follow 的加载必须串行(复用 Catalog 内部互斥)。
- 刷新指标复用现有 `index_refresh_total{dataset,result}`,`result ∈ {success,error}`(沿用既有 metrics 契约);失败不切换、不清空。

### 5.10 快照读者登记、心跳与撤销(R2,冻结契约)

新增 `core/index/readers.go`:

- `type ReaderClaim struct { NodeID string; SnapID string; PreviousSnapID string; PreviousUntil time.Time; UpdatedAt time.Time }`,JSON 字段 `node_id` / `snap_id` / `previous_snap_id,omitempty` / `previous_until,omitempty` / `updated_at`。
- 对象键 `dataset/<dataset>/readers/<url.PathEscape(nodeID)>.json`(一节点一 dataset 一文件)。
- `func NewReaderRegistry(store objectstore.Store, nodeID string, grace time.Duration) *ReaderRegistry`(grace<=0 回退 10s)、`func (r *ReaderRegistry) Declare(ctx context.Context, dataset, snapID string) error`、`func (r *ReaderRegistry) Withdraw(ctx context.Context, dataset string) error`、`func ReadReaderClaims(ctx context.Context, store objectstore.Store, dataset string) ([]ReaderClaim, error)`。
- `Declare`:切换快照(本次 snapID 与上次不同)时写 `previous_snap_id=旧 snap`、`PreviousUntil=now+grace`;同一快照重复声明保留 previous/PreviousUntil,待 `now > PreviousUntil` 后清空;Put 覆盖;幂等;成功后更新内存 last。
- `Withdraw`:写 `snap_id=""`、`previous_snap_id=<last>`、`PreviousUntil=now+grace`、`updated_at=now`,之后停止心跳;best-effort。
- `ReadReaderClaims`:无对象返回空集合;JSON 损坏返回错误(GC 需 fail-safe)。
- Agent 侧:用 `nodeid.FromEnv()` 的 ID 构造 registry;心跳间隔 = `IndexRefreshInterval/2`(下限 1s);ctx 取消时对已知 dataset 调 `Withdraw`(超时 5s);`OnSnapshotChange` 立即 `Declare`。

### 5.11 GC 按读者确认删除(R3,冻结契约)

`index.Config` 新增 `ReaderGrace time.Duration`(零值回退 `2*RefreshInterval`,默认 10s)与 `OnSweepSkip func(dataset, reason string)`。

`Collector.Sweep` 规则:

1. 读 claims;`UpdatedAt` 超过 `ReaderGrace` 的 claim 整体忽略(视为读者已死)。
2. 有效 claim 的 `SnapID` 计入 protected;`PreviousSnapID` 仅在 `now ≤ PreviousUntil` 时计入 protected(切换/撤销宽限期)。
3. protected = CURRENT ∪ 固定保留窗口(最近 `RetainSnapshots` 个)∪ 有效 claim 集合;`RetainSnapshots` 降级为兜底上限,不再是安全边界。
4. 快照对象(manifest+分片)只在“不在 protected”时删除;CURRENT 永不删除。
5. protected 快照的 manifest 缺失/损坏:调用 `OnSweepSkip(dataset,"manifest_unavailable")`,跳过本轮块删除,但继续删除其他可删快照对象,不得整体停摆。
6. 块删除仍要求“不在 liveBlocks 且 ref=0 且 pin=0”;liveBlocks 必须由全部 protected 快照重建。
7. 删除顺序保持“先快照对象、后数据块”;同一轮内不新增额外宽限。

### 5.12 Commit 孤儿清理与条件写探测(R4,冻结契约)

- `(*index.Writer).commitOnce` 记录本次 attempt 新 Put 的分片键与 manifest 键;任何失败(含冲突重试前、验证失败)做 best-effort `Delete`(逆序、超时 5s、错误忽略、不覆盖原始错误);不复用键不删;`PutIfMatch` 成功提交后不清理。
- GC 遇 protected 快照 manifest 缺失按 §5.11 第 5 条处理。
- 新增 `objectstore.ErrConditionalWriteUnsupported` 与 `func ProbeConditionalWrite(ctx context.Context, s Store) error`:写临时键,用不匹配 ETag 调 `PutIfMatch`;期望 `ErrConflict`,若返回 nil 则返回 `ErrConditionalWriteUnsupported`;结束删除临时键。
- Agent `svc.Config` 新增 `ObjstoreProbeConditionalWrite bool`(默认 false);开启时装配期探测,指标 `traincache_objectstore_conditional_write_supported` 取值 0/1、预置 0,不支持时告警但不阻止启动。
- `bench/k8s/minio.yaml` 镜像固定为 `minio/minio:RELEASE.2025-04-22T22-12-26Z`(未做拉取验证);新增真实后端条件写集成测试,环境变量 `TC_MINIO_ENDPOINT` / `TC_MINIO_ACCESS_KEY` / `TC_MINIO_SECRET_KEY` / `TC_MINIO_BUCKET` 任一缺失时 skip,存在时期望冲突返回 `ErrConflict`/412。

### 6.1 ConsumeOrder(共享内存载荷,JSON)

```json
{
  "dataset": "b-track", "snapshot_id": "snap-20261014",
  "stage_id": "epoch-2", "shuffle_seed": 20261015,
  "batch_size": 32, "prefetch_chunks": 256,

```

### 6.2 共享内存环形缓冲布局(文件 /run/traincache/orders/<pod-uid>.ring)

小端字节序;sidecar 创建并 `ftruncate`,Agent 只读 mmap。

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | magic `"TCO1"` |
| 4 | 2 | version=1 |
| 6 | 2 | 保留 |
| 8 | 8 | `writer_generation`(sidecar 每次启动 +1) |
| 16 | 8 | `write_seq`(全局递增写入序号) |
| 24 | 4 | `slot_size`(默认 1 MiB) |
| 28 | 4 | `slot_count`(默认 64) |
| 32 | 32 | 保留 |

64 B 头之后为 slot 数组,每 slot:`seq int64` + `len int32` + `payload`(ConsumeOrder JSON,UTF-8)。约定:

- 单写单读;writer 只追加序号,不回收;reader 按 `write_seq` 追读,落后超过 slot_count 时直接跳至最新(不阻塞 writer);
- `writer_generation` 变化 → reader 丢弃旧状态重读最新;
- 读端发现格式不符(magic / version 不对)→ 忽略该文件并计入错误指标;
- 文件在 tmpfs 上(hostPath `/run/traincache`,两侧 Pod 同路径挂载),宿主机重启自动清空——与"重启丢弃长期历史"语义一致。

### 6.3 钩子帧(socket JSON)

见 §5.4,行分隔 JSON;单帧 ≤ 4 KiB;解析失败丢弃并计数(异常计数不带 dataset 标签,防基数膨胀)。

`read_miss` 帧(D44):

```json
{"type":"read_miss","path":"shard-000.tar","chunk":3,"reason":"absent","ts":"2026-10-18T10:00:00Z"}
```

字段:`path`(core Entry 路径)、`chunk`(int64)、`reason`(`absent`|`corrupt`;无法区分时按 `absent`)、`ts`(上报时间戳)。

`read_stall` 帧:

```json
{"type":"read_stall","path":"shard-000.tar","chunk":3,"wait_ms":250,"ts":"2026-10-18T10:00:00.123456789Z"}
```

字段:`type`(固定 `read_stall`;与既有四帧一致)、`path`(core Entry 路径)、`chunk`(int64)、`wait_ms`(等待毫秒,仅 ≥100ms 上报)、`ts`(RFC3339Nano)。归因规则见 §5.4。

### 6.4 heatmap.json(路径 /var/cache/traincache/heatmap.json)

```json
{
  "version": 1,
  "dumped_at": "2026-10-14T10:00:00Z",
  "entries": { "<fp32hex>": { "heat": 1.5, "last_access": 1763000000, "access_count": 3 } }
}
```

周期性原子写(临时文件 + rename);重启恢复时读取;写入失败不影响服务。

### 6.5 指标命名规则

同一层级同一前缀(全部 `traincache_`);低基数维度进标签(dataset / node / result / endpoint / priority),高基数进日志;`dataset` 白名单外记 `other`(7.0 基数控制原则)。

## 7. 关键流程

### 7.1 启动与重启重扫描

1. 读配置(§8)→ nodeid 校验 → 初始化 core(cas / fetch / objectstore / catalog);
2. 枚举块目录(`cas.List`)重建内存索引;读取 heatmap.json;
3. 抽样校验:随机 1% 块全读校验(cas.Open 自校验 xxh3)。全过 → 先服务;发现损坏 → `Quarantine` 并入修复队列;
4. 后台全量扫描:低优先级遍历全部块,修复队列中的问题优先于剩余扫描;读 miss 经钩子 `read_miss` 上报,Agent 侧异步 demand 补块(与 prefetch 同一 Fetcher/single-flight,验收 6):`absent` → demand(最高优先级 P0 入队,reason=`demand`),`corrupt` → repair(`Quarantine` + `RepairOne`);补不及则本次读仍失败;全量未完成也能正常服务(CAS 读时自校验兜底);
5. 就绪探针 = gRPC 服务可用且抽样阶段完成;全量扫描进行中不影响 ready(7.0 部署约束)。

### 7.2 预热任务生命周期(验收 1/5)

`SubmitPreheat` → 校验 node / dataset → 解析快照(CURRENT 兜底)→ **`Catalog.LoadPrefixes(prefixes)` 只加载所需 Manifest 分片**(验收 5)→ 得块列表(与 `chunks` 求交,空=全量)→ 建任务(QUEUED)→ P0 入队 → 逐块:本地命中跳过(不下载)/ 未命中经 core fetch 下载(同键 single-flight 合并)→ 推进 completed / failed → 状态 RUNNING / DONE / ERROR → `GetPreheatStatus` 全程可查;`ReportBlocks` 流(北向)随每块完成触发(Controller 缺席时丢弃,不阻塞)。

### 7.3 持续预取与阶段切换(验收 8/9)

1. sidecar 推送首份 ConsumeOrder → `ordersource.Reader` 发现 ring → `svc` 组装 PersistentPrefetcher → `Start`(验收 8);
2. `Start` 循环:P2 邻域预取 cursor..cursor+lookahead(默认 8),每块完成推进调度游标并上报 metrics;钩子 `advance` → `OnConsumeSideAdvance` 推进纯消费位点;inotify OPEN → 指纹反查当前订单 → `OnConsumeSideAdvance`,单调 consume 去重后计 `traincache_consumption_advance_total{source="inotify"}`(钩子 advance 记 source="hook";钩子活跃期 inotify 被 collector 门控抑制,不双计),预取前沿与消费游标之差记 `traincache_prefetch_lead_blocks`(§5.2);
3. 新 ConsumeOrder 到达 → `OnStageSwitch`:旧阶段 cursor 后未消费块降级 P3(在途不取消);新阶段开头 K 块(`prefetch_chunks`)以 P1 高优先级入队(验收 9);K 块就绪后剩余块转 P2;返回 ETA(§5.2),上报 `traincache_stage_switch_eta_seconds`。该指标是 ETA(预计 stall),不是实测;切换期间的实际等待由钩子 `read_stall` 帧进 `traincache_read_stall_seconds{phase="switch",cause}`,按 §5.4 归因。

### 7.4 降级模式(验收 10)

sidecar 退出(ring 写入停滞 30s 或文件消失)→ Agent 置 degraded:停止依赖 OrderSource,以 inotify 打开事件驱动 cursor 推进与热度/命中率统计,`traincache_agent_degraded=1`;sidecar 恢复(新代际)自动退出降级。降级期消费推进记 `traincache_consumption_advance_total{source="inotify"}`(正常期钩子推进记 source="hook");inotify 兜底经指纹反查当前订单 Chunks 后推进纯消费位点,单调 consume 去重,反查仅覆盖当前订单是已知限制;实际 stall 由 `read_stall` 帧进 `traincache_read_stall_seconds`,phase 依 §5.2 状态机,无法判定记 unknown。

### 7.5 demand 补块与 repair 坏块修复(验收 6)

见 §5.7 使用语义。读 miss 经钩子 `read_miss` 上报,Agent 侧异步 demand 补块(D44):`absent` → demand(以最高优先级 P0 入队,reason=`demand`);`corrupt` → repair(`Quarantine` + `RepairOne`,Quarantine → fetch → Put → 校验 → RemoveQuarantined)。demand 与 prefetch 共用同一 Fetcher、同处一个 single-flight 域;全量扫描与异步 demand/repair 并发处理同块时由 core fetch single-flight 合并为一次下载;补不及则本次读仍失败,正确性契约不变。修复成功 → `traincache_quarantined_blocks` 递减、`traincache_cache_misses_total{result="refetched"}` 计数;修复队列长度与隔离坏块数分别由 `traincache_repair_queue_depth` 与 `traincache_quarantined_blocks` 暴露(GC 线,§5.8)。

### 7.6 GC 与磁盘淘汰

两件事分开,不要混(6.0 补充段):

- **GC(生命周期回收)**:复用 core `Collector.Sweep`,按 §5.11 执行“读者确认删除”:protected = CURRENT ∪ 固定保留窗口(最近 `RetainSnapshots` 个)∪ 有效 claim(`SnapID`;`PreviousSnapID` 仅在 `now ≤ PreviousUntil` 时计入),`RetainSnapshots` 降级为兜底上限;快照对象只在不在 protected 时删除,块删除仍要求不在 liveBlocks、ref=0、pin=0;周期运行,热度不参与;
- **磁盘淘汰(容量管理)**:Agent 层淘汰循环,默认每 30s 查一次磁盘利用率。删的是**仍被 CURRENT 快照引用的活块的本地副本**,经 core `cas.Evict`(core D28)执行——索引条目与引用关系不动,之后要用经 Lookup → Open miss → 回源(demand 或 prefetch;不重复 Acquire,core D28 簿记契约):
  - **触发线**:利用率超 k(默认 80%)→ 按得分 `S = max(h, R)` 升序 Evict,降至 k-Δ;
  - **危险线**:利用率超 M(默认 90%)→ R 清零、按 h 升序激进淘汰 + 告警指标/日志,降至 k-2Δ(「激进」= 牺牲纯投机块,即预取了还没被读的);
  - **硬保护**:cursor + lookahead(8 块,§7.3)任何情况下不淘汰——删了必被立即重读,等于白删还放大回源洪峰;消费窗口保护不设独立机制,新 ConsumeOrder 到达时刷新订单内块的 t_touch 即天然获得高 R(§5.5);
  - 热度只做淘汰的决策输入,簿记在 collector(§5.5),core 不感知热度。

| 项 | 值 |
|---|---|
| 镜像入口 | `traincache-agentd` |

| 安全 | readOnlyRootFilesystem=true;缓存目录写权限经 hostPath 与安全上下文授予 |

约束(7.0 原文):退出/重启/升级不得破坏本地缓存数据持久性,进程退出不应导致缓存目录中的有效数据块被主动删除;后台扫描、校验和预取任务不得无界占用节点资源;缓存未完成全量扫描不应直接导致 Agent 无法提供服务;Agent 必须能唯一确定自身所在 K8s 节点并在状态上报中携带节点标识。

训练 Pod 侧:hostPath 只读挂载 `/var/cache/traincache/blocks/`(验收 3);sidecar 容器挂载 `/run/traincache`(rw)。

## 9. 验收标准(7.0 十一条原文)

1. 手动调用 gRPC 接口能够下发预热任务并查询进度。→ M3
2. Agent 通过 DaemonSet 部署在符合条件的缓存节点上,重启后本地缓存数据不丢失,索引能够自动恢复。→ M4 / M7
3. 训练 Pod 能通过 hostPath 只读挂载访问本地 CAS 数据块,直接读取数据,不经过 Agent 的 gRPC 读接口。→ M7
4. CLI 支持指定节点、快照路径和数据块进行手动预热,并支持查询预热进度和节点缓存状态。→ M7
5. 路径预热只加载所需的 Manifest 分片,不要求加载整个 Manifest;指定块预热不会意外下载未选中的数据块。→ M3
6. 磁盘损坏的块能够通过后台扫描或读时 repair 修复,且不会因并发 repair 产生重复下载。→ M0 / M4
7. Prometheus 指标能够被外部服务访问,覆盖命中率、回源量、索引刷新、GC、延迟和节点状态,并控制标签基数。→ M6
8. 启动最小训练 Pod 和 OrderSource sidecar 后,Agent 能够接收 ConsumeOrder 并启动 PersistentPrefetcher。→ M2 / M3
9. 阶段切换事件到达后,Agent 能够及时将新阶段开头 K 个块加入高优先级预取队列。→ M3
10. OrderSource sidecar 退出后,Agent 在 30 秒内进入降级模式,通过 inotify 兜底并上报相应指标。→ M5
11. 上述关键流程均有可重复执行的测试覆盖。→ M7 总闸
12. `/metrics` 出现指标契约扩充后的 36 个 family,标签与 §5.8 逐字一致。→ M9 / M11(补充验收,不在 7.0 十一条内)
    - 本次新增 8 个:`traincache_prefetch_hit_ratio`、`traincache_read_stall_seconds`、`traincache_fetch_singleflight_merged_total`、`traincache_repair_queue_depth`、`traincache_prefetch_task_duration_seconds`、`traincache_prefetch_lead_blocks`、`traincache_consumption_advance_total`、`traincache_fetch_bandwidth_limit_bytes`;
    - 本次变更 6 个:`traincache_cache_hits_total`、`traincache_cache_misses_total`、`traincache_cache_hit_ratio`、`traincache_fetch_bytes_total`、`traincache_fetch_requests_total`、`traincache_stage_switch_eta_seconds`(ETA 语义);
    - R3/R4 新增 2 个:`traincache_index_sweep_skipped_total{dataset,reason}`(counter)与 `traincache_objectstore_conditional_write_supported`(gauge,0/1,不带 dataset,预置 0);
    - 验收命令沿用 M6/M7 的 `curl :9411/metrics`,断言上述 family 与标签集合出现(尤其 `phase` / `source` / `cause` / `reason` 取值),`read_stall_seconds` 需有 `_count` / `_sum`。

M8(demand 按需补块与预取去重)、M9(指标契约扩充)与 M11(R1–R4 快照跟随/读者登记/GC 安全边界)为补充验收,不在 7.0 十一条内。
