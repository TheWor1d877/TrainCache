# Agent 服务化设计(design)

> 本文档是 `docs/7.0 Agent服务化.md` 的下游设计文档,与核心库三件套(6.1 design / 6.2 plan / 6.3 decisions)平行。
> §5 接口签名与 §6 数据格式为冻结约定,实现子代理不得私改;发现问题回传 `BLOCKED`,由主对话裁决后更新本文档与 docs/decisions.md。

## 1. 定位

把核心库(core/,无服务形态 Go 库)包装为节点常驻服务,以 K8s DaemonSet 部署,每缓存节点一个实例,以节点为服务边界。

- 对外:gRPC(预热任务接收、块级任务上报、节点状态查询)+ Prometheus `/metrics`。
- 对内:调用 core 完成索引、下载、落盘、校验、回收;服务化层不重复实现其中任何一项。
- 训练 Pod 经 hostPath 只读挂载直读 CAS 块,读路径不经过 Agent(沿用 preheat 模型)。
- 自治:训练中持续预取、阶段切换重预取、重启重扫描、坏块修复、热度统计,均无需 Controller 在场。

非目标:

- 不是 Controller(筛选/门控/打分调度逻辑不在本设计);
- 不做读路径内联(FUSE read-through 是可选 stretch,本设计不含);
- 不做分布式缓存组(多节点协作留待后续文档);
- 不实现 Python DataLoader 钩子本体(仅冻结其与 Agent 的 socket 协议;钩子工程形态见 decisions Q10)。

## 3. 总体架构与依赖方向

部署拓扑(单节点视角):

```
┌─ control plane(未来)──────────────┐        ┌─ 训练 Pod ───────────────────────────┐
│ Controller                         │        │ DataLoader(钩子)                     │
└──────────┬─────────────────────────┘        │  │ 位点/打开块(Unix Socket,§5.4)     │
           │ gRPC 南向(§5.1)                  │  ▼                                   │
┌──────────▼──────────────────────────┐     ┌─┤ Agent(同节点)                        │
│ Agent DaemonSet Pod                 │     │ └─ ordersrc sidecar(Python)            │
│  svc(gRPC + 生命周期 + 装配)        │     │    按 Job 配置重算 ConsumeOrder        │
│   ├─ prefetch(四优先级预取)         │◄────┼──── 共享内存 ring(§6.2)                │
│   ├─ ordersource(读 ring)           │     │                                        │
│   ├─ collector(inotify 旁路采集)    │     └──── 直读:hostPath 只读挂载              │
│   ├─ rescan(重扫 / 修复)            │           /var/cache/traincache/blocks/      │
│   └─ metrics / nodeid               │                                            │
└───────┬─────────────────────────────┘                                            │
        │ core 库(cas / fetch / index / objectstore)                                │
        ▼                                                                          │
   数据源(MinIO / 本地源站)                                                          │
```

进程模型:三个可执行产物——

- `traincache-agentd`:DaemonSet 常驻服务(本设计主体);
- `traincache-ordersrc`:训练 Pod 内 sidecar(Python,按 Job 配置计算每阶段消费顺序并写共享内存;顺序语义必须与真实 loader 一致,见 decisions D3);
- `traincache`:CLI(gRPC 客户端)。

依赖方向(单向无环):

```
cmd/{agentd,traincache}  →  svc  →  prefetch, collector, rescan, metrics, nodeid, ordersource  →  core
ordersrc(独立小进程,不依赖 core)        api(proto 生成,仅被 svc / cmd / ordersource 引用)
```

- `svc` 是装配层:起服务、读配置、接探针,持有各子模块实例;
- 子模块之间互不依赖,数据经 `svc` 编排(与 core"index 不依赖 fetch"同风格);
- `ordersource` 只读共享内存,不依赖 core。

## 5. 核心接口(冻结约定)

### 5.1 gRPC(api/agent.proto)

```proto
syntax = "proto3";
package traincache.agent.v1;
option go_package = "traincache/agent/api/agentpb";

// 南向:Controller/CLI → Agent(7.0 验收 1/4/5)
service PreheatService {
  rpc SubmitPreheat(SubmitPreheatRequest) returns (SubmitPreheatResponse);
  rpc GetPreheatStatus(GetPreheatStatusRequest) returns (PreheatStatus);
}

// 节点状态查询(CLI 与就绪探针)
service NodeService {
  rpc GetNodeStatus(GetNodeStatusRequest) returns (NodeStatus);
  rpc ListSnapshot(ListSnapshotRequest) returns (ListSnapshotResponse);
}

// 北向:Agent → Controller,块级任务上报。
// proto 随本设计冻结,服务端实现推迟至 Controller 里程碑(decisions Q1)。
service ReportService {
  rpc ReportBlocks(stream BlockReport) returns (ReportAck);
}
```

消息(字段名冻结):

| 消息 | 字段 |
|---|---|
| `SubmitPreheatRequest` | `task_id string`(幂等键);`node string`(须等于本节点);`dataset string`;`snapshot_id string`(空=当前 CURRENT);`prefixes []string`(路径前缀,语义同 core `Catalog.LoadPrefixes`:空=空映射,含空串=全量);`chunks []ChunkRef`(可选,块级精确指定);`priority PreheatPriority` |
| `ChunkRef` | `path string`;`chunk int64`(core Entry 寻址) |
| `PreheatPriority` | 枚举 `P0=显式启动预取 / P1=阶段切换重预取 / P2=邻域预取 / P3=后台补全`(默认 P0) |
| `SubmitPreheatResponse` | `accepted bool`;`task_id string`;`message string` |
| `GetPreheatStatusRequest` | `task_id string` |
| `PreheatStatus` | `task_id`;`node`;`dataset`;`snapshot_id`;`paths []string`;`state`(枚举 `QUEUED / RUNNING / DONE / ERROR`);`total_blocks int64`;`completed_blocks int64`;`failed_blocks int64`;`started_at`、`updated_at`(google.protobuf.Timestamp) |
| `GetNodeStatusRequest` | `node string`;`item NodeStatusItem`(枚举:全量 / agent / catalog / space / tasks / rescan) |
| `NodeStatus` | `node`;`agent_ok bool`;`cache_root string`;`cached_bytes int64`;`free_bytes int64`;`running_tasks int64`;`rescan RescanStatus`;`catalog []DatasetCatalog` |
| `RescanStatus` | `phase`(枚举 `SAMPLING / FULL_SCAN / DONE`);`sampled int64`;`verified int64`;`quarantined int64`;`repair_queue int64` |
| `DatasetCatalog` | `dataset string`;`snapshot_id string`;`shards int64`;`entries int64` |
| `ListSnapshotRequest` | `dataset string`;`snapshot_id string`(空=CURRENT);`prefix string` |
| `ListSnapshotResponse` | `entries []EntryRef`(`path`;`chunk`;`size`) |
| `BlockReport` | `node`;`task_id`;`ref ChunkRef`;`fp string`;`bytes int64`;`result`(枚举 `OK / CORRUPT / REFETCHED`) |
| `ReportAck` | 空 |

错误语义:任务校验失败(节点不符、dataset 不存在)→ `InvalidArgument`;同 `task_id` 内容不同 → `AlreadyExists`;同 `task_id` 内容相同 → 幂等返回现有任务。RPC 一律带 context 超时(Agent 侧默认 10s);长时间任务经 `GetPreheatStatus` 轮询,不做长连接流。

### 5.2 PersistentPrefetcher(prefetch 包)

```go
type PersistentPrefetcher struct{ /* ... */ }
func New(cat *index.Catalog, f *fetch.Fetcher, cs *cas.Store,
         m *metrics.Registry, cfg Config) *PersistentPrefetcher

// 开始持续预取:从 cursor 起按当前 ConsumeOrder 邻域预取,每完成一块推进 cursor 并上报 /metrics。
// 可被显式启动预取(P0)与阶段切换重预取(P1)打断:在途请求不取消,新请求按更高优先级入队。
func (p *PersistentPrefetcher) Start(ctx context.Context)

// DataLoader 钩子每消费完一块调用,推进 cursor;预取提前量 = cursor + lookahead(默认 8)。
func (p *PersistentPrefetcher) OnConsumeSideAdvance(ctx context.Context, ref ChunkRef) error

// 阶段切换:旧阶段 cursor 之后未消费块降级 P3(在途请求不取消);
// 新阶段开头 K 块(K = 新 ConsumeOrder.prefetch_chunks)作为 P1 高优先级入队,剩余块转 P2 邻域预取;
// 返回"切换时刻到新窗口就绪"的预估时间,供 Agent 上报 traincache_stage_switch_stall_seconds。
func (p *PersistentPrefetcher) OnStageSwitch(ctx context.Context, next ConsumeOrder) (eta time.Duration, err error)

type Status struct {
    Stage      string   // 当前阶段标识
    Cursor     ChunkRef // 当前消费位点
    QueueDepth [4]int   // P0..P3 各队列长度
    HitRate    float64  // 预取命中率(窗口内消费时块已就绪的比例),供自适应 K 调参
}
func (p *PersistentPrefetcher) Status() Status
```

内部约定:四个严格优先级队列(P0>P1>P2>P3);调度协程串行出队,并发抓取受 core fetch 字节信号量统一约束;ETA = 新窗口剩余未就绪字节 ÷ 最近 30s 滑动平均吞吐(EMA α=0.3,口径含回源与本地命中);对已在本地(Catalog.Lookup 命中且 cas.Open 成功)的块不产生下载,直接视为就绪。

### 5.3 OrderSource 与共享内存(ordersource 包)

```go
type ConsumeOrder struct {
    Dataset        string     `json:"dataset"`
    SnapshotID     string     `json:"snapshot_id"`
    StageID        string     `json:"stage_id"`
    ShuffleSeed    int64      `json:"shuffle_seed"`
    BatchSize      int64      `json:"batch_size"`
    PrefetchChunks int        `json:"prefetch_chunks"` // 启动窗口大小 K
    Chunks         []ChunkRef `json:"chunks"`          // 本阶段消费顺序(有序块引用列表)
}

type OrderSource interface {
    // 当前阶段的消费顺序;尚无任何推送时返回 false。
    CurrentOrder() (ConsumeOrder, bool)
    // 订阅阶段切换事件:channel 每收到一个事件 push 一份新 ConsumeOrder。
    SubscribeStageSwitch(ctx context.Context) (<-chan ConsumeOrder, error)
}

// 读端实现:mmap 共享内存文件(布局见 §6.2),由 svc 装配。
// watchDir = /run/traincache/orders,自动发现新 Pod 的 ring 文件。
func NewReader(ringPath string, watchDir string) *Reader
```

语义约定:

- 阶段切换三源归一(decisions D10):epoch 边界、shuffle 重排、curriculum 切换统一为 sidecar 重算并推送一份新 ConsumeOrder;Agent 不区分事件来源。
- ring 单写(sidecar)单读(Agent);writer 重启由代际计数检测;reader 落后不阻塞 writer,跳过至最新(阶段切换只关心最新顺序)。
- Agent 侧心跳 = ring 写入序号推进;30s 无推进 → 进入降级模式(§7.4,验收 10)。

### 5.4 钩子 Unix Socket 协议

DataLoader 钩子(Python,训练 Pod 内)→ Agent:Unix datagram socket `/run/traincache/agent.sock`,行分隔 JSON,单向(Agent 不回帧)。

```json
{"type":"advance","path":"...","chunk":3}
{"type":"stage_switch","stage_id":"epoch-2","shuffle_seed":12345}
{"type":"open_report","path":"...","chunk":3}
```

- `advance` → `OnConsumeSideAdvance`;`stage_switch` → 转交 `OnStageSwitch`(主通道是 sidecar 推送,钩子直报为双通道冗余,以先到者为准并去重);
- `open_report` → collector 命中率统计(与 inotify 双源,钩子为主,inotify 兜底);
- socket 不存在或 sidecar 缺席 → 降级模式,以 inotify 打开事件驱动(§7.4)。

### 5.5 热度与命中率(collector 包)

```go
// inotify 旁路监听缓存目录打开事件(不侵入训练进程)。
func NewCollector(blockDir string, ring *ordersource.Reader,
                  m *metrics.Registry, cfg CollectorConfig) *Collector
func (c *Collector) Start(ctx context.Context)

type CollectorConfig struct {
    HeatDecayAge       time.Duration // 超过 N 的记录直接衰减热度,默认 24h
    HeatDumpInterval   time.Duration // 每 M 分钟 dump 一次,默认 30min
    HeatDecayInterval  time.Duration // 每隔 T 全体乘衰减因子,默认 24h
    HeatDecayFactor    float64       // 默认 0.5
    CalibrateWindow    int           // 交叉校准滑动窗口,默认 100 次打开
    CalibrateThreshold float64       // 匹配率低于该值重对齐,默认 0.8(即 7.0 默认 20% 偏差)
}
```

- 热度映射:`指纹 → (热度, 最近访问, 加权得分)`,内存持有,定期 dump `heatmap.json`(§6.4);
- 命中率:打开块集合与本地块求交集,滚动窗口(分钟级)+ 按训练阶段聚合,不落长期历史,重启丢弃;
- 交叉校准:窗口内实际打开顺序 vs OrderSource 期望顺序的匹配率 < 0.8 → 调 `OnConsumeSideAdvance` 把 cursor 重对齐到实际位点。

### 5.6 CLI(cmd/traincache)

纯 gRPC 客户端,不直接操作缓存目录,不重复实现缓存索引、数据块下载或落盘逻辑。

```
traincache prefetch --path /train-data --node worker-01 --chunks chunk-001,chunk-002,chunk-003
                    [--dataset NAME] [--snapshot-id ID] [--priority p0|p1|p2|p3]
traincache node status --node worker-01 [--item agent|catalog|space|tasks|rescan]
traincache status --node worker-01 --task-id <task-id>
```

- 全局 `--endpoint`(默认 `127.0.0.1:9410`);`--node` 仅作请求校验字段,不做地址解析(decisions Q2);
- `--chunks` 名字解析:先 `NodeService.ListSnapshot` 取 `--path` 前缀下条目,`chunk-NNN` = 按 `(path, chunk)` 字典序第 NNN 个条目(1 起);
- `traincache node status` 输出字段(7.0):Agent 是否可用、缓存目录内容、已缓存数据量、缓存剩余空间、运行中预热任务数、索引恢复与扫描状态;`--item` 单独查一项;
- `traincache status` 输出字段(7.0):任务 id、目标节点、数据路径、任务状态(等待/进行中/错误/完成)、总块数、已完成块数、失败块数、任务开始时间、最近更新时间;
- 未指明 `--dataset` 时,`--path` 需能映射到已注册 dataset(Agent 侧校验);输出格式默认人类可读表格(JSON 见 decisions Q9)。

## 6. 数据格式

### 6.1 ConsumeOrder(共享内存载荷,JSON)

```json
{
  "dataset": "b-track", "snapshot_id": "snap-20261014",
  "stage_id": "epoch-2", "shuffle_seed": 20261015,
  "batch_size": 32, "prefetch_chunks": 256,
  "chunks": [ {"path": "shard-000.tar", "chunk": 0}, {"path": "shard-007.tar", "chunk": 0} ]
}
```

字段语义见 §5.3;`chunks` 必须按消费顺序排列;`prefetch_chunks` 即 §7.3 的启动窗口 K。

### 6.2 共享内存环形缓冲布局(文件 /run/traincache/orders/<pod-uid>.ring)

小端字节序;sidecar 创建并 `ftruncate`,Agent 只读 mmap。

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | magic `"TCO1"` |
| 4 | 2 | version=1 |
| 6 | 2 | 保留 |
| 8 | 8 | `writer_generation`(sidecar 每次启动 +1) |
| 16 | 8 | `write_seq`(全局递增写入序号) |
| 24 | 4 | `slot_size`(默认 1 MiB) |
| 28 | 4 | `slot_count`(默认 64) |
| 32 | 32 | 保留 |

64 B 头之后为 slot 数组,每 slot:`seq int64` + `len int32` + `payload`(ConsumeOrder JSON,UTF-8)。约定:

- 单写单读;writer 只追加序号,不回收;reader 按 `write_seq` 追读,落后超过 slot_count 时直接跳至最新(不阻塞 writer);
- `writer_generation` 变化 → reader 丢弃旧状态重读最新;
- 读端发现格式不符(magic / version 不对)→ 忽略该文件并计入错误指标;
- 文件在 tmpfs 上(hostPath `/run/traincache`,两侧 Pod 同路径挂载),宿主机重启自动清空——与"重启丢弃长期历史"语义一致。

### 6.3 钩子帧(socket JSON)

见 §5.4,行分隔 JSON;单帧 ≤ 4 KiB;解析失败丢弃并计数(异常计数不带 dataset 标签,防基数膨胀)。

### 6.4 heatmap.json(路径 /var/cache/traincache/heatmap.json)

```json
{
  "version": 1,
  "dumped_at": "2026-10-14T10:00:00Z",
  "entries": { "<fp32hex>": { "heat": 1.5, "last_access": 1763000000, "access_count": 3 } }
}
```

周期性原子写(临时文件 + rename);重启恢复时读取;写入失败不影响服务。

### 6.5 指标命名规则

同一层级同一前缀(全部 `traincache_`);低基数维度进标签(dataset / node / result / endpoint / priority),高基数进日志;`dataset` 白名单外记 `other`(7.0 基数控制原则)。

## 7. 关键流程

### 7.1 启动与重启重扫描

1. 读配置(§8)→ nodeid 校验 → 初始化 core(cas / fetch / objectstore / catalog);
2. 枚举块目录(`cas.List`)重建内存索引;读取 heatmap.json;
3. 抽样校验:随机 1% 块全读校验(cas.Open 自校验 xxh3)。全过 → 先服务;发现损坏 → `Quarantine` 并入修复队列;
4. 后台全量扫描:低优先级遍历全部块,修复队列中的问题优先于剩余扫描;读进程遇未修坏块自行回源(core single-flight 防并发重复下载,验收 6);全量未完成也能正常服务(CAS 读时自校验兜底);
5. 就绪探针 = gRPC 服务可用且抽样阶段完成;全量扫描进行中不影响 ready(7.0 部署约束)。

### 7.2 预热任务生命周期(验收 1/5)

`SubmitPreheat` → 校验 node / dataset → 解析快照(CURRENT 兜底)→ **`Catalog.LoadPrefixes(prefixes)` 只加载所需 Manifest 分片**(验收 5)→ 得块列表(与 `chunks` 求交,空=全量)→ 建任务(QUEUED)→ P0 入队 → 逐块:本地命中跳过(不下载)/ 未命中经 core fetch 下载(同键 single-flight 合并)→ 推进 completed / failed → 状态 RUNNING / DONE / ERROR → `GetPreheatStatus` 全程可查;`ReportBlocks` 流(北向)随每块完成触发(Controller 缺席时丢弃,不阻塞)。

### 7.3 持续预取与阶段切换(验收 8/9)

1. sidecar 推送首份 ConsumeOrder → `ordersource.Reader` 发现 ring → `svc` 组装 PersistentPrefetcher → `Start`(验收 8);
2. `Start` 循环:P2 邻域预取 cursor..cursor+lookahead(默认 8),每块完成推进 cursor 并上报 metrics;钩子 `advance` → `OnConsumeSideAdvance` 推进 cursor(提前量 = cursor + lookahead);
3. 新 ConsumeOrder 到达 → `OnStageSwitch`:旧阶段 cursor 后未消费块降级 P3(在途不取消);新阶段开头 K 块(`prefetch_chunks`)以 P1 高优先级入队(验收 9);K 块就绪后剩余块转 P2;返回 ETA(§5.2),上报 `traincache_stage_switch_stall_seconds`。

### 7.4 降级模式(验收 10)

sidecar 退出(ring 写入停滞 30s 或文件消失)→ Agent 置 degraded:停止依赖 OrderSource,以 inotify 打开事件驱动 cursor 推进与热度/命中率统计,`traincache_agent_degraded=1`;sidecar 恢复(新代际)自动退出降级。

### 7.5 坏块修复(验收 6)

见 §5.7 使用语义;全量扫描与读时回源并发修复同块时由 core fetch single-flight 合并为一次下载;修复成功 → `traincache_quarantined_blocks` 递减、`traincache_cache_misses_total{result="refetched"}` 计数。

### 7.6 GC 与磁盘触发线

GC 正确性复用 core `Collector.Sweep`(保留快照可达 ∪ 读者 pin);Agent 层新增周期检查:磁盘利用率超 k(默认 80%)触发 Sweep 至 k-Δ;超 M(默认 90%)激进 Sweep + 告警指标/日志至 k-2Δ。热度表当前为咨询性(decisions Q5),不改变 Sweep 语义。

## 8. 部署与配置

DaemonSet 要点:

| 项 | 值 |
|---|---|
| 镜像入口 | `traincache-agentd` |
| hostPath 挂载 | `/var/cache/traincache`(rw,DirectoryOrCreate)、`/run/traincache`(rw,DirectoryOrCreate) |
| env | `NODE_NAME`(fieldRef spec.nodeName,必填,启动校验非空)、`TRAINCACHE_GRPC_ADDR`(默认 :9410)、`TRAINCACHE_METRICS_ADDR`(默认 :9411)、`TRAINCACHE_VERIFY`(xxh3 / xxh3+sha256,透传 core verify_level)、`TRAINCACHE_DATASET_WHITELIST`(逗号分隔)、`TRAINCACHE_HEAT_*`(N/M/T/k/Δ/M 覆盖) |
| 探针 | liveness = gRPC health check;readiness = GetNodeStatus 且 `rescan.phase != SAMPLING` |
| 资源 | request 100m/1Gi,limit 2C/4Gi(示例,bench 装置上校准后定) |
| 安全 | readOnlyRootFilesystem=true;缓存目录写权限经 hostPath 与安全上下文授予 |

约束(7.0 原文):退出/重启/升级不得破坏本地缓存数据持久性,进程退出不应导致缓存目录中的有效数据块被主动删除;后台扫描、校验和预取任务不得无界占用节点资源;缓存未完成全量扫描不应直接导致 Agent 无法提供服务;Agent 必须能唯一确定自身所在 K8s 节点并在状态上报中携带节点标识。

训练 Pod 侧:hostPath 只读挂载 `/var/cache/traincache/blocks/`(验收 3);sidecar 容器挂载 `/run/traincache`(rw)。

## 9. 验收标准(7.0 十一条原文)

1. 手动调用 gRPC 接口能够下发预热任务并查询进度。→ M3
2. Agent 通过 DaemonSet 部署在符合条件的缓存节点上,重启后本地缓存数据不丢失,索引能够自动恢复。→ M4 / M7
3. 训练 Pod 能通过 hostPath 只读挂载访问本地 CAS 数据块,直接读取数据,不经过 Agent 的 gRPC 读接口。→ M7
4. CLI 支持指定节点、快照路径和数据块进行手动预热,并支持查询预热进度和节点缓存状态。→ M7
5. 路径预热只加载所需的 Manifest 分片,不要求加载整个 Manifest;指定块预热不会意外下载未选中的数据块。→ M3
6. 磁盘损坏的块能够通过后台扫描或读时回源修复,且不会因并发修复产生重复下载。→ M0 / M4
7. Prometheus 指标能够被外部服务访问,覆盖命中率、回源量、索引刷新、GC、延迟和节点状态,并控制标签基数。→ M6
8. 启动最小训练 Pod 和 OrderSource sidecar 后,Agent 能够接收 ConsumeOrder 并启动 PersistentPrefetcher。→ M2 / M3
9. 阶段切换事件到达后,Agent 能够及时将新阶段开头 K 个块加入高优先级预取队列。→ M3
10. OrderSource sidecar 退出后,Agent 在 30 秒内进入降级模式,通过 inotify 兜底并上报相应指标。→ M5
11. 上述关键流程均有可重复执行的测试覆盖。→ M7 总闸

(分里程碑的逐条验收见 docs/plan.md。)
