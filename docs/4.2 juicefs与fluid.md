# juicefs 与 fluid

两组非 TrainCache 对照：JuiceFS（冷/热）与 Fluid（冷/热），加 direct 直读组。三组装置的起停入口都在 `bench/compare/Makefile`，跑分统一交给 `run_bench.py`。

## 1. 镜像

| 镜像 | 默认引用 | 用途 |
|---|---|---|
| JuiceFS 客户端 | `juicedata/mount:ce-v1.3.0` | juicefs 组的 mount Pod 与 measure Pod 内的 FUSE 挂载；fluid 组的 worker |
| Redis | `redis:7-alpine` | juicefs 与 fluid 各自的元数据实例 |
| 训练镜像 | `python:3.12-alpine` | 所有组的测量 Pod；slim 拉不到，别换 |
| BusyBox | `busybox:latest` | 导入 Job 与探活 |
| MinIO | `pgsty/minio:RELEASE.2026-08-04T00-00-00Z` | 源站；`make kind-up` 预载，重建集群时自动导入 |

离线机器先在宿主机拉齐，再导入集群：

```bash
docker pull juicedata/mount:ce-v1.3.0
docker pull redis:7-alpine
docker pull python:3.12-alpine
docker pull busybox:latest

for img in juicedata/mount:ce-v1.3.0 redis:7-alpine python:3.12-alpine busybox:latest; do
  kind load docker-image "$img" --name traincache
done
```

`up.sh` 不重试拉取，缺镜像时 Pod 停在 ImagePullBackOff，日志里给出上面两条命令。

Fluid 的控制面不在这些镜像里，先装一次：从 GitHub release 取离线 chart `fluid-1.1.0-alpha.9`，`helm install` 到 `fluid-system`，带 `--set runtime.juicefs.enabled=true`。`fluid/up.sh` 开头检查 `fluid-system` 命名空间，不存在直接退出。装法与当时的版本证据见 [3 现勘报告](<3 现勘报告.md>)。

## 2. 起组

```bash
cd bench
make -C compare compare-up GROUP=direct
make -C compare compare-up GROUP=juicefs-cold
make -C compare compare-up GROUP=juicefs-warm
make -C compare compare-up GROUP=fluid-cold
make -C compare compare-up GROUP=fluid-warm
```

`GROUP` 还接受 `juicefs`/`fluid` 不带后缀的别名，沿用各 `up.sh` 的缺省冷热态；正式跑分写全名，避免猜默认值。

每组吃同一份源数据与同一个 tc 档位，差异只在缓存层：

| 组 | 缓存介质 | 容量控制 | 元数据 | 数据通路 | 预热 | request / limit |
|---|---|---|---|---|---|---|
| direct | 无 | — | — | HTTP GET `shard-*.tar`，按 8MiB 分段读 | 无 | 500m、1Gi / 2 CPU、4Gi |
| juicefs-cold | 节点 hostPath `/var/cache/jfs` | `--cache-size 1024`（单位 MiB） | Redis 7 `redis.juicefs.svc:6379` | measure Pod 内自挂 FUSE `/mnt/jfs`（privileged） | 无，空缓存启动 | 500m、1Gi / 2 CPU、6Gi |
| juicefs-warm | 同上 | 同上 | 同上 | 同上 | `up.sh` 内 `juicefs warmup /mnt/jfs/` 预热整档，单独计时，15 分钟硬超时 | 500m、1Gi / 2 CPU、6Gi |
| fluid-cold | tieredstore HDD，`/tmp/juicefs-cache` | `quota: 1Gi` | Redis 7 `redis.fluid.svc:6379`（独立实例） | PVC `jfs-demo` 挂 `/data` | 不建 DataLoad | 500m、1Gi / 2 CPU、4Gi |
| fluid-warm | 同上 | 同上 | 同上 | 同上 | DataLoad `jfs-load`（target=`/`）预热整档，15 分钟超时 | 500m、1Gi / 2 CPU、4Gi |

juicefs 组预热前轮询 `/proc/mounts`，确认 `/mnt/jfs` 真的挂上了再开始。Pod Ready 只说明容器起来了，FUSE 可能还没挂好。

warm 组的预热在 `up.sh` 内完成，`up.sh` 返回才创建测量 Pod。`startup_makespan` 因此不含预热时间；预热时长单独记 `warmup_seconds`。

## 3. 跑分

五格串行用统一入口：

```bash
cd bench
python3 exp.py run compare-groups
```

`baselines/` 里的对照跑分只读，exp.py 只跑每格的 TrainCache 组，每格产物落 `~/tcd/bench/results/compare-groups/<格名>/`，含 `summary.csv`、`runs/`、`lock.json`。对照行从 `baselines/<格名>/summary.csv` 取。

要重建或重跑对照，直接用 `run_bench.py`。`--out` 的相对路径按 `RESULTS_DIR` 展开：

```bash
cd bench/compare
CAPACITY_RATIO=S python3 run_bench.py --tier S --rate 100mbit --reps 3 \
  --groups juicefs-cold juicefs-warm fluid-cold fluid-warm \
  --out compare-groups/S-100/summary.csv

CAPACITY_RATIO=S python3 run_bench.py --tier S --rate 300mbit --reps 3 \
  --groups direct fluid-cold \
  --out compare-groups/S-300/summary.csv
```

档位与参跑组的关系：S 档七组态，M 档 direct / fluid-cold / traincache-cold，L 档 traincache-cold / fluid-cold。M/L 档不传 `--rate` 时 runner 直接退出；S@300 不传 `--groups` 也退出，该格只允许三组。每格产物落 `~/tcd/bench/results/compare-groups/<格名>/`，含 `summary.csv`、`runs/`、`lock.json`。

写法只追加：本次有效行顶掉同组同 rep 的旧有效行，其余历史行原样保留；作废行只追加，不顶替有效行。中断后重跑同一条命令，从缺的那组接着做。

## 4. 组态特有的坑

`--cache-size` 的单位是 MiB。配 1024 才是 1GiB，配 1048576 等于 1TiB，容量限制永不生效。历史 juicefs 结果因此作废过一轮。

juicefs-warm 必须与冷组落同一节点。预热暖的是 jfs-mount 所在节点的 hostPath，测量 Pod 没有共置约束，落到别的节点就是空缓存起跑，warm 退化成 cold。`up.sh` 回传 `[MOUNT_NODE]`，`run_bench.py` 给测量 Pod 加 `kubernetes.io/hostname` nodeSelector；回传缺失直接判 `up_failed`。

tc 必须在预热之前挂。`up.sh` 曾把 `tc_apply` 排在预热后，节点重启后 qdisc 已丢，第一档预热走满速，之后各 rep 才被限住，同组 `warmup_seconds` 差出量级（2s 对 177s）。现在预热与测量走同一条限速链路。

cold 组只清目录不算冷态。跨 rep 存活的 FUSE 挂载会把文件页留在内核页缓存里，下一 rep 的首批读直接命中，根本不过限速链路，跑出比 direct 还快的假 cold 行。`run_bench.py` 的 `_clear_node_caches()` 在清目录后执行 `sync; echo 3 > /proc/sys/vm/drop_caches`（sudo -S 优先，特权 docker 回退，两条都不通则终止本轮）。缺这一步的行标 `void=True`、`reason=suspect_page_cache`。

fluid 组拆了再起会撞删除竞态。`down.sh` 删 Dataset 后，JuiceFSRuntime 由 Fluid 异步级联删除；下一次 `up.sh` 看到 Runtime 还在（带 deletionTimestamp）就跳过创建，它随即被回收，Dataset 永远等不到 Bound。`_common.sh` 用 `resource_live` 与 `wait_absent` 做删除屏障，`up.sh` 等 Runtime 删净再建；420s 的 Bound 超时只当保险，不用来掩盖竞态。

juicefs/fluid 的命中率是近似值。`hit_rate` 与 `startup_warmup_bytes` 按 cold≈全回源、warm≈全命中写死（`approx_cold_all_refetch` / `approx_warm_all_hit`），只有 makespan 与 stall 三项是实测。引用带命中率的结论时把口径一起写；胜负判定只看实测三项。

## 5. 拆组

```bash
cd bench
make -C compare compare-down GROUP=juicefs-cold    # 只拆该组
make -C compare compare-all-down                   # 四组全拆
```

`down.sh` 只删 Pod、PVC 与 CRD 实例，不动 MinIO 桶数据，也不动 `~/tcd`。
