# 6.2 缓存核心库实施计划（plan）

> 这份文档讲核心库怎么落地：分几个阶段、每个阶段写什么、怎么验收。
> 配套文档：`6.1 design.md` 冻结接口签名和数据格式，`6.3 decisions.md` 记录决策和未决问题。
> 做法是里程碑制：一次只推一个里程碑，派一个子代理写代码，主对话（负责派活和验收的会话）亲自跑验收命令，通过才进下一个。
> 几个词先说明。**里程碑**是带固定交付物和验收命令的阶段；**子代理**是只负责一小块编码任务的代理；**白名单**是允许改动的文件清单；**BLOCKED** 是子代理遇到约定行不通时回传的状态，意思是停下来等裁决。

## 0. 执行方式（固定）

这五条对所有里程碑生效，目的只有两个：别让多个子代理同时改同一个包，别让“子代理说自己过了”变成验收结论。

1. **派活**：子代理任务按七项模板下发（`[TASK] [CONTEXT] [INPUT] [WRITE] [DELIVER] [ACCEPT] [FORBID]`）。任务要自包含——把需要的约定原文贴进去（`6.1 design.md` §5 的签名、§6 的格式），子代理不靠对话历史也能干活。
2. **白名单**：`[WRITE]` 精确到文件。同一个文件同一时间只允许一个写入者，白名单外的文件不许碰。
3. **约定冻结**：`6.1 design.md` 的接口签名和数据格式不许私改。实现中发现约定走不通，子代理回传 `BLOCKED`（附理由和证据），主对话裁决、更新 `6.1 design.md` / `6.3 decisions.md` 之后再继续。
4. **验收**：里程碑做完，主对话亲自跑验收命令，不采信子代理的自报。失败就再派一个修复子代理，把报错原文和复现命令贴给它，主对话不亲自上手改代码。
5. **回传格式**：子代理固定回传 `STATUS/FILES/SYMBOLS/TESTS/DECISIONS/BLOCKERS/NEXT` 七项，不许夹带大段代码。

一句话：权限收紧、约定冻结、验收独立。

## 2. 里程碑 M1：工程骨架 + objectstore

**目标**：把 `6.1 design.md` 的约定落成能编译的骨架；`objectstore` 做完整实现（含条件写入），其余包先只声明接口。

先做 `objectstore` 的原因：它是对外部对象存储的唯一入口。接口和错误语义定下来，后面 `cas`、`index` 的测试才有稳定的假后端可用。

**任务清单**：

- **第 0 步（P0 前置验证；主对话在派活前确认，或把它算成本里程碑首步）**。这一步先验证两个外部假设，免得代码写完才发现环境不配合：
  1. **依赖可达性**：验证 `GOPROXY` 可用（候选 `https://goproxy.cn,direct`），确认能拉取
     `github.com/zeebo/xxh3`、`github.com/minio/minio-go/v7`（环境事实：github.com 本体不可达）。
     拉不下来 → 按 `6.3 decisions.md` Q4 裁决（vendor 或自实现），不进后续步骤；
  2. **S3 条件写入实测**：对开发环境里的对象存储（bench 装置 MinIO、真实 COS/OSS/S3 均可）发一次
     `PutObject` 带 `If-Match` / `If-None-Match: *` 的请求，确认支持 S3 条件写入（`6.3 decisions.md` Q3）。
     不支持 → 按 Q3 的备选方案裁决（乐观写 + 读回校验），`objectstore` 接口不变。
- 第 1 步：`core/go.mod`（module `traincache/core`，go 1.24，依赖仅上述两个）；
- 第 2 步：`objectstore/store.go` —— `Store` 接口 + `ErrNotFound`/`ErrConflict`（与 `6.1 design.md` §5.1 逐字一致）；
- 第 3 步：`objectstore/mock.go` —— 内存 Mock：ETag = md5hex(content)（S3 简单上传语义）、
  `PutIfMatch` 三态语义（不存在时写 / ETag 匹配时写 / 冲突报 `ErrConflict` 不写入）；

## 3. 里程碑 M2：cas 块存储

**目标**：CAS 层完整实现，`doc/7` 要求的四场景单测全绿。

CAS 是 content-addressed storage（内容寻址存储）：块文件叫什么、放哪里，全由内容哈希决定。同样的内容只落一份，读回来重算哈希就能发现损坏。

**任务清单**：

1. `cas/header.go` 实现：128B 块头编解码（布局见 `6.1 design.md` §6.3），magic/version 校验，`Header` 类型；
2. `cas/store.go` 实现：
   - `New(dir, verify)`（创建块目录 `blocks/`）；
   - `Put`：流式读 → 同时算 xxh3（+可选 sha256）→ 写 `<fp>.tmp-<rand>` 临时文件 → 完成后 `rename`
     到 `blocks/<fp[0:2]hex>/<fp hex>.blk`（目标目录不存在则先 `MkdirAll`）；不做 fsync；
   - `Open`：读块头验证 → 流式重算数据指纹比对 → 不符 `ErrCorrupt`；通过返回 `BlockReader`
     （从块头之后读，`Size()` = block_size）；
   - `Remove`：refcount>0 或 pin>0 → `ErrInUse`；不存在 → `ErrNotFound`；
3. `cas/refcount.go` 实现：`Acquire`/`Release`/`Pin`/`Unpin`（内存表，进程内语义）；
4. 四场景单测（`doc/7` 硬性要求，测试名必须可对应）。这四类对应现实里最容易出事的四种情况：
   - `TestConcurrentPutSameBlock`：N goroutine 并发 Put 相同内容 → 全部返回同一指纹、文件完整、
     目录无残留临时文件；
   - `TestCrashDuringWrite`：a) 注入失败点使 Put 中途终止 → 重开 Put 同内容成功、Open 正常；
     b) 预置孤儿 `<fp>.tmp-*` 文件 → 不影响 Open/后续 Put；
   - `TestDedup`：同内容两次 Put → 同一指纹、磁盘上仅一个块文件（含跨"路径"语义由内容决定，此处即同内容）；
   - `TestVerifyFailure`：篡改块数据（翻 1 字节）→ Open 返回 `ErrCorrupt`；篡改块头 magic → 同样报错；
     `VerifyXXH3SHA256` 模式下篡改 sha256 字节且内容指纹也改回 → 双重校验语义验证；
5. `internal/digest/digest_test.go`：XXH3_128/SHA256/NewXXH3/NewSHA256 正确性冒烟测试
   （M2 白名单内补建——M1 未建此文件，而 M2 验收含 `go test ./internal/...`）。

**交付物**：`cas` 与 `internal/digest` 全部导出符号实现；四场景测试。

**验收**：
```bash
cd core && go test ./cas/... ./internal/... -race   # 全绿
```
判据：① 四场景测试全部通过且 `-race` 干净；② `Remove` 在引用/pin 非零时返回 `ErrInUse` 有对应测试；
③ 不得引入 `6.1 design.md` §5.2 之外的导出符号。

一句话：块存得进去、读得出来、坏了能发现，这三个能力都在这一关交付。

## 4. 里程碑 M3：fetch 抓取编排

**目标**：限流下载、指令合并、校验失败重下。

三个词先说清。**在途字节**指已经开始下载、还没落盘的字节总量；**信号量**是并发控制工具，拿不到额度就等待；**in-flight map** 记录正在下载的 key，同一个 key 再来请求时直接等前一个的结果，不再发第二次下载。

**任务清单**：

1. `fetch/limiter.go` 实现：字节信号量（`Acquire(n)` 阻塞至在途 ≤ `MaxInflightBytes`，ctx 可取消）、
   单主机连接数（`MaxConnsPerHost`）、最大任务数（`MaxTasks`）；`Options` 默认值见 `6.1 design.md` §8；
2. `fetch/fetcher.go` 实现：`New`、`Fetch`（流程见 `6.1 design.md` §7.5）；in-flight map 合并同 key 请求
   （并发等待者共享结果与错误）；重试 ≤ `MaxRetries`；
3. 单测（mock objectstore + 临时目录 cas.Store）：
   - `TestInflightByteLimit`：并发下载大对象，实测峰值在途字节 ≤ 上限；
   - `TestMergeSameKey`：并发 Fetch 同 key → mock 计数实际 `Get` 恰好 1 次，所有调用者拿到同指纹；
   - `TestRetryAfterCorrupt`：mock 第 1 次喂坏数据（cas 校验失败）→ 自动 Remove + 重下第 2 次成功；
   - `TestRetryExhausted`：mock 每次喂坏数据 → 返回 `ErrTooManyRetries`；
   - `TestCtxCancel`：ctx 取消 → Acquire/下载中途退出，无 goroutine 泄漏（单测结尾检查）。

**交付物**：`fetch` 包实现与测试。

**验收**：
```bash
cd core && go test ./fetch/... -race              # 全绿
```
判据：① 上述五个测试全过；② 重试路径上 Remove 发生在 Open 校验失败后（日志/计数断言）。

一句话：下载要限速、要合并重复请求、坏数据要自动重来，三条都靠这一关兜住。

## 5. 里程碑 M4：index 读写路径

**目标**：分片/manifest/CURRENT 序列化、无冲突提交、Catalog 加载与 Lookup。

这一关的名词最多，先解释。**分片**是把大索引切成的小 JSON 文件，每片最多 10 万条；**manifest** 是“本次快照由哪些分片组成”的清单；**CURRENT** 是对象存储里指向当前快照的指针对象；**ETag** 是对象存储给每个对象版本算的内容标识，条件写入靠它判断“我读到的还是不是最新的”。**upsert** 指同一条键存在就覆盖、不存在就插入。

**任务清单**：

1. `index/format.go` 实现：
   - `Entry`/`ShardRef`/`Manifest` 序列化（JSON，`cas.Fingerprint` 编码为 hex，`Entry.Fingerprint`
     用 `json.Marshaler`/`Unmarshaler` 或等价手段）；
   - 对象存储键函数（`6.1 design.md` §6.1）；`CurrentKey` 内容格式 `"<snapID> <fp8>"`（空格分隔、无换行）；
   - 分片构建：entries 按 `(path, chunk)` 字典序排序 → 按条目数切分（≤ `MaxEntriesPerShard`，
     默认 100_000）→ 每片算 xxh3 指纹 → 文件名 `shard-<fp8>.idx`；
2. `index/writer.go` 实现：`Commit` 无冲突路径——读 CURRENT（`ErrNoCurrent` 视为空数据集首次提交，
   `expectedETag=""`）→ 读当前 manifest 与受影响分片 → 合并 entries（upsert，同 `(path,chunk)` 覆盖）→
   构建新分片（未变更分片复用旧键不重传）→ 上传新分片与新 manifest → 四步验证（`6.1 design.md` §7.1 第 4 点）→
   `PutIfMatch` 提交 CURRENT；
3. `index/catalog.go` 实现：`Catalog` 构造、`Refresh`（下载 manifest → 逐分片下载验证指纹
   （不符 `ErrInvalidShard`）→ 构建内存映射 → `atomic.Pointer` 原子切换）、`Lookup`（未命中返回
   `(Entry{}, false, nil)`；无快照返回 `ErrNoCurrent`）；
4. 单测（mock objectstore + 临时目录 cas）：
   - `TestCommitAndLookup`：构造跨 3 分片（缩小 MaxEntriesPerShard 触发）的数据集 → Commit →
     Catalog 加载 → 全部 `(path,chunk)` Lookup 命中、字段逐项相等；
   - `TestLookupMiss`：未提交的 `(path,chunk)` → `(_, false, nil)`；
   - `TestShardFingerprintMismatch`：篡改一个分片对象 → Refresh 报 `ErrInvalidShard` 且旧映射仍可用；
   - `TestFirstCommit`：空对象存储（无 CURRENT）→ Commit 成功，CURRENT 内容格式正确；
   - `TestUpsertAndReuse`：第二次 Commit 只改 1 条 → 未变更分片对象键不变（复用，无重传）、
     变更分片为新键。

**交付物**：`index` 包读写路径实现与测试。

**验收**：
```bash
cd core && go test ./index/...                    # 全绿
```
判据：① 上述五个测试全过；② 分片对象键与 manifest 指纹字段一致；③ CURRENT 解析格式与 `6.1 design.md` §6.1 一致。

一句话：这一关交付“查得到、改得动、改完不丢”，并发留给下一关。

## 6. 里程碑 M5：index 并发提交 + 后台刷新

**目标**：条件提交冲突重试、并发提交正确性、刷新循环原子性。

**原子切换**的意思是：读侧看到的映射要么全是旧快照，要么全是新快照，不会新旧混在一起。实现上用 `atomic.Pointer` 换指针，一次换完。

**任务清单**：

1. `index/writer.go` 补全冲突路径：`ErrConflict` → 重读最新快照 → 拿它重新合并构建 → 再提交，
   上限 `CommitMaxAttempts`（默认 5）次，耗尽返回错误（含已尝试次数信息）；
2. `index/catalog.go` 补全：`Start(ctx)` 后台循环（`RefreshInterval` 默认 5s，ctx 取消退出；
   刷新失败不退出循环，记录错误）；
3. 并发单测（mock objectstore，mock 的 `PutIfMatch` 必须支持 ETag 变化模拟真实竞争）：
   - `TestConcurrentCommit`：20 goroutine 各自 Commit 不同 entries → 全部成功（或个别达重试上限后
     以明确错误结束）；最终 CURRENT 有效、manifest 可解析、所有分片指纹一致、**所有 entries
     全部出现在最终快照中**（无静默丢失）；
   - `TestCommitConflictRetry`：人为制造竞争（两个 Writer 都拿同一份 CURRENT 提交）→ 恰一个生效，
     另一个重试后拿新快照再提交成功，两条数据都在；
   - `TestRefreshAtomicSwitch`：后台 Start 运行中持续 Lookup → 每次 Lookup 命中的结果永远属于
     **某一个完整快照**（新旧不混合，如 entry 集合与 snapshot 代次一致）；期间连续多次 Commit；
   - `TestRefreshErrorTolerance`：mock 注入一次分片损坏 → 刷新失败但循环继续、映射保持旧快照，
     修复后下一次刷新恢复。

**交付物**：并发提交与刷新实现及测试。

**验收**：
```bash
cd core && go test ./index/... -race              # 全绿，race 干净
```
判据：① 上述四个测试全过；② `-race` 无告警（原子切换与并发提交无数据竞争）；③ 冲突重试后无条目丢失。

一句话：多个写者同时提交，结果只能有一个，其余重试但不能丢数据。

## 7. 里程碑 M6：GC 回收 + 端到端集成

**目标**：旧快照/分片/块安全回收 + 全链路端到端测试，收尾总闸。

GC 里两个词：**活块**指还当前快照或保留窗口内快照引用得到的块；**孤儿块**指谁都引用不到、可以删的块。“保留窗口”在 `6.3 decisions.md` D14 定过：CURRENT 加最近 2 个已提交快照，共 3 代。

**任务清单**：

1. `index/gc.go` 实现 `Collector.Sweep`（`6.1 design.md` §7.3）：
   - 活块集合 = 保留窗口（CURRENT + 最近 2 个已提交快照，`RetainSnapshots`=3）索引可达指纹 ∪ 读者 pin；
   - 扫描 `cas` 目录（列出块文件并解析文件名指纹）→ 删不在活块集合且 refcount=0、pin=0 的块；
   - 删保留窗口外且不被保留快照复用的 manifest 与分片对象（CURRENT 指向的绝不删）；
2. 单测：
   - `TestSweepKeepsLiveBlocks`：CURRENT 引用的块一个不删；窗口内旧快照引用的块不删；
   - `TestSweepRemovesOrphans`：提交新快照后，不再被任何保留快照引用的块被删、旧 manifest/分片被删；
   - `TestSweepSkipsPinned`：pin>0 的孤儿块本次跳过不删；
   - `TestSweepNeverDeletesCurrent`：CURRENT 指向的快照与其对象始终在。
3. 端到端集成测试 `index/integration_test.go`（mock objectstore + 临时目录 cas + fetch，全链路）：
   写块（fetch.Fetch 经 mock 下载）→ `Writer.Commit` → `Catalog.Refresh` → `Lookup` → `cas.Open`
   读回校验数据逐字节一致 → 第二次 Commit（数据集更新）→ 刷新后新条目可见、旧条目按保留窗口
   处理 → `Sweep` 清理 → 并发读（Pin 持有）时 Sweep 不删在读块。

**交付物**：GC 实现、单测、端到端集成测试。

**验收（总闸）**：

判据：① 全包测试通过、`-race` 干净；② 端到端链路逐字节一致；③ `doc/7` 四场景在 M2 测试中仍全绿；

## 8. 里程碑 M7：索引分片按前缀目录加载

**背景**：`doc/7` 新增「索引分片按前缀目录加载」。服务侧的数据块按需下载，但 manifest 一直全量加载。训练可能只要 `/train-data` 下的数据；数据量涨上去以后，索引主体（分片）能到 GB 级，全量加载纯属浪费。核心库的 `Catalog` 提供「按前缀加载」能力，加载哪些前缀由 Agent 服务决定。主对话裁决：D22（`ShardRef` 增 `MinPath`/`MaxPath`）、D23（`Catalog` 增 `LoadPrefixes`，与 `Refresh`/`Start` 互斥使用模式）。

## 9. 里程碑 M8：cas 坏块隔离（Quarantine）

2. 单测 `cas/quarantine_test.go`（新建）：Quarantine 幂等、修复闭环（Quarantine → Put → 校验 → RemoveQuarantined）、List 语义（ListQuarantined 枚举、List 排除 quarantine）；复用 store_test.go 既有辅助，既有测试文件零改动；

## 10. 里程碑 M9：cas.Evict 本地副本淘汰
