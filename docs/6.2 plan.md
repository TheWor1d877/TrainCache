# 6.2 缓存核心库实施计划（plan）

> 配套：`6.1 design.md`（冻结约定：接口签名、数据格式）、`6.3 decisions.md`（决策与未决问题）。
> 本计划按"每次一个里程碑"的执行方式组织：M1→M9 严格串行，每个里程碑由主对话派
> **单个子代理**执行，完成后主对话亲自跑验收命令，通过才进入下一个。

## 0. 执行方式（固定）

1. **派活**：子代理任务按七项模板下发（`[TASK] [CONTEXT] [INPUT] [WRITE] [DELIVER] [ACCEPT] [FORBID]`），
   自包含——贴所需约定片段原文（design.md §5 对应签名、§6 对应格式），不依赖对话历史；
2. **白名单**：`[WRITE]` 精确到文件；同一文件同一时间只有一个写入者；不得动白名单外文件；
3. **约定冻结**：design.md 的接口签名与数据格式不可私改；实现中发现问题 → 回传 `BLOCKED`
   （理由 + 证据），由主对话裁决并更新 design.md / decisions.md 后再继续；
4. **验收**：主对话在里程碑完成后亲自执行验收命令（不信任子代理自报），失败则派修复
   子代理（贴报错原文 + 复现命令），不亲自上手改；
5. **回传格式**：子代理固定回传 `STATUS/FILES/SYMBOLS/TESTS/DECISIONS/BLOCKERS/NEXT`，禁止夹带大段代码。

## 3. 里程碑 M2：cas 块存储

**目标**：CAS 层完整实现，doc/7 四场景单测全绿。

**任务清单**：

1. `cas/header.go` 实现：128B 块头编解码（布局见 design.md §6.3），magic/version 校验，`Header` 类型；
2. `cas/store.go` 实现：
   - `New(dir, verify)`（创建块目录 `blocks/`）；
   - `Put`：流式读 → 同时算 xxh3（+可选 sha256）→ 写 `<fp>.tmp-<rand>` 临时文件 → 完成后 `rename`
     到 `blocks/<fp[0:2]hex>/<fp hex>.blk`（目标目录不存在则先 `MkdirAll`）；不做 fsync；
   - `Open`：读块头验证 → 流式重算数据指纹比对 → 不符 `ErrCorrupt`；通过返回 `BlockReader`
     （从块头之后读，`Size()` = block_size）；
   - `Remove`：refcount>0 或 pin>0 → `ErrInUse`；不存在 → `ErrNotFound`；
3. `cas/refcount.go` 实现：`Acquire`/`Release`/`Pin`/`Unpin`（内存表，进程内语义）；
4. 四场景单测（doc/7 硬性要求，测试名必须可对应）：
   - `TestConcurrentPutSameBlock`：N goroutine 并发 Put 相同内容 → 全部返回同一指纹、文件完整、
     目录无残留临时文件；
   - `TestCrashDuringWrite`：a) 注入失败点使 Put 中途终止 → 重开 Put 同内容成功、Open 正常；
     b) 预置孤儿 `<fp>.tmp-*` 文件 → 不影响 Open/后续 Put；
   - `TestDedup`：同内容两次 Put → 同一指纹、磁盘上仅一个块文件（含跨"路径"语义由内容决定，此处即同内容）；
   - `TestVerifyFailure`：篡改块数据（翻 1 字节）→ Open 返回 `ErrCorrupt`；篡改块头 magic → 同样报错；
     `VerifyXXH3SHA256` 模式下篡改 sha256 字节且内容指纹也改回 → 双重校验语义验证；
5. `internal/digest/digest_test.go`：XXH3_128/SHA256/NewXXH3/NewSHA256 正确性冒烟测试
   （M2 白名单内补建——M1 未建此文件，而 M2 验收含 `go test ./internal/...`）。

**交付物**：`cas` 与 `internal/digest` 全部导出符号实现；四场景测试。

**验收**：
```bash
cd core && go test ./cas/... ./internal/... -race   # 全绿
```
判据：① 四场景测试全部通过且 -race 干净；② `Remove` 在引用/pin 非零时返回 `ErrInUse` 有对应测试；
③ 不得引入 design.md §5.2 之外的导出符号。

## 5. 里程碑 M4：index 读写路径

**目标**：分片/manifest/CURRENT 序列化、无冲突提交、Catalog 加载与 Lookup。

**任务清单**：

1. `index/format.go` 实现：
   - `Entry`/`ShardRef`/`Manifest` 序列化（JSON，`cas.Fingerprint` 编码为 hex，`Entry.Fingerprint`
     用 `json.Marshaler`/`Unmarshaler` 或等价手段）；
   - 对象存储键函数（design.md §6.1）；`CurrentKey` 内容格式 `"<snapID> <fp8>"`（空格分隔、无换行）；
   - 分片构建：entries 按 `(path, chunk)` 字典序排序 → 按条目数切分（≤ `MaxEntriesPerShard`，
     默认 100_000）→ 每片算 xxh3 指纹 → 文件名 `shard-<fp8>.idx`；
2. `index/writer.go` 实现：`Commit` 无冲突路径——读 CURRENT（`ErrNoCurrent` 视为空数据集首次提交，
   `expectedETag=""`）→ 读当前 manifest 与受影响分片 → 合并 entries（upsert，同 `(path,chunk)` 覆盖）→
   构建新分片（未变更分片复用旧键不重传）→ 上传新分片与新 manifest → 四步验证（design.md §7.1 第 4 点）→
   `PutIfMatch` 提交 CURRENT；
3. `index/catalog.go` 实现：`Catalog` 构造、`Refresh`（下载 manifest → 逐分片下载验证指纹
   （不符 `ErrInvalidShard`）→ 构建内存映射 → `atomic.Pointer` 原子切换）、`Lookup`（未命中返回
   `(Entry{}, false, nil)`；无快照返回 `ErrNoCurrent`）；
4. 单测（mock objectstore + 临时目录 cas）：
   - `TestCommitAndLookup`：构造跨 3 分片（缩小 MaxEntriesPerShard 触发）的数据集 → Commit →
     Catalog 加载 → 全部 `(path,chunk)` Lookup 命中、字段逐项相等；
   - `TestLookupMiss`：未提交的 `(path,chunk)` → `(_, false, nil)`；
   - `TestShardFingerprintMismatch`：篡改一个分片对象 → Refresh 报 `ErrInvalidShard` 且旧映射仍可用；
   - `TestFirstCommit`：空对象存储（无 CURRENT）→ Commit 成功，CURRENT 内容格式正确；
   - `TestUpsertAndReuse`：第二次 Commit 只改 1 条 → 未变更分片对象键不变（复用，无重传）、
     变更分片为新键。

**交付物**：`index` 包读写路径实现与测试。

**验收**：
```bash
cd core && go test ./index/...                    # 全绿
```
判据：① 上述五个测试全过；② 分片对象键与 manifest 指纹字段一致；③ CURRENT 解析格式与 design.md §6.1 一致。

## 6. 里程碑 M5：index 并发提交 + 后台刷新

**目标**：条件提交冲突重试、并发提交正确性、刷新循环原子性。

**任务清单**：

1. `index/writer.go` 补全冲突路径：`ErrConflict` → 重读最新快照 → 基于它重新合并构建 → 再提交，
   上限 `CommitMaxAttempts`（默认 5）次，耗尽返回错误（含已尝试次数信息）；
2. `index/catalog.go` 补全：`Start(ctx)` 后台循环（`RefreshInterval` 默认 5s，ctx 取消退出；
   刷新失败不退出循环，记录错误）；
3. 并发单测（mock objectstore，mock 的 `PutIfMatch` 必须支持 ETag 变化模拟真实竞争）：
   - `TestConcurrentCommit`：20 goroutine 各自 Commit 不同 entries → 全部成功（或个别达重试上限后
     以明确错误结束）；最终 CURRENT 有效、manifest 可解析、所有分片指纹一致、**所有 entries
     全部出现在最终快照中**（无静默丢失）；
   - `TestCommitConflictRetry`：人为制造竞争（两个 Writer 基于同一 CURRENT 提交）→ 恰一个生效，
     另一个重试后基于新快照提交成功，两条数据都在；
   - `TestRefreshAtomicSwitch`：后台 Start 运行中持续 Lookup → 每次 Lookup 命中的结果永远属于
     **某一个完整快照**（新旧不混合，如 entry 集合与 snapshot 代次一致）；期间连续多次 Commit；
   - `TestRefreshErrorTolerance`：mock 注入一次分片损坏 → 刷新失败但循环继续、映射保持旧快照，
     修复后下一次刷新恢复。

**交付物**：并发提交与刷新实现及测试。

**验收**：
```bash
cd core && go test ./index/... -race              # 全绿，race 干净
```
判据：① 上述四个测试全过；② `-race` 无告警（原子切换与并发提交无数据竞争）；③ 冲突重试后无条目丢失。

## 8. 里程碑 M7：索引分片按前缀目录加载

**背景**：doc/7 新增「索引分片按前缀目录加载」——服务侧数据块按需下载但 manifest 全量，训练可能只需要 `/train-data` 下的数据；数据量上升后索引主体（分片）可达 GB 级，全量加载浪费。核心库 Catalog 提供「按前缀加载」能力；加载哪些前缀由 Agent 服务决定。主对话裁决：D22（ShardRef 增 MinPath/MaxPath）、D23（Catalog 增 LoadPrefixes，与 Refresh/Start 互斥使用模式）。

**任务清单**：

1. `index/format.go` / `index/writer.go`：`ShardRef` 增 `MinPath/MaxPath`（json `min_path`/`max_path`，D22），分片构建时填充（条目按 (path,chunk) 字典序排序后的首末 Path）；manifest 编解码同步；
2. `index/catalog.go`：实现 `LoadPrefixes`（D23 语义）：读 CURRENT → 下载 manifest（全量，小）→ 按 D22 范围交叠判定过滤相关分片（分片相关 ⟺ `MaxPath ≥ prefix` 且 `MinPath ≤ prefix 或 MinPath 以 prefix 开头`；多前缀取并集、同一分片去重只下载一次）→ 只下载、校验（指纹不符报 ErrInvalidShard）、加载相关分片 → 构建局部映射 → atomic.Pointer 原子切换；空 prefixes = 空映射；含空串元素 = 全量；失败不动旧映射；
3. 单测 `index/prefix_test.go`（新建）：
   - `TestLoadPrefixes`：多前缀数据集 → 只下载相关分片（mock 计数断言无关分片零下载），Lookup 命中相关前缀条目、未命中无关条目（miss 语义同 Refresh 代）；
   - `TestLoadPrefixesRangeOverlap`：分片边界跨前缀（一片含两个前缀的条目）→ 任一前缀命中即加载该分片、只下载一次；
   - `TestLoadPrefixesEmpty`：空列表 → 映射为空（全部 miss）；含空串元素 → 全量（等价 Refresh 全量）；
   - `TestLoadPrefixesErrorKeepsOldMapping`：相关分片注入损坏 → 返回 ErrInvalidShard 且旧映射仍可用（与 Refresh 错误语义一致）；
4. 既有 index 测试（M4–M6 全部）不改动且保持全绿。

**交付物**：ShardRef 范围字段 + LoadPrefixes 实现 + 4 个新单测。

**验收**：

```bash
cd core && go build ./... && go vet ./... && gofmt -l .     # 全绿、输出为空
```
