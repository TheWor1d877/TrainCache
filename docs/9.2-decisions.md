# S3 合并回源网关决策记录

| 决策 | 备选 | 未采用的原因 |
|---|---|---|
| D1 | 去掉 `S3Store.Get` 里的 `Stat`；网关合并 HEAD 与 GET | 前者修改 core 取数语义并重做错误映射；后者实现复杂度高于收益 |
| D2 | 纯 HTTP 反向代理，原样转发再重签 | PUT 要解 `aws-chunked`、List 要处理分页，出错面大 |
| D3 | 只保留 header，用 ctx 回写请求结果；或只保留 XML Code | 只保留 header 要跨层隐式回写；只保留 Code 违背 `9.0` 冻结的判断标准 |
| D4 | 只在 Store 层读 Code；只在传输层读头 | 前者丢失基线判断标准；后者拿不到类型化错误 |
| D6 | 允许部分写后重试，由调用方截断文件 | `Store` 接口不能截断，越界修改接口 |
| D7 | 缓冲等于块大小；沿用 5MiB | 等于块大小时 32 并发要 2GiB；5MiB 覆盖不了 8MiB 块 |
| D10 | 发起者直接写自己的响应，其余人订阅 | 发起者客户端一慢就阻塞拉取协程，造成队头阻塞 |
| D11 | 严格按 `L/|A|` 分额；加权公平 | 单 dataset 时额度闲置；加权与 `9.0` 的「不做加权」冲突 |
| D14 | 多副本加一致性哈希；Recreate | 多副本把同一个 key 的请求分到不同实例，合并失效；Recreate 停机更久 |
| D17 | 网关自己实现 `?location=` 响应 | 多一个接口面，且 Agent 侧一行配置就能避免 |
| D21 | 现在就冻结网关指标 | 端口与标签口径随实验调整，先冻结会返工 |
| D23 | COND v3 增 `environment.gateway` 与 `environment.gateway_image` | 网关 digest 不并进 9 键 `image_set` |
| D29 | 缓存默认关闭，由部署方显式开启 | 主场景是按 GB 计费的公有云桶，收益面该在默认位置；只有零收益部署才成立 |
| D30 | 内存 + 磁盘两层缓存 | 内存装不下 8GiB、32GiB 两档；能接的量与在途环形缓冲重叠，还要新写一套访问簿记与重启恢复 |
| D31 | 缓存配额按活跃 dataset 均分 | dataset 数一变就触发一轮淘汰，触发条件在别的 dataset 来请求那一刻，跑分算不出这一步 |
| D34 | 盘侧另设一套额度；或读盘不建条目、各自直发响应 | 两套额度要把稳态内存账重算；不建条目就丢掉同一块并发命中时的字节共享 |
| D35 | 给缓存卷设 `sizeLimit` | 超限由 kubelet 驱逐 Pod，淘汰压力变成调度事件，实验不可复算 |

## D1 只合并块 GET，HEAD 与其他方法不进合并路径

结论：只有 `<dataset>/blocks/` 前缀的 `GET` 进在途表。`HEAD` 原样转发源站，不合并。`CURRENT`、`manifest`、`snapshots/` 下的 `GET` 直通。`PUT`、`DELETE`、`LIST` 不经网关。

理由：`core/objectstore.S3Store.Get` 实际是 HEAD + GET 两次请求（minio-go 的 `Object.Stat()` 走 `StatObject`），与基线设想的单次 GET 不同。只合并 GET 可以在不修改 `core` 取数语义的前提下拿到 1/N 的字节收益。`CURRENT`/`manifest` 是快照指针，合并会把旧值返回给迟到的跟随请求，使 5s 跟随停在旧快照上。

影响：源站请求数是 N 个 HEAD + 1 个 GET，回源字节是 1/N。`9.1` K3 记录这条成本，实验报告按字节口径对比。

验证：`gateway/internal/server` 的路由用例断言四类请求各自进入哪条路径；`agent/svc` 用例断言非 `Get` 方法全部走源站客户端。

## D2 网关对外只服务 GET 与 HEAD

结论：网关只实现 GetObject 与 HeadObject 两种对象操作，其余方法回 405。服务范围见 `9.1` 附录 A。

理由：Agent 是只读的，唯一取数入口是 `Get`；`List`、`Put`、`PutIfMatch`、`Delete` 分别用于枚举、读者声明（reader claim）、条件写探测与 GC，全部可以直连源站，没有合并价值。全代理要处理 `aws-chunked` 解框、List 分页、条件写语义，工作量和出错面都大。

影响：网关不转发 PUT 与 LIST；`9.0` 只要求降低回源，没有规定全代理。

验证：契约测试对 PUT/DELETE/LIST 断言 405；对 GET/HEAD 断言正常转发。

## D3 失败响应形态：503、响应头与 XML 错误码

结论：网关自身失败回 `503`，带 `x-traincache-gateway: unavailable`，响应体为 S3 XML `<Error><Code>XTraincacheGatewayUnavailable</Code>…</Error>`。容量拒绝回 `503`，只带 `<Code>XTraincacheGatewaySlowDown</Code>`，不带响应头。源站错误原样透传，两者都不带。

理由：S3 的错误体是 XML，minio-go 只解析 XML；回 JSON 时 `ErrorResponse.Code` 为空，类型化错误无从产生。响应头是 `9.0` 冻结的判断标准，只能在传输层读；Code 在 S3Store 层读。reject 不属于「网关失效」，不带响应头，避免响应头语义分叉。

影响：`core/objectstore` 同时认响应头与 Code，两者取值在 `9.1` 4.2 与 4.4 冻结。

验证：`gateway/internal/server` 的错误响应用例逐字段断言；`core/objectstore` 的错误分类用例覆盖「只有响应头」「只有 Code」「两者都有」「两者都无」四种组合。

## D4 判断标准的实现方式：传输层看响应头，Store 层看 Code

结论：`Get` 在 ctx 里放一个每请求的信号结构，包装过的 `RoundTripper` 读到 `x-traincache-gateway` 就写进去；`S3Store.Get` 结合信号与 `ErrorResponse.Code` 产出 `ErrGatewayUnavailable` 或 `ErrGatewayRejected`。

理由：minio-go v7.3.0 的 `ErrorResponse` 只有 `Code`、`Message`、`StatusCode`，没有响应头字段。要让判断标准真的认这个响应头，只能在 `RoundTripper` 层拿。信号挂在请求 ctx 上，不用共享变量，避免并发请求互相误判。

影响：`S3Store` 增加可选 Transport，`NewS3Store` 签名保持不变，新增 `NewS3StoreWithOptions`。ctx 信号只在 `core/objectstore` 内部使用，不进接口。

验证：用 `httptest` 源站返回带响应头的 503，断言 `Get` 返回 `ErrGatewayUnavailable`；去掉响应头只保留 Code，结果相同。

## D5 降级状态机

结论：进程内四个量：`mode`、`gen`、`nextProbe`、`backoff`。初始退避 10s，每次失败翻倍，上限 120s；探测成功清零。探测权用 CAS 抢占，抢占后把 `nextProbe` 推到 5s 后，同一时刻最多一个探测请求。失败结果按 `gen` 丢弃。

理由：基线写明「下一次回源请求当探针」「失败间隔按退避拉长」。没有代际校验时，恢复瞬间到达的旧失败结果会把状态又打回直连，状态来回切换。CAS 占位避免 8 个并发取数同时发到网关。

影响：状态不写 CRD，Agent 重启回到配置默认。

验证：状态机单测覆盖 10s→20s→40s→80s→120s→120s 序列、并发探测只放行一个、恢复后旧结果被丢弃。

## D6 同一次 Get 的重试边界：已写字节为 0

结论：网关失败或拒绝时，只有在尚未向调用方 `w` 写入任何字节的前提下，才在同一次 `Get` 内改为走源站一次。已写字节非 0 直接返回错误。

理由：`core/fetch` 用 `io.Pipe` 把 `Get` 接到 `cas.Put`，部分字节已经落进临时文件。重试会从头再写一遍，污染内容。网关在写出响应体之前完成准入与拒绝，这条规则对 reject 总是成立。

影响：`backendStore` 用计数写入器判断，不修改 `Store` 接口，也不修改 `core/fetch`。

验证：用例让网关在写 0 字节时失败 → 断言走源站；让网关在写 1024 字节后断流 → 断言不改走源站、直接返回错误。

## D7 环形缓冲 10MiB 与生命周期

结论：单块环形缓冲默认 10485760 字节。拉取协程只在 `written` 与 `buf` 上推进，不看订阅者进度。归还条件是拉取协程结束且订阅者计数为 0。

理由：10MiB 大于实验块 8MiB，整块都能被后到者读取；生产 64MiB 块覆盖前 16%。基线的 5MiB 会让 8MiB 块只有前 60% 可合并。基线的归还条件「最后一个订阅者被踢就归还」存在一种时序：订阅者全被踢、拉取协程仍在写，缓冲被下一个条目复用时，上一个对象的字节会进入新对象的响应。归还条件因此加上拉取协程已结束。

影响：稳态内存 32 × 10MiB = 320MiB。池不限容量。

验证：缓冲单测覆盖绕回、踢人、最后一个订阅者离开后归还、拉取协程未结束时禁止归还。用 `-race` 运行并发读写用例。

## D8 迟到订阅者不加入

结论：`written > cap(buf)` 时到达的请求不加入在途表，直接发起一次独立回源，与开关无关。

理由：它从 0 开始读，而 0 处的字节已经被覆盖。加入后立刻触发踢出，只是多一次无用的挂载与唤醒。提前判断可以让它直接走独立回源，路径更短。这一分支也不查盘：在途条目收尾时才 rename，条目还在表里就意味着盘上没有这块。

影响：并发请求落到「独立回源」分支时仍然占准入额度，源站请求数会增加。这是合并窗口的真实边界；缓存层接走的是错峰到达的那一部分，同一个块在途期间的迟到者仍要付一份字节，付完把字节写进盘，下一次同样请求就从盘上读。

验证：用例让拉取协程写满 `cap+1` 字节后再发起请求，断言没有加入条目、走了独立回源；开关打开时同一用例断言该块落到盘上、条目名是 rename 之后的正式名。

## D9 被踢订阅者直连

结论：加入后落后超过 `cap` 的订阅者被摘除，HTTP 响应以截断结束。Agent 侧由 `core/fetch` 的既有重试重新发起一次 `Get`。

理由：网关已经向客户端发出了 200 和部分响应体，无法修改状态码，也无法回滚已发送的字节，响应只能以截断结束。`core/fetch` 的重试会重新走一次 `Get`，这次可能合并成功，也可能再次被踢。

影响：被踢的那次传输浪费了已发送的字节。60s 汇总里的 `kicked` 用来观察这个成本。

验证：用例让订阅者停止读取，断言被摘除且连接关闭；Agent 侧用例断言截断错误会触发 `fetch` 重试。

## D10 拉取协程模式：所有请求都是订阅者

结论：每个在途条目由一个拉取协程从源站读并写环形缓冲；发起请求本身也作为订阅者从缓冲读，不直接写自己的响应。

理由：发起者直接写客户端时，客户端一慢，拉取协程就阻塞，所有订阅者一起停，正是基线要防的队头阻塞。把发起者当作普通订阅者后，慢的一方只影响自己，超限被踢。

影响：发起者也可能被踢，此时它的响应同样截断。拉取协程在所有订阅者都离开后取消源站请求。

验证：用例让第一个请求的响应写入器阻塞，断言其他订阅者继续收到完整数据，第一个请求被踢。

## D11 公平准入算法

结论：按 `9.1` 6.5 的规则派发：`base = clamp(L/|A|, 1, L/2)`，`inflight < base` 放行；全局有空位且没有其他 dataset 排队时也放行；否则排队。排队上限 64，等待上限 2s，超时回 `SlowDown`。

理由：只按 `L/|A|` 分配时，只有一个活跃 dataset 会被封在 `L/2`，剩下的额度闲置。加「没有其他排队者就放行」这一条，单 dataset 能用满 `L`，同时保留「一个 dataset 不能占满全部额度、把另一个饿死」的约束。

影响：不做加权、不做抢占。已在途的请求不因份额变化被中止。

验证：调度单测覆盖单 dataset 用满、两个 dataset 各半、三 dataset 保底 1、排队超时、队列满、空闲份额转移。

## D12 到桶并发 64

结论：`gatewayBucketConcurrency` 默认 64，`traincache-config` 写同名值。

理由：Agent 每进程 16 个下载任务（`core/fetch` 默认），bench 的 warmup fanout 默认 2，预热阶段两个 Agent 合计 32 条连接；放行后落点节点若不在预热集合里再起 16 条需求读，峰值约 48。64 高于这个峰值，不会先于 Agent 侧成为瓶颈。

影响：内存上限随并发线性增长，准入缓冲 64 × 10MiB = 640MiB，另加热池 32 块；网关 Deployment 内存上限 1.5Gi。

验证：配置用例断言默认值；ConfigMap 写 64；bench 脚本不再改写该项。

## D13 源站错误一律透传

结论：网关到源站的连接失败、TLS 失败、超时回 504 + `XTraincacheGatewayOriginUnavailable`，不带 `unavailable` 头；源站返回的 4xx/5xx 原状态码、原 Code 透传。

理由：`9.0` 写明「源站透传上来的 5xx 不算，否则会把源站的问题盖成网关的问题」。连不上源站根因在源站，如果算成网关失效，源站不可达时会让所有节点降级，掩盖真实故障。

影响：Agent 看到源站错误时按普通取数失败处理，`core/fetch` 重试，不切后端。

验证：契约测试让源站返回 500/403/429，断言该响应头不存在、Code 与源站一致；让源站端口关闭，断言 504 且无响应头。

## D14 单副本与 SIGTERM 排水

结论：`replicas: 1`，不做 HPA。Deployment 用 `RollingUpdate`（`maxUnavailable: 0`，`maxSurge: 1`）。收到 SIGTERM 后 `readyz` 立即 503，停止接受新连接，等在途请求结束或 30s，再退出。`terminationGracePeriodSeconds: 40`。

理由：多副本会让同一个 key 的请求落到不同实例，合并失效，「合并」只在单实例内成立。单副本更新必然有一次切换，但可以把「连接被重置」改为「新连接去新 Pod、旧请求正常收尾」。不排水时，一次镜像更新会让所有节点命中降级判断标准，切换为直连。

影响：更新期间最长 30s 的旧 Pod 收尾时间。超过 30s 的请求按失败处理。

验证：集成用例在持有长连接时发送 SIGTERM，断言旧连接写完、新连接被拒；`kubectl rollout` 用例断言更新期间 Agent 不出现降级。

## D15 配置键与落位

结论：`traincache-config` 现 15 项。网关层已加 `gatewayEndpoint`、`gatewaySecure`、`gatewayBucketConcurrency`、`gatewayBlockBufferBytes`，缓存层再加 `gatewayCache`、`gatewayCacheDatasetBytes`、`gatewayCacheTotalBytes`，共 18 项。Agent DaemonSet 引用 `gatewayEndpoint`、`gatewaySecure` 两项；网关 Deployment 引用其余五项与三个 `objstore*`。缓存根目录是代码常量，不进 ConfigMap。

理由：按 `docs/PARAMETER-CONFIGURATION.md` 的落位判据判断。换集群或换实验轮次要修改的值写进 ConfigMap。凭证走 Secret。挂载路径属于清单拓扑，写成 volumeMount 的字面值。

影响：`hack/verify-config-placement.sh` 的 `WORKLOADS` 已含网关 Deployment，缓存三键由它引用即可通过；任一键漏引用会被判为孤立键，门禁失败。

验证：`make verify-metadata` 通过，ConfigMap 项数与清单引用一一对应。

## D16 `gatewaySecure` 独立于 `objstoreSecure`

结论：Agent 到网关是否 TLS 由 `TRAINCACHE_GATEWAY_SECURE` 单独控制，默认 false，与 `TRAINCACHE_OBJSTORE_SECURE` 无关。

理由：源站是云端 HTTPS 时 `objstoreSecure=true`，如果复用，Agent 会用 TLS 连集群内的网关，与「Agent 到网关默认明文」直接冲突。

影响：ConfigMap 多一个键。网关自己不监听 TLS。

验证：配置用例断言两个 env 独立；集成用例在 `objstoreSecure=true`、`gatewaySecure=false` 下断言明文连通。

## D17 网关客户端固定 Region

结论：Agent 构造网关 S3Store 时设置 `Region`，使 minio-go 不发送 `GET /<bucket>?location=`。

理由：minio-go 在区域（region）为空且缓存未命中时会先请求 bucket location，这次请求也会发到网关，多出一条本可以不存在的接口面。固定区域后网关只需处理 GET 与 HEAD。

影响：`Options` 增加 `Region` 字段，只对网关客户端设置；源站客户端保持不变。

验证：用记录请求的 `RoundTripper` 断言网关路径没有 `?location=` 请求。

## D18 单桶与 dataset 解析

结论：网关只服务配置里的一个桶，其它桶回 404 `NoSuchBucket`。dataset 取对象键第一个 `/` 之前的部分。

理由：`v1` 单桶是既有约定（`9.1` 5.1）。dataset 是公平调度与日志的区分字段，`BlockKey` 把 dataset 放在第一段。

影响：多桶需求出现时要修改配置模型。

验证：路由用例覆盖桶名不符、dataset 带连字符、路径含 `#`。

## D19 日志复用 `core/logging`

结论：网关用 `core/logging` 的脱敏与采样处理器，`component=gateway`，`log_schema_version=1`；`gateway/internal/logging` 只做初始化薄封装。

理由：脱敏、采样、动态级别是三条既有契约，重写会分叉。`agent/internal/logging` 已经证明这套封装够用。

影响：`docs/8.1` 的 `component` 固定枚举含 `gateway`；对应决策为 `docs/8.2` ADR-015。

验证：日志断言用例检查 `component/version/log_schema_version` 三字段与脱敏结果。

## D20 60s 汇总日志

结论：网关每 60s 输出一条 Info，字段见 `9.1` 7.3，固定消息 `gateway: 60s 汇总`。

理由：网关没有指标端点，实验靠 `merged`、`owners`、`cache_hit` 三列对账合并命中率、回源次数与缓存命中率。沿用 `logagg` 的 60s 汇总做法，日志即可回答「合并与缓存有没有生效」。

影响：日志量恒定，每分钟一行。

验证：日志断言用例解析该行，断言 `owners`、`merged`、`kicked`、`rejected`、`cache_hit` 存在且为整数。

## D21 网关不暴露 `/metrics`

结论：网关不暴露指标端点，不加网关侧指标族。

理由：端口与标签口径随实验调整，汇总先走日志，避免现在就冻结一套要改的契约。

影响：Prometheus 抓不到网关内部状态；实验用 60s 汇总对账。

验证：部署清单里没有网关的 metrics 端口；`docs/8.1` 的抓取配置不变。

## D22 Agent 侧新增两个指标族

## D23 bench 开关与 COND

结论：`run_bench.py` 增环境变量 `TRAINCACHE_GATEWAY=1`，透传到 `traincache/up.sh`；`summary.csv` 增一列 `gateway`（0/1）。COND v3 的 `environment` 增两个键：`gateway`（bool）与 `gateway_image`（string/null）。网关 digest 写在 `gateway_image` 上，9 键的 `image_set` 文件不变。缓存层再加一个开关：`TRAINCACHE_GATEWAY_CACHE=0/1`，由 `bench/scripts/ctrl_up.sh` patch 进 `traincache-config` 的 `gatewayCache`；`summary.csv` 增一列 `gateway_cache`（0/1），COND 的 `environment` 增 `gateway_cache`（bool），`gateway=false` 时 `gateway_cache` 必须是 false。

验证：`run_bench.py --selftest` 断言两列与透传；`summarize_compare.py --selftest` 断言按 `gateway`、`gateway_cache` 分组；`cond.py` 自测断言 `gateway=false` 且 `gateway_cache=true` 被判为非法 COND。

## D24 包结构与依赖方向

结论：新增 `traincache/gateway` 模块，内部按 `config`、`logging`、`server`、`merge`、`sched`、`origin`、`obs`、`cache` 分包。`gateway` 不 import `agent/*`、`controller/*`、`core/objectstore`。

理由：与 `core`、`agent` 的分层习惯一致：入口薄、internal 按职责分包、依赖单向。网关与 Agent 的错误码常量各写一份，避免为了两个字符串引入跨模块依赖。`cache` 只认标准库与自己的 `Metadata`，盘上字节交给 `merge` 时只是一个 `io.Reader`，这样环形缓冲那一侧不需要知道字节从盘上还是从源站来。

影响：`go.work`、`Makefile`、CI matrix、镜像构建各含网关一项。`gateway` 镜像的运行面从只读空目录变成要一块可写盘。

验证：`go list -deps` 断言依赖方向，含 `cache` 不依赖 `merge`、`origin`；`make verify-gateway` 通过。

理由：9410 是 Agent gRPC，9411 是 Agent 指标端口，9412 是 controller-manager metrics。9413 未被占用。探针与 S3 同端口时路径不冲突。

影响：Deployment 的 `containerPort`、Service 的 `port`、探针路径统一到 9413。

验证：`kubectl get svc` 与探针实际通过；端口冲突用例由部署验证覆盖。

## D26 不做 AIMD、零拷贝、请求分级

结论：三项都不做。

理由：回源次数从 N 降到 1，降幅已经足够；零拷贝在「1 份源字节扇出 N 路 + 迟到者重放」下不成立，且有 TLS 时失效；S3 GET 不携带优先级，网关再分一套会与上游的「在读/预铺」折叠冲突。三条理由来自 `9.0`。

影响：网关只用环形缓冲一种数据通路。

验证：设计评审确认没有引入第二套缓冲或分级队列。

## D27 网关客户端固定 Region 与 MaxRetries

结论：网关客户端的 `Options` 在构造时写入 `Region="us-east-1"` 与 `MaxRetries=1`；源站客户端两值都不设，保持 `NewS3Store` 的既有行为。

背景：minio-go 对 503 默认按全局 `minio.MaxRetry` 退避重试 10 次；`Region` 为空且缓存未命中时还会先发 `GET /<bucket>?location=`。网关的 503（准入拒绝、自身不可用）是控制信号，交给 Agent 立即回退直连或进入降级；SDK 放大重试会把一次信号变成十次请求，并挤占调用方的超时预算。`Region` 的取值与理由同时见 D17。

理由：这两个值决定客户端行为，不是部署参数，所以固定在 `agent/svc` 的构造常量里，不开放 env。`MaxRetries` 在 minio-go v7.3.0 中语义为总尝试次数，1 即不重试；`Options.MaxRetries` 只覆盖网关客户端，源站仍用 SDK 默认。

影响：`core/objectstore.Options` 增加 `Region string` 与 `MaxRetries int` 两个字段，`NewS3StoreWithOptions` 在 `MaxRetries > 0` 时写入 `minio.Options.MaxRetries`（0 表示沿用全局默认）；`NewS3Store` 不经过这两个字段。

验证：`gateway_test.go` 的 `TestGatewayMaxRetriesOverridesSDKDefault` 把 `minio.MaxRetry` 恢复为 SDK 默认 10，断言一次 `Get` 的 GET 次数 ≤2；`?location=` 的缺席由记录请求的 `RoundTripper` 断言（D17）。

## D28 合并响应回填 Last-Modified 与 ETag

结论：块键 GET 的合并响应在写 200 之前回填源站对象的 `Last-Modified` 与 `ETag`，不设 `Content-Length`（保持 chunked）。元数据复用这次 GET 的响应头，不额外发 HEAD。

背景：minio-go v7.3.0 的 `utils.go` 中 `ToObjectInfo` 对每个 GET 响应无条件解析 `Last-Modified`，缺失即返回 `InternalError`。合并响应若只写状态码与字节，Agent 的每次块读（`GetObject` → `io.Copy`）都会在首次读时报 `Last-Modified time format is invalid` 而失败。

理由：GET 响应本身已带 `Last-Modified` 与 `ETag`，直接捕获复用即可，保持 K3 的「N 次 HEAD + 1 次 GET」预算，不引入额外源站请求。minio-go 的 `Object.Stat` 在 v7.3.0 会把 `objectInfo.Size` 改写成剩余字节数，而 `Object.Read` 用该值判断 EOF，读流中调用会截断响应体，所以元数据在传输层从这次 GET 的响应头记录，不走 `Stat`。`Last-Modified` 缺失时只记 Debug，不阻断下载。

影响：`origin.Open` 返回 `*origin.Object`，新增 `Stat()` 读取 GET 响应头（`metadataTransport` 捕获，不发请求）；`merge.Entry` 增加 `SetMetadata`/`Metadata`，由拉取协程在首次读到字节时写入；`serveWithSub` 与 `serveIndependent` 在写 200 前回填两个头，不写 `Content-Length`。

验证：`gateway/internal/server/integration_test.go` 的 `TestIntegrationMinioClientMergesBlock` 断言 5 个客户端的 `ReadAll` 全部成功、源站 `GET=1`/`HEAD=5`，且每个合并响应带预期 `Last-Modified` 与 `ETag`、无 `Content-Length`。

## D29 缓存开关默认开启

结论：`gatewayCache` 默认 `true`，代码默认值同为 true，关闭要显式写 `false`。

理由：主场景是按 GB 计费的公有云桶，收益面放在默认位置上。该关的是零收益或负收益的部署：数据集小于节点本地盘（块一直留在节点盘上，9.0「缓存层」的三条命中来源少一条）、工作集大于单 dataset 上限（块在第二次被读到之前就被淘汰，只付写不付命中）、网关侧只有 HDD 且命中侧合计读速率超它（@1000 档 4 节点 500MB/s 对 HDD 顺序读低于 300MB/s）、源站不按流量计费且出口带宽快于集群取速率（省的那份字节单价为零）。最后一种情况下网关照挂，TLS 与回源 GET 次数的收益与缓存无关。

影响：关闭态走改动前的代码路径，不查盘也不写盘，两个实验臂除这一项之外完全相同。

验证：`config_test.go` 断言未设置与显式取值的结果；e2e 脚本两态各跑一次，断言关闭态 `cache_hit` 恒为 0 且缓存目录不产生文件。

## D30 缓存只做磁盘一层

结论：单层磁盘，不做内存层。

理由：bench 三档数据集 2GiB、8GiB、32GiB，内存装不下后两档。内存层要接的是环形缓冲窗口关闭之后仍被重复读的块，实验块 8MiB 整块落在 10MiB 缓冲内，@100 档窗口 0.67s、@300 档 0.225s，这一段与在途缓冲重叠；独立内存层还要新建一套块级访问簿记和重启恢复语义。

影响：内存账不变，稳态仍是并发额度 × 10MiB。

验证：`cache` 包只有盘上路径，没有第二套缓存结构；稳态用例断言堆不随读盘命中增长。

## D31 配额用固定上限，不做活跃 dataset 均分

结论：单 dataset 上限默认 32GiB，全局总上限默认 64GiB，两个值都进 `traincache-config`。活跃 dataset 之间均分配额不做。

理由：均分在 dataset 从 2 个变 4 个时把配额从 1/2 压到 1/4，立刻淘汰掉还能用的数据，触发条件是别的 dataset 来请求，跑分时算不出这一步。QoS 的额度均分作用在几秒就归还的短期占用上，缓存配额作用在长期驻写上，两条规则不同形。

影响：两个数字要按节点盘剩余空间调；单 dataset 上限 ≤ 总上限由启动校验保证。dataset 数变化只影响能不能写进新块，不动已驻写的字节。

验证：配额用例覆盖 dataset 从 2 个变 4 个时已驻写字节不缩、单 dataset 超限只删自己、全局超限才按 dataset 回收。

## D32 落盘布局、原子写与 `.meta`

结论：对象键整段当缓存目录下的相对路径，dataset 是第一层目录；块写进 `<name>.tmp` 再 rename，`.meta` 存 `etag`、`last_modified`、`size` 三个值，与块同名加后缀，一起写一起删。

理由：dataset 当第一层，回收单位就是这一层目录，与公平调度的分片粒度对齐。rename 原子，`Lookup` 只认正式名，任何请求读不到半块。minio-go 对每个 GET 响应无条件解析 `Last-Modified`（D28），读盘命中也得给这两个头；块不可变，所以 `.meta` 里那份与 Agent 这次直通源站的 HEAD 结果一致。

影响：`cache` 包不 import minio-go，元数据用自定义的 `Metadata`，转换在 server 层。键的任一分段超过 255 字节时跳过写盘，回源与合并照常。

验证：用例断言 rename 之前 `Lookup` 返回未命中；断言读盘响应的 `ETag` 与 `Last-Modified` 与写盘时记录的一致。

## D33 last-touch 表与三步淘汰

结论：dataset 的最后出现时间记在进程内存的一张表里，读命中与写盘成功都刷新，启动时 `Scan()` 按 dataset 目录的 mtime 填表。淘汰三步：dataset 超自己的上限就按块文件 mtime 从老到新删；全局仍超总上限就按 last-touch 表删最久没出现的 dataset 整个目录；仍放不下本次就不写盘。

理由：Linux 上目录 mtime 只在条目增删时变，一轮实验读 20 分钟全命中时 mtime 不动，按目录 mtime 判空闲会误删正在被读的 dataset。块级 mtime 是写盘时间，第 1 步是先写先删；空闲判断只用在 dataset 一层的第 2 步。

影响：进程重启后表由启动扫描重建，Pod 重建后目录本就是空的。第 3 步不写盘只影响下一次命中率，请求照原路返回。

验证：用例覆盖三步各删什么、`.meta` 与块同批删、放不下时盘上文件数不增加。

## D34 读盘与回源共用一条扇出路径

结论：读盘命中同样建 `merge` 条目、同样占一个准入槽，owner 一侧的 reader 从 `origin.Object` 换成盘上的 `Object`；订阅者、游标、踢出规则都不变。

备选两套额度或分开的理由：分两套要么把稳态内存账（并发额度 × 10MiB）写歪，要么为盘侧再建一套簿记。扇出要的是「一份字节分给 N 个响应」，与字节从哪来无关。

影响：`merge` 包不感知字节来源。代价是命中也要排队，队满时按 D3 的 reject 回退直连，不写降级状态。60s 汇总的 `cache_hit` 列与条目结束行的 `from` 字段由 server 层记。

验证：集成用例并发 5 个读盘 GET，断言五份字节一致、条目数为 1、源站 GET 不增加。

## D35 缓存卷用 emptyDir，不设 sizeLimit

结论：网关 Pod 在缓存路径挂一个 `emptyDir`，不设 `sizeLimit`；容器仍保持 `readOnlyRootFilesystem: true`，可写面只有这一个卷。

理由：写满多少字节由网关自己的配额与淘汰控制。`sizeLimit` 一到，kubelet 驱逐 Pod，淘汰压力变成调度事件，实验里不可复算，缓存也照样清空。

影响：Pod 重建后盘是空的（K9），容器重启（同一 Pod）盘上内容还在。`emptyDir` 落在节点盘上，与 Agent 的 CAS 缓存同一个文件系统（K10）。

验证：e2e 脚本删掉网关 Pod 后断言第一轮 `cache_hit` 为 0、第二轮起命中；断言缓存占用超过总上限时 Pod 不被驱逐，只有网关自己的淘汰行出现。
