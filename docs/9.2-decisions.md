# S3 合并回源网关决策记录

## D1 只合并块 GET，HEAD 与其他方法不进合并路径
结论：网关只实现 GetObject 与 HeadObject，只有 `<dataset>/blocks/` 前缀的整对象 `GET` 进在途表，`HEAD` 原样转发源站，`CURRENT`、`manifest`、`snapshots/` 下的 `GET` 直通，`PUT`、`DELETE`、`LIST` 一律 405、由 Agent 直连源站。
原因：`S3Store.Get` 实际是 HEAD 加 GET 两次请求，只合并 GET 能在不修改 `core` 取数语义的前提下拿到 1/N 的字节收益，代价是每个块仍从源站过一次 HEAD；`CURRENT` 与 manifest 是每 5s 变一次的快照指针，合并会把旧值返给迟到的跟随请求；Agent 是只读的，`List`、`Put`、`PutIfMatch`、`Delete` 分别用于枚举、读者声明、条件写探测与 GC，全代理要解 `aws-chunked`、处理分页与条件写语义，出错面大于合并价值。

## D3 失败响应形态：503、响应头与 XML 错误码
结论：网关自身失败回 503，带 `x-traincache-gateway: unavailable`，响应体是 S3 XML 且 `Code` 为 `XTraincacheGatewayUnavailable`；容量拒绝回 503、`Code` 为 `XTraincacheGatewaySlowDown`、不带该响应头；源站错误原样透传、两者都不带。
原因：minio-go 只解析 XML 错误体，回 JSON 时 `ErrorResponse.Code` 为空、类型化错误无从产生；响应头是冻结的判据、只能在传输层读，Code 在 Store 层读；容量拒绝不是「网关这一跳坏了」，带上响应头会让同一句话既表示故障又表示忙。

## D4 判断标准的实现方式：传输层看响应头，Store 层看 Code
结论：`Get` 在 ctx 里放一个每请求探针，由包装过的 `RoundTripper` 读到 `x-traincache-gateway` 就写进探针，Store 层结合探针与 `ErrorResponse.Code` 产出 `ErrGatewayUnavailable` 或 `ErrGatewayRejected`；探针只在 `core/objectstore` 内部使用，不进接口。
原因：minio-go v7.3.0 的 `ErrorResponse` 只有 `Code`、`Message`、`StatusCode` 三个字段、没有响应头，要真的认这个头只能在传输层拿；信号挂在请求 ctx 而不是共享变量，避免同一进程并发的多个请求互相误判。

## D5 降级状态机
结论：Agent 进程内四个量 `mode`、`gen`、`nextProbe`、`backoff`，初始退避 10s、每次失败翻倍、封顶 120s，探测成功清零；探测权用 CAS 抢占，抢到就把 `nextProbe` 推到 5s 后，失败结果按 `gen` 丢弃。
原因：基线要求把下一次回源请求当探针、失败间隔按退避拉长；没有代际校验时，恢复瞬间才到达的旧失败结果会把状态又打回直连，来回切换；没有抢占时一批并发取数会同时冲到已经判定失效的网关上。

## D6 同一次 Get 的重试边界：已写字节为 0
结论：网关失败或拒绝时，只有向调用方写出的字节数为 0 才在同一次 `Get` 内改走源站一次，已写字节非 0 直接返回错误；由 `backendStore` 的计数写入器判断，不修改 `Store` 接口也不修改 `core/fetch`。
原因：`core/fetch` 用 `io.Pipe` 把 `Get` 接到 `cas.Put`，部分字节已经落进临时文件，同次重走源站会从头再写一遍污染内容；网关在写出任何响应体字节之前完成准入判定，所以这条规则对容量拒绝总是成立。

## D7 环形缓冲 10MiB 与归还条件
结论：单块环形缓冲默认 10485760 字节（`TRAINCACHE_GATEWAY_BLOCK_BUFFER_BYTES`），拉取协程只在 `written` 与 `buf` 上推进、不看任何订阅者进度；归还条件是拉取协程结束且订阅者计数为 0，由最后离开的一方归还且只归还一次。
原因：10MiB 大于实验块 8MiB，整块都能被后到者追上，生产 64MiB 块覆盖前 16%，基线的 5MiB 连 8MiB 块都盖不住；基线原写的归还条件「最后一个订阅者被踢就归还」存在订阅者全被踢而拉取协程仍在写的时序，缓冲此时被下一个条目复用会把上一个对象的字节混进新对象的响应。

## D8 迟到的请求不加入在途条目
结论：请求到达时若条目在途但 `written` 已超过一个缓冲容量，它不加入条目，而是自己占一个准入额度发起独立回源，与缓存开关无关；这条分支不查盘。
原因：它从 0 开始读而 0 处的字节已经被覆盖，加入后立刻触发踢出，只多一次无用的挂载与唤醒；盘上的正式名是条目收尾时才 rename 出来的，条目还在表里就意味着这块还没落盘，查盘必然落空。

## D9 被踢订阅者以截断结束
结论：加入之后落后超过一个缓冲容量的订阅者被摘除订阅并关闭连接，响应以截断结束，由 Agent 侧 `core/fetch` 的既有重试重新发起一次 `Get`，网关不尝试改成错误码。
原因：状态码 200 和部分响应体已经发给客户端，既不能回写也不能回滚已发送的字节；被踢那次传输浪费掉的已发送字节用 60s 汇总的 `kicked` 列观察。

## D10 发起请求自己也走订阅通道
结论：每个在途条目由一个拉取协程从来源读字节写进环形缓冲，发起这个请求的客户端同样作为订阅者从缓冲取字节，不直接写自己的响应。
原因：发起者直接写客户端时，客户端一慢就把拉取协程堵住、所有订阅者一起停，正是基线要防的队头阻塞；改成普通订阅者后慢的一方只影响自己，超限被踢。

## D11 公平准入算法
结论：全局额度 L，活跃集合 A 是在途加排队大于 0 的 dataset，每份额 `base = clamp(floor(L/|A|), 1, floor(L/2))`，L 小于 2 时 base 取 L；在途数小于 base 放行，达到 base 后只有全局还有空位且没有其他 dataset 排队才放行；排队上限 64、单请求最长排队 2s，超时或队列满回 `XTraincacheGatewaySlowDown`；不做加权、不做抢占，已在途的请求不因份额变化被中止。
原因：只按 `L/|A|` 严格分配时单活跃 dataset 被封在 `L/2`、剩下一半额度闲置；只按「有空位就放行」分配时一个 WarmupTask 能把另一个饿死，两条合起来才同时满足用满与不饿死。

## D13 源站错误一律透传
结论：网关连不上源站、TLS 失败、超时回 504 加 `XTraincacheGatewayOriginUnavailable` 且不带 `unavailable` 头；源站返回的 4xx/5xx 用原状态码、原 `Code` 透传。
原因：源站的问题算成网关失效，就是把源站的故障盖成网关的故障；源站真的不可达时把所有节点一起判为降级，会掩盖真实故障原因，Agent 此时应按普通取数失败重试而不是切后端。

## D14 单副本、Recreate 与 SIGTERM 排水
结论：`replicas: 1` 不做 HPA，更新策略用 `Recreate`；收到 SIGTERM 后 `readyz` 立即转 503 让 Service 摘流，进程停止接受新连接，等在途 GET 结束或满 30s 再退出，`terminationGracePeriodSeconds` 取 40。
原因：多副本会把同一 key 的请求分到不同实例，合并只在单实例内成立；滚动更新会让旧 Pod 与新 Pod 各持一份在途表，扇出被分到两个进程；不排水时一次镜像更新会让所有节点同时命中失败判断标准、整体切到直连。

## D16 `gatewaySecure` 独立于 `objstoreSecure`
结论：Agent 到网关是否 TLS 由 `TRAINCACHE_GATEWAY_SECURE` 单独控制，默认 false，与 `TRAINCACHE_OBJSTORE_SECURE` 无关；网关自身监听仍是明文。
原因：源站是云端 HTTPS 时 `objstoreSecure` 为 true，复用这一个开关会让 Agent 用 TLS 去连集群内的明文网关，与「Agent 到网关默认明文」直接冲突。

## D17 网关客户端固定 Region 与 MaxRetries
结论：Agent 构造网关客户端时固定 `Region="us-east-1"` 与 `MaxRetries=1`，写在 `agent/svc` 的构造常量里、不开放配置；源站客户端两值都不设，沿用既有行为。
原因：Region 为空且缓存未命中时 minio-go 会先发 `GET /<bucket>?location=` 查桶位置，凭空多出一条接口面；SDK 默认对 503 退避重试 10 次，而网关的 503 是一次性控制信号，重试会把一次信号放大成十次请求并挤占调用方的超时预算——`MaxRetries` 在 v7.3.0 的语义是总尝试次数，1 即不重试。

## D20 网关观测走 60s 汇总日志、不暴露 /metrics
结论：网关不暴露指标端点、不加网关侧指标族，观测只靠每 60s 一条固定消息 `gateway: 60s 汇总` 的 Info，窗口切换用原子交换清零，保证每个请求的每个计数恰好落在一个窗口里。
原因：端口与标签口径会随实验调整，现在冻结一套指标就是等着返工；`merged`、`owners`、`cache_hit` 三列已经能回答「合并与缓存有没有生效」，日志量恒定每分钟一行。

## D26 不做 AIMD 背压、不做零拷贝、不做请求分级
结论：三项都不做，网关的数据通路只有环形缓冲一种，也不对请求分级。
原因：回源次数已经从 N 降到 1，降幅足够；零拷贝在「一份源字节扇出 N 路加迟到者独立重放」的形态下不成立，到源站那段有 TLS 时更失效；S3 GET 不携带上游优先级标记，上游 `core/fetch` 已把 P0 到 P3 折叠成在读与预铺两档准入，网关再分一套只会跟上游打架。

## D28 合并响应回填 Last-Modified 与 ETag
结论：块键 GET 的合并响应在写 200 之前回填源站对象的 `Last-Modified` 与 `ETag`，不设 `Content-Length` 保持 chunked；元数据从这次 GET 自己的响应头在传输层记录，不额外发 HEAD，缺失时只记 Debug 不阻断下载。
原因：minio-go v7.3.0 的 `ToObjectInfo` 对每个 GET 响应无条件解析 `Last-Modified`，缺失即报 `InternalError`，不回填则 Agent 的每次块读都在首次读时报时间格式非法；v7.3.0 的 `Stat` 会把 `objectInfo.Size` 改写成剩余字节数、而 `Read` 用该值判 EOF，读流中途调用会截断响应体，所以只能复用这次 GET 的头以保持 N 次 HEAD 加 1 次 GET 的预算。

## D29 缓存开关默认开启
结论：`gatewayCache`（env `TRAINCACHE_GATEWAY_CACHE`）默认 true，未设置即开，关闭要显式写 false；关闭态不构造缓存存储、不扫描盘、不查盘也不写盘，走改动前的取数路径。
原因：主场景是按 GB 计费的公有云桶，收益面该放在默认位置上；该关的是零收益或负收益的部署——数据集小于节点本地盘（块一直留在节点盘上）、工作集大于单 dataset 上限（块在第二次被读到之前就被淘汰）、网关侧只有顺序读低于 300MB/s 的 HDD 而命中侧合计读速率超过它、源站不计流量且出口快于集群取速率。

## D30 缓存只做磁盘一层
结论：只有一层磁盘缓存，不做内存层。
原因：bench 的数据集是 4 GiB 一档，内存装得下；内存层要接的是环形缓冲窗口关闭之后仍被重复读的块，而实验块 8MiB 整块落在 10MiB 缓冲内、@100 档窗口 0.67s、@300 档 0.225s，这一段与在途缓冲重叠，独立内存层还要新写一套块级访问簿记和重启恢复语义。

## D31 配额用固定上限，不做活跃 dataset 均分
结论：单 dataset 盘上驻写上限默认 32GiB，全局总上限默认 64GiB 且必须不小于前者，两个值都进 `traincache-config`；活跃 dataset 之间均分配额不做。
原因：均分会在 dataset 从 2 个变 4 个时把份额从 1/2 压到 1/4，立刻淘汰掉还能用的数据，而触发条件是别的 dataset 来请求的那一刻，跑分时算不出这一步；准入额度均分作用在几秒就归还的短期占用上，缓存配额作用在长期驻写上，两条规则不同形。

## D32 落盘布局、原子写与 `.meta`
结论：对象键整段当缓存根目录下的相对路径，dataset 是第一层目录；块先写 `<name>.tmp` 再 rename 成正式名，`.meta` 与块同名加后缀、存 `etag`、`last_modified`、`size` 三个值，与块一起写一起删，键里任一分段超过 255 字节时跳过写盘。
原因：dataset 当第一层，回收单位就正好是这一层目录，与公平调度的分片粒度对齐；rename 是原子操作、查盘只认正式名，任何请求都读不到半块；读盘命中也要回填那两个头，而块不可变，所以 `.meta` 里存的那一份与 Agent 这次直通源站 HEAD 的结果一致。

## D33 last-touch 内存表与三步淘汰
结论：每个 dataset 的最后出现时间记在进程内存的一张表里，读命中与写盘成功都刷新，启动时 `Scan()` 按 dataset 目录的 mtime 填表并按块文件重建驻写字节账；淘汰固定三步：该 dataset 超自己的上限就按块文件 mtime 从老到新删本 dataset 的块，全局仍超总上限就按 last-touch 表删最久没出现的 dataset 整个目录（并列取字典序小的），仍放不下本次就不写盘。
原因：Linux 上目录 mtime 只在条目增删时变化，一轮实验读 20 分钟全命中时 mtime 一动不动，拿目录 mtime 判空闲会误删正在被读的 dataset，所以空闲判断必须用内存表、只用在删整个 dataset 的那一步。

## D34 读盘与回源共用同一条扇出路径
结论：读盘命中同样创建在途条目、同样占一个准入槽，只是拉取协程一侧的 reader 从源站对象换成盘上的对象，订阅者、游标与踢出规则全部不变。
原因：拆成两套额度要么把稳态内存账（并发额度乘缓冲大小）写歪，要么为盘侧再建一套簿记；扇出要的只是「一份字节分给 N 个响应」，与字节从盘上还是从源站来无关。

## D35 缓存卷用 emptyDir 且不设 sizeLimit
结论：网关容器保持 `readOnlyRootFilesystem: true`，缓存路径单独挂一个 `emptyDir`，不设 `sizeLimit`，可写面只有这一个卷。
原因：写满多少字节由网关自己的配额与三步淘汰控制；`sizeLimit` 一到 kubelet 就驱逐 Pod，淘汰压力变成调度事件、实验不可复算，而且 Pod 一重建缓存照样清空。

## D36 带 Range 的块 GET 按区间合并并落盘
结论：带 Range 的块 GET 不再直通源站，按「键+区间」进在途表与磁盘缓存，同一区间的并发请求合并成一次回源，这一段的字节落进盘上的片段缓存。
原因：Agent 默认把每个块拆成 4 条 Range GET 并行取，纯透传时网关对块流量零作用，在途合并与磁盘缓存都接不到，源站字节与不装网关时持平，测不出网关。

## D37 片段单独落盘，不拼成整块
结论：片段按自己的键落盘，网关不把同一块的多段拼成整块再落盘，整块缓存与片段缓存两套并存。
原因：Agent 侧本来就要把四段拼成整块算指纹写盘，网关再拼一遍要多一套组装与完整性判定；代价是整块 GET 读不到片段缓存，这个代价可接受，因为 Agent 走网关时一律拆段取。
