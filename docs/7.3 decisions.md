### D1 文档体系

**结论**：7.0 的下游三件套，文件名和内部标题都不带编号。

**为什么**：6.x 文件内部编号(7.1/7.2/7.3)与外文件名已不一致,不再制造第二层映射混乱

**约束与影响**：
- 本文档三件套为 7.0 的下游设计与实施文档,与核心库三件套(6.1/6.2/6.3)平行;文件名与内部标题均不带编号

### D2 模块落位

**结论**：`agent/` 独立 module，用根 go.work 统一解析。

**为什么**：延续 core D1/D16"独立 module"精神。原方案否决根级 go.work 并写 replace,但根 go.work 已提交且 agent/ 位于其目录树下,不在 use 列表时 go build 直接报错;2026-10-14 主对话裁决改用 go.work 方案:module 保持独立、免 replace、workspace 统一解析

**约束与影响**：
- `agent/` 独立 Go module(`traincache/agent`),并入根 go.work(use ./core ./agent),go.mod 不写 replace

### D3 三个可执行产物

**结论**：产出 agentd、ordersrc、CLI，sidecar 用 Python。

**为什么**：sidecar 的顺序语义必须与真实 loader 的 shuffle 一致(torch / webdataset RNG),Python 直接复用训练生态,Go 复刻 RNG 风险高;共享内存协议语言中立(design §6.2)

**约束与影响**：
- `traincache-agentd`(Go,DaemonSet)、`traincache-ordersrc`(Python sidecar)、`traincache`(Go CLI)

### D4 包结构与依赖方向

**结论**：目录树按 cmd → svc → 子模块 → core 单向无环。

**为什么**：与 core"单向无环"同风格,子模块可并行派活

**约束与影响**：
- design §4 目录树;cmd → svc → 子模块 → core 单向无环;子模块互不依赖;ordersource 不依赖 core

### D5 端口

**结论**：gRPC 用 9410，指标用 9411，都可用 env 改。

**为什么**：避免 root 端口;固定默认值保证 CLI / 探针 / 抓取一致

**约束与影响**：
- gRPC 9410、/metrics 9411(非特权端口,env 可配)

### D6 gRPC 服务划分

**结论**：先做南向两个服务，北向只冻结 proto。

**为什么**：7.0 验收只含南向;北向方向性(谁拨号)依赖 Controller 设计(Q1),先冻结契约不阻塞

**约束与影响**：
- 南向 PreheatService + NodeService;北向 ReportService(ReportBlocks 流)proto 随本设计冻结,服务端实现推迟至 Controller 里程碑

### D7 任务寻址与状态机

**结论**：任务用四元组寻址，状态机补上 DONE。

**为什么**：7.0 CLI 状态只列"进行中/等待/错误",补齐 DONE 状态机才完备;复用 core 寻址,不发明第二套

**约束与影响**：
- 任务引用 =(dataset, snapshot_id, prefixes, chunks);chunk 用 core (path, chunk int64);状态机 QUEUED / RUNNING / DONE / ERROR

### D8 节点标识

**结论**：以 `NODE_NAME` 为权威，状态和指标都带 node。

**为什么**：7.0 要求"唯一确定自身所在 K8s 节点并在状态上报中携带节点标识";Downward API 是标准做法

**约束与影响**：
- env `NODE_NAME`(fieldRef spec.nodeName)权威,启动校验非空;所有状态与指标带 node

### D9 共享内存协议

**结论**：单写单读 ring，64B 头加槽位，读端落后就跳最新。

**为什么**：多 Pod 并发写同一文件需要锁,单写单读免锁;阶段切换只关心最新顺序,允许丢旧

**约束与影响**：
- `/run/traincache/orders/<pod-uid>.ring`;64B 头 + ring slot;单写单读、代际检测、reader 落后跳最新;slot 1 MiB×64 可配

### D10 阶段切换三源归一

**结论**：三种阶段切换统一成一条新 ConsumeOrder。

**为什么**：归一后 Agent 只剩一种切换语义(design §5.3),curriculum 检测复杂性隔离在 sidecar

**约束与影响**：
- epoch / shuffle / curriculum 统一为 sidecar 推送新 ConsumeOrder;7.0 留空的 curriculum 事件源 = sidecar 获训练进程通知后重算顺序;Agent 不区分三源

### D11 钩子通道

**结论**：单向 datagram 钩子，sidecar 是顺序主源。

**为什么**：7.0 要求钩子调用 PersistentPrefetcher 方法;单向 datagram 免连接管理,丢帧靠 inotify 旁路兜底

**约束与影响**：
- Unix datagram `/run/traincache/agent.sock`,行分隔 JSON 三帧型(advance / stage_switch / open_report),单向不回复;顺序主源 = sidecar,钩子只报位点与打开块（D44 起钩子帧扩为四帧）（D47 起扩为五帧）

### D12 core 增量(cas Quarantine)

**结论**：坏块隔离落进 core，按核心库文档流程排队。

**为什么**：7.0 明示"需要增加标记位";归属 core 是职责边界——服务化层不重复实现存储逻辑

**约束与影响**：
- 契约见 design §5.7;由核心库文档流程落地(6.3 新增决策,编号顺延),plan.md M0 引用

### D13 重扫描流程

**结论**：启动先抽样，后台跑全量，坏块读时修。

**为什么**：7.0 部署约束:"缓存尚未完成全量扫描不应直接导致 Agent 无法提供服务";CAS 读时自校验兜底

**约束与影响**：
- 启动 = 枚举 + 1% 抽样(全过先用)→ 后台全量(修复队列优先)→ 读时坏块 repair 回源(single-flight);readiness = 服务 up + 抽样完成,全量不拦

### D14 热度参数默认值

**结论**：先定一套热度默认值，数值全走 env。

**为什么**：7.0 只给示例值;先取可实现默认,校准留 bench 装置(dump 间隔原记 M=30min,与危险线 M=90% 撞名,改名 DumpInterval,见 D24)

**约束与影响**：
- N=24h、DumpInterval=30min、T=24h(因子 0.5)、k=80%、Δ=5%、M=90%;全部 env 可配;数值待 bench 校准

### D15 交叉校准口径

**结论**：100 次打开的匹配率低于 0.8 就重对齐 cursor。

**为什么**：把"20% 偏差"落成可测试的匹配率定义

**约束与影响**：
- 滑动窗口 100 次打开,实际顺序与 OrderSource 期望匹配率 < 0.8 即重对齐 cursor(即 7.0"默认 20% 偏差"的精确口径);inotify 与钩子双源,钩子为主

### D16 预取引擎参数

**结论**：lookahead 取 16，K 跟订单走，优先级高者先下。

**为什么**：7.0 原文约定;ETA 口径显式化便于测试

**约束与影响**：
- lookahead=16(7.0 默认);K = ConsumeOrder.prefetch_chunks;ETA = 新窗口剩余字节 ÷ EMA(α=0.3)吞吐;P0>P1>P2>P3,在途不取消

### D17 指标清单与命名

**结论**：指标按七条线列清单，靠标签控制基数。

**为什么**：7.0 基数控制三原则;清单化便于验收 7 逐项核对

**约束与影响**：
- design §5.8 七线 family 表(2026-10-14 增磁盘淘汰线);dataset / node / result / endpoint / priority 进标签;dataset 白名单外记 other;固定 bucket;高基数进日志

### D18 依赖引入

**结论**：只新增 grpc、prometheus、fsnotify 三个依赖。

**为什么**：不自研轮子,与 core D10 精神一致

**约束与影响**：
- 新增:grpc + protobuf、prometheus/client_golang、fsnotify;其余沿用 core 依赖链;派活时声明

### D19 部署

**结论**：DaemonSet 部署，升级不删有效块。

**为什么**：7.0 部署约束原文;节点筛选调度是 Controller 职责,不在本设计

**约束与影响**：
- design §8 DaemonSet 要点;升级不删有效块;节点选择 label 留待 Controller

### D20 CLI 细节

**结论**：CLI 默认连本机 9410，块名按字典序从 1 编号。

**为什么**：7.0 CLI 示例含 --chunks 名字;CLI 是纯 gRPC 客户端,不能本地读 manifest

**约束与影响**：
- `--endpoint` 默认 127.0.0.1:9410;`--node` 仅校验不做地址解析(Q2);`--chunks` 名字经 ListSnapshot 按 (path, chunk) 字典序 1 起编号解析

### D21 验收口径

**结论**：数字只认 bench 装置，11 条验收写进 plan。

**为什么**：与项目既有流程一致,关键流程可重复执行(验收 11)

**约束与影响**：
- bench 装置为唯一数字来源;11 条验收映射见 plan.md;验收命令风格沿用 6.2

### D22 ring 发现机制与写端实现协议

**结论**：每秒扫 ring 文件，写端只增不缩，seq 最后写。

**为什么**：design §6.2 未明文这些落地细节,2026-10-14 主对话裁决补充(M2 开工)

**约束与影响**：
- 发现 = svc 目录轮询(1s 扫 `*.ring`,新文件构造 Reader)+ Reader 内 200ms poll;写端只增不缩(ftruncate 至 max(现长, 64+slot_size),防读端 mmap SIGBUS);commit = 头 write_seq 最后写,reader 只读 seq ≤ 头 write_seq 的槽;槽索引 =(seq-1) mod slot_count;write_seq 跨代际续增;几何上限 slot_size∈[16, 64MiB]、slot_count∈[1, 1024]

### D23 格式错误指标

**结论**：格式错误单独计数，只按 magic/version 分因。

**为什么**：§6.2 要求"计入错误指标"但 §5.8 指标表无对应项,新增并登记(2026-10-14)

**约束与影响**：
- 新 family `traincache_ordersource_format_errors_total`(counter,labels=["reason"]∈{magic,version});不带 dataset 标签(坏文件读不出 dataset,防基数膨胀);ordersource 包级 atomic 计数,svc 每 tick 以 Set 绝对值同步

### D24 磁盘淘汰策略(热度驱动)

**结论**：淘汰和回收分两层，按 max(热度, 新鲜度) 打分。

**为什么**：7.0「辅助缓存淘汰」原设计落地:淘汰发生在「逻辑上还需要」的块里,Sweep 删不了活块(6.0 §7 只回收不引用数据),必须分层。加权平均算子被否决:单一权重无法同时保护「刚预取未读」(h=0 靠 R 保)与「历史热久未读」(R 低靠 h 保),取 max 是「谁强听谁」的最简形式(2026-10-14 主对话裁决,Q4/Q5 据此重结)

**约束与影响**：
- 淘汰与 GC 分两层:core Sweep 只做引用回收(语义不变);Agent 淘汰循环(默认 30s 周期)经 core `cas.Evict`(core D28,6.2 M9)删除活块本地副本,索引与引用不动,回源时不重复 Acquire。得分模型 `S = max(h, R)`:h 为热度(OPEN 合并后 `h ← h + (1−h)·β`,β=0.15;每 T 乘 0.5,超 N 直接衰减),R 为新鲜度(`R = 0.5^(Δt/T_R)`,T_R=6h;t_touch 取最后打开/预取写入/新 ConsumeOrder 刷新三者最大值)。触发线:利用率超 k 按 S 升序 Evict 至 k-Δ;危险线:超 M 时 R 清零按 h 升序激进淘汰+告警至 k-2Δ。cursor + lookahead(16 块)任何情况不淘汰;消费窗口保护 = 新订单刷新 t_touch,不设独立机制。dump 间隔改名 DumpInterval(原 M=30min 与危险线 M 撞名)。新增指标线 `traincache_evict_*`(D17 七线)

### D25 数据块对象键布局

**结论**：块键由 dataset、path、chunk 直接拼出来。

**为什么**：core 与 7.x 均未定义下载键;Entry.Node 仅是"块实际落盘的节点名"标签,不可作键;由 (dataset, path, chunk) 直接构造、无需解析(2026-10-15 M3 开工主对话裁决)

**约束与影响**：
- 数据块源站对象键 = `<dataset>/blocks/<path>#<chunk>`(path 约定不含 `#`);与 core 索引键 `dataset/<name>/...` 同风格;fetch.Fetch 的 key 为 opaque,core 无感知,由数据写入方与 Agent 共同遵守

### D44 读 miss 上报与 Agent 侧 demand 按需补块

### D45 prefetch 跨队列去重与优先级提升

**结论**：Status 拆消费位点和预取前沿，inotify 兜底去重。

**为什么**：消费位点与预取就绪前沿混用会让 inotify 兜底把"块已完成"误当"已消费",并使 lead 失去负值语义;inotify 事件本身无位点,只能凭指纹反查,代际缓存把逐 OPEN 的全订单 Lookup 降为同代际 O(1)。裁决日期 2026-10-18。

**约束与影响**：
- ① `Status.Cursor` 拆分为纯消费位点(仅由 advance/inotify 推进)与 `Status.PrefetchFrontier`(已就绪的最远块,不要求连续);`lead = frontier − cursor` 可为负,`Status` 不再暴露调度游标;
- ② inotify 兜底:OPEN → 指纹反查当前订单 → `OnConsumeSideAdvance`,去重靠 consume 单调而非已见集合(重复/落后事件返回 false 且无副作用),只有真正推进才计 `consumption_advance{source=inotify}`;钩子活跃期 inotify 被 collector 门控抑制,不与 source=hook 双计;
- ③ fp 反查无 Catalog 接口,只能遍历当前订单 Chunks 逐个 Lookup;按订单代际(stageID、Chunk 数、首尾 ref)缓存反向索引,同内容多路径返回候选逐个尝试;已知限制:反查仅覆盖当前订单 Chunks;
- ④ `traincache_prefetch_cursor` 指标仍是调度游标,未改(help 明示"调度进度,非 Status.Cursor");
- ⑤ self-open guard 目的:Agent 自身读打开本地块(预取本地命中、下载读回校验、ETA 探测、rescan 扫描/修复读回、backfill/stall 归因探测)同样产生 IN_OPEN,钩子沉默/降级期会被 inotify 兜底误判为训练消费,新增 `prefetch.SelfOpenGuard`(`Mark`/`SelfOpened`,并发安全、惰性清理、条目上限 8192,超出先清过期再淘汰最旧;nil 安全)在打开前登记指纹;
- ⑥ TTL 默认 3s(装配处传入),覆盖 inotify 轮询与处理延迟;已知偏差:TTL 内训练恰好打开同一 fp 会漏计一次消费推进(宁可少计不可虚增);
- ⑦ Mark 覆盖范围:prefetch 本地命中/修复重开/`reportFetchSuccess`/`estimateETA`、core fetch Put 成功后读回(经通用 `fetch.Options.OnLocalOpen` 钩子,core 不依赖 prefetch 类型)、rescan `verify`/`reportRepairFetch`(经 `SetSelfOpenMarker` 注入)、svc `backfill` 本地命中探测与 `stallLocalExists`;
- ⑧ 过滤位置:collector `SetOpenFilter`,仅在 `fireOpen` 调用兜底 open 回调前判断,true 则跳过(不推进 consume、不计数),`noteOpen` 的热度/命中率逻辑不受影响;nil filter 不过滤;
- ⑨ 已知遗留:`core/index` 的 `Writer.Commit` checksum 会打开本地块文件但未登记 self-open guard;当前生产代码无 Commit 调用者,仅测试使用,故不构成现网误判。

### D50 快照发布 vs 快照跟随边界与自开观测

**结论**：发布归写入方，Agent 只跟随，自开读统一登记。

**为什么**：两种角色分离,避免 Agent 误承担发布职责;Commit 的 checksum 读回会打开本地块文件(D49⑨ 遗留),进程内 observer 在 `Store.Open` 处统一登记,覆盖未来任何写入方内嵌调用 Commit 的自开读,使其不污染消费侧信号(inotify 热度、Cursor);observer 实例级而非进程级,避免多 Store 与测试间串扰。裁决日期 2026-10-19。

**约束与影响**：
- ① **快照发布 = 写入方**:产生新 entries 的组件调用 core/index `(*Writer).Commit`;Agent 不调用 `Commit`。发布调用方当前待定:Controller 设计未完成,且其现有职责不产生新索引,因此不直接调用 `Commit`。
- ② **快照跟随 = Agent 只读**:经 `index.Catalog.Start` / `Catalog.Refresh` 定时读 CURRENT → 下载并校验 manifest 与引用分片 → `atomic.Pointer` 原子切换内存映射。
- ③ 防护:core/cas 已提供 `SetOpenObserver(func(Fingerprint))`,在 `Store.Open` 内于 `os.Open` 之前回调,仅登记“本进程即将读打开该块”,不改变 Open 行为;observer 挂在 Store 实例上,传 nil 清除,不做进程级全局。Agent 服务在装配中创建 `cas.Store` 时调用 `cs.SetOpenObserver(guard.Mark)` 安装,位置必须在任何 prefetcher / rescan / backfill / fetch 构造之前。现有各调用点显式 Mark 保留,幂等。

### D51 前缀感知快照跟随(R1)

**结论**：Catalog 支持按前缀、按周期跟随 CURRENT。

**为什么**：Agent 此前仅由订单/预热触发加载,无订单时快照长期陈旧;前缀感知跟随在无活跃前缀时退化为整 manifest 跟随,并以 Catalog 内部互斥保证与 `ForOrder` 不并发切换。裁决日期 2026-10-19。

**约束与影响**：
- ① `(*index.Catalog).SnapID() string` 原子读当前 snapID,无则空串;`(*index.Catalog).RefreshManifest(ctx context.Context) error` 读 CURRENT+manifest,成功则原子切换 snapID 与空 entries,用于无活跃前缀时;`(*index.Catalog).Follow(ctx context.Context, prefixes func() []string) error` 阻塞循环,每 `Config.RefreshInterval` 检查 CURRENT,未变则跳过,`prefixes` 非空调 `LoadPrefixes`、为空调 `RefreshManifest`,失败保持旧映射并继续下一轮。
- ② `index.Config` 新增 `OnSnapshotChange func(dataset, snapID string)`,由 `Refresh` / `LoadPrefixes` / `RefreshManifest` / `Follow` 在每次成功原子切换后、锁外触发(Follow 经其内部加载方法触发),不得阻塞,回调 panic 不得向调用方传播,nil 安全;新增 `OnSnapshotError func(dataset string, err error)`,仅由 `Follow` 内部单轮加载失败触发(锁外),同样 nil 安全且 panic 不外传。
- ③ Agent 侧:`svc.Config` 新增 `IndexRefreshInterval time.Duration`(默认 5s);per-dataset 首次创建 Catalog 后启动一次 `go cat.Follow(ctx, prefixesFn)`,`prefixesFn` 返回该 dataset 最近订单的路径前缀;`ForOrder` 与 Follow 的加载必须串行(复用 Catalog 内部互斥)。
- ④ 刷新指标复用 `index_refresh_total{dataset,result}`,`result ∈ {success,error}`(沿用既有 metrics 契约);失败不切换、不清空。

### D52 快照读者登记、心跳与撤销(R2)

**结论**：读者登记快照、定期心跳，退出时撤销。

**为什么**：GC 需要知道哪些快照仍被读者使用;心跳过期即可判死,`PreviousSnapID` 覆盖切换宽限期,撤销后不再误保护。裁决日期 2026-10-19。

**约束与影响**：
- ① 新增 `core/index/readers.go`:`type ReaderClaim struct { NodeID string; SnapID string; PreviousSnapID string; PreviousUntil time.Time; UpdatedAt time.Time }`,JSON 字段 `node_id` / `snap_id` / `previous_snap_id,omitempty` / `previous_until,omitempty` / `updated_at`;对象键 `dataset/<dataset>/readers/<url.PathEscape(nodeID)>.json`(一节点一 dataset 一文件)。
- ② `func NewReaderRegistry(store objectstore.Store, nodeID string, grace time.Duration) *ReaderRegistry`(grace<=0 回退 10s)、`func (r *ReaderRegistry) Declare(ctx context.Context, dataset, snapID string) error`、`func (r *ReaderRegistry) Withdraw(ctx context.Context, dataset string) error`、`func ReadReaderClaims(ctx context.Context, store objectstore.Store, dataset string) ([]ReaderClaim, error)`。
- ③ `Declare`:切换快照时 previous = 本进程上次声明的 snapID、`PreviousUntil = now + grace`;同一快照重复声明保留 previous/PreviousUntil,待 `now > PreviousUntil` 后清空;Put 覆盖,幂等,成功后更新内存 last。`Withdraw`:写 `snap_id=""`、`previous_snap_id=<last>`、`previous_until=now+grace`、`updated_at=now`,之后停止心跳,best-effort;`ReadReaderClaims`:无对象返回空集合,JSON 损坏返回错误(GC 需 fail-safe)。GC 侧 `PreviousSnapID` 仅在 `now ≤ PreviousUntil` 时计入 protected。
- ④ Agent 用 `nodeid.FromEnv()` 的 ID 构造 registry;心跳间隔 = `IndexRefreshInterval/2`(下限 1s);ctx 取消时对已知 dataset 调 `Withdraw`(超时 5s);`OnSnapshotChange` 立即 `Declare`。

### D53 GC 按读者确认删除(R3)

**结论**：GC 以有效读者 claim 为保护集，保留窗口降为兜底。

**为什么**：固定保留窗口不是安全边界,读者可能在窗口外仍持有旧快照;以有效 claim 为保护集合并用 `PreviousSnapID` 覆盖切换宽限期,manifest 缺失时 fail-safe 防误删块。裁决日期 2026-10-19。

**约束与影响**：
- ① `index.Config` 新增 `ReaderGrace time.Duration`(零值回退 `2*RefreshInterval`,默认 10s)与 `OnSweepSkip func(dataset, reason string)`。
- ② `Collector.Sweep`:读 claims,`UpdatedAt` 超过 `ReaderGrace` 的 claim 整体忽略(视为读者已死);有效 claim 的 `SnapID` 计入 protected,`PreviousSnapID` 仅在 `now ≤ PreviousUntil` 时计入 protected(切换/撤销宽限期);protected = CURRENT ∪ 固定保留窗口(最近 `RetainSnapshots` 个)∪ 有效 claim 集合,`RetainSnapshots` 降级为兜底上限,不再是安全边界。
- ③ 快照对象(manifest+分片)只在“不在 protected”时删除,CURRENT 永不删除;protected 快照 manifest 缺失/损坏时调用 `OnSweepSkip(dataset,"manifest_unavailable")`,跳过本轮块删除,但继续删除其他可删快照对象,不得整体停摆。
- ④ 块删除仍要求“不在 liveBlocks 且 ref=0 且 pin=0”,liveBlocks 必须由全部 protected 快照重建;删除顺序保持“先快照对象、后数据块”,同一轮内不新增额外宽限。

### D54 Commit 孤儿清理与条件写探测(R4)

**结论**：失败提交清理孤儿对象，并探测后端条件写。

**为什么**：失败提交留下的新分片/manifest 无引用,不清理会造成孤儿对象;条件写在 mock 上无法证明真实后端支持,需真实 S3 兼容后端探测与集成测试。裁决日期 2026-10-19。

**约束与影响**：
- ① `(*index.Writer).commitOnce` 记录本次 attempt 新 Put 的分片键与 manifest 键;任何失败(含冲突重试前、验证失败)做 best-effort `Delete`(逆序、超时 5s、错误忽略、不覆盖原始错误);不复用键不删;`PutIfMatch` 成功提交后不清理。
- ② GC 遇 protected 快照 manifest 缺失按 D53/design §5.11 第 5 条处理。
- ③ 新增 `objectstore.ErrConditionalWriteUnsupported` 与 `func ProbeConditionalWrite(ctx context.Context, s Store) error`:写临时键,用不匹配 ETag 调 `PutIfMatch`,期望 `ErrConflict`,若返回 nil 则返回 `ErrConditionalWriteUnsupported`,结束删除临时键。
- ④ Agent `svc.Config` 新增 `ObjstoreProbeConditionalWrite bool`(默认 false);开启时装配期探测,指标 `traincache_objectstore_conditional_write_supported` 取值 0/1、预置 0,不支持时告警但不阻止启动。
- ⑤ `bench/k8s/minio.yaml` 镜像固定为 `minio/minio:RELEASE.2025-04-22T22-12-26Z`(未做拉取验证,开发演练用);真实环境连 COS/OSS/S3 时不需要这个文件;新增真实后端条件写集成测试,环境变量 `TC_S3_ENDPOINT`/`TC_S3_ACCESS_KEY`/`TC_S3_SECRET_KEY`/`TC_S3_BUCKET` 任一缺失时 skip,存在时期望冲突返回 `ErrConflict`/412。

1. 实现子代理发现约定不可行、不合理，先回传 `BLOCKED`（带上理由、证据和建议），代码先别动；
2. 主对话做裁决。采纳就更新 `docs/design.md` 和本文档：旧编号保留，新决策接着往后编号，然后重新派活；否决就说明理由，子代理按原来的约定继续；
3. Q* 结案时，在本文档 §2 的表格里登记结论和日期。必要时把它升级成 D*，或者改 `docs/design.md`。

### D55 Agent 预热任务增量

**结论**：预热服务加改派和取消 RPC，进度复用状态查询。

**为什么**：8.x GWAA 需要按 `(pod,node)` 改派/停止并读取窗口位图；复用 `GetPreheatStatus` 避免新增查询 RPC，两个动作 RPC 覆盖改派/取消；拉取方向与现有 RPC 一致，避免 Agent→Controller 反向连接（详见 `docs/8.3 decisions.md` D28）

**约束与影响**：

### D56 位序定义

**结论**：位图第 i 位对应请求 chunks 第 i 项。

**为什么**：位序若按块全局编号会随窗口变化漂移；绑定请求顺序使 Controller 与 Agent 无需共享全局映射，位图长度可推导（`ceil(len(chunks)/8)`）

### D57 ring 写端保活扩展到 bench reader

**结论**：D41 的 10s 重写节奏从 `traincache-ordersrc` sidecar 扩展到所有 ring 写端；`bench/compare/run_bench.py` 的 traincache 组 reader 加 heartbeat 线程，每 10s 重写当前 epoch 的订单。

**为什么**：D41 只约束了 manifest 里的 sidecar，而 bench 的 traincache 组由 `run_bench.py` 内联写 ring。订单每 epoch 只写一次、epoch 内静止，`LastAdvance`（D29）停滞 30s 后 collector 进 degraded 切 inotify 兜底——热度和命中率统计中途换源，跑分数据口径不一致、不可比。写端一次性写完退出是设计行为不是 bug，所以修的是写端节奏，不是降级阈值。

**约束与影响**：
- `run_bench.py` traincache reader 内：`_hb_stop = threading.Event()` + `_hb_epoch = [0]`；`_heartbeat_loop()` 每 10s 调 `_write_order(str(_hb_epoch[0]))`，异常吞掉不中断训练读取；epoch 主循环开头更新 `_hb_epoch[0] = epoch` 并照常 `_write_order`，`epoch == 0` 时拉起 daemon 线程，循环结束 `_hb_stop.set()` 收尾。
- 前提依赖读端 `ordersource.Reader` 的载荷字节去重（`lastEmitted`，代码内称"约定 7"）：内容相同不推送、不触发 `OnStageSwitch`，所以心跳只推进 `write_seq`、刷新 `LastAdvance`，不会每 10s 把预取队列打回 P1。
- 保活判据：跑分产物所在轮次要求 `traincache_agent_degraded` 全程为 0；出现过 1 则该轮命中率/热度曲线标 `degraded`，不参与组间对比。
- 新的自研 ring 写端（探针、临时脚本）按同一条约束实现，不得只写一次就静止。

### D58 缓存字节上限与淘汰双维度触发

**结论**：evictor 新增 `TRAINCACHE_CACHE_CAPACITY_BYTES` env（默认 0=关闭），开启后淘汰循环同时查磁盘利用率和字节占用，哪个先到阈值就按哪个维度触发；两个维度共享同一个得分模型 `S = max(h, R)` 和硬保护（cursor+lookahead 不淘汰）。

**为什么**：磁盘百分比水位（80%/90%）是间接约束，节点上还有其他 Pod 占用磁盘时，Agent 可能在磁盘还没到 80% 时就已经预取了大量数据，或者磁盘到了 80% 但 Agent 其实没写多少块。字节上限直接约束"这个节点 Agent 最多占多少 GB"，和 bench 公平实验里"所有组统一 1GB 缓存"的要求对齐。之前代码里 env 表没提、evictor.go 也没实现，属于 D19 部署约束漏项。

**约束与影响**：
- env `TRAINCACHE_CACHE_CAPACITY_BYTES`：默认 0 关闭；>0 开启字节维度；磁盘水位仍生效，双维度取先到者。关闭时退化成原行为，零代码路径变化。
- 触发线：字节占用超上限 → 按 S 升序 Evict 到上限的 85%；磁盘利用率超 k → 按 S 升序 Evict 到 k-Δ。两个条件不区分优先级，先满足哪个就先触发哪个的淘汰循环。
- 危险线：字节占用超上限的 95% → R 清零按 h 升序激进淘汰到上限的 80%；磁盘利用率超 M → 同 D32。两个危险线各自判定，互不依赖。
- 记账：evictor 维护累计 Evict 到的本地块字节数（`cas.Open` 成功后查文件大小、Evict 成功后从累计减），只统计 Agent 自己写的块，系统文件不计入。
- 指标：新增 `traincache_cache_capacity_bytes_total{source}`（gauge，source∈{disk,bytes}）暴露当前触发维度。
- bench 装置：所有组统一设 1GB（D19），保证公平对比。

### D59 淘汰策略抽象与运行时选择（M4）

**结论**：本条目走过两步。第一步（原决策）：`agent/evictor` 新增 `Policy` 接口（`Admit(candidate, victim) bool` / `Rank(victims) []Block`），上四档 heat/lru/lfu/wtinylfu，其中 wtinylfu（W-TinyLFU：用 count-min sketch 近似记块访问频率、靠准入判断挡掉一次性污染块的策略）规格为 window 1% + 两段 SLRU + count-min 4 行、宽度=块数×10、3bit 饱和、doorkeeper、定期减半。第二步（2026-10-24 撤档，权威口径见 10.1 D9）：不实现 W-TinyLFU，`Policy` 只留 `Rank(blocks []Block, danger bool) []Block`，"新块能不能换入"的准入判断（`Admit`）连同接线一起删除，配套指标 `admit_rejections`（准入拒绝数）与频率减半次数随之取消；策略收敛为三档 `heat`（现有热度打分，行为与改动前逐字一致，作回归基准）、`lru`、`lfu`。选择仍用 env `TRAINCACHE_EVICT_POLICY`（默认 heat，启动校验，未知值拒绝启动并打印合法清单）；lookahead 同步 env 化为 `TRAINCACHE_PREFETCH_LOOKAHEAD`（默认 16）。现有 `agent/evictor/tinylfu.go` 与 `bench/experiments/conds/policy-wtinylfu.json` 随代码任务删除（2026-10-24 已完成：两个文件均已移除，`Policy` 接口只剩 `Rank`）。

**为什么**：第一步：10.0 要求多策略同台，"用哪种淘汰"必须是运行时选项而不是代码分支。接口落在 `agent/evictor` 而不是 core——core 不该知道训练语义与访问历史（10.1 D7），`cas.Evict` 原语不动。扫点靠 env 注入，不改 CRD（10.1 D10）。实验块大小取 8MiB（10.1 D20）后 1GiB 缓存有 128 块，各档排序结果才有判别力。第二步（撤档理由，10.1 D9）：① bench 主场景是单 Job 顺序读，准入（拦截一次性块）的收益不明确；② window + 两段 SLRU + count-min + doorkeeper 的实现与验证成本高；③ 核查确认已写的 `tinylfu.go` 只是频率排序代理——window 与两段 SLRU 缺失、`Admit()` 从未被淘汰循环调用，留着会让策略同台对比失真。

**约束与影响**：
- 触发线、危险线、字节上限维度（D58）、硬保护（cursor+lookahead）与策略无关，三档共用；策略只替换"谁先被淘汰"这一层。
- `heat` 档回归判据：同一访问序列下与 D24/D32/D58 的旧行为逐块一致（10.1 M4 判据①）。
- 新指标线只保留策略切换计数，标签只放策略名（10.1 4.9）；准入拒绝数、频率减半次数两条指标随撤档取消。
- bench 装置：对照实验一律 `heat`；M5 淘汰矩阵与 Pareto 二由 `experiments/run_policy.py` 注入策略与 lookahead，矩阵从 4 策略缩到 3 策略（10.1 D9）。
