一个Go库，负责记录有哪些数据块，按照内容将数据块落盘，按需下载数据块
没有任何服务形态，现在就是一组代码加单元测试

##  路径索引
索引层（决定取什么）：manifest 条⽬键为 (path, chunkIndex) ，采⽤路径寻址。它不承诺跨路径去
重

维护一个表，记录某个路径下面的第i块数据存储在什么节点上面
一个数据集可能有几十万个块，如果都用这个表，那么这个表无法放入etcd中（上限1.5MB）,所以放到对象存储上面
这张表在对象存储中被切分成若干个索引分片管理，每个分片不要超过10w条数据

使用原子提交 + 快照来解决数据侧读写问题
角色： 写入方，Agent，分片构建任务，对象存储

Agent要在内存中维护块->位置的映射适合关系
这个映射关系常常会因为写入方写入而变化，所以需要常常到对象存储中更新
Agent先从对象存储下载分片文件，然后解析映射关系

数据集更新的时候,不能直接覆盖旧分片，而是通过一次原子提交 + 快照:
#### 1. 写新块：
写入方把新块写到新位置，不覆盖旧块。

#### 2. 写新分片： 
构建任务读取当前已经提交的快照`S1`,确定本次需要修改哪些分片，
之后构建任务生成新的分片，新分片使用独立的对象键，并且在提交之前不会被当前的快照引用

#### 3. 上传对象：
将分片上传到对象存储的唯一对象键下面，然后上传新的快照清单
此时即使新分片和快照已经存在于对象存储中，它们仍然只是尚未提交的数据，对读侧不可见

#### 4. 验证快照完整性：
提交之前，需要确定： 
1. 新快照已经上传
2. 快照引用的所有分片已经成功写入
3. 所有分片都符合预期的完整性要求
4. 被引用的新数据块都成功发布到CAS存储

#### 5. 原子提交：
构建任务尝试将CURRENT指针从快照S1更新成S2，但是要考虑到并发修改的情况
提交时必须使用对象存储支持的条件写入机制，确保只有当 CURRENT 仍然指向 S1 时，才能更新为 S2， 避免并发任务互相覆盖。
- 提交成功：S2 成为当前快照。
- 提交失败：重新读取最新快照，基于最新快照重新构建并提交。
具体条件写入方式取决于使用的 S3 对象存储实现——不同后端对 `If-Match` / `If-None-Match` 的支持程度可能不同，代码里有 `ProbeConditionalWrite` 兜底探测。

#### 6. 读侧刷新:
Agent定时（每 N 秒）读一次CURRENT。
快照变了，就执行：
下载S2的快照清单，
根据清单下载相应的索引分片，构建新的内存映射（注意下载的分片与清单要验证完整性）
原子切换内存映射的版本，不要在加载新分片的过程中逐个修改正在使用的旧映射

#### 7. 清理旧块与旧快照
旧快照清理：
CURRENT 指向的快照不能删除。
提交新快照后，旧快照可能仍被正在执行的读操作使用，因此不能立即删除。
确认旧快照不再被任何读操作使用后，删除旧快照的清单及不再被其他快照引用的索引分片。

旧数据块清理：
只有已提交快照不再引用的数据块，才能进入待回收集合。
删除数据块前，必须确认没有读操作正在使用它。
如果数据块仍被引用或正在被读取，则跳过本次回收，留待后续处理。

#### 注意： 写盘的原子性
写新块步骤与写新分片步骤应该做成先写临时文件，后面rename()改名的设计，这样别的进程永远看不到写了⼀半的块。
缓存块不做逐块 fsync——数据丢了重新下载就好，掉电丢块的代价就是重拉

#### 对象存储与快照的结构
```text
dataset/
├── snapshots/
│   ├── S1/
│   │   ├── manifest.json
│   │   ├── shard-001.idx
│   │   ├── shard-002.idx
│   │   └── shard-003.idx
│   │
│   └── S2/
│       ├── manifest.json
│       ├── shard-001.idx
│       ├── shard-002.idx
│       └── shard-003.idx
│
└── CURRENT
```
三个重要概念：
快照 ID
快照清单 manifest.json
CURRENT 提交指针

快照在逻辑上是完整快照，物理上允许复用旧分片。

## 快照读者登记
Agent 加载 S2 后，写一个"我在用 S2"的登记（本地一个带心跳时间戳的文件就够，不用搞分布式租约）切到新快照时撤销旧的。
清理方删旧快照前，检查所有登记：没人声明 + 心跳过期 + 不是 CURRENT，才删。
心跳过期就当读者死了，允许删，防止 Agent 崩了旧快照永远留着。

## CAS存储层
数据块下载时会流过内存，这个时候算一下xxh3指纹，按照指纹命名文件存盘（例:`blocks/ab/<指纹>.blk`）
速度⼤约 10GB/s 每核，不产⽣额外 I/O（应该，需检验）作为存储键。
这样就实现了读回校验：读回来时可以顺⼿校验数据有没有损坏（块头⽤ 64 字节记录⼤⼩和摘要，不需要额外的校验⽂件）

不同路径下内容相同的数据块只存储一份。
回收数据块时，需要确认该数据块不再被任何保留的已提交快照引用，并且没有读操作正在使用它，才能删除。
引用计数统计的是已提交索引快照对物理 CAS 块的逻辑引用，而不是单纯统计当前路径映射

注意: 引用计数是反应索引快照的逻辑引用关系，而不是读操作。
读操作的生命周期单独管理。

补充（2026-10-14）：上面的「回收」和后来的「缓存淘汰」是两个维度，不要混。回收只针对不再被引用的旧数据，管的是正确性；缓存淘汰管的是磁盘容量，删的是仍被快照引用的块的本地副本——索引条目和引用关系都不动，副本删了之后要用再重新下载（见 6.1 cas.Evict、7.1 §7.6）。

## 索引分片按前缀目录加载
服务侧数据块是按需下载的，但是manifest是全量的，训练可能只需要/train-data下面的数据，其余路径的快照是无关的
当数据量上去之后，manifest本身的大小也可能达到GB级别
所以"按照前缀加载manifest"是必要的

核心库catalog要提供「按前缀加载」的能力，而Agent服务（后续内容）决定「加载哪些前缀」

核心库 Catalog：
  - 提供 Load(prefixes []string) 或 LoadShards(refs []ShardRef)
  - 只下载、校验、加载指定分片
  - 维护局部内存映射

## sha256校验
现在的块头是64 字节，记录大小和摘要。可以扩展成128字节另外记录成：
```text
块头（例如 128 字节）：
  magic        4B
  version      2B
  flags        2B      // bit0: 是否带 sha256
  block_size   4B
  xxh3_128    16B      // 始终存在，作为存储键
  sha256      32B      // 可选，flags 置位时有效
  reserved    ...      // 对齐到 128B
```
存储键仍然是 XXH3-128，路径 blocks/ab/<xxh3>.blk 不变，去重逻辑不变。
SHA-256 只在需要时计算并写入块头。
读回时：默认只校验 XXH3；如果 flags 置位，再校验 SHA-256。

同时增加一个sha256开关：提供一个全局或按命名空间/桶级别的配置
`verify_level = xxh3 | xxh3+sha256`
这个开关可以做成只影响新写入的块，老块保持原样，避免全量重算。

## 限制并发抓取
下载块的时候按照在途字节数控制并发，而不是按照Goroutine数量
小文件会将goroutine撑爆，大文件会把内存撑爆，字节数是两种情况统⼀的度量。
同时限制对单个主机的连接数（默认 64）与最大并发下载任务数

单测全部通过，重点覆盖四种场景——多个 goroutine 同时写同⼀个块、写⼀半进程崩溃、相同内
容去重、校验失败后重新下载
