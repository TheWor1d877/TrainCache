### D1 文档编号
**结论**：新建 8.1 design、8.2 decisions 与 8.3 test 三件套；`docs/7.0 Controller & Scheduler.md` 零改动为默认，用户授权后可改 8.0（Q19）。
**为什么**：沿用 6.x/7.x 的"基线/实现契约"分层，基线缺陷由用户裁决修正。
**影响**：8.0 的基线哈希用 `git hash-object` 记录（该文件启动前已有用户改动，不以 `git diff` 判空）。

### D2 工程形态
**结论**：独立 Go module `traincache/controller`，加入根 `go.work`；`cmd/controller-manager`、`cmd/webhook`、`cmd/scheduler` 三个入口。
**为什么**：备选拆两个 module（共享类型需公共包）或塞进 agent（控制面与节点面混淆）；控制面依赖 k8s 客户端与调度框架，与 agent 依赖差异大。
**影响**：`go.work` 含三个 module。

### D3 CRD 约定
**结论**：group `traincache.io`、version `v1alpha1`；两个 CRD 均 Namespaced；只开 status 子资源，不定义 scale；跨对象引用仅限同 namespace；`spec.podCount`/`spec.dataSetRef` 不可变；Controller 不管理 Job/Pod 生命周期。
**为什么**：8.0 开头称 status/scale 解耦、scale 不开（G9）；v1 无水平扩缩语义，Pod 生命周期归训练侧。
**影响**：CRD YAML 断言无 scale；跨 namespace 引用被 webhook 校验拒绝；更新 podCount/dataSetRef 被拒（完整字段规格见 7.1 §5.1）。

### D4 块模型
**结论**：`spec.chunkSize int64` 字节 + `spec.shards[]{name,count,lastChunkSize}`；`totalChunks=Σcount`；全局块号按 spec 顺序累计，固化在 `status.blockLayout[].startChunk`。
**为什么**：备选 `resource.Quantity` 每次计算需解析，agent/core 全用 int64；避免引入第二套单位。
**影响**：单测断言跨 shard 累计、`Σcount=totalChunks`、区间无缝。

### D5 readinessTable 语义
**结论**：status 存 `[][]int32` 计数（窗口内就绪块数），比例一律现算 `rate=ready/K_i`；门控用整数判据 `required=floor(threshold*K_i)`（D26），`rate` 仅用于观测与展示。
**为什么**：基线计数与比例并存（G6）；计数无损、可审计；比例随 K 变化不宜持久化，浮点 rate 不适合作放行裁决。
**影响**：门控断言只依赖 `ready` 与 `required`。

### D6（由 D25 取代）D7（由 D30 取代）D14（由 D38 取代）D16（由 D32 取代）D17（由 D27 取代）
五条历史决策的现行结论分别见 D25（K 单一窗口）、D30（可达性标签）、D38（门控存在量词）、D32（随机并列）、D27（每任务注解键）。编号按规则保留。

### D8 Pod 关联
**结论**：`spec.targetRef{apiVersion,kind,name,podLabelSelector}` 与 `PodDetail.Index`；Index 必须为 `0..PodCount-1` 连续；Pod 通过 ordinal 映射到 PodDetail。
**为什么**：基线未定义发现方式（G2）；没有稳定映射，readiness 无法按 Pod 归属。
**影响**：单测校验；序号推导测试。

### D9 Gate 注入
**结论**：新增 MutatingWebhook，匹配 `objectSelector: traincache.io/warmup=enabled`；注入固定 gate `traincache.io/warmup` 与 annotation `traincache.io/warmup-task`、`traincache.io/pod-index`；`failurePolicy: Ignore`。
**为什么**：SchedulingGate 只能在创建时加入、事后只能摘（G1）；备选"用户模板自带 gate"把配置负担外推且易错。Ignore 的代价是静默降级，由 `GateInjectionDegraded` 条件兜底，换取 webhook 故障不阻塞训练。
**影响**：单测 + e2e：无 gate 时 Pending、放行后 Running。

### D10 Pod 序号推导
**结论**：优先 label `batch.kubernetes.io/job-completion-index`，其次 StatefulSet ordinal（Pod 名最后一段），都失败不注入并记事件 `WarmupTaskMappingFailed`。
**为什么**：序号须由 webhook 独立、确定地算出；控制器回填会与创建竞争。
**影响**：表驱动（Job/StatefulSet/裸 Pod）。

### D11 Agent 契约
**结论**：扩展 `traincache.agent.v1.PreheatService`：进度复用 `GetPreheatStatus`，`PreheatStatus` 追加 `generation=12`、`seq=13`、`ready_bitmap=14`、`canceled=15`，`SubmitPreheatRequest` 追加 `generation=8`；新增 `UpdatePreheat`/`CancelPreheat`；位序 = 请求 `chunks` 顺序，8.x 必须显式 `chunks`；`ReportBlocks` 保持 Unimplemented（细节见 D28 与 7.1 §12.1）。
**为什么**：备选新建 controlplane proto（双契约维护成本）、Agent 推送（需反向连接与服务发现）；拉取模型与现有 RPC 方向一致。
**影响**：Agent 测试；fake server；7.1 附录 A 与 7.1 §12.1 逐字一致。

### D12 幂等与陈旧
**结论**：`task_id="<namespace>/<name>/p<index>"`；`generation=metadata.generation`；Agent 对低 generation 返回 `FailedPrecondition`；`UpdatePreheat` 全量替换 `chunks` 并重定义位序，`seq` 单调递增；`CancelPreheat` 仅标记、不保证停止在途 P0；Cancel 后同 generation 再 Submit 视为新任务。
**为什么**：重复 reconcile、重启、乱序响应是常态；generation 单调性是唯一裁决依据，seq 解决同代际内位图新鲜度。
**影响**：单测（陈旧/重复/取消后重建/全量替换）；乱序响应用例。

### D13 门控参数位置
**结论**：`spec.gate{threshold,gapMin,slopeMin,tMax,minInterval}` 与 `spec.score{halfLife,cutoff}`；示例默认 `threshold=0.9`、`gapMin=0.1`（比例）、`slopeMin=0`（比例/秒）、`tMax=10m`、`minInterval=10s`、`halfLife=2·K_i`、`cutoff=8·K_i`；无 `window` 字段，K 为 per-Pod（D25）。
**为什么**：基线只有符号没有来源；参数须可声明、可回滚；默认值仅示例，生产由用户覆盖；gapMin/slopeMin 单位显式化避免与块数混淆。
**影响**：CRD 范围校验（0~1、非负）；边界测试；单位注释与默认值断言。

### D15 条件②采样
**结论**：`FirstReadyAt` 取首次出现任一 Pod 达标的时间，写入 `Condition FirstReady`；每个未达标 Pod 需两个间隔 ≥ `minInterval` 的样本才计算 slope，样本不足视为不满足。条件②是边际收益判据：等待价值随 gap 增大、slope 降低而下降，`gap>gapMin && slope<slopeMin` 时提前放行（Released）；条件③ `tMax` 是绝对上限。
**为什么**：基线未定义起点（G11）；固定"首次达标"避免交错达标反复重置；采样不足不误放行；②③分工，不把超时当收益判据。
**影响**：时钟注入（交错达标、单样本、零间隔）；②先于③触发的用例。

### D18 缺分行为
**结论**：Scheduler 在 Pod 分数注解缺失、节点缺项、JSON 损坏、`task` 不匹配、超 TTL 时返回 0 且 `Status` 为 nil。
**为什么**：备选返回 Unschedulable——会让 controller 故障演变为集群不可调度；返回 0 只影响落点偏好，读路径仍可回源。
**影响**：单测：五类缺失均 0 且不拒绝。

### D19 分数公式
**结论**：`w(i)=1 (i<K_i)`、`0.5^((i-K_i)/H) (K_i≤i<C)`、`0 (i≥C)`；`S=round(100*Σw·ready/Σw)`，`Σw=0` 时 0；NormalizeScore 按最大分缩放至 100。
**为什么**：0~100 与 NormalizeScore 约定一致；整数便于 annotation 存储；K_i 为每 Pod 启动窗口，与 D25 一致。
**影响**：边界 i=K_i-1/K_i/C-1/C；全 0/单点/多点。

### D20 日志契约
**结论**：标准库 `slog` + `JSONHandler`；`internal/logging` 仅 `New/Into/From`；字段固定 7.1 §6.5 集合；每 reconcile 生成 `request_id`；跨进程用 `task_id+node+generation` 关联。
**为什么**：agent 已用 slog 且无第三方；9.0 规范缺失（Q8），先冻结最小契约。
**影响**：日志断言测试；grep 脱敏。

### D21 日志为硬性验收
**结论**：每个功能交付必须包含日志点实现与至少一条日志断言测试，缺失则不通过。
**为什么**：用户明确要求"关键位置记录日志"为硬性任务，不可后补。
**影响**：各验收判据含日志项。

### D22 core 复用边界
**结论**：只读复用 `core/objectstore`、`core/index` 导出符号；不新增 core 接口、不改 core 代码。
**为什么**：快照/键布局已有唯一实现，重复实现会产生第二套事实。
**影响**：依赖图检查；core 测试零改动。

### D23 选主
**结论**：`CONTROLLER_LEADER_ELECTION` 默认 `false`；生产建议开启；webhook 独立进程不参与选主。
**为什么**：单副本开发简单；多副本时两个控制器同时下发会造成重复 RPC（幂等可兜底但浪费带宽）。
**影响**：清单可开启；重启测试。

### D24 并发与时钟
**结论**：每个 controller `MaxConcurrentReconciles=1`；状态全部落 CRD，内存仅 rateHistory 与连接池；所有时间比较用注入的 `Now func() time.Time`。
**为什么**：串行化避免同对象竞争；内存态最少化使重启可恢复；注入时钟使门控可测。
**影响**：并发与时钟测试；重启 e2e。

### D25 K 单一窗口（取代 D6）
**结论**：启动窗口与评分窗口统一为每 Pod 的 `K_i`（`PodDetail.K`）；删除 `ScorePolicy.Window`；门控与全局衰减评分都只用 `K_i`。
**为什么**：双窗口配置面与解释成本高；单窗口使"能否放行"和"落点偏好"共用同一事实。
**影响**：CRD 无 `window` 字段；不同 `K_i` 的 Pod 各自门控与评分有单测。

### D26 整数门控与 required 的 0/1 钳制（G6）
**结论**：`required=floor(threshold*K_i)`；`threshold>0` 且结果为 0 时取 1；放行判据 `ready>=required`。示例 K=8、threshold=0.8→required=6；浮点 `rate` 仅观测。
**为什么**：浮点比较受精度与采样抖动影响；整数门槛可审计、可复现；0→1 钳制避免小窗口因向下取整永远无法放行。
**影响**：表驱动 K=1/8/1024、threshold=0/0.8/1.0；边界 ready=required-1/required。

### D27 每任务 annotation 键编码（G3，由 D49 取代）
**结论**：已由 D49 取代；分数不再写到 Node，每任务键与 hash 编码不再存在。

### D28 Agent RPC 最小增量（G4）
**结论**：不新增 `GetPreheatProgress`；进度查询复用 `GetPreheatStatus`（扩展字段见 D11）；新增 `UpdatePreheat`/`CancelPreheat` 两个动作 RPC。
**为什么**：新查询 RPC 会扩大 Agent 契约与实现面；状态查询已携带位图进度，避免第二次往返。
**影响**：7.1 附录 A 与 7.1 §12.1 逐字一致；单测；proto 字段号断言。

### D29 默认消费顺序切分（G10）
**结论**：删除 `consumeOrderRef`；任一 Pod 的消费清单缺失/非法时忽略全部用户值，统一按 `[floor(i*T/P), floor((i+1)*T/P))` 升序切分，要求 `T>=P`；记事件 `ConsumeOrderDefaulted`，`status.consumeOrderSource=Default`。
**为什么**：悬空引用无法解析且无生产者；确定性切分可测、无需额外对象；`T<P` 无合法切分，显式拒绝而非静默生成空窗口。
**影响**：单测 T=P、T=P+1、T<P；`consumeOrderRef` 不再读取。

### D30 可达性标签人工维护（G8，取代 D7）
**结论**：`traincache.io/s3-access=true` 由人工维护，任何组件不得写入；`DataSet.spec.accessibleNodeSelector` 可选，未设置时默认等价于 `traincache.io/s3-access=true` 选择器。
**为什么**：基线要求人为打标签，selector 仅作可选收窄；默认值让最小清单免配置，同时保留多数据集差异化能力。
**影响**：单测：仅标签、标签+selector、selector 不命中；标签缺失节点被排除。

### D31 固定 Pod 集与不可变字段（G9）
**结论**：不开 scale；`spec.podCount` 与 `spec.dataSetRef` 创建后不可变（CRD CEL `self == oldSelf`，webhook 兜底）；Controller 不创建/管理 Job/Pod，仅通过 gate 与 status 协作。
**为什么**：扩容会改变 P×N 表与窗口映射，v1 不支持；Pod 生命周期归训练侧，越权会引入竞态。
**影响**：CRD YAML 无 scale；webhook 更新拒绝用例；e2e 中 Controller 无 Pod 写权限。

### D32 GWAA 贪心近似与随机并列（G12，取代 D16）
**结论**：GWAA 按 `c_ij` 贪心分配，属近似解；并列时随机选择，RNG 由参数注入，固定种子可复现；WarmupTask 的注入种子按「任务 UID + generation」派生，同一代内每轮重算取同一序列，代际变化才重掷；不追求全局最优。
**为什么**：精确分配是组合优化，P×N 规模下无必要；随机并列避免字典序裁决带来的系统性偏置，注入 RNG 保留可测试性。种子按代际固定，是因为冷启动时整张 `ReadinessTable` 全为 0、每个 `c_ij` 都并列，逐轮重掷会让目标集合反复翻转，每轮把上一轮刚提交的配对按 `target_shrink` 撤销，预热进度归零直到 `t_max` 降级。
**影响**：同种子 100 次一致、不同种子覆盖并列分支、贪心结果满足硬约束。

### D33 GWAA 冲突裁决是否允许共享（G12 延伸）
**结论**：默认保留差值裁决（`c_ij - secondBest_i` 大者保留、其余让步）。"共享最优节点"只是未启用的可选分支：仅当 `allowMultiPodPerNode=true`、无亲和冲突、粗容量允许，且 `|W_B \ W_A| < c_ij - c_ik` 时才允许次优 Pod 共享；前置条件是补 `count × maxPod` 粗资源记账（Q6 v1 不装箱）。`allowMultiPodPerNode=false` 时共享违反用户声明的放置约束，不可作为默认行为。
**为什么**：共享的真实代价是同节点多预热一个窗口（窗口重叠时便宜，不重叠接近双倍 IO）加资源争用；次优节点通常已预热，搬迁的"补预热"多为沉没成本；若次优节点差很多，搬迁代价才可能大于共享。
**影响**：启用触发：端到端取得真实 `wait_time` 后，数据显示让步搬迁代价显著才实现，且前提需按 D38 的 fanout 成本结构重新评估；不得默认启用。

### D34 Controller 下发预热时的快照标识
**结论**：`SubmitPreheatRequest.snapshot_id` 恒为空字符串；Controller 不下发 `DataSet.status.snapshotID` 解析出的具体快照 ID（Update 路径同理）。Agent 侧对非空值返回 `InvalidArgument`。
**为什么**：Agent 经 `Catalog` 自行跟随 CURRENT、按前缀加载 manifest 分片；下发具体 ID 会把任务键 `(dataset,snapshot_id)` 钉在某一代，快照推进后位图失去意义，也可能指向 Agent 未加载的快照（e2e 曾因此令全部预热被永久拒绝）。
**影响**：e2e 判据；Controller 组装请求的单测断言 `SnapshotId == ""`。

### D35 指标标签口径
**结论**：全部指标只用有界标签：`controller`(3 值)、`result`(固定枚举)、`op`(3 值)、`state`(3 值)、`dataset`（值取 `<namespace>/<name>`，避免跨命名空间碰撞）。不设按任务/Pod/节点展开的 ready 明细与门控序列 family，门控状态用有界计数的 `gate_tasks{state}` 观测；family 清单以 7.1 §9.5 的 11 项为准。
**为什么**：无界身份标签无法聚合与告警；`err.Error()`、Pod/Node/task 名、UID 禁止进标签。
**影响**：指标测试断言 family/标签名/枚举值。

### D36 WarmupTask status 明细粒度
**结论**：候选节点粒度的就绪块数只由 `ReadinessTable`（P×N）承载；`PodNodeReadiness` 明细只记判定所需的预热节点配对（条数口径由 D38/D39 定为实际 `Assignment` 数），门控/评分/落点判定只读这些配对。
**为什么**：P=64、N=256 时"每 Pod × 每候选节点一条"的明细为 4.18 MiB，超过 1 MiB 上限与 etcd 请求上限；收窄后 61,589 B 且不丢判定信息。
**影响**：`TestWarmupTaskStatusSize`（<1MiB）；e2e 判据复跑；上限口径见 Q11。

### D37 取消 DataSet→WarmupTask 反向引用
**结论**：删除 `DataSetStatus.WarmupTasks`；保留 `WarmupTaskSpec.DataSetRef` 单向引用；不设 OwnerReference、不建互相 watch。
**为什么**：该字段全仓无写入点且无 namespace/UID，属死字段；一旦回写而任务侧又 watch DataSet，会形成 reconcile 回环。
**影响**：CRD schema 断言不含该字段。

### D38 预热分配 fanout（单节点 → 每 Pod K 个预热节点）
**结论**：新增 `spec.preheatFanout`（默认 1、典型 2，0 与负数由 CRD 拒绝）；GWAA 按各 Pod 最大 `c_ij` 降序贪心认领 top-K 可行节点；节点容纳几个 Pod 由 `allowMultiPodPerNode` 与亲和字段声明（该字段正式接线）；跨 Pod 争同一节点仍按 `(c_ij − 次优 c_ik)` 差值裁决，差值大者保留、其余让步到次优可行节点；GWAA 不决定最终落点，落点由 Scheduler 在放行后的分数快照中从该 Pod 的暖节点里选出；门控条件①恢复存在量词：K 个预热节点中至少一个 `Ready ≥ floor(阈值 × K_i)` 即该 Pod 达标，全部 Pod 达标才放行，条件②③不变；放行时对全部预热节点写分数快照，沿用 D27 键与 D19 公式；`PodNodeReadiness` 每 Pod K 条（P×K 有界），候选粒度仍由 `ReadinessTable` 承载；代价是预热 IO 与缓存占用最多 K 倍，窗口重叠时更低。数量语义（"精确 K 个"）由 D39 修订为上限 + 下限，门控存在量词、暖备份等其余语义不变。
**为什么**：单节点预热下条件①的存在量词没有实际意义；放行时每行只有一个非零值，`NormalizeScore` 把唯一非零节点归一到 100，D19 的衰减分数不参与节点比较，打分退化成软钉住；唯一预热节点被高优先级任务抢占后其余节点全 0 分，Pod 落到冷节点回源，预热收益归零。有界 fanout 用成本换调度鲁棒性；`fanout=1` 时行为与之前一致，可平滑迁移。
**影响**：判据：固定种子 `fanout=2` 可复现、每 Pod K 节点且满足亲和、任一预热节点达标即放行、status <1 MiB、日志断言（D21）。

### D39 fanout 上限 + 下限与自适应目标数量（取代 D38 的固定数量部分）
**结论**：`spec.preheatFanout` 只作上限（默认 1、最小 1、典型 2），新增 `spec.preheatFanoutMin` 作目标下限（默认 1、最小 1、必须 `<= preheatFanout`）。GWAA 对每个分配单元按块数计算（完整算法见 7.1 §5.5）：`S_min=ceil(0.25×K_i)`；`best <= S_min` 判低信号，`band=min(maxFanout, 可行节点数)`；否则 `band=min(maxFanout, 满足 c_ij >= 0.5×best 的节点数)` 且至少 1；`target=clamp(band, minFanout, maxFanout)` 再按可行节点数封顶；`minFanout > band` 置 `ForcedByMin` 强制补位；`minFanout > 可行节点数` 计划阶段置 `MinUnmet` 且 `target=可行节点数`。亲和合并单元 `unitMin=max(成员 min)`、`unitMax=min(成员 max)`，`unitMin > unitMax` 返回冲突错误，目标集合成员共享。输出新增 `TargetSet` 与 `Decisions`（`TargetFanout/LowSignal/ForcedByMin/MinUnmet/FallbackOutOfTarget`）；除集合外兜底 1 个外 `Assignment ⊆ TargetSet`，冲突裁决与补齐只在集合内进行；集合内放不下时集合外兜底 1 个并置 `FallbackOutOfTarget=true`——兜底始终最多 1 个，因为集合外节点没有缓存分布依据，为凑 min 扩到多个会放大无效预热 IO 并破坏目标集合约束；无任何可行节点才 unassigned；`PreheatSet` 覆盖实际 `Assignment`。`MinUnmet` 的最终定义：冲突裁决、top-up、集合外兜底全部结束后 `len(Assignment[pod]) < 归一后的 min`（GWAA 输入 0 按 1 处理）；`ForcedByMin` 只表示目标被下限抬高，与 `MinUnmet` 是两件事。status 条数 = 实际 `Assignment`，正常在 `[min,max]`，可低于 min（`MinUnmet=true`），任何情况不超过 max（max 是硬上限）；无可行节点写一条空 `NodeName` 汇总。门控条件①仍为存在量词（集合大小以实际 Assignment 为准）；放行分数快照只覆盖实际 `Assignment` 的 P×actual 配对。日志新增 `fanout_min/fanout_max/fanout_target/fanout_actual/low_signal/forced_by_min/min_unmet/fallback_out_of_target/prune_reason`；`pods_per_node` 按实际配对计数。下限仅为目标：冲突、容量与兜底都可能让实际认领更少。
**为什么**：D38 的固定数量在缓存分布集中时多预热无收益节点，分布均匀时又缺区分度；0.25 作低信号下限、0.5 作保留线，让目标数量随分布伸缩——集中时只留最优节点，分散时保留多个暖备份；下限由用户显式声明，避免"算法认为 1 个就够"破坏调度鲁棒性；`TargetSet` 与 `Assignment` 分离使"允许预热范围"与"实际下发范围"可分别观测与裁剪。代价：低信号时目标取到上限（受可行数封顶），预热 IO 与缓存占用最多升到 max 倍，下限强制补位也增加成本；复杂度仍 O(P×N×max)。D38 原文不改、不标作废。
**影响**：判据①–⑩：固定种子复现；`12,1,0,0,0` × min=1/2/3 → 1/2/3；低信号 `1,1,0,0,0` 取上限 3；`11,7,3` 取 2；min>max 拒绝；min>可行数记 `MinUnmet`；status 条数与体积；日志字段；`fanout=1` 回归；8.0 未改动。

### D40 PodNodeReadiness 补齐 MinUnmet bool 字段与 StartupWindowReady 注释
**结论**：`PodNodeReadiness` 追加 `MinUnmet bool`（JSON tag `minUnmet,omitempty`，字段末尾），与 `gwaa.PodDecision.MinUnmet` 同步；Poll 构造条目时直接取该 Pod 的 `PodDecision.MinUnmet`（GWAA 规划结果，轮询不重算），同一 Pod 各条同值；给 `StartupWindowReady` 补注释（见 D41）。
**为什么**：下限未满足事实原先只记在 `PodDecision`，status 明细层没有对应字段，Controller 重启后无法从旧 status 还原"哪些 Pod 没分到足够预热节点"。
**影响**：CRD YAML 由 `controller-gen` 重新生成，零默认值、不写 CEL 规则（MinUnmet 只是观测标记）；`omitempty` 保证 JSON 兼容；验收断言 conflict 用例读回 `minUnmet: true`、重启后可还原。

### D41 StartupWindowReady 字段保留理由与语义
**结论**：`PodNodeReadiness.StartupWindowReady int32` 保留，定义为"窗口内就绪块数的原始计数"；当前实现中与 `ReadyInWindow` 由同一次就绪度计算赋值、值相同。语义分工：`ReadyInWindow` 是门控条件①判定读取的中间结果，`StartupWindowReady` 是 status 中给人直接读的窗口就绪快照（`StartupWindowReadyRate` 的分子）。字段与类型、JSON tag 均不变。
**为什么**：若未来门控口径调整（如 `ReadyInWindow` 改加权计数），`StartupWindowReady` 保持原始计数语义；实现层约束：两字段必须由同一次计算赋值，不得各用一种口径。
**影响**：readinessTable 日志断言同时检查两字段且值相等；`StartupWindowReadyRate = StartupWindowReady / K_i` 链路不回归。

### D42 preheatFanout 默认值上调为 2
**结论**：`spec.preheatFanout` 的 CRD 默认值由 1 上调为 2，最小值仍为 1；`spec.preheatFanoutMin` 默认保持 1。`preheatFanout` 仍只是上限，单节点候选时实际 `Assignment` 为 1，`MinUnmet` 按归一后的 min（输入 0 视为 1）比较，所以单节点不触发 `MinUnmet`。
**为什么**：默认 1 让 D38/D39 的暖备份语义在"不写字段"的默认用法下事实上失效——多数集群的候选节点数不止一个，用户不写 `preheatFanout` 就退回单节点预热，被抢占后仍会落到冷节点。默认 2 让双节点及以上的默认用法直接拿到一个暖备份；单节点集群的实际分配与之前完全一致，升级不改变单节点行为。
**影响**：`controller/api/v1alpha1/warmuptask_types.go` 的 `+kubebuilder:default` 与 `controller/config/crd/bases/traincache.io_warmuptasks.yaml` 同步为 2，CRD schema 断言（`crd_schema_test.go`）随之改判；不写 `preheatFanout` 的 WarmupTask 在 ≥2 个候选节点上预热 IO 与缓存占用最多升到 2 倍（上限内由 GWAA 目标数量决定，低信号时不会强行凑满）。介意预热流量或需要严格单节点行为的用户显式写 `preheatFanout: 1`。`preheatFanoutMin` 与门控口径不变。

### D43 K 自动计算与文件级消费清单
**结论**：`PodDetail.K` 是可选字段，CRD 下限 0；0 表示省略，由 Controller 计算：`W_i` 为 Pod i 实际分到的块数，`K_window = ceil(startupWindowBytes / chunkSize)`，`K_cache = floor(cacheCapacityBytes × maxFillFraction / (podCount × chunkSize))`，`K_i = clamp(min(W_i, K_window, K_cache), 1, W_i)`；`cacheCapacityBytes=0` 时跳过 `K_cache`。K 省略时，Controller 把算出的值 patch 回 `spec.podDetails[].k`，立即 `Requeue`，并发 Normal 事件 `KDefaulted`（日志 `startup window K defaulted`）。显式 K 的有效范围是 `1..W_i`；`K > W_i` 置 `Condition InvalidSpec=False` 并拒绝，不截断、不钳制。`cacheCapacityBytes > 0` 时，全部 Pod 实际请求块数合计超过 `cacheCapacityBytes × maxFillFraction` 只发 Warning 事件 `KExceedsFillLimit`，任务照常执行。`startupWindowBytes` 默认 536870912（512MiB），`maxFillFraction` 默认 0.125，`cacheCapacityBytes` 默认 0，三者由 ConfigMap `traincache-config` 注入为 `TRAINCACHE_*` 环境变量。`PodDetail.InitialConsumeFiles []string` 填 tar 分片名；每个 Pod 只写自己的分片，全部 Pod 合起来必须恰好覆盖全部分片且每个分片只出现一次；未满足该条件时整组回退默认均分，置 `status.consumeOrderSource=Default` 并发 `ConsumeOrderDefaulted`；`totalChunks < podCount` 置 `Condition InvalidSpec=False` 拒绝，不回退。预热请求块数为 `min(max(K_i, score.cutoff), W_i)`，超过消费顺序长度时截断。
**为什么**：用户按"启动阶段读多少字节"配置窗口，不自己换算块数；清单以分片为单位，与 `traincache ls` 看到的文件对齐，用户不需要知道全局块号。`min` 保证窗口不超过该 Pod 实际分到的数据，也不超过按 podCount 均摊的缓存预算；下界取 1 避免算出的 0 被误读成"省略"。`maxFillFraction=0.125` 让自动 K 下的多 Pod 预热不填满节点缓存。显式 K 超过 `W_i` 无法落到真实块上，只能拒绝；超过缓存预算仍可执行，但多出的块要回源。
**影响**：`warmuptask_types.go` 的 `K` 不必填（0 = 自动），CRD schema 的 `k` 下限为 0；`initialConsumeFiles` 的解析与校验单测覆盖未知分片、全组重复、未覆盖全部分片与 `totalChunks < podCount`，`ConsumeOrderSource`、`ConsumeOrderDefaulted` 与默认切分规则不变。`score.cutoff > K_i` 时请求块数取 `cutoff`，但不超过 `W_i`；只想预热 `K_i` 块的任务必须把 `cutoff` 设到 `K_i` 以内。

### D44 放行快照终态冻结
**结论**：`gateDecision` 随 status 落库后，该 `(任务 UID, generation)` 的分配即冻结：不再重算 GWAA、不再发 `Submit`/`Update`/`Cancel`、不再重写 Pod 分数注解，`status.podNodeReadiness` 的配对就是放行快照。冻结判定记在进程内 `pollTracker` 的「任务 UID → 已提交终态的最高 generation」表里，与 status 缓存副本无关；`isTerminal` 的 status 判断保留，负责跨进程重启。§7.8 落点兜底照常运行，只回填 `ActualNode` 并在实际落点提交 P0 预热。规格换代（`generation` 变化）与删除重建（新 UID）都重新开启循环。
**为什么**：放行那次 status patch 自身会触发一次 watch 事件，紧随其后的 reconcile 可能读到还没收到该 patch 的缓存副本，`isTerminal` 判不出来，于是把整条预热流水线重跑一遍。同一代的并列裁决又共用一条 RNG 流，取到哪个配对取决于本轮各分配单元走的是 `LowSignal` 还是 `c_ij ≥ 0.5×best` 分支，块陆续落盘会让分支组合变化——于是互换的配对被写回 status，刚提交的热配对被 `Cancel`，门控从 `Released` 倒退回 `Hold`。e2e 现场（2 Pod / 2 候选节点 / `fanout=1`）100 ms 内出现 3 次配对与 6 次 Cancel/Submit，其中 1 个 `NodeDeviation` 是互换的副产物（Pod 恰好落在放行注解给它 88 分的那个节点上），最终 status 配对还与放行写下的注解互相矛盾。只把种子钉在 `(UID, generation)` 上不足够：流的位置会随分支消耗量移动，必须由"终态不再重算"来封住。
**影响**：`internal/controller/warmup` 的 Reconcile 在 `reconcileDeviation` 之后的短路条件加上进程内冻结判定，status patch 成功后记录该 UID 的 generation；`pollTracker` 新增该表，与 rateHistory 同生命周期（内存态，重启后由 status 判定）。放行前（`Hold` 期）的每轮重算不变，`ReadinessTable` 变化仍会正常调整目标集合与实际分配。回归测试 `terminal_freeze_test.go` 用只返回放行前副本的 client 驱动第二次 Reconcile，断言零 placement RPC、零注解重写、配对不被改写。

### D45 目标集合在册保留（迟滞）
**结论**：GWAA 的 `Input` 增加 `Held map[int32][]string`，取本轮 `GetPreheatStatus` 报持有（`canceled=false` 且非 `NotFound`）且代际等于本轮的配对。目标集合按 §5.5 1–7 算出后，`Held` 里仍可行、未停止且满足保留线（非低信号时 `c_ij ≥ 0.5 × best`，低信号时视为满足）的节点强制留在集合内：集合已满就换掉排名最低且不在 `Held` 中的那个，未满就直接加入，`target` 数量不变。掉出保留带、被判停止、Agent 报未持有（含换代）之后不保留，按排序自由重选。迟滞只做集合内替换，不消耗 RNG，不动 `LowSignal`/`ForcedByMin`/`MinUnmet` 口径。
**为什么**：宽预热把同一个窗口投给全部候选节点，各节点进度天然同步，而目标集合取严格 `c_ij` 排序——谁刚多落一块谁就是 `best`。e2e 现场（1 Pod / 4 候选节点 / `fanout=1` / `t_max` 内）10 分钟里 `p0` 在四个节点间翻了 50 次，每次翻动一发 `Submit` 一发 `Cancel`，四个节点各下满 1059969024 B（合计 ≈4 GiB，即 A 级问题的 3–4 倍字节放大）。D44 的终态冻结只封住放行之后，`Hold` 期的翻转仍在。原 D32 把种子钉在 `(UID, generation)` 只保证同输入同输出，输入（`ReadinessTable`）每轮都在动，所以封不住翻转；要封住必须让"已在册"本身成为理由，而不是让分数比大小。
**影响**：`internal/gwaa` 的 `Compute` 多一个输入、目标集合构造后多一步替换；`internal/controller/warmup` 把 §7.4 的台账同时喂给 GWAA（原来只喂差异比较）。判据：`fanout=1`、四节点同步进度的场景里连续多轮 `assign` 不变、`agent submit`/`agent cancel` 日志计数为 0（首次宽预热除外）；节点掉出保留带后仍按 §5.5 换人（回归用例覆盖）。

### D46 重投后丢弃 seq 高水位
**结论**：`ApplyPlacement` 对某 `(pod,node)` 成功发出 `Submit` 或 `Update` 后，控制器立即删除 `pollTracker` 里该配对的 `seq` 高水位，下一轮起该节点从 `seq=1` 起的上报都算新鲜。`check` 的丢弃规则本身不变（同代 `seq ≤` 水位记 `stale`，低代际记 `old generation`）。
**为什么**：水位是配对级的、进程内长期保留，而 Agent 的任务实例是短命的：同名同代际的重投按附录 A 当新任务，`seq` 从 1 重启。两者一旦错配，重投之后该节点的全部进度对控制器不可见。e2e 现场（同 D45）：`traincache-worker2` 在 14:28:11 交了最后一份被接受的上报（`ready=31`），14:28:12 被重新提交，Agent 侧 14:33:36 报 `state=DONE total_blocks=128 completed_blocks=128`，控制器侧 `ready` 全程停在 31、`rate` 停在 0.2422，`requiredReady=115` 永远够不到，最终以 `tmax_exceeded` 降级。整段 `Hold` 期里 `ready` 只在翻动那一轮跳，说明表读的是各节点被冻结的旧值，不是现值。
**影响**：`ApplyPlacement` 成功后需要一个回调（或让 Reconcile 拿 `PlacementApplyResult` 的已提交配对去清水位），`pollTracker` 新增一个删除方法；指标口径不变，重投后恢复的上报照常记 `ok`。回归用例：伪造一个"重投后 seq 从 1 重启"的 Agent，断言清水位前该配对零进展、清水位后进度重新进表。

### D47 窗口变化判据改用窗口块数
**结论**：`PreheatStatus` 追加 `uint32 window_blocks = 16`，Agent 回显当前任务 `chunks` 项数（`UpdatePreheat` 全量替换后同步）；§7.4 的「未变化」判据改为 `generation` 相同且 `window_blocks` 等于本轮窗口块数。不去重、不用 `total_blocks`。
**为什么**：原判据比 `ready_bitmap` 长度，分辨率是 `ceil(块数/8)`；同一字节区间内窗口从 7 块缩到 8 块或反之都不发 `Update`，Agent 按旧窗口预热，首 epoch 命中率下降而不报错。`total_blocks` 按去重后的唯一块计，与窗口位置数不等价，拿来比会在含重复块的窗口上误判。窗口指纹哈希能覆盖同块数换块，但 Controller 与 Agent 要重复实现同一哈希，当前窗口由控制器单侧生成，块数足以判定。
**影响**：`agent/api/agent.proto`、`agent/svc/preheat.go`、`internal/controller/warmup` 的 `poll.go`/`place.go`/`gate.go`；位图长度校验与位序约定不变。

### D48 PodSetMismatch 只描述部分匹配
**结论**：`targetPodNames` 匹配数为 0 时不置 `Condition PodSetMismatch`、不发声、只记 Debug；匹配数大于 0 且不等于 `spec.podCount` 才置条件并发 Warning 事件；相等时摘条件。
**为什么**：宽预热先于 Pod 创建，预热期 `pods=0` 是预期状态。原判据把它当不一致，每轮 `Warn` 刷屏并让条件长期为真，既淹没真正的部分不一致，也让 8.2 的告警口径对每个任务都报一遍。
**影响**：`controller/internal/controller/warmup/controller.go` 前置检查段；条件与事件去重仍由 `setCondition` 的返回值承担，行为契约变更同步到 §7.2 步骤 3 与 §7.9。

### D49 Pod 分数注解（取代 D27）
**结论**：分数快照写在训练 Pod 自己的注解上，键为 `CONTROLLER_SCORE_ANNOTATION`（默认 `traincache.io/node-scores`），值 `{"v":1,"task":"<ns>/<name>","g":<gen>,"t":"RFC3339","s":{"<node>":0..100}}`；`s` 只含该 Pod 实际 `Assignment` 的节点。写分数与移除 scheduling gate 在同一次 Pod patch 内完成，失败时两者都不变；Pod 的 gate 移除后不再改写它的注解。Scheduler 读本 Pod 注解、按节点名取分，不再读 Node，也不再依赖 `pod-index` 定位分数。
**为什么**：原设计在放行时先写 Node 注解、几毫秒后摘 Pod 的 gate；Node 与 Pod 是两个对象、两条 watch 流，Scheduler 可能在看到 Pod 可调度时还没收到 Node 注解更新，取到 0 分（kind e2e 复现：分数在 .628/.632 写入，Scheduler 在 .640 仍读不到）。在同一 Pod patch 内写分数，Scheduler 看到的 Pod 对象自带分数，顺序竞争消失；不引入等待或重试延迟，放行时间不变。分数按 Pod 独立存放后，每个 Pod 的写入失败只影响它自己：该 Pod 继续被 gate 拦住，不会出现"分数已写但 Pod 仍被卡住"或反之的中间态。
**影响**：`internal/scorefmt` 删除键编码（`Key`/`KeyWithPrefix`/`ParseKey`），只保留值编解码，字段 `p` 改为 `s`；`internal/controller/warmup/annotation.go` 的 Node 读改写与冲突重试删除，写注解并入 `gate.go` 的摘 gate patch；`internal/scheduler` 改读 Pod 注解，去掉 pod-index 分支，指标枚举 `no_pod_index`/`invalid_pod_index`/`no_pod_entry` 换成 `no_node_entry`；配置默认值改为 `traincache.io/node-scores`；e2e 断言改读 Pod 注解。D27 的每任务键与 hash 编码作废。

## 3. 决策变更流程
1. 实现方发现约定不可实现或与基线冲突，回传 `BLOCKED`：附理由、证据（文件/行号/命令输出摘要）与建议方案。
2. 主对话裁决：采纳则更新 8.1 对应节与本文 D 条目；被取代的旧编号保留并在索引标注取代关系，新决策顺延编号。
3. Q 结案时在行内写裁决；影响冻结契约的升级为 D，并同步 8.2 的任务与判据。
4. 任何变更不得修改 8.0；需要基线变更时只输出增量建议，由用户决定（fanout 修订经用户授权直接落地 8.0，见 D38；上限+下限的数量语义只写 8.1/8.2，见 D39）。
