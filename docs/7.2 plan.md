# 8.2 Controller & Scheduler plan

> 对应设计：`docs/8.1 design.md`；决策与未决：`docs/8.3 decisions.md`；需求基线：`docs/8.0 Controller & Scheduler.md`（不改动）。
> 本计划不含已完成模块的重构；对 `agent/` 的唯一改动是 §M3 的最小增量 RPC。

这份文档回答一个问题：Controller 和 Scheduler 这么一大坨功能，按什么顺序做，每做完一块怎么算过关。

读法建议：先看 §1 的里程碑总览，找到当前要做的 M 编号；再跳进对应小节看目标、任务清单和验收命令。每个里程碑都是"能独立验收的一块"，做完一块再动下一块。

## 0. 执行方式（固定）

开发由子代理按里程碑纵向切片交付，主对话负责派活和验收。下面几条是固定的协作规则，不随里程碑变化。

- **派活**：一次一个 M，主对话不并行派同一文件的写入，避免冲突。
- **验收**：每个 M 完成后由独立验收子代理执行验收命令；主对话只接收 `VERDICT` 与判据结论（不信任自报，主对话也要亲自核一遍）。
- **M0 只出文档**：本阶段不创建业务代码，只冻结签名。
- **签名不符即 BLOCKED**：任何与 `docs/8.1 design.md` 冻结签名不一致的实现，必须先回传 `BLOCKED` 由主对话裁决，私自改签名是违规。

四条协作规则各自解决一件事："一次一个 M"是防止两个子代理同时改同一个文件；"独立验收"是不信任自报；"M0 只出文档"是先把契约定死再动代码；"签名不符即 BLOCKED"是不让实现者私自改契约。

## 4. M2 DataSet 控制器

这一步做的是"把一个 DataSet 对象从创建到落地"——校验字段、解析快照旧快照、算出块布局、找到哪些节点能访问。类比：DataLoader 要开始预取，先得知道有哪些块、块在哪些 shard、哪些节点有 S3 访问权限。

**目标**：DataSet 的校验、块布局固化、可达节点解析、快照校验与默认消费顺序兜底可运行。

## 5. M3 proto 增量与 Agent 实现（7.x 增量）

这一步给 Agent 加两个新 RPC（UpdatePreheat、CancelPreheat）、扩展 GetPreheatStatus 返回位图和 generation/seq。Agent 侧要能**幂等**（同一个请求发两遍结果一样，不会建两份预热任务）地维护每个 (pod,node) 任务的窗口顺序、generation（版本号，用来拒绝过期请求）、**位图**（每个块的就绪状态，0 未就绪、1 就绪）和 **seq**（状态变化计数器，用来判新旧）。

**目标**：最小化 RPC 增量——复用 `GetPreheatStatus` 并扩展字段，`SubmitPreheatRequest` 增加 generation，仅新增 `UpdatePreheat`/`CancelPreheat`；Agent 侧可幂等维护任务顺序、generation、位图与 seq。

**任务清单**

| #   | 任务                                                                                                                                                                                                                                                                                                                                                          | 类型         | 文件                                           |
|-----|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------|------------------------------------------------|
| 3.1 | 修改 `agent/api/agent.proto`：`SubmitPreheatRequest` 增 `uint64 generation = 8`；`PreheatStatus` 增 `uint64 generation = 12`、`uint64 seq = 13`、`bytes ready_bitmap = 14`；新增 `UpdatePreheat`（task_id/node/generation/chunks/priority，`chunks` 全量替换并重定义位序）与 `CancelPreheat`（task_id/node/generation）消息；不新增独立进度查询 RPC；重新生成 | 接口增量     | `agent/api/agent.proto`, `agent/api/agentpb/*` |
| 3.2 | Agent 任务表按 `task_id` 存储最近一次 chunks 顺序、generation、位图、seq                                                                                                                                                                                                                                                                                      | 业务         | `agent/svc/*` 或新文件                         |
| 3.3 | Submit/Update/Cancel 入参校验、低 generation 拒绝（`FailedPrecondition`）、幂等；Cancel 后同名同 generation 再 Submit 视为新任务                                                                                                                                                                                                                              | 业务         | 同上                                           |
| 3.4 | `GetPreheatStatus` 回显扩展字段：位序=最近一次 Submit/Update 的 chunks 顺序，长度恰为 `ceil(len(chunks)/8)`；状态变化时 seq 严格递增、无变化不变                                                                                                                                                                                                              | 业务         | 同上                                           |
| 3.5 | 位图在"落盘 + 校验通过"后置位；失败位保持 0；Update 全量替换 chunks 后按新顺序重定位图（seq++）                                                                                                                                                                                                                                                               | 业务         | 同上                                           |
| 3.6 | Agent metrics 白名单同步：family/标签与 8.1、7.1 附录一致，不新增 task_id/node 等高基数标签                                                                                                                                                                                                                                                                   | 观测         | `agent/metrics/*`                              |
| 3.7 | 日志点：RPC 入口/出口、拒绝陈旧 generation、位图与 seq 更新                                                                                                                                                                                                                                                                                                   | 日志（硬性） | 同上                                           |

**复用/新建判断**：Agent 那边 SubmitPreheat 的任务状态机、GetPreheatStatus 的响应通路、fetch/cas 下载链路都是现成的，直接复用；新加的只是"任务快照（存窗口顺序+generation+位图+seq）"和两个 RPC。

**交付物**：proto 最小增量、Agent 两个新 RPC、`GetPreheatStatus` 扩展字段、单测。

**验收**

```bash
cd agent && go build ./... && go vet ./... && go test ./... -race -count=1
```

**判据**：① 旧 RPC 行为不变（既有测试零改动通过，`PreheatStatus` 既有字段编号与语义不变）；② 低 generation 的 Submit/Update/Cancel 均返回 `FailedPrecondition`；③ Cancel 后重 Submit 为新任务；④ 位图长度恰为 `ceil(len(chunks)/8)`，bit 序与请求 chunks 顺序一致，越界/多余位不置位；⑤ generation 回显已接受值；seq 在状态变化时严格递增、无变化时不变；⑥ 并发 Submit 同一 task 不重复下载（singleflight 命中）；⑦ metrics 白名单一致；⑧ 源码中不存在独立进度查询 RPC 的定义或引用，进度统一走 `GetPreheatStatus`。

小结：M3 让 Agent 能被 Controller 改派和取消任务、能回报位图进度，是 Controller ↔ Agent 通信的增量。

## 6. M4 Agent 客户端、候选筛选与预热下发

前面 M1–M3 搭好了骨架和增量 RPC，这一步把 Controller 连起来：知道每个节点 Agent 的地址、筛出"能预热"的节点、把预热窗口下发过去。类比：Controller 拿到 DataSet 的块清单、算出每个 Pod 该读哪些块、找到能干活的 Agent Pod、把任务派下去。

**目标**：Controller 能解析节点 Agent 地址、按 `(pod,node)` 下发窗口预热。

**任务清单**

| #   | 任务                                                                                                                                                                 | 类型         | 文件                                   |
|-----|----------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------|----------------------------------------|
| 4.1 | 节点 → Agent Pod IP 解析与 30s 缓存                                                                                                                                  | 新模块核心   | `internal/agentclient/resolve.go`      |
| 4.2 | `Pool` 实现：Submit/Update/Cancel，超时与错误映射（进度查询 `Status` 在 M5 补充）                                                                                    | 新模块核心   | `internal/agentclient/client.go`       |
| 4.3 | 候选节点 `Filter`                                                                                                                                                    | 新模块核心   | `internal/controller/warmup/filter.go` |
| 4.4 | 窗口块展开：按显式 `initialConsumeOrder` 或默认切分区间取全局块号 → `ChunkRef{path,chunk}`，顺序即请求与位图位序                                                     | 业务         | `internal/controller/warmup/blocks.go` |
| 4.5 | 下发循环与失败退避                                                                                                                                                   | 业务         | `internal/controller/warmup/submit.go` |
| 4.6 | 消费顺序兜底接线：任一 Pod 顺序空/越界/重复 → 全部改用 `DefaultSplit`，发 `ConsumeOrderDefaulted` 事件并写 status `consumeOrderSource=Default`；`T<P` 置条件且不下发 | 业务         | 同上                                   |
| 4.7 | 日志点：筛选计数、消费顺序来源、每个 Submit、失败重试                                                                                                                | 日志（硬性） | 同上                                   |

**复用/新建判断**：gRPC 拨号/超时的写法沿用 agent CLI 的 `grpc.NewClient` + insecure 风格，不引入连接池库；`ChunkRef` 直接用 proto 里的类型；默认切分函数是 M2 刚写好的 `DefaultSplit`，这里直接调。Controller 不创建/修改/删除 Job 或 Pod，只往它们写 annotation、往 Agent 发 RPC。

**交付物**：agentclient、Filter、块展开与下发；fake gRPC server（bufconn）。

**验收**

```bash
cd controller && go test ./internal/agentclient/... ./internal/controller/warmup/... -race -count=1
```

**判据**：① 无 Ready agent 的节点被排除；② 污点/NotReady/不可达节点排除；③ 块展开对跨 shard 边界正确，块号顺序与请求/位图位序一致；④ Unavailable 触发重试且不改 status；⑤ 任一 Pod 顺序空/越界/重复时全部 Pod 使用默认切分，事件与 status 正确；`T<P` 不下发；⑥ 不创建/修改/删除 Job/Pod，Pod 数与 `podCount` 不一致时只置条件；⑦ 日志断言覆盖消费顺序来源、Submit 与失败路径。

小结：M4 是 Controller ↔ Agent 通信的第一阶段——下发预热任务，后面 M5 才开始拉进度。

## 7. M5 进度拉取与就绪表

任务已经下发到各节点 Agent 了，这一步要做两件事：**轮询**每个 Agent 的 GetPreheatStatus 拉取位图，**维护**一张 P×N 的**就绪表**（P 是 Pod 数、N 是候选节点数，每格记录这个节点上这个 Pod 的预热窗口就绪了多少）。这张表是后面门控（什么时候放行）和打分（哪个节点该被 Scheduler 选中）的数据来源。

**目标**：按周期调用 `GetPreheatStatus` 拉取扩展位图，维护 P×N 就绪表与 Pod 明细。

**任务清单**

| #   | 任务                                                                                                                          | 类型         | 文件                                   |
|-----|-------------------------------------------------------------------------------------------------------------------------------|--------------|----------------------------------------|
| 5.1 | Poll 定时器与 task 遍历（每 controller 串行），逐个 `(pod,node)` 调 `GetPreheatStatus(task_id)`；`Pool.Status` 复用 M4 连接池 | 业务         | `internal/controller/warmup/poll.go`   |
| 5.2 | 解码 `ready_bitmap`（位序=请求 chunks 顺序）、长度校验、按每 Pod `K_i` popcount、rate 计算                                    | 新模块核心   | `internal/nodescore/bitmap.go`         |
| 5.3 | readinessTable 行列稳定写入与 status patch                                                                                    | 业务         | `internal/controller/warmup/status.go` |
| 5.4 | 陈旧 generation / seq 回退 / 乱序响应丢弃：响应 generation 低于当前任务或 seq 小于已见值即丢弃                                | 业务         | 同上                                   |
| 5.5 | 连续失败降级与 `PreheatState`                                                                                                 | 业务         | 同上                                   |
| 5.6 | 日志点：轮询变化、位图/seq 丢弃、降级                                                                                         | 日志（硬性） | 同上                                   |

**复用/新建判断**：rate（就绪率）和窗口计算是 Controller 新写的；status patch 用 controller-runtime 的 `Status().Patch`，不自己造 API 客户端。

**交付物**：Poll 循环、位图工具、就绪表测试。

**验收**

```bash
cd controller && go test ./internal/nodescore/... ./internal/controller/warmup/... -race -count=1
```

**判据**：① 位图 bit i 对应请求 `chunks[i]`，逐位断言；② 位图长度必须为 `ceil(len(chunks)/8)`，不匹配按解析失败处理且不更新表；③ 每 Pod `K_i=1/7/8/9` 边界 popcount 正确；④ 旧 generation 或 seq 回退的响应不改变表，重复 seq 视为无变化；⑤ 连续 3 次失败置 `Failed`；⑥ 表尺寸 P×N 与候选节点顺序一致。

小结：M5 把"下发了哪些任务"变成"每个任务在哪个节点上就绪了多少"，是 GWAA 分配和门控放行的依据。

## 8. M6 GWAA

**GWAA** 是 Greedy With Arbitrary Accept（贪心近似分配）——它解决的问题是：P 个训练 Pod、N 个候选节点，每个 Pod 想预热 K 个节点，怎么分才能让每个 Pod 分到的节点缓存就绪率最高、同时满足亲和/反亲和约束、一个节点上不能放太多 Pod 的任务。不求全局最优，用贪心轮次收敛就够了。并列冲突靠注入 RNG 随机裁决，固定种子能复现，便于测试。

**目标**：纯函数贪心近似分配算法；并列用注入 RNG 随机裁决，固定种子可复现；可测试、可回退。不追求全局最优。

**任务清单**

| #   | 任务                                                                                                        | 类型         | 文件                                  |
|-----|-------------------------------------------------------------------------------------------------------------|--------------|---------------------------------------|
| 6.1 | `Compute`：粗铺→贪心认领→冲突裁决→有限轮收敛→回退；并列随机由注入的 `*rand.Rand` 决定，最大轮数 `len(Pods)` | 新模块核心   | `internal/gwaa/gwaa.go`               |
| 6.2 | 分配差异 → Submit/Update/Cancel 编排；无可行节点的 Pod 返回 unassigned                                      | 业务         | `internal/controller/warmup/place.go` |
| 6.3 | 未收敛告警与回退到首次贪心结果                                                                              | 业务         | 同上                                  |
| 6.4 | 日志点：分配变化、轮数、回退原因                                                                            | 日志（硬性） | 同上                                  |

**复用/新建判断**：没有现成算法可套，这是一个新写的纯函数；要求是"不依赖 k8s 类型"——纯 Go 输入输出，方便独立测试。RNG 由调用方注入，测试时固定种子保证每次输出一样。

**交付物**：GWAA 与编排；固定种子复现与随机种子合法性测试。

**验收**

```bash
cd controller && go test ./internal/gwaa/... ./internal/controller/warmup/... -race -count=1
```

**判据**：① 固定种子同一输入 100 次输出一致；② 随机种子多次运行：每个 Pod 至多一个节点、亲和/反亲和与一节点多 Pod 约束均满足、仅当无任何可行节点时才 unassigned；③ 并列由注入 RNG 随机裁决，不同种子可不同但均合法；④ 不收敛时回退首次贪心结果且日志 Warn；⑤ 分配变化只对差异调用 RPC。

小结：M6 决定"每个 Pod 预热哪几个节点"，是预热任务下发的调度策略。

## 9. M7 门控判定与放行

门控 = 给 Pod 加的一个"等待预热完再调度"的 gate。Pod 创建时 webhook 注入这个 gate，Scheduler 看到 gate 存在就不给 Pod 分配节点。M7 要写"什么时候摘掉这个 gate"——三个条件（超时、所有 Pod 就绪、边际收益不足）按固定顺序判。

**整数门控** 是这里的核心改动：用 `required_i = floor(threshold*K_i)`（一个整数）和 `ReadyInWindow >= required_i` 比较，替代原来的浮点 rate >= threshold。好处是审计友好——所有人看到的都是整数比较，不会有浮点舍入争议。

**目标**：三条件门控（条件①用整数 `required_i`）、放行时冻结评分并摘 gate。

> 边际收益说明：预热等待的收益随就绪率接近阈值而递减。条件②是边际收益判据——只在一个 Pod 已达标、其余 Pod 的 `gap` 仍大且 `slope` 已足够小（继续等待几乎不再涨）时提前放行；条件③是绝对上限，无论进度如何到 `TMax` 必须降级放行。判定顺序固定为 ③ 超时 → ① 全 Pod 达标 → ② 边际收益不足 → `Hold`。

**任务清单**

| #   | 任务                                                                                                                                            | 类型         | 文件                                 |
|-----|-------------------------------------------------------------------------------------------------------------------------------------------------|--------------|--------------------------------------|
| 7.1 | `Evaluate` 三条件与斜率采样；条件①用整数 `required_i = floor(threshold*K_i)`（`threshold>0` 且结果为 0 时取 1，上限 `K_i`）比较 `ReadyInWindow` | 新模块核心   | `internal/gate/gate.go`              |
| 7.2 | 首次达标时刻记录（条件②）                                                                                                                       | 业务         | `internal/controller/warmup/gate.go` |
| 7.3 | 放行编排：写每任务 annotation → 摘 gate → 写 status                                                                                             | 业务         | 同上                                 |
| 7.4 | 部分摘除失败的幂等重试                                                                                                                          | 业务         | 同上                                 |
| 7.5 | 日志点：每次判定、`required_i`/`gap`/`slope`、放行原因、摘除结果                                                                                | 日志（硬性） | 同上                                 |
| 7.6 | 整数门控边界矩阵（K=1/7/8/9 × threshold=0/0.8/0.9）与边际收益场景测试                                                                           | 测试         | `internal/gate/gate_test.go`         |

**复用/新建判断**：门控的三条件逻辑和整数门控是 Controller 新写的；Pod patch 用 controller-runtime client，不自己造 webhook 依赖。

**交付物**：门控纯函数、放行编排、时钟注入测试、整数门控边界矩阵测试。

**验收**

```bash
cd controller && go test ./internal/gate/... ./internal/controller/warmup/... -race -count=1
```

**判据**：① `required_i=floor(threshold*K_i)`，`threshold>0` 且结果为 0 时取 1，且恒 `0<=required_i<=K_i`；K=8/threshold=0.8 → 6；`rate` 仅用于观测/展示，不参与放行判定；② K=1/7/8/9 × threshold=0/0.8/0.9 矩阵全部有断言（threshold=0 时 `required_i=0`，条件①恒真）；③ 条件①/②/③ 各有正反用例；`t >= TMax` 必 Degraded；④ slope 采样不足不触发条件②；⑤ 边际收益场景：首个 Pod 达标后其余 `slope >= slope_min` 继续 Hold，`gap > gap_min && slope < slope_min` 才放行，接近阈值时等待收益递减不误放行；⑥ 摘 gate 幂等；⑦ annotation 写失败不摘 gate。

小结：M7 决定"什么时候放行所有 Pod"——放行后 Scheduler 才能开始给 Pod 分配节点。

## 10. M8 评分计算与 Node annotation

Scheduler 想给 Pod 选"预热就绪率最高"的节点，就得知道每个节点对每个 Pod 的预热就绪得分。M8 要做两件事：① 按窗口权重算每个节点对每个 Pod 的 `S(node)` 分；② 把分数写到 Node 的 annotation 上（key 按任务隔离、不覆盖）。Scheduler 读这个 annotation 来打分。

**目标**：按每 Pod `K_i`/H/C 计算 S(node)，按任务独立注解键读-改-写 Node annotation。

**任务清单**

| #   | 任务                                                                                                                                                                            | 类型         | 文件                                       |
|-----|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------|--------------------------------------------|
| 8.1 | 权重与分数计算：窗口用每 Pod `K_i`（不设全局窗口字段），`i<C` 截断，含 Σw=0 边界                                                                                                | 新模块核心   | `internal/nodescore/score.go`              |
| 8.2 | 每任务注解键 `traincache.io/scores-<namePrefix32>-<hash12>` 的计算、读-改-写与冲突重试；值为单行 JSON，字段 `v/task/g/t/p`，其中 `task="<ns>/<name>"`、`p={"<podIndex>":score}` | 业务         | `internal/controller/warmup/annotation.go` |
| 8.3 | 评分冻结与 generation 语义                                                                                                                                                      | 业务         | 同上                                       |
| 8.4 | 日志点：评分明细（Debug）、写入结果（Info）                                                                                                                                     | 日志（硬性） | 同上                                       |

**复用/新建判断**：annotation 键编码和值编解码是 M1 写的 `internal/scorefmt`，这里直接用；不同任务写不同的 annotation key，互不干扰；同一任务的多个 Pod 分数合并在同一个 key 的 JSON 里。

**交付物**：评分函数、每任务 annotation 写入器、并发合并与键编码测试。

**验收**

```bash
cd controller && go test ./internal/nodescore/... ./internal/controller/warmup/... -race -count=1
```

**判据**：① 两个 Pod 的 `K_i` 不同时，窗口边界（`i=K_i-1/K_i/C-1/C`）与分母各自正确；② Σw=0 时 S=0，取整与截断正确；③ 往返编解码逐字段一致（`v/task/g/t/p`）；④ 两个 task 并发写同一 Node 使用不同键，双方条目均保留；同 task 并发写同一 Node 不丢 `p` 条目；⑤ 冲突重试上限 5 次后返回 error；⑥ 过期条目保留但 Scheduler 不采用；⑦ 键与 `scorefmt` 编码一致、键名部分 ≤52。

小结：M8 把"就绪度"变成"分数"写到 Node 上，供 Scheduler 打分插件读取。

## 11. M9 MutatingWebhook

Pod 创建时 K8s 会调 webhook。M9 要做的是：拦截训练 Pod、注入三个 annotation（warmup-task 引用、pod-index 序号、gate 标志）。gate 标志让 Pod 保持 Pending 直到 Controller 放行。这里的逻辑是"能注入就注入，注入不了也不让 Pod 创建失败"——返回 allowed + 事件，Controller 后面检测到没注入再置条件。

**幂等**是这里的关键点：同一个 Pod 被 webhook 处理两次，annotation 不能加两份（不能有两个 gate）。

**目标**：Pod 创建时注入 gate、task 引用与 pod 序号。

## 17. 里程碑间依赖与回退

这一节讲清楚两件事：**哪些能并行、谁等谁**；以及失败了怎么回退。

**并行可能性**：
- M3（Agent 增量）排在 M0 之后就能开始，不依赖 M1/M2。M4 虽然要等 M3 出 RPC 签名才能写，但 M3 本身可以和 M1/M2 同时进行。
- M4–M5 必须等 M2 的 DefaultSplit 和 M3 的 RPC，这俩是前置。
- M6 要等 M5 的就绪表（没表就没得分输入）；M7 要等 M6（要知道分配到哪几个节点）；M8 可以和 M6 并行——它只依赖 M5 算出的分数权重，和分配结果无关。
- M9（Webhook）和前面所有业务里程碑解耦，M1 之后就能开干；M10 要等 M8 写 annotation 的格式定下来，但不依赖 Controller 主逻辑。
- M11 把 M2–M10 全部收齐才能跑端到端；M12 是 M11 之后的验收总闸；M13 排 M12 之后；M14 排 M13 之后。

**回退策略**：每个 M 独立提交一个 commit，哪个 M 验收失败就只回退这一个 commit。CRD 字段只增不改（向后兼容），所以回退一个 M 不会把已写入 status 的字段搞坏。

**判据**：
