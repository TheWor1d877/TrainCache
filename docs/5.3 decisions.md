### D1 库形态与位置

**结论**：核心库是无服务形态的 Go 库，独立 module `traincache/core`，代码放在新目录 `core/`。

**为什么**：`doc/7` 写明“没有任何服务形态，现在就是一组代码加单元测试”。做成独立 module 能和 bench 装置解耦。

**约束与影响**：库本身不跑进程；引用方按 module 路径 `traincache/core` 导入。

### D2 分层与依赖

**结论**：分成 `objectstore` / `cas` / `fetch` / `index` 四个包，外加 `internal/digest`。依赖单向无环：`index→cas、objectstore`；`fetch→objectstore、cas`；`cas` **不依赖** `objectstore`。

**为什么**：下载得到的字节流由 `fetch` 喂给 `cas.Put`，本地存储和远端存储因此解耦；`cas` 只碰本地磁盘，可以独立测试。

**约束与影响**：依赖方向是硬约束，反向 import 不允许。

### D3 块头格式

**结论**：统一 128B v1，不做 64B 变体。字段包括：magic `"TCBK"`、version=1、flags bit0 表示 sha256 有效、block_size uint32 LE、xxh3_128、sha256（可选）、reserved 对齐。

**为什么**：`doc/7` 的 64B 是过渡表述，128B 才是扩展目标。直接上 128B 可以避免维护两套解析逻辑。存储键恒为 xxh3-128，去重不受 sha256 开关影响。

**约束与影响**：v1 解析器只认这一种块头布局；块头长度固定 128B。

### D4 块切分

**结论**：`(path, chunkIndex)` 按 `ChunkSize` 固定切分，默认 64 MiB，参数可调。`Entry` 含 `Size`（末块可以不足），字节偏移由 `chunk × ChunkSize` 推导，不落盘。

**为什么**：`doc/7` 的键里带 chunkIndex，本身就是固定切分语义。offset 冗余但能推导，将来要支持变长块再加字段即可（JSON 向后兼容）。

**约束与影响**：`Entry` 不存 offset；读侧自己按块号乘块大小算偏移。

### D5 分片格式

**结论**：一个分片是 `Entry` 的 JSON 数组，字段名用全称。每片最多 `MaxEntriesPerShard` 条（默认 100_000，`doc/7` 的硬上限）。构建时先按 `(path, chunk)` 字典序排序，再按条目数切分（range-based）。完整性靠把分片内容的 xxh3-128 记进 manifest。

**为什么**：JSON 可读、可调试，构建和合并逻辑都简单。分片放在对象存储上，体积不敏感——10 万条约 13MB。

**约束与影响**：单分片超过 10 万条就违反契约。

### D6 分片对象键含内容指纹

**结论**：分片键是 `shard-<fp8>.idx`，其中 fp8 取内容 xxh3 的前 8 字节 hex。

**为什么**：内容没变的分片物理复用同一个对象键，天然去重、不用重传；内容一变就换新键，旧键没人引用后可以回收。

**约束与影响**：分片不存在“原地修改”，每次变更都产生新对象。

### D7 CURRENT 条件写入

**结论**：优先走 S3 条件写入：`PutIfMatch`（`If-Match: <etag>` / `If-None-Match: *`），ETag=MD5(content)（S3 简单上传语义）。后端不支持时回退“乐观写 + 读回校验 + 冲突重试”，接口不变，差异藏在实现层。

**为什么**：`doc/7` 指定条件写入，但具体方式取决于 S3 实现。接口抽象把实现差异挡在外面，Q3 会实测确认。

**约束与影响**：`objectstore` 接口要同时容得下主路径和回退路径。

### D8 CURRENT 内容含 manifest 指纹

**结论**：CURRENT 内容格式是 `"<snapID> <fp8>"`，空格分隔，没有换行。

**为什么**：校验链闭环：CURRENT → manifest → 分片。manifest 损坏能查出来，代价只是多一个字段。

**约束与影响**：写 CURRENT 之前必须先算好 manifest 指纹；格式里不能出现换行。

### D9 引用计数不持久化

**结论**：`Acquire/Release` 维护内存表。GC 判定以“保留快照可达 ∪ 读者 pin”为准，refcount 只做快速过滤和冗余校验。

**为什么**：持久化 refcount 有崩溃一致性难题（掉电就丢）。从快照重算可达集最可靠。`doc/7` 也明确“引用计数是逻辑引用、读操作单独管理”，后者就是 pin。

**约束与影响**：进程重启后 refcount 归零，GC 不能只看它。

### D10 哈希实现

**结论**：xxh3-128 用 `github.com/zeebo/xxh3`（纯 Go 实现），sha256 用标准库，两者都不自己写。

**为什么**：`doc/7` 引用 xxh3 的 10GB/s 指标；zeebo/xxh3 是社区主流的纯 Go 实现。xxh3 不算密码学哈希，碰撞概率按 0 处理；需要强校验时打开 sha256 兜底。

**约束与影响**：新增依赖只有 `zeebo/xxh3` 和 `minio-go` 两个。

### D11 不做逐块 fsync

**结论**：`rename()` 保证可见性，`Put` 不做 fsync。

**为什么**：`doc/7` 明确“数据丢了重新下载就好”。掉电丢块的代价就是重拉一次。

**约束与影响**：接受掉电后丢掉最近写入的块。

### D12 单测全用 mock

**结论**：全部单测都跑在 `objectstore.Mock` 上（内存实现），不依赖真实 S3 对象存储。真实后端的集成测试独立、可选。

**为什么**：单测要确定性、无网络依赖。M1 之后如果需要真实后端验证，再补集成环境。

**约束与影响**：mock 的行为必须贴近 S3 简单上传语义（ETag = md5hex(content)）。

### D13 verify_level 只影响新写块

**结论**：`VerifyXXH3SHA256` 模式下，新写入的块会算 sha256 并存进块头；老块按各自块头的 flags 校验，不做全量重算。

**为什么**：`doc/7` 明确要求“避免全量重算”。

**约束与影响**：切换 verify_level 不会改写已有块。

### D14 GC 保留窗口与触发

**结论**：保留集合 = CURRENT + 最近 2 个已提交快照（`RetainSnapshots`=3）。core 只提供显式 `Sweep` API，不在 `Commit` 里做“提交后惰性触发”；当前由 Agent 侧驱动：淘汰循环每 30 秒调一次 `sweep`，Agent 装配阶段也会显式调用 `collector.Sweep`。定时扫描归 Agent 层。

**为什么**：`doc/7` 只要求“确认无读者后删”。3 代是保守值，可调。库内不做自主定时器，生命周期交给宿主控制。

**约束与影响**：保留窗口外、又没有被保留快照引用的对象才删；CURRENT 指向的对象绝不删。

### D15 Go 版本基线

**结论**：go.mod 声明 `go 1.26.0`（本机工具链是 1.27.1）。

**为什么**：minio-go v7.3.0 的 go.mod 要求 go ≥ 1.25.0；工作区里 core、agent、controller 三个 module 已统一到 1.26.0，避免版本基线分裂。

**约束与影响**：升级 minio-go 前先看它的 go 版本要求。

### D16 模块命名

**结论**：module 名是 `traincache/core`，不设外部托管路径。

**为什么**：这是纯本地项目，避免依赖一个实际不存在的域名。

**约束与影响**：所有 import 路径以 `traincache/core/` 开头。

### D17 Catalog 绑定数据集

**结论**：构造器改成 `NewCatalog(store, dataset string, cfg Config)`，多一个 dataset 参数；`Refresh`/`Lookup` 签名不变。

**为什么**：冻结签名缺 dataset 入口。`Writer`/`Collector` 都通过方法参数传 dataset，`Catalog` 的 `Refresh`/`Lookup` 没有这个参数，所以 `Catalog` 天然绑定单数据集（M4 BLOCKER 裁决）。

**约束与影响**：一个 `Catalog` 实例只服务一个数据集，换数据集要新建实例。

### D18 ShardRef.Key 为完整对象键

**结论**：`Key` 存完整对象键 `dataset/<name>/snapshots/<id>/shard-<fp8>.idx`。未变更分片跨快照复用时，保留它首次创建时的完整键。读侧按 Key 下载，并校验文件名部分。

**为什么**：§5.4 原注释写“文件名部分”，这和 D6“物理复用同一对象键 + 无重传”互相矛盾。如果按新快照前缀拼接，复用的分片对象根本不存在，冷启动会 404，设计不自洽（M4 BLOCKER 裁决）。

**约束与影响**：读侧不能自己拼新前缀，必须用 `Key`。

### D19 objectstore.Store 增 List

**结论**：新增 `List(ctx context.Context, prefix string) ([]string, error)`，返回匹配 prefix 的全部对象键（字典序升序），没有匹配返回空切片。

**为什么**：Sweep 要删保留窗口外的快照对象，必须枚举对象存储——“最近 2 个已提交快照”的发现依赖全量清单。§5.1 的六方法接口没有枚举能力，这是 Phase 0 的设计遗漏（和 D17 同性质），M6 开工前裁决。

**约束与影响**：`Store` 接口从 6 个方法变成 7 个。

### D20 cas.Store 增 List

**结论**：新增 `List() ([]Fingerprint, error)`，枚举 `blocks/` 下的全部块指纹，忽略临时文件和非法文件名。

**为什么**：Sweep 在块侧要判“不在活块集合”，需要全量指纹枚举。`blocks/<fp[0:2]>/<fp>.blk` 是 cas 的封装细节，index 不该窥探（M6 开工前裁决）。

**约束与影响**：目录布局变化不往外泄露。

### D21 SnapshotPrefix 空 snapID 语义

**结论**：`SnapshotPrefix` 的输入契约是有效 snapID，空串输入未定义（当前实现会产生尾随双斜杠）。Sweep 枚举快照根时用 gc.go 的私有函数 `snapshotsPrefix`（在 `SnapshotPrefix` 基础上折并尾部分隔符），不导出，也不改 format.go。

**为什么**：M6 子代理发现 `SnapshotPrefix(dataset,"")` 恒得 `dataset/<name>/snapshots//`，导致枚举为空。折并方案保留单一布局知识来源（M6 DECISIONS 1 裁决采纳）。

**约束与影响**：调用方不能传空 snapID；空串行为不在契约内。

### D22 ShardRef 增 MinPath/MaxPath

**结论**：新增 `MinPath/MaxPath string`（json `min_path`/`max_path`），值等于分片内首末条 `Entry` 的 Path，条目按 `(path,chunk)` 字典序排。

**为什么**：`doc/7` 新增「索引分片按前缀目录加载」。读侧按前缀过滤时必须知道每个分片的路径范围，否则只能全量下载再判断，需求就落空了。manifest 本身只是 `ShardRef` 列表，体积小，加范围字段成本极低（2026-10-12 裁决）。

**约束与影响**：构建分片时必须填这两个字段；缺了读侧就没法做范围判定。

### D23 Catalog 增 LoadPrefixes

**结论**：`LoadPrefixes(ctx context.Context, prefixes []string) error`。流程：读 CURRENT → 下载 manifest → 只下载、校验、加载相关分片（按 D22 的范围交叠判定）→ 局部映射原子切换。空 prefixes 表示不加载任何分片（映射为空），含空串元素表示全量。失败不动旧映射。与 `Refresh`/`Start` 互斥使用模式（宿主二选一，前缀集变化时宿主再调一次）。

**为什么**：`doc/7` 建议 `Load(prefixes)` 或 `LoadShards(refs)`。裁决选 LoadPrefixes——语义明确，按 YAGNI 不提供 LoadShards。加载哪些前缀属于 Agent 服务的职责（`doc/7` 明示“Agent 服务决定加载哪些前缀”）（2026-10-12 裁决）。

**约束与影响**：`LoadPrefixes` 不能和 `Refresh`/`Start` 混着用。

### D24 cas 增 Quarantine/ListQuarantined/RemoveQuarantined

**结论**：签名与 7.1 design §5.7 逐字一致，落进 `6.1 design.md` §5.2。`Quarantine` 无条件移走坏块：不检查 refs/pins（坏块隔离是正确性动作，引用计数只是索引层的逻辑关系；修好以后同指纹块回到原位，引用不变），但持 `s.mu`，与 `Remove`/其他 `Quarantine` 串行（和 `Remove` 同一模式）。`ListQuarantined` 与 `List` 同规则（字节序升序、空切片、忽略临时/非法名）。`RemoveQuarantined` 目标不存在返回 nil。新导出符号只有这三个。

**为什么**：7.0 要求“将块标记为坏块”。坏块留在 `blocks/` 会让后续读持续失败，还会进 `List` 枚举、进 Sweep 判定。引用计数不因隔离清零——修好以后块回原位，索引引用自然恢复。

**约束与影响**：`Quarantine` 不看引用计数，这一点和 `Remove` 不同。

### D25 quarantine/ 目录布局

**结论**：`Store` 增私有字段 `rootDir`，保存用户传入的根路径。`New` 时在根下 `MkdirAll` 一个 `quarantine/`。布局沿用 `<quarantineDir>/<fp[0:2]hex>/<fp hex>.blk`，和 `blocks/` 一样分两级。移动用 `os.Rename`——两者同在根下、同一文件系统，操作原子，也不会报 EXDEV。

**为什么**：§5.7 冻结了“与 `blocks/` 并列”。并列布局让 `List()` 和 `index.Sweep` 天然不枚举坏块，gc.go 零改动；两级分片沿用现有布局知识。

**约束与影响**：`quarantine/` 必须和 `blocks/` 在同一文件系统下。

### D26 Quarantine/RemoveQuarantined 幂等语义

**结论**：`Quarantine` 发现源块不在 `blocks/` 时返回 nil（目标状态已经达到，不区分“已在 quarantine”和“从未存在”）；目标位置已有文件时，rename 原子覆盖。`RemoveQuarantined` 目标不存在返回 nil（和 `objectstore.Delete`“不存在不算错误”的风格一致）。只有真实 I/O 错误才报错。

**为什么**：修复队列和重扫描并发时，同一个块可能被多次隔离或清理。幂等让调用方不用判错重试，也和 core 已有的“不存在不算错误”先例一致（`objectstore.Delete`、`Release`/`Unpin` 空操作）。

**约束与影响**：调用方拿到 nil，只代表目标状态已经满足，不代表这次真的移动过文件。

### D27 Put 对已存在同指纹块行为

**结论**：`cas.Put` 遇到已存在的同指纹块时，先写临时文件再 rename 原子覆盖。指纹等于内容，覆盖的内容必然相同，等价于幂等跳过，不报错，实现不用改。Agent 修复路径：坏块已经被 `Quarantine` 移出 `blocks/`，重下后 `Put` 直接落在空位。

**为什么**：这条是 7.3 Q3（2026-10-14 查 core 结案）在 core 文档侧的登记，让 6.x 的决策链自洽。

**约束与影响**：`Put` 不需要加“存在就跳过”的分支。

### D28 cas 增 Evict（本地副本淘汰）

**结论**：`Evict(fp Fingerprint) error` 只删块的本地副本。refcount 不拦（引用是快照级逻辑簿记，和副本在不在本地无关），pin>0 返回 `ErrInUse`；块已不存在返回 `ErrNotFound`（幂等，与 `Remove`/`Sweep` 并发安全）。簿记契约：`Evict` 不动 refs；副本被淘汰后经 fetch 重下时，不重复 `Acquire`。新导出符号只有这一个方法。

**为什么**：Agent 层磁盘淘汰要删的是仍被快照引用的活块的本地副本（7.0「活数据淘汰」），现有 `Remove` 见 refcount>0 就报 `ErrInUse`，根本删不掉。Sweep 的引用回收语义（6.0 §7）不动，淘汰单开入口。放进 core 是职责边界——块文件布局和 pin 互斥锁都在 cas 内部（同 D24/D20 先例）（2026-10-14 裁决）。

**约束与影响**：`Evict` 成功后 refcount 不变，后续 `Release` 仍要能正常走。

### D29 index.Catalog 增 List

**结论**：`List(ctx context.Context, prefix string) ([]Entry, error)`。复用 D22 的分片相关性判定，只下载相关分片；返回 path 以 prefix 开头的条目（prefix 空表示全量），按 `(path, chunk)` 字典序排序；无 CURRENT 返回 `ErrNoCurrent`；失败不动旧映射。新导出符号只有这一方法。

**为什么**：agent 的 ListSnapshot RPC（7.1 §5.1）要按 prefix 枚举 `(path, chunk, size)`，`Catalog` 没有枚举导出面（2026-10-15 M3 前置主对话裁决）。

**约束与影响**：`List` 是纯读查询，不切换当前映射。

### D30 index.Catalog 增 ShardsLoaded

**结论**：`ShardsLoaded() int` 返回当前生效索引快照的 Manifest 分片数（`Shards` 长度）。还没有快照（未成功 `Start`/`Refresh`/`LoadPrefixes`）时返回 0。纯读，不长持锁。新导出符号只有这一方法。

**为什么**：agent 指标 `traincache_index_shards_loaded` 需要“已加载分片数”，`Catalog` 没有导出面，指标恒为 0（M6 遗留）。M7 总闸前裁决（2026-10-15）。

**约束与影响**：返回值只反映当前生效的快照。

### D31 多 tar 发布器（publish）职责与契约

**结论**：新增 `core/publish`：`Source{Path, ReaderAt, Size}`、`Options{Dataset, ChunkSize, Concurrency}`、`Result{SnapID, Entries, Bytes, UniqueBlocks}`、`Publish(ctx, store, cs, w, sources, opt)`。CLI `core/cmd/trainpublish` 接收多个 tar，每个 tar 对应一个 `Entry.Path`，块默认 64 MiB，全部条目合并后只调用一次 `Writer.Commit`。

具体约定有五条：

1. 发布编排归发布器，`Writer` 只负责索引提交；
2. 多 tar 合并为**单快照**，任一失败不 `Commit`；
3. `Entry.Node` 在 v1 reserved、固定留空，发布器不填。这一条覆盖 Q1 的 v1“写入方填写”结论；
4. 块键单点 `objectstore.BlockKey(dataset, path, chunk)` = `<dataset>/blocks/<path>#<chunk>`，用它替换 `agent/prefetch/pending.go` 与 `agent/rescan/repair.go` 的未导出副本；
5. 任一块上传失败不 `Commit`；`Commit` 失败只清理本次分片/manifest，远端块不自动删除。`Path` 不可变（tar 名带版本/哈希），`Commit` 只校验本地 CAS，所以必须先上传块再 `Commit`。

**为什么**：写侧编排跨 objectstore/cas/index 三者，放进任何一个既有包都会造成职责倒挂或依赖环。单快照保证读侧看不到逐 tar 发布的中间态。`Node` 的跨节点块放置语义还没定义，先保留字段，避免把错误语义固化。块键在 core 和 agent 两处重复实现容易漂移。远端孤儿块删除要先有跨快照可达性/复用判定，发布器不做破坏性清理。

**约束与影响**：`Entry.Node` 恒空；`Path` 不可变；块上传必须早于 `Commit`。

### D32 日志脱敏归属 core

**结论**：新增 `core/logging`，冻结 `Redact(s string) string` 与 `RedactURL(raw string) string` 两个函数（`6.1 design.md` §5.6）。只用标准库，不依赖 core 其他包，core 其他包也不依赖它。controller 和 agent 各自在日志落盘前调用，不各写一份。

**为什么**：`traincache/controller` 与 `traincache/agent` 是两个独立 module、互不引用，core 是共同依赖。两端各写一份会产生语义漂移和重复维护。代价是 core 多一个无状态工具包，两端的调用点还要后续接入（本轮不改调用点）。

**约束与影响**：包里只有这两个导出函数。

### D33 删除语义：CommitChanges 过滤式删除

**结论**：`Writer` 新增 `CommitChanges(ctx, dataset, puts []Entry, dels []Delete) (snapID string, err error)`；`Delete{Path, Chunk}`，`Chunk == -1` 表示该 path 全部块；`--prefix` 批量删除由 CLI 读旧快照展开成 path 列表后一次提交。合并规则 `new = filter(old, dels) ∪ puts`，冲突取 puts；`Commit(ds, entries)` 变为 `CommitChanges(ds, entries, nil)` 的包装，行为逐字不变。契约见 `6.1 design.md` §5.4 / §11.4（2026-10-22 裁决）。

**为什么**：`commitOnce` 每次提交都读全量旧条目、重建全部索引分片（未变更分片按指纹复用旧键），所以"删除"在这个模型里天然可表达为"这次没带上它"——不需要 tombstone、不需要原地修改不可变对象。前提判断：提交频率低频、批量（数据集级管理操作），全量重建的写放大可接受。

**约束与影响**：删除只影响索引快照；远端孤儿块仍走 Collector 回收规则，本地副本残留 v1 不主动清（design §11.5 显式不做）。高频交互式删除会踩写放大边界，届时另立决策（design §11.6）。

### D34 CLI 命名统一为 traincache 前缀

**结论**：本仓库可执行文件命名统一 `traincache` 前缀。新增数据集管理 CLI 命名 `traincacheds`（`core/cmd/traincacheds`）；`trainpublish` 改名 `traincachepublish`，Makefile 同时安装旧名 `trainpublish` 作兼容别名，过渡一个版本；agent 侧 `traincache`（RPC 客户端）不动。明确**不用 `tc`** 作为命令名（2026-10-22 裁决）。

**为什么**：`tc` 是 Linux iproute2 的流量控制工具（`/usr/sbin/tc`），本仓库 bench 装置大量用真 `tc` 做 tbf/netem 限速（见 doc/3），脚本里 `tc` 二义性必然出事。历史命名 `trainpublish`/`traincache` 已成习惯，统一前缀让 `traincache*` Tab 补全即可列出全家。

**约束与影响**：改名涉及 Makefile 与 bench/文档中的安装引用，`6.1 design.md` §10.3 冻结的 `trainpublish` usage 文本在别名移除时同步更新；过渡期内两个名字指向同一二进制。

## 3. 决策变更流程

1. 实现子代理发现约定不可行或不合理 → 回传 `BLOCKED`（理由、证据、建议）→ 先不动代码；
2. 主对话裁决。采纳就更新 `6.1 design.md` 和本文档（旧编号保留，新决策顺延编号），然后重新派活；否决就说明理由，子代理按原约定继续；
3. Q* 结案时，在 §2 表格里登记结论与日期，必要时升级为 D* 或修改 `6.1 design.md`。

一句话：先停手、再裁决、最后同步文档。
