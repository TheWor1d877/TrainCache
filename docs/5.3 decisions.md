本文记录核心库的全部裁决：**D** 是已定案的决策，**Q** 是已结案的未决问题。接口与格式在 `5.1 design.md`，里程碑在 `5.2 plan.md`。D 编号被 core/agent/controller 的代码注释引用，保留原编号，不合并、不重排。

### D1 库形态与位置

无服务形态的 Go 库，独立 module `traincache/core`，代码在新目录 `core/`。6.0 写明"没有任何服务形态，现在就是一组代码加单元测试"；独立 module 与 bench 装置解耦。库不跑进程，引用方按 module 路径导入。

### D2 分层与依赖

`objectstore` / `cas` / `fetch` / `index` 四个业务包 + `internal/digest`。依赖单向无环：`index→cas、objectstore`；`fetch→objectstore、cas`；`cas` 不依赖 `objectstore`。字节流由 `fetch` 喂给 `cas.Put`，本地与远端存储解耦，`cas` 可独立测试。反向 import 不允许。

### D3 块头格式

统一 128B v1，不做 64B 变体。字段：magic `"TCBK"`、version=1、flags bit0 表示 sha256 有效、block_size uint32 LE、xxh3_128、sha256（可选）、reserved 对齐。6.0 的 64B 是过渡表述，直接上 128B 免维护两套解析；存储键恒为 xxh3-128，去重不受 sha256 开关影响。v1 解析器只认这一种布局，块头长度固定 128B。

### D4 块切分

`(path, chunkIndex)` 按 `ChunkSize` 固定切分，默认 64 MiB、参数可调。`Entry` 含 `Size`（末块可不足），字节偏移由 `chunk × ChunkSize` 推导、不落盘。6.0 的键带 chunkIndex，本身就是固定切分语义；offset 可推导，将来要变长块再加字段（JSON 向后兼容）。`Entry` 不存 offset，读侧自己算。

### D5 分片格式

分片是 `Entry` 的 JSON 数组，字段名全称；每片最多 `MaxEntriesPerShard` 条（默认 100_000，6.0 硬上限）。构建先按 `(path, chunk)` 字典序排序、再按条数切（range-based）；完整性靠分片内容 xxh3-128 记进 manifest。JSON 可读、可调试，构建与合并逻辑简单；分片在对象存储上体积不敏感（10 万条约 13MB）。单分片超 10 万条即违反契约。

### D6 分片对象键含内容指纹

分片键 `shard-<fp8>.idx`，fp8 取内容 xxh3 前 8 字节 hex。内容没变的分片物理复用同一对象键——天然去重、不用重传；内容一变换新键，旧键无人引用后可回收。分片没有"原地修改"，每次变更产生新对象。

### D7 CURRENT 条件写入

主路径走 S3 条件写入 `PutIfMatch`（`If-Match: <etag>` / `If-None-Match: *`），ETag=MD5(content)（S3 简单上传语义）。后端不支持时回退"乐观写 + 读回校验 + 冲突重试"——接口不变，差异藏在实现层。6.0 指定条件写入但各 S3 实现支持度不一，抽象层把差异挡在外面（Q3 已实测确认，MinIO 支持主路径）。`objectstore` 接口要同时容得下主路径和回退路径。

### D8 CURRENT 内容含 manifest 指纹

CURRENT 内容 `"<snapID> <fp8>"`，空格分隔、无换行。校验链因此闭环：CURRENT → manifest → 分片，manifest 损坏能查出来，代价只有一个字段。写 CURRENT 前必须先算好 manifest 指纹；格式里不能出现换行。

### D9 引用计数不持久化

`Acquire/Release` 维护内存表；GC 判定以"保留快照可达 ∪ 读者 pin"为准，refcount 只做快速过滤和冗余校验。持久化 refcount 有崩溃一致性难题（掉电就丢），从快照重算可达集最可靠；6.0 也明确"引用计数是逻辑引用、读操作单独管理"（后者即 pin）。进程重启后 refcount 归零，GC 不能只看它。

### D10 哈希实现

xxh3-128 用 `github.com/zeebo/xxh3`（纯 Go 社区主流实现），sha256 用标准库，都不自己写。6.0 引用 xxh3 约 10GB/s 每核的指标；xxh3 不是密码学哈希，碰撞按 0 处理，需要强校验时打开 sha256 兜底。新增依赖只有 zeebo/xxh3 和 minio-go 两个。

### D11 不做逐块 fsync

`rename()` 保证可见性，`Put` 不做 fsync。6.0 明确"数据丢了重新下载就好"，掉电丢块的代价就是重拉。接受掉电后丢掉最近写入的块。

### D12 单测全用 mock

全部单测跑在 `objectstore.Mock`（内存实现）上，不依赖真实 S3；真实后端的集成测试独立、可选。单测要确定性、无网络依赖。mock 行为必须贴近 S3 简单上传语义（ETag = md5hex(content)）。

### D13 verify_level 只影响新写块

`VerifyXXH3SHA256` 模式下新写块算 sha256 存进块头；老块按各自块头 flags 校验，不做全量重算。6.0 明确要求避免全量重算。切换 verify_level 不改写已有块。

### D14 GC 保留窗口与触发

保留集合 = CURRENT + 最近 2 个已提交快照（`RetainSnapshots`=3）。core 只提供显式 `Sweep` API，不在 `Commit` 里做"提交后惰性触发"；当前由 Agent 侧驱动：淘汰循环每 30 秒调一次 `sweep`，Agent 装配阶段也显式调用 `collector.Sweep`。定时扫描归 Agent 层。6.0 只要求"确认无读者后删"；3 代是保守值、可调；库内不设自主定时器，生命周期交给宿主。窗口外且不被保留快照引用的对象才删；CURRENT 指向的绝不删。

### D15 Go 版本基线

go.mod 声明 `go 1.26.0`（本机工具链 1.27.1）。minio-go v7.3.0 要求 go ≥ 1.25.0；core、agent、controller 三个 module 统一到 1.26.0，避免基线分裂。升级 minio-go 前先看它的 go 版本要求。

### D16 模块命名

module 名 `traincache/core`，不设外部托管路径。纯本地项目，避免依赖一个不存在的域名。所有 import 路径以 `traincache/core/` 开头。

### D17 Catalog 绑定数据集

构造器为 `NewCatalog(store, dataset string, cfg Config)`；`Refresh`/`Lookup` 签名不变。冻结签名缺 dataset 入口：`Writer`/`Collector` 用方法参数传 dataset，而 `Catalog` 的 `Refresh`/`Lookup` 没有这个参数，所以 `Catalog` 绑定单数据集。一个 `Catalog` 实例只服务一个数据集，换数据集要新建实例。

### D18 ShardRef.Key 为完整对象键

`Key` 存完整对象键 `dataset/<name>/snapshots/<id>/shard-<fp8>.idx`；未变更分片跨快照复用时保留首次创建时的完整键。读侧按 Key 下载、校验文件名部分。"只存文件名部分"与 D6"物理复用同一对象键、无重传"矛盾：按新快照前缀拼接，复用分片对象根本不存在，冷启动 404。读侧不能自己拼新前缀，必须用 `Key`。

### D19 objectstore.Store 增 List

新增 `List(ctx context.Context, prefix string) ([]string, error)`：返回匹配 prefix 的全部对象键（字典序升序），无匹配返回空切片。Sweep 要删窗口外快照对象，必须枚举对象存储——"最近 2 个已提交快照"的发现依赖全量清单；原五方法接口没有枚举能力。`Store` 接口从 5 个方法变成 6 个。

### D20 cas.Store 增 List

新增 `List() ([]Fingerprint, error)`：枚举 `blocks/` 下全部块指纹，忽略临时文件与非法文件名。Sweep 在块侧要判"不在活块集合"，需要全量指纹枚举；`blocks/<fp[0:2]>/<fp>.blk` 是 cas 的封装细节，index 不该窥探。目录布局变化不外泄。

### D21 SnapshotPrefix 空 snapID 语义

`SnapshotPrefix` 的输入契约是有效 snapID，空串输入未定义（当前实现会产生尾随双斜杠 `dataset/<name>/snapshots//`，枚举为空）。Sweep 枚举快照根时用 gc.go 的私有函数 `snapshotsPrefix`（在 `SnapshotPrefix` 基础上折并尾部分隔符），不导出、不改 format.go——保留单一布局知识来源。调用方不能传空 snapID。

### D22 ShardRef 增 MinPath/MaxPath

新增 `MinPath/MaxPath string`（json `min_path`/`max_path`），值 = 分片内首末条 `Entry` 的 Path，条目按 `(path,chunk)` 字典序排。6.0 新增「按前缀加载」：读侧按前缀过滤必须知道每片的路径范围，否则只能全量下载再判断，需求落空；manifest 只是 ShardRef 列表、体积小，加范围字段成本极低。构建分片时必须填这两字段。

### D23 Catalog 增 LoadPrefixes

`LoadPrefixes(ctx context.Context, prefixes []string) error`：读 CURRENT → 下载 manifest → 只下载、校验、加载相关分片（按 D22 范围交叠判定）→ 局部映射原子切换。空 prefixes = 不加载任何分片（映射为空）；含空串元素 = 全量；失败不动旧映射；与 `Refresh`/`Start` 互斥使用（宿主二选一，前缀集变化时宿主再调一次）。6.0 建议 `Load(prefixes)` 或 `LoadShards(refs)`，裁决选 LoadPrefixes——语义明确，按 YAGNI 不提供 LoadShards。加载哪些前缀归 Agent 服务职责。

### D24 cas 增 Quarantine/ListQuarantined/RemoveQuarantined

签名与 6.1 design §5.7 逐字一致，落进 design §5.2。`Quarantine` 无条件移走坏块：不检查 refs/pins（隔离是正确性动作，引用计数是索引层逻辑关系；修好后同指纹块回原位、引用不变），但持 `s.mu`，与 `Remove`/其他 `Quarantine` 串行。`ListQuarantined` 与 `List` 同规则（字节序升序、空切片、忽略临时/非法名）。`RemoveQuarantined` 目标不存在返回 nil。新导出符号只有这三个。7.0 要求标记坏块；坏块留在 `blocks/` 会让后续读持续失败，还会进 `List` 枚举、进 Sweep 判定。`Quarantine` 不看引用计数，这一点与 `Remove` 不同。

### D25 quarantine/ 目录布局

`Store` 增私有字段 `rootDir` 保存用户传入根路径；`New` 时根下 `MkdirAll` `quarantine/`；布局沿用 `<quarantineDir>/<fp[0:2]hex>/<fp hex>.blk`，与 `blocks/` 一样分两级。移动用 `os.Rename`——同在根下、同一文件系统，原子且不报 EXDEV。并列布局让 `List()` 和 `index.Sweep` 天然不枚举坏块，gc.go 零改动。`quarantine/` 必须与 `blocks/` 在同一文件系统下。

### D26 Quarantine/RemoveQuarantined 幂等语义

`Quarantine` 源块不在 `blocks/` 时返回 nil（目标状态已达成，不区分"已在 quarantine"和"从未存在"）；目标已有文件时 rename 原子覆盖。`RemoveQuarantined` 目标不存在返回 nil（同 `objectstore.Delete` 风格）。只有真实 I/O 错误报错。修复队列和重扫描并发时同一块可能被多次隔离或清理，幂等让调用方不用判错重试，与 core 已有"不存在不算错误"先例一致（`objectstore.Delete`、`Release`/`Unpin` 空操作）。返回 nil 只代表目标状态满足，不代表这次真的移动过文件。

### D27 Put 对已存在同指纹块的行为

`cas.Put` 遇到已存在的同指纹块：先写临时文件再 rename 原子覆盖。指纹等于内容，覆盖的内容必然相同，等价幂等跳过，不报错、实现不用改。这是 6.3 Q3 在 core 文档侧的登记，让 6.x 决策链自洽。`Put` 不需要加"存在就跳过"分支。Agent 修复路径：坏块已被 `Quarantine` 移出 `blocks/`，重下后 `Put` 直接落在空位。

### D28 cas 增 Evict（本地副本淘汰）

`Evict(fp Fingerprint) error` 只删块的本地副本：refcount 不拦（引用是快照级逻辑簿记，与副本在不在本地无关）；pin>0 返回 `ErrInUse`；块已不存在返回 `ErrNotFound`（幂等，与 `Remove`/`Sweep` 并发安全）。簿记契约：`Evict` 不动 refs；副本被淘汰后经 fetch 重下时不重复 `Acquire`。新导出符号只有这一个方法。Agent 磁盘淘汰删的是仍被快照引用的活块副本（7.0「活数据淘汰」），`Remove` 见 refcount>0 就 `ErrInUse`，删不掉；Sweep 的引用回收语义（5.0 §CAS存储层）不动，淘汰单开入口。放进 core 是职责边界——块文件布局和 pin 互斥锁都在 cas 内部（同 D24/D20 先例）。`Evict` 成功后 refcount 不变，后续 `Release` 照常。

### D29 index.Catalog 增 List

`List(ctx context.Context, prefix string) ([]Entry, error)`：复用 D22 分片相关性判定，只下载相关分片；返回 path 以 prefix 开头的条目（prefix 空 = 全量），按 `(path, chunk)` 字典序排序；无 CURRENT 返回 `ErrNoCurrent`；失败不动旧映射。新导出符号只有这一方法。agent 的 ListSnapshot RPC（6.1 §5.1）要按 prefix 枚举 `(path, chunk, size)`，`Catalog` 缺枚举导出面。`List` 是纯读查询，不切换当前映射。

### D30 index.Catalog 增 ShardsLoaded

`ShardsLoaded() int` 返回当前生效索引快照的 Manifest 分片数（`Shards` 长度）；还没有快照（未成功 `Start`/`Refresh`/`LoadPrefixes`）时返回 0。纯读，不长持锁。新导出符号只有这一方法。agent 指标 `traincache_index_shards_loaded` 需要"已加载分片数"，`Catalog` 没有导出面时指标恒为 0。返回值只反映当前生效快照。

### D31 多 tar 发布器（publish）职责与契约

新增 `core/publish`：`Source{Path, ReaderAt, Size}`、`Options{Dataset, ChunkSize, Concurrency}`、`Result{SnapID, Entries, Bytes, UniqueBlocks}`、`Publish(ctx, store, cs, w, sources, opt)`。CLI `core/cmd/trainpublish` 接收多个 tar，每个 tar 对应一个 `Entry.Path`，块默认 64 MiB，全部条目合并后只调一次 `Writer.Commit`。五条具体约定：

1. 发布编排归发布器，`Writer` 只负责索引提交；
2. 多 tar 合并为**单快照**，任一失败不 `Commit`；
3. `Entry.Node` 在 v1 reserved、固定留空，发布器不填（Q1 的现行结论以本条为准）；
4. 块键单点 `objectstore.BlockKey(dataset, path, chunk)` = `<dataset>/blocks/<path>#<chunk>`，替换 `agent/prefetch/pending.go` 与 `agent/rescan/repair.go` 的未导出副本；
5. 任一块上传失败不 `Commit`；`Commit` 失败只清理本次分片/manifest，远端块不自动删除。`Path` 不可变（tar 名带版本/哈希）；`Commit` 只校验本地 CAS，所以先传块再 `Commit`。

理由：写侧编排跨 objectstore/cas/index 三者，放进任何既有包都会职责倒挂或成依赖环；单快照让读侧看不到逐 tar 的中间态；Node 的跨节点放置语义未定义，留空避免固化错误语义；块键两处重复容易漂移；远端孤儿块删除要先有跨快照可达性/复用判定，发布器不做破坏性清理。约束：`Entry.Node` 恒空；`Path` 不可变；块上传必须早于 `Commit`。

### D32 日志脱敏归属 core

新增 `core/logging`，提供 `Redact(s string) string`、`RedactURL(raw string) string` 与 `NewRedactingHandler(next slog.Handler) slog.Handler`（design §5.6）。只用标准库；core 其他包不依赖它，它也不依赖 core 其他包。`traincache/controller` 与 `traincache/agent` 是两个独立 module、互不引用，core 是唯一共同依赖；各写一份会产生语义漂移和重复维护。两端在 `logging.New` 里把 JSON handler 包一层 `NewRedactingHandler`，消息、字符串与 error 属性写出前统一脱敏，业务调用点不逐处手写。代价：core 多一个无状态工具包，每条日志多一次字符串扫描。

### D33 删除语义：CommitChanges 过滤式删除

`Writer` 新增 `CommitChanges(ctx, dataset, puts []Entry, dels []Delete) (snapID string, err error)`；`Delete{Path, Chunk}`，`Chunk == -1` 表示该 path 全部块；`--prefix` 批量删除由 CLI 读旧快照展开成 path 列表后一次提交。合并规则 `new = filter(old, dels) ∪ puts`，冲突取 puts；`Commit(ds, entries)` 变为 `CommitChanges(ds, entries, nil)` 的包装，行为逐字不变。契约在 design §5.4 / §11.4。

理由：`commitOnce` 每次提交读全量旧条目、重建全部分片（未变更分片按指纹复用旧键），"删除"在这个模型里天然 = "这次没带上它"——不需要 tombstone、不改不可变对象。前提：提交是低频、批量的数据集级管理操作，全量重建的写放大可接受。约束：删除只影响索引快照；远端孤儿块走 Collector 回收规则；本地副本残留 v1 不主动清（design §11.5）。高频交互式删除会踩写放大边界，届时另立决策（design §11.6）。

### D34 命令名按职责取

用户直接执行的命令保留职责名：`traincache`（RPC 客户端，探针与运维共用）、`traincacheds`（数据服务）、`trainpublish`（快照发布器）。不统一加产品前缀，也不为改名保留别名。唯一硬约束是禁用 `tc`：`tc` 是 Linux iproute2 的流量控制工具（`/usr/sbin/tc`），bench 装置大量用真 `tc` 做 tbf/netem 限速，脚本里会二义。容器内的服务进程名（`controller-manager`、`webhook`、`kube-scheduler`、`traincache-agentd`）不是用户命令，不在此列。

## 3. 决策变更流程

1. 实现子代理发现约定不可行或不合理 → 回传 `BLOCKED`（理由、证据、建议），不动代码；
2. 主对话裁决：采纳则更新 `5.1 design.md` 和本文档（旧编号保留，新决策顺延编号），重新派活；否决则说明理由，子代理按原约定继续；
3. Q 结案时在 §2 表格登记结论，必要时升级为 D 或修改 `5.1 design.md`。
