# 核心能力验收与测试 · 决策

本文记录验收与实验的口径裁决：**D** 是已定案的决策。需求见 `9.0 核心能力验收与测试.md`，实验协议与 COND 契约见 `9.2 实验协议.md`，装置细节见 `4 bench装置说明.md`。D 编号被 bench 代码与文档引用，保留原编号，不合并、不重排。

## 1. 术语

| 术语 | 含义 |
|---|---|
| COND | 一个实验点的全部条件（数据规模、缓存容量、带宽档、策略名、种子）写成一个 JSON。跑分脚本只读它。一个 COND = 一个可复现的实验点 |
| 预热 | 训练 Pod 调度之前，Controller 驱动 WarmupTask 把数据拉进节点缓存。此时 Pod 还没落地，不知道会落在哪个节点，所以是盲热。Fluid DataLoad、`juicefs warmup` 是同一语义 |
| 预取 | Pod 落地之后，Agent 跟着训练的消费顺序持续往后拉数据。epoch 或 shuffle 切换时按新顺序重预取 |
| makespan | 任务从提交到跑完的总时长。启动 makespan 指提交到第一个 step 开始 |
| stall | DataLoader 在等数据的时段，训练算力空转。判据是等待时间占该步时间的比例 |
| 启动窗口 K | 决定训练能不能立刻跑起来的前 K 个块 |
| fanout | 预热时把同一份数据同时复制到几个节点。复制 3 份，字节成本就是 3 倍 |
| lookahead | Agent 持续预取的提前量。默认 16 块；淘汰实验扫 8/16/32 |
| 容量档位 S/M/L | 缓存固定 1 GiB，数据集取 2/8/32 GiB，数据/缓存比 1:2、1:8、1:32 |
| 块 | 缓存与预取的最小单位。实验取 8 MiB，生产默认 64 MiB |
| 淘汰策略 | 缓存满了先踢哪些块。三档：`heat`（本项目现有热度）、`lru`、`lfu` |
| A/B/C/D 轨 | 四类合成负载。A 小文件元数据，B 8 GiB webdataset tar 分片，C 两 Job 倾斜（一个循环读 10% 热子集，一个顺序扫全量），D 单 Job 连续 epoch |
| 预注册 | 正式跑分前，把三张图、三档容量比、两张 Pareto 的假设、自变量取值、预期区间、阴性结论接受条件写成文件并冻结。此后只允许追加偏离说明 |
| 组态 | 跑分里的独立运行形态。五个受试者展开为七个组态：direct、juicefs-cold、juicefs-warm、fluid-cold、fluid-warm、traincache-cold、traincache-warm。五组是按受试者归并后的清单名，凡计数一律用七组态 |

预热和预取是两件事，文档中严格区分：一个发生在 Pod 落地前、由 Controller 驱动；一个发生在落地后、由 Agent 自治。

### 2.1 测量口径

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| D2 | makespan 起止 | 起点 = runner 创建 train-job 前取的时刻，注入 `TRAINCACHE_JOB_CREATED_AT`；终点分启动（首步）与全程（末步）。五组由训练脚本自报，`metadata.creationTimestamp` 只作交叉核对 | 五组同一把尺；避免 API server 落盘延迟混进启动时间 |
| D3 | stall 聚合 | `stall = wait_s / step_s`，报 mean 与 p90，中位数只判形态 | 实测中位数对带宽档不敏感：prefetch 吸收了差异（12.4→32.8 MB/s 时中位数 8.53%→8.38%） |
| D4 | 命中率分阶段 | 启动窗口 = 首步前；稳态 = 首步到第一次切换；切换期 = 切换事件到新窗口就绪 | 与 Agent 现有 `phase` 标签对齐 |
| D5 | 字节成本 | 三笔全记，fanout 重复字节进分母 | 「预热便宜」不能靠隐藏成本成立 |
| D25 | 命中率口径 | TrainCache 组主口径用训练侧 open-time 字节账：块打开时不在本地即 miss，`hit_rate = 1 − demand_miss_bytes / 读字节`；`traincache_fetch_bytes_total` 的 run 窗口增量另折 `source_saving_ratio = 1 − fetch/读字节`，两者分列不混用。JuiceFS/Fluid 出不了块级命中，按 warm≈全命中、cold≈全回源 + 回源字节近似，表内显式标注 | 不为对手编造指标，近似必须可见；自家数字必须能自证 |
| D8 | 现有策略的地位 | 现有热度策略包装成 `heat` 档，作三档同台的基线，行为不变 | 与「当前实现」同台，不是与想象中的实现同台 |
| D40 | 切换回落判据 | 基线 = 切换前 20 步 stall 均值；阈值 = `max(1.1×基线, 基线+5pp)`；切换后 10 步滚动均值首次 ≤ 阈值且之后连续 10 步保持，记为回落点；到 epoch 末未满足记右删失并单独报删失率；缺 20 步基线的事件标 `insufficient_baseline`，不进图三 | 判据先冻结，图三才有可比性 |
| D44 | 全程收益的构成 | 全程 makespan 含启动（提交 → 最后一步）；Pod 落地后的阶段另列，用来拆分启动收益与全程收益 | 两个收益不混报 |

### 2.2 采样与统计

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| D12 | 预注册时点 | 第一次正式跑分前冻结，此后只允许追加偏离说明 | 禁止看到结果再调参 |
| D13 | 统计口径 | 平均数 + bootstrap 95% CI（10000 次重采样） | 10.0 硬纪律的实现方式 |
| D18 | 采样次数 | 两张 Pareto 每点 7 次；三张曲面与淘汰矩阵每点 3 次，L 档探点 1 次 | Pareto 要看效应量、需要更紧的 CI；曲面只判符号，3 次足够 |
| D19 | 容量档位与参跑组 | S 档七组态，M 档 direct/fluid-cold/traincache-cold，L 档 traincache-cold/fluid-cold ×1 探点。五组对照的次数以本条与 D32 为准 | 真实数据/缓存比是数十倍，单点结论无法外推；L 档机时与磁盘不允许全量 |
| D32 | 机时结构 | ① 组内 rep 之间只做 cold_reset 清缓存，不 down/up 组件；warm 组每个 rep 都重新预热。② 次数按带宽分区：S @100 ×3 + @1000 ×3，各格统一 3 次。③ 不设 M @100 的 1-rep 链路受限参照，该形状由 S @100 提供。④ L 档回 1 次 @1000。⑤ 不做并行双轨 | rep 复用省约 2 分钟/次；正交信息≈0 的格子不花机时；tc 是全组共享出口，并行 = 均分带宽 = 整轮作废 |
| D30 | 参跑组 fluid 化 | M/L 档的 `juicefs-cold` 换成 `fluid-cold`；S 档保留全部七组态。Fluid 触发两次环境性失败时，M/L 该组自动落回 `juicefs-cold` 补跑，产物记 `baseline_substituted` | 欠配校验必须压在最强工业基线上，只比 JuiceFS CE 会被质疑绕过 Fluid；JuiceFS 没有退出实验 |
| D36 | Fluid 在 kind 上的可行性冒烟 | 对照层先做只验可行性的冒烟，通过条件三条：控制面与 Runtime 全 Ready 且缓存目录可写；2 GiB/400 步读完全部 tar 无 OOM 驱逐重启；Fluid 额外占用 ≤ 6 CPU / 6 GiB。两次环境性失败记 `fluid-unavailable-on-kind`，图二图三基线降级为 juicefs-warm，Fluid 在五组表标 `unavailable`，不补跑。manifest 错误修好再试，不计次数 | 先确认对手能站住，再拿对手当尺 |
| D14 | 异常轮处理 | 整轮作废并保留现场，不挑点；作废轮不进汇总 | 避免选择性报告 |
| D11 | 对照组公平性 | 同一轨迹、同一 tc 档、同一份数据；预热时长单列，不计入 makespan | 否则热读组凭空占便宜 |

### 2.3 负载与装置

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| D6 | 缓存欠配的实现 | Agent 淘汰侧设显式容量上限，不用容器内存限制 | 对照组是缓存目录语义，内存限制对不齐 |
| D20 | 实验块大小 | `trainpublish -chunk-size` 取 8 MiB，随产物归档；生产默认 64 MiB 不动 | 1 GiB 缓存按 64 MiB 只有 16 块，预取保护窗口覆盖整个缓存，淘汰排序统计失真；8 MiB 得 128 块，窗口占 1/8 |
| D31 | 带宽是实验自变量 | rate ∈ {100,300,1000} mbit，随 COND 的 `network.rate_mbit` 落盘。BW/r ∈ [1,2] 的两格（S@300、M@1000）只作解读，链路参数与其余格一致：tbf 限速 + netem 固定 `delay 20ms`，不加随机时延。burst 按 0.1 秒传输量推导（1250k/3750k/12500k），禁止跨档复用固定值。跑分第一格先测源站上限 C（实测值见 `docs/9.2 实验协议.md` §9.2），有效带宽取 min(名义 rate, C) | 逐包随机时延会打乱包序、触发 TCP 快速重传，300mbit 档实测吞吐从 35.6 MB/s 跌到 0.6 MB/s 以下，档位差异被装置掩盖；burst 固定会让 1000 mbit 的突发窗口从 128 ms 缩到 13 ms 而没人发现 |
| D21 | 限速与块大小解耦 | 带宽是链路属性，块大小只改请求数与单请求时长，两者不互相折算。tc 在节点网络层对七组透明，不做档位特判；8 MiB 块下窗口 128 MiB 无退化 | 链路与缓存粒度各管一头，混在一起就没法解释跨档结果 |
| D10 | lookahead 注入方式 | 用环境变量 `TRAINCACHE_PREFETCH_LOOKAHEAD` 注入，不进 CRD；对照实验统一取 16 | 扫点不该改 CRD |
| D28 | lookahead 扫点轴 | 淘汰曲面与 Pareto 二的 lookahead 轴取 8/16/32 三档 × 三策略 = 9 点，与 10.0 一致。8 MiB 块下 1 GiB 缓存共 128 块，三档对应窗口 64/128/256 MiB，即缓存的 1/16、1/8、1/4 | 三档能覆盖从保守到激进的欠配压力 |
| D7 | 策略接口落点 | `Policy` 接口放 `agent/evictor`，`core` 只留 `cas.Evict` 原语 | core 不该知道训练语义 |
| D9 | 淘汰策略只留三档 | 不实现 W-TinyLFU；`Policy` 只有 `Rank`，删掉 `Admit` 与准入接线 | 单 Job 顺序读下准入收益不明确，而 window + 两段 SLRU + count-min + doorkeeper 的实现与验证成本高。原 `tinylfu.go` 只是频率排序代理，留着会让三档同台对比失真 |
| D29 | 淘汰相关指标 | 不设策略切换计数、准入拒绝计数、频率减半计数 | 策略只能在启动时选定，运行期没有切换路径，计数恒为 0；另两个是 W-TinyLFU 的配套 |
| D22 | 测量体与调度体合一 | 每组一个 train-job Pod：measure 是主容器，traincache-warm 走 gate，其余（含 traincache-cold）普通调度；不设 sleep 占位 Pod | 贴近真实部署；预热在 group_up 内完成并等待，启动计时从创建训练 Pod 起算，gate 等待不进 makespan（D23） |
| D23 | 预热外置于计时 | 所有组的预热在 group_up 内完成并等待，15 分钟超时整轮作废 | 五组统一「预热不计入 makespan」 |
| D24 | 缓存跨 Pod 持久 | JuiceFS 缓存从 emptyDir 换 hostPath | 预热成果不能随测量 Pod 销毁，否则 warm 口径不成立 |
| D26 | 预热节点覆盖 | traincache-warm 的 WarmupTask fanout 固定 2，scheduler 按就绪度把 Pod 放到已预热节点 | 两个节点足以形成候选差；落点由 scheduler 打分决定，不靠全节点覆盖 |
| D16 | 训练负载形态 | D 轨真实负载验证用真实 PyTorch + webdataset 的 CPU 训练循环；对照五组用标准库复刻同一形态：按 trace 每 epoch 读完整分片后丢弃，每步 matmul 循环跑满 `COMPUTE_MS=200` 墙钟，不依赖训练脚本 | D 轨证明 stall 来自真实训练循环；对照层要五组同形、镜像轻，标准库复刻去掉训练框架这个变量 |
| D15 | 集群规模 | kind 4 worker（共 5 节点），宿主 32 核 / 30 GiB，对照组与主实验同集群 | fanout=2 时 4 个 worker 里 2 个已预热，Pod 仍有未预热候选；资源吃紧再拆集群 |

### 2.4 数据与环境

| # | 决策 | 结论 | 理由 |
|---|---|---|---|
| D33 | curriculum 形态 | 固定 3 个 stage，按 epoch 三等分；分片集合取同一置换的嵌套前缀（全量 ⊃ 2/3 ⊃ 1/3），stage 内不重排。epoch 边界与 stage 边界重合时只记一次切换（`kind=epoch+stage`） | 嵌套前缀让 curriculum 只缩小窗口、不引入新顺序，图三才能把「窗口变窄」和「换序」分开解释 |
| D34 | 缓存 30% 的口径 | 显式上限 `capacity_bytes = floor(dataset.bytes × 0.30)`，淘汰按上限触发；`disk_usage_ratio` 落在 25%~35% 只是验收检查，不是控制量。8 MiB 块下 2 GiB 数据集的 30% ≈ 76 块，排序统计粒度够用。对照实验的 1 GiB 固定缓存与 C 轨的 30% 是两套口径，不混用 | 控制量与观测量分开 |
| D35 | 对照组终点观测 | 五组统一由训练脚本自报首步与末步，容器退出时间只作交叉核对 | 与 D2 同一把尺 |
| D37 | 分析层依赖 | numpy + pandas + matplotlib（Agg），写入 `bench/requirements.txt`；不引入 plotly/scipy/seaborn；精确版本由 `lock.json` 记录 | 依赖越少越好复现 |
| D38 | L 档磁盘预算 | 上限 200 GiB；跑对照跑分前查一次 `df`。真不足时 L 档顺延或砍掉，不影响正式表 | L 档是符号探点 |
| D39 | L 档数据生成 | 生成器加 `--start-shard`/`--count` 追加生成第 32~127 号分片。每片种子只与自身序号有关（`config.SEED × 1000003 + shard`），所以分批追加与一次生成逐字节一致；已存在的分片跳过不重写，产物只追加 | 不覆盖已上传的源数据 |
| D41 | 快照与源数据的关系 | MinIO 里三类对象各司其职：`bench-b/shard-*.tar` 是五组共同的源数据，只此一份，不删不动；旧 `compare-data/`（64 MiB 块）保留供历史产物复现；正式实验一律用新快照 `compare-data-8m`（`-chunk-size 8388608`），DataSet CRD 指向它 | 新旧并存，历史轮次仍可解释 |
| D42 | tar 体积与声明值的偏差 | 分片按「tar ≈ 256 MiB」校准，但 tar 内是不可压缩的 JPEG 样本，实测每份约 252.6 MiB，于是 L 档 128 份实际约 31 GiB，比声明的 32 GiB 小约 3%，容量比实际约 1:31；S/M 档偏差在 1% 量级。三档都用声明值参与缓存容量计算 | 偏差方向一致、不影响组间可比性，出表时注明即可 |
