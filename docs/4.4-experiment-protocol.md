## 1. 共同口径

七组态：`direct`、`juicefs-cold`/`juicefs-warm`、`fluid-cold`/`fluid-warm`、`traincache-cold`/`traincache-warm`。冷热差别只在预热：预热耗时单列、不计入 makespan，预热搬的字节仍计入成本。组态细节见 4.2、4.3。

### 1.1 makespan 边界

七组态共用同一个 measure 脚本（`bench/compare/run_bench.py` 的 measure 模板），边界按下表采集；D/C 轨实验层用同名字段写 `run.json`（`bench/scripts/bench_track_d.py`、`bench_track_c.py`），两层的字段语义一致。

| 字段                  | 定义                                  | 采集方式                                                                                                                      |
|-----------------------|---------------------------------------|-------------------------------------------------------------------------------------------------------------------------------|
| `t_submit`            | 训练 Job 创建时刻                     | runner 在 `kubectl apply` 前取 `time.time()`，注入 Job 环境变量 `TRAINCACHE_JOB_CREATED_AT`（epoch 秒，字符串）；各组同一写法 |
| `t_pod_ready`         | 训练 Pod Ready 时刻                   | K8s Pod condition `Ready=True` 的 `lastTransitionTime`，runner 侧读回，不依赖 Pod 自报                                        |
| `t_first_step`        | 第一个 step 开始时刻                  | measure 脚本在第一个 batch 就绪之后、算力开始之前打点（epoch 秒）                                                             |
| `t_last_step`         | 最后一个 epoch 最后一个 step 结束时刻 | 最后一个 step 返回后打点                                                                                                      |

measure 脚本在 stdout 打一行 `RESULT key=value ...`（含 `startup_makespan`/`total_makespan`，由 `t_first_step`/`t_last_step` 减 `t_submit` 得到），每个 epoch 边界打一次 `[EPOCH_BOUNDARY] epoch=<n> ts=<epoch秒>`；runner 解析这两类标记，不读 Pod 内文件。`t_pod_ready` 由 runner 从 K8s 取，与 Pod 内时刻用同一把 epoch 秒尺子对齐。

两个 makespan：**启动 makespan** = `t_first_step - t_submit`，含调度、镜像拉取、Pod 启动与数据等待；**全程 makespan** = `t_last_step - t_submit`，含启动阶段，另单列 `t_last_step - t_pod_ready` 作为「落地后阶段」，用于拆分启动收益与全程收益。

`t_first_step` 必须在 batch 就绪之后打点，早打一步会把数据 stall 漏掉、指标失真。`metadata.creationTimestamp` 只作交叉核对，不作为 `t_submit` 主口径。

### 1.2 stall 口径

每一步记录 `wait_s`（本步开始等待 batch 到 batch 就绪）与 `step_s`（batch 就绪到本步计算结束）。

`stall = wait_s / step_s`。聚合报 `mean` 与 `p90`，中位数只用于判断「是否处于 stall 形态」，不作为主要比较指标。epoch 0 前 10 步标记为 `warmup`，不进入 stall 聚合，但仍进入 makespan。

### 1.3 阶段标签

每步带一个 `phase` 标签，取值固定为 `startup`、`steady`、`switch`：

| 阶段 | 起点 | 终点 |
|---|---|---|
| `startup` | `t_submit` | `t_first_step` |
| `steady` | `t_first_step` | 第一次切换事件 |
| `switch` | 切换事件时刻 | 新窗口 K 块全部就绪的时刻；若未就绪，截到该 epoch 结束 |

每个 epoch 边界都算一次切换事件，三种 shuffle 策略都一样；curriculum 的 stage 边界额外算一次。`switch` 优先于 `steady`，两个窗口同时活跃时按 `switch` 记。`traincache-warm` 的启动窗口以 WarmupTask 就绪状态（`startupWindowReady`/`gateDecision`）为准；`traincache-cold` 的 startup 阶段直接以 `t_first_step` 为终点。

epoch/stage 切换的训练侧 phase 用可观测代理：**新窗口 K 块对应的分片全部首次被训练侧打开的步**。代理晚于 Agent 的真实就绪时刻，会把少量 steady 预取归到 `switch`，报告里单列该口径差异；Agent 侧 `phase=switch` 的事件仍由 `ready_bitmap` 驱动，其命中计数列只作交叉校验。

### 1.4 命中率口径

命中率的统一定义：**该块打开时没有触达源站，就算命中**。

- 训练侧字节账由 measure 脚本按 phase 累计：每次打开累加 `read_bytes_<phase>`；打开时本地不存在、要等待预取或回源时，另把该块字节计入 `demand_miss_<phase>`。traincache 组精确到块；`direct` 整片 HTTP 直读，全部计入未命中；`juicefs-*`、`fluid-*` 出不了块级指标，按 D25 近似（warm≈全命中、cold≈全回源，分片粒度），产物 `hit_rate_basis` 列写明近似口径。
- 源站侧对账用 MinIO Prometheus 的 `minio_s3_traffic_sent_bytes` 在 run 窗口内的增量（`origin_egress_bytes`），与训练侧 fetch 字节的差值落 `origin_reconcile_diff`；差异超过 5% 时以源站为准并在报告里说明。MinIO 未开访问日志，不按块键做请求计数。
- `traincache` 组同时抓 `traincache_cache_hit_ratio{dataset,phase}` 与训练侧统计对账，差异超过 5% 时以训练侧 open-time 字节账为准。产物列的分工：
  - 主口径（整轮与分阶段）一律用训练侧 open-time 字节账：`hit_rate = 1 − demand_miss_bytes / read_bytes`，分阶段落 `hit_ratio_startup`/`hit_ratio_steady`/`hit_ratio_switch`，`hit_rate_basis=open_time_demand_miss_bytes`。
  - `traincache_fetch_bytes_total` 的 run 窗口增量单独折算 `source_saving_ratio = 1 − fetch_bytes_run / read_bytes`（`source_saving_basis=origin_saving`），衡量省下的源站流量，不与命中率混用。
  - Agent 侧 `traincache_cache_hits_total`/`traincache_cache_misses_total` 的增量按 `phase` 落 `hit_ratio_agent_*` 作交叉校验；`traincache_cache_hit_ratio{phase}` 末值落 `hit_ratio_gauge_*`，只作对账。Agent 窗口内没有读样本时这些列留空，不写 0。
- `direct` 组没有缓存层，命中率按 0% 记并标注「无缓存层」；`juicefs-*` 与 `fluid-*` 用 D25 近似口径，不依赖各自厂商指标的语义。

### 1.5 三笔字节成本

三笔全部计入收益分母，不允许只报 makespan 不报成本：

| 账目 | 范围 | 统计方法 |
|---|---|---|
| 启动预热 | warm 组的预热阶段 | `traincache-warm` 按模型计 `WARMUP_K × 8 MiB × 实际 fanout`（`warmup_basis=prefix_only(k*chunk*fanout)`，集群 fanout=2）；`juicefs-warm`/`fluid-warm` 按整份数据集计 1 份。冷组与 `direct` 记 0。`warmup_seconds` 取 `status.gateDecision.decidedAt − status.startedAt`，字段缺失时回退墙钟并记 `warmup_time_basis=wall`；未预热的冷组记 `cold` |
| 持续预取 | 门控放行/训练开始到训练结束 | 把 `traincache_fetch_bytes_total` 中 `reason=prefetch` 的增量按窗口边界归因：落在切换窗口内的计入第三笔，其余计入本笔 |
| 阶段切换重预取 | 每个 `switch` 窗口 | 同一计数器增量中落在切换窗口内的部分 |

归因序列由运行期采样点和训练结束后的最终快照组成，末段增量不会漏算。`prefetch_bytes_run` 单列 reason=prefetch 的窗口总增量，`other_fetch_bytes_run = fetch_bytes_run − prefetch_bytes_run` 放非预取回源；`sustained_prefetch_bytes + switch_reprefetch_bytes` 应等于 `prefetch_bytes_run`，对不上说明采样缺口，按实际值报告并在行内标注。

`traincache_fetch_bytes_total` 现有标签是 `{dataset,result,reason}`，没有 `phase`。阶段拆分不新增标签，对照层统一用 runner 解析到的 `[EPOCH_BOUNDARY]` 时刻对计数器做区间差分（D 轨用 `run.json` 的 `switch_events`）；采样目标周期 5 s、切换归因窗口 60 s，产物记 `sample_n` 与 `sample_max_gap_s`，差分边界与采样间隔的误差单独报告。源站侧总出站字节作为交叉校验，差异超过 5% 时以源站为准。

`fanout` 的重复字节不隐藏：fanout=2 时启动预热按 2 份计入，Agent 计数器按实例各自累计也天然包含这份重复。两本账都只记一次，不做「有效字节」折算。

### 1.6 胜负判据与允许的阴性结论

每组每个点报平均数与 bootstrap 95% 置信区间（10,000 次重采样）。比较两个组时，对「平均数差值」做同样的 bootstrap：

| 结论 | 条件（以 makespan 越低越好为例） |
|---|---|
| 赢 | 平均数改善 ≥ 5%，且差值 CI 上界 < 0 |
| 输 | 平均数恶化 ≥ 5%，且差值 CI 下界 > 0 |
| 相近 | 差值 CI 包含 0 |
| 可忽略 | CI 不包含 0，但平均数差异 < 5% |

命中率越高越好，方向反过来。§4 的「回落时间」以 20% 作为差异阈值，单次测量不判胜负。

任何「赢/输」必须跑满该点规定的次数：`pareto-startup` 每点 7 次、`pareto-sustained` 每点 2 次（D18），§5.3 每点 1 次；三个曲面族每点 1 次，只报方向与形态，不下胜负结论。对照层按 §1.9 的 S/M/L 分档是 3/3/1 次。判胜负的点至少 3 次，少于 3 次的点只报方向与形态（D19 的次数口径由 D32 按带宽分区接管；D19 起对照层不再适用「7 次」要求）。

以下阴性结论都可以写进报告，不需要为了「做出正结果」改档位；临时加档位、改阈值或改 K 只能作为下一轮新预注册：

- 启动门控在本次档位范围内从未赢过自由调度（`startup-surface`）。
- TrainCache 只在启动阶段赢，全程时长与 Fluid 相近。
- 阶段切换不是本装置的瓶颈，或预取已覆盖切换后的新窗口（`switch-recovery`）——此时给出新窗口 K 块就绪时刻与 ETA 的对照。
- `per-epoch` 重排下全程时长不随 epoch 数增长（`total-makespan`）——先查该点是否全部命中与命中率曲线，确认后写「该档位下缓存层不构成全程瓶颈」并给出字节账。
- 顺序单 Job 下三档淘汰策略差异小于 5%，排序策略对单 Job 顺序训练不关键，真正关键的是预取调度与跨租户保护（§5.3）。
- fanout=3 的重复字节成本超过它带来的启动收益；启动收益不随 fanout 增长（§5.1）。
- lookahead 在 8~32 区间内不改变全程收益（§5.2）。

出图的负收益区域必须在图上标出。正式开跑后与本文件不一致的操作，写清日期、原因与影响的 COND 和 run ID，记进该轮 commit message、CHANGELOG 与批次报告；本文的假设、档位与判据保持冻结，不回改。

### 1.7 冷态与作废

冷态分两层。入组时做全量 `cold_reset`：删测量 Pod，清四个节点缓存目录（traincache 的 `blocks` 与 `quarantine`、`/var/cache/jfs`、Fluid 的 `/tmp/juicefs-cache`），删后判空，再丢宿主机页缓存。冷组跨 rep 只做轻冷态 `rep_cold_reset`：删测量 Pod、清四个缓存目录、丢页缓存，不 down/up 组件；warm 组每个 rep 仍整轮 down/up 并重新预热，否则 WarmupTask 停在上一轮的 Released 状态，标着 warm 实际是冷读。

清目录只清磁盘层。Fluid/JuiceFS 的挂载进程跨 rep 存活，内核里那批 FUSE 文件的干净页不会因为删目录而失效，下一 rep 的首批读直接命中页缓存、不过 tc 限速链路。所以每个 rep 都要 `sync; echo 3 > /proc/sys/vm/drop_caches`；跑分器优先用 sudo 通道，其次特权 docker，两条都不通就中止，不出「看着是冷读其实是页缓存」的行。

作废情形写进 `reason` 列，行保留、不进汇总：`up_failed`、`pod_create_failed`、`pod_failed`、`parse_failed`、`read_queue_timeout`、`read_error`、`agent_degraded`、`evict_not_engaged`，以及人工判定的 `suspect_page_cache`（读数明显快于同格 `direct` 等物理上不可能的结果）。装置自检失败整轮作废并重跑，不允许挑掉坏点或把失败轮当异常值删除。

淘汰闸门有没有生效由三列自证，traincache 组每轮都落，其余组态留空：

| 列 | 取值 | 说明 |
|---|---|---|
| `evict_blocks_run` | run 窗口内各 agentd `traincache_evict_blocks_total{result}`（result∈{normal,danger}）增量之和 | 淘汰到底删过块没有；计数器归零（agentd 重启）时按末值起算 |
| `capacity_bytes_final` | 训练结束时各 agentd `traincache_cache_capacity_bytes_total{source="bytes"}` 的最大值 | Agent 自己记的字节账；容量为 0 时该累计不启用，恒为 0 |
| `cache_dir_peak_bytes` | run 窗口内单节点 `/var/cache/traincache/blocks` 已写完块字节的最大值：`docker exec` 在每个 worker 节点上 `find -name '*.blk'` 求和、取单节点最大值，按采样节拍读；预取在途的 `tmp-*` 半成品不计 | 目录里的真实字节，不经过 Agent，用作对账基准 |
| `cache_dir_peak_samples` | 同一个 run 窗口里目录字节被采了多少次 | 与下一列相乘即采样覆盖的窗口跨度，判据三的余量是不是采出来的侥幸读得出来 |
| `cache_dir_peak_period_s` | 相邻两次目录采样的时刻差均值。标称 5 s（`run_bench.py` 的 `SAMPLE_INTERVAL_S`），`docker exec` 串四个节点会把实际间隔拖长，这一列记实际值 | 判据三上界里「采样间隔内还能写进多少」那一项按这一列核，不拿标称值当实测 |

三条判据：

- `evict_blocks_run = 0` 且 `cache_dir_peak_bytes > 1.05 × cache_bytes`：目录已装过容量而淘汰一次没删，本轮的容量口径不成立，作废并记 `reason=evict_not_engaged`。5% 余量给采样间隔内的增长；预取在途的 `tmp-*` 半成品不在目录峰值口径里（只统计写完的 `.blk`），不占这份余量；淘汰有删块时不判这一条。
- `capacity_bytes_final` 对同一节点的目录字节末次采样 ≥1.5 倍或 ≤0.5 倍：Agent 的字节累计重复记账或漏记（同一批块在启动预扫与首次打开各记一次正好 2.00 倍），该轮的字节维度读数只作诊断，不进结论。峰值列是窗口最大值，不参与这一比对。
- 倾斜两族开跑前的探针另看目录峰值有没有压在上限附近：`cache_dir_peak_bytes ÷ cache_bytes ≤ 1.16`。分母是 COND 声明容量（`cache_bytes` 列），不是 `capacity_bytes_final`——后者是 Agent 训练结束时的在用字节末值，拿它当分母测的是 Agent 自己报的账，不是上限有没有被压住。1.16 的依据是淘汰和采样都按节拍响应、都不是连续的：六条倾斜 COND 统一 @100 mbit（链路实测有效带宽 11.95 MB/s）、声明容量 2 576 980 377、`agent/evictor/evictor.go` 的 `defaultInterval` 30 s、目录字节采样周期 5 s，从块写进越过上限的那刻到下一次清理真正执行之间，最多还能写进 (30 s + 5 s) × 11.95 MB/s ≈ 418 MB，对声明容量是 16%。两个节拍相加是这段盲区的上界，单看淘汰节拍会漏掉「采样格点之间涨上去又没被读到」那一段。把余量压到 5% 等于要求两个节拍合计 ≤10 s，产品没有这个承诺。式子里的 5 s 是标称值：正式路径的采样要串四个节点的 `docker exec`，实际节拍可能更长，跑完用 `cache_dir_peak_period_s` 回代同一式子重算，实际值到 10 s 时上界是 1.19。2026-11-02 两次取证实测峰值 2 935 277 824（轮询 0.5 s 时期的完整 run，比值 1.139）与 2 731 459 712（轮询 25 ms 的 7 min 取证跑，比值 1.060），都在本条之下；取证跑的目录字节是手动 30 s 采的 15 个点，正式路径按 5 s 采、并把点数与实际节拍一起写进 `cache_dir_peak_samples`、`cache_dir_peak_period_s`，让读者能核这是真实余量还是采样侥幸。超出的轮次不作废（淘汰是否生效仍看第一条），但「上限有没有压住」只作诊断，不进结论。

三列只证明闸门在动，不证明淘汰策略好坏；策略优劣看 §5.3 与 `pareto-sustained` 各点的命中率与全程时长。C 轨的 `--selftest` 用模拟下载器自带的 LRU 挤出分片，只验步记录字段与统计函数形态，不是产品淘汰生效的证据；产品证据只看上面三列。`make bench-doctor` 在开跑前做五条断言：本批声明了 COND 或 `TRAINCACHE_CACHE_CAPACITY_BYTES` 时，`traincache-config` 的 `cacheCapacityBytes` 必须等于该期望值；本批声明了 COND 或 `TRAINCACHE_PREFETCH_LOOKAHEAD`/`TRAINCACHE_EVICT_POLICY` 时，ConfigMap 的 `prefetchLookahead`、`evictPolicy` 必须等于 COND 的值（`apply -k` 会把这两项盖回清单默认 16、heat，见 §C4 映射表）；各 agentd 容器内的 `TRAINCACHE_CACHE_CAPACITY_BYTES`、`TRAINCACHE_PREFETCH_LOOKAHEAD`、`TRAINCACHE_EVICT_POLICY` 必须与 ConfigMap 声明值一致（配置改了但 agentd 没重启时进程内仍是旧值）；节点缓存目录里有块而各 agentd 的字节累计恒为 0 时报 FAIL；tc qdisc 在位时，从 MinIO Pod netns 回读的 tbf burst 折算成字节必须等于 `config.burst_for_rate(该档 rate)`，容 ±1%（iproute2 按 32 位字取整会掉零头，3750k 回读 3839962b；tc 未挂只 WARN 不 FAIL）。

### 1.8 环境与轨迹

- kind 集群：1 个 control-plane + 4 个 worker，共 5 个节点。对照组与主实验先同集群，资源吃紧再拆，拆组只允许整体迁移，不允许只迁一部分。
- 请求轨迹：同一 track+档位的七组态共用一份轨迹——S/D 用 `traces/track-compare-d-s8-per-epoch.json`，M/B 用 `traces/track-compare-b-m32-per-epoch.json`，L/B 用 `traces/track-compare-b-l128-per-epoch.json`，C 用 `traces/track-c-32shard-per-epoch.json`；记录分片顺序、seed、每步样本数，`per_epoch` 的稳定哈希写进每个 COND 与产物目录（对照层按同一份参数现场生成，sha 必须与 COND 一致）。
- tc：速率按 COND，延迟全档统一 20 ms，netem 不挂随机时延。
- 数据源：出图族与对照层共用 MinIO 上的 `compare-data-8m` 快照（128 个 tar，每片 256 MiB，约 31 GiB）。`startup-surface`、`switch-recovery`、`pareto-startup`/`pareto-sustained` 消费前 8 个分片（2 GiB，ratio 的分母）；`total-makespan` 消费前 32 个分片（8 GiB）；对照层的 S/M/L 三档消费前 8/32/128 个分片（2/8/31 GiB）。七组态在同一格消费同一批分片。
- 训练负载：出图族与对照层用同一 measure 形态——标准库脚本按 400 步/epoch、每步 200 ms、8 MiB 分段读复刻训练 I/O，记 `read_workers=2`。真实 PyTorch + webdataset 只用于倾斜两族（§5.2、§5.3）的 C 轨两 Job 与 `bench_track_d.py` 装置自检；出图族与对照层不依赖它。
- 网关开关：装置级环境变量 `TRAINCACHE_GATEWAY` 只改 traincache 组块 GET 的落点（开=经 `traincache-gateway` 合并回源，关=直连源站），direct/juicefs/fluid 三组不读网关。本文件除 §5.4 外的七族实验一律在关网关下跑，网关不是任何一张图的自变量；每行 `summary.csv` 仍落 `gateway` 列（`1`/`0`）记录装置状态，开关不同的行不落在同一产物目录。开关口径见 `docs/4.3-startup-and-experiments.md` §3.1。
- 对照组不可用预案：对照层开跑前先做仅验可行性的 Fluid 冒烟（控制面与 DataLoad/Runtime 全 Ready、400 步经 FUSE 跑通、组件额外占用 ≤6 CPU / 6 GiB）。两次失败且归因环境时记 `fluid-unavailable-on-kind`，五组表里 Fluid 行标 `unavailable`，不补跑、不另起集群；manifest 自身错误修好后重试不计次数。可行性冒烟不产生性能数字，不属于「看到结果再调参」。

### 1.9 容量比三档 S/M/L 与预注册假设（七组态对照，D19/D30/D31/D32）

真实训练里数据集通常是节点缓存的几十倍以上，只在一个容量比下跑分，结论无法外推。七组态对照按数据/缓存容量比分三档，缓存三档固定同一个 1 GiB：

| 档 | 数据 | 缓存 | 容量比 | 参跑组 | 带宽 | 每点次数 | 定位 |
|---|---|---|---|---|---|---|---|
| S | 2 GiB | 1 GiB | 1:2 | 全部七组态 | @100 与 @1000（另有 @300 档三组） | 3（@100 与 @1000 各 3 次） | 正式结果，现状口径 |
| M | 8 GiB | 1 GiB | 1:8 | `direct`、`fluid-cold`、`traincache-cold` | @1000 | 3 | 正式结果，欠配校验 |
| L | 32 GiB | 1 GiB | 1:32 | `traincache-cold`、`fluid-cold` | @1000 | 1 | 探点，产物标 `exploratory` |

口径说明：

- COND 的 `group` 用七值词表，与跑分器的组态名一一对应：`direct`、`juicefs-cold`、`juicefs-warm`、`fluid-cold`、`fluid-warm`、`traincache-cold`、`traincache-warm`。冷热由组态名表达，不靠「M/L 档的 `traincache` 就是冷启动」这类隐含约定。
- M 档与 L 档的基线用 `fluid-cold`（D30）：欠配校验必须压在最强工业基线上，只比 JuiceFS CE 会被质疑「绕过 Fluid」。`juicefs-cold`/`juicefs-warm` 仍留在 S 档七组态里。Fluid 若触发 D36 的两次环境性失败，M/L 该组落回 `juicefs-cold` 补跑，产物记 `baseline_substituted`。
- warm 组（`juicefs-warm`、`fluid-warm`、`traincache-warm`）只出现在 S 档：1:8 及以下预热至多覆盖数据的 1/8，热读相对冷读的优势缩小是算术事实，不是新发现，不陪跑 M/L。
- L 档每点 1 次，低于 §1.6 的「判胜负的点多于 3 次」纪律，因此标 `exploratory`：只报单点值、不报 CI、不进正式表，只用来回答「M 的方向是否延续」，不支持任何正式结论。CI 指 §1.6 的 bootstrap 95% 置信区间。
- 除容量档与带宽档外三档共用其余口径：同一轨迹、fanout=2（两个 s3-access 节点各预取一份）、淘汰 `heat`、D16 训练负载、固定 delay 20 ms。
- **带宽是第二个自变量**（D31）：tc rate 取 {100, 300, 1000} mbit，随 COND 落盘。burst 按「约 0.1 秒的传输量」推导（1250k / 3750k / 12500k），不跨档复用固定值。这里的 k 按 tc 的 1024 解析：1250k 挂上后是 1 280 000 字节，对 @100 的 tbf 速率 12.5 MB/s 是 102 ms 突发窗口（按 1000 算会读成 100 ms）；`tc qdisc show` 回读打印的 `burst 1250Kb` 是 KiB 不是 kilobit，命令行同时给的 `latency 50ms` 只定队列长度、不覆盖这个桶。netem 全档位只挂固定 `delay 20ms`，不加随机时延——逐包随机时延会把包序打乱，300mbit 档实测吞吐从 35.6 MB/s（95% 线速）跌到 0.6 MB/s 以下，档位差异被装置掩盖。「链路带宽 ÷ 每步读量」只用来解读分区：S 档 0.47 / 1.40 / 4.66，M 档 0.12 / 0.35 / 1.16，L 档 0.03 / 0.09 / 0.29——<1 链路受限，>2 计算主导。
- 每点次数按带宽分区（D32）：S 档 @100 与 @1000 各 3 次；M 档 @1000 3 次；L 档 @1000 1 次。3 次必须报均值 + bootstrap CI，只报中位数不满足 §1.6 的纪律。
- 块大小口径：正式实验一律读 8 MiB 块（8388608 字节）的 `compare-data-8m` 快照（切成 8 MiB 的理由见 §C2.2），生产默认 64 MiB 不变，旧 `compare-data` 快照只留作历史产物复现。快照覆盖 B 轨全部 128 个分片，S/M/L 只按轨迹收窄消费范围，不另发布小快照。
- L 档数据已生成（128 个 256 MiB 分片，追加约 24 GiB，只追加不覆盖 `bench-b` 源数据）；实际每份约 252.6 MiB、总量约 31 GiB，比声明值小约 3%，容量比约为 1:31，三档偏差同向、不影响组间可比性。
- 跑分第一格先做前置探针：无 tc 状态下测 MinIO 实际吞吐上限。上限 < 125 MB/s 时 @1000 档失效，带宽轴缩为 {100, 上限} 两档，并回写 D31。**已实测（§6.2）：C ≈ 674 MB/s，@1000 可达，三档独立，本条不触发。**

自变量：容量档 S(1:2) → M(1:8) → L(1:32)。假设按「自变量 → 预期正负区间 → 反例长什么样」写死：

| # | 假设：自变量 → 预期正负区间 | 反例长什么样 |
|---|---|---|
| HC.1 | 容量比越大，各组命中率越低、回源占比越高。预期：S→M 时三个冷组（`direct` 恒 0 除外）命中率单调下降、回源字节占比单调上升；即 M 档命中率 < S 档且回源占比 > S 档，`traincache` 与 `juicefs-cold` 两组都成立 | 命中率 S→M 不降甚至反升，或回源占比不升——先查产物与口径是否串档；确认后如实写「命中率与回源占比未随容量比单调变化」 |
| HC.2 | 容量比越大，TrainCache 相对基线的收益应增大。预期：`traincache-cold` 相对 `direct`、相对 `fluid-cold` 的启动与全程 makespan 改善幅度，从 S 档的 X% 增大到 M 档的 Y%，要求 Y > X（S、M 两档数字都要在表里列出） | 两种反例：① S→M 收益不增反降（Y ≤ X）；② M 档 `traincache-cold` 与 `fluid-cold` 的 makespan 均值差异落在差值 CI 内（CI 含 0，两组分不出快慢）。出现任一情形就如实写「容量比假设不成立」，不改档位 |
| HC.3 | 带宽越紧，TrainCache 相对基线的收益越大。预期：同一容量档内，链路受限区（@100，BW/r≈0.47）的 `traincache-cold` 启动与全程改善幅度大于预取有效区（@1000，BW/r≈4.66），即 X@100 > X@1000 | 反例：@1000 的改善幅度不小于 @100。此时如实写「收益与带宽无单调关系」；先查两档的 trace、chunk 与预热是否同口径，再下结论 |
| HC.4 | M 的方向延续到 L。预期：L 档单点上 `traincache-cold` 不慢于 `fluid-cold`，且相对 S/M 的收益方向同号。探点不做 CI 判断 | L 档差异反号或接近 0。单点分不出噪声和趋势，结论只写「L 档方向不延续/无法判定」，不允许用来推翻或确认 HC.2 |

判据：HC.2 在 S→M 必须有明确的「证实/证伪」表述，写进报告表；缺组或 CI 跨 0 也照写。加档位、改次数只能作为下一轮新预注册，不动本节。

## 2. 启动门控盈亏曲面（族 `startup-surface`，COND 前缀 `fig1-`）

### 2.1 自变量与档位

| 自变量 | 档位 | 说明 |
|---|---|---|
| 源站带宽 | 100 / 300 / 1000 mbit | 延迟固定 20 ms，burst 由 rate 推导（见 §C2.5） |
| 数据集/缓存容量比 | 1 / 2 / 4 | 缓存容量 = 数据集字节 ÷ 比值；2 即现有 50% 欠配 |
| fanout | 1 / 2 / 3 | 每 Pod 预热节点数上限；受 4 个 worker 约束 |

共 27 个组合，每个组合跑门控与自由两态，合计 54 点。固定参数：MinIO 快照前 8 个分片（2 GiB）、1 个 epoch、400 步/epoch、`read_workers=2`、`K=8`、`threshold=0.9`、`gapMin=0.1`、`slopeMin=0.001`、`TMax=10m`、`halfLife=4`、`cutoff=8`、lookahead 8、淘汰策略 `heat`、固定 seed 顺序。

对照组「自由调度」= 同一个 Job 去掉 SchedulingGate，不做启动门控；预热与服务端逻辑保留，用于区分「门控的收益」和「预热的收益」。两态的受试组态都是 `traincache-warm`，COND 只差 `prefetch.gate.mode`。

### 2.2 预注册假设

| # | 假设 | 预期 |
|---|---|---|

## 4. 阶段切换后的 stall 回落（族 `switch-recovery`，COND 前缀 `fig3-`）

### 4.1 自变量与档位

| 自变量 | 档位 | 说明 |
|---|---|---|
| epoch 数 | 1 / 3 / 6 | 决定切换次数 |
| shuffle 策略 | 固定 seed / 每 epoch 重排 / curriculum | 三种顺序形态 |

共 9 个点，只跑 `traincache-cold`。固定参数：MinIO 快照前 8 个分片（2 GiB）、100 mbit/20 ms、fanout=2、缓存 50%、`K=8`、门控参数同 §2、lookahead 8、淘汰策略 `heat`。

三种 shuffle 的定义：

- `fixed`：所有 epoch 用同一个 seed，消费顺序逐 epoch 相同。
- `per-epoch`：seed+epoch，每 epoch 重新做分片置换与样本 shuffle。
- `curriculum`：3 个 stage，分片集合依次为全量、2/3、1/3。全局置换 `P = Random(seed).permutation(n_tars)`；stage 0/1/2 分别使用嵌套前缀 `P[:n]`、`P[:ceil(2n/3)]`、`P[:ceil(n/3)]`；stage 内顺序 = `P` 过滤到该前缀，stage 内所有 epoch 完全一致。stage 归属：`E<3` 时为 stage 0；否则 `e < floor(E/3)` 为 0、`e < floor(2E/3)` 为 1、其余为 2。每个 epoch 边界都是切换事件；stage 边界与 epoch 边界重合时只记一次，事件标 `kind=epoch+stage`。1 个 epoch 时 curriculum 退化为单个 stage（全量），仅用于保持矩阵完整，不参与「curriculum 优于固定 seed」的结论。

### 4.2 回落时间的定义

每个切换事件算一次回落时间：

1. 基线 = 切换前 20 步的 stall 均值。
2. 阈值 = `max(1.1 × 基线, 基线 + 5 个百分点)`。基线接近 0 时用加法项，避免阈值退化为 0。
3. 从切换后第 1 步开始，取 10 步滚动 stall 均值；第一次满足「滚动均值 ≤ 阈值，且之后连续 10 步都 ≤ 阈值」的步，记为回落点。
4. 到该 epoch 结束仍未满足，记右删失（right-censored），回落时间按 epoch 结束计，并单独报删失率。

纵轴报每个点的回落时间；每点 1 次，不报 CI。同时报删失率，避免用「没恢复」伪装成「恢复得快」。

### 4.3 预注册假设

| # | 假设 | 预期 |
|---|---|---|
| H3.1 | 切换成本随 epoch 数增加 | `per-epoch` 的回落时间随 epoch 数增加而增加，6 epoch 点明显高于 1 epoch 点 |
| H3.2 | 固定 seed 时切换不是瓶颈 | `fixed` 的回落时间在各 epoch 数下相近，且不高于 `per-epoch` |
| H3.3 | curriculum 的切换代价最大 | `curriculum` 的回落时间高于 `fixed`；stage 越窄，切换瞬间 stall 峰值越高 |

### 4.4 采样

9 个点每点 1 次，不做符号翻转补测。

### 4.5 COND 与跑法

- COND：9 个，`fig3-<shuffle>-ep<E>`，`shuffle∈{fixed,per-epoch,curriculum}`；`curriculum` 的三档比例与边界规则按 §C2.4 记进 COND。
- 跑法：`python3 bench/exp.py run switch-recovery [--point curriculum-ep6]`（9 点串行）。

### 5.4 网关合并（族 `gateway-merge`，COND 前缀 `gw-`）

网关只在同一个对象键的并发请求上合并。单读端下 Agent 自己已按 key 合并，网关没有活干；要测出收益，必须让多个节点的 Agent 同时请求同一块。

设计是 3 读法 × 2 带宽 × 开关，12 个点：

| 读法 | 每节点读什么 | 作用 |
|---|---|---|
| `r1` | 全量 | 单读端，量网关自身开销 |
| `r4repl` | 全量，四份相同的读 | 收益臂，同 key 并发最密 |
| `r4shard` | 不相交的 2 个分片 | 阴性对照，不应出现合并 |

- 固定：S 档 2 GiB、8 MiB 块、1 GiB 缓存、1 epoch、3 reps。1 epoch 只测冷阶段，避开淘汰策略对重复 epoch 的影响。
- 起跑：四个 Pod 等到同一个绝对时刻再读（栅栏 25 秒），启动偏差不进合并窗口。
- 主指标：源站出站字节与全程 makespan。网关自己的 60 秒汇总（`merged`/`owners`/`kicked`/`rejected`）只作诊断；命中率是控制量，两臂差异应在噪声内。
- `r4repl`：关闭与开启的源站字节比应接近 4，makespan 同步下降；降不到说明栅栏没对齐，按作废处理。
- `r4shard`：两臂的字节与 makespan 应基本相等，出现差异说明测到的不是合并。
- `r1`：开启网关的 makespan 不应比关闭差，用来排除「多一跳拖慢单读端」。
- 1000 mbit 是阴性对照：合并仍可能发生，但源站不再是瓶颈，时间收益预期消失。报告先看 `merged/gets`，再决定结论写成「带宽高了收益消失」还是「窗口不足、合并未发生」。

### 6.1 镜像 digest 取值口径

镜像集文件里每个引用写成 `repo:tag@sha256:<digest>`，digest 取集群 containerd 的 manifest digest，不是 `docker images` 的 config digest。本地 build 的镜像没有 RepoDigests，`lock.py` 把 COND 记录值与 docker 侧摘要分开记，后者只作交叉核对。

### 6.2 前置探针实测

无 tc 状态下 MinIO 源站吞吐上限 **C ≈ 674 MB/s（9 次测量的中位数，区间 629~755；≈5.4 Gbit/s）**，采法：与 train-job 同路径（worker 节点上临时 Pod 经 `nodeIP:30090` nodePort），`mc cat bench-b/shard-xxxxx.tar | wc -c` 计时。并行 2 连接聚合 1120/870 MB/s、并行 3 聚合 1207 MB/s——上限随连接数增长，说明 674 MB/s 是单连接读者上限而非源站出口上限。

结论按 D31 的判据落定：**C ≫ 125 MB/s，@1000mbit 档可达，{100, 300, 1000} 三档互相独立，无格子塌缩成 `ceiling`，BW/r 分区无需按 C 重算**。

## 7. 机时

两条约束：§1.6、§1.9、§1.10 与 §2.3、§3.3、§4.4、§5.1、§5.2、§5.3、§5.4 写明的每点次数不允许降低；L 档 1 次探点不参与正式结论。

### 7.1 口径

单 run 时长 = max(源站传输时长, 计算下限) + 冷态与采集。

- 源站传输时长 = 数据集字节 × epoch 数 ÷ 有效带宽。有效带宽 = min(名义 rate, 源站实测上限 C)。
- 计算下限 = 400 步 × 200 ms × epoch 数——负载本身要花的 CPU 时间，限速再快也压不下去。
- 单 epoch 消费速率 r = 数据集字节 ÷ (400 × 200 ms)。BW/r 判断这一格受不受链路限制：<1 传输主导，>2 计算主导，落在 [1,2] 表示每步读量与链路带宽同量级。这个比值只用来解读结果，不改变链路参数。

### 7.2 参数

| 带宽档 | 链路 | 单 epoch 的 r（S/M） | BW/r（S） | BW/r（M） | 判定 |
|---|---|---|---|---|---|
| 100 mbit | 12.5 MB/s | 26.8 / 107.4 MB/s | 0.47 | 0.12 | 链路受限 |
| 300 mbit | 37.5 MB/s | 同上 | 1.40 | 0.35 | S 的读量与带宽同量级，M 链路受限 |
| 1000 mbit | 125 MB/s | 同上 | 4.66 | 1.16 | S 计算主导，M 的读量与带宽同量级 |

L 档跑 1 个 epoch，r = 429.5 MB/s，@1000 的 BW/r = 0.29，仍在链路受限区。三档规模按 §1.9：数据 2/8/32 GiB、缓存同为 1 GiB、8 MiB 块即 256/1024/4096 块，epoch 数 S 档 3、M 与 L 档 1（§C3）。

源站吞吐上限 C ≈ 674 MB/s 为实测值（§6.2），@1000 档链路能吃满，封顶塌缩分支不触发。

@100 mbit 档的有效带宽实测 11.95 MB/s（2026-11-02，集群内只读探针，同一对象取四种形态：单流整取、长连接顺序取、每块新建连接顺序取 32×8 MiB、4 并发取——四者都是 11.95 MB/s，整形装置不是瓶颈）。字节地板 = 实测 `fetch_bytes_run` 25.2 GB ÷ 11.95 MB/s ≈ 2110 s ≈ 35 min。这条地板同时是读侧第三条过滤的判据，除数取 `bench/config.py` 的 `TILT_EFF_BW_MB_S`（§1.10）。

前置探针（`policy-heat` 1 run，轮询 0.5 s 时期）实测 `total_makespan` 5510 s，聚合只有 4.58 MB/s，即链路能力的 38%。差额不在产品侧：agentd 的 demand 任务均值 0.785 s/8 MiB（10.2 MB/s，单槽等于线速），2428 个任务合计 1905 s，占 makespan 的 35%——抓取槽其余时间在等测量体发下一块。根因就是那 0.5 s 的轮询粒度：块抓取 0.82 s，而轮询只在 0.5 s 的格点上检查，检测平均延后 0.5–0.7 s，下一块的 `read_miss` 又要等本块检测并读完才发出，单块墙钟被抬到 1.79 s。

轮询降到 25 ms 后的取证跑（2026-11-02 14:32Z 起 7 min，`policy-heat` 同组态，原始记录 `~/tcd/probes/m5-gate-20261102/gate6-train-job-0-final.log` 与 `gate6-samples.txt`）：Job B 第 14–27 步的 `step_s` 稳定在 22.35–22.67 s，32 块/步即单块墙钟 0.70 s；同一窗口 agentd 的 demand 任务 258 个合计 170.2 s，单任务 0.66 s（8 MiB ÷ 0.66 s = 12.1 MB/s，等于线速），抓取槽占用从 35% 升到 94%。单块墙钟与抓取时间对齐，轮询的等待量清零。

单 run 账：96 步 × 22.5 s = 2160 s，比字节地板 2110 s 高 2%，加冷态、复位与采集 35 s，单 run 墙钟 ≈ 37 min。轮询 0.5 s 时期同一组态的完整 run 实测 `total_makespan` 5510 s ≈ 92 min。**9 run ≈ 5.5 h**。

再往下只剩带宽这一条：@300 mbit 下 8 MiB 的传输段从 0.67 s 降到 0.22 s，字节地板落到 25.2 GB ÷ 35.6 MB/s ≈ 708 s，单 run ≈ 12–13 min、9 run ≈ 2 h，但那是改档位，要按 §1 的预注册纪律另起一轮，且判据三的峰值上界要按 (30 s 淘汰节拍 + 5 s 采样周期) × 35.6 MB/s 重算（对声明容量约 48%，即上界 1.48）。带宽不改时，本节 37 min 与 5.5 h 是本批的现行口径。

网关族按 §5.4 的 12 点 × 3 reps = 36 run 计：100 mbit 档约 75 min、1000 mbit 档约 10 min，加冷态与切臂合计约 2.5 h。

### 7.5 交叉核对与串行约束

`startup-surface` 的 ratio=2 组合与对照层 S 档同参数（2 GiB 数据、1 GiB 缓存、fanout 2、@100 与 @1000），两者交叉核对，不另设基线；`total-makespan`、`switch-recovery` 只跑 TrainCache，不跑对照组；全程串行，不做双轨并行：tc 挂在 MinIO Pod 的出口上，并行等于均分带宽，整轮作废。
