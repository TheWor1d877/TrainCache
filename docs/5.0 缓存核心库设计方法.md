# 缓存核心库设计方法
一个Go库，负责记录有哪些数据块，按照内容将数据块落盘，按需下载数据块
没有任何服务形态，现在就是一组代码加单元测试

##  路径索引
索引层（决定取什么）：索引的条目键为Entry：{path, chunk, size, fp}，采用路径寻址，key是(path,chunk),它不承诺跨路径去
重

维护一张表，记录某个数据分片下的第 i 块数据对应哪个物理数据块（按内容指纹寻址，指纹决定块在 CAS 里的落盘位置）
一个数据集可能有几十万个块，如果都用这张表，那么它无法放入etcd中（上限1.5MB）,所以放到对象存储上面
这张表在对象存储中被切分成若干个索引分片管理，每个索引分片不要超过10w条数据。这里先做个消歧：本文后面出现的「分片」全部指索引分片，它和 doc 1、probes/可行性探针报告.md、doc 4 里训练数据侧的 webdataset tar 分片是两类东西——tar 分片是打包好的训练数据文件，索引分片是这张路径索引表的切片。两类分片最后都存放在 MinIO 上，名字撞车容易看混，所以本文一律写全名。

使用原子提交 + 快照来解决数据侧读写问题
角色： 写入方，Agent，索引分片构建任务，对象存储

Agent要在内存中维护块->位置的映射关系
这个映射关系常常会因为写入方写入而变化，所以需要常常到对象存储中更新
Agent先从对象存储下载索引分片文件，然后解析映射关系

数据集更新的时候,不能直接覆盖旧索引分片，而是通过一次原子提交 + 快照:
#### 1. 写新块：
写入方把新块写到新位置，不覆盖旧块。

#### 2. 写新索引分片： 
构建任务读取当前已经提交的快照`S1`,确定本次需要修改哪些索引分片，
之后构建任务生成新的索引分片，新索引分片使用独立的对象键，并且在提交之前不会被当前的快照引用

#### 3. 上传对象：
将索引分片上传到对象存储的唯一对象键下面，然后上传新的快照清单
此时即使新索引分片和快照已经存在于对象存储中，它们仍然只是尚未提交的数据，对读侧不可见

#### 4. 验证快照完整性：
提交之前，需要确定： 
1. 新快照已经上传
2. 快照引用的所有索引分片已经成功写入
3. 所有索引分片都符合预期的完整性要求
4. 被引用的新数据块都成功发布到CAS存储

#### 5. 原子提交：
构建任务尝试将CURRENT指针从快照S1更新成S2，但是要考虑到并发修改的情况
提交时必须使用对象存储支持的条件写入机制，确保只有当 CURRENT 仍然指向 S1 时，才能更新为 S2， 避免并发任务互相覆盖。
- 提交成功：S2 成为当前快照。
- 提交失败：重新读取最新快照，基于最新快照重新构建并提交。
具体条件写入方式取决于使用的 S3 对象存储实现——不同后端对 `If-Match` / `If-None-Match` 的支持程度可能不同，代码里有 `ProbeConditionalWrite` 兜底探测。

#### 6. 读侧刷新:
Agent定时（每 N 秒）读一次CURRENT。
快照变了，就执行：
下载S2的快照清单，
根据清单下载相应的索引分片，构建新的内存映射（注意下载的索引分片与清单要验证完整性）
原子切换内存映射的版本，不要在加载新索引分片的过程中逐个修改正在使用的旧映射

#### 7. 清理旧块与旧快照
旧快照清理：
CURRENT 指向的快照不能删除。
提交新快照后，旧快照可能仍被正在执行的读操作使用，因此不能立即删除。
确认旧快照不再被任何读操作使用后，删除旧快照的清单及不再被其他快照引用的索引分片。

旧数据块清理：
只有已提交快照不再引用的数据块，才能进入待回收集合。
删除数据块前，必须确认没有读操作正在使用它。
如果数据块仍被引用或正在被读取，则跳过本次回收，留待后续处理。

#### 注意： 写盘的原子性
写新块步骤与写新索引分片步骤应该做成先写临时文件，后面rename()改名的设计，这样别的进程永远看不到写了一半的块。
缓存块不做逐块 fsync——数据丢了重新下载就好，掉电丢块的代价就是重拉

## 快照读者登记
Agent 加载 S2 后，向对象存储写一个"我在用 S2"的登记（对象键 `dataset/<dataset>/readers/<nodeID>.json`，带心跳时间戳），切到新快照时更新登记并保留上一快照的宽限期，不用搞分布式租约。
清理方删旧快照前，检查所有登记：没人声明 + 心跳过期 + 不是 CURRENT，才删。
心跳过期就当读者死了，允许删，防止 Agent 崩了旧快照永远留着。

## CAS存储层
数据块下载时会流过内存，这个时候算一下xxh3指纹，按照指纹命名文件存盘（例:`blocks/ab/<指纹>.blk`）
xxh3 的计算速度大约 10GB/s 每核，不占用额外 I/O（应该，需检验），指纹直接作为存储键。
这样就实现了读回校验：读回来时可以顺手校验数据有没有损坏（块头用 64 字节记录大小和摘要，不需要额外的校验文件）

不同路径下内容相同的数据块只存储一份。
回收数据块时，需要确认该数据块不再被任何保留的已提交快照引用，并且没有读操作正在使用它，才能删除。
引用计数统计的是已提交索引快照对物理 CAS 块的逻辑引用，而不是单纯统计当前路径映射

注意: 引用计数是反映索引快照的逻辑引用关系，而不是读操作。
读操作的生命周期单独管理。

补充（2026-10-14）：上面的「回收」和后来的「缓存淘汰」是两个维度，不要混。回收只针对不再被引用的旧数据，管的是正确性；缓存淘汰管的是磁盘容量，删的是仍被快照引用的块的本地副本——索引条目和引用关系都不动，副本删了之后要用再重新下载（见 6.1 cas.Evict、6.1 §7.6）。

## 索引分片按前缀目录加载
服务侧数据块是按需下载的，但索引默认是全量加载的：训练可能只需要 /train-data 下面的某些path的数据，
其余路径的索引分片跟这次训练无关。数据量上去之后，全量索引分片加起来可能达到 GB 级别，全部下载加载太浪费，所以「按前缀加载索引分片」是必要的。
manifest 本身只是一份分片引用列表，体积小，仍然全量下载，真正省掉的是无关索引分片的下载。
核心库catalog要提供「按前缀加载」的能力，而Agent服务（后续内容）决定「加载哪些前缀」

核心库 Catalog：
  - 提供 Load(prefixes []string) 或 LoadShards(refs []ShardRef)
  - 只下载、校验、加载指定的索引分片
  - 维护局部内存映射

## sha256校验
现在的块头是64 字节，记录大小和摘要，之后将其扩展成128字节，另外记录成：
```text
块头（例如 128 字节）：
  magic        4B
  version      2B
  flags        2B      // bit0: 是否带 sha256
  block_size   4B
  xxh3_128    16B      // 始终存在，作为存储键
  sha256      32B      // 可选，flags 置位时有效
  reserved    ...      // 对齐到 128B
```
存储键仍然是 XXH3-128，路径 blocks/ab/<xxh3>.blk 不变，去重逻辑不变。
SHA-256 只在需要时计算并写入块头。
读回时：默认只校验 XXH3；如果 flags 置位，再校验 SHA-256。

同时增加一个sha256开关：提供一个全局或按命名空间/桶级别的配置
`verify_level = xxh3 | xxh3+sha256`
这个开关可以做成只影响新写入的块，老块保持原样，避免全量重算。

## 限制并发抓取
下载块的时候按照在途字节数控制并发，而不是按照Goroutine数量
小文件会将goroutine撑爆，大文件会把内存撑爆，字节数是两种情况统一的度量。
同时限制对单个主机的连接数（默认 64）与最大并发下载任务数

## 标准
单测全部通过，重点覆盖四种场景——多个 goroutine 同时写同一个块、写一半进程崩溃、相同内
容去重、校验失败后重新下载

## 附录: 概念辨析与示例
数据分片(tar)： 上游训练数据集的打包文件，如`shard-00000.tar`，百MB级webdataset，存储在上游数据源(不在本项目中，但是名字字符串在每条索引的path中)
数据块： 把一个 tar 按 64 MiB 等分后的物理单元，是缓存/传输/去重的最小单位，存储在对象存储
索引分片(idx)： 路径索引表的切片，回答，存储在对象存储
manifest(manifest.json)： 快照清单，这次快照由哪几部分索引分片组成，存储在对象存储
快照/snapshot： 由CURRENT指针，快照清单manifest与具体的索引分片组成

#### 对象存储层
训练数据以tar文件形式进来，被切成64MB大小的数据块之后按照内容指纹管理
path:数据分片的名字，chunk:块号，size: 快大小，fp: 指纹信息
对象存储格式：
```text
bucket/
├── dataset/<数据集名>/CURRENT                          ← 提交指针，文本："<snapID> <manifestFP8>"
├── dataset/<数据集名>/snapshots/<快照id>/manifest.json     ← 快照清单
├── dataset/<数据集名>/snapshots/<快照id>/shard-<fp8>.idx   ← 索引分片
└── <数据集名>/blocks/<path>#<chunk>                    ← 数据块（裸数据）
```
索引格式： `Entry：{path, chunk, size, fp}`
manifest格式：由ShardRef组成，每个Shard的组成：
```go
type ShardRef struct {
    Key         string `json:"key"`       // 分片的完整对象键
    MinPath     string `json:"min_path"`  // 分片内首条Entry的path
    MaxPath     string `json:"max_path"`  // 分片内末条Entry的path
    Entries     int64  `json:"entries"`   // 该分片的条目数
    Fingerprint string `json:"fp"`        // 分片内容的xxh3-128(32字符hex)
}
```
上传示例：
200MB 的 shard-00000.tar
→ 切成 4 块（3×64MiB + 8MiB 末块），每块算出 xxh3-128 指纹
→ 块作为独立对象上传：<名>/blocks/shard-00000.tar#0 ~ #3
→ 索引留下 4 条 Entry：{path, chunk, size, fp}
→ Entry 按 (path,chunk) 字典序排序、按 10 万条切成索引分片上传
→ 生成新 manifest，CURRENT 条件写入切换到新快照

#### Agent层
索引(内存中)是： (path,chunk) -> Entry的映射
数据块(磁盘中)是：`blocks/<fp前2位>/<fp>.blk`

Agent下载示例：
训练要"shard-00000.tar 第 2 块"
→ Catalog.Lookup(path, 2) 查内存映射 → Entry{fp: e5f6...}
→ 本地 blocks/e5/e5f6....blk 在？→ 在：Open 校验后直接读，结束
→ 不在：
→ 按 <数据集名>/blocks/shard-00000.tar#2 从对象存储 GET
→ 字节流经 cas.Put：边写本地盘边算 xxh3 → 得实际指纹
→ 回填 128B 块头（magic/version/大小/xxh3/可选sha256），rename 原子发布
→ Open 读回校验：验块头 + 流式重算数据指纹
→ 校验失败：删块重下（指数退避，有上限），成功：按 e5f6... 提供读取

#### xxh3完整校验链
核心：每一级的指纹由上一级背书
```text
CURRENT 里的 manifestFP8
 └─背书→ manifest.json
      └─背书→ manifest中每个索引分片的 ShardRef.Fingerprint
           └─背书→ 每条 Entry.fp
                └─背书→ 数据块内容（落盘时算出的指纹必须等于它）
```

#### 前缀加载
1. 按照数据集加载
每个数据集都维护一个CURRENT指针，这种情况下，只需要初始化的时候指定dataset即可
2. 只加载某个数据集下面的某些path
读 CURRENT → 下载 manifest（全量下载，它只有几十KB，便宜）
对索引分片逐个做区间相交判定（D22 公式）
观察那些是需要的索引分片，就下载即可
