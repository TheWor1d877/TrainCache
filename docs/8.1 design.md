# 8.1 Controller & Scheduler design

> 本文是 `docs/8.0 Controller & Scheduler.md`（用户基线，不改动）的实现契约。
> 与基线冲突处一律以本文冻结的约定为准，新增/修正均登记在 `docs/8.3 decisions.md`。
> 跨模块增量见 §12，并已追加到 `docs/7.1 design.md` 附录 A。
> 对 8.0 的增量（M14）：8.0 中 fanout 的"精确数量"语义由 M14 修订为"上限 + 下限"，8.0 原文不改；以本文 §5.1、§5.5 与 `docs/8.3 decisions.md` D39 为准。

先解释几个词。**冻结约定**指 §5 的接口签名、§6 的数据格式、本文所有表格和枚举取值已经定稿，实现的人照着写就行，字段名、类型、默认值都不能自己改。**幂等**指同一个动作重复执行，结果只算第一次——比如 `Submit` 同一个 `task_id`，再调一次不会建第二个任务。**best-effort** 指"尽力而为，失败就算了"，不阻塞主流程。**不得/禁止**就是硬约束，写进代码检查里的。

## 1. 模块定位

一句话：Controller 管预热的生命周期，Scheduler 管训练 Pod 往哪台机器上落；两者之间通过 Node annotation 传分数快照，不见面、不互调。

### 1.1 职责

新增 Go module `traincache/controller`，提供集群控制面三件套：

| 组件                | 职责                                                                                                      |
|---------------------|-----------------------------------------------------------------------------------------------------------|
| `DataSet` 控制器    | 校验数据契约、固化块编号与布局、解析可达节点、校验快照可访问性；只写 status，不触发预热                   |
| `WarmupTask` 控制器 | 筛候选节点、GWAA 分配、按块下发/更新/取消预热、轮询就绪进度、门控判定、放行时冻结评分并写 Node annotation |
| MutatingWebhook     | Pod 创建时注入 SchedulingGate、WarmupTask 引用与 Pod 序号注解，是门控链路的前置条件（基线缺口 G1）        |
| Scheduler 插件      | 只读 Node annotation，实现 `Score` / `NormalizeScore`，返回 0~100                                         |

怎么理解这张分工表：DataSet 控制器只管"数据是不是靠谱"，不管"谁来暖"；WarmupTask 才是执行者，从挑节点到下发任务到判放行一条龙；Webhook 是 Pod 创建时的拦截器，给 Pod 挂个"等预热好了再放行"的门；Scheduler 插件只做一件事——读 Node 上的分数，给每台机器打 0 到 100 分。

### 1.2 非目标

先说不做什么，免得读的时候期待错：

- 不介入训练读路径：训练 Pod 经 hostPath 直读本地 CAS，不经过 Controller 或 Agent。
- 不做数据发布：tar 切块与快照提交由 `core/publish` 与 `traincache trainpublish` 负责。
- 不做运行时重预取：epoch/shuffle/curriculum 切换由 Agent 的 `PersistentPrefetcher` 处理，不进入调度路径。
- 不实现 DataLoader/sampler：训练侧只消费 `ConsumeOrder` 与固定 chunk 序号。
- 不实现 Agent 服务端：Agent 侧 gRPC 增量由 7.x 承接（见 §12）。

小结：Controller 只管控制面，数据面和读路径完全不碰。

### 1.3 与已完成模块的关系

| 已有模块            | 复用方式                                                         | 依赖方向           |
|---------------------|------------------------------------------------------------------|--------------------|
| `core/objectstore`  | `NewS3Store` / `Store.Get` 校验 CURRENT、manifest、shard 存在性  | controller → core  |
| `core/index`        | 复用 `Manifest`、`ShardRef`、`Entry`、键布局常量；只读，不写索引 | controller → core  |
| `agent/api/agentpb` | 扩展现有 `PreheatService`，Controller 作为客户端                 | controller → agent |
| `agent/metrics`     | 只参考 family 命名纪律，新建 controller 独立 Registry            | 不复用代码         |
| `agent/cmd/agentd`  | 参考 slog 初始化、信号处理、优雅退出                             | 不复用代码         |

Controller 对 core 和 agent 的依赖方向都是单向的：读 core 的对象存储和索引、做 Agent gRPC 的客户端；不复用 metrics 的代码，只借命名风格。

小结：Controller 是上层消费者，core 和 agent 是被依赖的下层。

## 3. 总体架构与依赖方向

先看部署拓扑图，四个组件围成一圈：

```
                    kube-apiserver
        ┌───────────────┼────────────────┬──────────────┐
        │               │                │              │
   controller-manager  webhook       kube-scheduler   Node
        │               │                │              │
   ┌────┴────┐          │           TrainCacheScore     │
   │ DataSet │          │           (读 Node annot.)    │
   │ Warmup  │          │                ▲              │
   └────┬────┘          │                │              │
        │  gRPC(南向)   │                │              │
        ▼               │                │              │
   Agent(DaemonSet) ────┴────────────────┴──────────────┘
        │  写 Node annotation(pod 创建前)
        │
   S3 对象存储 / 本地 CAS
```

怎么读这张图：
- Controller-manager 管两个 CRD（DataSet 和 WarmupTask），通过 gRPC 南向调用 Agent 下发预热任务；
- Webhook 是 Pod 创建时的拦截器，先于调度器运行；
- Scheduler 插件不跟 Controller 说话，只看 Node annotation；
- Agent 是唯一能写 Node annotation 的一方——它写好了，Scheduler 才看得到。

依赖方向固定为单向：

```
cmd/* → internal/{controller,webhook,scheduler}
internal/controller/* → {api/v1alpha1, gwaa, gate, nodescore, agentclient, storage, config, logging, metrics}
internal/{nodescore,agentclient,webhook,scheduler} → api/v1alpha1
internal/{nodescore,scheduler} → scorefmt
internal/agentclient → agent/api/agentpb
internal/storage → core/{objectstore,index}
api/v1alpha1 → k8s.io/apimachinery only
```

禁止：`api → internal`、`gwaa/gate/scorefmt → k8s 客户端或 core`、`scheduler → controller 内部包`、`internal → cmd`。这些禁止项的本质是"底层不能倒过来依赖上层"——否则一个小改动可能牵一大片。

小结：依赖方向是严格的 DAG，任何反方向都会被视为架构违规。

## 4. 包结构

目录怎么分，基本对应上一节的依赖图。读树的时候抓三个要点：`api/` 放 CRD 类型（跨 module 的契约层），`cmd/` 放入口程序，其余每个 `internal/` 下的目录是一个独立能力。

## 5. 核心接口（冻结约定）

这一节是全文最硬的部分。签名和字段都冻结了，实现子代理照着写就行，**不得**私自修改签名；变更需回传 `BLOCKED` 由主对话裁决。

### 5.1 CRD 类型

Group `traincache.io`，Version `v1alpha1`。两个 CRD 均为 Namespaced，跨对象引用只允许同 namespace。只开 `status` 子资源，不定义 `scale`（基线缺口 G9）。`WarmupTaskSpec.podCount` 与 `dataSetRef` 不可变，由 CRD CEL 校验 `self == oldSelf`；Controller 不创建 Job/Pod、不扩缩容、不重建 Pod。`traincache.io/s3-access` 标签由用户/集群管理员手工维护，任何组件**不得**写入。

DataSet 负责"数据本身"：endpoint、bucket、数据集名、chunk 大小、shards 列表、可达节点选择器。下面的 struct 定义逐字抄，字段注释写得很清楚：

```go
// DataSet
type DataSetSpec struct {
    Endpoint               string                    `json:"endpoint"`
    Bucket                 string                    `json:"bucket"`
    DatasetName            string                    `json:"datasetName"`
    SecretRef              corev1.LocalObjectReference `json:"secretRef"`
    SnapshotID             string                    `json:"snapshotID,omitempty"` // 空 = CURRENT
    ChunkSize              int64                     `json:"chunkSize"`
    Shards                 []ShardSpec               `json:"shards"`
    AccessibleNodeSelector *metav1.LabelSelector     `json:"accessibleNodeSelector,omitempty"` // 可选收窄；未设置时默认 traincache.io/s3-access=true
    Shuffle                bool                      `json:"shuffle,omitempty"`
    Metadata               *DataSetMetadata          `json:"metadata,omitempty"`
}

type DataSetMetadata struct { // 仅登记，Controller/Agent 不读取
    SampleCount int64  `json:"sampleCount,omitempty"`
    Format      string `json:"format,omitempty"`
    Description string `json:"description,omitempty"`
    Version     string `json:"version,omitempty"`
    Source      string `json:"source,omitempty"`
    Purpose     string `json:"purpose,omitempty"`
}

type ShardSpec struct {
    Name          string `json:"name"`
    Count         int32  `json:"count"`         // 该分片的块数
    LastChunkSize int64  `json:"lastChunkSize"` // 末块字节数，0 < v <= ChunkSize
}

type DataSetStatus struct { // 不设反向引用，WarmupTask 单向引用 DataSet
    ObservedGeneration int64              `json:"observedGeneration,omitempty"`
    Conditions         []metav1.Condition `json:"conditions,omitempty"`
    SnapshotID         string             `json:"snapshotID,omitempty"` // 解析后的具体快照
    TotalChunks        int32              `json:"totalChunks,omitempty"`
    BlockLayout        []BlockLayout      `json:"blockLayout,omitempty"`
    AccessibleNodes    []string           `json:"accessibleNodes,omitempty"` // selector 的解析结果，升序
}

type BlockLayout struct {
    Shard         string `json:"shard"`
    StartChunk    int32  `json:"startChunk"` // 全局块号，跨分片累计
    Count         int32  `json:"count"`
    LastChunkSize int64  `json:"lastChunkSize"`
}
```

WarmupTask 负责"预热执行"：引用 DataSet，指明 Pod 集，定义门控和调度策略。注意 `PreheatFanout` 是上限、`PreheatFanoutMin` 是下限——M14 刚加的字段，两个值配合使用：

```go
// WarmupTask
type WarmupTaskSpec struct {
    DataSetRef    corev1.LocalObjectReference `json:"dataSetRef"`
    TargetRef     TargetRef                   `json:"targetRef"`
    PodCount      int32                       `json:"podCount"`
    // PreheatFanout 是每个 Pod 预热节点数的上限；默认 1，最小 1，典型值 2。
    // +kubebuilder:default=1
    // +kubebuilder:validation:Minimum=1
    PreheatFanout int32                       `json:"preheatFanout,omitempty"`
    // PreheatFanoutMin 是每个 Pod 预热节点数的目标下限；默认 1，最小 1，必须 <= PreheatFanout。
    // 冲突、容量或集合外兜底可让实际 Assignment 少于该值，此时 MinUnmet=true；任何情况下不超过 PreheatFanout。
    // +kubebuilder:default=1
    // +kubebuilder:validation:Minimum=1
    PreheatFanoutMin int32                    `json:"preheatFanoutMin,omitempty"`
    Affinity      AffinityPolicy              `json:"affinity,omitempty"`
    TrainingType  TrainingType                `json:"trainingType"`
    PodDetails    []PodDetail                 `json:"podDetails"`
    Gate          GatePolicy                  `json:"gate"`
    Score         ScorePolicy                 `json:"score"`
    Candidate     CandidatePolicy             `json:"candidate,omitempty"`
}

type TargetRef struct {
    APIVersion       string                `json:"apiVersion"`
    Kind             string                `json:"kind"` // Job | StatefulSet | Pod
    Name             string                `json:"name"`
    PodLabelSelector *metav1.LabelSelector `json:"podLabelSelector,omitempty"`
}

type PodDetail struct {
    Index                int32                       `json:"index"` // 0..PodCount-1，必须连续
    Resources            corev1.ResourceRequirements `json:"resources"`
    InitialConsumeOrder  []int32                     `json:"initialConsumeOrder"` // 全局块号；非法时整组回退默认切分
    K                    int32                       `json:"k"`                   // 启动窗口块数，同时是评分平台段长度（每 Pod 独立 K_i）
}

type GatePolicy struct {
    Threshold   float64         `json:"threshold"`   // 0~1
    GapMin      float64         `json:"gapMin"`      // 0~1
    SlopeMin    float64         `json:"slopeMin"`    // 比例/秒，通常 <=0
    TMax        metav1.Duration `json:"tMax"`
    MinInterval metav1.Duration `json:"minInterval"`
}

// K 不在 ScorePolicy 中：每 Pod 的 K_i 来自 PodDetail.K，既是启动窗口，也是评分平台段。
type ScorePolicy struct {
    HalfLife float64 `json:"halfLife"` // H：半衰期（块）
    Cutoff   int32   `json:"cutoff"`   // C：截断距离（块）
}

type CandidatePolicy struct {
    RequireReady     bool  `json:"requireReady"`
    IgnoreNoSchedule bool  `json:"ignoreNoSchedule"`
    MinFreeDiskBytes int64 `json:"minFreeDiskBytes,omitempty"`
}
```

```go
type WarmupTaskStatus struct {
    ObservedGeneration int64              `json:"observedGeneration,omitempty"`
    Conditions         []metav1.Condition `json:"conditions,omitempty"`
    Phase              WarmupPhase        `json:"phase,omitempty"`
    ConsumeOrderSource ConsumeOrderSource `json:"consumeOrderSource,omitempty"` // Spec|Default
    StartedAt          *metav1.Time       `json:"startedAt,omitempty"`
    CandidateNodes     []string           `json:"candidateNodes,omitempty"` // 稳定排序，行列表头
    ReadinessTable     [][]int32          `json:"readinessTable,omitempty"` // P x N，行=Pod 序号、列=CandidateNodes 顺序；窗口就绪块数（计数，非比例）
    PodNodeReadiness   []PodNodeReadiness `json:"podNodeReadiness,omitempty"` // 每 (Pod, 实际认领节点) 一条；条数=实际 Assignment 数，正常在 [min,max]，冲突/容量/兜底可低于 min（MinUnmet），任何情况下 ≤ preheatFanout
    GateDecision       GateDecision       `json:"gateDecision,omitempty"`
    LastUpdated        *metav1.Time       `json:"lastUpdated,omitempty"`
}

// PodNodeReadiness 表示"某 Pod 在某个预热节点上的就绪事实"，每个实际认领的 (Pod, 预热节点) 一条。
// 每 Pod 条数等于该 Pod 实际 Assignment 的节点数。正常情况下在 [spec.preheatFanoutMin, spec.preheatFanout] 内；
// 冲突、容量不足或集合外兜底可让实际数量低于下限，此时 MinUnmet=true。任何情况下不超过 spec.preheatFanout。
// 一个可行节点都没有时，该 Pod 只写一条 NodeName 为空的汇总记录；总条数不超过 P×spec.preheatFanout。
type PodNodeReadiness struct {
    PodIndex               int32        `json:"podIndex"`
    PodName                string       `json:"podName,omitempty"`
    NodeName               string       `json:"nodeName,omitempty"`             // 预热节点
    ActualNode             string       `json:"actualNode,omitempty"`           // 实际落点；同一 Pod 的各条取同一个值
    ReadyBlockBitmap       []byte       `json:"readyBlockBitmap,omitempty"`     // 该预热节点上报的位图
    StartupWindowReady     int32        `json:"startupWindowReady,omitempty"`   // 窗口内就绪块数（ReadyInWindow 的源值，实际赋值同 readyInWindow；保留字段，便于直接读窗口就绪计数）
    ReadyInWindow          int32        `json:"readyInWindow,omitempty"`
    RequiredReady          int32        `json:"requiredReady,omitempty"`        // floor(threshold*K_i)，见 §5.6
    StartupWindowReadyRate float64      `json:"startupWindowReadyRate,omitempty"` // 仅观测，不参与门控
    GlobalDecayScore       int32        `json:"globalDecayScore,omitempty"`
    State                  PreheatState `json:"state,omitempty"` // 该预热节点的状态；无可行节点时为该 Pod 的汇总态（任一候选 Ready→Ready，全部 Failed→Failed，否则 Preheating）
    MinUnmet               bool         `json:"minUnmet,omitempty"` // 该 Pod 全部预热节点的实际 Assignment 数量低于 preheatFanoutMin 下限；与 gwaa.PodDecision.MinUnmet 同步（冲突、容量不足或集合外兜底导致）
    LastReportTime         *metav1.Time `json:"lastReportTime,omitempty"` // 该预热节点最近一次上报
}

type GateDecision struct {
    State     GateState   `json:"state,omitempty"` // Hold|Released|Degraded
    Reason    string      `json:"reason,omitempty"`
    DecidedAt *metav1.Time `json:"decidedAt,omitempty"`
    PodRates  []PodRate   `json:"podRates,omitempty"`
}

type PodRate struct {
    PodIndex int32   `json:"podIndex"`
    Rate     float64 `json:"rate"`
    Gap      float64 `json:"gap"`
    Slope    float64 `json:"slope"`
}
```

枚举取值冻结：`TrainingType = epoch|shuffle|curriculum|static`；`ConsumeOrderSource = Spec|Default`（`Default` 表示任一 Pod 消费顺序非法后整组回退，见 §7.2）；`WarmupPhase = Pending|Filtering|Preheating|Gating|Released|Degraded|Failed`；`GateState = Hold|Released|Degraded`；`PreheatState = Preheating|Ready|Stopped|Failed`；`AffinityPolicy = Any|Pack|Spread`（仅记录，v1 不参与算法）。这些枚举值**不得**自己发明新的或换拼写。

### 5.2 DataSet 控制器

DataSet reconcile 的 Reconciler struct 和方法签名：

```go
type Reconciler struct {
    client.Client
    StoreFactory storage.Factory // secretRef -> objectstore.Store
    Recorder     record.EventRecorder
    Log          *slog.Logger
    Metrics      *metrics.Metrics
}

func (r *Reconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error)
```

前置条件：`chunkSize > 0`、`shards` 非空、`count > 0`、`0 < lastChunkSize <= chunkSize`、`0 <= snapshotID`、Secret 存在且含 `accessKey`/`secretKey`。

后置条件：成功时 `TotalChunks = Σ shards[i].Count`、`BlockLayout` 按 spec 顺序累计 `StartChunk`、`SnapshotID` 为解析后的具体值、`AccessibleNodes` 为可达节点解析结果（升序）：默认选择 `traincache.io/s3-access=true` 的 Node；`AccessibleNodeSelector` 非空时在该标签集合内收窄。标签只读，任何组件**不得**写入。有匹配节点时 `Condition Ready=True`；无匹配节点时置 `Condition NoAccessibleNodes=False` 并发事件，返回退避重试（节点标签可能随后补齐），WarmupTask **不得**下发。

错误语义：可重试错误（存储不可达、API 冲突）返回 error 由 controller-runtime 退避；不可重试错误写入 `Condition InvalidSpec/StorageUnreachable/SnapshotNotFound=False` 并返回 nil。**幂等**：任何一次 reconcile 都从 spec 全量重算，不依赖上一次结果——这意味着你可以随时重启 Controller，不会留下半更新状态。

### 5.5 GWAA

GWAA（Greedy Weighted Allocation Algorithm）是"贪心加权分配算法"——给每个 Pod 挑一批预热节点。它是纯函数，不读 k8s、不写 status、不记 log。

```go
func Compute(in Input) Placement
type Input struct {
    Pods      []PodState   // Index, K, ReadyCountByNode map[string]int32（块数）
    Nodes     []NodeState  // Name, Stopped bool
    FanoutMin int32        // 目标数量下限；0 视为 1（CRD 层已拒绝 0 与负数）
    Fanout    int32        // 目标数量上限；0 视为 1（CRD 层已拒绝 0 与负数）
    Rand      *rand.Rand   // 注入随机源；测试传固定种子，生产用时间种子
}
type Placement struct {
    TargetSet      map[int32][]string    // podIndex -> 目标节点集合，按 c_ij 降序、节点名升序
    Assignment     map[int32][]string    // podIndex -> 最终认领节点；除集合外兜底 1 个外，是 TargetSet 的子集
    PreheatSet     map[string][]int32    // nodeName -> podIndex，覆盖实际 Assignment 的配对
    Decisions      map[int32]PodDecision // podIndex -> 目标数量与异常标记
    UnassignedPods []int32
    Rounds         int
}
type PodDecision struct {
    TargetFanout        int32 // 目标数量
    LowSignal           bool  // best <= S_min，缓存分布不足以区分节点
    ForcedByMin         bool  // 下限高于保留线，强制补到目标数量
    MinUnmet            bool  // 最终实际 Assignment 少于下限（含冲突、容量、集合外兜底）
    FallbackOutOfTarget bool  // 目标集合内放不下，集合外兜底 1 个
}
```

以下全部按块数计算；若输入的 `ReadyCountByNode` 是比例，先按该 Pod 的 `K_i` 还原为块数。GWAA 先为每个分配单元（普通 Pod，或亲和合并后的超 Pod）选出目标集合，再在目标集合内完成贪心分配。

**目标数量算法**（对每个分配单元独立执行）：

1. `K_i` = 该单元启动窗口的块数。这一行先把窗口大小记下来，后面全靠它算。
2. `S_min = ceil(0.25 × K_i)`，作为"低信号"下限。怎么理解这个数：如果最好的节点也只有不到 25% 的窗口块是就绪的，说明缓存分布没明显差异——随便挑哪台都差不多。
3. 可行节点按 `c_ij` 降序、节点名升序排序；`best = c_i1`。目标集合的排序是确定的，不走随机。
4. 若 `best <= S_min`：判为低信号，`band = min(maxFanout, 可行节点数)`，置 `LowSignal=true`。低信号的意思是"没差可挑，全拿上限"。
5. 否则 `band = min(maxFanout, 满足 c_ij >= 0.5 × best 的节点数)`，且至少为 1。0.5 是保留线：与最优节点差距过大的缓存分布不进入目标集合。这条规则是为了"暖备份但不瞎备份"——不能把差距特别大的节点也算进目标集合。
6. `target = clamp(band, minFanout, maxFanout)`，再按可行节点数封顶。clamp 的意思是把 band 夹在 [min, max] 之间。
7. 若 `minFanout > band`：置 `ForcedByMin=true`，按上述排序强制补到 `target`，用于保留暖备份。`ForcedByMin` 只表示"下限高于保留线、目标被强制抬高"，不保证最终实际数量达到下限。
8. 若 `minFanout > 可行节点数`：计划阶段先置 `MinUnmet=true`，`target = 可行节点数`；没有可行节点时目标集合为空并进入 `UnassignedPods`。
9. 冲突裁决、top-up 与集合外兜底全部结束后，按最终 `Assignment` 回算 `MinUnmet`：`len(Assignment[pod]) < 归一后的 min` 时为 true，否则为 false。归一后的 min 指 `preheatFanoutMin` 经 CRD 默认后的值，GWAA 输入中的 0 按 1 处理。冲突、容量不足或兜底导致实际认领少于下限，也会在这里置 true。
10. `Decisions[podIndex]` 记录 `TargetFanout`、`LowSignal`、`ForcedByMin`、`MinUnmet`、`FallbackOutOfTarget`。

**亲和合并**：合并单元的 `unitMin = max(各成员 minFanout)`，`unitMax = min(各成员 maxFanout)`；若 `unitMin > unitMax`，返回冲突错误。目标集合对单元内所有成员共享。

**目标集合与最终落点**：`TargetSet` 只表示"允许在哪里预热"，`Assignment` 才是实际执行集合。除集合外兜底外，`Assignment` 是 `TargetSet` 的子集；冲突裁决与补齐只在目标集合内进行；多个 Pod 争同一节点且无法全部容纳时，仍按 `c_ij - secondBest_i` 较大者保留，其余让步到目标集合内尚未认领的次优节点；冲突裁决中的并列（同一 Pod 的候选节点 `c_ij` 相同，或 `c_ij - secondBest_i` 相同）用注入的 RNG 均匀随机决定（D32）；节点能容纳几个 Pod 由 `allowMultiPodPerNode` 与亲和约束声明，本模块按该声明判断节点是否还有空位；共享分支未启用（D33）。目标集合内一个都放不下时，为免完全未分配，允许在集合外兜底 1 个并置 `FallbackOutOfTarget=true`；只有没有任何可行节点时才进入 `UnassignedPods`。每轮结束后被让步 Pod 只能改认尚未认领的目标节点；最多 `len(Pods)` 轮，仍未收敛则保留首个贪心结果并 `slog.Warn("gwaa: 未收敛，保留首个贪心结果")`。`PreheatSet` 覆盖实际 `Assignment` 的配对，未分配的目标节点不进入 `PreheatSet`。冲突或容量限制可能让最终 `Assignment` 少于 `TargetFanout`，甚至低于下限；这是允许的结果，按实际 `Assignment` 写 status 并置 `MinUnmet`。集合外兜底始终最多 1 个节点，不为补足下限把集合外节点扩成多个。

GWAA 不决定最终落点，最终落点由 Scheduler 在放行后的分数快照中选择。固定随机种子下可复现；不同种子下输出合法（目标集合确定，`Assignment` 仍满足集合约束）。复杂度：O(P×N×max)；`max` 为小常量（默认 1、典型 2），在 P≤64、N≤256 约束下为有界上界。

小结：GWAA 先算"该找多少台"，再算"找哪几台"，最后算"每台分到哪个 Pod"；全程不碰 k8s，纯函数可测。

### 5.6 门控

门控的事很简单：训练 Pod 创建时被 Webhook 挂了个"等预热"的门，Controller 不停检查"现在能不能开门"。检查逻辑就是下面这个函数：

```go
func Evaluate(in Input) Decision
type Input struct {
    Now         time.Time
    Policy      GatePolicy
    Pods        []PodGateState // Index, AssignedNodes []string, ReadyByNode map[string]int32, K, Rate, PrevRate, PrevAt, FirstSampleSeen
    FirstReadyAt time.Time     // 首个 Pod 达标的时刻，零值表示尚未出现
    StartedAt   time.Time
}
type Decision struct { State GateState; Reason string; Rates []PodRate }
```

整数门控：对每个 Pod 计算 `required_i = floor(Threshold * K_i)`；若 `Threshold > 0 && required_i == 0` 则置 `required_i = 1`；`Threshold == 0` 时 `required_i = 0`。示例：`K=8, Threshold=0.8 → required=6`。条件①的满足条件是：每个 Pod 的预热节点集合（正常在 `preheatFanoutMin` 到 `preheatFanout` 之间，实际以 `Assignment` 为准；低于 min 时 `MinUnmet=true`）中至少有一个节点，其该 Pod 的 startupWindowReady ≥ floor(阈值 × K_i)。预热节点集合记在 `AssignedNodes`，`ReadyByNode[node]` 是该节点窗口内已落盘且校验通过的块数，`required_i = floor(Threshold*K_i)`；一个 Pod 只要有任一预热节点达标，就算该 Pod 达标。`Rate` 取集合内各节点 `Ready/K_i` 的最大值，供观测与条件②使用；`StartupWindowReadyRate` 仅作观测，不参与判定。条件②的 `Gap`/`Slope` 仍用连续 `Rate`（不取整），避免量化噪声。

判定顺序按固定优先级跑三条件：
- 条件③超时（`Now-StartedAt >= TMax`）→ `Degraded`：等太久了，不等了；
- 条件①（所有 Pod 的预热节点集合中都至少有一个节点满足 `Ready >= RequiredReady`）→ `Released`：全达标，开门；
- 条件②（`FirstReadyAt` 非零、`Now-FirstReadyAt >= MinInterval`、未达标 Pod 同时 `Gap > GapMin` 且 `Slope < SlopeMin`）→ `Released`：剩下的 Pod 补齐太慢，继续等的边际收益低，放行；
- 都不满足 → `Hold`：接着等。

`Gap = Threshold - Rate`，`Slope=(Rate-PrevRate)/(Now-PrevAt)`，`PrevAt` 零值或间隔 < MinInterval 时不参与条件②。条件①只在预热节点集合内判定，候选节点中没有被选为预热节点的那些节点不参与（见 decisions D38）。

边际收益语义：等待的价值是减少启动期回源。Agent 在放行后仍持续回填，未就绪块读到时会回源（正确但慢）；窗口内第 i 块要到训练第 i 步才被消费，若补齐速率不低于消费速率，等满窗口的边际收益趋零。因此条件②在"至少一个 Pod 达标"后，对每个尚未达标的 Pod 以 gap（剩余缺口）大且 slope（补齐速率）低作为"继续等待的边际收益低于成本"的判据；条件③ tMax 是绝对上限，代表占用资源的机会成本。

小结：门控三条件按"超时降级优先、全达标放行其次、慢补齐提前放行兜底"的顺序判定。

### 5.7 Webhook

```go
type PodMutator struct {
    Client client.Client
    Log    *slog.Logger
}

func (m *PodMutator) Handle(ctx context.Context, req admission.Request) admission.Response
```

Webhook 是 Pod 创建时的拦截器，只在两种条件同时满足时才介入：`objectSelector` 匹配 `traincache.io/warmup=enabled`；命名空间内存在 `TargetRef` 命中该 Pod 且 `Ready` 的 WarmupTask。

注入内容（**幂等**——重复调多少次，注入效果一样）：
1. `spec.schedulingGates` 追加 `{"name":"traincache.io/warmup"}`，已存在则跳过。
2. annotation `traincache.io/warmup-task: <namespace>/<name>`。
3. annotation `traincache.io/pod-index: <i>`；`i` 优先取 Pod label `batch.kubernetes.io/job-completion-index`，其次从 StatefulSet ordinal（Pod 名最后一个 `-` 后缀）解析；都失败则不注入并 `Events` 记录 `WarmupTaskMappingFailed`。
4. 不注入 nodeAffinity、不改资源、不改容器——Webhook 只负责挂门，其他不动。

`failurePolicy: Ignore`。注入失败时 Pod 正常创建，Controller 在后续 reconcile 中检测"带 `warmup=enabled` 但无 task 注解的 Pod"并记 `Condition GateInjectionDegraded`。

小结：Webhook 只做注入，注入失败不阻塞 Pod 创建；门控链路有兜底但会静默降级。

### 5.8 Scheduler 插件

```go
const Name = "TrainCacheScore"

type Plugin struct { handle framework.Handle; log *slog.Logger; ttl time.Duration }
var _ framework.ScorePlugin = (*Plugin)(nil)

func New(ctx context.Context, obj runtime.Object, h framework.Handle) (framework.Plugin, error)
func (p *Plugin) Name() string
func (p *Plugin) Score(ctx context.Context, state *framework.CycleState, pod *v1.Pod, nodeInfo *framework.NodeInfo) (int64, *framework.Status)
func (p *Plugin) NormalizeScore(ctx context.Context, state *framework.CycleState, pod *v1.Pod, scores framework.NodeScoreList) *framework.Status
```

Scheduler 插件的角色很单纯：给"Pod 该不该落到这台 Node"打个 0 到 100 分。分数来自 Node annotation，Controller 在门控放行时写进去。

`Score` 通过 `nodeInfo.Node().Name` 取节点名（v0.37 的 Score 签名直接传 `*framework.NodeInfo`，不再传节点名字符串），其余语义不变。逻辑：读 Pod annotation `traincache.io/warmup-task`（值 `<ns>/<name>`）与 `traincache.io/pod-index`（十进制 `<i>`）→ 用 `scorefmt.Key(ns, name)` 计算 Node annotation 键（§6.2，即 D27 的 `scores-<namePrefix32>-<hash12>`）→ 在该节点的 Node annotation 中读对应键的 JSON → 取 `p["<i>"]` → 未过期返回该分数。键缺失、条目缺失、`pod-index` 缺失、JSON 损坏、`task` 与 Pod 注解不匹配或超 TTL 一律返回 0。任何错误都返回 0 + `nil` status，**不得**让 Pod 因插件失败而被拒绝调度。

`NormalizeScore`：`score' = round(score * 100 / max(1, maxScore))`，全 0 时全部返回 0。KubeSchedulerConfiguration 只启用 `score`；`NormalizeScore` 不是可配置扩展点，由 framework 对实现了 `ScoreExtensions` 的 score 插件自动调用。权重由 `KubeSchedulerConfiguration` 配置。

小结：Scheduler 插件只做"读 annotation → 打分"一件事，读不到就给 0，绝不阻塞 Pod 调度。

## 6. 数据格式

这一节全是字节层面的约定，实现时逐字照做。字段顺序不影响 JSON 解析，但字段名、类型和默认值不能改。

### 6.1 CRD 状态布局

`ReadinessTable` 行下标 = `PodDetail.Index`，列下标 = `CandidateNodes` 顺序；值 = 该 Pod 在该节点启动窗口内"已落盘且校验通过"的块数，范围 `0..K_i`（每 Pod 使用自己的 `K`）。比例一律现算：`Rate = ReadyInWindow / K_i`。`RequiredReady = floor(Threshold*K_i)`（`Threshold>0` 且结果为 0 时取 1；`Threshold==0` 时为 0），按 Pod 计算后写入该 Pod 的各条 `PodNodeReadiness`。status 只存事实与判定所需的整数门槛；`StartupWindowReadyRate` 仅作观测，不参与判定。

`PodNodeReadiness` 明细按 `(PodDetail.Index, 预热节点)` 展开，条数等于该 Pod 实际 `Assignment` 的节点数（无可行节点时只写一条汇总记录，见下）。正常情况下每 Pod 条数在 `[preheatFanoutMin, preheatFanout]` 内；冲突、容量不足或集合外兜底让实际认领少于下限时，条数可以低于 `preheatFanoutMin`，此时 `MinUnmet=true`，status 仍跟随实际 `Assignment`。任何情况下每 Pod 条数不超过 `preheatFanout`，总条数不超过 P×preheatFanout。每条记录的 `NodeName` 是该 Pod 的一个预热节点，`ReadyBlockBitmap`、`ReadyInWindow`、`StartupWindowReady`、`StartupWindowReadyRate`、`LastReportTime` 都取这个节点最近一次上报；`State` 是这个预热节点的状态；`ActualNode` 记录 Pod 的实际落点，同一 Pod 的各条记录取同一个值。某个 Pod 一个可行节点都没有时，该 Pod 只写一条 `NodeName` 为空的记录，`State` 取该 Pod 的汇总态（任一候选 Ready→Ready；全部候选 Failed→Failed；否则 Preheating）。候选节点粒度的就绪块数只由 `ReadinessTable`（P×N，行=Pod 序号、列=`CandidateNodes` 顺序）承载。门控读取每个 Pod 的实际预热节点集合，评分快照覆盖实际 `Assignment` 的全部预热节点，最终落点由 Scheduler 在放行后的分数快照里选择。P≤64、N≤256、`preheatFanout` 取小常量（典型 2）时，明细与表的序列化体积仍小于 1 MiB，M13 重新实测。

### 6.2 Node annotation

每 WarmupTask 一个独立键，完整键为 `<prefix>-<namePrefix>-<hash12>`，其中 `<prefix>` 默认 `traincache.io/scores`（§8）。编码函数：

```go
func Key(ns, name string) string
// namePrefix = strings.TrimRight(name[:min(len(name),32)], "-.")
// hash12     = sha256(ns + "/" + name) 的前 12 位小写十六进制
// prefix     = 配置项（默认 traincache.io/scores），Controller/Scheduler 取值一致
// return prefix + "-" + namePrefix + "-" + hash12
```

键名部分（`scores-` + ≤32 + `-` + 12）≤ 52 字符，满足 63 上限。

值：单行 JSON，UTF-8，无换行。

```json
{"v":1,"task":"default/train-1","g":12,"t":"2026-10-20T08:00:00Z","p":{"0":87,"1":73}}
```

- `v`：格式版本，当前 1。
- `task`：`<namespace>/<name>`，写入时校验与键的 hash 一致。
- `g`：写入时的 WarmupTask `generation`。
- `t`：RFC3339 UTC 写入时刻；超过 `CONTROLLER_SCORE_TTL` 视为过期。
- `p`：键为 podIndex 十进制字符串，值为 0~100 整数分数。

每个 task 只读改写自己的键；多 task 共节点互不影响；TTL 按 `t` 判断。Scheduler 由 Pod annotation `traincache.io/warmup-task`（值 `<ns>/<name>`）计算同一键；键缺失、条目缺失、JSON 损坏、`task` 不匹配或超 TTL → 分数 0。

写入策略：一次 reconcile 内按 task 读-改-写本 task 的键，冲突时重读重试最多 5 次；不删除其他 task 的键。

## 7. 关键流程

前面五节讲零件，这一节讲这些零件怎么串起来跑。每个流程都对应一条或几条验收。

### 7.1 DataSet 校验与块布局

DataSet reconcile 的七步，按"先读后校验再探测再写 status"的顺序走：

1. 读取 DataSet；`deletionTimestamp` 非空则直接返回。做什么：拿到 CR 对象；为什么：删除中的对象不处理。
2. 校验 spec 字段；失败写 `InvalidSpec=False`，`Event` 记录原因，返回 nil。做什么：确认 chunkSize、shards、count、lastChunkSize、snapshotID 等在合理范围；为什么：spec 错了后面都是白跑。
3. 解析 Secret，构造 `objectstore.Store`；失败写 `StorageUnreachable=False`，返回 error 退避重试。做什么：拿到 S3 访问凭证并尝试连一下；为什么：Secret 不存在或对象存储挂了都是可重试错误。
4. `snapshotID` 为空时读 `CURRENT` 解析具体快照；读 manifest 并校验 `snapshot_id` 一致、`shards` 非空。做什么：确定到底用哪个快照版本；为什么：快照不存在时不能往下走。
5. 按 spec `Shards` 顺序累计 `StartChunk`，生成 `BlockLayout` 与 `TotalChunks`。做什么：把每个 shard 的块号映射成全局唯一编号；为什么：后续预热和门控都要按全局块号来。
6. 解析可达节点：默认选择 `traincache.io/s3-access=true` 的 Node；`AccessibleNodeSelector` 非空时在其结果内收窄；写升序 `AccessibleNodes`。无匹配节点置 `NoAccessibleNodes=False` 并发事件，停止下发；标签只读，任何组件**不得**写入。做什么：列出哪些机器能访问 S3；为什么：不可达的机器没法预热。
7. 写 status（带 `ObservedGeneration`）：有可达节点时 `Ready=True`，无匹配节点时 `Ready=False`（原因见步骤 6）；`Event` 提示引用它的 WarmupTask。做什么：把校验结果写回 CR；为什么：WarmupTask 要看这个 status 决定下不下发。

小结：DataSet reconcile 的唯一职责是把 spec 里的松散描述变成结构化、可校验、可引用的 status。

### 7.2 候选节点筛选与预热下发

WarmupTask reconcile 的前六步，从读取到筛选到下发：

1. 读取 WarmupTask 与 DataSet；DataSet 非 `Ready` 时写 `Condition DataSetNotReady` 并返回。做什么：拿到两个 CR；为什么：DataSet 不 Ready 说明数据侧还有问题，WarmupTask 不能往下走。
2. 校验 `PodDetail.Index` 必须覆盖 `0..PodCount-1` 且不重复；解析消费顺序：若任一 Pod 的 `InitialConsumeOrder` 为空、越界或重复，则忽略全部用户值，按默认切分 `T=totalChunks`，Pod i 取 `[floor(i*T/P), floor((i+1)*T/P))`，块号升序，置 `ConsumeOrderSource=Default` 并发 `ConsumeOrderDefaulted` 事件；否则 `ConsumeOrderSource=Spec`。默认切分要求 `T >= P`，否则 `Condition InvalidSpec=False` 并返回。做什么：确认 Pod 序号正确、消费顺序可用；为什么：消费顺序是预热的核心依据，错了预热就全错。
3. 列出 `TargetRef` 匹配的 Pod 与 Node；Pod 集合与 `PodCount` 不一致时只置 `Condition PodSetMismatch`，继续使用已有 Pod，不创建/重建/扩缩容。做什么：看看哪些机器上有目标 Pod；为什么：Controller 不负责调 Pod 数量，那是调度器的事。
4. 执行 `Filter`；DataSet 无可达节点时写 `NoAccessibleNodes` 并停止下发；结果为空写 `NoCandidates`，返回退避（节点状态可能变化）。做什么：按 §5.4 的规则筛一遍候选节点；为什么：只有过了筛选的节点才值得发预热任务。
5. 冻结本次分配输入：对每个 `(pod,node)` 调 `Submit`，`task_id` 见 §5.9；`chunks` 为该 Pod 消费顺序前 `max(K_i, Cutoff)` 块（显式列表，顺序即位序）。发送失败记 `ErrAgentUnavailable`，节点标记 `Stopped` 并在下一轮重试；永久拒绝（`InvalidArgument/FailedPrecondition` → `ErrPermanent`）记入 `Condition PreheatRejected=False`（reason=`AgentRejected`）并发 Warning 事件，不再重试该节点，见 §7.9。做什么：把预热任务通过 gRPC 发给每台候选节点的 Agent；为什么：这一步是"执行"的起点，失败要能重试也能识别永久错误。
6. 进入 `Preheating`，写 `CandidateNodes`、`StartedAt`（仅首次）。做什么：把状态流转写进 status；为什么：轮询循环后面才能据此知道"哪些 task 该查进度"。

小结：WarmupTask reconcile 完成筛选和下发两桩事——筛完候选节点，发给 Agent 执行。

### 7.3 进度拉取与就绪表

`Poll` 定时拉 Agent 上报的就绪情况，把原始位图翻译成 Controller 侧的状态表：

1. `Poll` 每 `CONTROLLER_POLL_INTERVAL` 遍历所有 `Preheating/Gating` 的 task。做什么：找出哪些 task 需要查进度；为什么：已经 Released 或 Failed 的不需要查。
2. 对实际 `Assignment` 中的每个 `(pod,node)` 调 `Progress`（内部 `GetPreheatStatus`）；返回 `Generation/Seq/ReadyBitmap/Completed/Failed/State/UpdatedAt/Total`，位图按该 `(pod,node)` 请求的 `chunks` 顺序解码。做什么：向每台 Agent 要"我这边哪些块就绪了"；为什么：这是就绪表的原始来源。
3. `ReadyInWindow = popcount(前 K_i 位)`；`RequiredReady` 按 §5.6 整数公式计算；`GlobalDecayScore` 由 §7.6 公式按该 Pod 的 `K_i` 与前 `C` 位计算。做什么：把位图翻译成有意义的数字；为什么：门控判定和评分都要用到这些数。
4. 更新 `ReadinessTable[p][n]` 与该 Pod 在每个预热节点上的 `PodNodeReadiness` 条目（含 `ReadyBlockBitmap`、`ReadyInWindow`、`RequiredReady`、`StartupWindowReadyRate`、`State`）；`LastReportTime` 用 `UpdatedAt`，缺失时用本地时钟。做什么：把翻译好的数写回 CR status；为什么：Gate 判定和 Scheduler 都要看这个。
5. 低于当前 generation 的响应丢弃并记 Debug；同 generation 下 `Seq` 小于已记录值也丢弃。连续 3 次 `ErrAgentUnavailable` 将对应预热节点的条目置 `Failed`，仅影响门控条件②的斜率计算，不阻塞超时降级。做什么：丢弃过期响应、处理 Agent 失联；为什么：避免旧数据覆盖新数据，同时不让单个节点挂掉就阻塞整个门控。

小结：Poll 是 Controller 的心跳——定时更新就绪状态，门控判定就靠这张表。

### 7.4 GWAA 分配

输入为 `ReadinessTable`、已停止节点集合、`spec.preheatFanoutMin` 与 `spec.preheatFanout`；每轮 Poll 后重算。GWAA 先按 §5.5 算出每个 Pod 的目标集合与实际 `Assignment`，不决定最终落点。分配变化时：对实际 `Assignment` 中新增的 `(pod,node)` 配对调 `Submit` 或 `Update`，对不再需要的配对调 `Cancel`，未变化的配对不重复调用。被清理的节点同时记录 `prune_reason`（如 `out_of_target`、`low_signal`、`target_shrink`）。分配结果只写 status，不写 Node。

怎么理解这一段：GWAA 在"预热过程中可能动态调整——某个节点缓存跟不上了、某个节点 Agent 停了，都会触发重算。但它只影响"哪个 Pod 去哪台 Agent 预热"，不影响"训练 Pod 最终落在哪台机器"。

### 7.5 门控与放行

四步，按"组装状态 → 判定 → 放行 → 冻结"的顺序：

1. 组装 `PodGateState`：`AssignedNodes` 取该 Pod 的实际预热节点集合（正常在 `preheatFanoutMin` 到 `preheatFanout` 之间，实际以 `Assignment` 为准；`MinUnmet` 时可低于 min），`ReadyByNode` 取各预热节点的窗口就绪数，`RequiredReady` 按 §5.6 整数公式计算，`Rate` 取集合内 `ReadyByNode[node] / K_i` 的最大值；`FirstReadyAt` 取自 status `Conditions` 中类型为 `FirstReady` 的 `LastTransitionTime`（首次出现任一 Pod 在任一预热节点上 `Ready >= RequiredReady` 时写入，之后不再更新）。做什么：把 status 里的分散字段拼成 Gate 函数需要的输入结构；为什么：Gate.Evaluate 吃一个统一的 Input struct。
2. `Evaluate` 返回 `Hold` 时不写 Node、不摘 Gate，`RequeueAfter = PollInterval`。做什么：判定能不能放行；为什么：Hold 时什么都不做，等下次 Poll 再来判定。
3. `Released/Degraded` 时：
   a. 对每个预热节点，计算在该节点上预热的本 task 各 Pod 的 `S(node)`（各 Pod 用各自 `K_i`），覆盖实际 `Assignment` 的 P×actual 配对（不是 P×max）；写本 task 自己的 Node annotation 键（§6.2），只读改写该键、不覆盖其他 task 的键；
   b. 逐个 Pod patch 移除 `traincache.io/warmup` gate（已移除则跳过）；
   c. 写 `GateDecision{State,Reason,DecidedAt,PodRates}` 与 `Phase=Released/Degraded`；
   d. 冻结评分：此后 generation 不变则不再改写本 task 的 annotation。
   做什么：放行三件事同时发生——写分数、摘门、写判定；为什么：三件事要在一次 reconcile 里全部完成，不能摘了门还没写分数。
4. 步骤 a 失败则整体重试，不摘 Gate；步骤 b 部分失败时已摘 Pod 不回滚，下一轮继续摘剩余 Pod（**幂等**）。做什么：处理部分失败；为什么：幂等设计保证重复 patch 没问题。

小结：门控放行是"写分数快照 + 摘 SchedulingGate"的原子动作，失败只整体重试不部分放行。

### 7.6 评分计算

按 `(pod,node)` 计算，使用该 Pod 自己的 `K_i`。对 Pod 的消费顺序位置 `i`（0 起）：`w(i)=1 (i<min(K_i,C))`；`w(i)=0.5^((i-K_i)/H) (K_i<=i<C)`；`w(i)=0 (i>=C)`。`S = round(100 * Σ(w(i)*ready(i)) / Σw(i))`；`Σw(i)=0` 时 `S=0`。位图缺失的位按 0 计；`K_i >= C` 时平台段截到 `C`，无衰减段。

怎么理解这个分数：`w(i)` 是权重函数——窗口内前 `K_i` 块权重都是 1（平台段），后面衰减段按半衰期衰减到截断距离 C 就归零。`S` 等于 100 乘以"加权已就绪量 / 加权总量"。权重这么分的原因是：启动窗口里的块最影响启动速度，给满权重；后面的块影响渐进降低。

小结：评分是"窗口内加权就绪比例"，直接供 Scheduler 打分调权。

### 7.7 调度

Scheduler 收到 `(Pod, Node)`：Pod 注解 `warmup-task` + `pod-index` → `scorefmt.Key(ns,name)` → 读 Node 上该键的 `p[podIndex]`；`Score` 返回该分数，`NormalizeScore` 归一化。键缺失、条目缺失、JSON 损坏、`task` 不匹配或超 TTL → 0。

一句话：Scheduler 只做"查表拿分"，算分那摊事在 Controller 放行时就做完了。

### 7.8 落点兜底

Controller 监听 Pod 的 `spec.nodeName`：落在该 Pod 的实际预热节点集合（实际 `Assignment`）内时，只把 `ActualNode` 回填到各条 `PodNodeReadiness`；落在集合之外时：
- 写各条 `PodNodeReadiness.ActualNode`、`Event NodeDeviation`；
- 对实际节点 `Submit` 同一 Pod 的窗口（优先级 P0），不取消原有预热节点；
- 不重新门控（Pod 已放行），失败只影响该 Pod 的读路径命中率，由 Agent 回源兜底。

为什么需要兜底：Scheduler 按分数调权选的 Node 可能不在预热节点集合里——分数只是权重，不是硬约束。兜底动作是"额外补一份 P0 预热"，但不重新走门控流程。

### 7.9 异常与降级

下面这张表列出了所有可能的异常场景和对应的处理方式：

| 场景                         | 行为                                                                                           |
|------------------------------|------------------------------------------------------------------------------------------------|
| Agent 不可达                 | 节点标记 Stopped，退避重试；全部不可达且 `t >= TMax` → `Degraded` 放行                         |
| Agent 永久拒绝               | `InvalidArgument/FailedPrecondition` 映射 `ErrPermanent`：写 `Condition PreheatRejected=False`（reason=`AgentRejected`）并发 Warning 事件；该节点不再重试，其余节点继续；全部候选被拒时不推进门控，仍由 `TMax` 兜底降级 |
| DataSet 失效                 | WarmupTask 停止下发，`Condition DataSetNotReady`，不推进门控                                   |
| 可达节点为空                 | `Condition NoAccessibleNodes`，停止下发；已有任务可 `Cancel`，门控仍受 `TMax` 降级约束         |
| Pod 集合与 `podCount` 不一致 | 只置 `Condition PodSetMismatch`，不创建/重建/扩缩容，继续使用现有 Pod                          |
| 消费顺序非法                 | 忽略全部用户值，按默认切分并 `ConsumeOrderDefaulted`；`T < P` 时 `Condition InvalidSpec=False` |
| Webhook 未注入               | `Condition GateInjectionDegraded`，不阻塞其他 Pod；该 Pod 无 gate，直接调度                    |
| Node annotation 写失败       | 不摘 Gate，退避重试（只重写本 task 的键）                                                      |
| Controller 重启              | 全部状态从 CRD/Node annotation 重建；rateHistory 丢失，条件②重新积累                           |
| 重复 reconcile               | 全量重算 + 幂等 patch；Submit/Cancel 幂等键保证不重复建任务                                    |

所有降级最终都指向 `TMax` 兜底——等超时必放行，不会永远卡着。

## 9. 日志与可观测性设计

### 9.1 硬性要求

> 新模块核心代码的每个关键位置必须记录结构化日志，并随对应里程碑一起验收；没有日志断言测试的里程碑不判通过。日志**不得**改变业务逻辑、接口、数据格式与运行行为。

### 9.2 基础设施

- 日志库：标准库 `log/slog`，与 agent 一致，`JSONHandler(os.Stderr)`，`cmd/*/main.go` 各初始化一次。
- `internal/logging` 只做三件事：`New(level) *slog.Logger`、`Into(ctx, l) context.Context`、`From(ctx) *slog.Logger`（缺失时返回 `slog.Default()`）。不引入第三方。
- 每个 reconcile/HTTP 请求生成 `request_id`（`<uid>/<generation>/<unixnano>`），放入 context 与所有日志；无分布式 traceId，跨进程关联用 `task_id + node + generation`。
- 级别：Info=状态迁移、放行、筛选结果、任务完成；Warn=降级、重试、跳过、未收敛；Error=reconcile 返回 error、RPC 永久失败；Debug=逐块/逐节点评分明细，默认关闭。

### 9.3 必记日志点

这张表列出了哪些位置必须打日志、什么级别、必须带哪些字段：

| 位置                      | 级别       | 必带字段                                                                               |
|---------------------------|------------|----------------------------------------------------------------------------------------|
| 每个 Reconcile 入口/出口  | Info       | `component,dataset_or_warmup_task,request_id,generation,duration_ms`                   |
| spec 校验失败             | Warn       | 上述 + `reason,err`                                                                    |
| 快照/存储校验失败         | Warn/Error | `dataset,snapshot,err`                                                                 |
| 候选筛选结果              | Info       | `warmup_task,pod,node,reason`（汇总计数）                                              |
| gRPC Submit/Update/Cancel | Info       | `warmup_task,task_id,pod,node,generation`                                              |
| gRPC 失败/重试            | Warn       | 上述 + `attempt,err`                                                                   |
| 进度轮询结果变化          | Debug      | `task_id,node,generation,seq,ready`                                                    |
| GWAA 分配变化/未收敛      | Info/Warn  | `warmup_task,assign,rounds,reason`                                                     |
| 消费顺序解析/默认切分     | Info       | `warmup_task,consume_order_source,reason`；默认切分同时发 `ConsumeOrderDefaulted` 事件 |
| 门控判定                  | Info       | `warmup_task,state,reason,rates,required`                                              |
| Gate 注入/摘除            | Info       | `warmup_task,pod,pod_index,node,request_id`                                            |
| Node annotation 写入      | Info       | `warmup_task,node,annotation_key,generation,entries`                                   |
| 评分计算                  | Debug      | `warmup_task,pod,node,score`                                                           |
| Scheduler 打分            | Debug      | `pod,node,annotation_key,score,stale`                                                  |
| Webhook 拒绝/跳过         | Warn       | `pod,namespace,reason`                                                                 |
| 降级/故障恢复             | Warn       | `component,reason,state`                                                               |

### 9.4 脱敏与性能

- **禁止**记录 Secret 内容、accessKey/secretKey、完整凭据 URL。
- `path`/`chunk`/`fp` 等高基数维度只进 Debug；Info 聚合到 dataset/task 维度。
- 日志调用**不得**在锁内做格式化之外的 I/O；`From(ctx)` 缺失时退化为全局 logger，不 panic。

### 9.5 指标（Prometheus，独立 Registry）

controller-manager 使用独立 Registry，经 `metricsserver.Options.ExtraHandlers` 暴露在 `/metrics/traincache`（内置 `/metrics` 仍归 controller-runtime）。scheduler 是独立进程，自建 Registry 并在 `CONTROLLER_METRICS_ADDR` 上暴露同一路径。所有标签值必须来自固定枚举；**禁止**把 `err.Error()`、Pod/Node/task 名、UID 等无界值放进标签。

| Family | 类型 | 标签 | 发射点 / 语义 |
| --- | --- | --- | --- |
| `traincache_controller_reconcile_total` | Counter | `controller` ∈ `dataset\|warmup\|warmup-degraded`；`result` ∈ `success\|error\|requeue` | 每个 Reconcile 退出时 +1；优先级 err≠nil → error，否则 RequeueAfter>0 → requeue，否则 success |
| `traincache_controller_reconcile_duration_seconds` | Histogram | `controller` | 同上，defer 覆盖所有返回路径（含 NotFound/DeletionTimestamp） |
| `traincache_controller_candidate_nodes` | Histogram | `dataset` = `<namespace>/<name>` | 候选节点筛选完成后观测 `len(candidates)` |
| `traincache_controller_preheat_rpc_total` | Counter | `op` ∈ `submit\|update\|cancel`；`result` ∈ `ok\|permanent\|unavailable` | 每次 Agent RPC 调用点 +1；`permanent` 对应 `ErrPermanent`，其余失败归 `unavailable` |
| `traincache_controller_gate_tasks` | Gauge | `state` ∈ `hold\|released\|degraded` | 首次门控评估起 Inc/Dec 维护；任务删除或进入终态时 Dec，重复状态不重复计数 |
| `traincache_controller_gate_hold_duration_seconds` | Histogram | 无 | 仅在离开 Hold（Released/Degraded）时观测一次 |
| `traincache_controller_agent_poll_total` | Counter | `result` ∈ `ok\|unavailable\|stale\|error` | 每次 `GetPreheatStatus` 轮询 +1；generation/seq 回退被丢弃记 `stale`，响应解析失败记 `error` |
| `traincache_controller_pods_per_node` | Histogram | 无 | 每次 GWAA 计算后对 `PreheatSet` 每个 node 观测 `len(pods)`；按预热配对计数，fanout 接线后该值可大于 1 |
| `traincache_controller_gwaa_unassigned_pods` | Gauge | `dataset` | 每次 GWAA 计算后 Set 为 `len(UnassignedPods)` |
| `traincache_controller_gwaa_fallback_total` | Counter | 无 | GWAA 不收敛、回退到首个贪心结果时 +1 |
| `traincache_scheduler_score_total` | Counter | `result` ∈ `ok\|no_task_ref\|invalid_task_ref\|no_pod_index\|invalid_pod_index\|no_annotation\|invalid_value\|task_mismatch\|stale_generation\|expired\|no_pod_entry` | scheduler 进程 `Evaluate` 的固定分支枚举 |

与原设计的差异：删除 `controller_ready_blocks{warmup_task,pod,node}`（P×N 集合基数）与 `controller_gate_state{warmup_task}`（每任务一条序列）；ready 明细改由 status 与日志排查，门控状态改用有界计数的 `gate_tasks{state}`。`controller_candidates` 更名为 `controller_candidate_nodes{dataset}`，`dataset` 采用 `<namespace>/<name>` 以避免跨命名空间碰撞。新增 poll 与 GWAA 指标以覆盖轮询与分配回退。高基数标签**禁止**进指标。

### 9.6 排查路径

门控不放行 → 查 `GateDecision.PodRates` 与 `PodNodeReadiness` → 查 `controller_preheat_rpc_total` → 查 Agent `GetPreheatStatus`（`generation/seq/ready_bitmap`）→ 查 Agent 自身指标。落点偏离 → 查 Pod 的 `ActualNode` 与 `NodeDeviation` 事件。

## 10. 风险与约束

- **R1 调度器依赖重量级。** 自定义 kube-scheduler 镜像需引入 `k8s.io/kubernetes`（或等价 framework runtime），版本必须与集群 minor 对齐；未对齐会导致插件 ABI 不兼容。见 Q1。
- **R2 Webhook 是关键路径。** 未注入 gate 时门控失效但不阻塞训练；`failurePolicy=Ignore` 是有意选择，代价是静默降级，依赖 `GateInjectionDegraded` 条件兜底。
- **R3 workspace 依赖。** 新 module 的跨 module import 依赖 `go.work`，`GOWORK=off` 构建会失败；与现有 agent→core 的做法一致，不引入 replace。
- **R4 CRD status 体积。** `ReadinessTable` 随 P×N 增长，`PodNodeReadiness` 随 P×K 增长（K 不超过 `preheatFanout`）；需在上限（P≤64、N≤256、K 为小常量）内测试；超出应改为只存表不存明细。
- **R5 内存态丢失。** rateHistory 随重启清空，条件②在重启后需重新积累，可能推迟放行，但不会错误放行。
- **R6 Agent 增量未落地。** Controller 依赖 7.x 新增 RPC；在 Agent 实现前，集成测试只能用 fake server。
- **R7 时钟。** 所有比较使用 `r.Now()` 注入的同一时钟；CRD 时间字段统一 UTC RFC3339。

## 11. 验收标准（总闸）

这 14 条全过才算完成。逐条读一遍，每条对应哪些里程碑在第二列已标明（§2）。

1. 跑通基本编译和测试：`cd controller && go build ./... && go vet ./... && go test ./... -race -count=1` 全绿，gofmt 干净。
2. CRD 生成链路正确：两个 CRD 可由 `controller-gen` 从类型重新生成，产物与提交一致；只开 `status`、无 `scale`；`podCount`/`dataSetRef` 的 CEL 不可变校验生效；Controller 不创建 Job/Pod。
3. 基线需求全部有落点：8.0 基线中的 D1–D8 每条在代码中有唯一落点，且 `docs/8.3 decisions.md` 有对应 D 编号。
4. DataSet 校验覆盖：字段非法、Secret 缺失、快照不存在、blockLayout 累计正确；`s3-access` 标签解析、`AccessibleNodeSelector` 收窄、无匹配节点时 `NoAccessibleNodes` 且停止下发。
5. 门控整数边界公式正确：`K=8, threshold=0.8 → required=6`；`threshold>0` 且 `floor` 为 0 时取 1；`threshold=0` 时 required=0；预热节点集合取实际 `Assignment`（正常在 `[preheatFanoutMin, preheatFanout]` 内），其中任一节点达到 `required_i` 即该 Pod 达标；条件②使用连续 rate；`StartupWindowReadyRate` 不参与判定；`t >= TMax` 必放行；全 Pod 达标必放行。
6. GWAA 算法正确性：固定种子下可复现、不同种子下输出合法；目标集合满足 `S_min=ceil(0.25×K_i)`、0.5 保留线、clamp 与强制下限规则；每个 Pod 的 status 条数等于实际 `Assignment` 节点数，正常在 `[minFanout, maxFanout]` 内，冲突/容量/兜底可低于 min 且 `MinUnmet=true`，任何情况下 ≤max；且除集合外兜底外 `Assignment ⊆ TargetSet`；冲突、并列（含随机回退）、不可收敛、集合外兜底、无可行节点五种情形均有测试，且不收敛保留首个贪心结果。
7. Node annotation 编解码正确：每 task 独立键：`Key(ns,name)` 往返一致、`namePrefix` 截断/去尾、`hash12` 稳定、键名 ≤ 52；两 task 共节点互不影响；过期/缺失/解析失败/`task` 不匹配时 Scheduler 返回 0 且不拒绝调度。
8. 消费顺序解析正确：任一 Pod 非法时整组回退默认切分并置 `ConsumeOrderSource=Default`、发 `ConsumeOrderDefaulted`；`T < P` 校验失败；`PodDetail.Index` 覆盖校验；Pod 集合不一致只置 `PodSetMismatch` 不修复。
9. Webhook 注入幂等：无匹配 task 时不注入；Pod 序号解析失败时有事件与条件。
10. 日志断言覆盖：每个里程碑的日志点有对应断言测试（至少一条 `slog` 输出捕获测试），覆盖 `annotation_key`、`generation`、`seq`、`consume_order_source`；M14 起同时断言 `fanout_min`、`fanout_max`、`fanout_target`、`fanout_actual`、`low_signal`、`forced_by_min`、`min_unmet`、`fallback_out_of_target`、`prune_reason`。
11. core/agent 代码不修改：不修改 `core/`、`agent/` 业务代码；对 `agent/api/agent.proto` 的修改仅限 §12 列出的增量。
12. 计划文档覆盖完整：`docs/8.2 plan.md` 的覆盖判断中不存在未标注的"缺失"项；标注为"部分覆盖"的项有明确后续任务。
13. M14 上限+下限行为正确：`preheatFanoutMin <= preheatFanout` 被校验；`min > 可行节点数` 时置 `MinUnmet`；冲突导致实际认领低于 min 时同样置 `MinUnmet`，status 条数跟随实际 `Assignment`；低信号取可行节点数封顶后的上限；`fanout=1, min=1` 与 M13 行为一致；放行快照只覆盖实际 `Assignment` 的 P×actual 配对。
14. 冲突下限用例正确：2 Pod、3 节点、`preheatFanoutMin=2`、`preheatFanout=2`、`preheatFanout=2`、`allowMultiPodPerNode=false`、两 Pod 缓存分布相同。允许一个 Pod 实际只认领 1 个节点；该 Pod `MinUnmet=true`、`PodNodeReadiness` 1 条、日志同时出现 `min_unmet` 与 `fallback_out_of_target`。任何 Pod 的条数都不超过 max。

## 12. 跨模块增量

### 12.1 Agent proto 增量（并入 7.1 附录 A）

`agent/api/agent.proto` 在现有 `traincache.agent.v1.PreheatService` 上做最小增量（进度复用 `GetPreheatStatus`）：

```proto
// 8.x 增量（2026-10-20）：在现有 traincache.agent.v1.PreheatService 上最小增量扩展。
// 进度查询复用 GetPreheatStatus；不新增 GetPreheatProgress。

message SubmitPreheatRequest {
  // 字段 1..7 保持现状
  uint64 generation = 8;  // 任务代际；0 表示未提供
}

message PreheatStatus {
  // 字段 1..11 保持现状
  uint64 generation = 12;   // 任务代际
  uint64 seq = 13;          // 位图变更序号，单调递增
  bytes ready_bitmap = 14;  // 位 i 对应请求 chunks 第 i 项；1=已落盘且校验通过
}

message UpdatePreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;         // 必须 >= Agent 当前代际
  repeated ChunkRef chunks = 4;  // 新的完整块列表，同时定义位序
  PreheatPriority priority = 5;
}

message UpdatePreheatResponse {
  bool accepted = 1;
  string message = 2;
}

message CancelPreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;
}

message CancelPreheatResponse {
  bool accepted = 1;
}

service PreheatService {
  // 已有
  rpc SubmitPreheat(SubmitPreheatRequest) returns (SubmitPreheatResponse);
  rpc GetPreheatStatus(GetPreheatStatusRequest) returns (PreheatStatus);
  // 新增
  rpc UpdatePreheat(UpdatePreheatRequest) returns (UpdatePreheatResponse);
  rpc CancelPreheat(CancelPreheatRequest) returns (CancelPreheatResponse);
}
```

`SubmitPreheatRequest.snapshot_id`（字段 4）恒为空：Controller **不得**把 DataSet status 中解析出的具体快照 ID 下发，Submit 与 Update 两条下发路径均保持空值（`UpdatePreheatRequest` 本身无该字段）。理由：Agent 自行跟随 CURRENT 并按需加载 manifest 分片，避免任务键随快照推进漂移；非空值在 7.x M3 Agent 侧返回 `InvalidArgument`。

语义：`task_id` 幂等；Agent 对低于已接受 `generation` 的请求返回 `FailedPrecondition`；`Cancel` 后同名同 generation 再 `Submit` 视为新任务；位图长度必须恰好 `ceil(len(chunks)/8)`，位序由请求 `chunks` 定义。`ReportBlocks` 保持 `Unimplemented`，8.x 不使用推送模型。
