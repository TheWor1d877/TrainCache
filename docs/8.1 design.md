# 日志与可观测性 · Design

> 本文承接 `docs/7.1 design.md` §9 与 `docs/6.1 design.md` §5.8：那两份文档已列过日志点表和指标清单，这里不重抄，只解决三层怎么贯通、契约怎么落地。排期见 `8.2 plan.md`，决策与取舍见 `8.3 decisions.md`，使用与运维手册见 `9.5 日志与监控使用说明.md`。

## 1. 设计目标与原则

结论先行：控制平面的结构化日志已经能用（slog JSON 输出 + context logger + 7.1 §9.3 十六个日志点 + M12 日志断言）；Agent 有日志，但各写各的，缺一份统一契约；DataLoader 连生产实现都没有，更谈不上日志契约，是三层里真正的断点。所以眼下最该补四件事：公共字段、关联 ID、采样限流、采集链路。日志条数本身反倒不急。

三条原则：

1. 日志是运维接口，写给运行系统的人查。一个字段只要被 runbook、看板或 CI 引用过，就成了契约：以后只能加，不能改。
2. 结构化、可关联、低基数、可断言。每条日志都要能被机器按 `component + task + node + reason` 聚合。高基数（取值多到数不过来、会让检索和指标爆炸的维度，比如文件路径）只允许出现在 Debug。
3. 事件、日志、指标各管各的，谁也不能顶替谁。

| 信号             | 适合承载                                                         | 不适合承载               | 本项目落点                                                                                                        |
|------------------|------------------------------------------------------------------|--------------------------|-------------------------------------------------------------------------------------------------------------------|
| 日志             | 单次决策上下文、错误原文、高基数字段（path/chunk/fp/request_id） | 计数、趋势、告警阈值     | 全部 Go 进程 stdout JSON；DataLoader 设计为 stdout JSON                                                           |
| 指标             | 计数、比率、分位、容量、告警                                     | 单任务排查、任意维度切片 | 控制平面 `controller/internal/metrics`、Agent `agent/metrics`；各进程 `/metrics` 由 Prometheus 抓取，Grafana 查询 |
| Kubernetes Event | 对象生命周期与面向使用者的原因（`kubectl describe` 可见）        | 高频明细、跨进程关联     | 门控放行/降级、默认切分、落点偏离、注入降级                                                                       |

一条信息该进哪个信号，按这个规则判：要计数、告警、跨 Pod 聚合 → 指标；要让用户在 `kubectl describe` 里看到对象为什么不动 → Event；其余排查上下文 → 日志。两条禁令：日志不能当告警阈值用；`request_id`/`pod`/`task_id` 不许进指标标签，这三个取值太多，会把指标时间序列撑爆。

关联的总目标（逻辑层，具体机制见 §5）：给定一个 Pod，能在中心存储里用 `warmup_task + pod_index` 把 controller → Agent → DataLoader 三段日志一次拉出来。

概述：DataLoader 是断点；日志是契约，先把公共字段定下来，再谈别的。

## 3. 统一日志契约

### 3.1 公共字段

字段契约自 ADR-007~010 起冻结为 v1（ADR=架构决策记录，条目见 7.3）：`log_schema_version` 从 1 起只增不改；新增字段允许为空；删字段或改含义必须走弃用周期，至少保留一个小版本并新旧双写。脱敏统一交给 `core/logging` 的 `Redact` / `RedactURL`（ADR-007），controller 和 Agent 共用同一套实现，谁也不许自己另写一套；`Redact`/`RedactURL` 与单测在仓库，两端共用；接线状态见 `TODO.md`（A）。

| 字段                                   | 类型       | 出现层               | 约束                                                                        |
|----------------------------------------|------------|----------------------|-----------------------------------------------------------------------------|
| `time`、`level`、`msg`                 | slog 内置  | 全部                 | `level` 取值 `DEBUG/INFO/WARN/ERROR`                                        |
| `log_schema_version`                   | int        | 全部                 | 从 1 起；只增不改                                                           |
| `component`                            | string     | 全部                 | 固定枚举：`controller-manager/webhook/scheduler/agentd/dataloader`          |
| `version`                              | string     | 全部                 | 构建版本，启动时写一次                                                      |
| `cluster`、`namespace`                 | string     | 控制平面、Agent      | 由采集侧补齐或启动配置注入；Agent 默认只有 `node`                           |
| `node`                                 | string     | 全部                 | Agent 必填（`NODE_NAME`）；控制平面调用 Agent 时必填                        |
| `pod`、`pod_index`                     | string/int | 控制平面、DataLoader | `pod` 用 `<namespace>/<name>`；`pod_index` 与 WarmupTask 绑定               |
| `warmup_task`                          | string     | 控制平面、DataLoader | `<namespace>/<name>`，沿用 8.1 现有字段名                                   |
| `task_id`                              | string     | Agent、DataLoader    | Agent 预取任务 ID；与 `warmup_task` 是多对一关系，不合并                    |
| `dataset`                              | string     | 全部                 | 已做白名单归并；白名单外写 `other`                                          |
| `snapshot`                             | string     | 控制平面、Agent      | 快照 ID；不写完整对象路径                                                   |
| `generation`、`seq`                    | uint64     | 控制平面、Agent      | 预取代际与位图序号；用于判断陈旧                                            |
| `request_id`                           | string     | 控制平面、Agent      | 控制平面格式 `<uid>/<generation>/<unixnano>`；Agent 从 gRPC metadata 继承   |
| `rpc`                                  | string     | 控制平面、Agent      | `SubmitPreheat/UpdatePreheat/CancelPreheat/GetPreheatStatus`                |
| `duration_ms`                          | int64      | 全部                 | 只在操作结束时出现                                                          |
| `result`                               | string     | 全部                 | 固定枚举：`ok/error/requeue/skipped/stale/degraded`                         |
| `err`                                  | string     | 全部                 | 错误原文，必须经脱敏；禁止整段堆栈进 Info                                   |
| `err_class`                            | string     | 全部                 | 固定枚举：`invalid_spec/not_found/unavailable/permanent/corrupt/io/timeout` |
| `reason`、`state`、`phase`、`priority` | string     | 全部                 | 取值来自各模块冻结枚举                                                      |
| `sampled`、`sample_rate`               | bool/float | 全部                 | 被采样时标明，便于估算真实量                                                |

表里 `dataset` 那行的"白名单"指：只允许列出来的取值原样进日志，白名单外的一律归并成 `other`，防止取值无限增长。

字段 schema 示例（仅示公共部分，业务字段另加）：

```json
{
  "time": "2026-10-21T10:00:00.123Z",
  "level": "INFO",
  "msg": "gate evaluated",
  "log_schema_version": 1,
  "component": "controller-manager",
  "version": "v8.3.0",
  "namespace": "train",
  "warmup_task": "train/wt-llm-7b",
  "dataset": "train/llm-7b",
  "node": "gpu-node-12",
  "generation": 7,
  "request_id": "6f1c.../7/1761031200123000000",
  "state": "Hold",
  "reason": "rate_below_required",
  "duration_ms": 12,
  "result": "ok",
  "sampled": false
}
```

命名与兼容规则：

- 固定小写 snake_case；`warmup_task` 与 `task_id` 保持现有语义，不新造 `task` 字段做二次抽象。
- 只增不改：新增字段可空；删除或改义必须走弃用周期，至少保留一个小版本并双写。
- Info 禁止高基数：`path`、`chunk`、`fp`、`pod_uid`、完整对象 URL 只在 Debug。`task_id`/`request_id` 允许进 Info，因为它们用于关联，但不得进指标标签。
- `err` 与 `err_class` 必须成对出现；`err` 给人看，`err_class` 给聚合与告警。

概述：字段表就是合同，版本号只往上走，高基数字段一律摁在 Debug。

### 3.2 级别策略

级别、采样与限流策略同样自 ADR-007~010 起冻结为 v1：只增不改；Warn/Error 永不采样（ADR-006），采样只落在 Debug 和 Info 头上。

| 级别  | 语义                                   | 本项目例子                                                  |
|-------|----------------------------------------|-------------------------------------------------------------|
| Debug | 逐块、逐样本、逐节点评分明细；默认关闭 | `pod score detail`、每块下载/校验成功、每 batch 延迟        |
| Info  | 状态迁移、决策结果、周期汇总、任务完成 | reconcile 起止、gate evaluated、任务 DONE、每分钟预取汇总   |
| Warn  | 可恢复异常、重试、跳过、未收敛、降级   | Agent 不可达、快照刷新失败保持旧映射、GWAA 未收敛、淘汰失败 |
| Error | 需人工介入                             | 永久拒绝、状态写失败、磁盘超危险线、采集链路自身失败        |

两个常见错误要避开：预期内的跳过（比如没有 WarmupTask 的 Pod）不能写成 Error；节点磁盘快写满这种事，只写一条 Warn 不发指标也不行，指标必须同时有。

概述：Debug 看明细、Info 看状态、Warn 看可恢复异常、Error 留给要人介入的事。

### 3.3 采样与限流

高频路径必须先聚合再落盘，每块、每帧都写一条 Info 是被禁止的：

| 路径                    | 默认策略                                                       |
|-------------------------|----------------------------------------------------------------|
| Agent 逐块下载/校验成功 | 不逐块记；每 60s 一条 Info 汇总（块数、字节、失败数、P50/P99） |
| Agent 缓存命中/未命中   | 指标为主；命中明细 Debug 且 1/100 采样                         |
| hooksock 每帧           | 不记 Info；只记格式错误（Warn）与启动；正常帧计数进指标        |
| DataLoader 每 batch     | 每 60s 一条 Info 分位汇总；单 batch 明细 Debug 1/100           |
| 淘汰/GC 每块            | 每轮一条 Info；单块 Debug 1/100                                |
| 控制平面轮询            | 状态变化记 Debug；无变化不记                                   |

限流机制：

- 进程内令牌桶（按固定速率攒额度，有额度才放行一条日志）：控制平面默认 100 行/秒、突发 200；Agent 默认 200 行/秒、突发 400；超限先丢 Debug，再丢 Info，Warn/Error 永不丢，丢弃计数进 `log_dropped_total`。
- 去重窗口：相同 `(component, event, node, task_id, reason)` 60s 内只出一条，后续在下一窗口带 `suppressed` 计数。
- 先采样后格式化：采样判断在读 `path/chunk` 之前完成，别为了一条注定被丢的日志去拼字符串。
- 采样配置项：`TRAINCACHE_LOG_SAMPLE_RATE`（Info，默认 1.0）、`TRAINCACHE_LOG_DEBUG_SAMPLE_RATE`（Debug，默认 0.01）。令牌桶速率、去重窗口、60s 汇总窗口、1/100 采样率都是固定值，暂不开放配置。

概述：高频路径只留汇总，限流先丢低级别的，Warn/Error 一条不丢。

### 3.4 脱敏红线

以下内容禁止出现在任何日志里：Secret 内容；`accessKey/secretKey/token/Authorization`；带签名的凭据 URL（查询参数里含 `X-Amz-Signature`、`Signature`、`Expires` 等的）；训练样本内容、张量数据、文件正文；完整对象存储路径（Info 级）。

对象存储端点只记 host；路径在 Debug 也只记截断前缀或 `path_hash`。所有 `err` 在落盘前过一层 `redact`（处理 URL userinfo、查询串、常见 key 名），脱敏实现单一、两端共用的规则见 §3.1。测试用哨兵 Secret 做负向断言，全量日志里不能出现。Agent 已有"训练 Pod 不接对象存储、不持凭证"的边界（6.3 D44），日志不能变成新的凭证泄漏口。

概述：凭证、样本、签名 URL 一律不落盘，脱敏统一走 `redact`。

### 4.3 DataLoader（冻结契约）

以下契约随训练侧钩子适配器一起落地，顺序不能反，不能先把日志写了再回头补契约；交付状态见 `TODO.md`（B）。本节字段、env 名与缺失降级行为冻结为 v1；`warmup_task` 的适用范围按 ADR-008 为控制平面 + DataLoader。

| 位置                  | 触发条件                              | 级别            | 必带字段                                                                                                       | 用途               |
|-----------------------|---------------------------------------|-----------------|----------------------------------------------------------------------------------------------------------------|--------------------|
| 启动上下文            | 进程/worker 启动                      | Info            | `component=dataloader,warmup_task,pod,pod_index,dataset,generation_at_start,hook_sock,log_schema_version`      | 建立与 Pod 的关联  |
| 数据源选择            | 每 batch 或每样本组                   | Debug/汇总 Info | `dataset,source=cas\|origin,phase,stage_id`                                                                    | 判断是否绕过缓存   |
| miss 与 prefetch 命中 | 缺块或命中                            | Debug/采样      | `dataset,chunk,reason=absent\|corrupt,prefetch_ready,wait_ms`                                                  | 归因到 Agent 预取  |
| 单 batch 延迟分位     | 每 60s                                | Info            | `dataset,phase,batches,p50_ms,p95_ms,p99_ms,stall_ms`                                                          | 训练侧真实体感     |
| 异常与降级            | 钩子发送失败、socket 不可用、回源失败 | Warn/Error      | `dataset,reason,err_class,fallback`                                                                            | 钩子故障不阻断训练 |
| 退出                  | 正常/异常退出                         | Info            | `dataset,batches,total_wait_ms,unreported_frames`                                                              | 收尾与丢帧核对     |

上下文来源（冻结契约）：

- webhook 在注入 gate/annotation 的同时注入环境变量：`TRAINCACHE_TASK=<ns>/<name>`、`TRAINCACHE_POD_INDEX=<n>`、`TRAINCACHE_DATASET=<ns>/<name>`、`TRAINCACHE_HOOK_SOCK=/run/traincache/agent.sock`。
- `TRAINCACHE_TASK` 是环境变量名，其值就是 warmup task 名，落到日志字段时写 `warmup_task`；日志字段中不出现 `task`（ADR-008）。
- `generation` 无法通过不可变 env 跟随 WarmupTask 更新；Pod 启动时由 webhook 写入 `TRAINCACHE_GENERATION_AT_START`，日志只记该启动值。
- 不引入新的 Pod annotation 读取依赖：DataLoader 只读 env，缺失时记 `context_missing=true` 并降级为仅本地日志，不影响训练。
概述：契约先冻结再实现；DataLoader 只认 env，缺上下文就降级，绝不拖累训练。

## 5. 关联与传播

目标链路一共六跳，每跳标现状和要做的动作：

| 跳 | 载体                                                                                     | 现状               | 动作                                                   |
|----|------------------------------------------------------------------------------------------|--------------------|--------------------------------------------------------|
| 1  | webhook `request_id`（admission UID/0/nano）                                             | 已实现             | 保留                                                   |
| 2  | Pod `traincache.io/warmup-task`、`traincache.io/pod-index`                               | 已实现（7.1 §6.3） | DataLoader 经 env 继承                                 |
| 3  | WarmupTask reconcile `request_id`                                                        | 已实现             | 每次外部调用都带                                       |
| 4  | gRPC metadata：`x-traincache-request-id`、`x-traincache-task`、`x-traincache-generation` | 契约               | Controller 客户端注入；Agent 拦截器写入 context logger |
| 5  | Agent 任务键 `task_id + node + generation`                                               | 已实现             | 保持为跨进程主键                                       |
| 6  | DataLoader env → 日志公共字段                                                            | 契约               | 缺失时 `context_missing=true`                          |

跨进程主键是 `task_id + node + generation`（7.1 §9.2 已明确无分布式 traceId）。`request_id` 由 webhook/WarmupTask reconcile 生成，经 gRPC metadata 传给 Agent（第 4 跳）；ADR-002 的"不出进程"指不引入分布式 traceId。目标查询是"给定一个 Pod，用 `warmup_task + pod_index` 拉出 controller → Agent → DataLoader 三段"，不引入 OpenTelemetry（选型理由见 7.3）。

三种信号的边界：

- 只进指标：计数、比率、分位、队列深度、磁盘利用率、`gate_tasks{state}`、`scheduler_score_total{result}`。这些需要长期趋势与告警，日志只作为样本。
- 只进 Event：`GateReleased/GateDegraded/ConsumeOrderDefaulted/NodeDeviation/WarmupTaskMappingFailed`、对象 condition 变化。它们面向 `kubectl describe`；Info 日志可以再写一份，但 Info 不能成为唯一来源。
- 只进日志：`request_id`、`task_id`、`pod`、`path/chunk/fp`、错误原文、每次决策的分支细节。它们基数高、生命周期短，不进指标也不进 Event。

概述：跨进程主键是 `task_id + node + generation`，六跳的载体与动作见上表。

## 6. 输出与汇总

日志和指标各走一条链路：

```text
容器 stdout/stderr (JSON)
  -> 节点 DaemonSet 采集（fluent-bit）
  -> Loki 3.6.9（标签索引 + 结构化元数据）
  -> Grafana 12.4.13 查询/看板；告警规则读取指标与少量日志计数

指标链路：
traincache-components: controller-manager(:9412)/metrics、agentd(:9411)/metrics、webhook/metrics、scheduler/metrics
traincache-custom-metrics: controller-manager/metrics/traincache、scheduler/metrics/traincache
  -> Prometheus 单实例（15s 抓取） -> Grafana 查询/看板；告警规则读取 Prometheus 指标
```

链路与标签规范：

- 只写 stdout，不写宿主机文件。容器运行时负责轮转，采集器按容器日志路径 tail；Agent 绝不能把日志写进缓存盘（`TRAINCACHE_CACHE_ROOT`），日志和缓存抢同一块盘会两败俱伤。
- 采集器是 fluent-bit：负责 tail 容器日志并转发 Loki；内存占用随缓冲与批量变化，部署前在目标节点实测，不预设精确数字。
- Loki 标签恰为 `cluster`、`namespace`、`component`、`level`、`node`、`stream` 六个且非空；`request_id`、`pod`、`task_id`、`path`、`service_name` 均不在标签中；`detected_level` 是计算字段，不算存储标签。这些高基数字段放 Loki structured metadata 或 JSON 正文，查询时过滤。
- 多租户：以 `namespace` 做逻辑隔离；Loki 多租户可用 `X-Scope-OrgID`，Grafana 按 namespace 做 RBAC。审计日志独立管道，不与业务日志混存。
- 指标链路独立于日志链路，按暴露路径拆两个抓取 job：`traincache-components` 抓 controller-manager（:9412）、agentd（:9411）、webhook、scheduler 的 `/metrics`，覆盖 `traincache` 与 `kube-system` 两个命名空间，6 个 target 全 up；`traincache-custom-metrics` 抓 controller-manager 与 scheduler 的 `/metrics/traincache`，2 个 target 全 up。scheduler 的项目指标只由 custom job 承载：components job 把它的抓取路径重写到 `/metrics/traincache` 后又整体 drop 该组件序列（kube-scheduler 的 `/metrics` 返回 404），避免重复计数；agentd 的项目指标在 `/metrics`，只由 components job 抓取；webhook 没有项目自定义注册表（源码未创建独立 registry、未配 ExtraHandlers），不纳入 custom job，这是有意安排。`traincache_controller_gate_hold_duration_seconds_count` 已能被 Prometheus 查到。Grafana 将 Prometheus 与 Loki 并列为数据源：指标查询走 Prometheus，日志查询走 Loki。指标标签只放有界维度，`request_id`、`pod`、`task_id`、`path` 不进指标标签。
- 指标本版基本不动，唯一明确新增的名字是 `log_dropped_total`。

保留与容量（容量为数量级，不编造精确值）：

- 计算方式：`日原始量 ≈ 进程数 × 每秒行数 × 平均行字节 × 86400`；压缩后通常为原始量的 10%-20%，按 15% 估算。
- 示例：100 个节点、每 Agent 稳态 1 行/秒、每行 500 B -> 约 4.3 GB/日原始、约 0.6 GB/日压缩；控制平面行数远小于此。Debug 全开或逐块日志会让单节点量级上升 10-100 倍，必须依赖采样。
- 保留期：默认 720h（30 天）；`level="DEBUG"` 的流 168h（7 天），通过 Loki `retention_stream` 实现；Event 由 Kubernetes 自身 TTL 管理，中心只保留聚合指标。

> 存储选型（Loki 而非 ES）的理由见 `8.3 decisions.md`。

概述：日志走 fluent-bit → Loki，指标走 Prometheus，两条链互不干扰；容量按公式估，不拍脑袋。

## 7. 管理与维护

- 动态日志级别：控制平面只读 `CONTROLLER_LOG_LEVEL`（`controller/internal/config/config.go`），改级别需重启；Agent 级别启动时固定 `info`。动态级别用 `slog.LevelVar`，载体在 localhost-only 的 `/debug/loglevel` 端点与 ConfigMap 热加载之间二选一（见 `TODO.md`（D）），并记录一次"级别变更"审计日志；禁止对公网暴露该端点。
- 日志即接口的变更流程：字段登记在本文 §3.1；新增字段走 PR 模板勾选；删除/改义必须双写一个小版本并在 runbook 中标注。日志消息 `msg` 也视为稳定标识，CI 断言按 `msg` 查找。
- CI 断言：7.1 §9.3 的每一行至少一个测试。控制平面已有 `m12_logs_assert_test.go`（warmup/webhook/scheduler/dataset）与 `logging_test.go`；Agent 端已有 `agent/svc/m12_logs_assert_test.go`，逐项断言 `msg + 必带字段 + level`；脱敏用哨兵 Secret 做负向断言。测试清单见 `8.4 test.md`。
- 采样配置：`TRAINCACHE_LOG_SAMPLE_RATE`、`TRAINCACHE_LOG_DEBUG_SAMPLE_RATE`；配置变更需重启或热加载，采样率本身写进启动日志。
- 成本控制：默认 Info、Debug 关闭；高频成功路径只留汇总；Loki 保留期按层设置；禁止在 Info 打印完整路径与逐块明细。
- 轮转与磁盘保护：容器运行时配置 `containerLogMaxSize` 与 `containerLogMaxFiles`；采集器设置磁盘缓冲上限与背压，压力下先丢 Debug；Agent 与 DataLoader 不自行写文件日志。
- 审计与普通日志分离：Kubernetes audit 记录 API 访问；应用日志只记录业务决策。不要在应用日志里伪造审计事件，也不要把 Secret 写进 audit 之外的任何日志。

概述：级别按配置调整、字段按流程改、CI 逐点断言、审计与业务日志各走各的管道。

五种常见现象的排查路径，按"先日志、再指标/事件、后 Agent/下游"的顺序查。

| 现象                | 第一查（日志）                                                                         | 第二查（指标/事件）                                                                                    | 第三查（Agent/下游）                                                              | 判定                                                                                                                      |
|---------------------|----------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------|
| 门控不放行          | `gate evaluated` 的 `state/reason/rates/required/gap/slope`；`gate removal incomplete` | `controller_gate_tasks{state="hold"}`、`gate_hold_duration_seconds`；Event `GateReleased/GateDegraded` | `GetPreheatStatus` 的 `generation/seq/ready_bitmap`；`preheat_rpc_total`          | `rates` 未达 `required` -> 预取未就绪；`reason=score_write_failed` -> 看 annotation 冲突；长时间 Hold -> 查 Agent 进度    |
| Agent 不可达        | `agent submit failed` / `agent update failed` 的 `node,err,err_class`                  | `controller_preheat_rpc_total{result="unavailable"}`、`traincache_agent_up`                            | Agent Pod 日志启动/监听失败；节点网络与 DaemonSet 状态                            | `permanent` -> 请求/代际问题；`unavailable` -> 网络、Pod 未就绪或 gRPC 端口                                               |
| DataLoader 慢       | DataLoader 每 60s 分位日志的 `p99_ms/stall_ms`；Agent `read_stall` 归因                | `traincache_read_stall_seconds{phase,cause}`、`hook_read_miss_total`、`prefetch_lead_blocks`           | `fetch_requests_total{result,reason}`、`fetch_inflight_bytes`、`disk_usage_ratio` | `cause=prefetch_lag` -> 预取不够快；`origin_slow` -> 对象存储；`local_slow` -> 本地盘/CPU；`lead_blocks` 为负 -> 消费领先 |

概述：先用日志锁定原因，再用指标确认范围，最后下钻到 Agent 或下游组件。
