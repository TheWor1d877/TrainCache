# 8.1 Controller & Scheduler design

> 本文是 `docs/8.0 Controller & Scheduler.md`（用户基线，不改动）的实现契约。
> 与基线冲突处一律以本文冻结的约定为准，新增/修正均登记在 `docs/8.3 decisions.md`。
> 跨模块增量见 §12，并已追加到 `docs/7.1 design.md` 附录 A。

## 1. 模块定位

### 1.1 职责

新增 Go module `traincache/controller`，提供集群控制面三件套：

| 组件                | 职责                                                                                                      |
|---------------------|-----------------------------------------------------------------------------------------------------------|
| `DataSet` 控制器    | 校验数据契约、固化块编号与布局、解析可达节点、校验快照可访问性；只写 status，不触发预热                   |
| `WarmupTask` 控制器 | 筛候选节点、GWAA 分配、按块下发/更新/取消预热、轮询就绪进度、门控判定、放行时冻结评分并写 Node annotation |
| MutatingWebhook     | Pod 创建时注入 SchedulingGate、WarmupTask 引用与 Pod 序号注解，是门控链路的前置条件（基线缺口 G1）        |
| Scheduler 插件      | 只读 Node annotation，实现 `Score` / `NormalizeScore`，返回 0~100                                         |

### 1.2 非目标

- 不介入训练读路径：训练 Pod 经 hostPath 直读本地 CAS，不经过 Controller 或 Agent。
- 不做数据发布：tar 切块与快照提交由 `core/publish` 与 `traincache trainpublish` 负责。
- 不做运行时重预取：epoch/shuffle/curriculum 切换由 Agent 的 `PersistentPrefetcher` 处理，不进入调度路径。
- 不实现 DataLoader/sampler：训练侧只消费 `ConsumeOrder` 与固定 chunk 序号。
- 不实现 Agent 服务端：Agent 侧 gRPC 增量由 7.x 承接（见 §12）。

### 1.3 与已完成模块的关系

| 已有模块            | 复用方式                                                         | 依赖方向           |
|---------------------|------------------------------------------------------------------|--------------------|
| `core/objectstore`  | `NewS3Store` / `Store.Get` 校验 CURRENT、manifest、shard 存在性  | controller → core  |
| `core/index`        | 复用 `Manifest`、`ShardRef`、`Entry`、键布局常量；只读，不写索引 | controller → core  |
| `agent/api/agentpb` | 扩展现有 `PreheatService`，Controller 作为客户端                 | controller → agent |
| `agent/metrics`     | 只参考 family 命名纪律，新建 controller 独立 Registry            | 不复用代码         |
| `agent/cmd/agentd`  | 参考 slog 初始化、信号处理、优雅退出                             | 不复用代码         |

## 3. 总体架构与依赖方向

```
                    kube-apiserver
        ┌───────────────┼────────────────┬──────────────┐
        │               │                │              │
   controller-manager  webhook       kube-scheduler   Node
        │               │                │              │
   ┌────┴────┐          │           TrainCacheScore     │
   │ DataSet │          │           (读 Node annot.)    │
   │ Warmup  │          │                ▲              │
   └────┬────┘          │                │              │
        │  gRPC(南向)   │                │              │
        ▼               │                │              │
   Agent(DaemonSet) ────┴────────────────┴──────────────┘
        │  写 Node annotation(pod 创建前)
        │
   S3 对象存储 / 本地 CAS
```

依赖方向固定为单向：

```
cmd/* → internal/{controller,webhook,scheduler}
internal/controller/* → {api/v1alpha1, gwaa, gate, nodescore, agentclient, storage, config, logging, metrics}
internal/{nodescore,agentclient,webhook,scheduler} → api/v1alpha1
internal/{nodescore,scheduler} → scorefmt
internal/agentclient → agent/api/agentpb
internal/storage → core/{objectstore,index}
api/v1alpha1 → k8s.io/apimachinery only
```

禁止：`api → internal`、`gwaa/gate/scorefmt → k8s 客户端或 core`、`scheduler → controller 内部包`、`internal → cmd`。

## 5. 核心接口（冻结约定）

实现子代理不得私自修改签名；变更需回传 `BLOCKED` 由主对话裁决。

### 5.1 CRD 类型

Group `traincache.io`，Version `v1alpha1`。两个 CRD 均为 Namespaced，跨对象引用只允许同 namespace。只开 `status` 子资源，不定义 `scale`（基线缺口 G9）。`WarmupTaskSpec.podCount` 与 `dataSetRef` 不可变，由 CRD CEL 校验 `self == oldSelf`；Controller 不创建 Job/Pod、不扩缩容、不重建 Pod。`traincache.io/s3-access` 标签由用户/集群管理员手工维护，任何组件不得写入。

```go
// DataSet
type DataSetSpec struct {
    Endpoint               string                    `json:"endpoint"`
    Bucket                 string                    `json:"bucket"`
    DatasetName            string                    `json:"datasetName"`
    SecretRef              corev1.LocalObjectReference `json:"secretRef"`
    SnapshotID             string                    `json:"snapshotID,omitempty"` // 空 = CURRENT
    ChunkSize              int64                     `json:"chunkSize"`
    Shards                 []ShardSpec               `json:"shards"`
    AccessibleNodeSelector *metav1.LabelSelector     `json:"accessibleNodeSelector,omitempty"` // 可选收窄；未设置时默认 traincache.io/s3-access=true
    Shuffle                bool                      `json:"shuffle,omitempty"`
    Metadata               *DataSetMetadata          `json:"metadata,omitempty"`
}

type DataSetMetadata struct { // 仅登记，Controller/Agent 不读取
    SampleCount int64  `json:"sampleCount,omitempty"`
    Format      string `json:"format,omitempty"`
    Description string `json:"description,omitempty"`
    Version     string `json:"version,omitempty"`
    Source      string `json:"source,omitempty"`
    Purpose     string `json:"purpose,omitempty"`
}

type ShardSpec struct {
    Name          string `json:"name"`
    Count         int32  `json:"count"`         // 该分片的块数
    LastChunkSize int64  `json:"lastChunkSize"` // 末块字节数，0 < v <= ChunkSize
}

type DataSetStatus struct { // 不设反向引用，WarmupTask 单向引用 DataSet
    ObservedGeneration int64              `json:"observedGeneration,omitempty"`
    Conditions         []metav1.Condition `json:"conditions,omitempty"`
    SnapshotID         string             `json:"snapshotID,omitempty"` // 解析后的具体快照
    TotalChunks        int32              `json:"totalChunks,omitempty"`
    BlockLayout        []BlockLayout      `json:"blockLayout,omitempty"`
    AccessibleNodes    []string           `json:"accessibleNodes,omitempty"` // selector 的解析结果，升序
}

type BlockLayout struct {
    Shard         string `json:"shard"`
    StartChunk    int32  `json:"startChunk"` // 全局块号，跨分片累计
    Count         int32  `json:"count"`
    LastChunkSize int64  `json:"lastChunkSize"`
}
```

```go
// WarmupTask
type WarmupTaskSpec struct {
    DataSetRef    corev1.LocalObjectReference `json:"dataSetRef"`
    TargetRef     TargetRef                   `json:"targetRef"`
    PodCount      int32                       `json:"podCount"`
    Affinity      AffinityPolicy              `json:"affinity,omitempty"`
    TrainingType  TrainingType                `json:"trainingType"`
    PodDetails    []PodDetail                 `json:"podDetails"`
    Gate          GatePolicy                  `json:"gate"`
    Score         ScorePolicy                 `json:"score"`
    Candidate     CandidatePolicy             `json:"candidate,omitempty"`
}

type TargetRef struct {
    APIVersion       string                `json:"apiVersion"`
    Kind             string                `json:"kind"` // Job | StatefulSet | Pod
    Name             string                `json:"name"`
    PodLabelSelector *metav1.LabelSelector `json:"podLabelSelector,omitempty"`
}

type PodDetail struct {
    Index                int32                       `json:"index"` // 0..PodCount-1，必须连续
    Resources            corev1.ResourceRequirements `json:"resources"`
    InitialConsumeOrder  []int32                     `json:"initialConsumeOrder"` // 全局块号；非法时整组回退默认切分
    K                    int32                       `json:"k"`                   // 启动窗口块数，同时是评分平台段长度（每 Pod 独立 K_i）
}

type GatePolicy struct {
    Threshold   float64         `json:"threshold"`   // 0~1
    GapMin      float64         `json:"gapMin"`      // 0~1
    SlopeMin    float64         `json:"slopeMin"`    // 比例/秒，通常 <=0
    TMax        metav1.Duration `json:"tMax"`
    MinInterval metav1.Duration `json:"minInterval"`
}

// K 不在 ScorePolicy 中：每 Pod 的 K_i 来自 PodDetail.K，既是启动窗口，也是评分平台段。
type ScorePolicy struct {
    HalfLife float64 `json:"halfLife"` // H：半衰期（块）
    Cutoff   int32   `json:"cutoff"`   // C：截断距离（块）
}

type CandidatePolicy struct {
    RequireReady     bool  `json:"requireReady"`
    IgnoreNoSchedule bool  `json:"ignoreNoSchedule"`
    MinFreeDiskBytes int64 `json:"minFreeDiskBytes,omitempty"`
}
```

```go
type WarmupTaskStatus struct {
    ObservedGeneration int64              `json:"observedGeneration,omitempty"`
    Conditions         []metav1.Condition `json:"conditions,omitempty"`
    Phase              WarmupPhase        `json:"phase,omitempty"`
    ConsumeOrderSource ConsumeOrderSource `json:"consumeOrderSource,omitempty"` // Spec|Default
    StartedAt          *metav1.Time       `json:"startedAt,omitempty"`
    CandidateNodes     []string           `json:"candidateNodes,omitempty"` // 稳定排序，行列表头
    ReadinessTable     [][]int32          `json:"readinessTable,omitempty"` // P x N，行=Pod 序号、列=CandidateNodes 顺序；窗口就绪块数（计数，非比例）
    PodNodeReadiness   []PodNodeReadiness `json:"podNodeReadiness,omitempty"` // 每 PodDetail.Index 一条
    GateDecision       GateDecision       `json:"gateDecision,omitempty"`
    LastUpdated        *metav1.Time       `json:"lastUpdated,omitempty"`
}

// PodNodeReadiness 表示“该 Pod 在其分配节点上的就绪事实”，每 PodDetail.Index 一条。
type PodNodeReadiness struct {
    PodIndex             int32        `json:"podIndex"`
    PodName              string       `json:"podName,omitempty"`
    AssignedNode         string       `json:"assignedNode,omitempty"` // 分配节点；未分配时为空
    ActualNode           string       `json:"actualNode,omitempty"`
    ReadyInWindow        int32        `json:"readyInWindow,omitempty"`
    RequiredReady        int32        `json:"requiredReady,omitempty"`        // floor(threshold*K_i)，见 §5.6
    StartupWindowReadyRate float64    `json:"startupWindowReadyRate,omitempty"` // 仅观测，不参与门控
    GlobalDecayScore     int32        `json:"globalDecayScore,omitempty"`
    State                PreheatState `json:"state,omitempty"` // 分配节点的状态；未分配时为该 Pod 的汇总态（任一候选 Ready→Ready，全部 Failed→Failed，否则 Preheating）
    LastReportTime       *metav1.Time `json:"lastReportTime,omitempty"` // 分配节点最近一次上报
}

type GateDecision struct {
    State     GateState   `json:"state,omitempty"` // Hold|Released|Degraded
    Reason    string      `json:"reason,omitempty"`
    DecidedAt *metav1.Time `json:"decidedAt,omitempty"`
    PodRates  []PodRate   `json:"podRates,omitempty"`
}

type PodRate struct {
    PodIndex int32   `json:"podIndex"`
    Rate     float64 `json:"rate"`
    Gap      float64 `json:"gap"`
    Slope    float64 `json:"slope"`
}
```

枚举取值冻结：`TrainingType = epoch|shuffle|curriculum|static`；`ConsumeOrderSource = Spec|Default`（`Default` 表示任一 Pod 消费顺序非法后整组回退，见 §7.2）；`WarmupPhase = Pending|Filtering|Preheating|Gating|Released|Degraded|Failed`；`GateState = Hold|Released|Degraded`；`PreheatState = Preheating|Ready|Stopped|Failed`；`AffinityPolicy = Any|Pack|Spread`（仅记录，v1 不参与算法）。

### 5.2 DataSet 控制器

```go
type Reconciler struct {
    client.Client
    StoreFactory storage.Factory // secretRef -> objectstore.Store
    Recorder     record.EventRecorder
    Log          *slog.Logger
    Metrics      *metrics.Metrics
}

func (r *Reconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error)
```

前置条件：`chunkSize > 0`、`shards` 非空、`count > 0`、`0 < lastChunkSize <= chunkSize`、`0 <= snapshotID`、Secret 存在且含 `accessKey`/`secretKey`。

后置条件：成功时 `TotalChunks = Σ shards[i].Count`、`BlockLayout` 按 spec 顺序累计 `StartChunk`、`SnapshotID` 为解析后的具体值、`AccessibleNodes` 为可达节点解析结果（升序）：默认选择 `traincache.io/s3-access=true` 的 Node；`AccessibleNodeSelector` 非空时在该标签集合内收窄。标签只读，任何组件不得写入。有匹配节点时 `Condition Ready=True`；无匹配节点时置 `Condition NoAccessibleNodes=False` 并发事件，返回退避重试（节点标签可能随后补齐），WarmupTask 不得下发。

错误语义：可重试错误（存储不可达、API 冲突）返回 error 由 controller-runtime 退避；不可重试错误写入 `Condition InvalidSpec/StorageUnreachable/SnapshotNotFound=False` 并返回 nil。幂等：任何一次 reconcile 都从 spec 全量重算，不依赖上一次结果。

### 5.4 候选节点筛选

```go
func Filter(in FilterInput) ([]string, error)
type FilterInput struct { Nodes []corev1.Node; Accessible set.Set[string]; Pods []PodDetail; Policy CandidatePolicy }
```

规则顺序（先排除后保留）：Node `Ready=True` → 命中 DataSet `AccessibleNodes` → 无 `NoSchedule/NoExecute` 污点（`IgnoreNoSchedule=true` 时只排除 NoExecute）→ allocatable 减去已请求资源后满足最大 `PodDetail.Resources` → 该节点存在 Ready 的 agent Pod。返回节点名升序，作为 readinessTable 的列顺序。

### 5.5 GWAA

```go
func Compute(in Input) Placement
type Input struct {
    Pods  []PodState   // Index, K, ReadyCountByNode map[string]int32
    Nodes []NodeState  // Name, Stopped bool
    Rand  *rand.Rand   // 注入随机源；测试传固定种子，生产用时间种子
}
type Placement struct {
    Assignment  map[int32]string  // podIndex -> nodeName
    PreheatSet  map[string][]int32 // nodeName -> podIndex 列表
    Rounds  int
}
```

定位是贪心近似，不追求最优。按各 Pod（或超 Pod）最大 `c_ij` 降序处理，并列由注入 RNG 随机；首选节点为 `c_ij` 最大者；所有并列（最大 `c_ij` 相同、`c_ij - secondBest_i` 差值相同、回退时的候选选择）用注入的 RNG 均匀随机决定，不再使用节点名/序号的固定次序。冲突时保留 `c_ij - secondBest_i` 较大者；共享分支未启用，见 8.3 D33；当前实现仍按差值裁决，`c_ij - secondBest_i` 大者保留、其余让步。每轮结束后被让步 Pod 只能改认次优节点；最多 `len(Pods)` 轮，仍未收敛则保留首个贪心结果并 `slog.Warn("gwaa: 未收敛，保留首个贪心结果")`。返回值必须满足“每 Pod 恰好一个节点、同节点可被多 Pod 认领”。纯函数，不读 k8s、不写 status、不记 log（调用方记）。固定随机种子下可复现；不同种子下输出合法（仍满足每 Pod 一个节点）。复杂度：默认一节点一 Pod 模式为 O(P×N)；`allowMultiPodPerNode=true` 时还需扫描节点占位单元，最坏 O(P²×N)，在 P≤64、N≤256 约束下为有界上界。

### 5.6 门控

```go
func Evaluate(in Input) Decision
type Input struct {
    Now         time.Time
    Policy      GatePolicy
    Pods        []PodGateState // Index, AssignedNode, K, Ready, Rate, PrevRate, PrevAt, FirstSampleSeen
    FirstReadyAt time.Time     // 首个 Pod 达标的时刻，零值表示尚未出现
    StartedAt   time.Time
}
type Decision struct { State GateState; Reason string; Rates []PodRate }
```

整数门控：对每个 Pod 计算 `required_i = floor(Threshold * K_i)`；若 `Threshold > 0 && required_i == 0` 则置 `required_i = 1`；`Threshold == 0` 时 `required_i = 0`。示例：`K=8, Threshold=0.8 → required=6`。条件①的满足条件是分配节点上 `Ready >= required_i`（`Ready` 即该节点窗口内已落盘且校验通过的块数）；`StartupWindowReadyRate` 仅作观测，不参与判定。条件②的 `Gap`/`Slope` 仍用连续 `Rate`（不取整），避免量化噪声。

判定顺序：条件③超时（`Now-StartedAt >= TMax`）→ `Degraded`；条件①（所有 Pod 在其 `AssignedNode` 上 `Ready >= RequiredReady`）→ `Released`；条件②（`FirstReadyAt` 非零、`Now-FirstReadyAt >= MinInterval`、未达标 Pod 同时 `Gap > GapMin` 且 `Slope < SlopeMin`）→ `Released`；否则 `Hold`。`Gap = Threshold - Rate`，`Slope=(Rate-PrevRate)/(Now-PrevAt)`，`PrevAt` 零值或间隔 < MinInterval 时不参与条件②。条件①使用分配节点而非任意候选节点（比基线更严格，见 decisions D14）。

边际收益语义：等待的价值是减少启动期回源。Agent 在放行后仍持续回填，未就绪块读到时会回源（正确但慢）；窗口内第 i 块要到训练第 i 步才被消费，若补齐速率不低于消费速率，等满窗口的边际收益趋零。因此条件②在“至少一个 Pod 达标”后，对每个未达标 Pod 以 gap（剩余缺口）大且 slope（补齐速率）低作为“继续等待的边际收益低于成本”的判据；条件③ tMax 是绝对上限，代表占用资源的机会成本。

`Score` 通过 `nodeInfo.Node().Name` 取节点名（v0.37 的 Score 签名直接传 `*framework.NodeInfo`，不再传节点名字符串），其余语义不变。逻辑：读 Pod annotation `traincache.io/warmup-task`（值 `<ns>/<name>`）与 `traincache.io/pod-index`（十进制 `<i>`）→ 用 `scorefmt.Key(ns, name)` 计算 Node annotation 键（§6.2，即 D27 的 `scores-<namePrefix32>-<hash12>`）→ 在该节点的 Node annotation 中读对应键的 JSON → 取 `p["<i>"]` → 未过期返回该分数。键缺失、条目缺失、`pod-index` 缺失、JSON 损坏、`task` 与 Pod 注解不匹配或超 TTL 一律返回 0。任何错误都返回 0 + `nil` status，不得让 Pod 因插件失败而被拒绝调度。

## 6. 数据格式

### 6.1 CRD 状态布局

`ReadinessTable` 行下标 = `PodDetail.Index`，列下标 = `CandidateNodes` 顺序；值 = 该 Pod 在该节点启动窗口内“已落盘且校验通过”的块数，范围 `0..K_i`（每 Pod 使用自己的 `K`）。比例一律现算：`Rate = ReadyInWindow / K_i`。`RequiredReady = floor(Threshold*K_i)`（`Threshold>0` 且结果为 0 时取 1；`Threshold==0` 时为 0），按 Pod 写入 `PodNodeReadiness`。status 只存事实与判定所需的整数门槛；`StartupWindowReadyRate` 仅作观测，不参与判定。

`PodNodeReadiness` 明细**每个 `PodDetail.Index` 一条**（共 P 条），语义为“该 Pod 在其分配节点上的就绪事实”，不再按候选节点展开。分配节点写入 `AssignedNode`；未分配时 `AssignedNode` 为空、`State` 取该 Pod 的汇总态（任一候选 Ready→Ready；全部候选 Failed→Failed；否则 Preheating）。`ReadyBlockBitmap`（分配节点上报的那份）、`ReadyInWindow`、`StartupWindowReady`、`StartupWindowReadyRate`、`LastReportTime` 都取分配节点的最近一次上报。候选节点粒度的就绪块数只由 `ReadinessTable`（P×N，行=Pod 序号、列=`CandidateNodes` 顺序）承载。门控判定、事件与条件保持原语义：只读取分配节点的值。

### 6.2 Node annotation

每 WarmupTask 一个独立键，完整键为 `<prefix>-<namePrefix>-<hash12>`，其中 `<prefix>` 默认 `traincache.io/scores`（§8）。编码函数：

```go
func Key(ns, name string) string
// namePrefix = strings.TrimRight(name[:min(len(name),32)], "-.")
// hash12     = sha256(ns + "/" + name) 的前 12 位小写十六进制
// prefix     = 配置项（默认 traincache.io/scores），Controller/Scheduler 取值一致
// return prefix + "-" + namePrefix + "-" + hash12
```

键名部分（`scores-` + ≤32 + `-` + 12）≤ 52 字符，满足 63 上限。

值：单行 JSON，UTF-8，无换行。

```json
{"v":1,"task":"default/train-1","g":12,"t":"2026-10-20T08:00:00Z","p":{"0":87,"1":73}}
```

- `v`：格式版本，当前 1。
- `task`：`<namespace>/<name>`，写入时校验与键的 hash 一致。
- `g`：写入时的 WarmupTask `generation`。
- `t`：RFC3339 UTC 写入时刻；超过 `CONTROLLER_SCORE_TTL` 视为过期。
- `p`：键为 podIndex 十进制字符串，值为 0~100 整数分数。

每个 task 只读改写自己的键；多 task 共节点互不影响；TTL 按 `t` 判断。Scheduler 由 Pod annotation `traincache.io/warmup-task`（值 `<ns>/<name>`）计算同一键；键缺失、条目缺失、JSON 损坏、`task` 不匹配或超 TTL → 分数 0。

写入策略：一次 reconcile 内按 task 读-改-写本 task 的键，冲突时重读重试最多 5 次；不删除其他 task 的键。

### 6.3 Pod 注入字段

| 字段                                   | 值                     |
|----------------------------------------|------------------------|
| `spec.schedulingGates[].name`          | `traincache.io/warmup` |
| annotation `traincache.io/warmup-task` | `<namespace>/<name>`   |
| annotation `traincache.io/pod-index`   | 十进制序号             |

### 6.4 proto 增量

见 §12 与 `docs/7.1 design.md` 附录 A；Controller 只使用增量后的消息，不自定义传输格式。

### 6.5 日志字段

固定小写 snake_case，禁止混用：`component`、`dataset`、`warmup_task`、`task_id`、`pod`、`pod_index`、`node`、`generation`、`seq`、`annotation_key`、`consume_order_source`、`phase`、`state`、`reason`、`duration_ms`、`err`。不记录 Secret 内容、access key、完整对象路径（Info 级）；块级明细只在 Debug 级。

## 7. 关键流程

### 7.1 DataSet 校验与块布局

1. 读取 DataSet；`deletionTimestamp` 非空则直接返回。
2. 校验 spec 字段；失败写 `InvalidSpec=False`，`Event` 记录原因，返回 nil。
3. 解析 Secret，构造 `objectstore.Store`；失败写 `StorageUnreachable=False`，返回 error 退避重试。
4. `snapshotID` 为空时读 `CURRENT` 解析具体快照；读 manifest 并校验 `snapshot_id` 一致、`shards` 非空。
5. 按 spec `Shards` 顺序累计 `StartChunk`，生成 `BlockLayout` 与 `TotalChunks`。
6. 解析可达节点：默认选择 `traincache.io/s3-access=true` 的 Node；`AccessibleNodeSelector` 非空时在其结果内收窄；写升序 `AccessibleNodes`。无匹配节点置 `NoAccessibleNodes=False` 并发事件，停止下发；标签只读，任何组件不得写入。
7. 写 status（带 `ObservedGeneration`）：有可达节点时 `Ready=True`，无匹配节点时 `Ready=False`（原因见步骤 6）；`Event` 提示引用它的 WarmupTask。

### 7.2 候选节点筛选与预热下发

1. 读取 WarmupTask 与 DataSet；DataSet 非 `Ready` 时写 `Condition DataSetNotReady` 并返回。
2. 校验 `PodDetail.Index` 必须覆盖 `0..PodCount-1` 且不重复；解析消费顺序：若任一 Pod 的 `InitialConsumeOrder` 为空、越界或重复，则忽略全部用户值，按默认切分 `T=totalChunks`，Pod i 取 `[floor(i*T/P), floor((i+1)*T/P))`，块号升序，置 `ConsumeOrderSource=Default` 并发 `ConsumeOrderDefaulted` 事件；否则 `ConsumeOrderSource=Spec`。默认切分要求 `T >= P`，否则 `Condition InvalidSpec=False` 并返回。
3. 列出 `TargetRef` 匹配的 Pod 与 Node；Pod 集合与 `PodCount` 不一致时只置 `Condition PodSetMismatch`，继续使用已有 Pod，不创建/重建/扩缩容。
4. 执行 `Filter`；DataSet 无可达节点时写 `NoAccessibleNodes` 并停止下发；结果为空写 `NoCandidates`，返回退避（节点状态可能变化）。
5. 冻结本次分配输入：对每个 `(pod,node)` 调 `Submit`，`task_id` 见 §5.9；`chunks` 为该 Pod 消费顺序前 `max(K_i, Cutoff)` 块（显式列表，顺序即位序）。发送失败记 `ErrAgentUnavailable`，节点标记 `Stopped` 并在下一轮重试；永久拒绝（`InvalidArgument/FailedPrecondition` → `ErrPermanent`）记入 `Condition PreheatRejected=False`（reason=`AgentRejected`）并发 Warning 事件，不再重试该节点，见 §7.9。
6. 进入 `Preheating`，写 `CandidateNodes`、`StartedAt`（仅首次）。

### 7.3 进度拉取与就绪表

1. `Poll` 每 `CONTROLLER_POLL_INTERVAL` 遍历所有 `Preheating/Gating` 的 task。
2. 对每个 `(pod,node)` 调 `Progress`（内部 `GetPreheatStatus`）；返回 `Generation/Seq/ReadyBitmap/Completed/Failed/State/UpdatedAt/Total`，位图按该 `(pod,node)` 请求的 `chunks` 顺序解码。
3. `ReadyInWindow = popcount(前 K_i 位)`；`RequiredReady` 按 §5.6 整数公式计算；`GlobalDecayScore` 由 §7.6 公式按该 Pod 的 `K_i` 与前 `C` 位计算。
4. 更新 `ReadinessTable[p][n]` 与 `PodNodeReadiness`（含 `ReadyInWindow`、`RequiredReady`、`StartupWindowReadyRate`、`State`）；`LastReportTime` 用 `UpdatedAt`，缺失时用本地时钟。
5. 低于当前 generation 的响应丢弃并记 Debug；同 generation 下 `Seq` 小于已记录值也丢弃。连续 3 次 `ErrAgentUnavailable` 将 Pod 状态置 `Failed`，仅影响门控条件②的斜率计算，不阻塞超时降级。

### 7.4 GWAA 分配

输入为 `ReadinessTable` 与已停止节点集合；每轮 Poll 后重算。分配变化时：对新增 `(pod,node)` 调 `Submit` 或 `Update`，对不再需要预热的 `(pod,node)` 调 `Cancel`。分配结果只写 status，不写 Node。

### 7.5 门控与放行

1. 组装 `PodGateState`：`K`/`Ready` 取分配节点上的窗口值，`RequiredReady` 按 §5.6 整数公式计算，`Rate = Ready / K_i`；`FirstReadyAt` 取自 status `Conditions` 中类型为 `FirstReady` 的 `LastTransitionTime`（首次出现任一 Pod `Ready >= RequiredReady` 时写入，之后不再更新）。
2. `Evaluate` 返回 `Hold` 时不写 Node、不摘 Gate，`RequeueAfter = PollInterval`。
3. `Released/Degraded` 时：
   a. 对每个候选节点计算本 task 所有 Pod 的 `S(node)`（各 Pod 用各自 `K_i`），写本 task 自己的 Node annotation 键（§6.2），只读改写该键、不覆盖其他 task 的键；
   b. 逐个 Pod patch 移除 `traincache.io/warmup` gate（已移除则跳过）；
   c. 写 `GateDecision{State,Reason,DecidedAt,PodRates}` 与 `Phase=Released/Degraded`；
   d. 冻结评分：此后 generation 不变则不再改写本 task 的 annotation。
4. 步骤 a 失败则整体重试，不摘 Gate；步骤 b 部分失败时已摘 Pod 不回滚，下一轮继续摘剩余 Pod（幂等）。

### 7.6 评分计算

按 `(pod,node)` 计算，使用该 Pod 自己的 `K_i`。对 Pod 的消费顺序位置 `i`（0 起）：`w(i)=1 (i<min(K_i,C))`；`w(i)=0.5^((i-K_i)/H) (K_i<=i<C)`；`w(i)=0 (i>=C)`。`S = round(100 * Σ(w(i)*ready(i)) / Σw(i))`；`Σw(i)=0` 时 `S=0`。位图缺失的位按 0 计；`K_i >= C` 时平台段截到 `C`，无衰减段。

### 7.7 调度

Scheduler 收到 `(Pod, Node)`：Pod 注解 `warmup-task` + `pod-index` → `scorefmt.Key(ns,name)` → 读 Node 上该键的 `p[podIndex]`；`Score` 返回该分数，`NormalizeScore` 归一化。键缺失、条目缺失、JSON 损坏、`task` 不匹配或超 TTL → 0。

### 7.8 落点兜底

Controller 监听 Pod 的 `spec.nodeName`；若与 `AssignedNode` 不同：
- 写 `PodNodeReadiness.ActualNode`、`Event NodeDeviation`；
- 对实际节点 `Submit` 同一 Pod 的窗口（优先级 P0），不取消原节点；
- 不重新门控（Pod 已放行），失败只影响该 Pod 的读路径命中率，由 Agent 回源兜底。

### 7.9 异常与降级

| 场景                         | 行为                                                                                           |
|------------------------------|------------------------------------------------------------------------------------------------|
| Agent 不可达                 | 节点标记 Stopped，退避重试；全部不可达且 `t >= TMax` → `Degraded` 放行                         |
| Agent 永久拒绝               | `InvalidArgument/FailedPrecondition` 映射 `ErrPermanent`：写 `Condition PreheatRejected=False`（reason=`AgentRejected`）并发 Warning 事件；该节点不再重试，其余节点继续；全部候选被拒时不推进门控，仍由 `TMax` 兜底降级 |
| DataSet 失效                 | WarmupTask 停止下发，`Condition DataSetNotReady`，不推进门控                                   |
| 可达节点为空                 | `Condition NoAccessibleNodes`，停止下发；已有任务可 `Cancel`，门控仍受 `TMax` 降级约束         |
| Pod 集合与 `podCount` 不一致 | 只置 `Condition PodSetMismatch`，不创建/重建/扩缩容，继续使用现有 Pod                          |
| 消费顺序非法                 | 忽略全部用户值，按默认切分并 `ConsumeOrderDefaulted`；`T < P` 时 `Condition InvalidSpec=False` |
| Webhook 未注入               | `Condition GateInjectionDegraded`，不阻塞其他 Pod；该 Pod 无 gate，直接调度                    |
| Node annotation 写失败       | 不摘 Gate，退避重试（只重写本 task 的键）                                                      |
| Controller 重启              | 全部状态从 CRD/Node annotation 重建；rateHistory 丢失，条件②重新积累                           |
| 重复 reconcile               | 全量重算 + 幂等 patch；Submit/Cancel 幂等键保证不重复建任务                                    |

## 9. 日志与可观测性设计

### 9.1 硬性要求

> 新模块核心代码的每个关键位置必须记录结构化日志，并随对应里程碑一起验收；没有日志断言测试的里程碑不判通过。日志不得改变业务逻辑、接口、数据格式与运行行为。

### 9.2 基础设施

- 日志库：标准库 `log/slog`，与 agent 一致，`JSONHandler(os.Stderr)`，`cmd/*/main.go` 各初始化一次。
- `internal/logging` 只做三件事：`New(level) *slog.Logger`、`Into(ctx, l) context.Context`、`From(ctx) *slog.Logger`（缺失时返回 `slog.Default()`）。不引入第三方。
- 每个 reconcile/HTTP 请求生成 `request_id`（`<uid>/<generation>/<unixnano>`），放入 context 与所有日志；无分布式 traceId，跨进程关联用 `task_id + node + generation`。
- 级别：Info=状态迁移、放行、筛选结果、任务完成；Warn=降级、重试、跳过、未收敛；Error=reconcile 返回 error、RPC 永久失败；Debug=逐块/逐节点评分明细，默认关闭。

### 9.4 脱敏与性能

- 禁止记录 Secret 内容、accessKey/secretKey、完整凭据 URL。
- `path`/`chunk`/`fp` 等高基数维度只进 Debug；Info 聚合到 dataset/task 维度。
- 日志调用不得在锁内做格式化之外的 I/O；`From(ctx)` 缺失时退化为全局 logger，不 panic。

### 9.5 指标（Prometheus，独立 Registry）

controller-manager 使用独立 Registry，经 `metricsserver.Options.ExtraHandlers` 暴露在 `/metrics/traincache`（内置 `/metrics` 仍归 controller-runtime）。scheduler 是独立进程，自建 Registry 并在 `CONTROLLER_METRICS_ADDR` 上暴露同一路径。所有标签值必须来自固定枚举；禁止把 `err.Error()`、Pod/Node/task 名、UID 等无界值放进标签。

| Family | 类型 | 标签 | 发射点 / 语义 |
| --- | --- | --- | --- |
| `traincache_controller_reconcile_total` | Counter | `controller` ∈ `dataset\|warmup\|warmup-degraded`；`result` ∈ `success\|error\|requeue` | 每个 Reconcile 退出时 +1；优先级 err≠nil → error，否则 RequeueAfter>0 → requeue，否则 success |
| `traincache_controller_reconcile_duration_seconds` | Histogram | `controller` | 同上，defer 覆盖所有返回路径（含 NotFound/DeletionTimestamp） |
| `traincache_controller_candidate_nodes` | Histogram | `dataset` = `<namespace>/<name>` | 候选节点筛选完成后观测 `len(candidates)` |
| `traincache_controller_preheat_rpc_total` | Counter | `op` ∈ `submit\|update\|cancel`；`result` ∈ `ok\|permanent\|unavailable` | 每次 Agent RPC 调用点 +1；`permanent` 对应 `ErrPermanent`，其余失败归 `unavailable` |
| `traincache_controller_gate_tasks` | Gauge | `state` ∈ `hold\|released\|degraded` | 首次门控评估起 Inc/Dec 维护；任务删除或进入终态时 Dec，重复状态不重复计数 |
| `traincache_controller_gate_hold_duration_seconds` | Histogram | 无 | 仅在离开 Hold（Released/Degraded）时观测一次 |
| `traincache_controller_agent_poll_total` | Counter | `result` ∈ `ok\|unavailable\|stale\|error` | 每次 `GetPreheatStatus` 轮询 +1；generation/seq 回退被丢弃记 `stale`，响应解析失败记 `error` |
| `traincache_controller_pods_per_node` | Histogram | 无 | 每次 GWAA 计算后对 PreheatSet 每个 node 观测 `len(pods)`；`allowMultiPodPerNode` 未接线时恒为 1 |
| `traincache_controller_gwaa_unassigned_pods` | Gauge | `dataset` | 每次 GWAA 计算后 Set 为 `len(UnassignedPods)` |
| `traincache_controller_gwaa_fallback_total` | Counter | 无 | GWAA 不收敛、回退到首个贪心结果时 +1 |
| `traincache_scheduler_score_total` | Counter | `result` ∈ `ok\|no_task_ref\|invalid_task_ref\|no_pod_index\|invalid_pod_index\|no_annotation\|invalid_value\|task_mismatch\|stale_generation\|expired\|no_pod_entry` | scheduler 进程 `Evaluate` 的固定分支枚举 |

与原设计的差异：删除 `controller_ready_blocks{warmup_task,pod,node}`（P×N 集合基数）与 `controller_gate_state{warmup_task}`（每任务一条序列）；ready 明细改由 status 与日志排查，门控状态改用有界计数的 `gate_tasks{state}`。`controller_candidates` 更名为 `controller_candidate_nodes{dataset}`，`dataset` 采用 `<namespace>/<name>` 以避免跨命名空间碰撞。新增 poll 与 GWAA 指标以覆盖轮询与分配回退。高基数标签禁止进指标。

### 9.6 排查路径

门控不放行 → 查 `GateDecision.PodRates` 与 `PodNodeReadiness` → 查 `controller_preheat_rpc_total` → 查 Agent `GetPreheatStatus`（`generation/seq/ready_bitmap`）→ 查 Agent 自身指标。落点偏离 → 查 Pod 的 `ActualNode` 与 `NodeDeviation` 事件。

## 10. 风险与约束

- **R1 调度器依赖重量级。** 自定义 kube-scheduler 镜像需引入 `k8s.io/kubernetes`（或等价 framework runtime），版本必须与集群 minor 对齐；未对齐会导致插件 ABI 不兼容。见 Q1。
- **R2 Webhook 是关键路径。** 未注入 gate 时门控失效但不阻塞训练；`failurePolicy=Ignore` 是有意选择，代价是静默降级，依赖 `GateInjectionDegraded` 条件兜底。
- **R3 workspace 依赖。** 新 module 的跨模块 import 依赖 `go.work`，`GOWORK=off` 构建会失败；与现有 agent→core 的做法一致，不引入 replace。
- **R4 CRD status 体积。** `ReadinessTable` 与 `PodNodeReadiness` 随 P×N 增长，需在上限（P≤64、N≤256）内测试；超出应改为只存表不存明细。
- **R5 内存态丢失。** rateHistory 随重启清空，条件②在重启后需重新积累，可能推迟放行，但不会错误放行。
- **R6 Agent 增量未落地。** Controller 依赖 7.x 新增 RPC；在 Agent 实现前，集成测试只能用 fake server。
- **R7 时钟。** 所有比较使用 `r.Now()` 注入的同一时钟；CRD 时间字段统一 UTC RFC3339。

## 11. 验收标准（总闸）

1. `cd controller && go build ./... && go vet ./... && go test ./... -race -count=1` 全绿，gofmt 干净。
2. 两个 CRD 可由 `controller-gen` 从类型重新生成，产物与提交一致；只开 `status`、无 `scale`；`podCount`/`dataSetRef` 的 CEL 不可变校验生效；Controller 不创建 Job/Pod。
3. 8.0 基线中的 D1–D8 每条在代码中有唯一落点，且 `docs/8.3 decisions.md` 有对应 D 编号。
4. DataSet 校验覆盖：字段非法、Secret 缺失、快照不存在、blockLayout 累计正确；`s3-access` 标签解析、`AccessibleNodeSelector` 收窄、无匹配节点时 `NoAccessibleNodes` 且停止下发。
5. 门控整数边界：`K=8, threshold=0.8 → required=6`；`threshold>0` 且 `floor` 为 0 时取 1；`threshold=0` 时 required=0；条件②使用连续 rate；`StartupWindowReadyRate` 不参与判定；`t >= TMax` 必放行；全 Pod 达标必放行。
6. GWAA 固定种子下可复现、不同种子下输出合法；冲突、并列（含随机回退）、不可收敛三种情形均有测试，且不收敛保留首个贪心结果。
7. Node annotation 每 task 独立键：`Key(ns,name)` 往返一致、`namePrefix` 截断/去尾、`hash12` 稳定、键名 ≤ 52；两 task 共节点互不影响；过期/缺失/解析失败/`task` 不匹配时 Scheduler 返回 0 且不拒绝调度。
8. 消费顺序：任一 Pod 非法时整组回退默认切分并置 `ConsumeOrderSource=Default`、发 `ConsumeOrderDefaulted`；`T < P` 校验失败；`PodDetail.Index` 覆盖校验；Pod 集合不一致只置 `PodSetMismatch` 不修复。
9. Webhook 注入幂等；无匹配 task 时不注入；Pod 序号解析失败时有事件与条件。
10. 每个里程碑的日志点有对应断言测试（至少一条 `slog` 输出捕获测试），覆盖 `annotation_key`、`generation`、`seq`、`consume_order_source`。
11. 不修改 `core/`、`agent/` 业务代码；对 `agent/api/agent.proto` 的修改仅限 §12 列出的增量。
12. `docs/8.2 plan.md` 的覆盖判断中不存在未标注的“缺失”项；标注为“部分覆盖”的项有明确后续任务。

## 12. 跨模块增量

### 12.1 Agent proto 增量（并入 7.1 附录 A）

`agent/api/agent.proto` 在现有 `traincache.agent.v1.PreheatService` 上做最小增量（进度复用 `GetPreheatStatus`）：

```proto
// 8.x 增量（2026-10-20）：在现有 traincache.agent.v1.PreheatService 上最小增量扩展。
// 进度查询复用 GetPreheatStatus；不新增 GetPreheatProgress。

message SubmitPreheatRequest {
  // 字段 1..7 保持现状
  uint64 generation = 8;  // 任务代际；0 表示未提供
}

message PreheatStatus {
  // 字段 1..11 保持现状
  uint64 generation = 12;   // 任务代际
  uint64 seq = 13;          // 位图变更序号，单调递增
  bytes ready_bitmap = 14;  // 位 i 对应请求 chunks 第 i 项；1=已落盘且校验通过
}

message UpdatePreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;         // 必须 >= Agent 当前代际
  repeated ChunkRef chunks = 4;  // 新的完整块列表，同时定义位序
  PreheatPriority priority = 5;
}

message UpdatePreheatResponse {
  bool accepted = 1;
  string message = 2;
}

message CancelPreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;
}

message CancelPreheatResponse {
  bool accepted = 1;
}

service PreheatService {
  // 已有
  rpc SubmitPreheat(SubmitPreheatRequest) returns (SubmitPreheatResponse);
  rpc GetPreheatStatus(GetPreheatStatusRequest) returns (PreheatStatus);
  // 新增
  rpc UpdatePreheat(UpdatePreheatRequest) returns (UpdatePreheatResponse);
  rpc CancelPreheat(CancelPreheatRequest) returns (CancelPreheatResponse);
}
```

`SubmitPreheatRequest.snapshot_id`（字段 4）恒为空：Controller 不得把 DataSet status 中解析出的具体快照 ID 下发，Submit 与 Update 两条下发路径均保持空值（`UpdatePreheatRequest` 本身无该字段）。理由：Agent 自行跟随 CURRENT 并按需加载 manifest 分片，避免任务键随快照推进漂移；非空值在 7.x M3 Agent 侧返回 `InvalidArgument`。

语义：`task_id` 幂等；Agent 对低于已接受 `generation` 的请求返回 `FailedPrecondition`；`Cancel` 后同名同 generation 再 `Submit` 视为新任务；位图长度必须恰好 `ceil(len(chunks)/8)`，位序由请求 `chunks` 定义。`ReportBlocks` 保持 `Unimplemented`，8.x 不使用推送模型。
