#### Controller的核心逻辑
- 概述
Controller是WarmupTask的唯一执行者，监听WarmupTask创建之后
先筛选出值得预热的节点，向这些节点Agent下发块级别的预热任务
然后持续收集Agent上报的进度，算出各个节点的就绪度
当就绪度达标之后，摘除Pod上面的SchedulingGate，保存此时的分数快照，放行调度，
同时将算好的分数快照暴露给调度器，作为调度器选择节点的一个偏好
它管“数据备好没、能不能放行、哪个节点备得最好”，不管“Pod 最终坐哪”

- 名词声明
就绪度：指数据准备好了多少的度量
窗口内就绪度：只看启动窗口内那部分数据准备好了多少
全局衰减就绪度:看全程数据备好了多少，但按块离起点的距离加权：窗口内权重 1，窗口外指数衰减，衰减到阈值以下不计
全局衰减就绪度 = 窗口内就绪度 + 窗口外就绪度

- 具体逻辑
1. Controller盯着训练Pod的声明，筛选(对应doc2的筛选语义)出候选节点
2. 给这些节点下发"这个Job启动窗口需要那些块"的WarmupTask
3. 接收Agent的进度汇报
4. 算出窗口内外就绪度（窗口外就绪度在预热过程中不会变，窗口内的每一次汇报都会变化，也是gate放开的信号）
5. 将就绪度填回到CRD的status里面
6. GangScheduling Gate(这不是在Scheduler里面的Permit hook上面的)，持续观察startupWindowReadyRate
7. 当下面三个条件满足其一就放行
   1. 存在至少M个候选节点，其 startupWindowReadyRate ≥ 门控阈值
   2. 边际收益 < 成本（当gate至少就绪一个节点之后，下一个候选预估分差rate<Δ_score）
   3. 超时t_max
8. 放行逻辑
   1. 算出所有Pod的全局衰减就绪度S(node),一会交给Scheduler的就是这个就绪度快照，从这往后预热的不算分数 
   2. 摘掉Pod的SchedulingGate
   3. 把各候选节点的 S(node) 快照写进对应Node的annotation


- 幂等操作
控制器重启，事件重放都不能产生重复操作informer的事件可能重复送达，reconcile 逻辑必须做到执⾏几次都结果⼀样

#### 就绪度得分逻辑
- 参数
W： 启动窗口大小（前W块权重均为1）
H： 半衰期（多少块后权重掉一半）
C： 截断距离（超过不计分）
- 公式
$$
w(i) =
\begin{cases}
1, & i < W \\
0.5^{\frac{i - W}{H}}, & W \leq i < C \\
0, & i \geq C
\end{cases}
$$
窗口内恒 1 ，窗口外按半衰期指数衰减：每过 H 块，权重减半，超过 C 直接 0，不计
存储的时候将窗口内就绪度与窗口外就绪度分开存储

## Scheduler
实现`Score`与`NormalizeScore`拓展点
- 编写程序
使用Go语言写一个TrainCacheScore程序，实现ScorePlugin接口，核心方法就是Score()
在里面读取你 Controller 写到 Node annotation 上的分数，做Normalization，并返回（返回的是一个0~100之间的整数）
- 写配置文件
在 KubeSchedulerConfiguration 的 profile 里启用插件，只挂到 score和normalizeScore扩展点：
```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
   - schedulerName: default-scheduler
     plugins:
        score:
           enabled:
              - name: TrainCacheScore
                weight: x  # 权重值，可根据实际需求调整
        normalizeScore:
           enabled:
              - name: TrainCacheScore
```
