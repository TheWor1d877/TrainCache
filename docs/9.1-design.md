# S3 合并回源网关实现契约
## 1. 定位与边界

### 1.1 职责

网关在 Agent 与源站之间做四件事。合并在途的整对象 GET：同一个对象键在途时，后来的请求挂到同一次源站下载上，源站只看到一次字节传输。磁盘缓存：开关打开时（默认打开），回源拿到的块留在网关的盘上，错峰到达的重复请求从盘上读，不再碰源站。限制到桶的并发下载数，并按活跃 dataset 公平分配额度。把「网关自己失败」与「源站失败」分开表达，供 Agent 选择是否降级。

### 1.2 边界

- 关闭缓存开关时只做在途合并：请求结束内存即释放，对象内容不落盘、不跨请求保留，容量与淘汰都不参与。开启时多一层磁盘缓存，服务对象仍是 `<dataset>/blocks/` 前缀，占用由单 dataset 上限与全局总上限两个值管，淘汰规则见 6.8。
- 入站认证的条件是集群内网可达。单副本部署，合并与缓存都只在这一个进程里成立。
- S3 GET 不携带 P0–P3，上游折叠后的优先级不透传，网关无请求分级。
- 合并路径只收 `<dataset>/blocks/` 前缀的 GET；HEAD 与其他键的 GET 直通源站；PUT、DELETE、LIST 回 405。路由见 4.1。
- 无 AIMD（加性增加、乘性减少）背压，无零拷贝，理由见 D26。

### 1.3 与已完成模块的关系

| 模块 | 关系 |
|---|---|
| `agent/svc` | 新增后端选择器。按配置选择一次 `Get` 走网关还是源站；持有降级状态 |
| `core/objectstore` | 新增网关错误判断标准与带选项的构造函数。现有 `Store` 接口不变 |
| `agent/metrics` | 新增两个指标族（family）：`traincache_source_mode`、`traincache_gateway_fallback_total` |
| `core/fetch` | 不修改。降级与重试都在 store 层之下完成，fetcher 只看到一次 `Get` 的结果 |
| `controller/deploy` | 新增网关 Deployment 与 Service，ConfigMap 增四个键。缓存层再加三个键与一个可写卷 |
| `bench` | 新增开关与一列产物字段。缓存层再加一列开关字段与 COND 的一个 `environment` 键 |

### 1.4 信任边界

- Agent 到网关：集群内网明文 HTTP，不认证。Agent 的 minio-go 按网关主机名算出 AWS Signature Version 4（SigV4）签名，网关忽略该签名。
- 网关到源站：TLS 在网关终止一次，签名由网关用自己那份凭证重算。全集群的加解密量从 N 降到 1。
- 网关与 Agent 共用 Secret `traincache-objstore` 的 `accessKey`、`secretKey`。

## 2. 架构概览

```
训练 Pod ── hostPath 只读 ──▶ 本地 CAS        （不经过网关）
Agent ── Get ──▶ backendStore ──┬─▶ origin S3Store ──▶ 源站
                                └─▶ gateway S3Store ──▶ Service ──▶ gateway Pod ──▶ 源站
```

网关内部：

```
HTTP server
  ├─ /healthz /readyz
  └─ GET|HEAD /<bucket>/<key>
        ├─ 非 <dataset>/blocks/ 前缀 ──▶ passthrough ──▶ origin
        └─ 块键 ──▶ registry.Lookup
                      ├─ 在途且能追上 ──▶ 挂为订阅者
                      ├─ 在途但落后超缓冲 ──▶ 独立回源（不合并）
                      └─ 不在途 ──▶ 查盘
                                    ├─ 命中 ──▶ 新建条目，owner 从盘读 ──▶ 扇出
                                    └─ 未命中 ──▶ 准入 ──▶ 新建条目 ──▶ 拉取协程
                                                            ├─▶ 环形缓冲 ◀── 订阅者
                                                            ├─▶ 自身响应
                                                            └─▶ 写盘（0 缓存开关时不写）
```

一次块 GET 的字节路径：源站（或缓存命中时的盘）把字节交给拉取协程，拉取协程写环形缓冲，订阅者从缓冲读走并写自己的 HTTP 响应。任一订阅者落后拉取协程超过环形缓冲容量（默认 10MiB，见 5.2）就被摘掉，该 HTTP 响应以截断结束。读盘扇出与读源站扇出共用这一条路径，只有 owner 一侧的 reader 不同。

## 4. 核心接口

### 4.1 网关 HTTP 契约

服务端只接受下列请求，其余一律 405 `MethodNotAllowed`。

| 请求 | 行为 |
|---|---|
| `GET /healthz` | 200，纯文本 `ok`。进程存活即成功 |
| `GET /readyz` | 200 表示可服务；收到 SIGTERM 后立即 503 |
| `HEAD /<bucket>/<key>` | 直通源站。不合并，不占准入额度 |
| `GET /<bucket>/<key>`，键不以 `<dataset>/blocks/` 开头 | 直通源站。不合并，不占准入额度 |
| `GET /<bucket>/<key>`，键以 `<dataset>/blocks/` 开头 | 先查在途表，再查盘，两者都没有才占一个准入额度回源。流程见 6.1 |

`<dataset>` 取对象键第一个 `/` 之前的部分。块键由 `objectstore.BlockKey` 生成，`path` 不含 `#`。

桶名必须等于网关配置的桶，否则 404 `NoSuchBucket`。

块键 GET 的合并响应（200）回填 `Last-Modified` 与 `ETag`，不设 `Content-Length`（保持 chunked）。minio-go v7.3.0 的 `ToObjectInfo` 对每个 GET 响应无条件解析 `Last-Modified`，缺失即 `InternalError`；回源路径的元数据复用这次 GET 的响应头，不额外发 HEAD（见 9.2 D28）。读盘命中的响应回填写盘时存进 `.meta` 的那一份（5.5），块不可变，所以它与 Agent 这次直通源站的 HEAD 结果一致。

### 4.2 错误响应

所有错误响应体是 S3 的 XML 格式，`Content-Type: application/xml`：

```xml
<Error><Code>XTraincacheGatewayUnavailable</Code><Message>gateway origin request failed</Message></Error>
```

| 场景 | 状态码 | `x-traincache-gateway` | `Code` |
|---|---|---|---|
| 网关自身失败（条目创建失败、拉取协程内部错误、panic 恢复） | 503 | `unavailable` | `XTraincacheGatewayUnavailable` |
| 准入排队超时、队列满 | 503 | 无 | `XTraincacheGatewaySlowDown` |
| 源站返回的错误（任何状态码，含 4xx/5xx） | 原状态码 | 无 | 与源站一致的 `Code` |
| 源站连不上、TLS 失败、超时 | 504 | 无 | `XTraincacheGatewayOriginUnavailable` |
| 方法不支持 | 405 | 无 | `MethodNotAllowed` |
| 桶名不符 | 404 | 无 | `NoSuchBucket` |

判断标准只有一条：`x-traincache-gateway: unavailable` 只表示「网关这一跳坏了」，不表示源站坏。源站故障一律原样透传，不带该头。

### 4.3 Agent 侧选择器

`backendStore` 实现 `objectstore.Store`，只截获 `Get`：

```go
type backendStore struct {
    origin  objectstore.Store
    gateway objectstore.Store // nil 表示未启用
    state   *sourceState
}

func (s *backendStore) Get(ctx context.Context, key string, w io.Writer) error
// Put / Delete / GetETag / PutIfMatch / List 一律转 origin
```

`sourceState` 有四个字段：

| 字段 | 含义 |
|---|---|
| `mode` | 0 直连，1 网关 |
| `gen` | 每次模式变化 +1，用于丢弃过期结果 |
| `nextProbe` | 下次允许试网关的单调时刻；0 表示不限制 |
| `backoff` | 当前退避时长，0 表示 10s 起点 |

状态迁移：

| 事件 | 迁移 |
|---|---|
| 启动 | `mode=0`；`GatewayEndpoint` 非空时 `mode=1`，`nextProbe=0` |
| `mode=1`，该请求成功 | 不变 |
| `mode=1`，该请求命中失败判断标准 | `mode=0`；`backoff = min(2×backoff 或 10s, 120s)`；`nextProbe = now+backoff`；`gen+1` |
| `mode=0`，`now < nextProbe` | 直接走源站，不探测 |
| `mode=0`，`now >= nextProbe`，抢到探测权 | 该请求走网关；成功则 `mode=1`、`backoff=0`、`nextProbe=0`、`gen+1`；失败按上一行处理 |
| `mode=0`，`now >= nextProbe`，未抢到探测权 | 直接走源站 |

探测权用 CAS 抢占：抢到时把 `nextProbe` 改为 `now+5s`，其余并发请求看到未来的时刻就直连。这样同一时刻最多一个请求发到网关。

失败结果按代际丢弃：请求开始时记下 `gen`，失败时若 `gen` 已变，说明期间发生过恢复，该结果不写状态。

### 4.4 失败判断标准

`core/objectstore` 提供：

```go
const (
    GatewayHeaderName        = "x-traincache-gateway"
    GatewayHeaderUnavailable = "unavailable"
    GatewayCodeUnavailable   = "XTraincacheGatewayUnavailable"
    GatewayCodeSlowDown      = "XTraincacheGatewaySlowDown"
    GatewayCodeOriginDown    = "XTraincacheGatewayOriginUnavailable"
)

var (
    ErrGatewayUnavailable = errors.New("objectstore: gateway unavailable")
    ErrGatewayRejected    = errors.New("objectstore: gateway rejected the request")
)

type Options struct {
    Transport  http.RoundTripper
    Region     string
    MaxRetries int
}
```

`Options` 供 `NewS3StoreWithOptions` 使用，`NewS3Store` 的签名与错误语义不变。网关客户端固定 `Region="us-east-1"`，避免 minio-go 先请求 `GET /<bucket>?location=`。固定 `MaxRetries=1`，minio-go v7.3.0 中该字段语义为「总尝试次数」，1 表示不重试——网关的 503 是控制信号，不允许 SDK 按默认 10 次退避放大。

传输层失败的类型化表达：

```go
type TransportError struct{ Err error }

func IsGatewayTransport(err error) bool
func IsGatewayTimeout(err error) bool
```

`IsGatewayTransport` 判断错误是否属于网关连接层失败，`IsGatewayTimeout` 进一步判断是否超时（`context.DeadlineExceeded` 或 `net.Error.Timeout()`）。只有安装响应头探针的网关 Store 才会产出 `TransportError`；源站 Store 的错误语义不变（`NewS3Store` 不安装探针，也不类型化传输层失败）。选择器据此把降级 `reason` 分为 `timeout` 与 `transport`。

`S3Store.Get` 按以下顺序分类：

1. 响应头命中 `GatewayHeaderUnavailable` → `ErrGatewayUnavailable`。
2. `minio.ToErrorResponse(err).Code == GatewayCodeUnavailable` → `ErrGatewayUnavailable`。
3. `Code == GatewayCodeSlowDown` → `ErrGatewayRejected`。
4. `isNoSuchObject(err)` → `ErrNotFound`。
5. `StatusCode == 0` 且 `ctx.Err() == nil` → 传输层失败（连不上、TLS、超时、流中断）。
6. 其余 → 原样返回。

minio-go 不暴露响应头，第 1 条由 `Options.Transport` 包装实现：`Get` 在 ctx 里放一个每请求信号结构，`RoundTripper` 读到响应头就写进去。该结构只在 `core/objectstore` 内部使用，不跨越包边界。

选择器的处理：

| `Get` 返回 | 写状态 | 同次调用改为走源站 |
|---|---|---|
| `ErrGatewayUnavailable` | 是，reason=unavailable | 已写字节为 0 时是 |
| 传输层失败 | 是，reason=timeout 或 transport | 已写字节为 0 时是 |
| `ErrGatewayRejected` | 否 | 已写字节为 0 时是 |
| 其余错误（含源站 4xx/5xx、`ErrNotFound`） | 否 | 否 |

「已写字节为 0」由 `backendStore` 用一个计数写入器包住调用方的 `w` 判断。网关在写出任何响应体字节之前完成准入判定。

`reason` 取值：`timeout` 覆盖 `context.DeadlineExceeded` 与 `net.Error.Timeout()`，其余传输层失败记 `transport`。

### 4.5 网关内部接口

```go
// merge
func (r *Registry) Attach(key string) (*Entry, bool)   // 在途且可追随时返回条目
func (r *Registry) Create(key string, buf []byte) *Entry
func (e *Entry) Subscribe() *Sub
func (e *Entry) Pump(ctx context.Context, src io.Reader) error
func (e *Entry) Finish(err error)
func (e *Entry) Release()                              // 引用计数归零时归还缓冲

// sched
func (s *Scheduler) Acquire(ctx context.Context, dataset string) (release func(), err error)

// cache
const RootDir = "/var/lib/traincache-gateway/cache"
var ErrNotFound = errors.New("cache: object not found")   // 盘上没有这一块
var ErrQuota = errors.New("cache: quota exceeded")        // 三步淘汰后仍放不下
func New(dir string, datasetLimit, totalLimit int64) *Store
func (s *Store) Lookup(key string) (*Object, error)    // 盘上没有此块 → ErrNotFound
func (s *Store) BeginPut(ctx context.Context, key string) (*Writer, error)  // 打开 .tmp；配额放不下 → ErrQuota
func (s *Store) Scan(ctx context.Context) error        // 启动时填 last-touch 表
func (s *Store) TotalBytes() int64                     // 盘上总驻留字节
func (s *Store) DatasetBytes(dataset string) int64     // 单个 dataset 的驻留字节
func (s *Store) LastTouch(dataset string) (time.Time, bool)  // dataset 最近一次被读写的时间
type Metadata struct { ETag string; LastModified time.Time; Size int64 }
```

`Attach` 在条目存在、未结束且 `written <= cap(buf)` 三条同时成立时返回条目，任一为假返回 false。

`Object` 是 `io.ReadCloser` 加一个 `Metadata()`；`Writer` 是 `io.Writer`，`Close(Metadata) error` 写完 `.meta` 再把 `.tmp` rename 成正式名，`Abort() error` 删掉 `.tmp`，是写盘中途失败时的收尾出口。server 层负责 `origin.ObjectInfo` 与 `cache.Metadata` 之间的转换，`cache` 包不认识 minio-go。
`Lookup` 只认 rename 之后的正式名，因此永远读不到半块；`BeginPut` 在配额放不下时返回 `ErrQuota`，调用方对已开的 Writer 调 `Abort()` 删掉 `.tmp`，请求照原路返回。
`TotalBytes()`、`DatasetBytes(dataset)`、`LastTouch(dataset)` 读盘上驻留字节与 last-touch 表，quota 淘汰与观测取数都走这三个方法。

## 5. 数据格式

### 5.1 对象键

数据块键 `<dataset>/blocks/<path>#<chunk>`，由 `objectstore.BlockKey` 生成。网关从第一个 `/` 之前取 dataset，用于公平调度、日志字段与缓存目录的第一层；其余部分不解析，只在写盘时整段当相对路径用（5.5）。键里任一以 `/` 分隔的分段超过 255 字节时跳过写盘，回源与合并照常——这是 ext4 的单个目录名上限。

### 5.2 环形缓冲

| 项 | 值 |
|---|---|
| 容量 | `TRAINCACHE_GATEWAY_BLOCK_BUFFER_BYTES`，默认 10485760（10MiB） |
| 稳态内存 | 准入并发 × 容量 = 64 × 10MiB = 640MiB |
| 复用 | `sync.Pool` 存 `*[]byte`，池不限容量 |
| 归还 | 拉取协程结束且订阅者计数为 0，由最后离开的一方归还 |

一个条目内的字段：

| 字段 | 含义 |
|---|---|
| `buf` | 长度等于容量的字节切片 |
| `written` | 已从源站读入的字节总数 |
| `done` / `err` | 拉取协程结束标志与错误 |
| `subs` | 当前订阅者集合 |

订阅者位置 `pos` 是相对对象起的偏移。可读区间恒为 `[pos, written)`。踢出条件 `written - pos > cap(buf)`。交付给客户端的字节只来自 `[0, written)`，任何「还没写满就返回」的分支都不允许。

环形缓冲是按 key 生命周期归还的在途内存，缓存是按配额淘汰的盘上字节，两笔账不重叠。

| `TRAINCACHE_LOG_LEVEL` | `info` | 四级，未知值退化为 info |

Agent env：

| env | 默认 | 说明 |
|---|---|---|
| `TRAINCACHE_GATEWAY_ENDPOINT` | 空 | 非空即启用；空则全部直连 |
| `TRAINCACHE_GATEWAY_SECURE` | `false` | Agent 到网关是否 TLS；与 `TRAINCACHE_OBJSTORE_SECURE` 无关 |
| `TRAINCACHE_OBJSTORE_COMPRESSION` | `false` | Agent 向源站与网关声明 gzip；`1/true/yes` 为真 |

非法值一律拒绝启动，报错格式与 `agent/svc/config.go` 同款：`config: KEY=%q 非法(...)`。

ConfigMap `traincache-config` 里与网关相关的项：`gatewayCache`、`gatewayCacheDatasetBytes`、`gatewayCacheTotalBytes` 由网关 Deployment 引用，Agent 侧不引用；`objstoreCompression` 由 Agent 与网关 Deployment 共同引用；`fetchRangeParallel` 只由 Agent 引用。`objstoreCompression` 与 `fetchRangeParallel` 的取值等于代码默认值，仍写进 ConfigMap，让开关在清单里可见。缓存根目录是代码常量 `/var/lib/traincache-gateway/cache`，不走 env，清单只负责把卷挂到这个路径。

### 5.5 盘上布局与配额

口径：缓存只存 `<dataset>/blocks/` 前缀的块，一份字节留在网关盘上给集群所有节点复用。占用算的是盘上驻写字节，不含在途缓冲。

目录布局把对象键整段当相对路径：

```
/var/lib/traincache-gateway/cache/
  <dataset>/blocks/<path>#<chunk>        块内容
  <dataset>/blocks/<path>#<chunk>.meta   元数据，JSON，字段 etag / last_modified / size
  <dataset>/blocks/<path>#<chunk>.tmp    写入中的临时名，rename 之前对 Lookup 不可见
```

dataset 是第一层目录，回收单位就是这一层目录。`.meta` 与块同名加后缀，一起写、一起删；`.meta` 缺失或解析失败的块按未命中处理，删掉重新回源。

参数（三项都在 5.3 的网关 env 表里，值来自 `traincache-config`）：

| 参数 | 默认 | 分项 |
|---|---|---|
| 单 dataset 上限 | 32GiB | 一个 dataset 在这台网关上最多驻写这么多字节 |
| 全局总上限 | 64GiB | 所有 dataset 加起来的上限，必须 ≥ 单 dataset 上限 |
| 元数据开销 | 每块两个文件 | `.meta` 是百字节级，按块大小 64MiB 算占比低于 0.001%，不计入配额 |

合计：稳态盘上占用 ≤ min(总上限, dataset 数 × 单 dataset 上限)。bench 的 L 档数据集 32GiB，默认的单 dataset 上限正好装下一整个数据集。

卷：网关容器原样保持 `readOnlyRootFilesystem: true`，缓存路径单独挂一个 `emptyDir`，不设 `sizeLimit`——超过总上限由网关自己淘汰，写不进去就不写。

## 6. 关键流程

### 6.1 块 GET 正常流程

1. 解析桶与键，校验桶名；计算 dataset。
2. `Registry.Attach`。命中且 `written <= cap` → 新建 `Sub{pos:0}`，挂上，进入第 7 步。
3. 在途但 `written > cap`（迟到者）→ 不加入，占到桶额度做独立回源。条目还在表里就意味着块还没 rename 落盘，这一分支不查盘。
4. 不在途 → 开关打开时 `Store.Lookup(key)`。
5. 未命中或开关关闭 → `Scheduler.Acquire(ctx, dataset)`。排队超过 2s 或队列已满 64 → 回 503 `XTraincacheGatewaySlowDown`，不写响应体。
6. 拿槽后依次再试一次 `Attach` 与一次 `Lookup`（并发请求可能已建条目，也可能刚把块写完 rename）。`Attach` 命中就释放槽、转订阅者；`Lookup` 命中就带着 `.meta` 里的元数据建条目，拉取协程的 src 换成盘上的 `Object`。两者都没命中才从池取缓冲、`Create` 条目、起拉取协程，用 minio-go `GetObject` 拉源站，边读边写环形缓冲，同时把同一段字节写进 `BeginPut` 打开的 `.tmp`。请求自己作为第一个订阅者。
7. 订阅者循环：等唤醒，从 `[pos, written)` 拷贝到 HTTP 响应，推进 `pos`；`written - pos > cap` 时被踢，响应以断开结束；`done` 后写完剩余字节返回。
8. 拉取协程结束：`done` 分支写完 `.meta` 并 rename，记录 `done/err`，唤醒全部订阅者，从在途表摘除。最后一个订阅者离开时归还缓冲、释放准入槽。
9. 每 60s 输出一条汇总。

读盘条目与回源条目共用同一个准入额度、同一个 10MiB 缓冲，所以稳态内存账（并发额度 × 缓冲）在开关两态、两种命中下都是同一个式子。

### 6.2 迟到与踢出

| 情况 | 处理 |
|---|---|
| 条目在途，`written <= cap` | 加入，从 0 开始读。缓冲能装下整个已写区间 |
| 条目在途，`written > cap` | 不加入，新建一次独立回源（占准入槽），该请求不享受合并。开关打开时这一次回源的字节同样写进盘 |
| 加入后消费落后 `written - pos > cap` | 摘除订阅者，关连接。客户端看到截断，由 `core/fetch` 重试 |
| 拉取协程已结束 | 不在途，按新请求处理。回源正常收尾的块此时已在盘上，走读盘扇出 |
| `Lookup` 打开文件后该块被并发淘汰 | 继续读完。`open` 返回的是 inode 引用，Linux 下 unlink 之后已打开的描述符照常读到文件尾，请求不受影响 |

### 6.3 源站错误

拉取协程第一次读就失败（404、403、5xx）：条目以该错误结束，所有订阅者收到与源站一致的状态码与 `Code`，不带 `x-traincache-gateway` 响应头。已写字节可能为 0，也可能只是一部分；订阅者收到的是「响应已开始但截断」或「未开始」两种情况之一，不做跨订阅者一致性补偿。

拉取协程中途失败：订阅者写完已缓冲的部分后连接断开，错误不额外表达。网关无法回写状态码，客户端只能看到截断。

### 6.4 降级与恢复

行为见 4.3，另加两条边界：

- 正在下载的请求不切换。降级只影响之后新发起的 `Get`。
- 状态只在 Agent 进程内存里，不写 CRD。Agent 重启回到配置默认：`gatewayEndpoint` 非空即 `mode=1`。

### 6.5 准入与公平调度

状态按 dataset 记 `inflight` 与 `waiting`。全局上限 `L` 取 `gatewayBucketConcurrency`。

派发规则（每次释放槽或新请求排队时执行）：

```
A = { d | inflight[d] + waiting[d] > 0 }
base = clamp(floor(L / |A|), 1, floor(L / 2))      // L < 2 时 base = L
候选 = 所有 waiting > 0 的 dataset，按 inflight/base 升序，同比值按到达先后
for d in 候选:
    if inflight[d] < base: 放行一个
    else if 全局 inflight < L 且 没有其他 dataset 在排队: 放行一个
    else: break
```

调度器不做加权、不做抢占。已在途的请求不因份额变化被中止。空闲份额自动让给还在排队的 dataset。排队上限 64，等待上限 2s，超时回 `SlowDown`。

### 6.6 启动与关闭

启动序：读配置 → 初始化日志 → 构造 origin 客户端 → 构造 registry/scheduler/cache → 开关打开时 `Store.Scan()` 填 last-touch 表 → 监听 → ready。扫描是一次 readdir，读每个 dataset 目录的 mtime 填表；某个目录读失败就跳过它并记 Warn，不影响启动。

关闭序：收到 SIGTERM → `readyz` 返回 503 → 停止接受新连接（`Server.Shutdown`）→ 等在途请求结束或满 30s → 取消所有拉取协程的 ctx → 退出。`terminationGracePeriodSeconds` 取 40，留出 10s 余量。

### 6.7 配置加载

`config.Load()` 一次性读 env 并校验：布尔走 `1/true/yes` 口径，整数必须 `>0`，地址用 `net.SplitHostPort` 校验。缓存的两个字节数除 `>0` 外还要求单 dataset 上限 ≤ 总上限。非法值返回错误，进程退出码 1。不做热加载，修改配置靠重启。

### 6.8 缓存写入与淘汰

写入：拉取协程每往缓冲写一段，同一批字节写进 `.tmp`；正常收尾时写完 `.meta` 再 rename 成正式名。中途失败（源站截断、TLS 断开、ctx 取消）删掉 `.tmp`，盘上不留半成品。独立回源那条分支不建条目，字节同样按这个协议落盘；同一个 key 被两个请求同时回源时，两个 `.tmp` 各自 rename，后一个覆盖前一个，内容相同。写盘出错不改变响应：字节照原路交给订阅者，只是下一次同样的请求还要回源。

淘汰按三步，顺序固定，在每次要写盘之前算一次：

| 步 | 条件 | 动作 |
|---|---|---|
| 1 | 该 dataset 的驻写字节超自己的上限 | 按块文件 mtime 从老到新删这个 dataset 里的块，`.meta` 同批删，删到回到上限内 |
| 2 | 全局驻写字节仍超总上限 | 按 last-touch 表挑最久没出现的 dataset，删掉它的整个第一层目录，删到回到总上限内或只剩请求中这一个 dataset |
| 3 | 前两步做完仍放不下这个块 | 本次不写盘 |

块的 mtime 是写盘时间，第 1 步因此是先写先删；空闲判断只用在 dataset 一层的第 2 步，读的是 last-touch 表。这张表记在进程内存里：dataset → 最后出现时间，读命中与写盘成功都刷新，启动时由 `Store.Scan()` 按目录 mtime 填。Linux 上目录 mtime 只在条目增删时变，纯读不刷新，拿它判空闲会在长时间全命中时误删（见 9.2 D33）。

配额与准入是两套账，不同形：准入按活跃 dataset 均分的是短期占用的下载槽，一个槽几秒就还回去；配额管的是长期驻写的字节，dataset 数一变就触发一轮淘汰的均分规则用在这里不成立。

## 7. 日志与可观测性

### 7.1 日志封装

### 7.3 60s 汇总

每 60s 一条 Info，`msg` 固定 `gateway: 60s 汇总`：

| 字段 | 含义 |
|---|---|
| `window_s` | 窗口秒数 |
| `gets` | 块 GET 总数 |
| `merged` | 挂到已有条目的请求数 |
| `owners` | 新建条目数，即真实源站 GET 数 |
| `passthrough` | 直通 GET/HEAD 数 |
| `kicked` | 被踢订阅者数 |
| `rejected` | 准入拒绝数 |
| `cache_hit` | 字节从盘上取走的请求数。开关关闭时恒为 0 |
| `bytes` | 本窗口从源站读入的字节数 |
| `datasets` | 窗口内出现过的 dataset 数 |

`merged / gets` 是在途合并的命中率，`cache_hit` 单独一列，两列相加才是网关接住的请求占比，`owners` 是回源次数。错峰到达的请求由 `cache_hit` 记账，「扇出必须同时发起」这个前提只约束 `merged` 那一列。实验对账用这几列，不依赖网关指标端点。

### 7.5 排查路径

| 现象 | 先看 |
|---|---|
| 训练读变慢、源站流量没降 | 网关 60s 汇总的 `merged/gets` 与 `kicked` |
| Agent 全部直连 | Agent 日志 `gateway fallback` 行的 `reason`；网关 `readyz` 与重启记录 |
| 只有部分节点直连 | 该节点 Agent 日志；网关汇总里 `rejected` 是否集中 |
| 网关 5xx 但源站正常 | 网关 `panic 恢复` 与 `准入拒绝` 行 |
| 缓存没接住请求 | 汇总的 `cache_hit`；网关盘上该 dataset 目录的驻写字节；`淘汰` 与 `写盘失败` 行；`gatewayCache` 是否为 `true` |

## 8. 风险与约束

| 编号 | 约束 | 影响 |
|---|---|---|
| K1 | 合并窗口是「条目在途且 `written <= 10MiB`」。8MiB 块覆盖整块；64MiB 块只覆盖前 10MiB（约 16%）。错峰到达的请求不合并 | 关闭缓存时实验的扇出必须同时发起，否则这一列收益接近 0；开启时错峰重复由 `cache_hit` 接住 |
| K2 | 单副本。更新或重启必然有一次切换 | 靠 SIGTERM 排水把影响压到「新连接去新 Pod」 |
| K3 | 网关不合并 HEAD。每个块仍然从源站过一次 HEAD | 源站请求数 = N 个 HEAD + 1 个 GET；字节是 1/N |
| K4 | 拉取协程中途失败时盘上没有补偿：`.tmp` 被删，正式名从未出现 | 客户端看到截断，由 `core/fetch` 重试 |
| K5 | 入站不认证 | 集群内任意 Pod 可用该 Service；单租户集群接受 |
| K6 | 网关是新增的故障域 | 网关故障时 Agent 全部直连，源站流量回到 N。Agent 在一次请求内完成降级，不阻塞读路径 |
| K7 | `CURRENT`/`manifest` GET 不合并、不进缓存 | N 个 Agent 每 5s 各回源一次，源站请求数随 N 线性。基线如此规定，实验单列 |
| K8 | 网关内部错误码与 `core/objectstore` 常量各写一份 | 两边取值由 4.2 与 4.4 冻结，修改一处必须同批修改另一处，由测试断言 |
| K9 | 缓存卷随 Pod 删除而清空（`emptyDir`）。网关 Pod 重建后盘是空的 | 之后每个块各回源一次并回填；容器重启（同一 Pod）盘上内容还在，靠启动 `Scan()` 认回来 |
| K10 | `emptyDir` 落在节点盘上，与 Agent 的 CAS 缓存同一个文件系统 | 两处配额之和要给节点盘留余量；写满会触发节点磁盘压力驱逐，代价由部署方承担 |
| K11 | 数据集小于节点本地盘、块一直留在节点盘上时，网关缓存零收益 | 同一份字节在集群里多一份，取数还多一跳。开启与否按 9.0「缓存层」的收益条件判 |
| K12 | 命中省的是 GET 的次数与字节，HEAD 照旧到源站 | 每次块读的 N 个 HEAD 不变，源站请求数下限由 HEAD 决定 |

三处与 `9.0` 基线不同：HEAD 不合并（D1）、缓冲默认 10MiB 而非 5MiB（D7）、Agent 到网关的 TLS 开关独立于源站（D16），原由与结论见 `9.2`。

## 附录 A：Agent 使用的 S3 操作

| S3 操作 | HTTP 形式 | Store 方法 | Agent 是否用 | 是否走网关 |
|---|---|---|---|---|
| GetObject | `GET /<bucket>/<key>` | `Get` | 是，唯一的块取数入口 | 是，块键走合并与缓存，其他键直通 |
| HeadObject | `HEAD /<bucket>/<key>` | `Get` 内部 `obj.Stat()`；`GetETag` | 是，每次 `Get` 前置一次 | 是，直通不合并 |
| GetBucketLocation | `GET /<bucket>?location=` | minio 内部 | 网关客户端固定 `Region`，不触发 | 否 |
| PutObject | `PUT /<bucket>/<key>` | `Put` | 是，读者声明（reader claim）心跳 | 否，直连源站 |
| ConditionalPut | `PUT` + `If-Match` / `If-None-Match` | `PutIfMatch` | 仅探测开关打开时 | 否，直连源站 |
| DeleteObject | `DELETE /<bucket>/<key>` | `Delete` | 是，claim 清理、GC | 否，直连源站 |
| ListObjects | `GET /<bucket>?list-type=2` | `List` | 是，重扫描（rescan）枚举、`knownDatasets` | 否，直连源站 |

结论：网关对外只需 GetObject 与 HeadObject 两种对象操作。
