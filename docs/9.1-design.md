# S3 合并回源网关设计（design）

## 定位

网关坐在 Agent 与源站之间，目标是降低回源次数。重复块有两个来源：预热扇出（preheatFanout）会让多个节点要同一批块；同一个 DataSet 上并发多个 WarmupTask 时，shuffle seed 不同，不同节点也会要同一块。两条手段各管一段：在途合并管同时到达的请求，源站只看到一次字节传输；磁盘缓存管错峰到达的重复，一个块只在第一次回源时付一份出口流量。在途合并的机制与节点内 `core/fetch` 的同键在途表相同，只是作用范围从单个节点扩到集群内所有 Agent。

开关关闭时网关只做在途合并，开启时（默认开启）在途合并之外加一层磁盘缓存。关闭态的口径是不命中不返回、不落盘、不管容量和淘汰；关闭态下同一块每个节点各付一份字节，出口流量等于源站带宽乘以节点数。开启态一份字节留在网关盘上给集群所有节点复用，省的是源站出口字节：一次错峰重复读省一个整块，64MiB 块合 0.0625GiB；请求数的单价比字节低几个数量级，不为它做设计。

命中来源有三条：节点本地盘被水位淘汰之后重下、新 Pod 冷启动、错峰迟到者。节点盘没满、块还在本地盘上时这层缓存零收益——同一份字节在集群里多一份，取数还多一跳——数据集大于节点盘时才有收益。窗口外「集群里某个节点已经有这块」的重复原本交给分布式缓存组，缓存组不做，这一段由网关的缓存层承接。

合并路径只收 `<dataset>/blocks/` 前缀的整对象 GET。带 Range 的请求、非块键的 GET 与全部 HEAD 直接透传源站；PUT、DELETE、LIST 一律 405。Agent 的块下载默认把每个块拆成 4 条 Range GET 并行取（`core/fetch` 的开关，默认打开），这些请求到网关仍是带 Range 的，既不查在途表也不查缓存，字节不写盘；不携带 Range 的整对象请求才进合并与缓存。入站不认证，条件是集群内网可达：单租户集群接受集群内任意 Pod 使用这个 Service。S3 GET 不携带上游的优先级标记，网关不做请求分级、不做 AIMD 背压、不做零拷贝，数据通路只有环形缓冲一种。

## 位置与部署形态

位置在集群侧，所有节点的 Agent 通过同一个 Service 访问网关。网关是独立进程、集中式部署：一个 Kubernetes Deployment、单副本，不是 DaemonSet——每节点一个等于回到节点内合并，跨节点没有效果。单副本是在途合并成立的前提，合并与缓存都只在这一个进程里成立，更新或重启必然有一次切换，所以更新用 Recreate 策略并靠 SIGTERM 排水把影响压到新连接去新 Pod。

网关不紧贴源站部署：贴源站时 N 份字节照样从存储节点网卡出去，省下的只是源站的 CPU 和磁盘读，带宽一分没省。源站是公网按 GB 计费的桶时挂网关收益最大；同机房自搭 MinIO 照样挂，允许与 MinIO 落在同一个节点，但必须是两个独立 Pod——网关与 MinIO 同 Pod 时两侧共享网络命名空间，省下的那 1 份字节走 lo 接口，挂在 eth0 上的限速器管不到，实验做不成。网关也不放到控制平面：数据面流量会挤占 etcd 与 apiserver 的 CPU 与网卡，控制面还是集群级故障域。

资源量级：出口等于源站带宽乘以节点数 N，单副本能扛的 N 是网关节点网卡带宽除以源站出口带宽；按 1Gbps 桶、N 为扇出 2 到 3 估，出口 2 到 3Gbps，是 25Gbps 网卡的一到两成。CPU 只有到源站那一段 TLS 加用户态拷贝，2 核量级。内存是扇出缓冲，在途块数乘以每个缓冲区大小，64 × 10MiB = 640MiB，两态相同，热池另留 32 块；Deployment 的内存 limit 取 1.5Gi。磁盘在关闭态是零，开启态是宿主盘上的缓存配额，等于单 dataset 上限乘以 dataset 数，另留全局总上限的余量。默认跟 Agent 混部，不必独占节点，用 requests/limits 保住自己的资源；只有当命中侧要付的读带宽被宿主盘拖住（宿主盘是顺序读低于 300MB/s 的 HDD，或同节点邻居写盘活跃）时，才给网关单独一块盘。开启缓存后出口分两段：命中侧的字节从网关盘上出，等于各节点取速率之和，4 节点 @1000 档是 500MB/s 即 4Gbps；未命中侧还是源站那一份 1Gbps，合计仍是 25Gbps 网卡的不到两成。

## 信任边界

Agent 到网关走集群内网明文 HTTP，默认不加密，可以做成 TLS 但默认关；TLS 只在网关到源站那一段终止一次，全集群的加解密量从 N 降到 1。这一设计只按集群全部在网内假设：一半节点在集群外的混合拓扑下，明文段会走出集群边界，加密与信任结论都不成立。

源站的 accessKey 与 secretKey 两把凭证，网关与 Agent 都需要有。Agent 发给网关的请求带的是按网关这个 host 算好的 SigV4 签名，网关忽略它；转发给源站前要用网关自己那份凭证重签，所以只有 AccessKey 不够。凭证照旧从挂进 Pod 的 Secret `traincache-objstore` 取，不经任何下发。

Agent 侧的网关地址配置项是 `TRAINCACHE_GATEWAY_ENDPOINT`，值写在 ConfigMap `traincache-config` 的 `gatewayEndpoint`，与已有的源站地址配成一对：非空即启用，空则全部直连。`DataSet.spec.endpoint` 只归 Controller 用，是它校验 DataSet 时读 CURRENT 与 manifest 的地址，从不下发给 Agent。

## 网关 HTTP 契约

服务端只接受下列请求，其余一律 405 `MethodNotAllowed`（带 `Allow: GET, HEAD` 头）：

| 请求 | 行为 |
|---|---|
| `GET /healthz` | 200，纯文本 `ok`。进程存活即成功，不依赖源站 |
| `GET /readyz` | 200 表示可服务；收到 SIGTERM 后立即 503 |
| `HEAD /<bucket>/<key>` | 直通源站。不合并，不占准入额度 |
| `GET /<bucket>/<key>`，键不以 `<dataset>/blocks/` 开头 | 直通源站。不合并，不占准入额度 |
| `GET /<bucket>/<key>`，键以 `<dataset>/blocks/` 开头且不带 Range 头 | 先查在途表，再查盘，两者都没有才占一个准入额度回源 |
| `GET /<bucket>/<key>`，块键且带 Range 头 | 带 Range 回源，原样透传 206 响应。不合并、不查盘、不写盘 |

桶名必须等于网关配置的桶，否则 404 `NoSuchBucket`；键为空回 404 `NoSuchKey`；Range 头语法不合法或区间越界回 416 `InvalidRange`。

对象键格式：数据块键 `<dataset>/blocks/<path>#<chunk>`，由 `objectstore.BlockKey` 生成，`path` 不含 `#`。`<dataset>` 取对象键第一个 `/` 之前的部分，用于公平调度、日志字段与缓存目录的第一层；其余部分不解析，只在写盘时整段当相对路径用。键里任一以 `/` 分隔的分段超过 255 字节时跳过写盘，回源与合并照常——这是 ext4 单个目录名的上限。

块键 GET 的合并响应（200）回填 `Last-Modified` 与 `ETag`，不设 `Content-Length`（保持 chunked）。minio-go v7.3.0 的 `ToObjectInfo` 对每个 GET 响应无条件解析 `Last-Modified`，缺失即报 `InternalError`，所以合并响应必须带这两个头；元数据复用这次 GET 的响应头，不额外发 HEAD。读盘命中的响应回填写盘时存进 `.meta` 的那一份，块不可变，所以它与 Agent 这次直通源站 HEAD 的结果一致。

`CURRENT` 与 manifest 是快照指针，内容每 5s 变一次，Agent 每 5s 跟随一次；这两类 GET 若被合并，旧快照的值会返给迟到的请求，跟随就停在旧快照上，所以它们与 Put、List 一样不进在途表也不进缓存。代价随之而来：合并路径不碰 HEAD，每个块仍然从源站过一次 HEAD，源站请求数是 N 个 HEAD 加 1 个 GET，回源字节是 1/N；每次块读的 N 个 HEAD 不变，源站请求数下限由 HEAD 决定。

## 错误响应

所有错误响应体是 S3 的 XML 格式，`Content-Type: application/xml`，Code 与 Message 中的 `<>&` 统一转义：

```xml
<Error><Code>XTraincacheGatewayUnavailable</Code><Message>gateway origin request failed</Message></Error>
```

| 场景 | 状态码 | `x-traincache-gateway` | `Code` |
|---|---|---|---|
| 网关自身失败（条目创建失败、拉取协程内部错误、panic 恢复） | 503 | `unavailable` | `XTraincacheGatewayUnavailable` |
| 准入排队超时、队列满 | 503 | 无 | `XTraincacheGatewaySlowDown` |
| 源站返回的错误（任何状态码，含 4xx/5xx） | 原状态码 | 无 | 与源站一致的 `Code` |
| 源站连不上、TLS 失败、超时 | 504 | 无 | `XTraincacheGatewayOriginUnavailable` |
| 方法不支持 | 405 | 无 | `MethodNotAllowed` |
| 桶名不符 | 404 | 无 | `NoSuchBucket` |

判断标准只有一条：`x-traincache-gateway: unavailable` 只表示「网关这一跳坏了」，不表示源站坏。源站故障一律原样透传、不带该头——把源站的 5xx 也算成网关失效，会把源站的问题盖成网关的问题。网关内部错误码与 `core/objectstore` 的常量各写一份，两边取值就是上面这张表，修改一处必须同批修改另一处，由契约测试断言。

## 迟到请求由谁服务

一个块 GET 到达时按三层顺序决定谁来服务：

| 层 | 条件 | 由谁服务 |
|---|---|---|
| 1 | 同一 key 在途 | 网关扇出，0 次额外回源 |
| 2 | 窗口外，但网关盘上已经有这块 | 网关读盘扇出，0 次回源 |
| 3 | 盘上没有 | 回源，付整份字节，字节同时写进盘 |

关闭缓存开关时第 2 层没有承接者，同一块每个节点各付一份字节；这一层接住的量就是缓存层的收益。合并窗口是「条目在途且已写字节不超过一个缓冲容量」：8MiB 实验块整块落在 10MiB 缓冲内，生产 64MiB 块只覆盖前 10MiB（约 16%）。错峰到达的请求不合并；关闭缓存时实验的扇出必须同时发起，否则这一列收益接近 0，开启缓存后错峰重复由读盘路径接住。

## 取数与扇出

一次块 GET 正常走完这样一条路：请求先解析桶与键、校验桶名、算出 dataset；然后查在途表，命中且还能追上就挂为订阅者。不在途时分两条：没有并发条目在途才查盘，命中就用盘上的对象当来源；查不到或开关关闭就占一个准入额度，拿到槽后再试一次在途表与一次查盘（并发请求可能已建条目，也可能刚把块写完落盘），两者都命中不了才从池里取缓冲、创建条目、起拉取协程回源。请求自己作为第一个订阅者从缓冲取字节。

拿到槽之后发现条目在途但已迟到的请求不加入条目：它从 0 开始读，而 0 处的字节已经被覆盖，加入只会立刻被踢；它占着槽做一次独立回源，开关开着时这次回源的字节同样写进盘。独立回源这条分支不查盘——条目还在表里就意味着块还没落盘。创建条目前条目恰好结束的窗口也有兜底：订阅动作在条目已结束或缓冲已归还时返回失败，该请求转为独立回源，绝不能交付空 200。

字节路径只有一条流式通道：拉取协程把源站（或盘）的字节一段段写进该条目的环形缓冲，每写一段唤醒全部订阅者，每个订阅者从自己的位置拷走 `[pos, written)` 区间的字节写进自己的 HTTP 响应，每段写完立即冲刷，让客户端边下边收。禁止整块缓冲完再分发，否则单请求的内存占用达到整个对象大小。拉取协程只看自己的写入进度，不看任何订阅者读没读完；读盘扇出与读源站扇出是同一条路径，只是协程一侧从盘上读，订阅者、游标与踢出规则都不变，共用同一个准入额度、同一个缓冲，所以稳态内存账在开关两态、两种命中下都是同一个式子。

条目结束：正常收尾时写 `.meta` 再把临时文件 rename 成正式名，记录结束状态与错误，唤醒全部订阅者，从在途表摘除；最后一个订阅者离开时归还缓冲并释放准入槽，两者都只归还一次。所有订阅者都离开而拉取还在进行时，取消源站请求，不让它继续下载没人要的数据。

失败分支的行为：

- 拉取协程第一次读就失败（404、403、5xx、连不上）：条目以该错误结束，还没收到字节的订阅者拿到与源站一致的状态码与 `Code`，不带 `x-traincache-gateway` 头；已经收到过部分字节的订阅者只看到响应截断。
- 拉取协程中途失败：订阅者写完已缓冲的部分后连接断开。状态码早已发出，网关无法回写，错误不额外表达；盘上的半成品临时文件被删掉，正式名从未出现，客户端看到的截断由 `core/fetch` 的既有重试重新发起一次 GET。
- 订阅者消费落后超过缓冲容量：在挂载时落后，直接独立回源；加入之后落后，被摘掉订阅并断开连接，客户端同样看到截断，由 `core/fetch` 重试。被踢的那次传输浪费了已发送的字节，60s 汇总的 `kicked` 列就是观察这个成本的。这防的是慢消费者占住整个扇出（head-of-line blocking）；发起请求本身也走订阅者通道，客户端再慢也只影响自己。

## 环形缓冲

| 项 | 值 |
|---|---|
| 容量 | `TRAINCACHE_GATEWAY_BLOCK_BUFFER_BYTES`，默认 10485760（10MiB） |
| 稳态内存 | 准入并发 × 容量 = 64 × 10MiB = 640MiB |
| 热池 | 归还的缓冲先进 32 块的 LIFO 热表，表满才交给 `sync.Pool`；池不限容量 |
| 归还 | 拉取协程结束且订阅者计数为 0，由最后离开的一方归还，只归还一次 |

条目内维护缓冲 `buf`、已写入字节总数 `written`、结束标志与错误、订阅者集合。偏移 `i` 的字节存放在 `buf[i % 容量]`，越过尾部绕回 0；订阅者可读区间恒为 `[pos, written)`，踢出条件 `written - pos > 容量`。交付给客户端的字节只来自 `[0, written)`：复用的缓冲里留着上一个对象的字节，任何「还没写满就返回」的分支都会把上一个 dataset 的字节混进本对象的响应。基线的归还条件「最后一个订阅者被踢就归还」存在一种时序——订阅者全被踢、拉取协程仍在写，缓冲被下一个条目复用时旧字节会进新对象的响应——所以归还条件加上「拉取协程已结束」。单次交付上限 256KiB：一次把全部可读字节拷给每个订阅者会让整条扇出的瞬时内存翻倍，扇出上限取满并发准入 64；限长后瞬时拷贝上界是订阅者数乘 256KiB。

配置项只有单块缓冲的大小，没有「总缓冲区大小」这一项：稳态内存已经由准入并发数与单块容量的乘积定住。缓冲是按 key 生命周期归还的在途内存，缓存是按配额淘汰的盘上字节，两笔账不重叠。

## 准入与公平调度

到桶的并发下载数限制在 64 个（`TRAINCACHE_GATEWAY_BUCKET_CONCURRENCY`，实际要按桶的 QPS 调参）。额度按活跃 dataset 公平分配，防止一个 WarmupTask 把另一个饿死：全局上限 L，活跃集合 A 是「在途加排队大于 0」的 dataset，每份额 `base = clamp(floor(L/|A|), 1, floor(L/2))`，L 小于 2 时 base 取 L；候选按在途数升序（同比值按到达先后），在途数小于一份额就先放行，达到一份额后只有「全局还有空位且没有其他 dataset 在排队」才放行。单 dataset 因此能用满全部额度，两个 dataset 各占一半，三个 dataset 每份额保底 1，空闲份额自动让给还在排队的。不做加权、不做抢占，已在途的请求不因份额变化被中止。

排队上限 64，单请求最长排队 2s，排队超时或队列满回 503 `XTraincacheGatewaySlowDown`，不写响应体。准入到顶、缓冲到顶把请求拒回直连不算网关失效：那是容量信号，一次性，不写进降级状态。

用 bench 装置测试时，网关的并发额度必须明显高于被测的 tc 档位，也高于集群内 Agent 的合计下载并发，否则串联两个瓶颈：Agent 每进程 16 个下载任务，bench 的 warmup fanout 默认 2，warmup 阶段两个 Agent 合计 32 条连接；放行后落点节点若不在预热集合里再起 16 条需求读，峰值约 48。默认 64 高于这个峰值。

## 盘上布局与配额淘汰

缓存只存 `<dataset>/blocks/` 前缀的块，占用算的是盘上驻写字节，不含在途缓冲。目录布局把对象键整段当缓存根目录下的相对路径，dataset 是第一层目录，回收单位就是这一层目录：

```
/var/lib/traincache-gateway/cache/
  <dataset>/blocks/<path>#<chunk>        块内容
  <dataset>/blocks/<path>#<chunk>.meta   元数据 JSON，字段 etag / last_modified / size
  <dataset>/blocks/<path>#<chunk>.tmp    写入中的临时名，rename 之前对查盘不可见
```

写入：拉取协程每往缓冲写一段，同一批字节写进 `.tmp`；正常收尾时先写 `.meta` 再把 `.tmp` rename 成正式名。查盘只认 rename 之后的正式名，任何请求读不到半块。`.meta` 与块同名加后缀，一起写、一起删；`.meta` 缺失或解析失败的块按未命中处理，删掉重新回源。中途失败（源站截断、TLS 断开、ctx 取消）删掉 `.tmp`，盘上不留半成品。同一个 key 被两个请求同时回源时，两个临时文件各自 rename，后一个覆盖前一个，内容相同。写盘出错不改变响应：字节照原路交给订阅者，只是下一次同样的请求还要回源，缓存里写不进字节只影响下一次命中率。

配额按 dataset 定：单 dataset 上限默认 32GiB，全局总上限默认 64GiB 且必须不小于单 dataset 上限，两个值都来自 `traincache-config`。稳态盘上占用不超过 min(总上限, dataset 数 × 单 dataset 上限)；bench 的 L 档数据集 32GiB，默认的单 dataset 上限正好装下一整个数据集。元数据 `.meta` 是百字节级，按块大小 64MiB 算占比低于 0.001%，不计入配额。

淘汰按三步，顺序固定，在每次要写盘之前算一次：

| 步 | 条件 | 动作 |
|---|---|---|
| 1 | 该 dataset 的驻写字节超自己的上限 | 按块文件 mtime 从老到新删这个 dataset 里的块，`.meta` 同批删，删到回到上限内 |
| 2 | 全局驻写字节仍超总上限 | 按 last-touch 表挑最久没出现的 dataset（并列取字典序小的），删掉它的整个第一层目录，删到回到总上限内或只剩请求中这一个 dataset |
| 3 | 前两步做完仍放不下这个块 | 本次不写盘 |

块的 mtime 是写盘时间，第 1 步因此是先写先删；空闲判断只用在第 2 步，读的是 last-touch 表。这张表记在进程内存里（dataset 到最后出现时间），读命中与写盘成功都刷新；Linux 上目录 mtime 只在条目增删时变，一轮实验读 20 分钟全命中时 mtime 不动，拿目录 mtime 判空闲会误删正在被读的 dataset，所以表必须在内存里维护。启动时扫一遍缓存根目录填表：按 dataset 目录的 mtime 记最后出现时间，按块文件重建驻写字节账，顺手清掉上个进程留下的 `.tmp`；某个目录读失败就跳过它并记 Warn，不影响启动。

缓存卷：网关容器保持 `readOnlyRootFilesystem: true`，缓存路径单独挂一个 `emptyDir`，不设 `sizeLimit`——超过总上限由网关自己淘汰，写不进去就不写；`sizeLimit` 一到 kubelet 就驱逐 Pod，淘汰压力变成调度事件，实验不可复算。`emptyDir` 随 Pod 删除清空，网关 Pod 重建后盘是空的，之后每个块各回源一次并回填；容器重启（同一 Pod）盘上内容还在，靠启动扫描认回来。`emptyDir` 落在节点盘上，与 Agent 的 CAS 缓存是同一个文件系统，两处配额之和要给节点盘留余量。

## 缓存开关与取数顺序

缓存开关的值写在 ConfigMap `traincache-config` 的 `gatewayCache`，环境变量 `TRAINCACHE_GATEWAY_CACHE`，默认开。清单不因开关分叉：卷常挂，开关只控制读不读写——关闭态网关不构造缓存存储、不扫描盘、不查盘也不写盘，走改动前的取数路径；带缓存与不带缓存两个实验臂除这个开关外装置完全相同，否则两臂对照不成立。开启态比关闭态多出的东西——查盘那一步、命中侧出口带宽、磁盘配额与计量——都写在上面的取数与淘汰两节里。

取数顺序合起来是三句话：先看有没有在途条目，有且能追上就挂上去扇出；没有就查盘，命中就从盘读出来扇出；盘上也没有才回源，回源的字节一边扇出一边写进盘。开启缓存后多一种冷启动：网关重启、盘是空的，之后的请求逐个回源、逐个回填；回源成功走的是正常路径，不触发 Agent 的降级判断，也不写进降级状态。

网关没有指标端点，实验对账靠 60s 汇总日志。

## Agent 侧后端选择

`backendStore` 实现 `objectstore.Store`（含 `RangeStore` 的区间读取），只截获 `Get` 与 `GetRange`；`Put`、`Delete`、`GetETag`、`PutIfMatch`、`List` 一律转源站客户端。`gatewayEndpoint` 为空时不构造网关 Store，行为与没有网关时完全一致：同一构造函数、同一超时、同一错误语义。

降级状态是 Agent 进程里的四个量，全节点一份，不区分 dataset：

| 字段 | 含义 |
|---|---|
| `mode` | 0 直连源站，1 走网关 |
| `gen` | 每次模式变化加一，用于丢弃过期结果 |
| `nextProbe` | 下次允许试网关的单调时刻；零值表示不限制 |
| `backoff` | 当前退避时长；0 表示从 10s 起点开始 |

同一节点上所有 dataset 的取数在发起前都问同一句「现在走哪个后端」，问的是同一个量，所以降级与恢复都是整个节点一起。状态迁移：

| 事件 | 迁移 |
|---|---|
| 启动 | `mode=0`；`GatewayEndpoint` 非空时 `mode=1`、`nextProbe=0` |
| `mode=1`，请求成功 | 不变 |
| `mode=1`，请求命中失败判断标准 | `mode=0`；`backoff = min(2×backoff 或 10s, 120s)`；`nextProbe = now+backoff`；`gen` 加一 |
| `mode=0`，未到 `nextProbe` | 直接走源站，不探测 |
| `mode=0`，到 `nextProbe` 且抢到探测权 | 该请求走网关；成功则 `mode=1`、`backoff=0`、`nextProbe=0`、`gen` 加一；失败按上一行处理 |
| `mode=0`，到 `nextProbe` 但没抢到探测权 | 直接走源站 |

不需要专门的健康检查通道，下一次回源请求就当探针。探测权用互斥抢占：抢到时把 `nextProbe` 推到 5s 后，其余并发请求看到未来的时刻就直连，同一时刻最多一个请求发到网关。失败结果按代际丢弃：请求开始时记下 `gen`，失败时若 `gen` 已变，说明期间发生过恢复，该结果不写状态，避免恢复瞬间到达的旧失败结果把状态又打回去。

失败或拒绝时，只有向调用方写出的字节数为 0，才在同一次 `Get` 内改为走源站一次；已写字节非 0 直接返回错误。`core/fetch` 用管道把 `Get` 接到本地写盘，部分字节已经落进临时文件，重试会从头再写一遍污染内容。网关在写出任何响应体字节之前完成准入判定，所以这条规则对准入拒绝总是成立。

这个状态只活在 Agent 进程内存里，不写回任何 CRD：DataSet 对象不变，Controller 不知道哪个节点在降级。Agent 重启回到配置默认，网关地址非空即启用。正在下载的请求不切换，降级只影响之后新发起的取数。

## 失败判断标准

失败的判定条件具体是三种：连不上、TLS 握手失败、超时。只有网关自己那一跳的 5xx 算失效；源站透传上来的 5xx 不算——直连同样会失败，切过去只是把源站的问题盖成网关的问题。403、429 两个状态码不算，需要特例。准入到顶、缓冲到顶把请求拒回直连不算失效，一次性，不写进降级状态。

`core/objectstore` 侧按以下顺序给一次网关 `Get` 的错误分类：

1. 响应头 `x-traincache-gateway: unavailable` 命中——`ErrGatewayUnavailable`。
2. `minio.ToErrorResponse(err).Code` 等于 `XTraincacheGatewayUnavailable`——`ErrGatewayUnavailable`。
3. `Code` 等于 `XTraincacheGatewaySlowDown`——`ErrGatewayRejected`。
4. 对象不存在——`ErrNotFound`。
5. HTTP 状态码为 0 且 ctx 未取消——传输层失败（连不上、TLS、超时、流中断），包成 `TransportError`。
6. 其余原样返回（含源站 4xx/5xx）。

minio-go 不暴露响应头，第 1 条由包装的 `RoundTripper` 实现：`Get` 在 ctx 里放一个每请求探针，传输层读到响应头就写进去，错误分类时结合探针与 Code。探针只在 `core/objectstore` 内部使用，不进接口。只有安装了探针的网关 Store 才产出 `TransportError`；源站 Store 的错误语义不变。

选择器据此决定是否写降级状态、是否同次改走源站：

| `Get` 返回 | 写降级状态 | reason | 同次改走源站 |
|---|---|---|---|
| `ErrGatewayUnavailable` | 是 | `unavailable` | 已写字节为 0 时是 |
| 传输层失败 | 是 | 超时记 `timeout`，其余记 `transport` | 已写字节为 0 时是 |
| `ErrGatewayRejected` | 否 | 无 | 已写字节为 0 时是 |
| 其余错误（含源站 4xx/5xx、`ErrNotFound`） | 否 | 无 | 否 |

网关客户端固定 `Region="us-east-1"` 与 `MaxRetries=1`，写在 `agent/svc` 的构造常量里，不开放配置：Region 为空时 minio-go 会先发 `GET /<bucket>?location=` 查桶位置，固定区域后网关只需处理 GET 与 HEAD；minio-go v7.3.0 中 `MaxRetries` 的语义是总尝试次数，1 表示不重试，SDK 默认对 503 退避重试 10 次，会把一次控制信号放大成十次请求并挤占调用方的超时预算。源站客户端两值都不设，沿用既有行为。构造入口是 `NewS3StoreWithOptions(endpoint, accessKey, secretKey, bucket, secure, opts)`，`Options` 带 `Transport`、`Region`、`MaxRetries`、`Compression` 四个字段，`NewS3Store` 的签名与错误语义不变。

## 配置

网关进程读取的环境变量：

| env | 默认 | 说明 |
|---|---|---|
| `TRAINCACHE_OBJSTORE_ENDPOINT` | `127.0.0.1:9000` | 源站地址，不带 scheme，host 必须非空 |
| `TRAINCACHE_OBJSTORE_ACCESS_KEY` / `SECRET_KEY` | 空 | 源站凭证，来自 Secret |
| `TRAINCACHE_OBJSTORE_BUCKET` | `traincache` | 唯一服务的桶 |
| `TRAINCACHE_OBJSTORE_SECURE` | `false` | 网关到源站是否 TLS |
| `TRAINCACHE_OBJSTORE_COMPRESSION` | `false` | 网关向源站声明 gzip；带 Range 的请求不参与协商 |
| `TRAINCACHE_GATEWAY_LISTEN` | `:9413` | S3 与探针共用监听地址 |
| `TRAINCACHE_GATEWAY_BUCKET_CONCURRENCY` | `64` | 到桶并发上限，正整数 |
| `TRAINCACHE_GATEWAY_BLOCK_BUFFER_BYTES` | `10485760` | 单块环形缓冲字节数，正整数 |
| `TRAINCACHE_GATEWAY_CACHE` | `true` | 磁盘缓存开关；未设置即开，`1/true/yes` 开，其余取值关 |
| `TRAINCACHE_GATEWAY_CACHE_DATASET_BYTES` | `34359738368` | 单 dataset 盘上驻写上限（32GiB），正整数 |
| `TRAINCACHE_GATEWAY_CACHE_TOTAL_BYTES` | `68719476736` | 全局总上限（64GiB），正整数，且不小于单 dataset 上限 |
| `TRAINCACHE_LOG_LEVEL` | `info` | 四级，未知值退化为 info |

Agent 侧相关：

| env | 默认 | 说明 |
|---|---|---|
| `TRAINCACHE_GATEWAY_ENDPOINT` | 空 | 非空即启用；空则全部直连 |
| `TRAINCACHE_GATEWAY_SECURE` | `false` | Agent 到网关是否 TLS；与 `TRAINCACHE_OBJSTORE_SECURE` 无关 |
| `TRAINCACHE_FETCH_RANGE_PARALLEL` | `true` | 每个块拆成 4 条 Range GET 并行下载；非法值拒绝启动 |

校验口径：布尔取 `1/true/yes`（大小写不敏感，`TRAINCACHE_GATEWAY_CACHE` 用同一口径但未设置即开）；整数必须大于 0；地址用 `net.SplitHostPort` 校验、端口限 1 到 65535；缓存两个字节数还要求单 dataset 上限不大于总上限。非法值返回错误、进程退出码 1，报错格式与 `agent/svc/config.go` 同款。一次性读取，不做热加载，修改配置靠重启进程。缓存根目录 `/var/lib/traincache-gateway/cache` 是代码常量，不走 env，清单只负责把卷挂到这个路径。

ConfigMap `traincache-config` 里与网关相关的七个键：`gatewayEndpoint`、`gatewaySecure` 由 Agent DaemonSet 引用；`gatewayBucketConcurrency`、`gatewayBlockBufferBytes`、`gatewayCache`、`gatewayCacheDatasetBytes`、`gatewayCacheTotalBytes` 由网关 Deployment 引用，Agent 侧不引用；`objstoreCompression` 两边共同引用，`fetchRangeParallel` 只由 Agent 引用。取值为代码默认值的开关也写进 ConfigMap，让开关在清单里可见。Deployment 的 env 全部走 `configMapKeyRef`/`secretKeyRef`，没有字面量值。

## 部署与更新

单副本 Deployment，Recreate 策略：滚动更新会让旧 Pod 与新 Pod 各持一份在途表，扇出被分到两个进程，停一次再起来的代价比合并失效低。收到 SIGTERM 后 `readyz` 立即转 false，Service 的就绪探测周期 2s 先把 Pod 摘流；进程停止接受新连接，等在途 GET 结束或满 30s 再退出，`terminationGracePeriodSeconds` 取 40 留余量。Agent 的在途下载因此看到的是正常收尾而不是连接重置；30s 内未结束的请求按普通失败处理，由 `core/fetch` 重试。存活探测走 `/healthz`，周期 5s、连错 3 次重启，不依赖源站。

启动顺序：日志先于配置初始化（配置错误也要以同一套 JSON 结构输出），然后读配置、构造源站客户端、构造在途表/调度器/汇总器、开关打开时构造缓存存储并扫描目录、监听、ready。监听成功后才置 ready，探针不依赖源站。动态日志级别端点 `/debug/loglevel` 绑固定回环地址 `127.0.0.1:6060`，不走 env，不进 Service。

## 日志与可观测性

日志复用 `core/logging` 的脱敏与采样处理器，`component=gateway`、`log_schema_version=1`，与 `agent/internal/logging` 同构；`gateway/internal/logging` 只做设级别、装处理器、注入三个字段。错误行必须带 `err` 与 `err_class`，不吞异常。Info 不写 `key` 这类高基数字段，`dataset` 可以进 Info。`accessKey`、`secretKey`、`Authorization`、`x-amz-*` 由脱敏处理器处理，调用点不重复处理。

关键日志点：

| 位置 | 级别 | 字段 |
|---|---|---|
| 启动完成 | Info | `component,version,listen,origin,bucket,concurrency,buffer_bytes,cache,cache_dataset_bytes,cache_total_bytes` |
| 收到 SIGTERM | Info | `inflight` |
| 退出完成 | Info | `drained,forced` |
| 条目创建 | Debug | `dataset,key` |
| 条目结束 | Debug | `dataset,key,written,duration_ms,subs,from,err`，`from` 取 `origin` 或 `cache` |
| 订阅者加入 | Debug | `dataset,subs` |
| 订阅者被踢 | Warn | `dataset,reason=slow_consumer,written,pos` |
| 准入拒绝 | Warn | `dataset,reason=queue_full 或 wait_timeout` |
| 读盘命中 | Debug | `dataset,key` |
| 写盘失败 | Warn | `dataset,key,reason,err,err_class` |
| 淘汰 | Info | `dataset,step,removed_bytes` |
| 源站失败 | Warn | `dataset,status,code,err,err_class` |
| panic 恢复 | Error | `panic,stack` |
| 60s 汇总 | Info | 见下表 |

每 60s 输出一条 Info，消息固定 `gateway: 60s 汇总`，窗口切换用原子交换清零，每个请求的每个计数恰好落在一个窗口里：

| 字段 | 含义 |
|---|---|
| `window_s` | 窗口秒数 |
| `gets` | 块 GET 总数 |
| `merged` | 挂到已有条目的请求数 |
| `owners` | 新建条目数，即真实源站 GET 数 |
| `passthrough` | 直通 GET/HEAD 数 |
| `kicked` | 被踢订阅者数 |
| `rejected` | 准入拒绝数 |
| `cache_hit` | 字节从盘上取走的请求数；开关关闭时恒为 0 |
| `bytes` | 本窗口从源站读入的字节数 |
| `datasets` | 窗口内出现过的 dataset 数 |

`merged / gets` 是在途合并的命中率，`cache_hit` 单独一列，两列相加才是网关接住的字节占比；「扇出必须同时发起」这个前提只约束 `merged` 那一列，错峰到达的请求由 `cache_hit` 记账，不再约束整个实验。实验对账用这几列，不依赖网关指标端点。

排查路径：

| 现象 | 先看 |
|---|---|
| 训练读变慢、源站流量没降 | 网关 60s 汇总的 `merged/gets` 与 `kicked` |
| Agent 全部直连 | Agent 日志 `gateway fallback` 行的 `reason`；网关 `readyz` 与重启记录 |
| 只有部分节点直连 | 该节点 Agent 日志；网关汇总里 `rejected` 是否集中 |
| 网关 5xx 但源站正常 | 网关 `panic 恢复` 与 `准入拒绝` 行 |
| 缓存没接住请求 | 汇总的 `cache_hit`；网关盘上该 dataset 目录的驻写字节；`淘汰` 与 `写盘失败` 行；`gatewayCache` 是否为 `true` |

## 指标

网关进程不暴露 `/metrics`，没有网关侧指标族。Agent 侧新增两个指标族：

| 指标族 | 类型 | 标签 | 取值 |
|---|---|---|---|
| `traincache_source_mode` | gauge | 无 | 0 直连，1 网关；构造时预置 |
| `traincache_gateway_fallback_total` | counter | `reason` ∈ {`unavailable`,`timeout`,`transport`} | 降级次数 |

注册表的指标族总数从 40 增到 42，既有指标族的名字、类型、标签不动。

## 兼容性

`objectstore.Store` 接口不变，`backendStore` 是新增实现；`NewS3Store` 签名不变，新增 `NewS3StoreWithOptions`，老调用点不修改。`gatewayEndpoint` 为空时 Agent 与改动前完全一致。ConfigMap 既有键的名称与语义不动；部署只新增一个 Deployment 与一个 Service，既有工作负载除 DaemonSet 增两条引用外不修改。
