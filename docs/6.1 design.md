# 6.1 缓存核心库设计（design）

> 需求来源：`6.0 缓存核心库设计方法.md`。这份文档定下核心库的冻结约定：接口签名、数据格式、包结构。
> “冻结”的意思是实现者不能私自改。确实要改，先回传 BLOCKED，由主对话裁决。
> 配套文档：`6.2 plan.md`（里程碑与验收）、`6.3 decisions.md`（决策与未决问题）。读者懂 Go 和存储基础就能跟下来，新名词第一次出现时我会解释。

## 1. 库的定位

结论先说：这是一个无服务形态的 Go 库，编译进层2 Agent（未来 Controller 侧组件也能用），不单独跑进程。它管三件事。

1. **记录有哪些数据块**——路径索引层。它维护 `(path, chunkIndex) → 块指纹` 的映射，再以快照形式存进对象存储。
   - 块是按固定大小切开的数据片；指纹是内容的哈希值，后面当键用。
   - 快照是一次提交后的完整索引版本，读侧只认最新一份。
2. **按内容落盘**——CAS 存储层。它用 xxh3-128 指纹当键，同样的内容只存一份，读回来还要校验。
   - CAS 是 content-addressed storage，内容寻址存储。文件放哪由内容哈希决定，不按路径放。
3. **按需下载**——抓取编排层。它限制下载速率、合并重复请求、校验失败就重下。

**非目标**：库里没有服务进程，也不含网络协议和调度逻辑（这些属于 Agent 和 Controller）。跨路径的索引去重也不做，去重只发生在 CAS 层。

一句话：库只负责“块在哪、块怎么存、块怎么下”，其余交给上层。

## 3. 总体架构与依赖方向

先看图。图里是五个包，以及它们之间的调用方向。

```
                ┌──────────── index ────────────┐
                │ Writer / Catalog / Collector  │   记录块→节点映射、快照、提交、刷新、回收
                └──────┬───────────────┬────────┘
                       │               │
            ┌──────────▼──┐      ┌─────▼──────────┐
            │    cas      │      │  objectstore   │   对 S3 兼容对象存储的抽象（含条件写入）
            │  本地块存储   │      └─────▲──────────┘
            └──────▲──────┘            │
                   │            ┌──────┴──────────┐
            ┌──────┴───────────┐│      fetch       │   下载编排：限流、合并、重试
            │  fetch（下载编排） │└──────▲──────────┘
            └──────▲──────────┘       │
                   │        ┌─────────┴──────────┐
                   │        │  internal/digest   │   xxh3-128 / sha256 封装
                   └───────►└────────────────────┘
```

图里有三个业务层、一个对象存储抽象和一个哈希工具：

- `index` 管索引：记录“块 → 节点”的映射，负责快照、提交、刷新、回收。
- `cas` 管本地块存储。
- `fetch` 管下载编排：限流、合并、重试。
- `objectstore` 把 S3 兼容存储抽象成接口，条件写入也在这一层。
- `internal/digest` 封装 xxh3-128 和 sha256。

依赖方向单向无环，这是硬约束：

- `index → cas、objectstore`
- `fetch → objectstore、cas`
- `publish → index、cas、objectstore`，`index` 不反向依赖 `publish`
- `cas → internal/digest`，只碰本地文件系统

`cas` 有意不依赖 `objectstore`。下载得到的字节流由 `fetch` 喂给 `cas.Put`，本地存储和远端存储因此解耦。

一句话：依赖只往下走，`cas` 不认识对象存储，`index` 不认识发布器。

## 5. 核心接口（冻结约定）

下面六小节的 Go 代码是冻结约定。签名、常量、结构体字段都不能改；要改先回传 BLOCKED。

代码注释里写的是行为契约，重点看错误返回值和并发语义。正文只解释“为什么这么定”，不重复注释。

### 5.1 objectstore

这一层把 S3 兼容存储收成 6 个方法。其中 `PutIfMatch` 是快照原子提交的关键：它让“只有一个人能改 CURRENT”成立。

```go
package objectstore

var (
    ErrNotFound = errors.New("objectstore: object not found")
    ErrConflict = errors.New("objectstore: conditional write conflict")
)

// Store 是对 S3 兼容对象存储的最小抽象。
type Store interface {
    // Get 将对象内容完整写入 w；不存在返回 ErrNotFound。
    Get(ctx context.Context, key string, w io.Writer) error
    // Put 上传对象，返回服务端 ETag。对相同内容 ETag 必须稳定（S3 简单上传语义）。
    Put(ctx context.Context, key string, r io.Reader, size int64) (etag string, err error)
    // Delete 删除对象；对象不存在不算错误。
    Delete(ctx context.Context, key string) error
    // GetETag 返回对象当前 ETag；不存在返回 ErrNotFound。
    GetETag(ctx context.Context, key string) (string, error)
    // PutIfMatch 条件写入：expectedETag 为空串时要求 key 不存在（If-None-Match: *），
    // 否则要求当前 ETag == expectedETag（If-Match）。冲突返回 ErrConflict，不写入。
    PutIfMatch(ctx context.Context, key string, r io.Reader, size int64, expectedETag string) (newETag string, err error)
    // List 返回匹配 prefix 的全部对象键（字典序升序）；无匹配返回空切片（D19）。
    // 供 index.Collector.Sweep 枚举快照对象用。
    List(ctx context.Context, prefix string) ([]string, error)
}

// 构造器（M1 冻结）：
func NewMock() *Mock
func NewS3Store(endpoint, accessKey, secretKey, bucket string, secure bool) (*S3Store, error)

// 块键与条件写探测（7.1 §5.12）：
func BlockKey(dataset, path string, chunk int64) string // <dataset>/blocks/<path>#<chunk>
// ProbeConditionalWrite 写临时键后用故意不匹配的 ETag 调 PutIfMatch：
// 后端支持条件写返回 nil；后端忽略前置条件返回 ErrConditionalWriteUnsupported；
// 其他存储错误原样返回。探测对象尽力删除。
func ProbeConditionalWrite(ctx context.Context, s Store) error
```

补充三点：

- `Put` 对相同内容必须返回稳定的 ETag。ETag 是服务端给对象版本打的标记；S3 简单上传语义下，它由内容决定。
- `PutIfMatch` 的 `expectedETag` 为空串时，要求 key 不存在；非空时，要求当前 ETag 与它相等。冲突返回 `ErrConflict`，并且不写入。你可以把它理解成对象存储上的 compare-and-swap。
- `List` 按字典序返回全部键，供 GC 枚举快照对象用（D19）。

一句话：对象存储层只暴露最小能力，原子性靠条件写拿到。

### 5.2 cas

`cas` 管本地磁盘上的块。一个块文件由 128 字节块头和后面的数据组成，文件名就是内容指纹。

```go
package cas

// 块头（header.go，M2 实现；字节布局见 §6.3）：
const (
    HeaderSize    = 128    // 块头字节数
    FlagHasSHA256 = 1 << 0 // flags bit0：块头含有效 sha256
)

const Magic = "TCBK" // 块头 magic（4 字节）

type Header struct {
    Version   uint16   // = 1
    Flags     uint16   // FlagHasSHA256 置位时 SHA256 字段有效
    BlockSize uint32   // 数据字节数（不含块头）
    XXH3      [16]byte // 数据指纹 = 存储键
    SHA256    [32]byte
}

func ParseHeader(b []byte) (Header, error) // 校验 magic/version/reserved 区；长度不足报错
func (h Header) Encode() [HeaderSize]byte  // 编码为 128 字节（reserved 区置 0）

type Fingerprint [16]byte // xxh3-128，作为存储键

func (f Fingerprint) String() string                    // 32 字符小写 hex
func FingerprintFromHex(s string) (Fingerprint, error)  // 解析 32 字符 hex（长度/字符不符报错）

type VerifyLevel int
const (
    VerifyXXH3        VerifyLevel = iota // 默认：只验 xxh3
    VerifyXXH3SHA256                     // 新写块时同时算 sha256 写入块头，读时双重校验
)

var (
    ErrCorrupt  = errors.New("cas: block verification failed")
    ErrNotFound = errors.New("cas: block not found")
    ErrInUse    = errors.New("cas: block is referenced or being read")
)

type Store struct { /* dir、verify、refcount 表（内部） */ }

func New(dir string, verify VerifyLevel) (*Store, error)

// Put 流式写入：边读边算指纹，写临时文件，完成后 rename 到 blocks/<fp[0:2]hex>/<fp hex>.blk。
// 同指纹并发写安全（rename 原子，最终文件完整）；返回指纹与数据字节数。
// 不做 fsync（丢失代价 = 重拉）。
func (s *Store) Put(ctx context.Context, r io.Reader) (Fingerprint, int64, error)

// Open 打开块并校验：读块头验证 magic/version，流式重算数据 xxh3（及 sha256，按块头
// flags 与 Store.verify 决定）比对；不符返回 ErrCorrupt（调用方负责 Remove 后重拉）。
// 校验通过后返回从数据区起读的句柄。
func (s *Store) Open(fp Fingerprint) (*BlockReader, error)

// Remove 删除块；仍有引用或读者（pin）时返回 ErrInUse。
func (s *Store) Remove(fp Fingerprint) error

// Evict 只删除块的本地副本，供 Agent 层磁盘淘汰用（D28）：refcount 不拦
// （引用是快照级逻辑簿记，与副本是否在本地无关），pin>0 返回 ErrInUse；
// 已不存在返回 ErrNotFound（与 Remove/Sweep 并发安全）。索引条目不受影响，
// 后续读取经 Catalog.Lookup 命中 + Open 得 ErrNotFound 后由 fetch 重下。
func (s *Store) Evict(fp Fingerprint) error

// Acquire/Release 引用计数：Acquire +1（引用计数 = 已提交快照对该 CAS 块的逻辑引用）；
// Release -1，归零后块进入可回收状态。读操作不占引用计数，用 Pin/Unpin 单独管理生命周期。
func (s *Store) Acquire(fp Fingerprint) error
func (s *Store) Release(fp Fingerprint)

// Pin/Unpin 读操作生命周期：Pin 计数 >0 时 Remove 必须返回 ErrInUse。
func (s *Store) Pin(fp Fingerprint) error
func (s *Store) Unpin(fp Fingerprint)

// List 枚举 blocks/ 下全部块指纹（D20）：忽略临时文件与非法文件名；供 GC 枚举用。
func (s *Store) List() ([]Fingerprint, error)

// Quarantine 把 Open 校验失败的坏块物理移入 cas 根下 quarantine/ 目录（与 blocks/ 并列），
// 不再出现在 List() 中。幂等：源块不在 blocks/（已在 quarantine 或从未存在）返回 nil；
// 目标已存在时 rename 原子覆盖。不检查 refs/pins（坏块隔离是正确性动作，引用计数是
// 索引层的逻辑关系，修复后同指纹块回原位、引用不变）；持 s.mu 与 Remove/其他 Quarantine
// 串行。仅真实 I/O 错误报错。
func (s *Store) Quarantine(fp Fingerprint) error

// ListQuarantined 枚举 quarantine/ 下全部块指纹（与 List 同规则：忽略临时文件与非法
// 文件名，按指纹字节序升序，无块返回空切片）。供修复队列与重扫描枚举隔离块用。
func (s *Store) ListQuarantined() ([]Fingerprint, error)

// RemoveQuarantined 删除 quarantine/ 下的块（修复成功后清理）；目标不存在返回 nil
// （同 objectstore.Delete“不存在不算错误”语义）。仅真实 I/O 错误报错。
func (s *Store) RemoveQuarantined(fp Fingerprint) error

// SetOpenObserver 安装实例级 Open 前置观察者：每次 Open（命中或缺失）在调用 os.Open
// 之前以请求指纹触发一次，仅表示"本进程即将读打开该块"；随后打开成败不影响触发。
// 传 nil 清除。观察者不改变 Open 的返回值与错误语义，与并发 Open 数据竞争安全。
func (s *Store) SetOpenObserver(fn func(Fingerprint))

type BlockReader struct { /* 包装 *os.File，从块头之后开始读 */ }
func (r *BlockReader) Read(p []byte) (int, error)
func (r *BlockReader) Close() error
func (r *BlockReader) Size() int64 // 数据字节数（块头 block_size）
```

几个容易混的点，单独说清：

- **`Put` 先写临时文件，再 rename。** 指纹要读完整个流才算得出来，所以临时文件名用 `tmp-<random>`，不用 `<fp>.tmp-*`。rename 是原子操作，别的进程看不到写了一半的块。
- **`Remove` 和 `Evict` 不一样。** `Remove` 受引用计数约束，块还有引用就不让删。`Evict` 只删本地副本，引用计数不动（D28 的约定）。下次读会先 `Catalog.Lookup` 命中，再 `Open` 报 `ErrNotFound`，由 `fetch` 重下。
- **`Acquire/Release` 数的是“谁在逻辑上引用这个块”。** 引用来自已提交的快照。你可以把它想成借书卡：书上贴着几张卡，就说明有几个快照登记了它。
- **`Pin/Unpin` 数的是“现在谁正在读”。** 读操作不占引用计数，用 pin 单独管生命周期。`Pin > 0` 时 `Remove` 必须返回 `ErrInUse`。借书卡和正在看书的人是两件事。
- **`Quarantine` 处理坏块。** `Open` 校验失败后，把块 rename 到 `quarantine/` 目录，`List()` 不再枚举它。坏块隔离是正确性动作，所以不看引用计数；修复后同指纹的块回到原位，引用关系不变。

一句话：引用计数管快照，pin 管读操作，坏块单独关起来。

### 5.3 fetch

`fetch` 把远端对象变成本地块。它要同时满足三件事：不压垮网络、不重复下载同一个对象、校验失败能自己恢复。

```go
package fetch

type Options struct {
    MaxInflightBytes int64 // 在途下载字节上限（信号量口径，非 goroutine 数），默认 1 GiB
    MaxConnsPerHost  int   // 单主机连接数上限，默认 64
    MaxTasks         int   // 最大并发下载任务数，默认 8
    MaxRetries       int   // 校验失败重下次数，默认 3
    // OnLocalOpen 在 Put 成功、Open 读回校验之前以块指纹调用一次（可为 nil）。
    // 通用钩子：core 不依赖 Agent 侧类型；实现不得阻塞（调用方通常仅做内存记账）。
    OnLocalOpen func(fp cas.Fingerprint)
}

var ErrTooManyRetries = errors.New("fetch: verification failed after max retries")

type Fetcher struct { /* objectstore.Store、*cas.Store、limiter、in-flight map（内部） */ }

func New(store objectstore.Store, cs *cas.Store, opts Options) *Fetcher

// MaxInflightBytes 返回实际生效的在途下载字节上限（Options 补齐默认值后）。
func (f *Fetcher) MaxInflightBytes() int64

// Fetch 下载对象：Acquire(expectSize) 字节信号量 → store.Get 流经 cas.Put 落盘 →
// Open 读回校验 → 失败则 Remove 后重试（≤ MaxRetries）→ Release 信号量。
// 相同 key 的并发 Fetch 合并为一次实际下载（in-flight map，等待者共享结果）。
// 返回块指纹。命中检查是调用方职责：先经 index.Catalog.Lookup 取指纹、cas.Open
// 验存在，未命中才调用本方法（对应 docs/7 "缓存命中就不触及数据源"）。
// 簿记契约：Fetch 不做 Acquire；调用方在首次写入时 Acquire 一次即可。Evict（D28）
// 只删本地副本不动引用，故副本被 Evict 后经本方法重下时不得重复 Acquire（D28）。
func (f *Fetcher) Fetch(ctx context.Context, key string, expectSize int64) (cas.Fingerprint, error)
```

- `MaxInflightBytes` 限制的是在途字节数，不是 goroutine 数。1 GiB 是信号量口径，下载大对象时更贴近真实带宽占用。
- 相同 key 的并发 `Fetch` 合并成一次真实下载，等待者共享结果。这是 in-flight map 的作用。
- 命中检查由调用方做：先 `index.Catalog.Lookup` 拿指纹，再 `cas.Open` 确认本地有块，没命中才调 `Fetch`。这样缓存命中不会碰数据源。
- 簿记契约要记住：`Fetch` 自己不 `Acquire`。调用方在首次写入时 `Acquire` 一次；`Evict` 删掉本地副本后，重下不能再 `Acquire`（D28）。

一句话：下载层只搬字节，命中判断和引用簿记都留给调用方。

接口多，但职责只有三块：

- **`Writer.Commit` 负责写。** 它把本次增量 upsert 合并进当前快照，重新切分片，上传，再用条件写更新 CURRENT。详细五步在 §7.1。
- **`Catalog` 负责读。** 它把索引放在内存里，定时刷新，切换时用 `atomic.Pointer` 一次性换掉整份映射。`LoadPrefixes` 只加载和给定前缀相关的分片，适合 Agent 按目录取索引（D23）。
- **`Collector.Sweep` 负责回收。** 它先算活块集合，再删掉没人引用、也没人正在读的块，最后清理窗口外的快照对象。
- **`ReaderRegistry` 负责登记。** Agent 通过 `Declare` 声明自己跟随的 snapID 并定时刷新心跳；GC 读取全部 claim，把未过期声明里的 `SnapID` 与 `PreviousSnapID` 都计入保护集合。声明对象损坏时 `Sweep` 必须 fail-safe，跳过本轮块删除。

几个字段的约定：

- `Entry.Chunk` 是块序号，块字节范围是 `[chunk*ChunkSize, +Size)`，末块可以不足一个 `ChunkSize`。
- `Entry.Node` 记录块实际落在哪个节点。v1 里这个字段保留不用，见 §10.6。
- `ShardRef.Key` 是完整对象键。未变更的分片跨快照复用，键保持首次创建时的值（D18）。
- `ShardRef.MinPath/MaxPath` 是分片内首末条目的路径。读侧靠它判断“这个分片和前缀有没有关系”（D22）。
- 条目按 `(path, chunk)` 字典序排，分片按条目数切，不按哈希切。

一句话：`Writer` 写、`Catalog` 读、`Collector` 收、`ReaderRegistry` 登记，四者共享同一套格式定义。

四个函数，两种哈希，一次性计算和流式计算都有。

### 5.6 logging

日志脱敏，Controller 和 Agent 共用。两个独立 module 都能引这个包，所以它只依赖标准库。


- 敏感键（小写比较）：`accesskey`、`access_key`、`secretkey`、`secret_key`、`token`、`authorization`、`password`、`secret`、`credential`、`signature`、`expires`、`x-amz-signature`、`x-amz-credential`、`x-amz-security-token`。
- `Redact` 识别 `key=value`、`key: value`、`"key":"value"`、`"key": "value"` 四类片段，键不区分大小写。命中后只把 value 换成 `***`，键和分隔符原样保留；空串原样返回。

一句话：脱敏逻辑集中在一个包，两个上层 module 共用，避免各写一份。

## 6. 数据格式

### 6.1 对象存储键布局

结论：所有对象都放在 `dataset/<name>/` 下面，分三类键：快照清单、索引分片、CURRENT 指针。

```text
<bucket>/
└── dataset/<name>/
    ├── snapshots/<snapID>/manifest.json
    ├── snapshots/<snapID>/shard-<fp8>.idx      # fp8 = 分片内容 xxh3 前 8 字节 hex
    └── CURRENT                                 # 内容："<snapID> <manifestFP8>"（空格分隔，无换行）
```

- 快照逻辑上是完整的一份，物理上复用旧分片。没变的分片，对象键和内容指纹都不变，不用重传。
- CURRENT 里带着 manifest 指纹，校验链是 CURRENT → manifest → 各分片。

一句话：CURRENT 是唯一入口，改它等于切快照。

### 6.2 索引分片（shard-<fp8>.idx）

- 格式是 JSON 数组，元素是 `Entry`，字段名用全称（见 §5.4）。`fp` 是 32 字符 hex。
- 构建规则：条目先按 `(path, chunk)` 字典序排序，再按条目数切成 range。每片最多 `MaxEntriesPerShard` 条，默认 100_000（doc/7 上限）。
- 完整性：分片内容的 xxh3-128 写进 manifest 的 `ShardRef.Fingerprint`。读侧下载后重算比对，不一致报 `ErrInvalidShard`。
- 路径范围：首末条目的 Path 写进 `ShardRef.MinPath/MaxPath`（D22）。读侧据此跳过无关分片。

一句话：分片先排序再按条数切，所以范围过滤能成立。

### 6.3 CAS 块文件（blocks/<fp[0:2]hex>/<fp hex>.blk）

统一 128 字节块头。v1 就是最终格式，不再做 64 字节变体。

```text
offset  size  field
0       4     magic  "TCBK"（0x54 43 42 4B）
4       2     version = 1
6       2     flags   bit0 = 块头含有效 sha256
8       4     block_size   uint32 LE（数据字节数，不含块头）
12      16    xxh3_128     数据指纹 = 存储键 = 文件名
28      32    sha256       flags bit0 置位时有效，否则全 0
60      68    reserved     全 0（对齐到 128B）
128     n     数据
```

逐字段说明：

- `magic` 固定为 `TCBK`，用来快速识别文件类型。
- `version` 目前是 1。
- `flags` 的 bit0 表示块头里的 sha256 有效。
- `block_size` 只算数据字节数，不含块头。
- `xxh3_128` 同时是存储键和文件名。
- `sha256` 只在 flags bit0 置位时有效，否则全 0。
- `reserved` 全 0，把块头对齐到 128 字节。

- 存储键永远是 xxh3-128。打开 sha256 不改变去重逻辑。
- `VerifyXXH3SHA256` 只影响新写入的块。老块 flags bit0=0，读时按自己的 flags 校验，不做全量重算。
- 坏块隔离（Quarantine，7.1 design §5.7）：坏块 rename 到 `quarantine/<fp[0:2]hex>/<fp hex>.blk`，和 `blocks/` 同级、同两级布局。它不再出现在 `List()` 里，只在 `ListQuarantined()` 里。

一句话：块头自带校验信息和版本，坏块搬到隔离目录，主目录始终干净。

### 6.4 manifest.json

`{"snapshot_id":"...","created_at":"...","shards":[{"key":"dataset/<name>/snapshots/<snapID>/shard-<fp8>.idx","min_path":"/a/...","max_path":"/b/...","entries":N,"fp":"<完整hex>"}]}`

（`ShardRef.Key` 为完整对象键（D18）：新分片位于本次快照目录；未变更分片跨快照复用保留首次创建时的完整键。
`ShardRef.Fingerprint` 存完整 16 字节 hex；文件名部分用其前 8 字节。`MinPath/MaxPath` 为分片路径范围（D22）。）

- `snapshot_id` 和 `created_at` 标识这一次快照。
- `shards` 是分片引用列表。
- `ShardRef.Key` 是完整对象键（D18）。新分片在本次快照目录下；没变的分片沿用首次创建时的键。
- `Fingerprint` 存完整 16 字节 hex，文件名只用前 8 字节。
- `MinPath/MaxPath` 是分片的路径范围（D22）。

一句话：manifest 只存引用和范围，真正的条目在分片里。

## 7. 关键流程

### 7.1 提交事务（`Writer.Commit`，对应 doc/7 步骤 1–5）

结论：Commit 不改旧数据。它新建一套对象，最后靠一次条件写把 CURRENT 指过去。

1. **写新块**（发生在 Commit 之前）。调用方通过 `fetch.Fetch` 或 `cas.Put` 把新块写进 CAS，然后 `cas.Acquire` 引用 +1。CAS 键是内容指纹，新块天然不覆盖旧块。
2. **写新分片。** 读当前快照 S1 和受影响的分片，把本次 entries 合并进去，重排、重新切分，写成新的本地临时文件再 rename。没受影响的分片直接复用旧键。
3. **上传对象。** 新分片和新 manifest 用独立键上传。提交前读侧看不到它们，因为读侧只认 CURRENT。
4. **验证完整性。** 提交前确认四件事：新 manifest 上传成功；manifest 引用的分片都在，指纹一致；分片条目数没超上限；manifest 引用的新块已经在 CAS 里，并且 `Open` 校验通过。
5. **原子提交。** 调 `PutIfMatch(CURRENT, "<newSnapID> <newManifestFP8>", expectedETag=MD5("<oldSnapID> <oldManifestFP8>"))`。
   - 成功，新快照生效。
   - 返回 `ErrConflict`，说明别人先提交了。重读最新快照，以它为基准重新合并、构建、提交，最多 5 次。

一句话：先写新对象、再校验、最后改指针，读侧永远只看到完整快照。

### 7.2 读侧刷新（`Catalog`，对应 doc/7 步骤 6）

结论：Catalog 每 5 秒看一次 CURRENT。变了就整份加载，加载完一次性换指针。

定时读 CURRENT。内容没变就跳过；变了就走这条链：下载新 manifest → 逐个下载分片并验证指纹 → 构建新内存映射 → `atomic.Pointer` 一次性切换。加载新分片的过程中，绝不逐个修改正在服务的旧映射。manifest 和分片都要过完整性校验。

按前缀加载（`LoadPrefixes`，对应 doc/7 的“索引分片按前缀目录加载”）：

- manifest 全量下载。它只有 ShardRef 列表，体积小；GB 级的索引主体在分片里。
- 用 `ShardRef.MinPath/MaxPath` 和各 prefix 做范围判断（D22）。分片相关 ⟺ `MaxPath ≥ prefix` 且（`MinPath ≤ prefix` 或 `MinPath` 以 `prefix` 开头）。
- 只下载、校验、加载相关的分片，构建局部映射后原子切换。失败不动旧映射。
- 加载哪些前缀由 Agent 服务决定，库只提供能力（D23）。`LoadPrefixes` 和 `Refresh/Start` 二选一使用，不能同时跑后台循环。

一句话：刷新是“整份建好再换指针”，前缀加载只是把整份缩小到相关分片。

### 7.3 回收（`Collector.Sweep`，对应 doc/7 步骤 7）

结论：只删“窗口外、没人引用、没人正在读”的对象。

- **旧快照和分片**：CURRENT 指向的快照不删。保留窗口是 CURRENT 加最近 2 个提交过的快照。窗口外的快照如果还有 pin 的读者在用，跳过；否则删 manifest，以及其他保留快照不再复用的分片对象。
- **旧数据块**：活块集合 = 保留快照索引能到达的指纹 ∪ 读者 pin。只删同时满足三个条件的块：不在活块集合、refcount=0、pin=0。还有人在用的跳过，留到下次。
- 引用计数记录的是“已提交索引快照对这个块的逻辑引用”，不统计读操作。读操作的生命周期由 pin 单独管。

一句话：GC 的安全线是“快照还引用它，或者有人正在读它”。

### 7.4 CAS 写入与并发（`cas.Store.Put`）

结论：用临时文件加 rename 拿到原子性，不靠 fsync。

- 写盘顺序：先写 `tmp-<random>` 临时文件，写完块头和数据，再 `rename()` 到 `blocks/<fp[0:2]hex>/<fp hex>.blk`。别的进程和 goroutine 永远看不到写了一半的块。孤儿临时文件不影响 `Open`，也不影响后续 `Put`，M2 的测试会锁定这一点。
- 不做逐块 fsync。掉电丢了块，代价就是重新下载。
- 多 goroutine 同时写同一个指纹：各写各的临时文件，rename 原子覆盖，最后留下的文件一定完整。同指纹的内容一定相同，xxh3 碰撞概率按 0 处理（D9）。

一句话：原子性来自 rename，持久性靠重下，不靠 fsync。

### 7.5 校验失败重下（`fetch.Fetcher.Fetch`）

链路是：下载 → `cas.Put` → `cas.Open` 读回校验 → 遇到 `ErrCorrupt` 就 `cas.Remove` → 重试，最多 `MaxRetries` 次 → 还失败就报 `ErrTooManyRetries`。

`Remove` 在这里安全，因为引用要等 `Fetch` 成功后由上层 `Acquire`，此刻没有引用也没有 pin。

一句话：坏块先删再下，默认最多重试 3 次。

## 9. 验收标准（总闸）

`cd core && go build ./... && go vet ./... && go test ./...` 全绿，单测还要重点覆盖四个场景（doc/7 硬性要求）。

1. **多个 goroutine 同时写同一个块。** 造法：并发 `Put` 同一份内容。看三件事：最终文件完整、指纹正确、没有临时文件泄漏。
2. **写一半进程崩溃。** 造法：注入失败点让 `Put` 中途终止，或者预置孤儿临时文件。重开后同内容 `Put` 要能完成，能清掉孤儿临时文件，`Open` 不受影响。
3. **相同内容去重。** 造法：同内容 `Put` 两次。看指纹是否相同、磁盘上是否只有一份。
4. **校验失败后重新下载。** 造法：篡改块内容。`Open` 要报 `ErrCorrupt`，`Fetch` 要自动 `Remove` 再重下，最后恢复。

分里程碑的逐条验收在 `6.2 plan.md`。

一句话：四场景覆盖并发、崩溃、去重、损坏四条最容易出错的路径。

## 10. 多 tar 发布器（publish）

### 10.1 职责与位置

`core/publish` 是写侧编排，对应 doc/7 步骤 1 的“写入方”。

它做的事：把一批 tar 源按 `ChunkSize` 切块，写进本地 CAS 和对象存储，生成 `index.Entry` 列表，最后只调一次 `index.Writer.Commit` 原子发布。

它不做的事：不维护快照、不做读侧刷新、不回收数据。索引合并、分片构建、条件提交仍归 `index.Writer`。

CLI 在 `core/cmd/trainpublish`，只解析参数、装配依赖，不承载发布语义。依赖方向见 §3：`publish → index、cas、objectstore`，`index` 不反向依赖 `publish`。

一句话：发布器负责“切块、上传、交一次 Commit”，快照语义仍在索引层。

### 10.2 包契约（冻结）

```go
package publish

type Source struct {
    Path   string      // tar 文件名，即 Entry.Path；必须不可变
    Reader io.ReaderAt // tar 内容，允许并发按偏移读取
    Size   int64
}

type Options struct {
    Dataset     string
    ChunkSize   int64 // 0 = DefaultChunkSize（64 MiB）
    Concurrency int   // 0 = DefaultConcurrency（4）
}

type Result struct {
    SnapID       string
    Entries      int   // 本次发布的条目数（各 tar 切块数之和）
    Bytes        int64 // 各 Source.Size 之和
    UniqueBlocks int   // 本次观察到的不同内容指纹数（本地 CAS 去重）
}

func Publish(ctx context.Context, store objectstore.Store, cs *cas.Store,
    w *index.Writer, sources []Source, opt Options) (Result, error)
```

- `Source.Path` 就是索引路径，取 tar 文件名。同一批次内必须唯一，不能包含 `#`（块键分隔符）。
- `Options.ChunkSize` 传 0，用默认 64 MiB；`Concurrency` 传 0，用默认 4。
- `Result.Entries` 是本次发布生成的条目数，不是提交后快照的总条目数。Commit 做的是 upsert 合并。
- 跨路径内容相同的块，本地 CAS 只存一份，`UniqueBlocks` 按这个口径统计。对象存储仍按各 `Path` 分别保留 `<path>#<chunk>` 键，不跨路径合并。

一句话：契约把“本地去重”和“远端按路径分开”两件事同时定死。

### 10.3 CLI（trainpublish）

```text
usage: trainpublish --dataset <name> [options] <tar> [<tar>...]
```

- 每个位置参数是一个 tar，`Path` 取文件名（basename）。同一批次里 `Path` 重复会报 `ErrDuplicatePath`。
- 必需参数 `--dataset`。对象存储参数有 `--endpoint`、`--access-key`、`--secret-key`、`--bucket`、`--secure`。
- 切块和并发：`--chunk-size`（字节，默认 64 MiB）、`--concurrency`（默认 4）。
- 本地工作目录：`--work-dir` 指定临时目录；`--keep-work-dir` 结束后保留，方便排查；`--probe-conditional-write` 在发布前探测对象存储是否支持条件写。
- 成功后打印 `Result` 摘要（snapID / entries / bytes / unique_blocks）。失败以非零码退出。

一句话：CLI 只做参数到库调用的映射，语义都在库内。

### 10.4 多 tar → 单快照

所有 tar 的条目合并成一个 `[]index.Entry`，只调一次 `Writer.Commit`，不按 tar 分批提交。

任何一个 tar 读取失败，或者任何一块处理失败，整次发布就失败，也不调 `Commit`。读侧因此永远看不到半成品快照。

一句话：一次发布对应一个快照，要么全成功，要么什么都没有。

### 10.5 块键与「先块后 Commit」

- 块键统一由 `objectstore.BlockKey(dataset, path, chunk)` 生成，格式是 `<dataset>/blocks/<path>#<chunk>`，和 6.0 的对象存储布局一致。`agent/prefetch/pending.go` 和 `agent/rescan/repair.go` 里两份未导出的实现改成调这个函数，格式知识只维护一处。
- 每个块的顺序：按 `ReaderAt` 读 `[chunk*ChunkSize, +size)` → `cas.Put` 落本地、拿指纹并完成校验 → `store.Put(BlockKey, ...)` 上传远端。
- `Writer.Commit` 的完整性验证只检查本地 CAS（`Open` 校验），不校验远端块对象。所以必须先上传完全部块，再 `Commit`，避免新快照指向远端不存在的块。
- 并发由 `Options.Concurrency` 限制。`Commit` 等所有块成功后，只调一次。

一句话：先块后提交，因为 Commit 只看本地，看不到远端缺没缺。

### 10.6 Node 保留（reserved）

`index.Entry.Node` 在 v1 是保留字段：固定留空，发布器不填节点信息，JSON 里因为 `omitempty` 直接不出现。

等跨节点块放置落地，再定义它的取值语义和去重策略。在那之前，不要给它赋予发布语义。

一句话：字段先占位，语义等跨节点功能上线再定。

### 10.7 失败语义与约束

- 任一块上传失败，就不 `Commit`。已上传的远端块不删，成为孤儿块，等后续回收或复用时覆盖。
- `Commit` 失败，`Writer` 只 best-effort 删除本次尝试上传的分片和 manifest，发布器不删远端块对象。远端孤儿块不自动删除，避免误删可能被其他快照复用的内容。
- `Path` 不可变：同一个 Path 不能对应不同内容。tar 文件名要带版本或哈希，例如 `shard-00000-v3-<hash>.tar`。重复发布同 Path 且内容一致，按 upsert 幂等处理。
- 本地 CAS 是 `Commit` 的校验来源。发布完成后，工作目录可以清理。
- 远端孤儿块的清理不归发布器管。当前 `Collector.Sweep` 只处理快照对象和本地块，远端块的清理策略留待后续决策。

一句话：发布失败允许留孤儿块，宁可多留，不可误删。

## 11. 数据集管理 CLI（`traincacheds`）

### 11.1 定位

`trainpublish` 已覆盖"增/改"（切块→上传→一次 Commit），但删除、查询、回收触发没有命令行入口。`traincacheds` 补这三块，是给运维/使用者看的**数据集管理平面**。

三条边界先划清：

- 一切索引变更只走 `Writer.CommitChanges` 这扇单门，CLI 绝不绕过快照直接 PUT/DELETE 索引对象；
- 数据块删除只经 Collector 回收规则（"已提交快照不再引用"才进待收集），CLI 不做原地删块对象的事；
- Agent 侧零改动——删除的传播靠已有的 Follow 快照切换，不新增 RPC。

一句话：CLI 是操作者的手，快照协议仍是唯一的路。

### 11.2 命名规范（D34）

可执行名统一 `traincache` 前缀。**不用 `tc`**——它和 Linux iproute2 的流量控制工具 `/usr/sbin/tc` 撞名，本仓库 bench 装置里就大量使用真 `tc` 限速，混用必出事。

| 可执行 | 职责 | 说明 |
|---|---|---|
| `traincacheds` | 数据集管理（rm/ls/stat/gc），新增，`core/cmd/traincacheds` | 本里程碑交付 |
| `traincachepublish` | 多 tar 发布，`core/cmd/trainpublish` 改名 | Makefile 同时安装旧名 `trainpublish` 作兼容别名，过渡一个版本 |
| `traincache` | Agent RPC 客户端（prefetch/status），不动 | 已在 agent/cmd |

### 11.3 命令面

```text
traincacheds rm      <ds> --path p.tar[,…] | --prefix p/  [--dry-run] [--yes]
traincacheds ls      datasets | snapshots <ds> | entries <ds> [--prefix p/] [--limit n]
traincacheds stat    <ds> [--path p.tar]
traincacheds gc      <ds> [--dry-run]
```

- `rm`：`--path` 删指定 tar 的全部块；`--prefix` 支持目录级批量（读旧快照 → 前缀过滤 → 一次 CommitChanges），这是本命令的主要形态（D33）。
- 安全阀：`rm`/`gc` 默认先跑 dry-run，打印影响的 Entry 条数与字节数；非交互环境实际执行必须带 `--yes`。`CURRENT`、仍被读者 claim 的快照永不删除（沿用 §5.11/GC 既有规则）。
- `ls datasets`：按 `dataset/` 前缀枚举存在 CURRENT 的数据集（依赖 objectstore.List，D19）。
- `ls entries` / `stat`：复用 `Catalog.List`（D29）与 manifest 的 `ShardRef.Entries`，不新增 core 导出。
- `stat` 的两个形态口径不同，差别在开销：`stat <ds>` 只读 CURRENT + manifest.json 两次 GET，输出 `dataset snapshot shards entries`；`stat <ds> --path p` 才经 `Catalog.List(p)` 下载相关分片，额外输出条目级的 `paths bytes`。条目级总量在 manifest 里不存在（§6.4：清单只存引用与路径范围），要它就得下载分片，所以不带 `--path` 时不报，避免一条"看一眼"的命令悄悄拖全量索引。
- `gc`：手动执行一次 `Collector.Sweep`，与 Agent 30s 周期淘汰循环同款逻辑，纯触发不新建规则。
- 配置沿用 `TRAINCACHE_OBJSTORE_*` 环境变量族 + flag 覆盖，与 trainpublish 同名同口径；退出码 0 成功 / 1 运行错误 / 2 参数错误。

一句话：四个动词，全部站在既有导出面上，唯一的新 core 能力只有 CommitChanges。

### 11.4 CommitChanges 契约（冻结）

签名与合并规则见 §5.4。这里补三条语义约定：

1. **删除 = 新快照里不存在**：`commitOnce` 本就读全量旧条目重建分片，删除只是"这次没带上它"，不需要 tombstone、不需要标记对象。
2. **dels 指向不存在的条目是幂等 no-op**：过滤不命中不算错，与 `Delete`/`Release` 的"不存在不算错误"风格一致（D26 同族）。
3. **puts 与 dels 冲突取 puts**：同一 `(path,chunk)` 既删又放，新值生效——支持"重写某块"一次提交完成。

一句话：删除语义借"全量再物化"的模型白拿，成本只是 API 签名宽了一点。

### 11.5 删除的传播路径与显式不做

```text
traincacheds rm 提交 S2（不含目标条目）
  → Agent Follow 到 S2，映射中消失        ← 已有机制，零改动
  → 远端孤儿块/旧快照 → gc（Sweep）回收   ← 已有规则，零改动
  → 训练 Pod 读被删 path → Lookup 未命中  ← 语义正确
```

**显式不做（v1）**：各节点本地 CAS 里被删 path 的残留块副本，不主动清理，靠磁盘淘汰自然消退。理由：主动清需要 Agent 新增按删除事件扫本地块的逻辑，而误清比滞留危险（旧快照可能仍被其他读者 claim）。将来若磁盘压力证明有必要，再立独立里程碑。

### 11.6 已知规模边界

`commitOnce` 每次提交读全量旧分片重建（未变更分片复用旧键不重传）。低频批量管理操作没问题；若删除/写入变成高频交互（控制台点删），写放大和冲突重试会先出问题，届时考虑"按分片局部提交"，属于新决策不属于本里程碑。

一句话：管理平面的账要记在"提交频率"上，不是"命令实现"上。

### 11.7 验收标准（与 6.2 plan.md M13 一致）

```bash
cd core && go build ./... && go vet ./... && gofmt -l .       # 全绿、输出为空
cd core && go test ./index/... -race -count=1                 # CommitChanges 新用例 + 既有用例
cd core && go test ./... -race -count=1                       # 全量回归
```

1. 三命令全绿；
2. `Commit` 行为与 M4/M5 既有用例逐字一致（只许加包装不许改语义）；
