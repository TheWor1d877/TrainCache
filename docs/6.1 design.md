# Agent 服务化设计(design)

> 本文档是 `docs/6.0 Agent服务化.md` 的下游设计文档,与核心库三件套(5.1 design / 5.2 plan / 5.3 decisions)平行。§5 接口签名与 §6 数据格式为冻结约定:字段名、类型、默认值、错误码实现者不得私改;发现冲突回传 `BLOCKED`(理由 + 证据),由主对话裁决后统一更新本文档与 decisions 文档——多人并行实现各改各接口就拼不起来。

## 1. 定位

把 core/(纯 Go 库,无服务形态)包装成常驻服务 `traincache-agentd`,每台缓存节点一个实例,以节点为服务边界:一个 Agent 只认识本机的缓存目录和本机的块,没有全局视图;单机故障不扩散,Controller 不在线时训练照跑。

- 对外:gRPC(接收预热任务、上报块级任务、节点状态查询)+ Prometheus `/metrics`。
- 对内:调用 core 完成缓存索引、数据块存储、校验和回收;服务化层不重复实现其中任何一项。
- 缓存根 `/var/cache/traincache`,CAS 块统一存 `blocks/` 下,物理路径由块内容指纹确定。
- 训练 Pod 经 hostPath 只读挂载直读 CAS 块,读路径不经过 Agent 的 gRPC 读接口。
- 自治能力:训练中持续预取、阶段切换重预取、重启重扫描、坏块修复、热度统计,均无需 Controller 在场。

范围边界:本设计只做本机缓存管家(收任务、算顺序、搬数据、报状态);筛选/门控/打分调度归 Controller,FUSE read-through 内联读与分布式缓存组不在本设计;Python DataLoader 钩子本体由钩子工程实现,这里只冻结其与 Agent 的 socket 协议(钩子工程形态见 decisions Q10)。

## 3. 总体架构与依赖方向

Agent 的 DaemonSet Pod 与训练 Pod 在同一台机器上,通过 hostPath 和 Unix socket 打交道,不走网络。

```
┌─ control plane(未来)──────────────┐        ┌─ 训练 Pod ───────────────────────────┐
│ Controller                        │        │ DataLoader(钩子)                     │
└──────────┬────────────────────────┘        │  │ 位点/打开块(Unix Socket,§5.4)     │
           │ gRPC 南向(§5.1)                 │  ▼                                   │
┌──────────▼──────────────────────────┐      │ Agent(同节点)                        │
│ Agent DaemonSet Pod                 │      │  ordersrc sidecar(Python)            │
│  svc(gRPC + 生命周期 + 装配)        │ ◄────┼─── 共享内存 ring(§6.2)               │
│   ├─ prefetch(四优先级预取)         │      │    按 Job 配置重算 ConsumeOrder      │
│   ├─ ordersource(读 ring)           │      │                                      │
│   ├─ collector(inotify 旁路采集)    │      └──── 直读:hostPath 只读挂载           │
│   ├─ rescan(重扫 / 修复)            │      │   /var/cache/traincache/blocks/      │
│   └─ metrics / nodeid               │      └──────────────────────────────────────┘
└───────┬─────────────────────────────┘
        │ core 库(cas / fetch / index / objectstore)
        ▼
   数据源(S3 对象存储 / 本地源站)
```

两条路要分清。**数据面**:训练进程从 hostPath 直接读块,不经过 Agent;读 miss 时钩子发 `read_miss`,Agent 后台异步补块(§5.4、§7.5)。**控制面**:Controller 或 CLI 通过 gRPC 下发预热任务,sidecar 通过共享内存把消费顺序交给 Agent。

三个可执行产物:

| 产物 | 形态 | 职责 |
|---|---|---|
| `traincache-agentd` | Go,DaemonSet 常驻服务 | 本设计主体 |
| `traincache-ordersrc` | Python,训练 Pod 内 sidecar | 按 Job 配置算出每个阶段的消费顺序,写进共享内存;算出的顺序必须和真实 loader 一致(decisions D3) |
| `traincache` | Go,CLI | 纯 gRPC 客户端 |

依赖方向单向、不允许环:

```
cmd/{agentd,traincache}  →  svc  →  prefetch, collector, rescan, metrics, nodeid, ordersource  →  core
ordersrc(独立小进程,不依赖 core)        api(proto 生成,仅被 svc / cmd / ordersource 引用)
```

- `svc` 是装配层:起服务、读配置、接探针,持有各子模块实例。
- 子模块之间互不依赖,数据由 `svc` 编排(与 core 里"index 不依赖 fetch"同风格),每个模块可单独测。
- `ordersource` 只读共享内存,不碰 core;`ordersrc` 是另一个进程,连 core 都不依赖,可以跟着训练镜像走。

## 5. 核心接口(冻结约定)

### 5.1 gRPC(api/agent.proto)

Agent 对外三个 gRPC 服务,按方向分:

- `PreheatService`:南向,Controller 或 CLI 下发预热任务、查询进度;
- `NodeService`:节点状态查询,CLI 和就绪探针都用它;
- `ReportService`:北向,Agent 往 Controller 报块级结果。proto 现在就冻结,服务端实现推到 Controller 里程碑(decisions Q1)。

```proto
syntax = "proto3";
package traincache.agent.v1;
option go_package = "traincache/agent/api/agentpb";

// 南向:Controller/CLI → Agent(7.0 验收 1/4/5)
service PreheatService {
  rpc SubmitPreheat(SubmitPreheatRequest) returns (SubmitPreheatResponse);
  rpc GetPreheatStatus(GetPreheatStatusRequest) returns (PreheatStatus);
}

// 节点状态查询(CLI 与就绪探针)
service NodeService {
  rpc GetNodeStatus(GetNodeStatusRequest) returns (NodeStatus);
  rpc ListSnapshot(ListSnapshotRequest) returns (ListSnapshotResponse);
}

// 北向:Agent → Controller,块级任务上报。
// proto 随本设计冻结,服务端实现推迟至 Controller 里程碑(decisions Q1)。
service ReportService {
  rpc ReportBlocks(stream BlockReport) returns (ReportAck);
}
```

消息定义(字段名冻结):

| 消息 | 字段 |
|---|---|
| `SubmitPreheatRequest` | `task_id string`(幂等键);`node string`(须等于本节点);`dataset string`;`snapshot_id string`(空=当前 CURRENT;非空值 M3 不支持,返回 `InvalidArgument`);`prefixes []string`(路径前缀,语义同 core `Catalog.LoadPrefixes`:空=空映射,含空串=全量);`chunks []ChunkRef`(可选,块级精确指定);`priority PreheatPriority` |
| `ChunkRef` | `path string`;`chunk int64`(core Entry 寻址) |
| `PreheatPriority` | 枚举 `P0=显式启动预取 / P1=阶段切换重预取 / P2=邻域预取 / P3=后台补全`(默认 P0) |
| `SubmitPreheatResponse` | `accepted bool`;`task_id string`;`message string` |
| `GetPreheatStatusRequest` | `task_id string` |
| `PreheatStatus` | `task_id`;`node`;`dataset`;`snapshot_id`;`paths []string`;`state`(枚举 `QUEUED / RUNNING / DONE / ERROR`);`total_blocks int64`(去重后的唯一块数);`completed_blocks int64`;`failed_blocks int64`;`started_at`、`updated_at`(google.protobuf.Timestamp);`window_blocks uint32`(当前窗口块数,等于 `chunks` 项数,含重复位置) |
| `GetNodeStatusRequest` | `node string`;`item NodeStatusItem`(枚举:全量 / agent / catalog / space / tasks / rescan) |
| `NodeStatus` | `node`;`agent_ok bool`;`cache_root string`;`cached_bytes int64`;`free_bytes int64`;`running_tasks int64`;`rescan RescanStatus`;`catalog []DatasetCatalog` |
| `RescanStatus` | `phase`(枚举 `SAMPLING / FULL_SCAN / DONE`);`sampled int64`;`verified int64`;`quarantined int64`;`repair_queue int64` |
| `DatasetCatalog` | `dataset string`;`snapshot_id string`;`shards int64`;`entries int64` |
| `ListSnapshotRequest` | `dataset string`;`snapshot_id string`(空=CURRENT);`prefix string` |
| `ListSnapshotResponse` | `entries []EntryRef`(`path`;`chunk`;`size`) |
| `BlockReport` | `node`;`task_id`;`ref ChunkRef`;`fp string`;`bytes int64`;`result`(枚举 `OK / CORRUPT / REFETCHED`) |
| `ReportAck` | 空 |

错误语义:

- 任务校验失败(节点不符、dataset 不存在)→ `InvalidArgument`;
- 同 `task_id` 内容不同 → `AlreadyExists`(幂等:内容相同返回现有任务);
- `task_id` 是幂等键。

RPC 一律带 context 超时,Agent 侧默认 10s;长时间任务靠 `GetPreheatStatus` 轮询,不做长连接流。

### 5.2 PersistentPrefetcher(prefetch 包)

Agent 的心脏:四个严格优先级队列(P0>P1>P2>P3),一个调度协程串行出队,并发下载受 core fetch 的分级额度约束——需求读补块走前台,预取走后台。队列任务按块去重,同一块不排两次。

```go
type PersistentPrefetcher struct{ /* ... */ }
func New(cat *index.Catalog, f *fetch.Fetcher, cs *cas.Store,
         m *metrics.Registry, cfg Config) *PersistentPrefetcher

type Config struct {
    Lookahead int // 邻域预取提前量,默认 16(≤0 取默认;D16)
    // OnP0Done:P0 块完成回调(ref=块引用,err=该块结果;err==nil 表示就绪或下载成功),
    // 在调度协程内同步调用,不得阻塞;nil 表示无回调(仅 P0 触发)。
    OnP0Done func(ref ChunkRef, err error)
}

// 开始持续预取:从 cursor 起按当前 ConsumeOrder 邻域预取,每完成一块推进 cursor 并上报 /metrics。
// 可被显式启动预取(P0)与阶段切换重预取(P1)打断:在途请求不取消,新请求按更高优先级入队。
func (p *PersistentPrefetcher) Start(ctx context.Context)

// DataLoader 钩子每消费完一块调用,推进消费位点;预取提前量 = consume + lookahead(默认 16)。
// 返回是否真正推进:ref 不在当前订单、ctx 已取消、尚无阶段,或 idx <= consume
// (重复/回退事件)返回 false,且不产生任何副作用。
func (p *PersistentPrefetcher) OnConsumeSideAdvance(ctx context.Context, ref ChunkRef) bool

// 阶段切换:旧阶段 cursor 之后未消费块降级 P3(在途请求不取消);
// 新阶段开头 K 块(K = 新 ConsumeOrder.prefetch_chunks)作为 P1 高优先级入队,剩余块转 P2 邻域预取;
// 返回"切换时刻到新窗口就绪"的预估时间,供 Agent 上报 traincache_stage_switch_eta_seconds。
func (p *PersistentPrefetcher) OnStageSwitch(ctx context.Context, next ConsumeOrder) (eta time.Duration, err error)

// 显式启动预取(P0)入队:refs 按顺序以 P0 严格最高优先级入队,在途不取消;
// 每块完成(就绪或下载成败)经 Config.OnP0Done 回调(若有)。空列表返回 nil。
// 去重(D45):以 blockKey(dataset,ChunkRef)=<dataset>/blocks/<path>#<chunk>(与 fetch key 一致)维护 pending 表;
// 键已存在且 task 未开始 → 按最高优先级提升(不新建 task);已在运行 → 忽略。
func (p *PersistentPrefetcher) EnqueueP0(ctx context.Context, refs []ChunkRef) error

type Status struct {
    Stage            string   // 当前阶段标识
    Cursor           ChunkRef // 纯消费位点:仅由 advance/inotify 推进
    PrefetchFrontier ChunkRef // 预取前沿:已就绪的最远块(不要求连续)
    QueueDepth       [4]int   // P0..P3 各队列长度(按去重后的 task 计数,D45)
    HitRate          float64  // 预取命中率(窗口内消费时块已就绪的比例),供自适应 K 调参
}
func (p *PersistentPrefetcher) Status() Status
```

内部约定:

- 并发抓取由 core fetch 统一约束,预取自己不管限速:预取块按后台优先级准入,最多占半额任务槽与半额在途字节,需求读回源时还要让路(5.1 §5.3);
- ETA = 新窗口剩余未就绪字节 ÷ 最近 30s 滑动平均吞吐(EMA α=0.3,口径含回源与本地命中);
- 已经在本地(Catalog.Lookup 命中且 cas.Open 成功)的块不产生下载,直接当就绪处理——否则每次阶段切换都会重复下已有的块。

并发约定(D45):

- pending 表覆盖 P0–P3 队列和运行中的 task,由 `mu` 保护;同一个 blockKey 任一时刻最多一个 task;task 成功或终止后移除键,失败重试期间保留;OnDone / OnP0Done 对每个被接受的 task 恰好回调一次;SubmitPreheat 的 total / completed 按去重后的块计数,重复提交不会让数字翻倍。

阶段与打点约定(指标契约见 §5.8):

- phase 状态机只有四个取值:`phase ∈ {startup, steady, switch, unknown}`。
  - `startup`:Agent 启动起,到首个 ConsumeOrder 的首 K 块就绪(称"启动窗口 ready"),K = §6.1 `prefetch_chunks`;
  - `switch`:`OnStageSwitch` 起到新窗口 K 块全部就绪,完成点与 ETA 一致;
  - `steady`:其余时间;
  - `unknown`:判定不了的情况,比如事件关联不到任何已知窗口、降级后关联不到阶段。
  - 两个窗口同时活跃时,`switch` 优先。
- 双游标口径:消费游标由 `advance` 钩子推进(降级期由 inotify 打开事件兜底,§7.4),`Status.Cursor` 暴露这个口径;预取前沿指"已就绪的最远块",不要求连续,经 `Status.PrefetchFrontier` 暴露。`Status` 不暴露调度游标(`traincache_prefetch_cursor` 指标仍是调度游标)。`Start` 里"每完成一块推进 cursor"说的是预取前沿,不改消费游标。
- 预取领先:`traincache_prefetch_lead_blocks` = 预取前沿 − 消费游标(按当前 ConsumeOrder.Chunks 序列计块数),即 `lead = frontier − cursor`,可以为负;负值表示消费跑在预取前面,要等数据。
- 任务耗时打点位置:task 被 pending 表接受并入队时记起点,同 blockKey 去重提升不重置起点;进入终态(就绪或下载失败终止)时向 `traincache_prefetch_task_duration_seconds{dataset, priority}` observe 一次。priority ∈ {P0,P1,P2,P3},取 task 最终生效的最高优先级;CLI 的 `--priority` 用小写 p0..p3,映射到指标标签时统一大写 P0..P3。
- `Status.HitRate` 以最近 100 个消费样本的滑动窗口计算,直接输出为 `traincache_prefetch_hit_ratio{dataset}`(§5.5)。

### 5.3 OrderSource 与共享内存(ordersource 包)

消费顺序由训练 Pod 里的 sidecar 算出,写进共享内存 ring,Agent 侧 `Reader` 读出。两侧约定:

```go
type ChunkRef struct {
    Path  string `json:"path"`  // core Entry 寻址(§5.1 ChunkRef)
    Chunk int64  `json:"chunk"`
}

type ConsumeOrder struct {
    Dataset        string     `json:"dataset"`
    SnapshotID     string     `json:"snapshot_id"`
    StageID        string     `json:"stage_id"`
    ShuffleSeed    int64      `json:"shuffle_seed"`
    BatchSize      int64      `json:"batch_size"`
    PrefetchChunks int        `json:"prefetch_chunks"` // 启动窗口大小 K
    Chunks         []ChunkRef `json:"chunks"`          // 本阶段消费顺序(有序块引用列表)
}

type OrderSource interface {
    // 当前阶段的消费顺序;尚无任何推送时返回 false。
    CurrentOrder() (ConsumeOrder, bool)
    // 订阅阶段切换事件:channel 每收到一个事件 push 一份新 ConsumeOrder。
    SubscribeStageSwitch(ctx context.Context) (<-chan ConsumeOrder, error)
}

// 读端实现:mmap 共享内存文件(布局见 §6.2),由 svc 装配。
// watchDir = /run/traincache/orders,自动发现新 Pod 的 ring 文件。
func NewReader(ringPath string, watchDir string) *Reader
```

语义约定:

- 阶段切换三源归一(decisions D10):epoch 边界、shuffle 重排、curriculum 切换,在 Agent 眼里是同一件事——sidecar 重算,推一份新的 ConsumeOrder,Agent 不区分事件来源。
- ring 单写(sidecar)单读(Agent)。writer 重启靠代际计数检测;reader 落后不阻塞 writer,直接跳到最新——阶段切换只关心最新顺序。
- Agent 侧心跳就是 ring 的写入序号推进;30s 没有推进 → 进入降级模式(§7.4,验收 10)。

### 5.4 钩子 Unix Socket 协议

DataLoader 钩子(Python,训练 Pod 内)往 Agent 发消息:Unix datagram socket `/run/traincache/agent.sock`,行分隔 JSON,单向,Agent 不回帧。选 datagram:丢一帧不影响训练,不需要重传。帧共五种类型(D11、D44、D47):advance / stage_switch / open_report / read_miss / read_stall。

```json
{"type":"advance","path":"...","chunk":3}
{"type":"stage_switch","stage_id":"epoch-2","shuffle_seed":12345}
{"type":"open_report","path":"...","chunk":3}
{"type":"read_miss","path":"...","chunk":3,"reason":"absent","ts":"2026-10-18T10:00:00Z"}
{"type":"read_stall","path":"...","chunk":3,"wait_ms":250,"ts":"2026-10-18T10:00:00.123456789Z"}
```

五帧各自的去向:

- `advance` → `OnConsumeSideAdvance`。
- `stage_switch` → 转交 `OnStageSwitch`。主通道是 sidecar 推送,钩子直报算双通道冗余,以先到者为准并去重。
- `open_report` → collector 的命中率统计。它和 inotify 是两个来源,钩子为主,inotify 兜底。
- `read_miss`(D44)→ `HookHandlers.Miss(ref, reason)`。字段 `path`、`chunk`、`reason`(`absent`|`corrupt`)、`ts`;分不清 absent 和 corrupt 时按 `absent` 上报。svc 收到后先解析 dataset 归属,再看索引与本地块:归属解析不要求 Catalog 命中;条目未命中不影响归属,缺失块仍按 D25 键 `(dataset, path, chunk)` 以最高优先级 P0 入队补块,复用 `EnqueueP0` 语义,回源 reason=`demand`——demand 不依赖索引;损坏(ErrCorrupt)走 repair,即 `Quarantine` + `RepairOne`。这一帧是事后信号,best-effort,不保证本次读之前补齐。demand 和 prefetch 共用同一个 Fetcher、同处一个 single-flight 域,但准入等级不同:demand 走前台(`fetch.PriorityForeground`)、prefetch 走后台(`fetch.PriorityBackground`),demand 因此不会被在途预取挡住;补不及则本次读仍失败,正确性契约不变。训练侧不直连对象存储、保持只读 hostPath、不拿凭证,训练侧 Open 失败后只用这个单向异步通道把缺失块告诉 Agent,由 Agent 在自己的 fetch 域里补块。
- `read_stall`(D47)→ 实际消费等块 ≥100ms(阈值可配)时由钩子上报,字段 `type`、`path`、`chunk`、`wait_ms`、`ts`(RFC3339Nano);`type` 是帧类型字段名,和既有各帧一致,取值 `read_stall`。Agent 按 `ts` ±5s 去关联该块的预取状态,归因分四类:
  - 本地存在且不是当前窗口预取的 → `local_slow`;
  - core fetch 在途 → `origin_slow`;
  - 不在本地也不在途(pending 或未知)→ `prefetch_lag`;
  - 解析不了或者超出时间窗 → `unknown`。
  归因结果写进 `traincache_read_stall_seconds{dataset, phase, cause}`;只有 ≥100ms 的等待进直方图。帧格式错误照旧计 `traincache_hook_format_errors_total{reason="parse|size"}`(D33)。

socket 不存在或 sidecar 缺席时,Agent 转降级模式,改用 inotify 打开事件驱动(§7.4)。

### 5.5 热度与命中率(collector 包)

collector 用 inotify 旁路监听缓存目录的文件打开事件,不侵入训练进程,产出热度(给淘汰用)和命中率(给人看和给调参用)。用途:命中率判断缓存效果,触发扩容、预警。

```go
// inotify 旁路监听缓存目录打开事件(不侵入训练进程)。
func NewCollector(blockDir string, ring *ordersource.Reader,
                  m *metrics.Registry, cfg CollectorConfig) *Collector
func (c *Collector) Start(ctx context.Context)

type CollectorConfig struct {
    HeatDecayAge       time.Duration // 超过 N 的记录直接衰减热度,默认 24h
    HeatDumpInterval   time.Duration // 每 DumpInterval 分钟 dump 一次,默认 30min
    HeatDecayInterval  time.Duration // 每隔 T 全体乘衰减因子,默认 24h
    HeatDecayFactor    float64       // 默认 0.5
    HeatOpenBeta       float64       // 单次打开的热度增量系数 β,默认 0.15(D24)
    HeatTouchHalfLife  time.Duration // 新鲜度 R 半衰期 T_R,默认 6h(D24)
    CalibrateWindow    int           // 交叉校准滑动窗口,默认 100 次打开
    CalibrateThreshold float64       // 匹配率低于该值重对齐,默认 0.8(即 7.0 默认 20% 偏差)
}
```

数据结构与更新规则:

- 热度映射是 `指纹 → (热度h, 最近触摸时间t_touch)`,在内存里持有,定期 dump 成 `heatmap.json`(§6.4)。指纹是块的 xxh3 哈希,同一块换路径也认得。
- `type EvictionEntry struct { FP cas.Fingerprint; Heat float64; LastTouch time.Time; Accesses int64 }`——Collector 和 Evictor 两边各有一份定义但字段一致。`Accesses` 是累计打开次数(collector.accessCount),供 LFU 档策略消费(策略抽象与三档选型见 6.3 D59,M4 实现;W-TinyLFU 档已撤档)。
- 更新规则(D24):每次 OPEN 合并后 `h ← h + (1−h)·β`,热度按比例逼近 1,越热的块涨得越慢。每 T 全体乘衰减因子、超 N 直接衰减并淘汰得分低于阈值的条目;`t_touch` 取最后打开、预取写入、新 ConsumeOrder 刷新三者的最大值。同一进程反复打开一个文件要合并(训练进程一个 epoch 里可能反复打开同一块,inotify 每次都报 OPEN;合并后统计的是"有多少数据被读",不是"打开次数")。
- 淘汰得分:**`S = max(h, R)`**,其中 `R = 0.5^(Δt/T_R)`(Δt = now − t_touch),双信号取强:「刚预取还没被读过」靠 R 保,「历史热块久未读」靠 h 保;加权平均做不到同时保护两类块。依据见 6.3 D24。淘汰序与两条线见 §7.6。
- 命中率:把消费者(插桩的 DataLoader,只完成上报接口不写逻辑)报告的打开块集合和本地块集合求交集,滚动窗口按分钟级统计,再按训练阶段聚合。不落长期历史,导出到监控,重启即丢。阶段与来源词汇冻结:
  - `phase ∈ {startup, steady, switch, unknown}`(状态机见 §5.2);命中/未命中按事件发生时的 phase 打标。
  - 命中来源 `source ∈ {prefetch, cache, unknown}`:prefetch = 当前窗口内由 Agent 预取放置;cache = 本地已有且非当前窗口预取;unknown = 无来源信息。
  - 预取命中率口径:`Status.HitRate` = 最近 100 个消费样本里"消费时块已就绪"的比例,输出为 `traincache_prefetch_hit_ratio{dataset}`。它和 `cache_hit_ratio`(hits/(hits+misses),打开命中率)是两个口径,不混用。
  - dataloader 上报并非完美精确,计划读到的不一定实际成功读到;本设计不声称 Agent 在读路径上做了精确记账,指标是观测口径而非账本。
- 交叉校准:窗口内实际打开顺序和 OrderSource 期望顺序的匹配率低于 0.8 时,调 `OnConsumeSideAdvance` 把 cursor 重对齐到实际位点,防止 sidecar 算的顺序和真实 loader 长期漂移。

热度只做决策输入,不参与正确性。

### 5.6 CLI(cmd/traincache)

CLI 是纯 gRPC 客户端:不直接操作缓存目录,不重复实现缓存索引、数据块下载或落盘,所有逻辑在 Agent 侧,线上线下行为一致。

```
traincache prefetch --task-id T --path /train-data --node worker-01 \
                    --chunks shard-000.tar:0,shard-000.tar:1 \
                    [--dataset NAME] [--snapshot-id ID] [--priority p0|p1|p2|p3]
traincache prefetch --task-id T --path /train-data --node worker-01 \
                    --files shard-000.tar,shard-001.tar --dataset NAME \
                    [--snapshot-id ID] [--priority p0|p1|p2|p3]
traincache ls --dataset NAME [--snapshot-id ID] [--prefix P] [--chunks]
traincache node status --node worker-01 [--item agent|catalog|space|tasks|rescan]
traincache status --node worker-01 --task-id <task-id>
```

- 全局 `--endpoint` 默认 `127.0.0.1:9410`。`--node` 只作请求校验字段,不做地址解析(decisions Q2):它告诉服务端"预期操作哪台机器",连哪台由 endpoint 决定。
- `--priority` 接受小写 `p0|p1|p2|p3`,映射到指标标签时统一为大写 `P0|P1|P2|P3`(与 §5.8 指标词汇一致)。
- `--chunks` 是逗号分隔的 `path:chunk`,每项直接构造 `ChunkRef` 填入 `SubmitPreheatRequest.chunks`;此时 `--dataset` 可选。
- `--files` 是逗号分隔的 tar 分片名,必须同时给 `--dataset`;CLI 先调 `NodeService.ListSnapshot`,把每个分片展开为该分片的全部块,再填入 `chunks`。分片名在快照中找不到时退出 1。
- `--chunks` 与 `--files` 互斥且至少给一个;`--path` 是 `SubmitPreheatRequest.prefixes` 的唯一元素。
- 路径预热:Agent 若没有存储该路径下的快照,去远端拉取(详见 6.x)。
- `traincache node status` 输出(7.0):Agent 是否可用、缓存目录内容、已缓存数据量、缓存剩余空间、运行中预热任务数、索引恢复与扫描状态;`--item` 只查其中一项。
- `traincache status` 输出(7.0):任务 id、目标节点、数据路径、任务状态(等待/进行中/错误/完成)、总块数、已完成块数、失败块数、任务开始时间、最近更新时间。
- `traincache ls` 列出快照条目:默认按文件聚合输出 `FILE CHUNKS BYTES`;`--chunks` 展开到块,输出 `FILE CHUNK BYTES`。`--dataset` 必填,`--snapshot-id` 空表示当前 CURRENT,`--prefix` 过滤路径。
- 没写 `--dataset` 时,`--path` 必须能映射到已注册的 dataset,校验在 Agent 侧做。输出默认人类可读表格(JSON 方案见 decisions Q9)。

### 5.7 核心库增量:cas 坏块隔离

7.0 要求"将块标记为坏块(需要增加标记位)"。实现不加标记位,改为把坏块移进 cas 根下的 `quarantine/` 目录,与 `blocks/` 平级,`List()` 自然看不到它。方法由核心库提供(core 5.3 D24–D27,6.2 plan.md M0 引用):

```go
// cas.Store 新增:
//   坏块物理移入 cas 根下 quarantine/ 目录(与 blocks/ 并列),不再出现在 List() 中。
func (s *Store) Quarantine(fp Fingerprint) error         // Open 校验失败的块可调用;幂等
func (s *Store) ListQuarantined() ([]Fingerprint, error)
func (s *Store) RemoveQuarantined(fp Fingerprint) error  // 修复成功后清理
```

Agent 侧用法:读时遇到坏块走 repair,顺序 `Quarantine` → 入修复队列 → `fetch.Fetch` 回源重下 → `cas.Put` → 校验通过 → `RemoveQuarantined`。多个并发 repair 撞同一块时复用 core 既有 single-flight,只下一次(7.0 验收 6)。`cas.Put` 对已存在同指纹块的行为是 rename 原子覆盖(幂等覆盖),已登记为 core 5.3 D27。

语义与词汇(冻结,全集词汇表另见 6.3 D36):

- `phase ∈ {startup, steady, switch, unknown}`;命中来源 `source ∈ {prefetch, cache, unknown}`;stall 归因 `cause ∈ {local_slow, prefetch_lag, origin_slow, unknown}`;消费推进 `source ∈ {hook, inotify}`;priority ∈ {P0,P1,P2,P3}(大小写映射见 §5.2)。
- `traincache_cache_hits_total` 的 `result` 固定 `success`;`traincache_cache_misses_total` 的 `result ∈ {success, error, refetched}`(refetched 对应 demand 补块成功,§7.5)。
- 回源 `reason ∈ {prefetch, demand, repair, other}`,术语冻结:prefetch(预取)= 按 P0–P3 队列主动提前下载;demand(按需补块)= 训练侧 `read_miss` 钩子触发、复用预取队列补块;repair(修复)= 坏块 `Quarantine` 后重下;回源(origin fetch)是三者总称,不是第四条路径。这三组词在文档和代码里不能互相替代,写错会导致指标口径对不上。帧名 `read_miss`、`handleReadMiss`、`traincache_hook_read_miss_total` 保持不变(该指标统计帧,不区分回源路径)。
- `traincache_fetch_singleflight_merged_total` 由 Agent 侧的 fetch 调用包装器统计:同一个 key 在途时第二个调用 +1,不改 core/fetch。
- `traincache_fetch_bandwidth_limit_bytes` = 配置的字节信号量上限(全场口径,后台预取实际可用一半);与 `traincache_fetch_inflight_bytes` 求比值可判断限速是否打满。
- `traincache_prefetch_hit_ratio` 来自 `Status.HitRate`(100 样本滑动窗口,§5.2/§5.5)。
- `traincache_read_stall_seconds` 只记 ≥100ms 的消费等待(阈值可配);`_count` = stall 事件数,`_sum` = stall 总时长。
- `traincache_stage_switch_eta_seconds` 是"阶段切换预计 stall(ETA)",不是实测 stall;实测值一律走 `traincache_read_stall_seconds`(phase=switch)。两者不得混用或互相替代。
- `traincache_quarantined_blocks` 与 `traincache_repair_queue_depth` 归 GC 线(对齐 7.0「坏块隔离和修复队列」)。
- `traincache_consumption_advance_total` 的 inotify 兜底:inotify OPEN → 指纹反查当前订单 → `OnConsumeSideAdvance`,单调 consume 去重后计 source="inotify";钩子活跃期 inotify 被 collector 门控抑制,不会和 source="hook" 双计。已知限制:反查只覆盖当前订单的 Chunks。
- `traincache_index_refresh_total` 的 `result ∈ {success,error}`(R1 快照跟随复用,沿用既有 metrics 契约);失败不切换、不清空。`traincache_index_sweep_skipped_total` 的 `reason` 当前是 `manifest_unavailable`。

固定 bucket:

- `traincache_request_duration_seconds` / `traincache_index_refresh_duration_seconds`:`{.01,.05,.1,.5,1,5,10,30}`s;
- `traincache_read_stall_seconds`:`{0.1,0.25,0.5,1,2,5,10,30,60}`s;
- `traincache_prefetch_task_duration_seconds`:`{0.1,0.5,1,2,5,10,30,60,120}`s。

基数纪律(7.0 原文要求,目标是 Prometheus 时间序列数量不随数据规模爆炸):

- 标签编译期固定,不引入用户输入;phase / source / cause / reason / priority 取值都是编译期枚举,集合外的值直接忽略该次打点,不新增基数;
- `dataset` 走配置文件白名单,白名单外记 `other`;
- `node` 是第二正交维度,为多节点聚合预留;多项目共用对象存储时 dataset 是区分归属的核心维度;
- 高基数维度(path / chunk / fp / task_id)进日志或追踪(decisions Q6);延迟用固定 bucket(见上)。

### 5.9 快照角色边界:快照发布 vs 快照跟随

Agent 只读快照,不发布快照。

- **快照发布(写入方)**:产生新 entries 的组件调用 core/index `(*Writer).Commit`,由它合并快照并推进 CURRENT。Controller 现有职责不产生新索引,因此不直接调用 `Commit`;Agent 不承担发布职责。发布方落地见 `TODO.md`（B）。
- **快照跟随(Agent,只读)**:经 `index.Catalog.Start` / `Catalog.Refresh` 定时读 CURRENT → 下载并校验 manifest 与引用分片 → `atomic.Pointer` 原子切换内存映射(读的人永远看到完整一份);失败保持旧映射。Agent 不调用 `Commit`。
- **自开观测防护**:core/cas 提供 `SetOpenObserver(func(Fingerprint))`,在 `Store.Open` 内于 `os.Open` 之前回调,仅登记"本进程即将读打开该块",不改变 Open 行为;observer 挂在 Store 实例上,传 nil 清除,不做进程级全局。Agent 装配中创建 `cas.Store` 时调用 `cs.SetOpenObserver(guard.Mark)` 安装,位置必须在任何 prefetcher / rescan / backfill / fetch 构造之前——一旦有写入方内嵌调用 `Commit`,其自开读会污染消费侧信号(inotify 热度、Cursor)。现有各调用点显式 Mark 保留,幂等。

**前缀感知快照跟随(R1,冻结契约)**

- `(*index.Catalog).SnapID() string`:原子读当前 snapID,无则空串。
- `(*index.Catalog).RefreshManifest(ctx context.Context) error`:读 CURRENT+manifest,成功则原子切换 snapID 与空 entries;用于无活跃前缀时。当前 snapID 未变且现有 entries 非空时为空操作:不切换、不清空,也不触发 `OnSnapshotChange`。
- `(*index.Catalog).Follow(ctx context.Context, prefixes func() []string) error`:阻塞循环,每 `Config.RefreshInterval` 检查 CURRENT;未变则跳过;`prefixes` 非空调 `LoadPrefixes`,为空调 `RefreshManifest`;失败保持旧映射并继续下一轮。
- `index.Config` 新增 `OnSnapshotChange func(dataset, snapID string)`:由 `Refresh` / `LoadPrefixes` / `RefreshManifest` / `Follow` 在每次成功原子切换后、锁外触发(Follow 经其内部调用的加载方法触发);未发生切换的空操作不触发;不得阻塞,回调 panic 不得向调用方传播,nil 安全。
- `index.Config` 新增 `OnSnapshotError func(dataset string, err error)`:仅由 `Follow` 内部单轮加载失败触发(锁外调用),用于错误计数;同样 nil 安全且 panic 不外传。其他加载方法失败不触发该回调。
- Agent 侧:`svc.Config` 新增 `IndexRefreshInterval time.Duration`(默认 5s);per-dataset 首次创建 Catalog 后启动一次 `go cat.Follow(ctx, prefixesFn)`,`prefixesFn` 返回该 dataset 最近订单的路径前缀。`Follow` 启动即执行首轮检查,所以启动时机在 bundle 构造内、当前订单的路径前缀 hint 写入之后(svc 在 `m.mu` 与 bundle 锁下先装 hint 再启动 Follow),首轮 tick 不得读到空前缀;`ForOrder` 与 Follow 的加载必须串行(复用 Catalog 内部互斥)。
- 刷新指标复用现有 `index_refresh_total{dataset,result}`,`result ∈ {success,error}`;失败不切换、不清空。

### 5.10 快照读者登记、心跳与撤销(R2,冻结契约)

GC 删旧快照前需要知道还有没有节点在读;每个节点的 Agent 主动登记"我在读哪个快照"。

新增 `core/index/readers.go`:

- `type ReaderClaim struct { NodeID string; SnapID string; PreviousSnapID string; PreviousUntil time.Time; UpdatedAt time.Time }`,JSON 字段 `node_id` / `snap_id` / `previous_snap_id,omitempty` / `previous_until,omitempty` / `updated_at`。
- 对象键 `dataset/<dataset>/readers/<url.PathEscape(nodeID)>.json`(一节点一 dataset 一文件)。
- `func NewReaderRegistry(store objectstore.Store, nodeID string, grace time.Duration) *ReaderRegistry`(grace<=0 回退 10s)、`Declare(ctx, dataset, snapID) error`、`Withdraw(ctx, dataset) error`、`ReadReaderClaims(ctx, store, dataset) ([]ReaderClaim, error)`。
- `Declare`:切换快照(本次 snapID 与上次不同)时写 `previous_snap_id=旧 snap`、`PreviousUntil=now+grace`(给 GC 一个宽限期:刚切换完旧快照不能立刻删);同一快照重复声明保留 previous/PreviousUntil,待 `now > PreviousUntil` 后清空;Put 覆盖;幂等;成功后更新内存 last。
- `Withdraw`:写 `snap_id=""`、`previous_snap_id=<last>`、`PreviousUntil=now+grace`、`updated_at=now`,之后停止心跳;best-effort。
- `ReadReaderClaims`:无对象返回空集合;JSON 损坏返回错误(GC 需 fail-safe)。
- Agent 侧:用 `nodeid.FromEnv()` 的 ID 构造 registry;心跳间隔 = `IndexRefreshInterval/2`(下限 1s);ctx 取消时对已知 dataset 调 `Withdraw`(超时 5s);`OnSnapshotChange` 立即 `Declare`。

### 5.11 GC 按读者确认删除(R3,冻结契约)

GC 的安全边界从"CURRENT + 固定保留最近 N 个"改为按有效 claim 判断——固定保留数对正在切快照的读者不安全。

`index.Config` 新增 `ReaderGrace time.Duration`(零值回退 `2*RefreshInterval`,默认 10s)与 `OnSweepSkip func(dataset, reason string)`。

`Collector.Sweep` 规则:

1. 读 claims;`UpdatedAt` 超过 `ReaderGrace` 的 claim 整体忽略(视为读者已死)。
2. 有效 claim 的 `SnapID` 计入 protected;`PreviousSnapID` 仅在 `now ≤ PreviousUntil` 时计入 protected(切换/撤销宽限期)。
3. protected = CURRENT ∪ 固定保留窗口(最近 `RetainSnapshots` 个)∪ 有效 claim 集合;`RetainSnapshots` 降级为兜底上限,不再是安全边界。
4. 快照对象(manifest+分片)只在"不在 protected"时删除;CURRENT 永不删除。
5. protected 快照的 manifest 缺失或损坏:调用 `OnSweepSkip(dataset,"manifest_unavailable")`,跳过本轮块删除,但继续删除其他可删快照对象,不得整轮停摆。
6. 块删除仍要求"不在 liveBlocks 且 ref=0 且 pin=0";liveBlocks 必须由全部 protected 快照重建——漏了这一步,活块会被误删。
7. 删除顺序保持"先快照对象、后数据块";同一轮内不新增额外宽限。

### 5.12 Commit 孤儿清理与条件写探测(R4,冻结契约)

- `(*index.Writer).commitOnce` 记录本次 attempt 新 Put 的分片键与 manifest 键;任何失败(含冲突重试前、验证失败)做 best-effort `Delete`(逆序、超时 5s、错误忽略、不覆盖原始错误);不复用键不删;`PutIfMatch` 成功提交后不清理。失败的尝试不在对象存储里留下无人引用的孤儿对象。
- GC 遇 protected 快照 manifest 缺失按 §5.11 第 5 条处理。
- 新增 `objectstore.ErrConditionalWriteUnsupported` 与 `func ProbeConditionalWrite(ctx context.Context, s Store) error`:写临时键,用不匹配 ETag 调 `PutIfMatch`;期望 `ErrConflict`,若返回 nil 则返回 `ErrConditionalWriteUnsupported`;结束删除临时键。目的是提前知道后端支不支持条件写,不必等真正提交时才失败。
- Agent `svc.Config` 新增 `ObjstoreProbeConditionalWrite bool`(默认 false);开启时装配期探测,指标 `traincache_objectstore_conditional_write_supported` 取值 0/1、预置 0,不支持时告警但不阻止启动。
- bench/k8s/minio.yaml 作为开发演练用的本地 S3 兼容后端(MinIO 镜像固定为 `pgsty/minio:RELEASE.2026-08-04T00-00-00Z`,manifest digest `sha256:b6bfe7239bfc83fb90d31612d9704d86039dd714f7904b3f1ad68f211e602372`);真实环境连 COS/OSS/S3 时不需要这个文件;新增真实后端条件写集成测试,环境变量 TC_S3_ENDPOINT / TC_S3_ACCESS_KEY / TC_S3_SECRET_KEY / TC_S3_BUCKET 任一缺失则 skip,存在时期望冲突返回 ErrConflict/412。

## 6. 数据格式

字节层面的约定,实现逐字照做。JSON 字段顺序不影响解析,字段名和类型不能改。

### 6.1 ConsumeOrder(共享内存载荷,JSON)

```json
{
  "dataset": "b-track", "snapshot_id": "snap-20261014",
  "stage_id": "epoch-2", "shuffle_seed": 20261015,
  "batch_size": 32, "prefetch_chunks": 256,
  "chunks": [ {"path": "shard-000.tar", "chunk": 0}, {"path": "shard-007.tar", "chunk": 0} ]
}
```

字段语义见 §5.3。两条硬要求:`chunks` 必须按消费顺序排列,顺序错了预取就全错;`prefetch_chunks` 就是 §7.3 里的启动窗口 K。

### 6.2 共享内存环形缓冲布局(文件 /run/traincache/orders/<pod-uid>.ring)

小端字节序。sidecar 负责创建并 `ftruncate`,Agent 只读 mmap。文件头 64 字节:

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 4 | magic `"TCO1"` |
| 4 | 2 | version=1 |
| 6 | 2 | 保留 |
| 8 | 8 | `writer_generation`(sidecar 每次启动 +1) |
| 16 | 8 | `write_seq`(全局递增写入序号) |
| 24 | 4 | `slot_size`(默认 1 MiB) |
| 28 | 4 | `slot_count`(默认 64) |
| 32 | 32 | 保留 |

64 B 头之后是 slot 数组,每个 slot 布局:`seq int64` + `len int32` + `payload`(ConsumeOrder JSON,UTF-8)。约定:

- 单写单读;writer 只追加序号,不回收;reader 按 `write_seq` 追读,落后超过 slot_count 时直接跳至最新,不阻塞 writer;
- `writer_generation` 变化 → reader 丢弃旧状态重读最新(识别 sidecar 重启:旧 ring 序号可能和新的对不上);
- 读端发现格式不符(magic / version 不对)→ 忽略该文件并计入错误指标(§5.8 ordersource_format_errors);
- 文件放在 tmpfs 上(hostPath `/run/traincache`,两侧 Pod 同路径挂载),宿主机重启自动清空,与"重启丢弃长期历史"语义一致。

### 6.3 钩子帧(socket JSON)

帧格式与五帧字段见 §5.4。约束:单帧 ≤ 4 KiB;解析失败就丢弃并计数(异常计数不带 dataset 标签,防基数膨胀)。`read_stall` 的 `ts` 为 RFC3339Nano,`wait_ms` 仅 ≥100ms 上报;归因规则见 §5.4。

### 6.4 heatmap.json(路径 /var/cache/traincache/heatmap.json)

```json
{
  "version": 1,
  "dumped_at": "2026-10-14T10:00:00Z",
  "entries": { "<fp32hex>": { "heat": 1.5, "last_access": 1763000000, "access_count": 3 } }
}
```

周期性原子写(临时文件 → rename),进程中途挂掉不留半个 JSON。重启恢复时读它;写入失败不影响服务,最多丢一段热度历史。

### 6.5 指标命名规则

同一层级同一前缀,全部 `traincache_`。取值集合可枚举的低基数维度进标签(dataset / node / result / endpoint / priority),取值数量随数据增长的高基数维度进日志;`dataset` 白名单外记 `other`(7.0 基数控制原则)。

## 7. 关键流程

### 7.1 启动与重启重扫描

Agent 重启后需要重建 CAS 索引,才能知道哪些块本地直接命中、哪些需要重新拉取;磁盘会静默损坏,所以要校验。启动后按顺序五件事:

1. 读配置(§8)→ 校验 nodeid → 初始化 core(cas / fetch / objectstore / catalog)。
2. 枚举块目录(`cas.List`)重建内存索引,同时读取 heatmap.json。不读块内容,很快。
3. 抽样校验:随机挑 1% 的块全读校验(cas.Open 自带 xxh3 校验)。全过 → 大概率这批块没问题,先把服务挂出来;发现损坏 → `Quarantine` 塞进修复队列,交给后台全量慢慢修。抽样让服务尽快可用,全量校验放后台低优先级。
4. 后台全量扫描:低优先级遍历所有块,维护一个需修复的队列,队列中已有的修复问题优先于剩余块的扫描。坏块在读时全量扫描还没修好:从队列拿出来,交给 Agent 直接从对象存储拉取,与修复下载共用 core 的 single-flight,不会两边都下。扫描期间读 miss 的异步处理见 §5.4/§7.5(`absent` → demand,`corrupt` → repair;补不及则本次读仍失败)。全量扫描没跑完也能正常服务,因为 CAS 读块时本身自校验,后台全量是提前发现。
5. 就绪探针判断条件:gRPC 服务可用,且抽样阶段完成。全量扫描进行中不影响 ready(7.0 部署约束)。

先求"能用",再求"全验"。

### 7.2 预热任务生命周期(验收 1/5)

一次 `SubmitPreheat` 的完整路径:

`SubmitPreheat` → 校验 node / dataset → 解析快照(CURRENT 兜底)→ **`Catalog.LoadPrefixes(prefixes)` 只加载所需 Manifest 分片**(验收 5;整份 manifest 在大数据集上加载慢到不可接受)→ 得块列表(与 `chunks` 求交,空=全量)→ 建任务(QUEUED)→ P0 入队 → 逐块处理:本地命中跳过(不下载),未命中经 core fetch 下载(同键 single-flight 合并)→ 推进 completed / failed → 状态置 RUNNING / DONE / ERROR → `GetPreheatStatus` 全程可查;`ReportBlocks` 流(北向)随每块完成触发,Controller 缺席时直接丢弃,不阻塞。指定块预热只下选中的块,不会顺手下邻居。

### 7.3 持续预取与阶段切换(验收 8/9)

节点上一条抓取管线,任务按 P0–P3 四级排队;节点上 n 个训练 Pod,每个 Pod 一个消费队列、队列上滑动的预取窗口;窗口中的块先查本地 CAS,已有的不管,没有的按任务来源定优先级入管线。

1. sidecar 推送首份 ConsumeOrder → `ordersource.Reader` 发现 ring → `svc` 组装 PersistentPrefetcher → `Start`(验收 8)。
2. `Start` 循环做 P2 邻域预取,范围是 cursor..cursor+lookahead(默认 16),每完成一块推进调度游标并上报 metrics;两条信号(钩子 `advance`、inotify OPEN 兜底)推进消费位点,去重与门控见 §5.8,差值记 `traincache_prefetch_lead_blocks`(§5.2)。
3. 新 ConsumeOrder 到达 → `OnStageSwitch`(验收 9):旧阶段 cursor 之后未消费的块降级 P3(在途不取消,腾出排队位置);新阶段开头 K 块(`prefetch_chunks`)以 P1 高优先级入队;K 块就绪后剩余块转 P2;函数返回 ETA(§5.2),上报 `traincache_stage_switch_eta_seconds`。

ETA 是预计 stall,不是实测。切换期间实际等了多久,由钩子 `read_stall` 帧进 `traincache_read_stall_seconds{phase="switch",cause}`,归因按 §5.4。两个指标不能互相替代。

### 7.4 降级模式(验收 10)

sidecar 退出(ring 写入停滞 30s 或文件消失)→ Agent 置 degraded(`traincache_agent_degraded=1`):不再依赖 OrderSource,改用 inotify 打开事件驱动 cursor 推进与热度/命中率统计;sidecar 恢复(新代际)后自动退出。降级期消费推进记 source="inotify",正常期钩子记 source="hook"(去重与门控见 §5.8)。已知限制:inotify 兜底的指纹反查只覆盖当前订单,订单外的打开事件认不出来。实际 stall 仍由 `read_stall` 帧进 `traincache_read_stall_seconds`,phase 按 §5.2 判定,判不出记 `unknown`。降级就是换一个信号源继续跑:功能打折,不中断。

### 7.5 demand 补块与 repair 坏块修复(验收 6)

读 miss 帧的接线与语义见 §5.4(`absent` → demand P0 入队,reason=`demand`;`corrupt` → repair,顺序见 §5.7)。补充三点:全量扫描和异步 demand/repair 同时碰到同一块时,core fetch 的 single-flight 合并成一次下载,不重复拉(repair、demand、prefetch 同处一个 single-flight 域,repair 与 demand 走前台准入、prefetch 走后台);补不及则本次读仍失败——Agent 只负责加速,不负责让读一定成功;修复成功后 `traincache_quarantined_blocks` 递减、`traincache_cache_misses_total{result="refetched"}` 计数,隔离数与队列长度由 `traincache_quarantined_blocks` / `traincache_repair_queue_depth` 暴露(GC 线,§5.8)。

### 7.6 GC 与磁盘淘汰

GC 和淘汰是两件事:

- **GC(生命周期回收)**:复用 core `Collector.Sweep`,按 §5.11 执行"读者确认删除"。快照对象只在不在 protected 时删;块删除还要求不在 liveBlocks、ref=0、pin=0。周期运行,热度不参与。GC 管"旧快照还能不能留"。
- **磁盘淘汰(容量管理)**:缓存磁盘有限,可能被快照引用的块远大于盘容量;活数据淘汰 = 在"逻辑上还需要"的块里,决定哪些本地副本值得留。筛选活数据:快照引用 + 无 pin 的本地块。淘汰动作只删本地副本(经 core `cas.Evict`,core D28),索引条目与引用关系不动,之后要用经 fetch 重新下载(不重复 Acquire,core D28 簿记契约);这与 core 回收旧快照/旧块的 Sweep(只删不再被引用的数据)是两回事。淘汰管"磁盘快满了先扔谁"。

淘汰循环细节:

- 周期:Agent 层淘汰循环默认每 30s 查磁盘利用率**和字节占用两个维度**,取先触发者。
- **字节上限**:env `TRAINCACHE_CACHE_CAPACITY_BYTES`(默认 0=关闭)。开了之后,Agent 累计 Evict 到的本地块字节数不能超这个值;触发时淘汰循环额外按剩余字节空间判断,比磁盘水位先到就先按字节阈值走。关掉时只有磁盘水位一个维度。
- **触发线**:磁盘利用率超 k(默认 80%)**或**字节占用超 `TRAINCACHE_CACHE_CAPACITY_BYTES`(开了的话)→ 按得分 `S = max(h, R)` 升序 Evict,降到 k-Δ 或字节上限的某百分比(默认 85%)。
- **危险线**:磁盘利用率超 M(默认 90%)**或**字节占用超上限的 95%(开了的话)→ R 清零,按 h 升序激进淘汰,同时打告警指标/日志,降到 k-2Δ 或字节上限的某百分比(默认 80%)。"激进"是牺牲纯投机块:预取了但还没被读过的块。
- **硬保护**:cursor + lookahead(16 块,§7.3)在任何情况下都不淘汰——删了马上还要读,等于白删还多一次回源。消费窗口不设独立保护机制:新 ConsumeOrder 到达时刷新订单内块的 t_touch,这些块自然拿到高 R(§5.5)。
- 热度只做淘汰的决策输入,簿记在 collector(§5.5),core 不感知热度。
- **策略档位(M4)**:"谁先被淘汰"抽象成 `Policy` 接口(`agent/evictor/policy.go`,只留 `Rank`;"新块能不能换入"的 `Admit` 准入方法已随 W-TinyLFU 撤档删除,见 6.3 D59),三档 heat/lru/lfu 运行时经 env `TRAINCACHE_EVICT_POLICY` 选择,默认 `heat` 与原行为逐字一致(回归基准);触发线、危险线、字节上限、硬保护与策略无关,三档共用(见 6.3 D59)。

**热度辅助预热**(7.0):冷启动后读磁盘热度(heatmap.json)选出历史高频块,查本地 CAS 排除已有,对缺的块发起 fetch(低优先级、限流,可取消);也可手动触发。缓存淘汰看近期(内存),预热看历史(磁盘)。

| 探针 | liveness = gRPC health check(判进程活着);readiness = GetNodeStatus 且 `rescan.phase != SAMPLING`(判能否提供基本服务) |
| 资源 | request 100m/1Gi,limit 2C/4Gi(示例值,待 bench 装置校准后定) |
| 安全 | readOnlyRootFilesystem=true;缓存目录写权限经 hostPath 与安全上下文授予 |

硬约束(7.0 原文):

- Agent 必须具备访问本地缓存目录的权限,能执行缓存扫描、数据块读取、预热写入和垃圾回收;
- Agent 的退出、重启和升级不得破坏本地缓存数据的持久性,进程退出不应导致缓存目录中的有效数据块被主动删除;
- 后台扫描、校验和预取任务不得无界占用节点资源(CPU、内存请求与限制即为此设);
- 缓存未完成全量扫描不应直接导致 Agent 无法提供服务。

训练 Pod 侧两处配置:hostPath 只读挂载 `/var/cache/traincache/blocks/`(验收 3);sidecar 容器挂载 `/run/traincache`(rw)。

## 附录 A:8.x 增量(Controller/Scheduler 所需 Agent 契约)

> 来源:`docs/7.1 design.md` §5.9、§12.1。仅追加增量,不改动上文既有约定;Agent 侧实现见 `docs/6.2 plan.md` 附录 M12。

为 Controller 加的接口,与前面的约定并行。**代际(generation)** 是任务版本号,Controller 用它防止旧请求覆盖新状态;**位图(ready_bitmap)** 是"哪些块已就绪"的压缩表示,第 i 位对应 `chunks` 第 i 项。

### A.1 proto 增量

```proto
// 8.x 增量:在现有 traincache.agent.v1.PreheatService 上最小增量扩展。
// 进度查询复用 GetPreheatStatus；不新增 GetPreheatProgress。

message SubmitPreheatRequest {
  // 字段 1..7 保持现状
  uint64 generation = 8;  // 任务代际；0 表示未提供
}

message PreheatStatus {
  // 字段 1..11 保持现状
  uint64 generation = 12;   // 任务代际
  uint64 seq = 13;          // 位图变更序号，单调递增
  bytes ready_bitmap = 14;  // 位 i 对应请求 chunks 第 i 项；1=已落盘且校验通过
  bool canceled = 15;       // 已收到 Cancel 且未被重新 Submit；Cancel 只标记不删除
  uint32 window_blocks = 16;  // 当前窗口块数 = len(chunks)；Controller 据此判定窗口未变化
}

message UpdatePreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;         // 必须 >= Agent 当前代际
  repeated ChunkRef chunks = 4;  // 新的完整块列表，同时定义位序
  PreheatPriority priority = 5;
}

message UpdatePreheatResponse {
  bool accepted = 1;
  string message = 2;
}

message CancelPreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;
}

message CancelPreheatResponse {
  bool accepted = 1;
}

service PreheatService {
  // 已有
  rpc SubmitPreheat(SubmitPreheatRequest) returns (SubmitPreheatResponse);
  rpc GetPreheatStatus(GetPreheatStatusRequest) returns (PreheatStatus);
  // 新增
  rpc UpdatePreheat(UpdatePreheatRequest) returns (UpdatePreheatResponse);
  rpc CancelPreheat(CancelPreheatRequest) returns (CancelPreheatResponse);
}
```

### A.2 Agent 侧语义

一条主线:Controller 每次改任务带更新的 `generation`,Agent 只接受不旧于当前代际的请求;进度用 `seq` 比新旧、用位图看具体哪块好了——网络乱序也不会把新状态盖回旧的。

- 任务表以 `task_id` 为键,记录 `generation`、有序 `chunks` ref 列表、位图、`seq`、状态;`SubmitPreheat` 与 `UpdatePreheat` 均幂等。
- 位序=请求 `chunks` 顺序:位图第 `i` 位对应当前任务 `chunks` 第 `i` 项,仅"`cas.Put` 落盘且校验通过"后置 1;失败位保持 0;位图长度 `ceil(len(chunks)/8)`。
- `seq` 单调递增:任一位置位或位图重置都使 `seq` 增加;Controller 用 `(generation, seq)` 判断进度新鲜度。
- `UpdatePreheat`:**全量替换** `chunks`,同时重定义位序并重置旧位图;在途请求不取消(沿用 §5.2 四队列约定);`priority` 随请求更新。
- `CancelPreheat`:标记任务取消(`canceled=true`、任务仍留在任务表里,幂等),并**撤回该任务尚未完成的下载**(D62):任务受理时结一个下载作用域,窗口里的块逐个结上它,取消即取消该作用域,块在下一个 ctx 边界(准入排队、源站读、写盘)退出并按失败回调,`completed` 保留取消前已完成的块数、任务落 `ERROR`。作用域派生自预取管理器自身的 ctx,所以 Agent 关停仍然连带取消;它只在任务出表时释放(`drop`、TTL 过期、本次取消),DONE 不释放——DONE 后仍可能收到 `UpdatePreheat` 续窗。被撤的块之后若被真实需求读到,按正常读路径重新入队。
- `generation` 低于 Agent 当前代际返回 `FailedPrecondition`;同 generation 的 Cancel 后再 `SubmitPreheat` 视为新任务。
- `GetPreheatStatus` 返回 `generation`/`seq`/`ready_bitmap` 全量位图、`canceled` 与 `window_blocks`;由 Controller 主动拉取,Agent 不推送。
- `window_blocks` 等于当前任务 `chunks` 项数(`UpdatePreheat` 全量替换后同步更新),与 `total_blocks` 不是一回事:`total_blocks` 按去重后的唯一块计,`window_blocks` 按窗口位置计。位图长度只区分 `ceil(块数/8)`,同一字节区间内的窗口变化只能靠该字段发现。
- 现状说明:`ReportService.ReportBlocks` 现为 Unimplemented 占位,本增量不实现、不使用。
