# Checkpoint 异步 Sidecar 决策记录

条目编号与 10.1 的引用一一对应。每条记背景、备选、结论、理由、影响、验证。

## D1 本地落盘位置：工作卷默认用磁盘

背景：10.0 把训练程序的写入目标定为 Memory 介质的 emptyDir，大模型一份 checkpoint 从几十 GB 起。

备选：加大 Pod 内存限额；改为磁盘 emptyDir，有 NVMe 时训练直接写 NVMe；有 NVMe 写 NVMe，没有则写内存。

结论：改磁盘。卷名保留 `checkpoint-mem`，挂载点改为 `/checkpoints-work`；有 NVMe 时训练程序的目标是 NVMe 卷，工作卷只在上传完成前保留最近一份。

理由：内存的单价与容量不是为几十 GB 顺序写准备的。OOM 杀的是训练容器，现场只会看到训练进程莫名退出。

影响：可用空间从 Pod 内存限额变为节点磁盘，保存耗时上升。10.0 的内存卷语义作废。

验证：1 GiB 目录跑一次保存，观察 Pod 内存用量与耗时；磁盘占用与保留份数一致。

## D2 凭证以引用注入，准入不读 Secret

背景：10.0 说 webhook 把 Secret 注入容器。现有 webhook 的 RBAC 没有 Secret 权限，注释明确写它不碰 Secret。

备选：准入读出值写进 Pod spec；准入只写 `secretKeyRef` 与 `configMapKeyRef`。

结论：只写引用。

理由：读值要求控制面组件持有读全命名空间 Secret 的权限，一处被攻破就是全集群凭证泄露；写引用不增加权限，缺键时 Pod 停在 `CreateContainerConfigError`，与仓库「缺配置就失败、不静默兜底」的做法一致。

影响：准入阶段看不到值，配置错误要到 Pod 启动才暴露，启动日志要打印生效值。

验证：删掉 ConfigMap 的一个键，确认 Pod 停在 `CreateContainerConfigError`。

## D3 关闭进程互见

背景：10.0 要求 `shareProcessNamespace: true`，兜底扫描靠读训练进程的 `/proc/<pid>/fd` 判断文件是否仍被打开。

备选：打开进程互见，保留 fd 扫描；关闭，兜底判据改为目录稳定性。

结论：关闭。

理由：同 Pod 内容器同用户，训练容器能读 checkpointd 的 `/proc/<pid>/environ`，两把凭证直接暴露。10.0 把凭证隔离写成边界，这条边界比兜底扫描的精度重要。

影响：不写 `.done` 的训练程序只能靠字节数与修改时间判断，10.1 §6.2 给出替代判据。

验证：不创建 `.done` 且持续追加的目录不被提前上传；训练容器读不到 checkpointd 的环境变量。

## D4 本期不发指标

背景：10.0 要六个指标，进程在训练 Pod 内；现有 Prometheus 只抓常驻组件的固定端口。

备选：加 Pod 注解与抓取发现；不发指标只写日志；用 pushgateway 推送。

结论：只写日志。

理由：训练 Pod 与任务同生命周期，抓取会周期性漏点，短任务采不到；改抓取配置会动到现有全部 target；pushgateway 要新增组件并处理重启后的残留。9.2 的 D21 对网关做过同样取舍。

影响：没有流量与耗时曲线，实验靠日志汇总。10.0 的六个指标名保留为后续项。

验证：日志统计的 `bytes` 总和与后端对象大小对得上。

## D5 本期不发 Pod 事件，不访问 API server

背景：10.0 列了五个 Pod 事件，发事件必须访问 API server 并取得授权。

备选：给 checkpointd 一套只发事件的 Role；不发事件只写日志。

结论：不发事件。

理由：训练 Pod 用默认 ServiceAccount，给它加 events 权限等于同命名空间所有 Pod 都能发事件；事件只提供 describe 里的一行，日志已有相同字段。

影响：排障入口从 describe 移到日志，10.0 的事件表标为后续项。

验证：Pod 里没有 API server 的环境变量与 token 挂载。

## D6 插件自带 S3 客户端，不扩展 core/objectstore

背景：`core/objectstore` 封装了 minio-go 与签名，接口只有 Get、Put、Delete、List，表达不了分片与跨进程续传。

备选：给 `core/objectstore` 加 multipart 接口；插件直接依赖 minio-go。

结论：插件自带。

理由：`Store` 是读路径契约，agent 与 gateway 两条链路都在用，为写路径改它要同时回归两条读路径；插件是独立二进制，自带客户端不动共享契约。

影响：多一个 minio-go 依赖，凭证解析与错误分类有第二份，两边按同一套错误码取值。

验证：同一后端配置分别由 agent 与插件访问，签名、TLS、region 处理一致。

## D7 一期一 Pod 一 rank

背景：目录布局是 `rank-<rank>/`，一个 rank 一个 Pod；torchrun 默认一个 Pod 起多个进程。

备选：一期支持多 rank，目录加进程序号；只支持一 Pod 一 rank，留扩展位。

结论：只支持一 Pod 一 rank。

理由：rank 目录与 Pod 一一对应，world_size 份 manifest 的判断才成立。多 rank 要每个训练进程写各自子目录，训练框架不一定配合。

影响：torchrun 默认用法跑不了，写进限制。扩展方式为 rank 目录下再分一层进程序号，manifest 加 `local_rank`，属于 version 2。

验证：一 Pod 一 rank 跑通保存与恢复；一 Pod 两 rank 在准入日志里被标为不支持并拒绝注入。

## D8 每任务一份 ConfigMap

背景：10.0 用 annotation 指向同 namespace 的 ConfigMap。

备选：并入全局 `traincache-config`；每个训练任务一份。

结论：每任务一份，另加 label `traincache.io/checkpoint=enabled` 供准入选择。

理由：不同任务的后端、前缀、保留份数不同，并入全局会在多任务并行时互相覆盖；选择器只认 label，annotation 进不了 `objectSelector`。

影响：用户要维护两份对象，接入多一步。

验证：两个任务用不同前缀并行跑，互不影响。

## D9 模块与镜像命名

背景：笔记写 `traincache/traincache-checkpoint`，发布文档的写法是 `traincache-agentd`、`traincache-gateway`。

备选：`traincache/checkpoint`；`traincache/traincache-checkpointd`。

结论：后者。模块目录 `checkpoint/`，module path `traincache/checkpoint`，二进制 `checkpointd`。

理由：两个非控制面镜像都带 `traincache-` 前缀，另一种写法读起来像第二个仓库；仓库已有目录名与镜像名不同的先例。

影响：笔记改一处，发布脚本的组件名记为 `traincache-checkpointd`。

验证：`hack/build-images.sh` 能构建，`hack/verify-release-metadata.sh` 的组件表能通过。

## D10 插件协议用 NDJSON over UNIX socket

背景：笔记写「编码待定」，10.0 定为 NDJSON，实现要冻一份契约。

备选：gRPC，需要 protoc 与生成代码；NDJSON 分帧。

结论：NDJSON，协议版本 1，帧与方法见 10.1 §4.1。

理由：插件由第三方实现，gRPC 把工具链也一并要求；协议面只有三个方法与一个进度帧，标准库即可实现，调试能直接看文本。

影响：连接管理、僵死判定与半行处理要自己写；大字段不进协议，统一走文件路径。

验证：20 行 Python 假插件跑通握手与 `resolve`。

## D11 manifest 由插件写，checkpointd 不解析

背景：10.0 把 manifest 的生成、写入顺序与校验都交给插件。

备选：checkpointd 统一生成，插件只交文件清单；插件生成。

结论：插件生成，字段结构在 10.1 §5.1 冻结。

理由：不同后端的校验手段不同，S3 用 ETag，PVC 用文件哈希；统一生成等于把后端细节拉回进程内。结构冻结后，跨插件的恢复判断才有一致标准。

影响：插件实现者必须按结构写，版本号只增不改。

验证：两个插件产出的 manifest 互相读取都能通过校验。

## D12 保存与恢复加总时限

背景：10.0 的外层重试 5 次、间隔 30s，插件内部还有退避，两层相乘没有上限，最坏超过 25 分钟。

备选：保留原次数不加时限；加保存 15 分钟、恢复 10 分钟的总时限。

结论：加总时限。

理由：训练侧等待有上限，超时后应快速失败让 Job 重建 Pod；无上限的重试让故障表现为卡住，现场分不清是在重试还是死锁。

影响：极端慢链路会提前失败，时限是环境变量，可调。

验证：注入每次都超时的后端，确认时限到达后停止重试并写一条 ERROR。

## D13 `.done` 误判的补救

背景：20 秒兜底扫描用「两次扫描大小与修改时间不变」判断就绪，mmap 写或长间隔刷盘时会上传半份文件。

备选：两次稳定；连续 3 次稳定且文件总字节数与登记值一致；整目录算哈希比对。

结论：连续 3 次加字节数比对。

理由：连续 3 次把窗口拉到 40 秒以上，覆盖多数刷盘间隔；字节数能抓住「大小已定、内容仍在改」的情形。整目录哈希每次多读一遍全量数据。

影响：兜底路径的就绪延迟增加约 40 秒，主路径不受影响。

验证：每 25 秒追加一次的目录前两次不被判就绪；20 秒内写完的目录第三次扫描后入队。

## D14 恢复超时的可观测出口

背景：探针 `failureThreshold: 360`、周期 10 秒，进程不退出，一小时里 Pod 既不 Running 也不重启。

备选：超时后进程退出；停止密集重试，转成每 5 分钟一轮并写 ERROR。

结论：每 5 分钟一轮。

理由：进程退出会让 kubelet 反复重启 sidecar，把日志冲掉，也解决不了后端不可用；保留进程可以让现场进去看状态文件与网络。

影响：一小时内仍表现为 Pending，可观测点只有日志与探针；超过一小时 kubelet 重启容器，重启后重新进入恢复。

验证：断开后端，确认 10 分钟后日志间隔变为 5 分钟，探针持续失败，容器未重启。

## D15 工作卷改名与目录归属

背景：10.0 的卷名是 `checkpoint-mem`，训练程序创建 `<task_id>`；但恢复发生在训练容器启动之前，训练程序还没有机会建目录。

备选：保留卷名并让训练程序建目录；改名并把建目录的责任移给 checkpointd。

结论：卷名改 `checkpoint-work`，挂载点 `/checkpoints-work`；checkpointd 在启动序里创建 `<task_id>`；工作卷对 checkpointd 可写。

理由：启动顺序决定谁先到。恢复要往工作卷写文件，目录必须先存在；保存成功后 checkpointd 还要删除副本，只读挂载会让删除失败。

影响：10.0 的卷名作废；训练容器仍只多一个 `TRAINCACHE_CHECKPOINT_DIR`。

验证：e2e 在空 emptyDir 上先恢复再写新 step。

## D16 续传状态按文件拆，首行存上传头

背景：5.2 原定每个 step 一个 JSONL。S3 的分片上传需要 upload id 与对象键，只有 part/etag/bytes 无法跨进程续传；一个 step 又有多个文件。

备选：每个 step 一个文件并扩展字段；每个待传文件一个文件，首行放上传头。

结论：`state_path` 是目录，每个文件一个 `<sha256>.jsonl`，首行 `kind=upload` 带 upload_id/key/file，之后是分片记录。

理由：文件内容相同的对象可以共用状态；upload id 与键属于单个 multipart 上传。加可选字段不破坏已有的 part/etag/bytes 读取。

影响：S3 插件在保存成功后删除这些文件；local 插件不使用。

验证：MinIO 集成用例在取消一次上传后复用已确认分片。

## D17 NVMe 卷本期用 emptyDir

背景：10.0 写“节点 NVMe 的 emptyDir 或 local PV”。emptyDir 无法指定节点盘类型；local PV 需要静态供给与节点标签，仓库里没有。

备选：引入 local PV provisioner；本期用 emptyDir。

结论：本期 `checkpoint-nvme` 是 emptyDir，落在节点磁盘。

理由：缓存是加速项，不是正确性依赖。引入 PV 供给会扩大部署面并需要集群管理员动作，先保证保存与恢复正确。

影响：NVME_DIR 指向节点磁盘；缓存可跨容器重启但不可跨 Pod 重建。后续装置验证前不承诺 NVMe 收益。

验证：e2e 关闭缓存跑通；缓存命中在容器重启后仍生效的用例待补。

## D18 逐步日志的消息里带 step

背景：core 的采样器按 `(component,event,task_id,reason)` 去重 60 秒。逐步事件如果只改字段不改消息，第二个 step 的记录会被当成重复丢弃；探针两次切换也会被吞。

备选：改 core 的去重键；在 checkpointd 侧让消息携带变化维度。

结论：逐步事件的消息里带 step，探针切换的消息里带状态。

理由：去重键是全仓共享契约，为单个组件加字段会影响所有模块。消息本身是 event，把变化维度放进 event 不需要改 core。

影响：日志检索仍可用结构化字段；按消息文本匹配的脚本要跟着改。

验证：连续保存两个 step，日志里两条“上传完成 step N”都在；探针 restoring/ready/failed 三条都在。

## D19 一个镜像带两个插件，但不进 install.yaml

背景：插件是独立进程，需要落在共享卷上；发布物里已经有五个组件镜像。

备选：每个插件一个镜像；一个镜像里放 checkpointd 与两个内置插件。

结论：一个镜像 `traincache-checkpointd`，内含 `/opt/traincache/plugins/{s3,local}/<name>`；准入注入的 initContainer 把它复制到 emptyDir；该镜像随版本构建，但不写进 install.yaml 的五个 Deployment 引用。

理由：插件与 checkpointd 必须同版本，拆镜像会让配对关系散落在部署清单里。install.yaml 只覆盖常驻组件；checkpointd 是按 Pod 注入的。

影响：发布候选多记一个 digest；verify-release-assets 只要求 install.yaml 的五个 digest 出现在 candidate.json 中。

验证：build-images 能构建该镜像；e2e 从镜像路径复制插件后跑通保存与恢复。

## D20 checkpointd 登记进日志组件枚举

背景：checkpointd 是独立进程，日志 `component` 实际取值 `checkpointd`，但 8.1 §3.1 的枚举没有它。

备选：沿用 `dataloader` 或 `agentd`；不加枚举、采集侧按未知值处理；按只增不改加一行。

结论：按只增不改加一行，8.1 §3.1 的枚举补 `checkpointd`，并写 8.2 ADR-016；不新增采样规则、标签与指标。

理由：采集侧对未知 `component` 的处理是丢弃还是放行取决于实现，枚举缺项会让同一组件的日志在两侧口径不一致；复用别的名字又会把 checkpoint 的日志混进预热或 DataLoader 的查询里。

影响：8.4 的来源表与查询示例同步补 `checkpointd`。10.3 的 Q4 结案。

验证：`checkpoint/e2e` 的 sidecar 日志带 `component=checkpointd`，按该标签能查到。

## D21 sidecar 镜像没有默认值

背景：checkpointd 镜像随版本换 digest，没有一个长期有效的默认 tag；`traincache-checkpointd:dev` 从未发布到镜像仓库，准入写死它会让 Pod 卡在 `ImagePullBackOff`。

备选：写死一个 tag；准入时忽略镜像错误；镜像由 ConfigMap 键或 Pod 注解给出，两处都空就拒绝。

结论：镜像取自 ConfigMap 键 `checkpointImage` 或 Pod 注解 `traincache.io/checkpoint-image`，注解优先；两处都空时准入拒绝该 Pod。

理由：仓库里「缺配置就失败、不静默兜底」的做法同样适用于镜像。注入一个拉不到的镜像，Pod 会停在拉镜像阶段并给出与配置问题无关的错误信息；准入拒绝能直接把原因说清楚。

影响：每个启用 checkpoint 的任务要准备一份带 `checkpointImage` 的 ConfigMap，或在 Pod 注解里给镜像。install.yaml 仍不含 checkpointd（D19），镜像由发布产物单独提供。

验证：ConfigMap 与注解都缺镜像时，准入返回拒绝并指明缺哪个键；给注解时注入的镜像就是注解里的值。

## D22 准入读 ConfigMap 走直连 API

背景：准入要读任务的 ConfigMap。webhook 用的 manager 缓存 client 会为 ConfigMap 起 informer，而 webhook 的 RBAC 只给了 `get`。

备选：给 RBAC 加 `list`/`watch`；准入改用直连 API 的 reader；把配置搬进 Pod 注解。

结论：准入用直连 API 的 reader 读 ConfigMap 与 Job，RBAC 保持只有 `get`。

理由：缓存 client 的读要先等 informer 同步起来，只有 `get` 权限时 informer 永远同步不上，读操作会一直阻塞到准入超时，Pod 直接被拒；给全集群 ConfigMap 的 `list`/`watch` 换来的只是一次配置读取，权限放大没有必要。

影响：每次准入请求多一次 API 调用，配置读不到时准入失败并给出原因；webhook 的 RBAC 注释要写明它不读 Secret。

验证：集群里过一遍准入，注入的 sidecar 拿到 ConfigMap 的值。

## D23 工作卷的权限靠 fsGroup 与组可写目录

背景：checkpointd 保存成功后要删掉工作卷上的副本（D1：工作卷只保留最近一份）。checkpointd 以 65532 非 root 运行，训练程序的 uid 不受我们控制。

备选：checkpointd 用 root 跑；训练程序自己删副本；靠 fsGroup 与组可写目录。

结论：checkpointd 保持非 root。卷设 `fsGroup=65532`，`<task_id>` 目录由 checkpointd 按 0775 建出，训练程序用组可写方式建 step 目录（`umask 0002`）；两边任一不满足，删副本就会失败，checkpointd 记 WARN。

理由：让 checkpointd 用 root 能一次解决删除，但它同时持有后端凭证，权限放大换来的只是一个 unlink。组可写目录是共享卷上的常规做法，`fsGroup` 本来就在注入契约里，只差把目录模式写进契约。训练程序不配合时后果是工作卷涨满，不是静默丢数据：删除失败有 WARN。

影响：训练程序要按组可写方式建 step 目录；训练程序的 uid 若是 65532 本身则无此要求。删除失败会一直重试到副本删掉为止。

验证：`checkpoint/e2e` 的 `loop` 模式连续 100 步，跑完工作目录为空、NVMe 缓存只留 1 份。
