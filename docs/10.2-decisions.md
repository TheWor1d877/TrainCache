# Checkpoint 异步 Sidecar 决策记录

条目编号与 10.1 的引用一一对应。每条记背景、备选、结论、理由、影响、验证。

## D1 本地落盘位置：工作卷默认用磁盘

背景：10.0 把训练程序的写入目标定为 Memory 介质的 emptyDir，大模型一份 checkpoint 从几十 GB 起。

备选：加大 Pod 内存限额；改为磁盘 emptyDir，有 NVMe 时训练直接写 NVMe；有 NVMe 写 NVMe，没有则写内存。

结论：改磁盘。工作卷是磁盘 emptyDir，卷名与挂载点由 D15 定（`checkpoint-work` / `/checkpoints-work`）；有 NVMe 时训练程序的目标是 NVMe 卷，工作卷只在上传完成前保留最近一份。

理由：内存的单价与容量不是为几十 GB 顺序写准备的。OOM 杀的是训练容器，现场只会看到训练进程莫名退出。

影响：可用空间从 Pod 内存限额变为节点磁盘，保存耗时上升。10.0 的内存卷语义作废。

验证：1 GiB 目录跑一次保存，观察 Pod 内存用量与耗时；磁盘占用与保留份数一致。

## D2 凭证以引用注入，准入不读 Secret

背景：10.0 说 webhook 把 Secret 注入容器。现有 webhook 的 RBAC 没有 Secret 权限，注释明确写它不碰 Secret。

备选：准入读出值写进 Pod spec；准入只写 `secretKeyRef` 与 `configMapKeyRef`。

结论：只写引用。

理由：读值要求控制面组件持有读全命名空间 Secret 的权限，一处被攻破就是全集群凭证泄露；写引用不增加权限，缺键时 Pod 停在 `CreateContainerConfigError`，与仓库「缺配置就失败、不静默兜底」的做法一致。

影响：准入阶段看不到值，配置错误要到 Pod 启动才暴露，启动日志要打印生效值。

验证：删掉 ConfigMap 的一个键，确认 Pod 停在 `CreateContainerConfigError`。

## D3 关闭进程互见

背景：10.0 要求 `shareProcessNamespace: true`，兜底扫描靠读训练进程的 `/proc/<pid>/fd` 判断文件是否仍被打开。

备选：打开进程互见，保留 fd 扫描；关闭，兜底判据改为目录稳定性。

结论：关闭。

理由：同 Pod 内容器同用户，训练容器能读 checkpointd 的 `/proc/<pid>/environ`，两把凭证直接暴露。10.0 把凭证隔离写成边界，这条边界比兜底扫描的精度重要。

影响：不写 `.done` 的训练程序只能靠字节数与修改时间判断，10.1 §6.2 给出替代判据。

验证：不创建 `.done` 且持续追加的目录不被提前上传；训练容器读不到 checkpointd 的环境变量。

## D4 本期不发指标

背景：10.0 要六个指标，进程在训练 Pod 内；现有 Prometheus 只抓常驻组件的固定端口。

备选：加 Pod 注解与抓取发现；不发指标只写日志；用 pushgateway 推送。

结论：只写日志。

理由：训练 Pod 与任务同生命周期，抓取会周期性漏点，短任务采不到；改抓取配置会动到现有全部 target；pushgateway 要新增组件并处理重启后的残留。9.2 的 D21 对网关做过同样取舍。

影响：没有流量与耗时曲线，实验靠日志汇总。10.0 的六个指标名保留为后续项。

验证：日志统计的 `bytes` 总和与后端对象大小对得上。

## D5 本期不发 Pod 事件，不访问 API server

背景：10.0 列了五个 Pod 事件，发事件必须访问 API server 并取得授权。

备选：给 checkpointd 一套只发事件的 Role；不发事件只写日志。

结论：不发事件。

理由：训练 Pod 用默认 ServiceAccount，给它加 events 权限等于同命名空间所有 Pod 都能发事件；事件只提供 describe 里的一行，日志已有相同字段。

影响：排障入口从 describe 移到日志，10.0 的事件表标为后续项。

验证：Pod 里没有 API server 的环境变量与 token 挂载。

## D6 插件自带 S3 客户端，不扩展 core/objectstore

背景：`core/objectstore` 封装了 minio-go 与签名，接口只有 Get、Put、Delete、List，表达不了分片与跨进程续传。

备选：给 `core/objectstore` 加 multipart 接口；插件直接依赖 minio-go。

结论：插件自带。

理由：`Store` 是读路径契约，agent 与 gateway 两条链路都在用，为写路径改它要同时回归两条读路径；插件是独立二进制，自带客户端不动共享契约。

影响：多一个 minio-go 依赖，凭证解析与错误分类有第二份，两边按同一套错误码取值。

验证：同一后端配置分别由 agent 与插件访问，签名、TLS、region 处理一致。

## D7 一期一 Pod 一 rank

背景：目录布局是 `rank-<rank>/`，一个 rank 一个 Pod；torchrun 默认一个 Pod 起多个进程。

备选：一期支持多 rank，目录加进程序号；只支持一 Pod 一 rank，留扩展位。

结论：只支持一 Pod 一 rank。

理由：rank 目录与 Pod 一一对应，world_size 份 manifest 的判断才成立。多 rank 要每个训练进程写各自子目录，训练框架不一定配合。

影响：torchrun 默认用法跑不了，写进限制。扩展方式为 rank 目录下再分一层进程序号，manifest 加 `local_rank`，属于 version 2。

验证：一 Pod 一 rank 跑通保存与恢复；一 Pod 两 rank 在准入日志里被标为不支持并拒绝注入。

## D8 每任务一份 ConfigMap

背景：10.0 用 annotation 指向同 namespace 的 ConfigMap。

备选：并入全局 `traincache-config`；每个训练任务一份。

结论：每任务一份。启用与配置来源用同一个标记表达：Pod 的 label `traincache.io/checkpoint` 的值就是这份 ConfigMap 的名字（标记的合并过程见 D24）。

理由：不同任务的后端、前缀、保留份数不同，并入全局会在多任务并行时互相覆盖。选择器只认 label，annotation 进不了 `objectSelector`，所以这个标记必须是 label；既然它已经必须存在，把配置来源放进它的值就不再要求接入方对齐两处。

影响：用户要维护 ConfigMap 与引用它的 label，但启用只看一处。ConfigMap 名要符合 label 取值的字符限制（小写字母、数字与 `-`，≤63 字符），这本来就是 ConfigMap 名的规则，不额外收窄。

验证：两个任务用不同前缀并行跑，互不影响。

## D9 模块与镜像命名

背景：笔记写 `traincache/traincache-checkpoint`，发布文档的写法是 `traincache-agentd`、`traincache-gateway`。

备选：`traincache/checkpoint`；`traincache/traincache-checkpointd`。

结论：后者。模块目录 `checkpoint/`，module path `traincache/checkpoint`，二进制 `checkpointd`。

理由：两个非控制面镜像都带 `traincache-` 前缀，另一种写法读起来像第二个仓库；仓库已有目录名与镜像名不同的先例。

影响：笔记改一处，发布脚本的组件名记为 `traincache-checkpointd`。

验证：`hack/build-images.sh` 能构建，`hack/verify-release-metadata.sh` 的组件表能通过。

## D10 插件协议用 NDJSON over UNIX socket

背景：笔记写「编码待定」，10.0 定为 NDJSON，实现要冻一份契约。

备选：gRPC，需要 protoc 与生成代码；NDJSON 分帧。

结论：NDJSON，协议版本 1，帧与方法见 10.1 §4.1。

理由：插件由第三方实现，gRPC 把工具链也一并要求；协议面只有三个方法与一个进度帧，标准库即可实现，调试能直接看文本。

影响：连接管理、僵死判定与半行处理要自己写；大字段不进协议，统一走文件路径。

验证：20 行 Python 假插件跑通握手与 `resolve`。

## D11 manifest 由插件写，checkpointd 不解析

背景：10.0 把 manifest 的生成、写入顺序与校验都交给插件。

备选：checkpointd 统一生成，插件只交文件清单；插件生成。

结论：插件生成，字段结构在 10.1 §5.1 冻结。

理由：不同后端的校验手段不同，S3 用 ETag，PVC 用文件哈希；统一生成等于把后端细节拉回进程内。结构冻结后，跨插件的恢复判断才有一致标准。

影响：插件实现者必须按结构写，版本号只增不改。

验证：两个插件产出的 manifest 互相读取都能通过校验。

## D12 保存与恢复加总时限

背景：10.0 的外层重试 5 次、间隔 30s，插件内部还有退避，两层相乘没有上限，最坏超过 25 分钟。

备选：保留原次数不加时限；加保存 15 分钟、恢复 10 分钟的总时限。

结论：加总时限。

理由：训练侧等待有上限，超时后应快速失败让 Job 重建 Pod；无上限的重试让故障表现为卡住，现场分不清是在重试还是死锁。

影响：极端慢链路会提前失败，时限是环境变量，可调。

验证：注入每次都超时的后端，确认时限到达后停止重试并写一条 ERROR。

## D13 `.done` 误判的补救

背景：20 秒兜底扫描用「两次扫描大小与修改时间不变」判断就绪，mmap 写或长间隔刷盘时会上传半份文件。

备选：两次稳定；连续 3 次稳定且文件总字节数与登记值一致；整目录算哈希比对。

结论：连续 3 次加字节数比对。

理由：连续 3 次把窗口拉到 40 秒以上，覆盖多数刷盘间隔；字节数能抓住「大小已定、内容仍在改」的情形。整目录哈希每次多读一遍全量数据。

影响：兜底路径的就绪延迟增加约 40 秒，主路径不受影响。

验证：每 25 秒追加一次的目录前两次不被判就绪；20 秒内写完的目录第三次扫描后入队。

## D14 恢复超时的可观测出口

背景：探针 `failureThreshold: 360`、周期 10 秒。恢复失败后进程不退出，一小时内 Pod 既不 Running 也不重启，Job 也不会失败，配额一直被占。

备选：超时后立即进程退出；停止密集重试，转成每 5 分钟一轮并写 ERROR；每 5 分钟一轮，到第二个期限（放弃期限）再退出。

结论：先转慢速重试，`RESTORE_DEADLINE`（默认 10 分钟）到达后每 5 分钟一轮、每轮写一条 ERROR；到 `RESTORE_GIVE_UP_AFTER`（默认 60 分钟）仍然失败则进程以退出码 3 结束，与配置非法的 2 分开。该值必须大于 `RESTORE_DEADLINE`，不满足判配置非法，与「缺配置就失败、不静默兜底」一致。

理由：立即退出会让 kubelet 反复重启 sidecar，把日志冲掉，也解决不了后端不可用；慢速重试段保留现场，让人进去看状态与网络。只重试不退出则恢复永远不成功的那个 Pod 停在 `Init`，训练容器、sidecar 与已占用的 GPU 都不释放，外面看不出它已经死了。退出交给 Job 记账：`restartPolicy: OnFailure` 下 init 容器在同一个 Pod 里重启，每次重启算一次失败、计入 `backoffLimit`，用完后 Job 以 `BackoffLimitExceeded` 判 Failed，配额随 Pod 释放。checkpointd 不访问 API server（D5），退出是它唯一能表达的失败信号。

影响：一小时内的可观测点仍是日志与探针；超过 `RESTORE_GIVE_UP_AFTER` 表现为 init 容器在同一个 Pod 里反复重启，重启次数用完 `backoffLimit` 后 Job 判 Failed。`status.failed` 记的是失败的 Pod 数，这种形态下是 1，不是重启次数。接入方把 `backoffLimit` 设成 0 时一次放弃即判失败。排障入口是退出前最后一条 ERROR 与 `state` 日志。

验证：断开后端，`RESTORE_GIVE_UP_AFTER` 设 30 秒，确认慢速重试按 5 分钟不触发、进程在期限内以非零退出，Job 的容器重启次数随之增加、用完 `backoffLimit` 后以 `BackoffLimitExceeded` 判 Failed；`RESTORE_GIVE_UP_AFTER` 小于 `RESTORE_DEADLINE` 时配置校验报 `invalid_spec`。kind 1.37 上的实测见 `docs/10.3-test.md` 的恢复放弃行。

## D15 工作卷改名与目录归属

背景：10.0 的卷名是 `checkpoint-mem`，训练程序创建 `<task_id>`；但恢复发生在训练容器启动之前，训练程序还没有机会建目录。

备选：保留卷名并让训练程序建目录；改名并把建目录的责任移给 checkpointd。

结论：卷名改 `checkpoint-work`，挂载点 `/checkpoints-work`；checkpointd 在启动序里创建 `<task_id>`；工作卷对 checkpointd 可写。

理由：启动顺序决定谁先到。恢复要往工作卷写文件，目录必须先存在；保存成功后 checkpointd 还要删除副本，只读挂载会让删除失败。

影响：10.0 的卷名作废；训练容器仍只多一个 `TRAINCACHE_CHECKPOINT_DIR`。

验证：e2e 在空 emptyDir 上先恢复再写新 step。

## D16 续传状态按文件拆，首行存上传头

背景：5.2 原定每个 step 一个 JSONL。S3 的分片上传需要 upload id 与对象键，只有 part/etag/bytes 无法跨进程续传；一个 step 又有多个文件。

备选：每个 step 一个文件并扩展字段；每个待传文件一个文件，首行放上传头。

结论：`state_path` 是目录，每个文件一个 `<sha256>.jsonl`，首行 `kind=upload` 带 upload_id/key/file，之后是分片记录。

理由：文件内容相同的对象可以共用状态；upload id 与键属于单个 multipart 上传。加可选字段不破坏已有的 part/etag/bytes 读取。

影响：S3 插件在保存成功后删除这些文件；local 插件不使用。

验证：MinIO 集成用例在取消一次上传后复用已确认分片。

## D17 NVMe 卷本期用 emptyDir

背景：10.0 写“节点 NVMe 的 emptyDir 或 local PV”。emptyDir 无法指定节点盘类型；local PV 需要静态供给与节点标签，仓库里没有。

备选：引入 local PV provisioner；本期用 emptyDir。

结论：本期 `checkpoint-nvme` 是 emptyDir，落在节点磁盘。

理由：缓存是加速项，不是正确性依赖。引入 PV 供给会扩大部署面并需要集群管理员动作，先保证保存与恢复正确。

影响：NVME_DIR 指向节点磁盘；缓存可跨容器重启但不可跨 Pod 重建。后续装置验证前不承诺 NVMe 收益。

验证：e2e 关闭缓存跑通；缓存命中在容器重启后仍生效的用例待补。

## D18 逐步日志的消息里带 step

背景：core 的采样器按 `(component,event,task_id,reason)` 去重 60 秒。逐步事件如果只改字段不改消息，第二个 step 的记录会被当成重复丢弃；探针两次切换也会被吞。

备选：改 core 的去重键；在 checkpointd 侧让消息携带变化维度。

结论：逐步事件的消息里带 step，探针切换的消息里带状态。

理由：去重键是全仓共享契约，为单个组件加字段会影响所有模块。消息本身是 event，把变化维度放进 event 不需要改 core。

影响：日志检索仍可用结构化字段；按消息文本匹配的脚本要跟着改。

验证：连续保存两个 step，日志里两条“上传完成 step N”都在；探针 restoring/ready/failed 三条都在。

## D19 一个镜像带两个插件，digest 写进 install.yaml 的 ConfigMap

背景：插件是独立进程，需要落在共享卷上；发布物里已经有五个组件镜像。

备选：每个插件一个镜像；一个镜像里放 checkpointd 与两个内置插件；checkpointd 完全不进清单。

结论：一个镜像 `traincache-checkpointd`，内含 `/opt/traincache/plugins/{s3,local}/<name>`；准入注入的 initContainer 把它复制到 emptyDir；该镜像随版本构建，它的 digest 写进 install.yaml 的 `traincache-checkpoint-image` ConfigMap（键 `checkpointImage`），webhook 读它作为注入镜像的发布默认值。

理由：插件与 checkpointd 必须同版本，拆镜像会让配对关系散落在部署清单里。checkpointd 没有常驻 Deployment，但它的取值要跟发布走：digest 落在清单里，安装方不必自己抄镜像名，发布流水线也能对它做与另外五个镜像一样的校验。

影响：install.yaml 里出现第六个 digest 引用；发布候选仍记六个 digest，verify-release-assets 要求六个全部对得上且可解析。

验证：build-images 能构建该镜像；e2e 从镜像路径复制插件后跑通保存与恢复；渲染 install.yaml 后 ConfigMap 里的取值是本次发布的 digest。

## D20 checkpointd 登记进日志组件枚举

背景：checkpointd 是独立进程，日志 `component` 实际取值 `checkpointd`，但 8.1 §3.1 的枚举没有它。

备选：沿用 `dataloader` 或 `agentd`；不加枚举、采集侧按未知值处理；按只增不改加一行。

结论：按只增不改加一行，8.1 §3.1 的枚举补 `checkpointd`，并写 8.2 ADR-016；不新增采样规则、标签与指标。

理由：采集侧对未知 `component` 的处理是丢弃还是放行取决于实现，枚举缺项会让同一组件的日志在两侧口径不一致；复用别的名字又会把 checkpoint 的日志混进预热或 DataLoader 的查询里。

影响：8.4 的来源表与查询示例同步补 `checkpointd`。10.3 的 Q4 结案。

验证：`checkpoint/e2e` 的 sidecar 日志带 `component=checkpointd`，按该标签能查到。

## D21 sidecar 镜像的取值顺序

背景：checkpointd 镜像随版本换 digest，没有一个长期有效的默认 tag；仓库内的开发清单写 `traincache-checkpointd:dev`，它只在把镜像导入节点的开发环境里成立，发布清单里必须是本次发布的 digest。

备选：写死一个 tag；准入时忽略镜像错误；镜像只由 ConfigMap 键或 Pod 注解给出，两处都空就拒绝。

结论：镜像按 Pod 注解 `traincache.io/checkpoint-image`、ConfigMap 键 `checkpointImage`、本次发布的默认镜像（webhook Deployment 的 `CHECKPOINT_IMAGE`，来自 install.yaml 的 `traincache-checkpoint-image` ConfigMap）三处依次取值，前面的覆盖后面的；三处都空时准入拒绝该 Pod。

理由：仓库里「缺配置就失败、不静默兜底」的做法同样适用于镜像。注入一个拉不到的镜像，Pod 会停在拉镜像阶段并给出与配置问题无关的错误信息；准入拒绝能直接把原因说清楚。发布默认放在最后，让它只兜底而不夺走接入方显式指定的镜像。

影响：接入方仍可用 ConfigMap 键或 Pod 注解指定自己的镜像；用 install.yaml 装机的集群不写这两个来源也能用，注入的 sidecar 就是本次发布的 digest；手工装 webhook 且没给 `CHECKPOINT_IMAGE` 时，缺镜像仍会被准入拒绝。

验证：ConfigMap 与注解都缺镜像、webhook 也没带发布默认时，准入返回拒绝并指明缺哪个键；给注解时注入的镜像就是注解里的值；只给发布默认时注入的镜像是该默认。

## D22 准入读 ConfigMap 走直连 API

背景：准入要读任务的 ConfigMap。webhook 用的 manager 缓存 client 会为 ConfigMap 起 informer，而 webhook 的 RBAC 只给了 `get`。

备选：给 RBAC 加 `list`/`watch`；准入改用直连 API 的 reader；把配置搬进 Pod 注解。

结论：准入用直连 API 的 reader 读 ConfigMap 与 Job，RBAC 保持只有 `get`。

理由：缓存 client 的读要先等 informer 同步起来，只有 `get` 权限时 informer 永远同步不上，读操作会一直阻塞到准入超时，Pod 直接被拒；给全集群 ConfigMap 的 `list`/`watch` 换来的只是一次配置读取，权限放大没有必要。

影响：每次准入请求多一次 API 调用，配置读不到时准入失败并给出原因；webhook 的 RBAC 注释要写明它不读 Secret。

验证：集群里过一遍准入，注入的 sidecar 拿到 ConfigMap 的值。

## D23 工作卷的权限靠 fsGroup 与组可写目录

背景：checkpointd 保存成功后要删掉工作卷上的副本（D1：工作卷只保留最近一份）。checkpointd 以 65532 非 root 运行，训练程序的 uid 不受我们控制。

备选：checkpointd 用 root 跑；训练程序自己删副本；靠 fsGroup 与组可写目录。

结论：checkpointd 保持非 root（镜像写死 `USER 65532:65532`）。卷设 `fsGroup=65532`，`<task_id>` 目录由 checkpointd 按 0775 建出，训练程序用组可写方式建 step 目录（`umask 0002`）；两边任一不满足，删副本就会失败，checkpointd 记 WARN。

理由：让 checkpointd 用 root 能一次解决删除，但它同时持有后端凭证，权限放大换来的只是一个 unlink。组可写目录是共享卷上的常规做法，`fsGroup` 本来就在注入契约里，只差把目录模式写进契约。训练程序不配合时后果是工作卷涨满，不是静默丢数据：删除失败有 WARN。

影响：训练程序要按组可写方式建 step 目录；训练程序的 uid 若是 65532 本身则无此要求。删除失败会一直重试到副本删掉为止。完整的五条前提写在 10.1 §4.3.1：卷上 fsGroup 生效（`fsGroupPolicy` 不是 None）、训练程序落在同一组、step 目录组可写、`<task_id>` 目录由 checkpointd 建、工作卷是训练容器与 checkpointd 共用的同一个卷。

验证：`checkpoint/e2e` 的 `loop` 模式连续 100 步，跑完工作目录为空、NVMe 缓存只留 1 份。

## D24 启用标记合为一个 label

背景：接入要同时给 label `traincache.io/checkpoint=enabled` 和 annotation `traincache.io/checkpoint=<ConfigMap 名>`。前者是准入的选择器，后者是配置来源。忘加 label 时 `objectSelector` 不匹配，API server 根本不调用这条 webhook，Pod 原样放行、不报错，checkpointd 不在场，用户要到第一次保存才发现。

备选：接入方接受两个标记并列并自查；改用 `namespaceSelector` 让整个 namespace 进 webhook，由 webhook 判 annotation；把两个标记合成一个 label，值就是 ConfigMap 名。

结论：合成一个 label。`traincache.io/checkpoint` 的值是同 namespace 的 ConfigMap 名；`objectSelector` 用 `matchExpressions` 按 `Exists` 匹配这个键，不再限定取值。annotation `traincache.io/checkpoint` 删除，不再参与启用与配置选择。值不是合法 ConfigMap 名、为空，或按它读不到 ConfigMap 时，准入拒绝该 Pod 并写明缺哪个。`traincache.io/checkpoint-image`、`task-id`、`world-size`、`rank`、`checkpoint-step` 这些 annotation 的作用不变。

理由：`objectSelector` 只看 label，annotation 进不了选择器，这是 Kubernetes 的机制，改不了。两个标记并列把「配了配置没配选择器」变成一种无声失败，而选择器和配置来源本来就是同一件事：要不要启用、用哪份配置。合到一个 label 上之后，要启用就必须写对这一个标记，写错的下一步是准入拒绝，不是放行。`namespaceSelector` 会把 webhook 推到全部 Pod 的准入链上，`failurePolicy: Fail` 下 webhook 不通即整个集群建不出 Pod，为一个可选功能承担的可用性风险过大。

影响：这是接入契约的破坏性改动。已按 0.5.1 契约接入的 Pod 要把 annotation 的值挪到 label 上，label 值不再是 `enabled`；只写 label=enabled 的老 Pod 会被当作「找名为 enabled 的 ConfigMap」处理，读不到即拒绝，不会静默放行。10.0 原文写的是 annotation 带配置名，落地按本节。10.1 §4.2 的准入契约同步。

验证：只给 label 且值是真 ConfigMap 名时注入成功；label 值写成不存在的名字时准入拒绝并在响应里给出该名字；没有 label 时 Pod 不改且 webhook 不被调用；只有旧 annotation 没有 label 时 Pod 不改（这是接入方必须迁移的证据）。

## D25 step 完整性按 rank 集合判定

背景：`world_size` 来自 annotation、ConfigMap 键或 Job 的 `parallelism`，都是提交时写死的静态值。判一个 step 完整只看「rank 0 到 world_size-1 的 manifest 都在」。弹性训练把副本数从 8 改成 12 之后，前 8 份齐了照样判完整，恢复出来的进程缺 4 个 rank 的数据，直到加载才炸。

备选：只支持固定副本数，不做检测（当前 10.1 的范围声明）；数份数够即判完整；按目录里实际出现的 rank 集合判完整。

结论：按集合判。完整性要求实际存在的 rank 集合恰好等于 `{0 … world_size-1}`：缺任一份判不完整，出现 `rank ≥ world_size` 的多余份同样判不完整并记 WARN，`reason=rank_beyond_world_size`，附带看到的最大 rank。本期仍不支持弹性训练改变副本数（D7 的一期一 Pod 一 rank 与固定副本数范围不变），本条做的是「副本数确实变了时不把它当成功」。

理由：数份数只能证明凑够了个数，证明不了编号连续。rank 是按编号命名目录的，集合比对在同一次枚举里就能做，不额外访问后端。判不完整的代价是这个 step 不恢复（`requireCheckpoint` 为 false 时跳过、为 true 时报失败），比恢复出一个缺 rank 的现场便宜得多。多余份出现说明声明值与实际拓扑不符，这条 WARN 是唯一能把它说出来的地方。

影响：完整性判定变严。历史上传里如果存在「编号不连续但份数够」的 step，改后不再判完整；这种情况本来也无法恢复出可用的世界。弹性训练仍不在支持范围，本节不改变该边界。

验证：单测构造 rank 集合 `{0,1,2}`、`{0,1,3}`、`{0,1,2,3}` 三种目录，`world_size=3` 时分别判完整、不完整（缺 2）、不完整（多出 3）；`rank=3` 存在时有 `reason=rank_beyond_world_size` 的 WARN。

## D26 跨链路对账键用 Job 名，checkpointd 日志带 `job`

背景：预热链路的任务标识是 `<namespace>/<WarmupTask 名>/p<序号>`，checkpoint 的 `task_id` 是 annotation 覆盖值、owner Job 名或 `<namespace>-<uid 前 8 位>`。两套字符串格式互斥（预热 ID 含 `/`，checkpoint 的 `task_id` 校验禁 `/`），同一场训练在两条链路的日志里对不到一起。

备选：统一两套 ID 的生成，由一方产出并传递；不动 ID，另给一个两边都能填的关联键；接受无法对账。

结论：不统一 ID，对账键固定为 owner Job 名。checkpointd 的全部日志带 `job` 字段，取值依次是 Pod 的 `batch.kubernetes.io/job-name` label、`job-name` label，两者都没有时为空串。`task_id` 的语义与取值顺序不变（D 前的现状）。预热链路侧，WarmupTask 通过 ownerReference 或同名 label 关联到训练 Job（`controller/internal/controller/warmup` 已有这条判定），按 Job 名查询即可。本期不发指标（D4），对账只发生在日志侧。

理由：两套 ID 各自服务的对象不同：`task_id` 是后端键空间的一部分，改动会让已上传的 checkpoint 找不到；预热的 ID 是 CR 名加序号，改动要动 CRD 语义。把它们拉平的代价落在数据契约上，而真正要回答的问题是「这条日志属于哪场训练」，Job 名本来就是训练的作业名，两边都拿得到，不要求接入方额外配置。annotation 覆盖 `task_id` 时它会与 Job 名脱钩，这正是需要独立 `job` 字段的场景。

影响：checkpointd 日志多一个字段，采样键 `(component,event,task_id,reason)` 不含 `job`，去重行为不变（D18）。空串 `job` 表示该 Pod 不属于 Job（裸 Pod 或自定义 CR 直接建 Pod），这类场景仍需按 `task_id` 查询。10.3 的日志用例补这条断言。

验证：属于某个 Job 的 Pod，其 sidecar 日志每条都带 `job=<job-name>`；给了 `traincache.io/task-id` 覆盖时 `job` 仍是 Job 名；裸 Pod 时 `job` 为空且日志不丢。

## D27 第三方插件本期不交付

背景：插件是独立子进程，`PLUGIN_PATH` 可指向任意二进制，插件与 checkpointd 同容器同权限，能读它的全部环境变量（含两把凭证）并读写挂载卷。审核流程、插件镜像仓库与版本约束当时都没定。

备选：本期开放第三方插件，配套审核与版本约束；只交付内置插件，`PLUGIN_PATH` 保留为开发态；删掉 `PLUGIN_PATH`，插件路径不可覆盖。

结论：本期只交付内置的 `s3` 与 `local` 两个插件，不提供第三方插件的支持承诺，不写审核流程、仓库与版本约束。`PLUGIN_PATH` 保留，用途限定为开发与 e2e 指向自建二进制，写进 10.1 的信任边界；生产接入第三方插件不在本期范围。

理由：接一个第三方插件等于允许它在训练 Pod 内执行任意代码并读到凭证，这条边界需要的是流程约束（谁审核、镜像放哪、版本怎么锁），不是代码约束，本期没有流程结论可写。代码侧的白名单同样解决不了问题：能进 Pod 的镜像本来就能带任意二进制，白名单只把「用 Traincache 插件名」这一步变成必需。内置两个插件覆盖 S3 兼容后端与共享文件系统两类，本期够用。

影响：`docs/10.1-design.md` §1.2 与 §1.4 引用本条。第三方插件的审核、仓库与版本约束等有人提需求再开条目，本期不留占位。

验证：发布镜像里 `/opt/traincache/plugins/` 只有 `s3` 与 `local`；`PLUGIN_PATH` 指向仓库外二进制时握手仍按协议版本判插件可用性（4.1），生产清单不出现该变量。
