# Checkpoint 异步 Sidecar 决策记录

条目编号与 10.1 的引用一一对应。每条只记已裁决的结论、原因与对接入方的影响。

## D1 本地落盘位置：工作卷默认用磁盘

结论：工作卷是磁盘 emptyDir，卷名与挂载点为 `checkpoint-work` / `/checkpoints-work`；有 NVMe 时训练程序的目标是 NVMe 卷，工作卷只在上传完成前保留最近一份。10.0 的内存卷语义作废。

原因：一份 checkpoint 从几十 GB 起，内存的单价与容量不是为几十 GB 顺序写准备的；OOM 杀的是训练容器，现场只看到训练进程莫名退出。可用空间从 Pod 内存限额变为节点磁盘，保存耗时上升。

## D2 凭证以引用注入，准入不读 Secret

结论：准入只写 `secretKeyRef` 与 `configMapKeyRef`，不读出值。

原因：读值要求控制面组件持有读全命名空间 Secret 的权限，一处被攻破就是全集群凭证泄露；写引用不增加权限，缺键时 Pod 停在 `CreateContainerConfigError`，与仓库「缺配置就失败、不静默兜底」一致。准入阶段看不到值，配置错误要到 Pod 启动才暴露，启动日志要打印生效值。

## D3 关闭进程互见

结论：不设 `shareProcessNamespace: true`，`shareProcessNamespace` 保持关闭。

原因：同 Pod 内容器同用户，训练容器能读 checkpointd 的 `/proc/<pid>/environ`，两把凭证直接暴露。凭证隔离这条边界比兜底扫描的精度重要。不写 `.done` 的训练程序只能靠字节数与修改时间判断，10.1 §6.2 给出替代判据。

## D4 本期不发指标

结论：checkpointd 只写日志，不发指标。10.0 的六个指标名保留为后续项。

原因：训练 Pod 与任务同生命周期，抓取会周期性漏点，短任务采不到；改抓取配置会动到现有全部 target；pushgateway 要新增组件并处理重启后的残留。9.2 的 D21 对网关做过同样取舍。没有流量与耗时曲线，实验靠日志汇总。

## D5 本期不发 Pod 事件，不访问 API server

结论：不发 Pod 事件，只写日志。10.0 的事件表标为后续项。

原因：发事件必须访问 API server 并取得授权，训练 Pod 用默认 ServiceAccount，给它加 events 权限等于同命名空间所有 Pod 都能发事件；事件只提供 describe 里的一行，日志已有相同字段。排障入口从 describe 移到日志。

## D6 插件自带 S3 客户端，不扩展 core/objectstore

结论：插件自带 minio-go 依赖，不改 `core/objectstore`。

原因：`Store` 是读路径契约，agent 与 gateway 两条链路都在用，为写路径改它要同时回归两条读路径；插件是独立二进制，自带客户端不动共享契约。代价是多一个依赖，凭证解析与错误分类有第二份，两边按同一套错误码取值。

## D7 一期一 Pod 一 rank

结论：只支持一 Pod 一 rank。

原因：rank 目录与 Pod 一一对应，world_size 份 manifest 的判断才成立；多 rank 要每个训练进程写各自子目录，训练框架不一定配合。torchrun 默认用法跑不了，写进限制。扩展方式为 rank 目录下再分一层进程序号、manifest 加 `local_rank`，属于 version 2。

## D8 每任务一份 ConfigMap

结论：每个训练任务一份 ConfigMap，Pod 的 label `traincache.io/checkpoint` 的值就是这份 ConfigMap 的名字（标记的合并过程见 D24）。

原因：不同任务的后端、前缀、保留份数不同，并入全局会在多任务并行时互相覆盖。选择器只认 label，annotation 进不了 `objectSelector`，所以这个标记必须是 label；既然它已经必须存在，把配置来源放进它的值就不再要求接入方对齐两处。用户要维护 ConfigMap 与引用它的 label，但启用只看一处。ConfigMap 名要符合 label 取值的字符限制（小写字母、数字与 `-`，≤63 字符），这本来就是 ConfigMap 名的规则，不额外收窄。

## D9 模块与镜像命名

结论：模块目录 `checkpoint/`，module path `traincache/checkpoint`，二进制 `checkpointd`，镜像 `traincache/traincache-checkpointd`。

原因：两个非控制面镜像都带 `traincache-` 前缀，另一种写法读起来像第二个仓库；仓库已有目录名与镜像名不同的先例。发布脚本的组件名记为 `traincache-checkpointd`。

## D10 插件协议用 NDJSON over UNIX socket

结论：NDJSON，协议版本 1，帧与方法见 10.1 §4.1。

原因：插件由第三方实现，gRPC 把工具链也一并要求；协议面只有三个方法与一个进度帧，标准库即可实现，调试能直接看文本。连接管理、僵死判定与半行处理要自己写；大字段不进协议，统一走文件路径。

## D11 manifest 由插件写，checkpointd 不解析

结论：插件生成 manifest，字段结构在 10.1 §5.1 冻结。

原因：不同后端的校验手段不同，S3 用 ETag，PVC 用文件哈希；统一生成等于把后端细节拉回进程内。结构冻结后跨插件的恢复判断才有一致标准。插件实现者必须按结构写，版本号只增不改。

## D12 保存与恢复加总时限

结论：保存与恢复都加总时限。

原因：训练侧等待有上限，超时后应快速失败让 Job 重建 Pod；无上限的重试让故障表现为卡住，现场分不清是在重试还是死锁。极端慢链路会提前失败，时限是环境变量，可调。

## D13 `.done` 误判的补救

结论：就绪判据用连续 3 次稳定且文件总字节数与登记值一致。

原因：连续 3 次把窗口拉到 40 秒以上，覆盖多数刷盘间隔；字节数能抓住「大小已定、内容仍在改」的情形。整目录哈希每次多读一遍全量数据。兜底路径的就绪延迟增加约 40 秒，主路径不受影响。

## D14 恢复超时的可观测出口

结论：恢复失败后先转慢速重试，`RESTORE_DEADLINE`（默认 10 分钟）到达后每 5 分钟一轮、每轮写一条 ERROR；到 `RESTORE_GIVE_UP_AFTER`（默认 60 分钟）仍然失败则进程以退出码 3 结束，与配置非法的 2 分开。该值必须大于 `RESTORE_DEADLINE`，不满足判配置非法（退出码 2，`err_class=invalid_spec`），与「缺配置就失败、不静默兜底」一致。

原因：立即退出会让 kubelet 反复重启 sidecar，把日志冲掉，也解决不了后端不可用；慢速重试段保留现场，让人进去看状态与网络。只重试不退出则恢复永远不成功的那个 Pod 停在 `Init`，训练容器、sidecar 与已占用的 GPU 都不释放。退出交给 Job 记账：`restartPolicy: OnFailure` 下 init 容器在同一个 Pod 里重启，每次重启算一次失败、计入 `backoffLimit`，用完后 Job 以 `BackoffLimitExceeded` 判 Failed，配额随 Pod 释放。checkpointd 不访问 API server（D5），退出是它唯一能表达的失败信号。

影响：一小时内的可观测点仍是日志与探针；超过 `RESTORE_GIVE_UP_AFTER` 表现为 init 容器在同一个 Pod 里反复重启，重启次数用完 `backoffLimit` 后 Job 判 Failed。`status.failed` 记的是失败的 Pod 数，这种形态下是 1，不是重启次数。接入方把 `backoffLimit` 设成 0 时一次放弃即判失败。排障入口是退出前最后一条 ERROR 与 `state` 日志。

## D15 工作卷改名与目录归属

结论：卷名 `checkpoint-work`，挂载点 `/checkpoints-work`；checkpointd 在启动序里创建 `<task_id>`；工作卷对 checkpointd 可写。10.0 的卷名作废。

原因：恢复发生在训练容器启动之前，训练程序还没有机会建目录，工作卷上的目录必须先存在；保存成功后 checkpointd 还要删除副本，只读挂载会让删除失败。训练容器仍只多一个 `TRAINCACHE_CHECKPOINT_DIR`。

## D16 续传状态按文件拆，首行存上传头

结论：`state_path` 是目录，每个文件一个 `<sha256>.jsonl`，首行 `kind=upload` 带 upload_id/key/file，之后是分片记录。

原因：S3 的分片上传需要 upload id 与对象键，只有 part/etag/bytes 无法跨进程续传；一个 step 又有多个文件。文件内容相同的对象可以共用状态，upload id 与键属于单个 multipart 上传；加可选字段不破坏已有的 part/etag/bytes 读取。S3 插件在保存成功后删除这些文件，local 插件不使用。

## D17 NVMe 卷本期用 emptyDir

结论：本期 `checkpoint-nvme` 是 emptyDir，落在节点磁盘。

原因：emptyDir 无法指定节点盘类型；local PV 需要静态供给与节点标签，仓库里没有。缓存是加速项，不是正确性依赖，引入 PV 供给会扩大部署面并需要集群管理员动作，先保证保存与恢复正确。NVME_DIR 指向节点磁盘；缓存可跨容器重启但不可跨 Pod 重建，装置验证前不承诺 NVMe 收益。

## D18 逐步日志的消息里带 step

结论：逐步事件的消息里带 step，探针切换的消息里带状态。

原因：core 的采样器按 `(component,event,task_id,reason)` 去重 60 秒，逐步事件如果只改字段不改消息，第二个 step 的记录会被当成重复丢弃；去重键是全仓共享契约，为单个组件加字段会影响所有模块，把变化维度放进 event 不需要改 core。日志检索仍可用结构化字段；按消息文本匹配的脚本要跟着改。

## D19 一个镜像带两个插件，digest 写进 install.yaml 的 ConfigMap

结论：一个镜像 `traincache-checkpointd`，内含 `/opt/traincache/plugins/{s3,local}/<name>`；准入注入的 initContainer 把它复制到 emptyDir；该镜像随版本构建，它的 digest 写进 install.yaml 的 `traincache-checkpoint-image` ConfigMap（键 `checkpointImage`），webhook 读它作为注入镜像的发布默认值。

原因：插件与 checkpointd 必须同版本，拆镜像会让配对关系散落在部署清单里。checkpointd 没有常驻 Deployment，但它的取值要跟发布走：digest 落在清单里，安装方不必自己抄镜像名，发布流水线也能对它做与另外五个镜像一样的校验。install.yaml 里出现第六个 digest 引用，发布候选仍记六个 digest。

## D20 checkpointd 登记进日志组件枚举

结论：8.1 §3.1 的 `component` 枚举按只增不改补 `checkpointd`，并写 8.2 ADR-016；不新增采样规则、标签与指标。

原因：采集侧对未知 `component` 的处理是丢弃还是放行取决于实现，枚举缺项会让同一组件的日志在两侧口径不一致；复用别的名字又会把 checkpoint 的日志混进预热或 DataLoader 的查询里。8.4 的来源表与查询示例同步补 `checkpointd`。

## D21 sidecar 镜像的取值顺序

结论：镜像按 Pod 注解 `traincache.io/checkpoint-image`、ConfigMap 键 `checkpointImage`、本次发布的默认镜像（webhook Deployment 的 `CHECKPOINT_IMAGE`，来自 install.yaml 的 `traincache-checkpoint-image` ConfigMap）三处依次取值，前面的覆盖后面的；三处都空时准入拒绝该 Pod。

原因：仓库里「缺配置就失败、不静默兜底」的做法同样适用于镜像，注入一个拉不到的镜像会让 Pod 停在拉镜像阶段并给出与配置问题无关的错误信息。发布默认放在最后，让它只兜底而不夺走接入方显式指定的镜像。接入方仍可用 ConfigMap 键或 Pod 注解指定自己的镜像；用 install.yaml 装机的集群不写这两个来源也能用，注入的 sidecar 就是本次发布的 digest；手工装 webhook 且没给 `CHECKPOINT_IMAGE` 时，缺镜像仍会被准入拒绝。

## D22 准入读 ConfigMap 走直连 API

结论：准入用直连 API 的 reader 读 ConfigMap 与 Job，RBAC 保持只有 `get`。

原因：webhook 的 manager 缓存 client 会为 ConfigMap 起 informer，而 RBAC 只给了 `get`，informer 永远同步不上，读操作会一直阻塞到准入超时，Pod 直接被拒；给全集群 ConfigMap 的 `list`/`watch` 换来的只是一次配置读取，权限放大没有必要。每次准入请求多一次 API 调用，配置读不到时准入失败并给出原因；webhook 的 RBAC 注释写明它不读 Secret。

## D23 工作卷的权限靠 fsGroup 与组可写目录

结论：checkpointd 保持非 root（镜像写死 `USER 65532:65532`）。卷设 `fsGroup=65532`，`<task_id>` 目录由 checkpointd 按 0775 建出，训练程序用组可写方式建 step 目录（`umask 0002`）；两边任一不满足，删副本就会失败，checkpointd 记 WARN。

原因：让 checkpointd 用 root 能一次解决删除，但它同时持有后端凭证，权限放大换来的只是一个 unlink。组可写目录是共享卷上的常规做法，`fsGroup` 本来就在注入契约里，只差把目录模式写进契约。训练程序不配合时后果是工作卷涨满，不是静默丢数据，删除失败有 WARN。

影响：训练程序要按组可写方式建 step 目录；训练程序的 uid 若是 65532 本身则无此要求。删除失败会一直重试到副本删掉为止。完整的五条前提写在 10.1 §4.3.1：卷上 fsGroup 生效（`fsGroupPolicy` 不是 None）、训练程序落在同一组、step 目录组可写、`<task_id>` 目录由 checkpointd 建、工作卷是训练容器与 checkpointd 共用的同一个卷。

## D24 启用标记合为一个 label

结论：启用标记合成一个 label。`traincache.io/checkpoint` 的值是同 namespace 的 ConfigMap 名；`objectSelector` 用 `matchExpressions` 按 `Exists` 匹配这个键，不再限定取值。annotation `traincache.io/checkpoint` 删除，不再参与启用与配置选择。值不是合法 ConfigMap 名、为空，或按它读不到 ConfigMap 时，准入拒绝该 Pod 并写明缺哪个。`traincache.io/checkpoint-image`、`task-id`、`world-size`、`rank`、`checkpoint-step` 这些 annotation 的作用不变。

原因：`objectSelector` 只看 label，annotation 进不了选择器，这是 Kubernetes 的机制，改不了。两个标记并列把「配了配置没配选择器」变成一种无声失败，而选择器和配置来源本来就是同一件事：要不要启用、用哪份配置。合到一个 label 上之后，要启用就必须写对这一个标记，写错的下一步是准入拒绝，不是放行。`namespaceSelector` 会把 webhook 推到全部 Pod 的准入链上，`failurePolicy: Fail` 下 webhook 不通即整个集群建不出 Pod，为一个可选功能承担的可用性风险过大。

影响：这是接入契约的破坏性改动。已按 0.5.1 契约接入的 Pod 要把 annotation 的值挪到 label 上，label 值不再是 `enabled`；只写 label=enabled 的老 Pod 会被当作「找名为 enabled 的 ConfigMap」处理，读不到即拒绝，不会静默放行。10.0 原文写的是 annotation 带配置名，落地按本节。10.1 §4.2 的准入契约同步。

## D25 step 完整性按 rank 集合判定

结论：按集合判。完整性要求实际存在的 rank 集合恰好等于 `{0 … world_size-1}`：缺任一份判不完整，出现 `rank ≥ world_size` 的多余份同样判不完整并记 WARN，`reason=rank_beyond_world_size`，附带看到的最大 rank。本期仍不支持弹性训练改变副本数（D7 的边界不变），本条做的是「副本数确实变了时不把它当成功」。

原因：数份数只能证明凑够了个数，证明不了编号连续。rank 是按编号命名目录的，集合比对在同一次枚举里就能做，不额外访问后端。判不完整的代价是这个 step 不恢复（`requireCheckpoint` 为 false 时跳过、为 true 时报失败），比恢复出一个缺 rank 的现场便宜得多。多余份出现说明声明值与实际拓扑不符，这条 WARN 是唯一能把它说出来的地方。完整性判定变严：历史上传里如果存在「编号不连续但份数够」的 step，改后不再判完整，这种情况本来也无法恢复出可用的世界。

## D26 跨链路对账键用 Job 名，checkpointd 日志带 `job`

结论：不统一两套 ID，对账键固定为 owner Job 名。checkpointd 的全部日志带 `job` 字段，取值依次是 Pod 的 `batch.kubernetes.io/job-name` label、`job-name` label，两者都没有时为空串。`task_id` 的语义与取值顺序不变。预热链路侧，WarmupTask 通过 ownerReference 或同名 label 关联到训练 Job，按 Job 名查询即可。本期不发指标（D4），对账只发生在日志侧。

理由：两套 ID 各自服务的对象不同：`task_id` 是后端键空间的一部分，改动会让已上传的 checkpoint 找不到；预热的 ID 是 CR 名加序号，改动要动 CRD 语义。把它们拉平的代价落在数据契约上，而真正要回答的问题是「这条日志属于哪场训练」，Job 名本来就是训练的作业名，两边都拿得到，不要求接入方额外配置。annotation 覆盖 `task_id` 时它会与 Job 名脱钩，这正是需要独立 `job` 字段的场景。

影响：checkpointd 日志多一个字段，采样键 `(component,event,task_id,reason)` 不含 `job`，去重行为不变（D18）。空串 `job` 表示该 Pod 不属于 Job（裸 Pod 或自定义 CR 直接建 Pod），这类场景仍需按 `task_id` 查询。

## D27 第三方插件本期不交付

结论：本期只交付内置的 `s3` 与 `local` 两个插件，不提供第三方插件的支持承诺，不写审核流程、仓库与版本约束。`PLUGIN_PATH` 保留，用途限定为开发与 e2e 指向自建二进制，写进 10.1 的信任边界；生产接入第三方插件不在本期范围。

理由：插件与 checkpointd 同容器同权限，能读它的全部环境变量（含两把凭证）并读写挂载卷；接一个第三方插件等于允许它在训练 Pod 内执行任意代码并读到凭证，这条边界需要的是流程约束（谁审核、镜像放哪、版本怎么锁），不是代码约束，本期没有流程结论可写。代码侧的白名单同样解决不了问题：能进 Pod 的镜像本来就能带任意二进制。内置两个插件覆盖 S3 兼容后端与共享文件系统两类，本期够用。第三方插件的审核、仓库与版本约束等有人提需求再开条目，本期不留占位。
