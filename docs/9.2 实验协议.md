> 对应需求：`docs/9.0 核心能力验收与测试.md`；执行计划：`docs/9.1 plan.md`

## 0. 概述

这份文件先把“量什么、怎么量、什么算赢、什么时候算输”写死，再看数据。三张旗舰图哪怕大半区域是负的，只要按本文件的口径如实报告，就算验收通过。

## 1. 七组态对照与共同口径

七组态吃同一份请求轨迹、同一个 tc 档位、同一份数据：

| 组名 | 数据路径 | 缓存层 | 预热/预取 |
|---|---|---|---|
| `direct` | 训练 Pod 直接 HTTP 读 MinIO | 无 | 无 |
| `juicefs-cold` | JuiceFS CE 挂载 MinIO | JuiceFS 单机缓存，空缓存启动 | 无 |
| `juicefs-warm` | 同上 | JuiceFS 单机缓存 | `juicefs warmup` 预热整档数据集，预热完成后开始计时 |
| `fluid-cold` | Fluid + JuiceFSRuntime + 亲和 | Fluid 管理的缓存，空缓存启动 | 无 |
| `fluid-warm` | 同上 | Fluid 管理的缓存 | DataLoad 预热整档数据集，预热完成后开始计时 |
| `traincache-cold` | Agent 预热块 + 训练 Pod hostPath 只读挂载 | TrainCache Agent 缓存 | 全程预取（不预热、不门控，普通调度） |
| `traincache-warm` | 同上 | TrainCache Agent 缓存 | WarmupTask 预热启动窗口 + 启动门控 + 全程预取 |

三个 warm 组的预热耗时单列，不计入 makespan；预热搬的字节仍计入成本。其余四组没有“预热时间不计”的例外。

### 1.1 makespan 边界

七组态共用同一个 measure 脚本（`bench/compare/run_bench.py` 的 measure 模板），边界按下表采集；D/C 轨实验层用同名字段写 `run.json`（`bench/scripts/bench_track_d.py`、`bench_track_c.py`），两层的字段语义一致。

| 字段 | 定义 | 采集方式 |
|---|---|---|
| `t_submit` | 训练 Job 创建时刻 | runner 在 `kubectl apply` 前取 `time.time()`，注入 Job 环境变量 `TRAINCACHE_JOB_CREATED_AT`（epoch 秒，字符串）；各组同一写法 |
| `t_pod_ready` | 训练 Pod Ready 时刻 | K8s Pod condition `Ready=True` 的 `lastTransitionTime`，runner 侧读回，不依赖 Pod 自报 |
| `t_first_step` | 第一个 step 开始时刻 | measure 脚本在第一个 batch 就绪之后、算力开始之前打点（epoch 秒） |
| `t_last_step` | 最后一个 epoch 最后一个 step 结束时刻 | 最后一个 step 返回后打点 |
| `t_origin_first_byte` | 源站收到该 run 第一个数据请求的时刻 | MinIO 访问日志；D 轨 `collect.py` 回填，对照层只作诊断，不作为 makespan 主口径 |

对照层的落地形式：measure 脚本在 stdout 打一行 `RESULT key=value ...`（含 `startup_makespan`/`total_makespan`，后者由 `t_first_step`/`t_last_step` 减 `t_submit` 得到），每个 epoch 边界打一次 `[EPOCH_BOUNDARY] epoch=<n> ts=<epoch秒>`；runner 解析这两类标记，不读 Pod 内文件。`t_pod_ready` 由 runner 从 K8s 取，与 Pod 内时刻用同一把 epoch 秒尺子对齐。

两个 makespan 定义：

- **启动 makespan** = `t_first_step - t_submit`。它包含调度、镜像拉取、Pod 启动、数据等待，直到第一步真正开始。
- **全程 makespan** = `t_last_step - t_submit`。它包含启动阶段；另外单列 `t_last_step - t_pod_ready` 作为“落地后阶段”，用于拆分启动收益与全程收益。

`t_first_step` 必须在 batch 就绪之后打点。如果在等 batch 之前打，数据 stall 会被漏掉，指标失真。`metadata.creationTimestamp` 只作交叉核对，不作为 `t_submit` 主口径。

### 1.2 stall 口径

每一步记录两个时间：

- `wait_s`：从本步开始等待 batch，到 batch 就绪的时长。
- `step_s`：batch 就绪到本步计算结束的时长。

`stall = wait_s / step_s`。聚合报 `mean` 与 `p90`，中位数只用于判断“是否处于 stall 形态”，不作为主要比较指标。epoch 0 前 10 步标记为 `warmup`，不进入 stall 聚合，但仍进入 makespan。

### 1.3 阶段标签

每步带一个 `phase` 标签，取值固定为 `startup`、`steady`、`switch`：

| 阶段 | 起点 | 终点 |
|---|---|---|
| `startup` | `t_submit` | `t_first_step` |
| `steady` | `t_first_step` | 第一次切换事件 |
| `switch` | 切换事件时刻 | 新窗口 K 块全部就绪的时刻；若未就绪，截到该 epoch 结束 |

每个 epoch 边界都算一次切换事件，三种 shuffle 策略都一样。curriculum 的 stage 边界额外算切换事件。`switch` 优先于 `steady`；两个窗口同时活跃时按 `switch` 记。`traincache-warm` 启动窗口以 WarmupTask 的就绪状态（`startupWindowReady`/`gateDecision`）为准；`traincache-cold` 不建 WarmupTask、不打 gate 标签，startup 阶段直接以 `t_first_step` 为终点。epoch/stage 切换的训练侧 phase 用可观测代理：**新窗口 K 块对应的分片全部首次被训练侧打开的步**。代理晚于 Agent 的真实就绪时刻，会把少量 steady 预取归到 `switch`，报告里单列该口径差异；Agent 侧 `phase=switch` 的事件仍由 `ready_bitmap` 驱动，其命中计数列只作交叉校验。

### 1.4 命中率口径

命中率的统一定义：**该块打开时没有触达源站，就算命中**。

- 训练侧字节账由 measure 脚本按 phase 累计：每次打开累加 `read_bytes_<phase>`；打开时本地不存在、要等待预取或回源时，另把该块字节计入 `demand_miss_<phase>`。traincache 组精确到块；`direct` 整片 HTTP 直读，全部计入未命中；`juicefs-*`、`fluid-*` 出不了块级指标，按 D25 近似（warm≈全命中、cold≈全回源，分片粒度），产物 `hit_rate_basis` 列写明近似口径。
- 源站侧对账用 MinIO Prometheus 的 `minio_s3_traffic_sent_bytes` 在 run 窗口内的增量（`origin_egress_bytes`），与训练侧 fetch 字节的差值落 `origin_reconcile_diff`；差异超过 5% 时以源站为准，并在报告里说明。MinIO 未开访问日志，不按块键做请求计数。
- `traincache` 组同时抓 `traincache_cache_hit_ratio{dataset,phase}`，与训练侧统计对账；两者差异超过 5% 时，以训练侧 open-time 字节账为准，并在报告里说明。产物列的分工：
  - 主口径（整轮与分阶段）一律用训练侧 open-time 字节账：`hit_rate = 1 − demand_miss_bytes / read_bytes`，分阶段落 `hit_ratio_startup`/`hit_ratio_steady`/`hit_ratio_switch`，`hit_rate_basis=open_time_demand_miss_bytes`。
  - `traincache_fetch_bytes_total` 的 run 窗口增量单独折算 `source_saving_ratio = 1 − fetch_bytes_run / read_bytes`（`source_saving_basis=origin_saving`），衡量省下的源站流量，不与命中率混用。
  - Agent 侧 `traincache_cache_hits_total`/`traincache_cache_misses_total` 的增量按 `phase` 落 `hit_ratio_agent_*` 作交叉校验；`traincache_cache_hit_ratio{phase}` 末值落 `hit_ratio_gauge_*`，只作对账。Agent 窗口内没有读样本时这些列留空，不写 0。
- `direct` 组没有缓存层，命中率按 0% 记，并标注“无缓存层”；`juicefs-*` 与 `fluid-*` 用 D25 近似口径，不依赖各自厂商指标的语义。

### 1.5 三笔字节成本

三笔全部计入收益分母，不允许只报 makespan 不报成本：

| 账目 | 范围 | 统计方法 |
|---|---|---|
| 启动预热 | warm 组的预热阶段 | `traincache-warm` 按模型计 `WARMUP_K × 8 MiB × 实际 fanout`（`warmup_basis=prefix_only(k*chunk*fanout)`，集群 fanout=2）；`juicefs-warm`/`fluid-warm` 按整份数据集计 1 份。冷组与 `direct` 记 0。`warmup_seconds` 取 `status.gateDecision.decidedAt − status.startedAt`，字段缺失时回退墙钟并记 `warmup_time_basis=wall`；未预热的冷组记 `cold` |
| 持续预取 | 门控放行/训练开始到训练结束 | 把 `traincache_fetch_bytes_total` 中 `reason=prefetch` 的增量按窗口边界归因：落在切换窗口内的计入第三笔，其余计入本笔 |
| 阶段切换重预取 | 每个 `switch` 窗口 | 同一计数器增量中落在切换窗口内的部分 |

归因序列由运行期采样点和训练结束后的最终快照组成，末段增量不会漏算。`prefetch_bytes_run` 单列 reason=prefetch 的窗口总增量，`other_fetch_bytes_run = fetch_bytes_run − prefetch_bytes_run` 放非预取回源；`sustained_prefetch_bytes + switch_reprefetch_bytes` 应等于 `prefetch_bytes_run`，对不上说明采样缺口，按实际值报告并在行内标注。

`traincache_fetch_bytes_total` 现有标签是 `{dataset,result,reason}`，没有 `phase`。阶段拆分不新增标签，对照层统一用 runner 解析到的 `[EPOCH_BOUNDARY]` 时刻对计数器做区间差分（D 轨用 `run.json` 的 `switch_events`）；采样目标周期 5 s、切换归因窗口 60 s，产物记 `sample_n` 与 `sample_max_gap_s`，差分边界与采样间隔的误差单独报告。源站侧总出站字节作为交叉校验，两者差异超过 5% 时以源站为准。

`fanout` 的重复字节不隐藏：fanout=2 时启动预热按 2 份计入，Agent 计数器按实例各自累计也天然包含这份重复。两本账都只记一次，不做“有效字节”折算。

### 1.6 胜负判据

每组每个点报平均数与 bootstrap 95% 置信区间（10,000 次重采样）。比较两个组时，对“平均数差值”做同样的 bootstrap：

| 结论 | 条件（以 makespan 越低越好为例） |
|---|---|
| 赢 | 平均数改善 ≥ 5%，且差值 CI 上界 < 0 |
| 输 | 平均数恶化 ≥ 5%，且差值 CI 下界 > 0 |
| 相近 | 差值 CI 包含 0 |
| 可忽略 | CI 不包含 0，但平均数差异 < 5% |

命中率越高越好，方向反过来。图三的“回落时间”用 20% 作为赢/输阈值，其余规则相同。

最终报告里任何“赢/输”必须跑满该点规定的次数：曲面与淘汰矩阵每点 3 次，两张 Pareto 每点 7 次（D18）；对照层按 1.9 的 S/M/L 分档是 3/3/1 次（D19 的次数口径由 D32 按带宽分区接管；D19 起，对照层不再适用“7 次”要求）。

### 1.7 冷态与作废

冷态分两层。入组时做全量 `cold_reset`：删测量 Pod，清四个节点缓存目录（traincache 的 `blocks` 与 `quarantine`、`/var/cache/jfs`、Fluid 的 `/tmp/juicefs-cache`），删后判空，再丢宿主机页缓存。冷组跨 rep 只做轻冷态 `rep_cold_reset`：删测量 Pod、清四个缓存目录、丢页缓存，不 down/up 组件；warm 组每个 rep 仍整轮 down/up 并重新预热，否则 WarmupTask 停在上一轮的 Released 状态，标着 warm 实际是冷读。

清目录只清磁盘层。Fluid/JuiceFS 的挂载进程跨 rep 存活，内核里那批 FUSE 文件的干净页不会因为删目录而失效，下一 rep 的首批读直接命中页缓存、不过 tc 限速链路。所以每个 rep 都要 `sync; echo 3 > /proc/sys/vm/drop_caches`；跑分器优先用 sudo 通道，其次特权 docker，两条都不通就中止，不出“看着是冷读其实是页缓存”的行。

作废情形写进 `reason` 列，行保留、不进汇总：`up_failed`、`pod_create_failed`、`pod_failed`、`parse_failed`、`read_queue_timeout`、`read_error`、`agent_degraded`，以及人工判定的 `suspect_page_cache`（读数明显快于同格 `direct` 等物理上不可能的结果）。装置自检失败整轮作废并重跑，不允许挑掉坏点或把失败轮当异常值删除。

### 1.8 环境与轨迹

- kind 集群：1 个 control-plane + 4 个 worker，共 5 个节点。对照组与主实验先同集群，资源吃紧再拆，拆组只允许整体迁移，不允许只迁一部分。
- 请求轨迹：同一 track+档位的七组态共用一份轨迹——S/D 用 `traces/track-compare-d-s8-per-epoch.json`，M/B 用 `traces/track-compare-b-m32-per-epoch.json`，L/B 用 `traces/track-compare-b-l128-per-epoch.json`，C 用 `traces/track-c-32shard-per-epoch.json`；记录分片顺序、seed、每步样本数，`per_epoch` 的稳定哈希写进每个 COND 与产物目录（对照层按同一份参数现场生成，sha 必须与 COND 一致）。
- tc：速率按 COND，延迟全档统一 20 ms，netem 不挂随机时延。
- 数据源：五张图与对照层共用 MinIO 上的 `compare-data-8m` 快照（128 个 tar，每片 256 MiB，约 31 GiB）。图一、图三、Pareto 一/二消费前 8 个分片（2 GiB，ratio 的分母）；图二按数据集消费前 8 或 32 个分片（2/8 GiB）；M7 的 S/M/L 三档消费前 8/32/128 个分片（2/8/31 GiB）。七组态在同一格消费同一批分片。
- 训练负载：五张图与 M7 用对照层 measure 形态——标准库脚本按 400 步/epoch、每步 200 ms、8 MiB 分段读复刻训练 I/O，记 `read_workers=2`。真实 PyTorch + webdataset 只用于 M5 的 C 轨两 Job 与 `bench_track_d.py` 装置自检；图与对照层不依赖它。
- 对照组不可用预案：M6 先做仅验可行性的 Fluid 冒烟（控制面与 DataLoad/Runtime 全 Ready、400 步经 FUSE 跑通、组件额外占用 ≤6 CPU / 6 GiB）。两次失败且归因环境时记 `fluid-unavailable-on-kind`，图二/图三主基线降级为 `juicefs-warm`，Fluid 行标 `unavailable`，不补跑、不另起集群；manifest 自身错误修好后重试不计次数。可行性冒烟不产生性能数字，不属于“看到结果再调参”。

### 1.9 容量比三档 S/M/L 与预注册假设（七组态对照，D19/D30/D31/D32）

真实训练里数据集通常是节点缓存的几十倍以上，只在一个容量比下跑分，结论无法外推。七组态对照按数据/缓存容量比分三档，缓存三档固定同一个 1 GiB：

| 档 | 数据 | 缓存 | 容量比 | 参跑组 | 带宽 | 每点次数 | 定位 |
|---|---|---|---|---|---|---|---|
| S | 2 GiB | 1 GiB | 1:2 | 全部七组态 | @100 与 @1000（另有 @300 档三组） | 3（@100 与 @1000 各 3 次） | 正式结果，现状口径 |
| M | 8 GiB | 1 GiB | 1:8 | `direct`、`fluid-cold`、`traincache-cold` | @1000 | 3 | 正式结果，欠配校验 |
| L | 32 GiB | 1 GiB | 1:32 | `traincache-cold`、`fluid-cold` | @1000 | 1 | 探点，产物标 `exploratory` |

口径说明：

- COND 的 `group` 用七值词表，与跑分器的组态名一一对应：`direct`、`juicefs-cold`、`juicefs-warm`、`fluid-cold`、`fluid-warm`、`traincache-cold`、`traincache-warm`。冷热由组态名表达，不再靠「M/L 档的 `traincache` 就是冷启动」这类隐含约定。
- M 档与 L 档的基线用 `fluid-cold`（D30）：欠配校验必须压在最强工业基线上，只比 JuiceFS CE 会被质疑「绕过 Fluid」。`juicefs-cold`/`juicefs-warm` 仍留在 S 档七组态里。Fluid 若触发 D36 的两次环境性失败，M/L 该组落回 `juicefs-cold` 补跑，产物记 `baseline_substituted`。
- warm 组（`juicefs-warm`、`fluid-warm`、`traincache-warm`）只出现在 S 档：1:8 及以下预热至多覆盖数据的 1/8，热读相对冷读的优势缩小是算术事实，不是新发现，不陪跑 M/L。
- L 档每点 1 次，低于 9.0 的“至少 3 次”硬纪律。因此 L 档标 `exploratory`（探点：只报单点值、不报 CI、不进正式表，只用来回答“M 的方向是否延续”），不支持任何正式结论。CI 指 1.6 的 bootstrap 95% 置信区间。
- 除容量档与带宽档外三档共用其余口径：同一轨迹、fanout=2（两个 s3-access 节点各预取一份）、淘汰 `heat`、D16 训练负载、固定 delay 20 ms。
- **带宽是第二个自变量**（D31）：tc rate 取 {100, 300, 1000} mbit，随 COND 落盘。burst 按「约 0.1 秒的传输量」推导（1250k / 3750k / 12500k），不跨档复用固定值。netem 全档位只挂固定 `delay 20ms`，不加随机时延——逐包随机时延会把包序打乱，300mbit 档实测吞吐从 35.6 MB/s（95% 线速）跌到 0.6 MB/s 以下，档位差异被装置掩盖。「链路带宽 ÷ 每步读量」只用来解读分区：S 档 0.47 / 1.40 / 4.66，M 档 0.12 / 0.35 / 1.16，L 档 0.03 / 0.09 / 0.29——<1 链路受限，>2 计算主导。
- 每点次数按带宽分区（D32）：S 档 @100 与 @1000 各 3 次；M 档 @1000 3 次；L 档 @1000 1 次。3 次必须报均值 + bootstrap CI，只报中位数不满足 9.0 的硬纪律。
- 块大小口径：正式实验一律用 8 MiB 块（8388608 字节）的 `compare-data-8m` 快照，生产默认 64 MiB 不变，旧 `compare-data` 快照只留作历史产物复现。快照覆盖 B 轨全部 128 个分片，S/M/L 只按轨迹收窄消费范围，不另发布小快照。块是缓存与预取的最小单位；1 GiB 缓存按 64 MiB 只有 16 块、按 8 MiB 有 128 块，后者淘汰排序统计才够用。
- L 档 32 GiB 数据已生成（128 个 256 MiB 分片，追加生成约 24 GiB，只追加不覆盖 `bench-b` 源数据）；实际每份约 252.6 MiB，实际数据量约 31 GiB，比声明值小约 3%，容量比相应约为 1:31。三档偏差同向、不影响组间可比性。
- 跑分第一格先做前置探针：无 tc 状态下测 MinIO 实际吞吐上限。上限 < 125 MB/s 时 @1000 档失效，带宽轴缩为 {100, 上限} 两档，并回写 D31。**已实测（§8.2）：C ≈ 674 MB/s，@1000 可达，三档独立，本条不触发。**

## 4. 图三：阶段切换 stall 回落曲线

### 4.1 自变量与档位

| 自变量 | 档位 | 说明 |
|---|---|---|
| epoch 数 | 1 / 3 / 10 | 决定切换次数 |
| shuffle 策略 | 固定 seed / 每 epoch 重排 / curriculum | 三种顺序形态 |

共 9 个点。固定参数：MinIO 快照前 8 个分片（2 GiB）、100 mbit/20 ms、fanout=2、缓存 50%、`K=8`、门控参数同图一、lookahead 8、淘汰策略 `heat`。

三种 shuffle 的定义：

- `fixed`：所有 epoch 用同一个 seed，消费顺序逐 epoch 相同。
- `per-epoch`：seed+epoch，每 epoch 重新做分片置换与样本 shuffle。
- `curriculum`：3 个 stage，分片集合依次为全量、2/3、1/3。全局置换 `P = Random(seed).permutation(n_tars)`；stage 0/1/2 分别使用嵌套前缀 `P[:n]`、`P[:ceil(2n/3)]`、`P[:ceil(n/3)]`；stage 内顺序 = `P` 过滤到该前缀，stage 内所有 epoch 完全一致。stage 归属：`E<3` 时为 stage 0；否则 `e < floor(E/3)` 为 0、`e < floor(2E/3)` 为 1、其余为 2。每个 epoch 边界都是切换事件；stage 边界与 epoch 边界重合时只记一次，事件标 `kind=epoch+stage`。1 个 epoch 时 curriculum 退化为单个 stage（全量），仅用于保持矩阵完整，不参与“curriculum 优于固定 seed”的结论。

### 4.2 回落时间的定义

每个切换事件算一次回落时间：

1. 基线 = 切换前 20 步的 stall 均值。
2. 阈值 = `max(1.1 × 基线, 基线 + 5 个百分点)`。基线接近 0 时用加法项，避免阈值退化为 0。
3. 从切换后第 1 步开始，取 10 步滚动 stall 均值；第一次满足“滚动均值 ≤ 阈值，且之后连续 10 步都 ≤ 阈值”的步，记为回落点。
4. 到该 epoch 结束仍未满足，记右删失（right-censored），回落时间按 epoch 结束计，并单独报删失率。

纵轴报每个点的回落时间平均数与 95% CI；同时报删失率，避免用“没恢复”伪装成“恢复得快”。

### 4.3 预注册假设

| # | 假设 | 预期 |
|---|---|---|
| H3.1 | 每 epoch 重排时 TrainCache 回落明显快于 Fluid | epoch ≥3 时，回落时间平均数比 Fluid 低 ≥20%，且 CI 上界 < 0 |
| H3.2 | 固定 seed 时两者相近 | 固定 seed 下差异在 ±5% 内；切换本身不是瓶颈 |
| H3.3 | curriculum 比固定 seed 慢、比 Fluid 快 | curriculum 的回落时间介于两者之间；stage 越窄，切换瞬间 stall 峰值越高 |
| H3.4 | 切换成本随 epoch 数增加 | per-epoch 的回落时间随 epoch 数增加而增加；fixed 不明显增加 |

### 4.4 阴性结论的接受条件

如果每 epoch 重排下 TrainCache 没有更快回落，报告写“阶段切换不是本装置的瓶颈，或预取没赶上切换后的新窗口”，并给出新窗口 K 块就绪时刻与 ETA 的对照。允许这个阴性结论，不修改图三的档位。

### 8.1 镜像 digest 取值口径

四个 Traincache 组件为 dev 构建，集群清单统一 `:dev`；另外六个是第三方固定版本。COND 把每个引用写成 `repo:tag@sha256:<digest>`，digest 取自集群 containerd。

取法：`docker exec <kind 节点> ctr -n k8s.io images ls`，取第二列 ref 与第三列 Digest；五台节点上同名镜像的 Digest 一致。

两个取值口径：

1. 记的是 containerd 的 manifest digest，不是 docker image ID（`docker images` 的 config digest）。`@sha256:` 在镜像引用里的语义是 manifest digest，两者不是同一个值。
2. `fluid` / `fluid-csi` 取 `v1.0.8-6533239`，这是 `fluid-system` 里实际在跑的版本；节点上另存的 v1.1.0 未使用。

kubelet 报的 `imageID`（形如 `docker.io/library/import-2026-10-24@sha256:…`）是 kind `load docker-archive` 给导入镜像打的标记，不是内容摘要；docker 侧的 `RepoDigests` 是上游 registry 的清单摘要，与 containerd 本地存的摘要本就不同（本地 build 的四个 Traincache 镜像没有 RepoDigests）。`lock.py` 把两路分开记：`docker_images` 取 COND 记录值，`docker_repo_digests` 只做交叉核对。

### 8.2 前置探针实测（9.1 §12.2）

无 tc 状态下 MinIO 源站吞吐上限 **C ≈ 674 MB/s（9 次测量的中位数，区间 629~755；≈5.4 Gbit/s）**，采法：与 train-job 同路径（worker 节点上临时 Pod 经 `nodeIP:30090` nodePort），`mc cat bench-b/shard-xxxxx.tar | wc -c` 计时。并行 2 连接聚合 1120/870 MB/s、并行 3 聚合 1207 MB/s——上限随连接数增长，说明 674 MB/s 是单连接读者上限而非源站出口上限。

结论按 D31 的判据落定：**C ≫ 125 MB/s，@1000mbit 档可达，{100, 300, 1000} 三档互相独立，无格子塌缩成 `ceiling`，BW/r 分区无需按 C 重算**。

`chunk_size_bytes` 与生产默认的关系：生产默认块大小 67108864（64 MiB）不变；实验把块切成 8 MiB，只在空桶首次发布时用 trainpublish 的 `-chunk-size` 写入桶级声明，不改生产代码。块大小按桶固定，改大小必须清空桶重灌或换桶。原因：1 GiB 缓存按 64 MiB 只有 16 块，预取保护窗口（lookahead 16 块）覆盖整个缓存，淘汰排序统计失真；按 8 MiB 有 128 块，窗口占 1/8（D20）。正式实验一律读 8 MiB 切块的 `compare-data-8m` 快照（trainpublish `-chunk-size 8388608` 发布，首次写入 `_traincache/format.json`，D41）。

`equal-thirds` 的精确语义：`E<3` 时全部 epoch 属于 stage 0；否则 `e < floor(E/3)` 为 stage 0、`e < floor(2E/3)` 为 stage 1、其余为 stage 2。分片集合取 `P = Random(dataset.seed).permutation(n_tars)` 的嵌套前缀：stage 0/1/2 分别为 `P[:n]`、`P[:ceil(2n/3)]`、`P[:ceil(n/3)]`；stage 内顺序为 `P` 过滤到该前缀，stage 内所有 epoch 一致。`E=1` 时退化为 stage 0 全量。

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `enabled` | bool | 是 | — | `direct` 为 false，其余为 true |

| `ratio` | float | 条件 | `enabled=true` 时必填 | 数据集/缓存容量比；`capacity_bytes` 必须等于 `dataset.bytes / ratio` 的 ±1% |
| `capacity_ratio` | string | 条件 | `S`/`M`/`L`；仅 `figure=compare-d`/`compare-b` 必填，其余 figure 不填 | 对照实验的容量档位标签（D19）；同时决定该档的参跑组（D30） |
| `evict_policy` | string | 是 | `heat`/`lru`/`lfu`/`external` | TrainCache 的策略取 `heat`/`lru`/`lfu` 三档（D9）；`external` 表示由 JuiceFS/Fluid 自己管理，TrainCache 不应用 |
| `warmup_seconds` | int | 否 | ≥0，默认 0 | 本点预热预算秒数；预热时长单列、不计入 makespan（D11/D23） |
| `root` | string | 否 | 绝对路径 | TrainCache 缓存根；默认 `/var/cache/traincache` |

`ratio` 的档位：图一用 1/2/4；图二按数据集取 2（2 GiB）或 8（8 GiB），缓存固定 1 GiB；图三用 2；C 轨倾斜场景用 3.3333，表示缓存容量为数据集字节的 30%。30% 是显式容量上限：`capacity_bytes = floor(dataset.bytes × 0.30)`，runner 以 `capacity_bytes` 为准，`ratio` 只作展示与交叉校验；稳态 `disk_usage_ratio` 是否落在 25%~35% 是验收检查，不是控制量。

`capacity_ratio`、`ratio`、`capacity_bytes` 的关系：

- `capacity_bytes` 是唯一的控制量（淘汰触发的容量上限）；`ratio = dataset.bytes ÷ capacity_bytes`，两者继续按校验规则 4 做 ±1% 交叉校验。
- `capacity_ratio` 只是对照实验的档位别名，不引入新容量语义。固定映射：`S`↔ratio 2（2 GiB 数据 / 1 GiB 缓存）、`M`↔ratio 8（8 GiB / 1 GiB）、`L`↔ratio 32（32 GiB / 1 GiB）；三档缓存都是同一个 1 GiB。
- 写了 `capacity_ratio` 时，`dataset.bytes`、`capacity_bytes`、`ratio` 三个值必须与档位映射自洽（±1%），runner 校验；不一致直接拒绝。
- `capacity_ratio` 还决定该档跑哪些组态（D30）：`S` 档七组态全跑，`M` 档跑 `direct`/`fluid-cold`/`traincache-cold`，`L` 档跑 `traincache-cold`/`fluid-cold`。`group` 不在所属档位的组态集合里，校验器直接拒绝。
- C 轨（`pareto2`/`policy`）用 `ratio=3.3333`，不填 `capacity_ratio`：S/M/L 档与 C 轨 30% 是两套场景口径，不混用（D34）。

`warmup_seconds` 口径：预热外置于计时——所有组的预热在 `group_up` 内完成并等待，超过 15 分钟整轮作废（D23）。冷组写 0；`juicefs-warm`、`fluid-warm` 与 `traincache-warm` 写实测预热时长。runner 从 `up.sh` 回传的 `[WARMUP_SECONDS]` 取值，记入 `summary.csv` 的 `warmup_seconds` 列；该时长不进 makespan，预热搬的字节计入成本（预注册 §1）。

| `compare-b` | `track=B`；缓存固定 1 GiB，`epochs=1`，`evict_policy=heat`，`fanout=2`。M 档：`capacity_ratio=M`，`ratio=8`（8 GiB / 1 GiB），`rate_mbit=1000`，参跑组 `direct`/`fluid-cold`/`traincache-cold` 各一个 COND，`reps=3`（D32）。L 档：`capacity_ratio=L`，`ratio=32`（32 GiB / 1 GiB），`rate_mbit=1000`，参跑组 `traincache-cold`/`fluid-cold` 各一个 COND，`reps=1`，产物由 runner 依 `capacity_ratio=L` 自动标 `exploratory`（预注册 1.9；warm 组不陪跑 M/L） |
| `policy` | `track=C`；倾斜双 Job 在同一个测量 Pod 内并发，走真实 Agent 与节点 hostPath 缓存；`ratio=3.3333`；`epochs=3`；`evict_policy` 三档（`heat`/`lru`/`lfu`）；`reps=3`；不填 `capacity_ratio` |

`compare-d` 扫两个轴：组态与带宽。基准带宽 100 mbit 跑全部七组态（轴 `group`）；300 mbit 只跑 `direct`/`fluid-cold`/`traincache-cold` 三组（`BW/r∈[1,2]`，链路处于读取与计算的交界）；1000 mbit 跑全部七组态。

`group` 不是 `traincache-cold`/`traincache-warm` 时，`prefetch` 不生效，但 COND 里仍要写 `fanout` 与 `window_k` 的对照值（用同一档位下 `traincache-cold` 的同名 COND 共享），runner 会拒绝缺失的对照。

## C5. 校验规则

runner 在开跑前逐条校验，任一失败直接拒绝，不进入执行：

1. JSON 可解析，`schema_version="1"`，无未知字段，必填字段非空。
2. `name` 与文件名一致，且在 `conds/` 下唯一。
3. `dataset.bytes` 与 `shards × shard_size_bytes` 误差 ≤1%。
4. `cache.enabled=true` 时，`capacity_bytes` 与 `dataset.bytes / ratio` 误差 ≤1%。
5. `cache.enabled=false` 只允许 `group=direct`。
6. `group=traincache-cold`/`traincache-warm` 时 `prefetch` 必填；其他组态 `prefetch` 可选，但对照字段必须齐。
7. `workload.shuffle=curriculum` 时 `curriculum` 必填，且 `stages=3`、`shard_fractions` 与 COND 记录值逐字一致。
8. `sampling.reps` 取值：`fig1`/`fig2`/`fig3` 与 `policy` 为 3；`pareto1`/`pareto2` 必须为 7；`compare-*` 按容量档位走（D32）——`capacity_ratio=S` 时 3、`M` 时 3、`L` 时 1（`exploratory` 标记见 §C2.8）。
9. `trace.sha256` 是 64 位小写 hex；`environment.images` 每项是 `repo@sha256:...`；两者为全零或 `aaaa…` 占位符时拒绝执行。
10. 同一 `figure` 内，除被扫的自变量外，其余字段必须与基准 COND 一致。runner 用 `tags` 里的 `axis=<name>` 标出本点扫的轴。`compare-d` 扫两个轴：基准带宽点用 `axis=group`，非基准带宽点（300/1000 mbit）用 `axis=rate`；`compare-b` 只扫组态，用 `axis=group`。
11. `cache.capacity_ratio` 只允许出现在 `figure=compare-d`/`compare-b`；出现时 `dataset.bytes`、`capacity_bytes`、`ratio` 必须满足 S↔2、M↔8、L↔32 的档位映射（±1%），且缓存 1 GiB、数据 2/8/32 GiB。
12. `dataset.chunk_size_bytes` 正式实验必须为 8388608；`evict_policy` 只能是 `heat`/`lru`/`lfu`/`external`（D9）。
13. `group` 只能是 7 个组态名之一（`direct`/`juicefs-cold`/`juicefs-warm`/`fluid-cold`/`fluid-warm`/`traincache-cold`/`traincache-warm`）；COND 写了 `capacity_ratio` 时，`group` 还必须落在该档位的参跑组集合内（`S` 七组态、`M` 三组、`L` 两组），越组直接拒绝（D30）。
14. `network.rate_mbit` 只能是 100/300/1000；`network.burst_k` 必须等于该 rate 的推导值（1250/3750/12500）。链路形态不进 COND：netem 一律只有 `network.delay_ms` 给的固定时延（D31）。
