# bench 操作手册

## 1 环境准备

### 1.1 宿主机与工具

宿主机跑 Linux，装 Docker、kind、kubectl、git、python3。kind 的 5 个节点是 Docker 容器，共用这台机器。首次准备留 40 GiB 可用磁盘：数据层 4 GiB，MinIO 的 PVC 30 GiB。

```bash
docker info >/dev/null && echo docker-ok
kind version
kubectl version --client
python3 --version
```

四条命令都返回 0 即可。

### 1.2 镜像

bench 用五个 Traincache 镜像：controller-manager、webhook、kube-scheduler、traincache-agentd、traincache-gateway。跑 e2e 族再加 traincache-checkpointd。

```bash
./hack/build-images.sh
./hack/kind-load.sh traincache \
  ghcr.io/thewor1d877/traincache/controller-manager:dev \
  ghcr.io/thewor1d877/traincache/webhook:dev \
  ghcr.io/thewor1d877/traincache/kube-scheduler:dev \
  ghcr.io/thewor1d877/traincache/traincache-agentd:dev \
  ghcr.io/thewor1d877/traincache/traincache-gateway:dev
```

每个镜像带 `io.traincache.src-fp` 标签，值是该次构建的源码指纹。`ctrl_up.sh` 比对标签与当前工作树，不一致时拒绝拉起。改过 `agent/`、`controller/`、`core/`、`gateway/`、`checkpoint/` 里任一文件后，重跑上面两条命令。

导入到四个 worker 的判据：

```bash
for n in traincache-worker traincache-worker2 traincache-worker3 traincache-worker4; do
  docker exec "$n" crictl images -q ghcr.io/thewor1d877/traincache/traincache-agentd:dev
done
```

四行都有输出即导入成功。

### 1.3 Python 环境

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r bench/requirements.txt
```

venv 放 repo 根目录，`bench/Makefile` 的 python 指向它。后续命令都在激活后的 shell 里执行。torch 不在清单里，训练负载跑在镜像内。

判据：`python3 -c "import numpy, pandas, boto3, webdataset"` 不报错。

### 1.4 kind 集群

集群名 `traincache`，1 个 control-plane 加 4 个 worker，配置在 `bench/k8s/kind-config.yaml`。`make -C bench bench-up` 建这个集群并导入 minio、busybox 两个基础镜像。单独建一次：

```bash
kind create cluster --config bench/k8s/kind-config.yaml
kubectl get nodes
```

`kubectl get nodes` 打印 5 行，STATUS 全为 `Ready`。

## 2 拉起与自检

### 2.1 拉起

```bash
make -C bench bench-up
```

目标依次做七件事：建集群、部署 MinIO、生成缺的数据、上传桶、拉起控制面与 agentd、挂 tc 限速、跑两次冷读。每步幂等，集群与数据已存在时跳过。数据生成与两次冷读占大部分时间。

末行输出 `== bench-up 完成:装置已拉起并通过冷读验证 ==` 时结束。冷读判定是两次全量读的耗时相对差不超过 10%。

### 2.2 自检

```bash
make -C bench bench-doctor
echo $?
```

doctor 只读，逐项打印 PASS、FAIL、WARN，覆盖工具与解释器、Python 依赖、集群与节点、worker 镜像、控制面与 Agent、淘汰证据、MinIO 与桶、tc qdisc、数据目录与磁盘。

判据：输出里没有 FAIL 行，退出码 0。WARN 不阻塞开跑，逐条读原因再决定。

### 2.3 拆装置

```bash
make -C bench bench-down
```

拆掉 tc 限速，保留集群与 `~/tcd` 数据。删集群用 `kind delete cluster --name traincache`。

## 3 数据准备

数据在 `~/tcd/bench/data/`。当前已有：主数据集 128 片（本装置读前 16 片）、倾斜清单两个、训练负载 16 片。正常跑族跳过本节。

### 3.1 生成

```bash
python3 bench/scripts/synth_dataset.py --count 16
python3 bench/scripts/synth_tilt.py
python3 bench/scripts/synth_train.py
```

| 脚本 | 产物 | 参数 |
|---|---|---|
| `synth_dataset.py` | 16 × 256 MiB 的 tar，落 `track_b/tars`，名 `shard-NNNNNN.tar` | `--count` 生成片数，`--start-shard` 起始片号 |
| `synth_tilt.py` | `full-shards.txt` 与 `hot-shards.txt`，落 `track_c` | 无参数，复用主数据集 |
| `synth_train.py` | 16 × 128 MiB，落 `track_d` | 无参数取 `bench/config.py` 的默认值 |

分片种子只与片号有关。补缺失分片用 `--start-shard 16 --count N`，结果与一次生成逐字节一致。

### 3.2 上传

```bash
python3 bench/scripts/upload_bench.py
```

写入 MinIO 的 `bench-b` 桶，已有对象跳过。重写源数据加 `UPLOAD_FORCE=1`。

### 3.3 校验

```bash
python3 bench/run.py compare --rho 4 --rate 300 --group traincache-cold --dry-run
ls ~/tcd/bench/data/track_b/tars/shard-*.tar | head -16 | wc -l
du -cb $(ls ~/tcd/bench/data/track_b/tars/shard-*.tar | head -16) | tail -1
sha256sum ~/tcd/bench/data/track_b/tars/shard-00000.tar
```

判据三条。dry-run 打印的数据字节为 4294967296，缓存字节为 1073741824。前 16 片合计约 3.95 GiB，每片实测约 252.6 MiB，与声明值的偏差见 4.3 D42。同一片两次生成的 sha256 相同。COND 的规模校验由 runner 开跑前执行，规则见 4.2 §11。

## 4 跑族

入口 `python3 bench/run.py <族>`。族 ID 九个：`compare`、`gateway`、`evict`、`prefetch`、`warmup`、`switch`、`chaos`、`multiconsumer`、`e2e`。

每次先加 `--dry-run`。它只打印计划，每行一格：COND 名、数据字节、缓存字节、rate、reps，不碰集群。核对格子数与 ρ 取值后再跑。

产物落 `~/tcd/bench/results/<族 ID>/<COND 名>/`。族间串行，两个族并行会抢 MinIO `eth0` 上的共享令牌桶（4.1 §1）。全部跑一遍：

```bash
for f in compare gateway evict prefetch warmup switch chaos multiconsumer e2e; do
  python3 bench/run.py "$f" || break
done
```

参数含义见 4.1 §3，各族的轴与取值见 4.2 对应小节，判据见 4.3 §3.2。

### 4.1 compare

36 格，108 跑，15.6 h。1000 mbit 与 300 mbit 各 45 跑，单跑 6.0 与 7.5 min；100 mbit 18 跑，单跑 18.4 min。

```bash
python3 bench/run.py compare --dry-run
python3 bench/run.py compare
python3 bench/run.py compare --rho 2 --rate 300 --group traincache-cold
```

第三条只跑一格。产物 `~/tcd/bench/results/compare/compare-<组态>-rho<ρ>-<带宽>/`。判据见 4.3 §3.2「compare·组间胜负」。

### 4.2 gateway

4 格，12 跑，1.5 h，单跑 7.5 min。读端固定 4，300 mbit，ρ=4。

```bash
python3 bench/run.py gateway --dry-run
python3 bench/run.py gateway
```

产物 `~/tcd/bench/results/gateway/gateway-g<臂号>-r4/`。判据见 4.3 §3.2「gateway·复制读合并」与「gateway·臂间比较」。

### 4.3 evict

6 格，18 跑，1.8 h，单跑 6.0 min。1000 mbit，ρ 取 1 与 8。

```bash
python3 bench/run.py evict --dry-run
python3 bench/run.py evict
```

产物 `~/tcd/bench/results/evict/evict-<算法>-rho<ρ>/`。判据见 4.3 §3.2「evict·策略可分辨」与「evict·策略不可分辨」。

### 4.4 prefetch

18 格，54 跑，5.4 h，单跑 6.0 min。1000 mbit，ρ 取 1 与 8。

```bash
python3 bench/run.py prefetch --dry-run
python3 bench/run.py prefetch
python3 bench/run.py prefetch --rho 8 --lookahead 16 --fanout 2
```

产物 `~/tcd/bench/results/prefetch/prefetch-la<窗口块数>-fan<fanout>-rho<ρ>/`。判据见 4.3 §3.2「prefetch·转平」与「prefetch·重复字节」。

### 4.5 warmup

12 格，36 跑，3.6 h，单跑 6.0 min。1000 mbit，ρ 取 1 与 8。

```bash
python3 bench/run.py warmup --dry-run
python3 bench/run.py warmup
```

产物 `~/tcd/bench/results/warmup/warmup-<gated|free>-w<秒>-rho<ρ>/`。判据见 4.3 §3.2「warmup·门控有效」「warmup·门控无价值」「warmup·门控负收益」。

### 4.6 switch

8 格，24 跑，2.4 h，单跑 6.0 min。1000 mbit，ρ 取 1 与 8。

```bash
python3 bench/run.py switch --dry-run
python3 bench/run.py switch
```

产物 `~/tcd/bench/results/switch/switch-<场景>-rho<ρ>/`，其中 `recovery.json` 逐切换事件记回落时间与删失标记。判据见 4.3 §3.2「switch·回落」「switch·差异」「switch·右删失」。

### 4.7 chaos

6 格，18 跑，1.8 h，单跑 6.0 min。1000 mbit，ρ 取 1 与 8。

```bash
python3 bench/run.py chaos --dry-run
python3 bench/run.py chaos --fault kill_agent --dry-run
python3 bench/run.py chaos --fault kill_agent
```

第三条按故障单跑，`--fault` 取 `kill_agent`、`tamper_block`、`minio_down`。注入动作由 `bench/chaos/inject/` 下的脚本执行。产物 `~/tcd/bench/results/chaos/chaos-<故障>-rho<ρ>/`。判据见 4.3 §3.2 的三条混沌判据。

节点丢失按需复现走混沌套件入口，不进 `run.py` 的正式格：

```bash
bash bench/chaos/run.sh --fault node_loss --kubeconfig <本轮副本>
```

脚本停掉目标节点的 kind 容器，等 DataSet 的 `NoAccessibleNodes` 变 True、WarmupTask 落到 Degraded，再启动容器并等三者恢复。停容器期间该节点上的 Pod 全部失联，不与其他族并行。

### 4.8 multiconsumer

4 格，12 跑，1.2 h，单跑 6.0 min。1000 mbit，ρ=4，两个读端。

```bash
python3 bench/run.py multiconsumer --dry-run
python3 bench/run.py multiconsumer
```

产物 `~/tcd/bench/results/multiconsumer/multi-hot<比例>-<spread|colocated>/`。判据见 4.3 §3.2「multiconsumer·热比例效应」。

### 4.9 e2e

3 格，6 跑，7.0 h。每场景 2 跑，单跑 70 min，跑满 3 epoch 训练加一次 checkpoint 落盘与恢复。

```bash
python3 bench/run.py e2e --dry-run
python3 bench/run.py e2e
```

产物 `~/tcd/bench/results/e2e/e2e-<场景>/`，另存 checkpoint 目录与两次运行的 `lock.json`。判据见 4.3 §3.2「e2e·恢复成功」。

## 5 看结果

### 5.1 summary.csv

每行一次采样，每格 3 行，e2e 族 2 行。列按用途分组。

| 列 | 含义 |
|---|---|
| `family` `rho` `rate` `group` `load` `gateway` `rep` `cond` `run_id` | 定位一行属于哪个族、哪个 ρ、哪档带宽、哪个组态、哪种负载、网关开关、第几次采样 |

```bash
python3 -m json.tool ~/tcd/bench/results/compare/compare-traincache-cold-rho4-1000/lock.json
```

读两个数：`K_cache` 应与 4.1 §2 的表格一致；`cache_dir_peak_bytes` 除以声明容量得 `r_peak`，上限判定只在 100 mbit 的格子做，阈值见 4.3 §3.1。

## 6 排障

### 6.1 tc 没生效

现象：100 mbit 档的冷读跑出 600 MB/s 以上，正常应在 11.95 MB/s 附近。

```bash
make -C bench bench-doctor
```

看「tc qdisc」节。判据：MinIO Pod 的 `eth0` 上有 tbf，rate 与本档一致，burst 与本档期望值差在 ±1% 内。没有 qdisc 就重挂：

```bash
bash bench/scripts/tc_apply.sh 100mbit 20ms --target minio
```

MinIO Pod 重建后 netns 换新，qdisc 随之消失，重挂一次。

### 6.2 ImagePullBackOff

```bash
kubectl -n traincache get pod
kubectl -n traincache describe pod <pod> | sed -n '/Events/,$p'
docker images | grep traincache
```

判据：事件里写 `ErrImagePull` 或 `ImagePullBackOff`，且宿主 `docker images` 里没有该 tag。处理：先 `./hack/build-images.sh <组件>`（或 `docker pull <镜像>`），再 `./hack/kind-load.sh traincache <镜像>`，最后 `make -C bench bench-up` 重拉控制面。

### 6.3 Pod 一直 Pending

warmup 族 `gated` 的格子停在 Pending 属正常：调度闸门等预热完成才摘。其余 Pending 查事件：

```bash
kubectl -n traincache describe pod <pod> | sed -n '/Events/,$p'
```

判据：`Insufficient cpu` 或 `Insufficient memory` 说明节点资源不够，先拆掉别的负载；`node(s) didn't match Pod's node affinity` 说明反亲和或标签不满足，补标签：

```bash
kubectl label node <node> traincache.io/s3-access=true
```

### 6.4 COND 校验失败

现象：runner 在开跑前退出，打印 COND 文件名与不合格字段。

```bash
python3 bench/run.py compare --rho 4 --rate 300 --group traincache-cold --dry-run
```

判据：输出里没有校验失败提示。常见四种：`shards × shard_size_bytes` 不等于 4 GiB；`rho` 写了五个取值之外的值；`reps` 或 `epochs` 不是 3；出现 v3 字段 `figure`、`track`、`capacity_ratio`、`ratio`。改 COND 文件，或用 `--conds-dir` 指向另一份目录。规则全集见 4.2 §11。

### 6.5 格子已有产物

`--dry-run` 打印的 COND 名就是目录名，产物在 `~/tcd/bench/results/<族 ID>/<COND 名>/`。旧产物先归档再跑：

```bash
mv ~/tcd/bench/results/compare/compare-traincache-cold-rho4-1000 \
   ~/tcd/bench/results/compare/compare-traincache-cold-rho4-1000-v0.5.0
```

判据：原路径已空出，归档目录名带版本号。再开跑。4.5 的记录指向新目录。

### 6.6 镜像新鲜度门禁

现象：`ctrl_up.sh` 报镜像的源码指纹与工作树不一致。

处理：`./hack/build-images.sh` 重建，`./hack/kind-load.sh traincache <五个镜像>` 导入，再跑 `make -C bench bench-up`。

判据：doctor 的「worker 镜像」节全为 PASS。

### 6.7 桶里缺分片

现象：doctor 的「MinIO 与桶」节报 `shards` 小于 16。

```bash
python3 bench/scripts/upload_bench.py
make -C bench bench-doctor
```

判据：重跑 doctor 后该节报 `shards=16`。

## 7 产物契约

每格一个目录 `~/tcd/bench/results/<族 ID>/<COND 名>/`，固定内容如下。

| 路径 | 内容 | 读法 |
|---|---|---|
| `summary.csv` | 逐次采样的指标行，每格是 `sampling.reps` 行 | §5.1 |
| `version` | 产出该格的版本号 | §5.3 |
| `lock.json` | 实际生效参数、镜像 digest、tc 档位、`K_cache`、cache 峰值字节 | §5.2 |
| `runs/<组态>-rNN/` | 每次采样一份，含 `per_step_1_w1.jsonl`（逐步 stall）、`run.json`（本轮参数）、`recovery.json`（切换事件） | 4.3 §2.2 |
| 运行日志 | 装置侧与被测侧的原始输出 | — |
| `checkpoint/` | e2e 族另存，含两轮运行的 checkpoint 与 `lock.json` | 4.2 §10 |

单格 3 次采样对应 3 个 `runs` 子目录，e2e 族 2 个。目录只追加，重跑前按 §6.5 归档。

族根 `~/tcd/bench/results/<族 ID>/` 下放该族全部格子。混沌族的格子内是逐轮目录，每轮一份 `summary.txt`，其余族是格子根目录的 `summary.csv`。
