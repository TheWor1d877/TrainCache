# bench 操作手册

## 环境准备

### 宿主机与工具

宿主机跑 Linux，装 Docker、kind、kubectl、git、python3。kind 的 5 个节点是 Docker 容器，共用这台机器。首次准备留 40 GiB 可用磁盘：数据层 4 GiB，MinIO 的 PVC 30 GiB。

```bash
docker info >/dev/null && echo docker-ok
kind version
kubectl version --client
python3 --version
```

四条命令都返回 0 即可。

宿主机不要求免密 sudo。清宿主机页缓存有四条通道，`cold_reset.sh` 按顺序取第一条可用的：root 直跑、`sudo -n`、kind 节点容器内写 `/proc/sys/vm/drop_caches`、`sudo -S` 配 `bench/.sudo-pass`。kind 节点是特权容器、与宿主机共用内核，容器里写的是同一份页缓存，所以装置不依赖密码文件。`bench/.sudo-pass` 只在前三条都不可用时才需要，权限 600。

### 镜像

bench 用五个 Traincache 镜像：controller-manager、webhook、kube-scheduler、traincache-agentd、traincache-gateway。跑 e2e 族再加 traincache-checkpointd 与训练镜像 `traincache-trainer:v0.9.2`。训练镜像含 torch 与 webdataset，由 `bench/e2e/build-trainer.sh` 构建并导入 kind，不在 `hack/build-images.sh` 的 Go 镜像之列。

```bash
./hack/build-images.sh
./hack/kind-load.sh traincache \
  ghcr.io/thewor1d877/traincache/controller-manager:v0.9.2 \
  ghcr.io/thewor1d877/traincache/webhook:v0.9.2 \
  ghcr.io/thewor1d877/traincache/kube-scheduler:v0.9.2 \
  ghcr.io/thewor1d877/traincache/traincache-agentd:v0.9.2 \
  ghcr.io/thewor1d877/traincache/traincache-gateway:v0.9.2
```

每个镜像带 `io.traincache.src-fp` 标签，值是该次构建的源码指纹。`ctrl_up.sh` 检查四个 worker 上这五个镜像都在，并比对集群里的镜像引用与清单渲染结果，不一致就重新 apply 清单。改过 `agent/`、`controller/`、`core/`、`gateway/`、`checkpoint/` 里任一文件后，重跑上面两条命令。

导入到四个 worker 的判据：

```bash
for n in traincache-worker traincache-worker2 traincache-worker3 traincache-worker4; do
  docker exec "$n" crictl images -q ghcr.io/thewor1d877/traincache/traincache-agentd:v0.9.2
done
```

四行都有输出即导入成功。

### Python 环境

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r bench/requirements.txt
```

venv 放 repo 根目录，`bench/Makefile` 的 python 指向它。后续命令都在激活后的 shell 里执行。torch 与 webdataset 不在清单里，e2e 族要自行装好（CPU 版 torch 即可）；`bench/e2e/build-trainer.sh` 把这两个包打进训练镜像，训练进程在集群内 Pod 里跑，不在宿主机跑。

判据：`python3 -c "import numpy, pandas, boto3, webdataset"` 不报错；跑 e2e 时再 `python3 -c "import torch, webdataset"`。

### kind 集群

集群名 `traincache`，1 个 control-plane 加 4 个 worker，配置在 `bench/k8s/kind-config.yaml`。`make -C bench bench-up` 建这个集群并导入 minio、busybox 两个基础镜像。单独建一次：

```bash
kind create cluster --config bench/k8s/kind-config.yaml
kubectl get nodes
```

`kubectl get nodes` 打印 5 行，STATUS 全为 `Ready`。

按顺序过，每条不过就先修再往下走。

| 项 | 判据 | 怎么查 |

## 拉起与自检

### 拉起

```bash
make -C bench bench-up
```

目标依次做七件事：建集群、部署 MinIO、生成缺的数据、上传桶、拉起控制面与 agentd、挂 tc 限速、跑两次冷读。每步幂等，集群与数据已存在时跳过。数据生成与两次冷读占大部分时间。

末行输出 `== bench-up 完成:装置已拉起并通过冷读验证 ==` 时结束。冷读判定是两次全量读的耗时相对差不超过 10%。

### 自检

```bash
make -C bench bench-doctor
echo $?
```

doctor 只读，逐项打印 PASS、FAIL、WARN，覆盖工具与解释器、Python 依赖、集群与节点、worker 镜像、控制面与 Agent、淘汰证据、MinIO 与桶、tc qdisc、数据目录与磁盘。

判据：输出里没有 FAIL 行，退出码 0。WARN 不阻塞开跑，逐条读原因再决定。

### 查跑分进度

```bash
bash bench/scripts/progress.sh
```

只读，不改任何状态。打印测量 Pod 状态、各 Pod 最后一条训练步、已跑完 Pod 的 `RESULT` 行、MinIO eth0 的限速档位、各格 `summary.csv` 的有效轮数、跑分日志尾部。

跑分进行中另开一个终端跑这条命令即可，不用等装置日志。

### 盯跑分进度

```bash
bash bench/scripts/watch_progress.sh ~/tcd/bench/results ~/tcd/bench/logs/gateway-formal.pid ~/tcd/bench/logs/run-gateway-formal-<时间戳>.log
```

位置参数依次是结果目录、驱动进程的 pid 文件、驱动日志。后台跑时用 `setsid nohup` 挂起，与终端断开不影响。

每 60 秒往 `~/tcd/bench/logs/watch-progress-<时间戳>.log` 追加一行：驱动已运行时长、各格 `summary.csv` 的有效行数与总行数、测量 Pod 与 Agent Pod 的状态计数。有效行指 `void` 不是 true 的行。出现新作废行或失败现场文件（`pod_failed.log`、`measure_errors.log`）时，额外记一行 `EVENT`。驱动进程退出后记一行 `DONE` 并结束。

只读监控，不改任何状态，也不碰驱动进程。

跑分进行中需要连续盯进度时用这条命令；只想看一眼当下状态用 `progress.sh`。

### 拆装置

```bash
make -C bench bench-down
```

拆掉 tc 限速，保留集群与 `~/tcd` 数据。删集群用 `kind delete cluster --name traincache`。

## 数据准备

数据在 `~/tcd/bench/data/`。装置拉起后目录里已有：主数据集 16 片、倾斜清单两个、训练负载 16 片。数据齐备时跑族跳过这些命令。

### 生成

```bash
python3 bench/scripts/synth_dataset.py --count 16
python3 bench/scripts/synth_tilt.py
python3 bench/scripts/synth_train.py
```

| 脚本 | 产物 | 参数 |
|---|---|---|
| `synth_dataset.py` | 16 × 256 MiB 的 tar，落 `dataset/tars`，名 `shard-NNNNN.tar` | `--count` 生成片数，`--start-shard` 起始片号 |
| `synth_tilt.py` | `full-shards.txt` 与 `hot-shards.txt`，落 `tilt` | 无参数，复用主数据集 |
| `synth_train.py` | 16 × 128 MiB，落 `train` | 无参数取 `bench/config.py` 的默认值 |

分片种子只与片号有关。补缺失分片用 `--start-shard 16 --count N`，结果与一次生成逐字节一致。

### 上传

```bash
python3 bench/scripts/upload_bench.py
```

写入 MinIO 的 `bench-b` 桶，已有对象跳过。重写源数据加 `UPLOAD_FORCE=1`。

### 校验

```bash
python3 bench/run.py compare --rho 4 --rate 300 --group traincache-cold --dry-run
ls ~/tcd/bench/data/dataset/tars/shard-*.tar | head -16 | wc -l
du -cb $(ls ~/tcd/bench/data/dataset/tars/shard-*.tar | head -16) | tail -1
sha256sum ~/tcd/bench/data/dataset/tars/shard-00000.tar
```

判据三条。dry-run 打印的数据字节为 4294967296，缓存字节为 1073741824。前 16 片合计约 3.95 GiB，每片实测约 252.6 MiB，比声明的 4 GiB 小约 1.3%；缓存容量仍按声明值除以 ρ 计算。同一片两次生成的 sha256 相同。COND 的规模校验由 `cond.py` 执行，`shards × shard_size_bytes` 必须等于 16 × 268435456，否则判为不合格。

## 跑族

入口 `python3 bench/run.py <族>`。族 ID 十一个：`compare`、`gateway`、`evict`、`evict-mix`、`prefetch`、`warmup`、`switch`、`chaos`、`multiconsumer`、`e2e`、`rangepar`。

每次先加 `--dry-run`。它只打印计划，每行一格：COND 名、数据字节、缓存字节、rate、reps，不碰集群。核对格子数与 ρ 取值后再跑。

产物落 `~/tcd/bench/results/<族 ID>/<COND 名>/`。族间串行，两个族并行会抢 MinIO `eth0` 上的共享令牌桶。全部跑一遍：

```bash
for f in compare gateway evict evict-mix prefetch warmup switch chaos multiconsumer e2e rangepar; do
  python3 bench/run.py "$f" || break
done
```

产物与日志分三个目录放：正式产物在 `~/tcd/bench/results/`，冒烟产物在 `~/tcd/bench/smoke/<时间戳>/`，日志与运行状态文件在 `~/tcd/bench/logs/`。冒烟通过环境变量 `TRAINCACHE_RESULTS_ROOT` 把产物根指向自己的目录，不写进正式产物根；正式轮要换产物根也用这个变量。

### evict-mix 冒烟

混合访问淘汰族正式轮是 9 格 × 5 rep = 45 跑。冒烟把采样数缩到 1，格数不缩：淘汰策略（heat/lru/lfu）与 ρ（2/4/8）两个轴全走一遍，路径与正式轮同源——同一份 COND、同一条 `run.py → run_policy → run_bench` 链路、同一份断言代码。

```bash
bash bench/scripts/run_smoke_evict_mix.sh
```

抽 9 格，每格 1 rep，共 9 跑。族前先 `cold_reset.sh`，每格跑完立即执行硬断言，不符当场终止，不带病跑完。

断言七条，写在脚本里：

| 断言 | 判据 |
|---|---|
| 这轮不作废 | `void` 不是 true |
| 淘汰轮次大于 0 | `evict_rounds_normal + evict_rounds_danger > 0` |
| 两个存活率有值 | `lowfreq_fresh_survive` 与 `highfreq_stale_survive` 非空 |
| 读侧不丢数据 | `read_errors` 与 `queue_timeouts` 都是 0 |
| 字节账自洽 | `sustained_prefetch_bytes + switch_reprefetch_bytes` 与 `prefetch_bytes_run` 的差不超过 max(1 B, 1%) |
| 已知答案探针 | `dataset_bytes` 是 4294967296，`cache_bytes` 是 4294967296 ÷ ρ |
| 这一行属于本格 | `family` 是 evict-mix，`evict_policy` 与 `rho` 与格名对上 |

只验断言不占机时，对既有产物跑一遍：

```bash
bash bench/scripts/run_smoke_evict_mix.sh --assert-only
```

每格跑完把该格的 agentd 日志留档到 `~/tcd/bench/smoke/<时间戳>/agentd-logs/`（agentd 在下一格会被重启，日志随即冲掉），并记录跑前跑后的 agentd Pod UID，作为重启路径被执行过的证据。

冒烟产物落 `~/tcd/bench/smoke/<时间戳>/results/evict-mix/`，不进正式产物根 `~/tcd/bench/results/`。脚本用环境变量 `TRAINCACHE_RESULTS_ROOT` 把产物根指向自己的目录，正式轮的行不会被冒烟行顶掉，正式轮仍按完整 reps 跑。

冒烟不设 `POD_TIMEOUT` 等放宽参数。放宽过装置参数的格在正式轮必须 `--force` 重跑。

脚本自己写 pid 到 `~/tcd/bench/logs/smoke-evictmix.pid`，日志 `~/tcd/bench/logs/smoke-evictmix-<时间戳>.log`，失败格清单 `~/tcd/bench/logs/smoke-evictmix-failures-<时间戳>.txt`。后台跑用 `setsid nohup` 挂起，并按盯跑分进度一节挂哨兵，盯跑分进度一节的第四个位置参数传 `evict-mix` 可以展开逐格明细。

### compare

68 格，204 跑。1000 mbit 与 300 mbit 各 93 跑，100 mbit 18 跑。

```bash
python3 bench/run.py compare --dry-run
python3 bench/run.py compare
python3 bench/run.py compare --rho 2 --rate 300 --group traincache-cold
```

第三条只跑一格。产物 `~/tcd/bench/results/compare/compare-<组态>-rho<ρ>-<带宽>/`。

要重跑整套 traincache 组态时，用 `bench/scripts/rerun_compare.py`。它按带宽降序、同档按 ρ 升序排格子，跳过已完成格（`summary.csv` 有效行数 ≥ reps），产物默认落 `<数据层>/bench/results/compare`：

```bash
python3 bench/scripts/rerun_compare.py --dry-run                      # 只看顺序
python3 bench/scripts/rerun_compare.py --group traincache-cold        # 冷启 15 格
python3 bench/scripts/rerun_compare.py --group traincache-warm        # 暖启 10 格
python3 bench/scripts/rerun_compare.py --out-root <另一个产物根>       # 换结果树
```

判定按组间胜负：逐 ρ 判定，`direct` 在每个带宽档只有 ρ=4 一个代表点，ρ≠4 的格子回退对照同带宽的 ρ=4 格。

跨组比较并行能力前，先测各组 mount 进程到 MinIO 的实际回源连接数。在 juicefs 与 fluid 的测量 Pod 起来并有读流量时，从 kind 节点容器进 MinIO Pod 的网络命名空间数：

```bash
docker exec <minio-node> nsenter --net=/var/run/netns/cni-<uuid> \
  ss -tn state established '( sport = :9000 )'
```

命名空间路径是 `/var/run/netns/cni-<uuid>`，从 MinIO Pod 内 `readlink /proc/self/ns/net` 拿到的是 `net:[<inode>]`，这个形式不能直接传给 `nsenter`。MinIO 容器里没有 `ss`，源站侧的采样只能从 kind 节点容器进网络命名空间做；挂载侧在 JuiceFS mount Pod 内采样，容器里有 `ss`。

分别数 juicefs 与 fluid 挂载 Pod 所在命名空间的连接数，与 TrainCache 的读端连接数对比。两侧读数应当一致，源站侧会多出 MinIO 自身的健康检查连接。Fluid 侧要先把 tar 分片导入挂载点，读分片的同时逐秒采样，连接数在读流量稳定后才收敛。

### gateway

3 格，9 跑。G0 单跑 24 min（直读，2026-11-08 实测 1454 s），G1 单跑 37.5 min（走 agentd，实测 2251 s），G2 单跑 8 min（网关把复制读的重复回源压成一份，2026-11-08 实测 466 s 与 491 s、源站出站 4.49 GB 到 4.65 GB）。读端固定 4，300 mbit，ρ=4。G0 臂的 agent 块缓存关掉，测量 Pod 走 direct 读法直读 MinIO；G1 与 G2 走 agentd，容量 1 GiB。G2 臂的网关按「键+区间」把同一段合并成一次回源并把这一段落进盘上的片段缓存，源站因此只出 1 份。

```bash
python3 bench/run.py gateway --dry-run
python3 bench/run.py gateway
```

产物 `~/tcd/bench/results/gateway/gateway-g<臂号>-r4/`。判定按网关缓存与臂间比较：G2 对 G0 的源站字节比落在 12 ± 5%，越界整轮作废；臂间比较取同格 3 次，G2 分别与 G0、G1 比 makespan，阈值 5%。源站字节只算 Get 路径：G2 臂取 `gateway_bytes`（网关 60 秒汇总的 `bytes` 求和，汇总行带 `aggregate` 标记，不被日志采样器的 60 秒去重丢掉），G0 与 G1 臂取 `origin_egress_bytes`（MinIO 集群指标的 `minio_s3_traffic_sent_bytes` 增量）。Agent 元数据路径直连源站的流量不在口径内。`bench/experiments/report.py` 的网关族判定会直接给出这个比值与带内带外。

### chaos

6 格，18 跑。1000 mbit，ρ 取 1 与 8。

```bash
python3 bench/run.py chaos --dry-run
python3 bench/run.py chaos --fault kill_agent --dry-run
python3 bench/run.py chaos --fault kill_agent
```

第三条按故障单跑，`--fault` 取 `kill_agent`、`tamper_block`、`minio_down`。注入动作由 `bench/chaos/inject/` 下的脚本执行。产物 `~/tcd/bench/results/chaos/chaos-<故障>-rho<ρ>/`。判定按故障逐条二值判：替代 Pod Ready 且 UID 与旧 Pod 不同、RESCAN_PHASE 离开 SAMPLING、隔离块数为 0、观察窗口内 fetch 字节增量不超过单块字节，是 `kill_agent` 的通过条件；`tamper_block` 看 RESCAN_PHASE 走完 FULL_SCAN、`traincache_fetch_requests_total{reason="repair"}` 增量 ≥ 1；`minio_down` 在有 WarmupTask 时看 `status.phase` 出现 Degraded，源站恢复后训练 Pod 重建为 Running 且恢复窗口内 error 增量为 0。

节点丢失按需复现走混沌套件入口，不进 `run.py` 的正式格：

```bash
bash bench/chaos/run.sh --fault node_loss --kubeconfig <本轮副本>
```

脚本停掉目标节点的 kind 容器，等节点 NotReady、WarmupTask 落到 Degraded，再启动容器并等节点 Ready。停容器期间该节点上的 Pod 全部失联，不与其他族并行。

判据只读两条状态线：节点 Ready 条件与 WarmupTask 的 phase。DataSet 的 `accessibleNodes` 只按标签解析、不看节点 Ready，WarmupTask 的 `candidateNodes` 在门控决策后不再更新，两者在节点掉线期间都不变，不能当判据；该节点上 agent Pod 的状态同样不更新——kubelet 随节点容器一起停了，Pod 状态冻结在上报前的取值，要等节点回来才刷新。

门控决策落库后本代不再重算，所以 `phase` 停在 Degraded 不退回，节点回来也不变。

要让任务在预热阶段就进入 Degraded，把 `spec.gate.tMax` 调短即可，默认 10 分钟。

### e2e

3 格，6 跑。每场景 2 跑，跑满预热、3 epoch 训练加一次 checkpoint 落盘与恢复。单跑时长待冒烟实测回填。

python3 bench/run.py e2e

## 产物契约

数据层三个目录各管一件事：正式产物在 `~/tcd/bench/results/`，冒烟产物在 `~/tcd/bench/smoke/<时间戳>/`（`results/` 下是冒烟产物树，`agentd-logs/` 是逐格 agentd 日志留档），日志与运行状态文件在 `~/tcd/bench/logs/`（驱动日志、哨兵进度日志、pid 文件、失败格清单、compare 组态运行日志 `logs/compare/`）。冒烟产物与日志都不写进正式产物根。

每格一个目录 `~/tcd/bench/results/<族 ID>/<COND 名>/`，固定内容如下。

| 路径 | 内容 |
|---|---|
| `summary.csv` | 逐次采样的指标行，每格是 `sampling.reps` 行 |
| `lock.json` | 实际生效参数、镜像 digest、tc 档位、缓存字节 |
| `runs/<组态>-rNN/` | 每次采样一份，含 `per_step_1_w1.jsonl`（逐步 stall）、`run.json`（本轮参数）、`recovery.json`（切换事件） |
| 失败现场 | `pod_failed.log` 或 `measure_errors.log`，只在失败时出现 |
| `ckpt/` | e2e 族另存，含 checkpoint 文件 |
| `run_phase1.json` | e2e 族另存，阶段一的 `run.json` |

对照族、网关族、预取族、预热族、阶段切换族、并行下载族与多消费者族的单格 3 次采样落在 3 个 `runs` 子目录里。淘汰族由 `run_policy.py` 执行，每轮目录直接放在格子根下，名字是 `<COND 名>-rNN-<时间戳>`，里面有 `run.json` 与 `per_step_a.jsonl`、`per_step_b.jsonl`；该轮的 `summary.csv` 在轮目录内的 `compare-<格名>/` 子目录里，整格跑完后各轮有效行汇总到格子根的 `summary.csv`，完成判据与报告读的是格根这份。端到端族也把每轮目录直接放在格子根下，里面有 `run.json`、`per_step_*.jsonl`、`ckpt/` 与 `run_phase1.json`；设了 `PROMETHEUS_URL` 时另有 `series.json`。目录只追加，重跑前按归档步骤处理。

族根 `~/tcd/bench/results/<族 ID>/` 下放该族全部格子。混沌族的格子内是逐轮目录，每轮一份 `summary.txt`，其余族是格子根目录的 `summary.csv`。
