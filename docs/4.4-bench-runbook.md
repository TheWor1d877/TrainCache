# bench 操作手册

## 环境准备

### 宿主机与工具

宿主机跑 Linux，装 Docker、kind、kubectl、git、python3。kind 的 5 个节点是 Docker 容器，共用这台机器。首次准备留 40 GiB 可用磁盘：数据层 4 GiB，MinIO 的 PVC 30 GiB。

```bash
docker info >/dev/null && echo docker-ok
kind version
kubectl version --client
python3 --version
```

四条命令都返回 0 即可。

宿主机不要求免密 sudo。清宿主机页缓存有四条通道，`cold_reset.sh` 按顺序取第一条可用的：root 直跑、`sudo -n`、kind 节点容器内写 `/proc/sys/vm/drop_caches`、`sudo -S` 配 `bench/.sudo-pass`。kind 节点是特权容器、与宿主机共用内核，容器里写的是同一份页缓存，所以装置不依赖密码文件。`bench/.sudo-pass` 只在前三条都不可用时才需要，权限 600。

### 镜像

bench 用五个 Traincache 镜像：controller-manager、webhook、kube-scheduler、traincache-agentd、traincache-gateway。跑 e2e 族再加 traincache-checkpointd。

```bash
./hack/build-images.sh
./hack/kind-load.sh traincache \
  ghcr.io/thewor1d877/traincache/controller-manager:dev \
  ghcr.io/thewor1d877/traincache/webhook:dev \
  ghcr.io/thewor1d877/traincache/kube-scheduler:dev \
  ghcr.io/thewor1d877/traincache/traincache-agentd:dev \
  ghcr.io/thewor1d877/traincache/traincache-gateway:dev
```

每个镜像带 `io.traincache.src-fp` 标签，值是该次构建的源码指纹。`ctrl_up.sh` 比对标签与当前工作树，不一致时拒绝拉起。改过 `agent/`、`controller/`、`core/`、`gateway/`、`checkpoint/` 里任一文件后，重跑上面两条命令。

导入到四个 worker 的判据：

```bash
for n in traincache-worker traincache-worker2 traincache-worker3 traincache-worker4; do
  docker exec "$n" crictl images -q ghcr.io/thewor1d877/traincache/traincache-agentd:dev
done
```

四行都有输出即导入成功。

```bash

source .venv/bin/activate

kubectl get nodes
```

`kubectl get nodes` 打印 5 行，STATUS 全为 `Ready`。

## 拉起与自检

### 拉起

```bash
make -C bench bench-up
```

目标依次做七件事：建集群、部署 MinIO、生成缺的数据、上传桶、拉起控制面与 agentd、挂 tc 限速、跑两次冷读。每步幂等，集群与数据已存在时跳过。数据生成与两次冷读占大部分时间。

末行输出 `== bench-up 完成:装置已拉起并通过冷读验证 ==` 时结束。冷读判定是两次全量读的耗时相对差不超过 10%。

### 自检

```bash
make -C bench bench-doctor
echo $?
```

doctor 只读，逐项打印 PASS、FAIL、WARN，覆盖工具与解释器、Python 依赖、集群与节点、worker 镜像、控制面与 Agent、淘汰证据、MinIO 与桶、tc qdisc、数据目录与磁盘。

判据：输出里没有 FAIL 行，退出码 0。WARN 不阻塞开跑，逐条读原因再决定。

### 查跑分进度

```bash
bash bench/scripts/progress.sh
```

只读，不改任何状态。打印测量 Pod 状态、各 Pod 最后一条训练步、已跑完 Pod 的 `RESULT` 行、MinIO eth0 的限速档位、各格 `summary.csv` 的有效轮数、跑分日志尾部。

跑分进行中另开一个终端跑这条命令即可，不用等装置日志。

### 拆装置

```bash
make -C bench bench-down
```

拆掉 tc 限速，保留集群与 `~/tcd` 数据。删集群用 `kind delete cluster --name traincache`。

## 数据准备

数据在 `~/tcd/bench/data/`。装置拉起后目录里已有：主数据集 128 片（本装置读前 16 片）、倾斜清单两个、训练负载 16 片。数据齐备时跑族跳过这些命令。

### 生成

```bash
python3 bench/scripts/synth_dataset.py --count 16
python3 bench/scripts/synth_tilt.py
python3 bench/scripts/synth_train.py
```

| 脚本 | 产物 | 参数 |
|---|---|---|
| `synth_dataset.py` | 16 × 256 MiB 的 tar，落 `dataset/tars`，名 `shard-NNNNNN.tar` | `--count` 生成片数，`--start-shard` 起始片号 |
| `synth_tilt.py` | `full-shards.txt` 与 `hot-shards.txt`，落 `tilt` | 无参数，复用主数据集 |
| `synth_train.py` | 16 × 128 MiB，落 `train` | 无参数取 `bench/config.py` 的默认值 |

分片种子只与片号有关。补缺失分片用 `--start-shard 16 --count N`，结果与一次生成逐字节一致。

### 上传

```bash
python3 bench/scripts/upload_bench.py
```

写入 MinIO 的 `bench-b` 桶，已有对象跳过。重写源数据加 `UPLOAD_FORCE=1`。

### 校验

```bash
python3 bench/run.py compare --rho 4 --rate 300 --group traincache-cold --dry-run
ls ~/tcd/bench/data/dataset/tars/shard-*.tar | head -16 | wc -l
du -cb $(ls ~/tcd/bench/data/dataset/tars/shard-*.tar | head -16) | tail -1
sha256sum ~/tcd/bench/data/dataset/tars/shard-00000.tar
```

判据三条。dry-run 打印的数据字节为 4294967296，缓存字节为 1073741824。前 16 片合计约 3.95 GiB，每片实测约 252.6 MiB，比声明的 4 GiB 小约 1.3%；缓存容量仍按声明值除以 ρ 计算。同一片两次生成的 sha256 相同。COND 的规模校验由 runner 开跑前执行，`shards × shard_size_bytes` 必须等于 16 × 268435456，否则整格拒绝。

## 跑族

入口 `python3 bench/run.py <族>`。族 ID 十个：`compare`、`gateway`、`evict`、`prefetch`、`warmup`、`switch`、`chaos`、`multiconsumer`、`e2e`、`rangepar`。

每次先加 `--dry-run`。它只打印计划，每行一格：COND 名、数据字节、缓存字节、rate、reps，不碰集群。核对格子数与 ρ 取值后再跑。

产物落 `~/tcd/bench/results/<族 ID>/<COND 名>/`。族间串行，两个族并行会抢 MinIO `eth0` 上的共享令牌桶。全部跑一遍：

```bash
for f in compare gateway evict prefetch warmup switch chaos multiconsumer e2e rangepar; do
  python3 bench/run.py "$f" || break
done
```

### compare

68 格，204 跑，26.4 h。1000 mbit 与 300 mbit 各 93 跑，单跑 6.0 与 7.5 min；100 mbit 18 跑，单跑 18.4 min。

```bash
python3 bench/run.py compare --dry-run
python3 bench/run.py compare
python3 bench/run.py compare --rho 2 --rate 300 --group traincache-cold
```

第三条只跑一格。产物 `~/tcd/bench/results/compare/compare-<组态>-rho<ρ>-<带宽>/`。判定按组间胜负：逐 ρ 判定，`direct` 只有 ρ=4 一个代表点，ρ≠4 的格子回退对照同带宽的 ρ=4 格。

跨组比较并行能力前，先测各组 mount 进程到 MinIO 的实际回源连接数。在 juicefs 与 fluid 的测量 Pod 起来并有读流量时，从 kind 节点容器进 MinIO Pod 的网络命名空间数：

```bash
docker exec <minio-node> nsenter --net=/var/run/netns/cni-<uuid> \
  ss -tn state established '( sport = :9000 )'
```

命名空间路径是 `/var/run/netns/cni-<uuid>`，从 MinIO Pod 内 `readlink /proc/self/ns/net` 拿到的是 `net:[<inode>]`，这个形式不能直接传给 `nsenter`。MinIO 容器里没有 `ss`，源站侧的采样只能从 kind 节点容器进网络命名空间做；挂载侧在 JuiceFS mount Pod 内采样，容器里有 `ss`。

分别数 juicefs 与 fluid 挂载 Pod 所在命名空间的连接数，与 TrainCache 的读端连接数对比。两侧读数应当一致，源站侧会多出 MinIO 自身的健康检查连接。Fluid 侧要先把 tar 分片导入挂载点，读分片的同时逐秒采样，连接数在读流量稳定后才收敛。

### gateway

3 格，9 跑，3.5 h。G0 单跑 24 min（直读，2026-11-08 实测 1454 s），G1 单跑 37.5 min（走 agentd，实测 2251 s），G2 单跑 8 min（网关把复制读的重复回源压成一份，2026-11-08 实测 466 s 与 491 s、源站出站 4.49 GB 到 4.65 GB）。读端固定 4，300 mbit，ρ=4。G0 臂的 agent 块缓存关掉，测量 Pod 走 direct 读法直读 MinIO；G1 与 G2 走 agentd，容量 1 GiB。G2 臂的网关按「键+区间」把同一段合并成一次回源并把这一段落进盘上的片段缓存，源站因此只出 1 份。

```bash
python3 bench/run.py gateway --dry-run
python3 bench/run.py gateway
```

产物 `~/tcd/bench/results/gateway/gateway-g<臂号>-r4/`。判定按网关缓存与臂间比较：G2 对 G0 的源站字节比落在 12 ± 5%，越界整轮作废；臂间比较取同格 3 次，比 makespan 与源站字节，阈值 5%。源站字节只算 Get 路径：G2 臂取 `gateway_bytes`（网关 60 秒汇总的 `bytes` 求和，汇总行带 `aggregate` 标记，不被日志采样器的 60 秒去重丢掉），G0 与 G1 臂取 `origin_egress_bytes`（MinIO 集群指标的 `minio_s3_traffic_sent_bytes` 增量）。Agent 元数据路径直连源站的流量不在口径内。`bench/experiments/report.py` 的网关族判定会直接给出这个比值与带内带外。

### chaos

6 格，18 跑，1.8 h，单跑 6.0 min。1000 mbit，ρ 取 1 与 8。

```bash
python3 bench/run.py chaos --dry-run
python3 bench/run.py chaos --fault kill_agent --dry-run
python3 bench/run.py chaos --fault kill_agent
```

第三条按故障单跑，`--fault` 取 `kill_agent`、`tamper_block`、`minio_down`。注入动作由 `bench/chaos/inject/` 下的脚本执行。产物 `~/tcd/bench/results/chaos/chaos-<故障>-rho<ρ>/`。判定按故障逐条二值判：替代 Pod Ready 且 UID 与旧 Pod 不同、RESCAN_PHASE 离开 SAMPLING、隔离块数为 0、观察窗口内 fetch 字节增量不超过单块字节，是 `kill_agent` 的通过条件；`tamper_block` 看 RESCAN_PHASE 走完 FULL_SCAN、`traincache_fetch_requests_total{reason="repair"}` 增量 ≥ 1；`minio_down` 看 WarmupTask `status.phase` 出现 Degraded、源站恢复后训练 Pod 重建为 Running 且恢复窗口内 error 增量为 0。

节点丢失按需复现走混沌套件入口，不进 `run.py` 的正式格：

```bash
bash bench/chaos/run.sh --fault node_loss --kubeconfig <本轮副本>
```

脚本停掉目标节点的 kind 容器，等节点 NotReady、WarmupTask 落到 Degraded，再启动容器并等节点 Ready。停容器期间该节点上的 Pod 全部失联，不与其他族并行。

判据只读两条状态线：节点 Ready 条件与 WarmupTask 的 phase。DataSet 的 `accessibleNodes` 只按标签解析、不看节点 Ready，WarmupTask 的 `candidateNodes` 在门控决策后不再更新，两者在节点掉线期间都不变，不能当判据；该节点上 agent Pod 的状态同样不更新——kubelet 随节点容器一起停了，Pod 状态冻结在上报前的取值，要等节点回来才刷新。

门控决策落库后本代不再重算，所以 `phase` 停在 Degraded 不退回，节点回来也不变。

要让任务在预热阶段就进入 Degraded，把 `spec.gate.tMax` 调短即可，默认 10 分钟。

e2e 实测期间临时部署 Prometheus 抓 agentd 与 MinIO 指标，跑完拆除：

```bash
docker pull prom/prometheus:v2.53.0 && kind load docker-image prom/prometheus:v2.53.0 --name traincache
kubectl apply -f bench/k8s/prometheus.yaml
kubectl -n traincache port-forward svc/traincache-bench-prometheus 9090:9090 &
PROMETHEUS_URL=http://127.0.0.1:9090 python3 bench/run.py e2e
kubectl delete -f bench/k8s/prometheus.yaml
```

设了 `PROMETHEUS_URL` 时，collect 在每轮结束后把 25 条原始序列按 run 窗口导出到该轮目录的 `series.json`，计数器存原始值，速率在报告侧算。序列持久化靠这份导出，不靠 Prometheus 的 TSDB——存储是 emptyDir，拆部署即丢。

## 看结果

### summary.csv

每行一次采样，每格 3 行，e2e 族 2 行。列按用途分组。

| 列 | 含义 |
|---|---|
| `family` `rho` `rate` `group` `load` `gateway` `rep` `cond` `run_id` | 定位一行属于哪个族、哪个 ρ、哪档带宽、哪个组态、哪种负载、网关开关、第几次采样 |
| `status` `void` `reason` | `status=ok` 且 `void=false` 的行才进汇总；整轮作废时 `void=true` 并在 `reason` 里写明原因，作废轮不进汇总 |
| `startup_makespan` `total_makespan` `post_pod_s` `stall_ratio` `stall_p90` | 启动与全程 makespan 取 `t_first_step − t_submit` 与 `t_last_step − t_submit`，就绪后阶段取 `t_last_step − t_pod_ready`；`stall_ratio` 是 `wait_s ÷ step_s` 的均值，`stall_p90` 是它的 90 分位 |
| `hit_rate` `hit_ratio_startup` `hit_ratio_steady` `hit_ratio_switch` `source_saving_ratio` | 命中率取 `1 − demand_miss_bytes ÷ read_bytes` 并按 startup、steady、switch 分列；`source_saving_ratio` 取 `1 − fetch_bytes_run ÷ read_bytes` |
| `startup_warmup_bytes` `sustained_prefetch_bytes` `switch_reprefetch_bytes` `fetch_bytes_run` | 三笔字节成本与回源总量，后两项之和应等于 `prefetch_bytes_run` |
| `cache_bytes` `peak_resident_bytes` `chunk_size_bytes` `prefetch_lookahead` `evict_policy` `gate_mode` | 该轮生效的配置 |
| `cache_dir_peak_bytes` `cache_peak_ratio` `evict_blocks_run` | 缓存峰值字节、峰值除以声明容量的倍率、run 窗口内的淘汰块数 |

## 排障

### tc 没生效

现象：100 mbit 档的冷读跑出 600 MB/s 以上，正常应在 11.95 MB/s 附近。

```bash
make -C bench bench-doctor
```

看「tc qdisc」节。判据：MinIO Pod 的 `eth0` 上有 tbf，rate 与本档一致，burst 与本档期望值差在 ±1% 内。没有 qdisc 就重挂：

```bash
bash bench/scripts/tc_apply.sh 100mbit 20ms --target minio
```

单流限速档的形态多两层：根是 htb（类给聚合带宽），htb 的类下挂 netem，netem 自带的 class 下挂 fq，fq 的 maxrate 给出每条连接的上限。tbf 不是 classful，挂不了子 qdisc，所以这一档不能把 fq 挂在 tbf 之下。回读时 `tc qdisc show` 给 htb、netem、fq 三条，`tc class show` 给 htb 的类（rate 与 ceil 相同才算硬上限）。节点上没加载 `sch_fq` 模块时挂 fq 报错，先 `modprobe sch_fq`。

MinIO Pod 重建后 netns 换新，qdisc 随之消失，重挂一次。

### 冷态没生效

现象：某轮实验的冷读明显快于线速，或两轮冷读的耗时差超出 10%。

每组实验前跑 `bash bench/scripts/cold_reset.sh`，它做三件事：清宿主机页缓存、重启 MinIO、重挂 tc。页缓存没清掉时源站对象还在宿主机缓存里，读回不经过网络。

清页缓存的通道依次是 root 直跑、`sudo -n`、kind 节点容器、`sudo -S` 配 `bench/.sudo-pass`。四条都不可用时脚本以非零退出，这轮实验作废，补齐通道后重跑。`make -C bench bench-doctor` 的「数据目录与磁盘」一节打印当前可用的通道。

### 单流限速验不出

现象：并行下载族跑完，两臂的 makespan 没差，或开臂反而更慢。单流上限没生效时，4 路并行共用一份带宽，并行没有收益。

形态在 `bench/scripts/tc_apply.sh` 里已经实现，`--per-conn` 给单流上限时形态是 htb（类给聚合带宽）→ netem（时延与丢包）→ fq（maxrate 给单流上限）。`bash bench/scripts/tc_apply.sh --self-test` 只验命令形态，不验真机效果。放开集群后验三件事：

1. `sch_fq` 模块能加载：`modprobe sch_fq` 不报错。
2. qdisc 树回读是 htb → netem → fq 三层，fq 行里有 maxrate，htb 类的 rate 与 ceil 相同。
3. 单流限速可测：一条连接与四条连接读同一分片，速率差要能测出来，一条连接不超过 32 mbit，四条连接之和明显更大。

形态没挂对就跑 24 跑是白跑。

### 缓存峰值倍率超声明容量

现象：`summary.csv` 的 `cache_peak_ratio` 大于 1。

声明容量在当前实现下是软上限，峰值可以超过声明值，倍率只记不判，判定看「淘汰生效」那条（`evict_blocks_run` 为 0 且倍率大于 1.05 时整轮作废）。成因在 agent 侧：`agent/collector` 的 `ListForEviction()` 只返回被 `Open` 或 `Touch` 过的指纹，预取写入但还没被训练消费掉的块不在候选集里。

`cache_peak_ratio` 列要在同一批 COND 上重测一遍，旧产物里没有这一列，且旧产物的 agent 镜像早于这一列的加入，峰值成因没在当前代码上验证过。

### ImagePullBackOff

```bash
kubectl -n traincache get pod
kubectl -n traincache describe pod <pod> | sed -n '/Events/,$p'
docker images | grep traincache
```

判据：事件里写 `ErrImagePull` 或 `ImagePullBackOff`，且宿主 `docker images` 里没有该 tag。处理：先 `./hack/build-images.sh <组件>`（或 `docker pull <镜像>`），再 `./hack/kind-load.sh traincache <镜像>`，最后 `make -C bench bench-up` 重拉控制面。

另一种情形是镜像在宿主上存在、节点上却拉不到，而守护集引用的名字与清单不一致。先比对两边：

```bash
kubectl -n traincache get ds traincache-agentd -o jsonpath='{.spec.template.spec.containers[0].image}'
docker exec traincache-worker crictl images -q ghcr.io/thewor1d877/traincache/traincache-agentd:dev
```

守护集引用必须是 `ghcr.io/thewor1d877/traincache/traincache-agentd:dev` 这类全名，与 `hack/kind-load.sh` 装进节点的名字一致。引用是裸名（例如 `traincache-agentd:dev`）时节点上并没有这个名字，守护集滚动更新必然拉不到镜像。控制面脚本会比对集群里的镜像引用与清单渲染结果，不一致就重新应用清单修正；单独跑 `kubectl apply -k controller/deploy` 同样能修正。

### 训练 Pod 正常跑完却被记成 pod_failed

现象：`summary.csv` 的 `void` 为 `True`、`reason` 为 `pod_failed`，但 `kubectl -n traincache logs <pod>` 里有完整的 `RESULT` 行，`kubectl get pod` 显示 `Succeeded`。

原因：装置等训练 Pod 结束有上限（`POD_TIMEOUT`，默认 1800 s），到点就把这一轮记成作废。低带宽档与复制读的族天生就跑得久——traincache-cold 100 mbit 档 3 epoch 的字节地板 1030 s，实测全程约 1990 s；复制读 4 个读端读同一批分片，源站要出 4 份副本，300 mbit 下传输地板就是 1374 s。闸门按单读端算就会把正常推进的 run 截掉。

查 Pod 实际耗时：

```bash
kubectl -n traincache get pods -l app=train-job \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.status.startTime}{"\t"}{.status.containerStatuses[0].state.terminated.finishedAt}{"\n"}{end}'
```

处理：闸门按该格态的源站字节地板推导（`bench/compare/run_bench.py` 的 `pod_timeout_s`）：倾斜组态取地板 × `TILT_TIMEOUT_HEADROOM`（默认 4）；traincache 组态取 max(常量, 地板 × `TRAINCACHE_TIMEOUT_HEADROOM`（默认 4）)；复制读的族地板乘读端数，取 max(常量, 地板 × `REPLICATION_TIMEOUT_HEADROOM`（默认 2）)。冒烟要临时放宽时给 `POD_TIMEOUT` 环境变量，显式值优先。

判据：重跑后 `summary.csv` 的 `void` 为 `False`、`status` 为 `ok`。

### 网关臂的 agent 缓存没关掉

现象：G0 臂的 agentd 日志里有淘汰记录（「超危险线,激进淘汰」），源站出站字节远少于 4 份，`lock.json` 的 `cell.cache_bytes` 不是 0。

原因：COND 写 `cache.enabled=false`，但装置没把「缓存关掉」这件事告诉运行时——不下发容量时，装置按缺省 ρ=4 给 agentd 1 GiB。这一臂名义上关缓存，实际跑的是「无网关 + 1 GiB 缓存」，和 G1 塌成同一配置，消融轴失效。

处理：`bench/experiments/cond.py` 的 `cond_to_env` 在 `cache.enabled` 为 false 时显式下发 `TRAINCACHE_CACHE_CAPACITY_BYTES=0`；多读端路径据此改走直读（HTTP 直读 MinIO，不挂 agentd 的缓存目录与订单目录）。判据：`lock.json` 的 `cell.cache_bytes` 为 0，agentd 日志没有淘汰记录，测量 Pod 的 env 里有 `TRAINCACHE_DIRECT_READ=1`。

### 读队列断供

现象：`summary.csv` 的 `reason` 是 `read_queue_timeout`，Pod 日志里有 `ERROR epoch=1 step=0: read queue empty for 300.0s`，该 Pod 提前结束、`total_makespan` 只有正常值的一半左右，其余 Pod 正常。

原因：预热与训练读抢下载额度。预热把下载任务槽占满时，训练打开第一块要等预热积压跑完；门控在预热刚开始、任何一个节点报上一块时就放行，训练启动窗口里的读正好撞上这段积压。300 mbit 档每秒只有 37.5 MB，预热积压几百块就能把首读拖过 300 秒。

处理：先看 agentd 的预热下载汇总，确认训练启动时预热是否还在跑；再看门控 decision 的 reason 是不是 `min_progress_any_node`。预热与补块的准入分档、补块插队、门控最小进展比例三处一起决定这一格还会不会断供。

判据：重跑后 `queue_timeouts` 为 0，四个 Pod 的 `total_makespan` 彼此接近。

## 产物契约

每格一个目录 `~/tcd/bench/results/<族 ID>/<COND 名>/`，固定内容如下。

| 路径 | 内容 |
|---|---|
| `summary.csv` | 逐次采样的指标行，每格是 `sampling.reps` 行 |
| `lock.json` | 实际生效参数、镜像 digest、tc 档位、`K_cache`、cache 峰值字节 |
| `runs/<组态>-rNN/` | 每次采样一份，含 `per_step_1_w1.jsonl`（逐步 stall）、`run.json`（本轮参数）、`recovery.json`（切换事件）；e2e 设 `PROMETHEUS_URL` 时另有 `series.json`（原始指标序列） |
| 运行日志 | 装置侧与被测侧的原始输出 |
| `checkpoint/` | e2e 族另存，含两轮运行的 checkpoint 与 `lock.json` |

单格 3 次采样对应 3 个 `runs` 子目录，e2e 族 2 个。目录只追加，重跑前按归档步骤处理。

族根 `~/tcd/bench/results/<族 ID>/` 下放该族全部格子。混沌族的格子内是逐轮目录，每轮一份 `summary.txt`，其余族是格子根目录的 `summary.csv`。
