### D1 文档编号

**结论**：新建 `docs/8.1 design.md`、`docs/8.2 plan.md`、`docs/8.3 decisions.md`；`docs/8.0 Controller & Scheduler.md` 零改动（默认；用户授权后可改 8.0，见 Q19）。

**为什么**：沿用 6.x/7.x 的"基线/实现契约"分层。`.0` 为用户基线、禁改（见 docs-versioning-convention）；基线缺陷由用户裁决修正。

**约束与影响**：
- M0 判据：`git hash-object` 8.0 与启动时记录值一致（该文件启动前已有用户改动，不以 `git diff` 判空）

### D2 工程形态

**结论**：新增独立 Go module `traincache/controller`，加入根 `go.work`；含 `cmd/controller-manager`、`cmd/webhook`、`cmd/scheduler` 三个入口。

**为什么**：备选是拆两个 module（隔离更彻底但共享类型需公共包）或塞进 agent（控制面与节点面混淆）。选独立 module 是因为控制面依赖 k8s 客户端与调度框架，与 agent 依赖差异大。

**约束与影响**：
- `cd controller && go build ./...`；`go work` 列表含三个 module

### D3 CRD 约定

**结论**：group `traincache.io`、version `v1alpha1`；`DataSet` 与 `WarmupTask` 均为 Namespaced；只开 status 子资源，不定义 scale；跨对象引用仅限同 namespace；`spec.podCount`/`spec.dataSetRef` 不可变；不管理 Job/Pod 生命周期（2026-10-20 修订）。

**为什么**：基线开头称 status/scale 解耦但后文只有 status（G9）；v1 不需要水平扩缩语义，Pod 生命周期归训练侧。

**约束与影响**：
- CRD YAML 断言无 scale；跨 namespace 引用在 webhook 校验中拒绝；更新 `podCount`/`dataSetRef` 被拒

### D4 块模型

**结论**：`spec.chunkSize int64` 字节 + `spec.shards[]{name,count,lastChunkSize}`；`totalChunks=Σcount`；全局块号按 spec 顺序累计，固化在 `status.blockLayout[].startChunk`。

**为什么**：备选是 `resource.Quantity`（序列化友好但每次计算需解析，agent/core 全用 int64）。选 int64，避免控制器引入第二套单位。

**约束与影响**：
- M2 单测：跨 shard 累计、`Σcount=totalChunks`、区间无缝

### D5 readinessTable 语义

**结论**：status 中存 `[][]int32` **计数**（窗口内就绪块数），比例一律现算 `rate=ready/K_i`；门控用整数判据 `required=floor(threshold*K_i)`（见 D26），`rate` 仅用于观测与展示（2026-10-20 修订）。

**为什么**：基线 G6 计数/比例并存。计数无损、可审计；比例随 K 变化不可持久化；浮点 rate 不适合作为放行裁决。

**约束与影响**：
- M5 单测：K=1/8/1024 下 rate 计算与表值；门控断言只依赖 `ready` 与 `required`

### D6 **作废 2026-10-20（由 D25 取代：K 单一窗口）** K 与 W 分离

**结论**：原结论：`PodDetail.K` 是启动窗口（门控分母）；`ScorePolicy.Window` 是评分窗口；二者独立配置，不要求相等（已作废，见 D25）。

**为什么**：原理由：基线 G7 曾按双窗口理解；双窗口配置面与解释成本高，统一后由 D25 取代。

**约束与影响**：原验证作废；见 D25。

### D7 **作废 2026-10-20（由 D30 取代：s3-access 人工标签）** 可达节点口径

**结论**：原结论：`DataSet.spec.accessibleNodeSelector` 是唯一事实来源，解析结果写 `status.accessibleNodes`；Node 标签 `traincache.io/s3-access` 只用于人工粗筛/排障，不参与控制器判定（已作废，见 D30）。

**为什么**：原理由：基线 G8 曾按 selector 唯一事实来源实现；用户明确标签由人工维护且 selector 可选，由 D30 取代。

**约束与影响**：原验证作废；见 D30。

### D8 Pod 关联

**结论**：新增 `spec.targetRef{apiVersion,kind,name,podLabelSelector}` 与 `PodDetail.Index`；`Index` 必须为 `0..PodCount-1` 连续；Pod 通过 ordinal 映射到 `PodDetail`。

**为什么**：基线 G2 未定义发现方式。没有稳定映射，readiness 无法按 Pod 归属。

**约束与影响**：
- M2 校验；M9 webhook 序号推导测试

### D9 Gate 注入

**结论**：新增 MutatingWebhook；匹配 `objectSelector: traincache.io/warmup=enabled`；注入固定 gate `traincache.io/warmup`、annotation `traincache.io/warmup-task` 与 `traincache.io/pod-index`；`failurePolicy: Ignore`。

**为什么**：SchedulingGate 只能在创建时加入，Controller 事后只能摘（G1）。备选"要求用户模板自带 gate"把配置负担外推且易错。Ignore 的选择：webhook 故障不阻塞训练，代价是静默降级，由 `GateInjectionDegraded` 条件兜底。

**约束与影响**：
- M9 单测 + M11 e2e：无 gate 时 Pending、放行后 Running

### D10 Pod 序号推导

**结论**：优先 Pod label `batch.kubernetes.io/job-completion-index`；其次 StatefulSet ordinal（Pod 名最后一段）；都失败则不注入并记事件 `WarmupTaskMappingFailed`。

**为什么**：序号必须可由 webhook 独立、确定地算出；不依赖控制器回填（回填会与创建竞争）。

**约束与影响**：
- M9 表驱动：Job/StatefulSet/裸 Pod

### D11 Agent 契约

**结论**：扩展现有 `traincache.agent.v1.PreheatService`：进度查询复用 `GetPreheatStatus`，不新增 `GetPreheatProgress`；`PreheatStatus` 追加 `generation=12`、`seq=13`、`ready_bitmap=14`，`SubmitPreheatRequest` 追加 `generation=8`；新增 `UpdatePreheat`/`CancelPreheat` 两 RPC；位序=请求 `chunks` 顺序，8.x 必须显式 `chunks`；`ReportBlocks` 保持 Unimplemented、8.x 不使用（2026-10-20 修订）。

**为什么**：备选：新建 controlplane proto（双契约维护成本）、Agent→Controller 推送（需反向连接与服务发现，且 agent 现为服务端）。拉取模型方向与现有 RPC 一致，位图挂在既有状态响应上。

**约束与影响**：
- M3 agent 测试；M4/M5 fake server；7.1 附录 A 与 8.1 §12.1 逐字一致

### D12 幂等与陈旧

**结论**：`task_id="<namespace>/<name>/p<index>"`；`generation=metadata.generation`；Agent 对低 generation 返回 `FailedPrecondition`；`UpdatePreheat` 全量替换 `chunks` 并重定义位序，`seq` 单调递增；`CancelPreheat` 仅标记、不保证停止在途 P0；Cancel 后同 generation 再 Submit 视为新任务（2026-10-20 修订）。

**为什么**：重复 reconcile、重启、乱序响应是常态；以 generation 单调性做唯一裁决依据，seq 解决同代际内位图新鲜度。（**幂等**=同一个请求发两遍结果一样，不会重复建预热任务）

**约束与影响**：
- M3 单测：陈旧/重复/取消后重建/全量替换；M5 乱序响应

### D13 门控参数位置

**结论**：`spec.gate{threshold,gapMin,slopeMin,tMax,minInterval}` 与 `spec.score{halfLife,cutoff}`；示例默认：`threshold=0.9`、`gapMin=0.1`（比例）、`slopeMin=0`（比例/秒）、`tMax=10m`、`minInterval=10s`、`halfLife=2·K_i`、`cutoff=8·K_i`；删除 `window=max(K_i)`，K 为 per-Pod（2026-10-20 修订）。

**为什么**：基线只有符号没有来源（O2）。参数必须可声明、可回滚；默认值只是示例，生产由用户覆盖；gapMin/slopeMin 单位显式化避免与块数混淆。

**约束与影响**：
- CRD 校验：范围检查（0~1、非负）；M7 边界测试；单位注释与默认值断言

### D14 **作废（由 D38 取代：门控恢复存在量词）** 条件①判定面

**结论**：原结论：使用 GWAA 的**分配节点**上该 Pod 的 rate，而非"任意候选节点"（已作废，见 D38）。

**为什么**：原理由：基线写"存在候选节点达标"。用任意节点会在分配节点未就绪时放行，导致 Pod 落到未预热节点。更严格且与 D32 的分配面一致。

**约束与影响**：原验证作废；见 D38。

### D15 条件②采样

**结论**：`FirstReadyAt` 取首次出现任一 Pod 达标的时间，写入 `Condition FirstReady`；每个未达标 Pod 需两个间隔 ≥ `minInterval` 的样本才计算 slope；样本不足视为不满足；条件②为边际收益判据：等待价值随 gap 增大、slope 降低而下降，故 `gap>gapMin && slope<slopeMin` 时触发降级（Released），条件③ `tMax` 为绝对上限（2026-10-20 修订）。

**为什么**：基线 G11 未定义起点。固定"首次达标"避免交错达标反复重置；采样不足不误放行；②③分工避免把超时当收益判据。

**约束与影响**：
- M7 时钟注入：交错达标、单样本、零间隔；②先于③触发的用例

### D16 **作废 2026-10-20（由 D32 取代：随机并列）** GWAA 并列与回退

**结论**：原结论：按 `c_ij` 最大，并列取节点名字典序最小；冲突保留 `c_ij-secondBest_i` 较大者，仍并列取 Pod 序号较小者；最多 P 轮，不收敛则回退首次贪心（已作废，见 D32）。

**为什么**：原理由：基线 G12 曾要求并列可裁决；字典序会引入系统性偏置，由 D32 取代。

**约束与影响**：原验证作废；见 D32。

### D17 **作废 2026-10-20（由 D27 取代：每任务键）** Node annotation

**结论**：原结论：单键 `traincache.io/scores` 存全任务 JSON，读-改-写，冲突重试 5 次（已作废，见 D27）。

**为什么**：原理由：多 WarmupTask 共节点时单键互相覆盖、体积无界，由 D27 的每任务独立键取代。

**约束与影响**：原验证作废；见 D27。

### D18 缺分行为

**结论**：Scheduler 在 Pod 注解缺失、Node 注解缺失、条目缺失、JSON 损坏、超 TTL 时返回 0，且 `Status` 为 nil。

**为什么**：备选：返回 Unschedulable。会让 controller 故障演变为集群不可调度；返回 0 只影响落点偏好，读路径仍可回源。

**约束与影响**：
- M10 单测：五类缺失均 0 且不拒绝

### D19 分数公式

**结论**：`w(i)=1(i<K_i)`、`0.5^((i-K_i)/H)(K_i≤i<C)`、`0(i≥C)`；`S=round(100*Σw·ready/Σw)`，`Σw=0` 时 0；NormalizeScore 按最大分缩放至 100（2026-10-20 修订：W→K_i）。

**为什么**：基线只有符号。0~100 与 NormalizeScore 的约定一致；整数便于 annotation 存储；K_i 为每 Pod 启动窗口，与 D25 一致。

**约束与影响**：
- M8 边界 i=K_i-1/K_i/C-1/C；M10 全 0/单点/多点

### D20 日志契约

**结论**：标准库 `slog` + `JSONHandler`；`internal/logging` 仅 `New/Into/From`；字段固定 §6.5 集合；每 reconcile 生成 `request_id`；跨进程用 `task_id+node+generation` 关联。

**为什么**：agent 已用 slog 且无第三方；9.0 规范缺失（Q8），先冻结最小契约，待 9.0 补齐后对齐。

**约束与影响**：
- M12 日志断言测试；grep 脱敏

### D21 日志为硬性验收

**结论**：每个里程碑必须包含日志点实现与至少一条日志断言测试；缺失则里程碑不通过。

**为什么**：用户明确要求把"关键位置记录日志"作为硬性任务，不可后补。

**约束与影响**：
- 8.2 §14 判据②；每个 M 的判据含日志项

### D22 core 复用边界

**结论**：Controller 只读复用 `core/objectstore`、`core/index` 的导出符号；不新增 core 接口、不改 core 代码。

**为什么**：快照/键布局已有唯一实现，重复实现会产生第二套事实。

**约束与影响**：
- M2 依赖图检查；core 测试零改动

### D23 选主

**结论**：`CONTROLLER_LEADER_ELECTION` 默认 `false`；生产建议开启；webhook 独立进程不参与选主。

**为什么**：单副本开发简单；多副本时两个控制器同时下发会造成重复 RPC（幂等可兜底但浪费带宽）。

**约束与影响**：
- M11 清单可开启；M12 重启测试

### D24 并发与时钟

**结论**：每个 controller `MaxConcurrentReconciles=1`；状态全部落 CRD，内存仅 rateHistory 与连接池；所有时间比较用注入的 `Now func() time.Time`。

**为什么**：串行化避免同对象竞争；内存态最少化使重启可恢复；注入时钟使门控可测。

**约束与影响**：
- M5/M7 并发与时钟测试；M12 重启 e2e

### D25 K 单一窗口（取代 D6）

**结论**：启动窗口与评分窗口统一为每 Pod 的 `K_i`（`PodDetail.K`）；删除 `ScorePolicy.Window`；门控与全局衰减评分都只用 `K_i`（2026-10-20）。

**为什么**：双窗口配置面与解释成本高；单窗口使"能否放行"和"落点偏好"共用同一事实，且与 8.x 冻结口径一致。

**约束与影响**：
- M7/M8 单测：CRD 无 `window` 字段；不同 `K_i` 的 Pod 各自门控与评分正确

### D26 整数门控与 required 的 0/1 钳制（G6）

**结论**：`required=floor(threshold*K_i)`；若 `threshold>0` 且结果为 0 则取 1；放行判据为 `ready>=required`。示例 K=8、threshold=0.8→required=6；浮点 `rate` 仅观测。

**为什么**：浮点比较受精度与采样抖动影响；整数门槛可审计、可复现；0→1 钳制避免小窗口因向下取整永远无法放行。

**约束与影响**：
- M7 表驱动：K=1/8/1024、threshold=0/0.8/1.0；required 0→1 钳制；边界 ready=required-1/required

### D27 每任务 annotation 键编码（G3，取代 D17）

**结论**：键 `traincache.io/scores-<namePrefix32>-<hash12>`；`hash12=sha256(ns+"/"+name)` 前 12 位小写 hex；`namePrefix` 截断 32 字符并去尾部 `-`/`.`；key 名（`/` 后部分）≤52（7+32+1+12）；值 `{"v":1,"task":"<ns>/<name>","g":<gen>,"t":"RFC3339","p":{"<idx>":0..100}}`（2026-10-20）。

**为什么**：单键 JSON 多任务共节点会互相覆盖且体积无界；每任务独立键把冲突面降到单任务，key 有界且可预测。

**约束与影响**：
- M8 往返/并发：同名不同 ns、长名截断、hash 稳定性、key 名长度 ≤52、非法 JSON 读回降级为 0

**结论**：默认保留现有差值裁决（`c_ij - secondBest_i` 大者保留、其余让步）：`allowMultiPodPerNode=false` 时共享违反用户声明的放置约束，不可作为默认行为。`allowMultiPodPerNode=true` 时 M6 已允许共节点，冲突主要只剩反亲和（不可共享）与节点容量，此时"共享"作为**未启用的可选分支**：仅当 `allowMultiPodPerNode=true`、无亲和冲突、粗容量允许，且 `\|W_B \ W_A\| < c_ij - c_ik` 时，才允许次优 Pod 共享最优节点而非让步。前置条件：先补 `count × maxPod` 粗资源记账（Q6 目前不装箱）。启用触发条件：M11 端到端取得真实 `wait_time` 后，若数据显示让步搬迁代价显著，再实现；不得默认启用。状态：**已记录，未实现**（2026-10-20）。D38 的 fanout 模型改变了"让步搬迁"的成本结构，共享分支的启用前提需结合 D38 重新评估。

**约束与影响**：
- 设计记录，暂无实现判据；启用前须由 M11 真实 `wait_time`/IO 数据支撑

### D38 预热分配 fanout（单节点 → 每 Pod K 个预热节点）

**结论**：新增 `spec.preheatFanout`（int，默认 1，典型 2，0 与负数由 CRD 拒绝）；GWAA 按各 Pod 最大 `c_ij` 降序贪心认领 top-K 可行节点，节点能容纳几个 Pod 由 `allowMultiPodPerNode` 与亲和字段声明（该字段正式接线），跨 Pod 争同一节点时仍按 `(c_ij − 次优 c_ik)` 差值裁决，差值大者保留、其余让步到次优可行节点；GWAA 不再决定最终落点，最终落点由 Scheduler 在放行后的分数快照中从该 Pod 的 K 个暖节点里选出；门控条件①恢复存在量词，K 个预热节点中至少一个 `Ready ≥ floor(阈值 × K_i)` 即该 Pod 达标，全部 Pod 达标才放行，条件②③不变；放行时对全部预热节点（P×K 配对）写分数快照，沿用 D27 的 annotation 键与 D19 的分数公式；`PodNodeReadiness` 由每 Pod 一条改为每 Pod K 条（只记 K 个预热节点，P×K 有界），候选节点粒度仍由 `ReadinessTable` 承载；代价是预热 IO 与缓存占用最多 K 倍，窗口重叠时更低（2026-10-21）。

**为什么**：单节点预热下，门控条件①的存在量词没有实际意义；放行时 `writeScores` 每行只有一个非零值，`NormalizeScore` 把唯一非零节点归一到 100，D19 的衰减分数不参与节点比较，打分退化成软钉住；分数只是调度偏好，原先那个唯一的预热节点被高优先级任务抢占后其余节点全 0 分，Pod 会落到冷节点回源，预热收益归零；暖备份用有界 fanout 换调度鲁棒性；`fanout=1` 时除修复既有假收敛缺陷外与现行为一致，可平滑迁移。D36 不标作废，但 status 粒度由每 Pod 一条放宽为每 Pod K 条，体积约束仍成立，M13 重新实测。

**约束与影响**：
- M13 判据①–⑨：固定种子 `fanout=2` 可复现、每 Pod K 节点且满足亲和、任一预热节点达标即放行、status <1 MiB、日志断言（D21）

### D39 fanout 上限 + 下限与自适应目标数量（取代 D38 的固定数量部分）

**结论**：`spec.preheatFanout` 只作上限（默认 1、最小 1、典型 2），新增 `spec.preheatFanoutMin` 作下限（默认 1、最小 1、必须 `<= preheatFanout`）。GWAA 对每个分配单元按块数计算：`K_i` 为窗口块数，`S_min=ceil(0.25×K_i)`；可行节点按 `c_ij` 降序、节点名升序排序，`best=c_i1`；若 `best <= S_min` 判为低信号，`band=min(maxFanout, 可行节点数)`；否则 `band=min(maxFanout, 满足 c_ij >= 0.5×best 的节点数)` 且至少 1；`target=clamp(band, minFanout, maxFanout)` 再按可行节点数封顶；`minFanout > band` 置 `ForcedByMin` 并按排序强制补位；`minFanout > 可行节点数` 置 `MinUnmet` 且 `target=可行节点数`；低信号置 `LowSignal`。亲和合并单元的 `unitMin=max(各成员 min)`、`unitMax=min(各成员 max)`，`unitMin > unitMax` 返回冲突错误，目标集合对成员共享。输出新增 `TargetSet`（目标集合）与 `Decisions`（`TargetFanout`、`LowSignal`、`ForcedByMin`、`MinUnmet`、`FallbackOutOfTarget`）；除集合外兜底 1 个外，`Assignment` 是 `TargetSet` 的子集，冲突裁决与补齐只在目标集合内进行；目标集合内一个都放不下时允许集合外兜底 1 个并置 `FallbackOutOfTarget=true`，无任何可行节点才 unassigned；`PreheatSet` 覆盖实际 `Assignment`，不覆盖未分配的目标节点。`PodNodeReadiness` 每 Pod 条数等于实际 `Assignment`；正常在 `[min,max]` 内，冲突/容量/兜底可低于 min（`MinUnmet=true`），任何情况下不超过 max；无可行节点写一条空 `NodeName` 汇总记录。门控条件①仍为存在量词：预热节点集合（大小在 min 到 max 之间；`MinUnmet` 时按实际数量）中任一节点 `Ready >= required_i` 即该 Pod 达标；放行分数快照只覆盖实际 `Assignment` 的 P×actual 配对，覆盖不到 P×max。日志新增 `fanout_min`、`fanout_max`、`fanout_target`、`fanout_actual`、`low_signal`、`forced_by_min`、`min_unmet`、`fallback_out_of_target`、`prune_reason`；`pods_per_node` 仍按实际配对计数。下限仅为目标：`preheatFanoutMin` 是目标下限，冲突、容量限制与集合外兜底都可能让实际认领更少。`MinUnmet` 的最终定义是：冲突裁决、top-up 与集合外兜底全部结束后，`len(Assignment[pod]) < min`（`preheatFanoutMin` 经 CRD 默认后的值，GWAA 输入 0 按 1 处理）即为 true；计划阶段 `min > 可行节点数` 也先置 true。`ForcedByMin` 仍只表示 `min > band`、目标被强制抬高，和 `MinUnmet` 是两件事。status 的 `PodNodeReadiness` 条数始终等于实际 `Assignment` 数量（无可行节点时的一条空汇总记录除外），正常在 `[min,max]` 内，`MinUnmet` 时可低于 min。`max` 仍是硬上限，任何情况下不超过。集合外兜底最多 1 个节点：集合外节点不在目标集合里，没有缓存分布依据，兜底只为避免完全未分配；为凑 min 扩到多个会放大无效预热 IO 并破坏目标集合约束（2026-10-22）。

**为什么**：D38 的固定数量在缓存分布集中时多预热了无收益节点，在分布均匀时又缺少区分度。用 0.25 作低信号下限、0.5 作保留线，让目标数量随缓存分布伸缩：集中时只留最优节点，分散时保留多个暖备份；下限由用户显式声明，避免"算法认为 1 个就够"破坏调度鲁棒性。`TargetSet` 与 `Assignment` 分离，使"允许预热范围"和"实际下发范围"可分别观测与裁剪。代价是低信号时目标数量取到上限（受可行节点数封顶），预热 IO 与缓存占用最多升到 max 倍；下限强制补位也会增加暖备份成本。复杂度仍为 O(P×N×max)。D38 的"精确 fanout 数量"由 D39 取代；D38 的门控存在量词、分数覆盖、暖备份等语义不变。D38 原文不改、不标作废。

**约束与影响**：
- M14 判据①–⑩：固定种子复现；`12,1,0,0,0` × min=1/2/3；低信号 `1,1,0,0,0` 取上限；`11,7,3` 取 2；除兜底外 `Assignment ⊆ TargetSet`；min>max 拒绝；min>可行数记 `MinUnmet`；status 条数与体积；日志字段；`fanout=1` 回归；8.0 未改动

### D40 PodNodeReadiness 补齐 MinUnmet bool 字段与 StartupWindowReady 注释

**结论**：`PodNodeReadiness` struct 新增 `MinUnmet bool` 字段（JSON tag `minUnmet,omitempty`），与 `gwaa.PodDecision.MinUnmet` 同步置位；同时给已有 `StartupWindowReady` 字段补一条注释说明它是 `ReadyInWindow` 的源值、保留字段。

**为什么**：GWAA 分配后把"实际 Assignment 数量低于 preheatFanoutMin 下限"这个事实记在 `PodDecision.MinUnmet`（8.1 §5.5），但 status 明细层 `PodNodeReadiness` 没对应字段。Controller 轮询就绪后写 status 时丢失了这个信息，Controller 重启 reconcile 后也无法从 status 还原"哪些 Pod 没分到足够预热节点"。`StartupWindowReady` 字段已存在，但 docs/8.1 之前没解释它和 `ReadyInWindow` 的关系，实现层各自赋值容易产生不一致。

**约束与影响**：
- 字段只增不移：`MinUnmet bool` 追加到 `PodNodeReadiness` 末尾，`omitempty` 保证 JSON 兼容性；`StartupWindowReady` 字段原地补注释，不改类型和 tag。
- 置位时机：Controller `Poll` 里为每个 (Pod, 预热节点) 构造 `PodNodeReadiness` 时，`MinUnmet` 直接取该 Pod 的 `PodDecision.MinUnmet`（GWAA 规划结果，轮询时不重算）。同一 Pod 的各条记录 `MinUnmet` 值相同。
- CRD YAML 重新生成：`controller-gen` 生成新的 CRD manifest，字段零默认值、不写 `optional` 之外的 CEL 规则——MinUnmet 只是观测标记，不参与准入校验。
- 验收：CRD schema 含 `minUnmet` 字段；status patch 后读回含 `minUnmet: true`（冲突导致实际 Assignment < min 的 Pod）；Controller 重启后 reconcile 能从旧 status 的 `minUnmet` 字段还原该 Pod 处于"下限未满足"状态。

### D41 StartupWindowReady 字段保留理由与语义

**结论**：`PodNodeReadiness.StartupWindowReady int32` 字段保留，定义为"窗口内就绪块数的原始计数"，由 `ReadyInWindow` 赋值路径直接携带——当前实现里两者值完全相同（Poll 轮询时同一次就绪度计算同时写入两个字段）。字段存在的原因是 8.1 门控契约（§5.6）里 `ReadyInWindow` 是门控判定的中间结果，而 `StartupWindowReady` 是"完整计数快照"，便于日志/trace 里直接读窗口就绪数而不用再解算一次 `ReadyInWindow/ReadyBlockBitmap`。保留字段 + 明确注释，不删除、不重命名。

**为什么**：Controller Poll 轮询每个预热节点的 `ReadyBlockBitmap` 后，在构造 `PodNodeReadiness` 时同时写 `StartupWindowReady`（窗口内 ready 块数）和 `ReadyInWindow`（同样的值）。两者当前行为完全相同，但语义归属不同：`ReadyInWindow` 是门控条件①"全 Pod 达标"判定用的字段（gate.Evaluate 里直接读），`StartupWindowReady` 是 status 里给人读的"窗口就绪度"快照（`StartupWindowReadyRate` 也用它作分子）。docs/8.1 之前没写清楚两者关系，实现层如果哪天改了门控计算逻辑（比如 ReadyInWindow 变成"加权计数"），StartupWindowReady 应该保持"原始计数"语义。

**约束与影响**：
- 字段保留、类型不变（`int32`），JSON tag 不变（`startupWindowReady,omitempty`）。
- 注释已在 8.1 D40 步中补好："mirrors StartupWindowReady for the 8.1 gate contract"——说明它和 ReadyInWindow 的同源关系。
- 实现层约束：Poll 构造 `PodNodeReadiness` 时，`StartupWindowReady` 和 `ReadyInWindow` 必须由同一次计算赋值，不能一个用 bitmap 直接计数、一个用不同口径。如果未来门控逻辑变，ReadyInWindow 可以单独调整口径，StartupWindowReady 保持"窗口内 ready 块数"原始定义。
- 验收：readinessTable 日志断言里同时检查两个字段、值相等；`StartupWindowReadyRate = StartupWindowReady / K_i` 的计算链路不回归。

1. 实现子代理发现约定不可实现或与基线冲突，回传 `BLOCKED`：带上理由、证据（文件/行号/命令输出摘要）和建议方案。
