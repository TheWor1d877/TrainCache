## 2. 各条决策

### ADR-001 存储选 Loki 而非 Elasticsearch

**结论**：起步阶段用 Loki + Grafana 做日志中心存储，不引入 Elasticsearch（ES）。

**为什么**：需要一个中心存储汇聚三层（controller / Agent / DataLoader）的 JSON 日志，并支撑看板查询与告警。Loki 只给少量标签建索引、正文压缩存放；ES 给全文建倒排索引（把正文里每个词都登记进索引，检索能力强但贵）。本项目的查询以 `component + task + node + reason + request_id` 为主，标签加结构化元数据就够用；Loki 的写入成本与运维复杂度都低。ES 的全文索引适合复杂检索，但存储与集群成本高。

**约束与影响**：只有出现「跨字段任意全文检索」的硬需求时，才重新评估 ES。

### ADR-002 只做有界关联，不引入 OpenTelemetry / 分布式 tracing

**结论**：只做「有界关联」——给定一个 Pod，用 `warmup_task + pod_index` 把 controller / Agent / DataLoader 三段的日志拉出来；不引入 OpenTelemetry 完整 tracing。

**为什么**：三段日志跨进程，天然串不成一条链路。引入 OpenTelemetry 要给每次请求挂一个全链路 traceId；7.1 §9.2 已明确没有分布式 traceId，全链路 tracing 会牵动 7.x/8.x 的契约，改造成本高，对当前排障场景收益有限。

**约束与影响**：跨进程主键仍是 `task_id + node + generation`；`request_id` 目前只在控制平面进程内使用（「不出进程」指不引入分布式 traceId，P2 计划经 gRPC metadata 传播，见 8.1 §5）；必要上下文通过 gRPC metadata 与钩子帧的增量字段传播，缺省兼容——老版本不填这些字段也能正常工作。

### ADR-003 只写 stdout，Agent 绝不写缓存盘

**结论**：所有进程只写 stdout/stderr，由容器运行时负责轮转、采集器 tail 收集；Agent 不得把日志写进 `TRAINCACHE_CACHE_ROOT`。

**为什么**：日志落地位置影响轮转、采集与磁盘争用。进程自写文件到宿主机、写进缓存盘、只写 stdout 三个候选里选 stdout：容器运行时原生就管容器日志轮转，采集链路统一；也避免日志与缓存争用同一块盘，把预取/命中拖垮。

**约束与影响**：Agent 与 DataLoader 不自行写文件日志；磁盘保护依赖 `containerLogMaxSize/MaxFiles`（容器日志单文件大小与保留份数上限）与采集器背压（下游收不动时反过来压住上游的发送速度）。

### ADR-004 指标标签只放有界维度

**结论**：标签只放 `cluster/namespace/component/level/node/stream` 等有界维度；`request_id/pod/task_id/path` 一律不进指标标签、不建 Loki 标签，改放 structured metadata 或 JSON 正文，查询时再过滤。

**为什么**：指标的 label 和 Loki 的 label 都是索引项，高基数（标签取值太多导致索引/指标数量爆炸）会撑爆索引、拖慢查询。`request_id` 这类字段的取值近乎无限，每来一个请求就多一套索引项，进标签必然导致索引爆炸，所以只允许种类数得清的维度当标签。

**约束与影响**：两条铁律——禁止用日志做告警阈值，禁止把无限编号塞进指标。

### ADR-005 不新造 `task` 字段做二次抽象

**结论**：保留 `warmup_task` 与 `task_id` 两个字段，保持现有语义，不合并、不新造统一的 `task`。

**为什么**：控制平面用 `warmup_task`，Agent/DataLoader 用 `task_id`。两者是多对一关系：一个 WarmupTask 对应多个 Agent 预取任务，语义不同。强行合并会丢信息，还会破坏 8.1 的既有字段。

**约束与影响**：关联时靠 `warmup_task + pod_index`（控制平面侧）与 `task_id + node + generation`（Agent 侧）分别定位。

### ADR-006 Warn/Error 永不采样

**结论**：日志超限时先丢 Debug、再丢 Info；Warn/Error 永不丢，并计数 `log_dropped_total`。

**为什么**：Warn/Error 是需要人工介入的信号，采样会掩盖稀有但致命的错误，导致排障时缺样本。

**约束与影响**：令牌桶（按固定速率发令牌、拿到令牌才放行一条日志的限流算法）丢弃策略与「必要时临时提高采样率并留审计记录」配套；`permanent/io/corrupt` 类错误不得被采样丢弃。

### ADR-007 脱敏实现归属 core

**结论**：在 `traincache/core` 新增 `core/logging` 包，提供 `Redact` 与 `RedactURL`，controller 与 Agent 两端共同调用；契约冻结于 5.1 §5.6、5.3 D32。

**为什么**：脱敏（日志落盘前把 Secret、URL 里的凭证等敏感信息抹掉）两端都必须做，但 controller 与 Agent 是互不引用的独立 module。两端各写一份会产生语义漂移（两边规则慢慢变得不一致）与重复维护；放在 controller 则 Agent 引用不到；core 已是两端共同依赖，且该包无状态、仅依赖标准库。

**约束与影响**：脱敏规则随 core 模块版本演进；`Redact`/`RedactURL` 与单测已在仓库，controller 与 Agent 的调用点接入见 `TODO.md`（A）。

### ADR-008 `warmup_task` 的适用范围

**结论**：`warmup_task` 适用范围定为「控制平面 + DataLoader」；日志字段中不出现 `task`；`TRAINCACHE_TASK` 仅作为环境变量名保留，不是日志字段名。

**为什么**：ADR-005 已决定保留 `warmup_task` 与 `task_id`、不新造 `task`，这里进一步明确 `warmup_task` 出现在哪些组件的日志字段中。DataLoader 需要通过 `warmup_task` 与控制平面关联，否则跨层排障断链；新造 `task` 字段会破坏已冻结字段语义。

**约束与影响**：DataLoader 有值时日志必带 `warmup_task`；Agent 侧仍用 `task_id + node + generation`。

### ADR-009 Agent 日志包路径

**结论**：Agent 日志包路径定为 `agent/internal/logging`，已实现，导出 API（`New/Into/From`）与 `controller/internal/logging` 对称。

**为什么**：Agent 需要与控制平面对称的日志初始化入口（级别解析、字段注入、脱敏接入）。散落在 `agent/svc` 内初始化不利于统一；`agent/internal/logging` 与控制平面镜像对称，Go 的 `internal` 目录限制跨 module 导入，避免被外部依赖；跨端共用的脱敏逻辑走 core（ADR-007）。

**约束与影响**：Agent 各服务从该包取日志构造与字段注入入口，不自行创建 handler。

### ADR-010 十六点覆盖先核对后定

**结论**：先逐条核对控制平面与 Agent 的现有日志落点，再确定 P0 需要新增的条目；不预先承诺十六点全量新增。

**为什么**：7.1 §9.3 的十六点日志覆盖是验收口径，部分点已有实现或需按组件拆分。直接全量新增会把已实现项重复计入，也会为凑数新增没有消费者的日志点。

**约束与影响**：核对结果记录在 8.1 §4.4，作为 9.x 实施清单与测试断言（`msg + 必带字段 + level`）的输入。

### ADR-011 指标后端采用 Prometheus，与 Loki 同属 observability 独立根

**结论**：指标后端采用 Prometheus 单实例，与 Loki 同属 `controller/deploy/observability/` 独立 kustomize 根（kustomize 是 K8s 官方的清单组织工具，一个「根」就是一套可以整体 apply 的清单目录）；按 15s 间隔抓取 controller-manager（:9412）、agentd（:9411）、webhook、scheduler 的 `/metrics`，覆盖 `traincache` 与 `kube-system` 两个命名空间；Grafana 同时接入 Prometheus 与 Loki。指标标签只放有界维度，`request_id`、`pod`、`task_id`、`path` 不进标签。

**为什么**：Loki 只承载日志，无法承担指标的长期抓取、趋势查询与告警。托管/多副本 Prometheus 在单集群规模下是过度设计；不设中心后端则只能逐进程查看。Prometheus 是 `/metrics` 生态的事实标准，与 Grafana 原生集成；与 Loki 共用独立部署根，观测栈可整体安装、升级和卸载，不牵动主清单。

**约束与影响**：单实例无 HA（高可用），Prometheus 故障期间指标断档；本地存储容量与保留策略需单独管理；多集群场景需再评估远程写或联邦（把多个 Prometheus 的数据分层汇聚）。

### ADR-012 observability 使用独立 kustomize 根与单独 e2e 脚本

**结论**：`controller/deploy/observability/` 作为独立 kustomize 根，不被 `controller/deploy/kustomization.yaml` 引用；验收脚本单独提供为 `controller/e2e/observability.sh`，不并入主 e2e。

**为什么**：fluent-bit、Loki、Prometheus、Grafana 与业务控制平面的部署生命周期不同，观测栈的体积和资源开销也远大于主清单。并入主清单会让业务部署背上重依赖；独立根可单独安装、升级和卸载，单独 e2e 可独立运行，失败不阻塞主链路验收。

**约束与影响**：代价是需要显式 apply 两个根，CI 与文档要维护两套入口；只部署主清单时没有可观测性，需在运行手册中写明前置步骤。`controller/e2e/observability.sh` 支持 up/verify/down，verify 已在 kind 集群验收通过。

### ADR-013 指标按暴露路径拆两个抓取 job

**结论**：`traincache-components` 抓 controller-manager、agentd、webhook、scheduler 的 `/metrics`；`traincache-custom-metrics` 抓 controller-manager 与 scheduler 的 `/metrics/traincache`。scheduler 的项目指标唯一由 custom job 承载，原 job 对该组件的序列做 drop；agentd 的项目指标在 `/metrics`，只由原 job 抓取；webhook 没有项目自定义注册表（源码未创建独立 registry、未配 ExtraHandlers），不纳入 custom job，不是配置遗漏。

**为什么**：项目指标与控制平面通用指标暴露在不同路径，scheduler 的项目指标需要避免与通用 job 重复计数。所有组件统一抓 `/metrics` 覆盖不了 `/metrics/traincache` 这条路径；按暴露路径拆分才能同时覆盖两类指标，并让 scheduler 的项目指标只被一个 job 抓取。

**约束与影响**：代价是需要维护两个 job 与一条 drop 规则，新增组件时要明确它属于哪个 job。


## 风险与取舍总表

| 风险             | 影响                                   | 取舍/缓解                                                                        |
|------------------|----------------------------------------|----------------------------------------------------------------------------------|
| 日志量           | 节点磁盘、Loki 成本、采集背压          | 默认 Info、Debug 关闭、成功路径聚合、采样与限流；压力下先丢 Debug                |
| 基数             | Loki 标签爆炸、查询变慢                | 标签只放有界维度；`pod/task_id/request_id/path` 只进正文或结构化元数据           |
| 隐私与凭证       | Secret/URL 泄漏到中心存储              | 脱敏函数 + 哨兵测试 + 代码评审红线；对象存储端点只记 host                        |
| 跨层关联成本     | 需要改 proto/帧/env，牵动 7.x/8.x 契约 | 只做增量可选字段，缺省兼容；先打通 `warmup_task + pod_index`，不引入完整 tracing |
| 日志契约漂移     | 看板/告警/runbook 失效                 | 字段登记、只增不改、CI 按 `msg` 与字段断言                                       |
| 采样掩盖稀有错误 | 排障时缺样本                           | Warn/Error 不采样；保留按 `reason` 的计数指标；必要时临时提高采样率并留审计记录  |
