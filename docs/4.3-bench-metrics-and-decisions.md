# bench 口径与决策

## 1 术语

| 术语 | 含义 |
|---|---|
| COND | 一个实验格的全部条件写成一个 JSON 文件，`python3 bench/run.py compare --rho 2 --rate 300 --group traincache-cold` 对应一份。`bench/run.py` 只读 COND 的字段决定这一格怎么跑。 |
| 预热 | 训练 Pod 调度之前，controller 建 WarmupTask 把数据拉进节点缓存。Pod 还没落到节点，覆盖哪些节点由 `preheatFanout` 决定，取 2 时预热两个节点。 |
| 预取 | 训练 Pod 调度到节点之后，agentd 按训练的消费顺序持续往后拉块。窗口大小由 `TRAINCACHE_PREFETCH_LOOKAHEAD` 控制，默认 16 块。 |
| 启动窗口 K | 训练开始之前必须就绪的块数。`startupWindowBytes` 取 536870912 字节，按 8 MiB 块折算 K 为 64 块。缓存容量折算出的块数记作 `K_cache`，见 §2.5。 |
| ρ | 数据集字节除以缓存容量。数据集固定 4294967296 字节，ρ=4 时缓存容量 1073741824 字节。 |
| 负载形态 | COND 的 `load` 字段，取 `dataset`、`tilt`、`train` 三值，分别读主数据集 tar、倾斜清单、训练负载。 |
| 组态 | 一次跑分的独立运行形态，共七种：`direct`、`juicefs-cold`、`juicefs-warm`、`fluid-cold`、`fluid-warm`、`traincache-cold`、`traincache-warm`。组态名对应 `bench/compare/` 下的起停脚本，例如 `traincache-warm` 由 `bench/compare/traincache/up.sh` 加调度闸门起。 |
| 淘汰策略 | 缓存写满后按什么顺序删块。`TRAINCACHE_EVICT_POLICY` 取 `heat`、`lru`、`lfu`。 |
| 基线格与被测格 | 基线格是五种基线组态各一格，统一跑 ρ=4，作为参照值。被测格是 `traincache-cold` 与 `traincache-warm`，每个 ρ 各一格，共十格。 |

## 2 指标与算式

### 2.1 启动与全程 makespan

makespan 是从提交训练任务到训练结束的墙钟时长，单位 s。四个时刻都以 epoch 秒记录。

| 符号 | 含义 | 采集方式 |
|---|---|---|
| `t_submit` | 训练 Job 创建时刻 | runner 在 `kubectl apply` 之前取 `time.time()`，注入 Job 环境变量 `TRAINCACHE_JOB_CREATED_AT` |
| `t_pod_ready` | 训练 Pod Ready 时刻 | runner 读 Pod condition `Ready=True` 的 `lastTransitionTime` |
| `t_first_step` | 第一步开始时刻 | 第一个 batch 就绪之后、算力开始之前打点 |
| `t_last_step` | 最后一步结束时刻 | 最后一个 epoch 的最后一个 step 返回之后打点 |

```text
启动 makespan = t_first_step − t_submit
全程 makespan = t_last_step − t_submit
就绪后阶段   = t_last_step − t_pod_ready
```

measure 脚本在 stdout 写一行 `RESULT key=value ...`，每个 epoch 边界写一行 `[EPOCH_BOUNDARY] epoch=<n> ts=<epoch秒>`。runner 解析这两类标记，不读 Pod 内文件。`metadata.creationTimestamp` 只作交叉核对，不作 `t_submit`。

epoch 0 的前 10 步标为 warmup，不进 stall 聚合，仍计入 makespan。

### 2.2 stall

每一步记两个时长，单位 s。

| 符号 | 含义 |
|---|---|
| `wait_s` | 从本步开始等待 batch 到 batch 就绪的时长 |
| `step_s` | batch 就绪到本步计算结束的时长 |

```text
stall = wait_s ÷ step_s
```

`stall` 是无量纲比率。聚合报 `mean` 与 `p90`，中位数只用于判断是否处于 stall 形态。warmup 的 10 步不参与聚合。

### 2.3 命中率

命中率的定义是该块打开时有没有触达源站。三阶段边界如下。

| 阶段 | 起点 | 终点 |
|---|---|---|
| startup | `t_submit` | `t_first_step` |
| steady | `t_first_step` | 第一次切换事件 |
| switch | 切换事件时刻 | 新窗口 K 块全部就绪；未就绪时截到该 epoch 结束 |

每个 epoch 边界算一次切换事件，三种 shuffle 策略相同。curriculum 的 stage 边界额外算一次。两个窗口同时活跃时按 switch 记。

```text
hit_rate_<phase> = 1 − demand_miss_bytes_<phase> ÷ read_bytes_<phase>
source_saving_ratio = 1 − fetch_bytes_run ÷ read_bytes
```

`read_bytes_<phase>` 是训练侧按阶段累计的打开字节（B），`demand_miss_bytes_<phase>` 是打开时本地不存在、需要等预取或回源的字节（B）。`hit_rate` 无量纲。`fetch_bytes_run` 是 `traincache_fetch_bytes_total` 在 run 窗口内的增量（B），`source_saving_ratio` 衡量省下的源站流量，与命中率分列。

组态口径不同，产物列 `hit_rate_basis` 写明来源。

| 组态 | 命中率口径 |
|---|---|
| `traincache-cold`、`traincache-warm` | 训练侧块打开时记账的字节账，精确到块 |
| `direct` | 按 0 记，无缓存层 |
| `juicefs-*`、`fluid-*` | warm 近似全命中，cold 近似全回源，按分片粒度 |

agentd 侧 `traincache_cache_hits_total`、`traincache_cache_misses_total` 按 `phase` 折成 `hit_ratio_agent_*` 作交叉校验。两侧差异超过 5% 时，以训练侧字节账为准。

### 2.4 三笔字节成本

三笔账都从 run 窗口的计数器增量取，单位 B。

| 账目 | 符号 | 范围 | 算法 |
|---|---|---|---|
| 启动预热 | `warmup_bytes` | 预热阶段 | `WARMUP_K`（预热块数）× 8388608 × 实际 fanout；juicefs-warm 与 fluid-warm 按整份数据集计 1 份；冷组与 `direct` 记 0 |
| 持续预取 | `sustained_prefetch_bytes` | 训练开始到结束 | `reason=prefetch` 的增量中落在非切换窗口的部分 |
| 切换重预取 | `switch_reprefetch_bytes` | 每个 switch 窗口 | `reason=prefetch` 的增量中落在切换窗口的部分 |

两笔预取之和应等于窗口总量，对不上时按实际值报告并在行内标注。

```text
sustained_prefetch_bytes + switch_reprefetch_bytes = prefetch_bytes_run
```

三笔账之和就是该格的字节成本；fanout 造成的重复字节计入成本，不折算成有效字节。做收益对比时，横轴取字节成本，纵轴取 makespan 改善。源站出站字节取 MinIO 的 `minio_s3_traffic_sent_bytes` 窗口增量，与训练侧 fetch 字节的差异记 `origin_reconcile_diff`，差异超过 5% 时以源站为准。

### 2.5 K_cache

`K_cache` 是缓存容量折算出的块数，由 controller 计算，随产物落盘。

```text
K_cache = floor(cacheCapacityBytes × maxFillFraction ÷ (podCount × chunkSize))
```

| 符号 | 含义 | 单位与取值 |
|---|---|---|
| `cacheCapacityBytes` | 该格的缓存容量，等于 4294967296 ÷ ρ | B |
| `maxFillFraction` | 缓存可填充比例 | 0.125，无量纲 |
| `podCount` | 预热覆盖的 Pod 数 | 本装置取 1 |
| `chunkSize` | 块大小 | 8388608 B |

ρ=8 时缓存容量 536870912 B，`K_cache` = floor(536870912 × 0.125 ÷ 8388608) = 8 块。ρ=0.5 时 `K_cache` 为 128 块。五个 ρ 的取值表见 4.1 §2。`K_cache` 是派生量，不作独立实验轴，每格的实际值写进 `lock.json`。

上式只覆盖 controller 自动算 K 的路径。COND 里显式写 `k` 时按填写的值执行，`maxFillFraction` 超限只发 Warning 不拒绝。对照族与并行下载族的 warm 组走显式 K。

### 2.6 缓存峰值与声明容量

`cache_dir_peak_bytes` 是 run 窗口内单节点 `/var/cache/traincache/blocks` 下已完成块文件的字节和的最大值，单位 B。预取在途的 `tmp-*` 半成品不计入。

```text
r_peak = cache_dir_peak_bytes ÷ cache_bytes
```

`cache_bytes` 是该格 COND 的声明容量（B）。`capacity_bytes_final` 是 agentd 训练结束时的在用字节。`r_peak` 无量纲，判定规则见 §3。

`capacity_bytes_final` 取各 agentd `traincache_cache_capacity_bytes_total` 的最大值。它与同节点目录末次采样的比值落在 0.5 到 1.5 之外时，该轮的字节维度读数只作诊断。

## 3 判据阈值

判据阈值只在本节定义，4.2 各族的判定引用本节。

### 3.1 全体判据

| 判据名 | 阈值 | 判定方式 |
|---|---|---|
| 采样与统计 | 每格 3 次采样；区间用 10000 次 bootstrap 重采样 | 报平均数与 95% 置信区间 |
| 赢 | 相对比较对象的改善 ≥ 5% 且差值 CI 上界 < 0 | makespan 越低越好，命中率越高越好 |
| 输 | 恶化 ≥ 5% 且差值 CI 下界 > 0 | 同上，方向相反 |
| 相近 | 差值 CI 含 0 | 只写分不出快慢 |
| 可忽略 | CI 不含 0 且均值差 < 5% | 与相近分开记 |
| 字节账自洽 | `sustained + switch_reprefetch` 等于 `prefetch_bytes_run` | 差值为 0 记通过，否则按实际值报告 |
| 淘汰生效 | `evict_blocks_run` > 0 | 等于 0 且 `r_peak` > 1.05 时整轮作废，记 `evict_not_engaged` |
| 上限压住 | `r_peak` ≤ 1 + 418 MB ÷ 声明容量 | 只在 100 mbit 的格子判定，其余带宽的盲区大于容量，比值只记录 |
| 作废 | 整轮作废，保留现场 | 作废轮不进汇总，不挑点删除 |

上限判据里的 30 s 是 `agent/evictor/evictor.go` 的 `defaultInterval`，5 s 是目录字节采样的标称周期，11.95 MB/s 是 100 mbit 档的实测有效带宽。两项相乘得 418 MB，是淘汰执行前还能写进缓存的字节上界。ρ=4 时声明容量 1 GiB，上界为 1.39；ρ=1 时为 1.10；ρ=8 时声明容量 0.5 GiB，上界为 1.78，这一格的比值只能说明淘汰在删块。

### 3.2 按族的判据

| 族 | 判据名 | 阈值 | 判定方式 |
|---|---|---|---|
| `compare` | 组间胜负 | 5% | 只在 ρ=4 的格子上有基线，该格按 5% 规则判；其余 ρ 只报被测格数值 |
| `gateway` | 复制读合并 | 关闭与开启的源站字节比落在 4 ± 5% | 越界说明栅栏未对准，整轮作废 |
| `gateway` | 臂间比较 | 5% | 同格 3 次，两两比 makespan 与源站字节 |
| `evict` | 策略可分辨 | 两两相对差 ≥ 5% | 命中率、`total_makespan`、`b_evictions_of_hot` 任一项越界即记可分辨 |
| `evict` | 策略不可分辨 | 三项相对差都 < 5% | 只写三档无差异 |
| `prefetch` | 转平 | 相邻 lookahead 档改善 < 5% | 记转平点，不判胜负 |
| `prefetch` | 重复字节 | fanout 每加 1，预热字节按份数增加 | 从三笔账直接读，不进百分比判据 |
| `warmup` | 门控有效 | 启动 makespan 改善 ≥ 10% | ρ > 1 的格子 |
| `warmup` | 门控无价值 | 差值在 ±5% 内 | 1000 mbit 的格子 |
| `warmup` | 门控负收益 | 恶化 ≥ 5% | 在图上标出 |
| `switch` | 回落 | 阈值 = max(1.1 × 基线, 基线 + 5pp) | 10 步滚动均值首次 ≤ 阈值且之后连续 10 步保持 |
| `switch` | 差异 | 20% | 单次测量不判胜负 |
| `switch` | 右删失 | 到 epoch 末仍未回落 | 回落时间按 epoch 末计，单独报删失率 |
| `multiconsumer` | 热比例效应 | 5% | 比命中率与 makespan |
| `e2e` | 恢复成功 | 任务跑完且恢复窗口 `fetch_requests{result="error"}` 增量为 0 | 二值判定 |
| `rangepar` | 并行收益 | l0 的开臂关臂 makespan 比落在 0.9 到 1.1；l1 与 l2 的比值不小于 1.8；l3 的比值不小于 1.5 | 同档两臂各 3 次，比 `total_makespan` 的中位数 |
| `rangepar` | 字节守恒 | 两臂的 `origin_egress_bytes` 与 `fetch_bytes_run` 差异小于 2% | 并行不得靠多打字节换时间 |
| `rangepar` | 命中不退化 | 开臂 `hit_rate` 不低于关臂 2 个百分点 | 同一数据集同一容量，命中不应因并行而变 |

`e2e` 每场景 2 次采样，共 6 跑，不受 §3.1 每格 3 次的约束；该族只做二值判定，不报 CI。

`switch` 的回落基线取切换前 20 步的 stall 均值。基线不足 20 步的事件标 `insufficient_baseline`，不进回落曲线。

`rangepar` 的两臂只差 Range 并行开关，比较在同档内做。开臂每块发 4 条 Range GET，连接数是关臂的四倍，所以「并行收益」那条读的是端到端效果，含「单块内并发提高」这一项。

`chaos` 族的判据是二值，按故障逐条判定。

| 故障 | PASS 判据 |
|---|---|
| `kill_agent` | 替代 Pod Ready 且 UID 与旧 Pod 不同；RESCAN_PHASE 离开 SAMPLING；隔离块数为 0；观察窗口内 fetch 字节增量不超过单块字节 |
| `netem_degrade` | `traincache_read_stall_seconds_bucket{le="60"}` 的计数等于 `traincache_read_stall_seconds_count`；训练 Pod 不退出 |
| `netem_degrade_rate` | qdisc 回读里有 tbf 与 netem；读等待全部落在 60 s 桶内；训练 Pod 不退出 |
| `minio_down` | WarmupTask `status.phase` 出现 Degraded；训练 Pod 进入 Failed 或 Succeeded，或 Job 的 `status.failed` 非 0；源站恢复后训练 Pod 重建为 Running，恢复窗口内 error 增量为 0 |
| `tamper_block` | RESCAN_PHASE 走完 FULL_SCAN；`traincache_fetch_requests_total{reason="repair"}` 增量 ≥ 1；隔离块数与修复队列取窗口峰值 |
| `stop_ordersrc` | `traincache_agent_ordersources{state="stalled"}` ≥ 1；`traincache_agent_degraded` 走 0 到 1 再到 0 |
| `node_loss` | 节点 NotReady；DataSet condition `NoAccessibleNodes` 为 True；WarmupTask `status.phase` 为 Degraded；容器启动回来后节点 Ready 且两条状态线复原 |

混沌族取上表中的三个故障作轴，族内取值见 4.2 §8。每档取三个时点：注入前基线、注入窗口内的周期采样、注入后终值。counter 判据取窗口差分，gauge 判据取终值。

## 4 决策记录

编号沿用 D 号，外部文档与代码注释按号引用。

| 编号 | 决策 | 结论 | 理由 |
|---|---|---|---|
| D2 | makespan 起止 | 起点是 runner 在 `kubectl apply` 前取的时刻，注入 `TRAINCACHE_JOB_CREATED_AT`；终点分首步与末步两个口径，由训练脚本自报；`metadata.creationTimestamp` 只作交叉核对 | 七组态共用同一把计时尺，API server 落盘延迟不进启动时间 |
| D3 | stall 聚合 | `stall = wait_s ÷ step_s`，报 mean 与 p90，中位数只判形态 | 中位数对带宽档不敏感，预取吸收了差异 |
| D4 | 命中率分阶段 | 启动窗口是首步之前；稳态是首步到第一次切换；切换期是切换事件到新窗口就绪 | 与 agentd 的 `phase` 标签同口径 |
| D5 | 字节成本 | 三笔全记，fanout 重复字节计入成本 | 预热成本不能靠隐藏重复字节变小 |
| D6 | 缓存欠配的实现 | agentd 淘汰侧设显式容量上限，不用容器内存限制 | 对照组是缓存目录语义，内存限制对不齐 |
| D7 | 策略接口落点 | `Policy` 接口放 `agent/evictor`，`core` 只留 `cas.Evict` 原语 | `core` 不承担训练语义 |
| D8 | 现有策略的地位 | 现有热度策略包成 `heat`，与 `lru`、`lfu` 同台 | 基线取当前实现的实际行为 |
| D9 | 淘汰策略只留三档 | 只实现 `heat`、`lru`、`lfu`；`Policy` 只有 `Rank`，不设准入 | 单 Job 顺序读下准入收益不明确，实现与验证成本高 |
| D10 | lookahead 注入方式 | 用环境变量 `TRAINCACHE_PREFETCH_LOOKAHEAD` 注入，不进 CRD；对照格统一取 16 | 扫点不改 CRD |
| D11 | 对照组公平性 | 同一轨迹、同一 tc 档、同一份数据；预热时长单列，不计入 makespan | 热读组不能靠预热时间占便宜 |
| D12 | 预注册 | 正式跑分前冻结族的轴、ρ 取值与判据，此后不回改 | 防止看到结果再调参 |
| D13 | 统计口径 | 平均数加 bootstrap 95% CI，10000 次重采样 | 预注册纪律的实现方式 |
| D14 | 异常轮处理 | 整轮作废并保留现场，作废轮不进汇总 | 避免选择性报告 |
| D15 | 集群规模 | kind 4 个 worker，共 5 个节点，每个节点 32 核 / 31 GB；对照与被测同集群 | 读数与装置在同一集群，不引入跨集群差异 |
| D16 | 对照层负载形态 | 标准库脚本按轨迹读完整分片后丢弃，每步 `matmul` 跑满 `COMPUTE_MS=200` ms，不依赖训练框架 | 七组态同形，镜像轻，去掉训练框架这个变量 |
| D18 | 采样次数 | 每格 3 次，写在 COND 的 `sampling.reps` | 3 次够算 CI，机时留给族数 |
| D19 | 容量轴与参跑组 | 主轴 ρ 取 0.5、1、2、4、8；基线只跑 ρ=4，被测组态跑满五个 ρ | 缓存装不装得下数据决定结论能推到哪 |
| D20 | 实验块大小 | `trainpublish -chunk-size` 取 8 MiB，随产物归档；生产默认 64 MiB 不动 | ρ=8 时缓存 0.5 GiB，64 MiB 块只有 8 块，16 块预取窗口超过缓存；8 MiB 得 64 块，窗口占 1/4 |
| D21 | 限速与块大小解耦 | 带宽是链路属性，块大小只改请求数与单请求时长；tc 对七组态透明 | 两者混在一起，跨档结果无法解释 |
| D22 | 测量体与调度体合一 | 每格一个 train-job Pod，measure 是主容器；`traincache-warm` 走 gate，其余普通调度；不设占位 Pod | 贴近真实部署 |
| D23 | 预热外置于计时 | 预热在 `group_up` 内完成并等待，15 分钟超时整轮作废；预热时长单列 | 七组态统一「预热不计入 makespan」 |
| D24 | 缓存跨 Pod 持久 | JuiceFS 缓存用 hostPath，不用 emptyDir | 预热成果不能随测量 Pod 销毁 |
| D25 | 命中率口径 | 主口径是 `1 − demand_miss ÷ 读字节`，分阶段落列；`source_saving_ratio` 另列不混用；JuiceFS 与 Fluid 按 warm 全命中、cold 全回源近似，标 `hit_rate_basis` | 对照组不编造块级指标，自家数字能自证 |
| D26 | 预热节点覆盖 | `traincache-warm` 的 WarmupTask fanout 固定 2，scheduler 按就绪度选落点 | 两个节点足以形成候选差 |
| D28 | lookahead 扫点 | lookahead 取 8、16、32，与 fanout 1、2、3 交叉成 9 组，在 ρ=1 与 ρ=8 各跑一遍；淘汰策略不进交叉 | 两轴覆盖欠配两端，策略差异由淘汰族单点判定 |
| D29 | 淘汰相关指标 | 不设策略切换计数、准入拒绝计数、频率减半计数 | 策略只在启动时选定，运行期没有切换路径，计数恒为 0 |
| D30 | 基线与被测格分离 | 五种基线 `direct`、`juicefs-cold`、`juicefs-warm`、`fluid-cold`、`fluid-warm` 只跑一次，代表点 ρ=4；被测格 `traincache-cold` 与 `traincache-warm` 跑满五个 ρ | 基线对 ρ 不敏感，重复跑只填同一批数字 |
| D31 | 带宽是自变量 | rate 取 100、300、1000 mbit，随 COND 落盘；burst 按 0.1 秒传输量推导为 1250k、3750k、12500k；netem 只挂固定 `delay 20ms` | 随机时延打乱包序，300 mbit 档实测从 35.6 MB/s 跌到 0.6 MB/s 以下，档间差异被装置掩盖 |
| D32 | 机时结构 | rep 之间只清缓存，不 down/up 组件；warm 组每个 rep 重新预热；各族串行跑，不并行 | rep 复用省约 2 分钟；tc 是全组共享出口，并行等于均分带宽 |
| D33 | curriculum 形态 | 固定 3 个 stage，按 epoch 三等分；分片集合取同一置换的嵌套前缀，stage 内不重排；epoch 与 stage 边界重合时只记一次切换 | 嵌套前缀只缩小窗口，不引入新顺序 |
| D34 | 缓存容量口径 | 缓存容量一律由 ρ 推导，倾斜与训练负载用同一阶梯 | 控制量与观测量分开 |
| D36 | Fluid 可行性冒烟 | 开跑前做只验可行性的冒烟，通过条件三条：控制面与 Runtime 全 Ready 且缓存目录可写；整份数据集读完、400 步无 OOM 驱逐重启；Fluid 额外占用不超过 6 CPU / 6 GiB。两次环境性失败记 `fluid-unavailable-on-kind`，该格标 `unavailable`，不补跑 | 先确认 Fluid 能跑完，再拿它当基线 |
| D40 | 切换回落判据 | 基线取切换前 20 步 stall 均值；阈值取 `max(1.1 × 基线, 基线 + 5pp)`；切换后 10 步滚动均值首次不超过阈值、且之后连续 10 步保持，记为回落点；到 epoch 末未满足记右删失并报删失率；缺 20 步基线的事件标 `insufficient_baseline` | 判据先冻结，回落时间才有可比性 |
| D41 | 快照与源数据 | MinIO 的 `bench-b/shard-*.tar` 是唯一源数据；正式读数用 8 MiB 块的 `compare-data-8m` 快照，DataSet CRD 指向它；数据集取前 16 片 | 源数据不复制，块大小由快照固定 |
| D42 | tar 体积偏差 | 每片 tar 实测约 252.6 MiB，16 片约 3.95 GiB，比声明的 4 GiB 小约 1.3%；缓存容量仍按声明值除以 ρ 计算 | 偏差方向一致，组间可比 |
| D44 | 全程收益的构成 | 全程 makespan 从提交到最后一步；Pod 就绪后阶段另列 | 启动收益与全程收益分开报 |

| D46 | 网关读数口径 | 主指标是源站出站字节与全程 makespan；网关 60 秒汇总只作诊断；命中率是控制量 | 字节与时间能外部复算，日志计数受窗口截断影响 |
| D47 | COND 的字段取舍 | COND 写 ρ、rate、load、族轴参数、`sampling.reps` 与数据规模声明；缓存字节由 ρ 推导，不写绝对值；生效值与派生量记进 `lock.json` | 派生值写进 COND 会与 ρ 漂移 |
| D48 | ρ 的注入方式 | 缓存容量等于 `int(4294967296 ÷ ρ)`，经 `TRAINCACHE_CACHE_CAPACITY_BYTES` 写进 `traincache-config`；换 ρ 只改这一个变量 | 一个自变量只走一条注入路径 |
| D49 | K_cache 的记录 | `K_cache` 由缓存容量、`maxFillFraction`、`podCount`、块大小算出，每格实际值随 `lock.json` 落盘，不作独立轴 | 预热覆盖范围随 ρ 变，记录后才能复算 |
| D50 | 负载形态 | COND 的 `load` 取 `dataset`、`tilt`、`train`；数据分别取自 `track_b/tars`、`track_c` 清单、`track_d` | 负载形态是数据的组织方式，与族轴分开 |
| D51 | 产物字段 | `summary.csv` 用 `rho` 列取代 `tier`，并加 `family`、`load`、`gateway`；每格目录落 `version`、`lock.json` 与运行日志 | 汇总与复算要能按族和 ρ 定位 |
