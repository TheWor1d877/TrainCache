# 日志与监控使用说明

面向使用和运维 TrainCache 的人：日志从哪来、存在哪、怎么看；指标从哪来、怎么看、每个指标干什么用。

## 一、整体流向

```
控制平面（controller-manager / webhook / scheduler）
Agent（agentd，每个节点一个）
训练 Pod 内的 DataLoader（经钩子适配器上报）
        │
        │  只往 stdout 打单行 JSON
        ▼
节点上的容器运行时日志
        │
        │  每个节点一个 fluent-bit 负责收取
        ▼
Loki（observability 命名空间，单副本）
        │
        ▼
Grafana ──同时查──> Prometheus（每 15 秒抓一次各进程的 /metrics）

各进程 /metrics ──被定时抓取──> Prometheus
```

概述：日志走 fluent-bit → Loki，指标走 Prometheus 主动抓取，Grafana 是统一的查询入口。

## 二、日志从哪来，到哪去

### 来源

所有进程只往 stdout/stderr 打日志，一行一个 JSON。不写宿主机文件，Agent 也不往缓存盘写日志。三类来源：

| 来源 | component 值 | 说明 |
|---|---|---|
| 控制平面 | `controller-manager`、`webhook`、`scheduler` | 协调、门控、调度相关 |
| 节点 Agent | `agentd` | 预热、预取、修复、淘汰 |
| DataLoader | `dataloader` | 训练侧钩子适配器，字段契约已冻结 |

### 汇合与存储

每个 worker 节点上有一个 fluent-bit（DaemonSet）。它读取节点的 `/var/log/containers` 和 `/var/log/pods`，把 JSON 解析出来，补上 `cluster` 字段，再送到 Loki。DaemonSet 没有配 tolerations，调度不到带污点的控制面节点，所以控制面节点自己的系统日志不会进 Loki；TrainCache 的组件本来都跑在 worker 上，不受影响。

**多节点日志的汇合点是 Loki。** 不管日志来自哪个节点，最后都进同一个 Loki，用 `node` 标签区分来源节点。

Loki 部署在 `observability` 命名空间，单副本。数据存在容器内的 `/loki` 目录：`/loki/chunks` 是压缩存放的日志正文，索引是 tsdb 格式，也在 `/loki` 下。

当前用的是 filesystem 存储，底层卷是 emptyDir。**这意味着 Loki Pod 一旦重建，历史日志全部丢失。** 这是为了方便 kind 环境验证做的取舍，生产环境应换成持久卷或对象存储。

三类来源的日志都在同一个 Loki 里，没有分库，用标签区分：

```
{namespace="traincache", component="controller-manager"}
{component="agentd", node="node-1"}
```

DataLoader 的日志将来也进同一个 Loki，`component="dataloader"`。

## 三、日志里有什么

### 公共字段

契约规定的公共字段如下（完整约束见 8.1 §3.1），各字段的适用范围见表中说明：

| 字段 | 含义 |
|---|---|
| `time` | 时间戳 |
| `level` | `DEBUG` / `INFO` / `WARN` / `ERROR` |
| `msg` | 人读的消息 |
| `log_schema_version` | 日志格式版本，当前是 1，只增不改 |
| `component` | 哪个进程打的 |
| `version` | 程序版本 |
| `node` | 所在节点 |
| `dataset` | 数据集名 |
| `duration_ms` | 操作耗时，只在操作结束时出现 |
| `result` | `ok` / `error` / `requeue` / `skipped` / `stale` / `degraded` |
| `err` | 给人看的错误文本 |
| `err_class` | 错误分类，给聚合和告警用（契约字段） |
| `reason` | 跳过、降级、重试的原因 |
| `state` | 状态 |
| `phase` | 阶段（目前只作为指标标签） |
| `priority` | 预取优先级 P0–P3（目前只作为指标标签和命令行参数） |
| `sampled` / `sample_rate` | 这条是否被采样、采样率多少（契约字段） |

`err` 现在所有进程都在用，是可读的错误原文。`err_class` 设计上和 `err` 成对出现，一个给人读、一个给聚合用，取值固定为 `invalid_spec`、`not_found`、`unavailable`、`permanent`、`corrupt`、`io`、`timeout`；当前查询以 `err` 为准，`err_class` 的接入状态见 `TODO.md`（C）。

### 被提升为 Loki 标签的只有六个

`cluster`、`namespace`、`component`、`level`、`node`、`stream`。

其余字段（包括 `task_id`、`request_id`、`pod`、`path`）都留在 JSON 正文里。原因是这些字段取值太多，做成标签会把 Loki 的索引撑爆。

### 一条日志长什么样

```json
{"time":"2026-10-21T23:10:00Z","level":"INFO","msg":"preheat submitted","log_schema_version":1,"component":"controller-manager","task_id":"t-123","result":"ok","duration_ms":12}
```

## 四、怎么查日志

### 方式一：kubectl logs

最直接，但只能看到**当前还存在的 Pod**，而且受容器日志轮转限制（每容器 50Mi，最多 3 个文件）。

```bash
kubectl -n traincache logs deploy/traincache-controller-manager --tail=100
kubectl -n traincache logs -l app.kubernetes.io/name=traincache-agentd --tail=50
```

### 方式二：Loki 查询接口

先做端口转发：

```bash
kubectl -n observability port-forward svc/loki 3100:3100
```

然后查：

```bash
# 某个组件的最近日志
curl -s 'http://localhost:3100/loki/api/v1/query_range' \
  --data-urlencode 'query={component="controller-manager"}' \
  --data-urlencode 'limit=20'

# 某个节点上的 Agent 日志
curl -s 'http://localhost:3100/loki/api/v1/query_range' \
  --data-urlencode 'query={component="agentd", node="traincache-e2e-worker"}'

# 只看错误
curl -s 'http://localhost:3100/loki/api/v1/query_range' \
  --data-urlencode 'query={level="ERROR"}'

# 按任务号查（task_id 不是标签，要先解析 JSON）
curl -s 'http://localhost:3100/loki/api/v1/query_range' \
  --data-urlencode 'query={component="agentd"} | json | task_id="t-123"'
```

### 方式三：Grafana

```bash
kubectl -n observability port-forward svc/grafana 3000:3000
```

浏览器打开 `http://localhost:3000`，默认账号密码都是 `admin`（当前没有单独配置密码）。进入 Explore，数据源选 `Loki`，输入上面的查询语句即可。

### 方式四：临时打开 Debug

日志级别在进程内可调，只影响当前 Pod，Pod 重启后回到 env 值。env、端点契约与审计字段见 8.1 §7。

先做端口转发（manager / webhook / agentd 在 `traincache`，scheduler 在 `kube-system`）：

```bash
NS=traincache
POD=$(kubectl -n $NS get pod -l app.kubernetes.io/name=traincache-controller-manager -o jsonpath='{.items[0].metadata.name}')
kubectl -n $NS port-forward pod/$POD 6060:6060
```

另开终端，查询并修改级别：

```bash
curl -s http://127.0.0.1:6060/debug/loglevel                          # {"level":"info"}
curl -s -X PUT http://127.0.0.1:6060/debug/loglevel -d '{"level":"debug"}'
kubectl -n $NS logs $POD --tail=20 | grep 'log level changed'         # 审计:component/old/new/remote_addr
```

改完按方式一或方式二查日志就能看到 `level=DEBUG` 行；排查结束把级别改回 `{"level":"info"}`。agentd 把标签换成 `app.kubernetes.io/name=traincache-agentd`，scheduler 换成 `-n kube-system` 与 `app.kubernetes.io/name=traincache-scheduler`。

### 一个实际排查顺序

1. 先看 `{level="ERROR"}` 最近有没有新增。
2. 用 `{component="..."}` 缩到出问题的进程。
3. 需要定位具体任务时，用 `| json | task_id="..."`。
4. 需要定位节点问题时，加 `node` 标签。

跨层的排查路径（门控不放行、Agent 不可达等五种现象）见 `docs/8.1 design.md` 附录 A 的 runbook。

## 五、监控数据从哪来

### 数据来源：各进程的 /metrics

| 组件 | 端口与路径 | 说明 |
|---|---|---|
| controller-manager | `:9412/metrics/traincache` | 项目自己的指标 |
| controller-manager | `:9412/metrics` | controller-runtime 的通用指标 |
| webhook | `:9412/metrics` | 只有通用指标，没有项目指标 |
| scheduler | `:9412/metrics/traincache` | 项目自己的指标 |
| agentd | `:9411/metrics` | 项目自己的指标 |

### 抓取方式

Prometheus 每 15 秒来读一次，共两个抓取任务：

- `traincache-components`：抓 `/metrics`，覆盖 controller-manager、webhook、三个 agentd、scheduler
- `traincache-custom-metrics`：抓 `/metrics/traincache`，覆盖 controller-manager 和 scheduler

scheduler 也在第一个任务的 target 列表里，但 kube-scheduler 的 `/metrics` 返回 404，所以配置里先把它的抓取路径改成 `/metrics/traincache`，再把抓回来的序列全部丢弃。scheduler 的指标最终只由第二个任务存储，这样既不重复计数，也不会让第一个任务一直报错。webhook 没有项目指标，所以不进第二个任务。

两个任务都是 `up` 状态才算采集正常。

### 指标存哪

Prometheus 存在自己的 TSDB 目录 `/prometheus`，也是 emptyDir。**Pod 重建后历史指标会丢。** 当前 `--storage.tsdb.retention.time=6h`，只保留 6 小时。这是 kind 环境的配置，生产环境需要调大。

### 怎么查

```bash
kubectl -n observability port-forward svc/prometheus 9090:9090
```

浏览器打开 `http://localhost:9090`，或者直接用接口：

```bash
# 所有抓取目标是否在线
curl -s 'http://localhost:9090/api/v1/query?query=up'

# 当前处于 Hold 状态的任务数
curl -s 'http://localhost:9090/api/v1/query?query=traincache_controller_gate_tasks{state="hold"}'
```

Grafana 里也可以用 Explore 选 `Prometheus` 数据源，查询语句写法相同。

## 六、监控服务怎么运行

### 部署位置

全部在 `observability` 命名空间，清单在 `controller/deploy/observability/`，是一个独立的 kustomize 根，不会被主部署包含。

| 工作负载 | 作用 |
|---|---|
| `loki` StatefulSet | 存日志，单副本 |
| `grafana` Deployment | 查询界面，同时接 Loki 和 Prometheus |
| `prometheus` Deployment | 定时抓指标，单副本 |
| `fluent-bit` DaemonSet | 每个 worker 节点一个，负责收日志并送给 Loki（控制面节点没有） |

### 启停与自检

```bash
# 部署（会等待所有工作负载就绪）
bash controller/e2e/observability.sh up

# 自检：日志链路、指标链路、标签、数据留存
bash controller/e2e/observability.sh verify

# 拆除
bash controller/e2e/observability.sh down
```

`verify` 会做六件事：验证探针日志是合法 JSON、能按标签查到、Pod 删除后日志还在、Prometheus 目标在线、Grafana 两个数据源都在、kind 的日志轮转配置正确。

### 注意

- 镜像用官方短名（`prom/prometheus`、`grafana/loki` 等）。集群里的 containerd 不读宿主机的 mirror 配置，`observability.sh` 先在宿主机 `docker pull` 再 `kind load`。
- 日志轮转（每容器 50Mi、最多 3 个文件）写在 `controller/e2e/kind.yaml` 里，**只在下一次创建集群时生效**。改现有集群需要重建。

## 七、指标清单

### 控制平面

| 指标 | 看什么 | 能做什么 |
|---|---|---|
| `traincache_controller_reconcile_total` | 协调次数，按 controller 和结果分 | 判断控制循环是否在正常推进、失败率多高 |
| `traincache_controller_reconcile_duration_seconds` | 单次协调耗时 | 发现协调变慢、定位性能退化 |
| `traincache_controller_candidate_nodes` | 每次协调看到的候选节点数 | 判断节点池是否变小、筛选是否过严 |
| `traincache_controller_preheat_rpc_total` | 向 Agent 下发预热 RPC 的次数 | 看 submit/update/cancel 的量和失败率 |
| `traincache_controller_agent_poll_total` | 轮询 Agent 进度的次数 | 判断轮询是否异常频繁或失败 |
| `traincache_controller_pods_per_node` | GWAA 每节点分配的 Pod 数 | 看分配是否均衡 |
| `traincache_controller_gwaa_unassigned_pods` | 没被分配的 Pod 数 | 大于 0 说明节点不够或约束太紧 |
| `traincache_controller_gwaa_fallback_total` | GWAA 回退次数 | 看分配算法是否经常收敛不了 |

### 门控与调度

| 指标 | 看什么 | 能做什么 |
|---|---|---|
| `traincache_controller_gate_tasks` | 各状态的任务数（hold/released/degraded） | 看有多少任务卡在门控、有多少降级 |
| `traincache_controller_gate_hold_duration_seconds` | 任务在 Hold 状态停留多久 | 发现门控超时、评估放行策略是否太保守 |
| `traincache_scheduler_score_total` | 打分分支次数 | 看调度插件是否在正常工作 |

### Agent

| 指标 | 看什么 | 能做什么 |
|---|---|---|
| `traincache_agent_up` | 进程是否活着（1/0） | 最基本的存活告警 |
| `traincache_agent_degraded` | 是否降级（1/0） | 全部订单通道都 stalled 才为 1；单路状态看 `traincache_agent_ordersources` |

| `traincache_cache_misses_total` | 缓存未命中次数 | 找未命中的数据集和阶段 |

| `traincache_fetch_requests_total` | 回源请求次数，带原因 | 看回源压力和失败原因 |
| `traincache_fetch_bytes_total` | 回源字节数 | 估算带宽消耗 |
| `traincache_fetch_inflight_bytes` | 在途回源字节数 | 判断是否打满带宽 |

| `traincache_fetch_bandwidth_limit_bytes` | 配置的带宽上限 | 核对限速是否按预期生效 |

| `traincache_index_refresh_duration_seconds` | 索引刷新耗时 | 定位索引变慢 |
| `traincache_index_shards_loaded` | 已加载索引分片数 | 看前缀加载是否按预期工作 |
| `traincache_index_sweep_skipped_total` | 索引清理跳过的次数 | 排查清理逻辑是否被频繁跳过 |
| `traincache_gc_sweeps_total` | GC 清扫次数 | 看回收任务是否在跑 |
| `traincache_gc_blocks_removed_total` | 回收的块数 | 评估回收量 |
| `traincache_gc_objects_removed_total` | 回收的对象数 | 同上，针对对象存储 |
| `traincache_evict_blocks_total` | 淘汰删除的块数 | 看缓存盘压力 |
| `traincache_evict_protected_skipped_total` | 因被保护而跳过的淘汰数 | 判断保护机制是否过严 |
| `traincache_disk_usage_ratio` | 缓存盘使用率 | 磁盘告警的主指标 |
| `traincache_quarantined_blocks` | 坏块隔离数量 | 发现数据损坏 |

| `traincache_prefetch_lead_blocks` | 预取前沿领先消费游标多少块 | 判断预取是领先还是落后 |
| `traincache_prefetch_queue_depth` | 四个优先级队列的长度 | 看是否堆积 |
| `traincache_prefetch_cursor` | 预取调度游标位置 | 跟踪预取推进 |
| `traincache_prefetch_task_duration_seconds` | 预取任务从入队到完成的耗时 | 看预取时延 |
| `traincache_consumption_advance_total` | 消费推进事件数，按来源分 | 看 hook 和 inotify 是否都在工作 |
| `traincache_read_stall_seconds` | 训练侧读等待时间 | 直接反映训练是否被 IO 卡住 |
| `traincache_rescan_progress` | 重启重扫进度 0–1 | 重启后判断何时恢复完成 |
| `traincache_stage_switch_eta_seconds` | 阶段切换的预计耗时 | 看切换是否拖慢 epoch |
| `traincache_objectstore_conditional_write_supported` | 对象存储是否支持条件写（1/0） | 为 0 说明快照原子提交能力受限，需要关注 |

## 八、常见疑问

**Pod 删了，日志还在吗？** 在。fluent-bit 已经把它送进 Loki，Pod 删除不影响已入库的日志。`verify` 脚本专门验证了这一点。

**为什么 kubectl logs 看不到昨天的日志？** 容器日志有轮转上限：每个容器 50Mi，最多保留 3 个文件，超出部分被 kubelet 删掉。历史日志去 Loki 查。

**为什么重启 Loki 或 Prometheus 后数据没了？** 两个服务都用 emptyDir 存数据，Pod 重建就清空。这是 kind 环境的配置，生产要换持久卷。Prometheus 另外只保留 6 小时。

**为什么指标里没有 pod 名、task_id、request_id？** 这些字段取值太多，做成标签会让时序数据库膨胀。它们放在日志里，需要时用日志查（见第四节）。

**日志里的 version 显示 `dev` 或 `(devel)` 正常吗？** 正常。本地构建没有注入版本号：控制平面三个进程显示 `dev`，agentd 从 Go 的构建信息里取，显示 `(devel)`。正式构建注入版本号后就会显示真实版本。

**门控一直 Hold 怎么办？** 先看 `traincache_controller_gate_tasks{state="hold"}` 有多少，再看 `traincache_controller_gate_hold_duration_seconds` 的分布。如果同时 `traincache_controller_agent_poll_total{result="unavailable"}` 在涨，说明 Agent 侧有问题，先查 Agent 是否在线。完整排查路径见 9.1 附录 A。

**训练很慢，先看哪个指标？** 先看 `traincache_read_stall_seconds`，它直接反映训练读数据被卡了多久。再看 `traincache_cache_hit_ratio` 和 `traincache_prefetch_lead_blocks`，判断是命中率不够还是预取没跟上。
