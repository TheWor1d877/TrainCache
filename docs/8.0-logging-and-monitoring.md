# 日志与监控

目标：三层日志共用一个契约，给定一个 Pod 能一次查出 controller、Agent、DataLoader 三段。

三层日志共用一个契约，日志与指标各走一条采集链路。三层的字段、日志点与关联键见下文。

## 现状

控制平面已经可用。7.1 §9 列的十六类日志点全部实现，日志断言和指标断言都已通过。指标包在 `controller/internal/metrics`。

Agent 有日志，也有指标，42 个 metric family 在 `agent/metrics`。`agent/internal/logging` 已建立（component/version/level/context），`agentd/main.go` 的错误字段已统一为 `err`；逐块下载与缓存命中按「级别与采样」一节的规则汇总。

DataLoader 段由训练侧的轻量钩子适配器接入，不替换 PyTorch DataLoader；字段契约冻结为 v1（8.1 §4.3），适配器实现在 `agent/hooklib/`。仓库内的训练脚本在 `bench/` 和 `probes/` 里。

三层的关联键是 `task_id + node + generation`；跨进程传播、脱敏、采样与限流按下文契约执行。

## 采集链路

一条链路：容器 stdout 的 JSON → 节点 DaemonSet（fluent-bit）→ Loki → Grafana。

指标走另一条链路：各进程在 `/metrics` 暴露指标，Prometheus 单实例每 15 秒抓取一次，覆盖 `traincache` 和 `kube-system` 两个命名空间，Grafana 从 Prometheus 查指标。

几条硬约束：

- 所有进程只写 stdout/stderr，不写宿主机文件。
- Agent 不得写 `TRAINCACHE_CACHE_ROOT`。日志和缓存不抢同一块盘。
- 容器日志的上限交给运行时：`containerLogMaxSize`、`containerLogMaxFiles`。
- 中心存储保留期：默认 30 天（720h），Debug 7 天（168h），通过 Loki `retention_stream` 实现。Event 由 Kubernetes TTL 管。
- 审计日志单独一条管道，不混在这条里。

Loki 标签只放有界维度：`cluster`、`namespace`、`component`、`level`、`node`、`stream`。`request_id`、`pod`、`task_id`、`path` 不进标签，放 structured metadata 或 JSON 正文。

## 字段契约

公共字段是所有层都有的，其余按层叠加。

| 范围                  | 字段                                                                                                                                                                                                   |
|-----------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 全层                  | `time`、`level`、`msg`、`log_schema_version`、`component`、`version`、`node`、`dataset`、`duration_ms`、`result`、`err`、`err_class`、`reason`、`state`、`phase`、`priority`、`sampled`、`sample_rate` |
| 控制平面              | `warmup_task`                                                                                                                                                                                          |
| 控制平面 + Agent      | `cluster`、`namespace`、`snapshot`、`generation`/`seq`、`request_id`、`rpc`                                                                                                                            |
| 控制平面 + DataLoader | `pod`、`pod_index`                                                                                                                                                                                     |
| Agent + DataLoader    | `task_id`                                                                                                                                                                                              |

`log_schema_version` 从 1 起，只增不改。字段名一律小写 snake_case。

枚举固定：

- `level`：`DEBUG`、`INFO`、`WARN`、`ERROR`。
- `component`：`controller-manager`、`webhook`、`scheduler`、`agentd`、`dataloader`。
- `result`：`ok`、`error`、`requeue`、`skipped`、`stale`、`degraded`。
- `err_class`：`invalid_spec`、`not_found`、`unavailable`、`permanent`、`corrupt`、`io`、`timeout`。
- `rpc`：`SubmitPreheat`、`UpdatePreheat`、`CancelPreheat`、`GetPreheatStatus`。

几条规矩：

- `err` 和 `err_class` 必须成对出现。`err` 给人看，`err_class` 给聚合和告警用。
- `warmup_task` 和 `task_id` 是两个东西，多对一。不合并成一个 `task` 字段。
- `path`、`chunk`、`fp`、`pod_uid`、完整对象 URL 只在 Debug 出现。
- `task_id`、`request_id` 可以进 Info 正文，不得进指标标签。

日志是运维接口。被 runbook、看板、CI 引用的字段只能增不能改。要删或者改含义，走弃用周期，至少保留一个小版本，期间双写。

## 级别与采样

四级的分工：

- Debug：逐块、逐样本、逐节点的明细。默认关闭。
- Info：状态迁移、决策、周期汇总、任务完成。
- Warn：可恢复的异常、重试、跳过、未收敛、降级。
- Error：需要人介入。

高频路径不逐条记。Agent 逐块下载和校验只出每 60 秒一条 Info 汇总，带块数、字节数、失败数和 P50/P99。缓存命中和未命中的明细走 Debug，按 1/100 采样。hooksock 的正常帧不记 Info，只记格式错误和启动。DataLoader 每 batch 一条，每 60 秒一条分位汇总，单 batch 明细 1/100。淘汰和 GC 每轮一条 Info，单块 Debug 1/100。

限流用令牌桶。控制平面默认 100 行/秒、突发 200；Agent 默认 200 行/秒、突发 400。超限先丢 Debug，再丢 Info。Warn 和 Error 永不丢，丢了多少记 `log_dropped_total`。

去重：相同的 `(component, event, node, task_id, reason)` 在 60 秒内只出一条，下一个窗口带上 `suppressed` 计数。

采样判断放在读 `path`、`chunk` 之前。不要先把明细读出来再决定丢不丢。

## 脱敏

红线只有几条，但都是硬要求：

- 不记 Secret。
- 不记 `accessKey`、`secretKey`、`token`、`Authorization`。
- 不记带签名的 URL。含 `X-Amz-Signature`、`Signature`、`Expires` 这类查询参数的一律算。
- 不记训练样本、张量、文件正文。
- Info 级不记完整对象路径。对象存储端点只记 host。

`err` 落盘前过一遍 `Redact`，URL 形态的值再过 `RedactURL`。测试用哨兵 Secret 做负向验证，全量日志里不能出现。脱敏在 `core/logging`，两端 logger 的 handler 各包一层，写出前统一处理。

## 三层分别写什么

### 控制平面

控制平面已有基线，字段与级别按 8.1 §4.1 执行，业务逻辑不动。

十六类日志点的落点：`warmup/controller.go` 和 `dataset/controller.go` 的 reconcile 入口出口、`place.go` 的 Agent RPC、`logGateDecision` 的门控判定、`scoreNode` 的评分、webhook 准入、scheduler 打分、GWAA 分配、annotation 写入、落点偏离检查。

### Agent

Agent 的日志点：

- 启动、装配、退出带 `component` 和 `version`。
- 逐块下载和校验按 60 秒汇总，带块数、字节数、失败数和 P50/P99。
- 缓存命中、未命中、`read_miss` 的明细走 Debug 采样，指标是 `traincache_hook_read_miss_total`。

已经有的：`svc/preheat.go` 的任务生命周期、代际拒绝、窗口更新、取消；`svc/hooksock.go` 的收端就绪和帧错误；`svc/backfill.go` 的坏块隔离与修复；`svc/orders.go` 的订单通道降级恢复、`collector/heatmap.go` 的 inotify 溢出；`evictor/evictor.go` 的 GC 和淘汰；`svc/readerheartbeat.go` 的读声明和心跳。

`agent/internal/logging` 与 `controller/internal/logging` 导出 API 对称。两端 `New` 都在 JSON handler 外包 `core/logging` 的 `NewRedactingHandler`，日志写出前统一脱敏。

### DataLoader

以下是已冻结的字段与上下文契约（v1），随训练侧钩子适配器（`agent/hooklib/`）一起交付。

启动必须带的上下文：`component=dataloader`、`warmup_task`、`pod`、`pod_index`、`dataset`、`generation_at_start`、`hook_sock`、`log_schema_version`。

其余日志点四类：

- 数据源选择：`source=cas|origin`、`phase`、`stage_id`。
- miss 和预取命中：`chunk`、`reason=absent|corrupt`、`prefetch_ready`、`wait_ms`。
- 单 batch 分位：`batches`、`p50_ms`、`p95_ms`、`p99_ms`、`stall_ms`。
- 退出：`batches`、`total_wait_ms`、`unreported_frames`。

上下文从环境变量拿，由 webhook 注入：`TRAINCACHE_TASK`、`TRAINCACHE_POD`、`TRAINCACHE_POD_INDEX`、`TRAINCACHE_DATASET`、`TRAINCACHE_HOOK_SOCK`、`TRAINCACHE_GENERATION_AT_START`。

只读 env，缺了就记 `context_missing=true`，降级为只有本地日志，不影响训练。不新增读取 Pod annotation 的依赖。

钩子帧可以带可选字段 `warmup_task`、`pod`、`pod_index`、`dataset`、`generation`。缺省时按现有行为处理，保持 D33/D44 兼容。帧里不出现 `task` 与 `seq`，任务归属统一用 `warmup_task`。

## 关联

跨进程的主键是 `task_id + node + generation`。不引入分布式 traceId（7.1 §9.2 已定）。

目标查询：给定一个 Pod，用 `warmup_task + pod_index` 拉出 controller → Agent → DataLoader 三段。

`request_id` 的格式：`<uid>/<generation>/<unixnano>`。webhook 侧是 admission UID / 0 / 纳秒时间。

传播方式走 gRPC metadata，三个 key：`x-traincache-request-id`、`x-traincache-task`、`x-traincache-generation`。Controller 客户端注入，Agent 拦截器写进 context logger。

## 指标

日志链路自身的指标只有一个：`log_dropped_total`。

指标由 Prometheus 单实例抓取：每 15 秒从 controller-manager（:9412）、agentd（:9411）、webhook、scheduler 的 `/metrics` 拉一次，覆盖 `traincache` 和 `kube-system` 两个命名空间；Grafana 负责查询和看板。指标标签只放有界维度，`request_id`、`pod`、`task_id`、`path` 不进标签。

实测按暴露路径分两个抓取 job：

- `traincache-components` 抓 controller-manager、agentd、webhook、scheduler 的 `/metrics`，6 个 target 全 up。
- `traincache-custom-metrics` 抓 controller-manager 和 scheduler 的 `/metrics/traincache`，2 个 target 全 up。
- scheduler 的项目指标只由 custom job 抓；原 job 已经把这组件的项目指标 drop，避免重复计数。
- agentd 的项目指标在 `/metrics`，只由原 job 抓取。
- webhook 没有项目自定义注册表（源码没建独立 registry，也没配 ExtraHandlers），所以不进 custom job。这不是配置遗漏。
- `traincache_controller_gate_hold_duration_seconds_count` 已经能在 Prometheus 查到。

指标 family 的标签按本节的有界维度规则复核。

分工：

- 只进指标：计数、比率、分位、队列深度、磁盘利用率、`gate_tasks{state}`、`scheduler_score_total{result}`。
- 只进 Event：`GateReleased`、`GateDegraded`、`ConsumeOrderDefaulted`、`NodeDeviation`、`WarmupTaskMappingFailed`，以及对象 condition 变化。
- 只进日志：`request_id`、`task_id`、`pod`、`path`/`chunk`/`fp`、错误原文、决策分支细节。

禁止用日志做告警阈值。也禁止把 `request_id`、`pod`、`task_id` 放进指标标签。

## 配置

- `CONTROLLER_LOG_LEVEL`：控制平面级别，四级校验，改级别要重启。
- `TRAINCACHE_LOG_SAMPLE_RATE`：Info 采样率，默认 1.0。
- `TRAINCACHE_LOG_DEBUG_SAMPLE_RATE`：Debug 采样率，默认 0.01。
- 令牌桶、去重窗口、60 秒汇总窗口、1/100 采样，都是固定值，暂不开放配置。
- 容器日志轮转：kind 配置通过 KubeletConfiguration patch 设置 `containerLogMaxSize: 50Mi`、`containerLogMaxFiles: 3`，下次 `kind create cluster` 生效。

动态日志级别已实现，env、`/debug/loglevel` 端点契约与操作步骤见 8.1 §7。
