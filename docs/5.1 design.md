# 缓存核心库设计（design）

核心库回答三个问题：某个数据块在哪、块怎么落本地盘、块怎么下载。需求来自 `5.0 缓存核心库设计方法.md`

这份文档冻结接口签名、数据格式和包结构：实现者不许私改。确实要改，先回传 BLOCKED，由主对话裁决。决策与裁决在 `5.2 decisions.md`，测试清单在 `5.3 test.md`。

## 1. 库定位

一个无服务形态的 Go 库，编译进层2 Agent（Controller 侧组件也能用），不单独跑进程。它管三件事：

1. **记录有哪些数据块**——路径索引层：维护 `(path, chunkIndex) → 块指纹` 的映射，以快照形式存进对象存储。指纹是内容的哈希值，后面当键用；快照是一次提交后的完整索引版本，读侧只认最新一份。
2. **按内容落盘**——CAS 存储层：用 xxh3-128 指纹当键。CAS 即 content-addressed storage（内容寻址存储），文件位置由内容哈希决定，同样内容只存一份，读回来还要校验。
3. **按需下载**——抓取编排层：按字节限流、合并重复请求、校验失败就重下。

边界：库里没有服务进程、网络协议和调度逻辑，那些属于 Agent 和 Controller；索引不承诺跨路径去重，去重只发生在 CAS 层；core 不 import 训练语义。

## 2. 概念辨析

本文的「分片」一律指**索引分片**。它和 doc 1、probes/可行性探针报告.md、doc 4 里训练数据侧的 webdataset tar 分片是两类东西：tar 分片是打包好的训练数据文件，索引分片是路径索引表的切片。两类最后都存放在 MinIO 上，所以名字要写全。

| 术语 | 含义 |
|------|------|
| 数据分片（tar） | 上游训练数据集的打包文件，如 `shard-00000.tar`，百 MB 级，存在上游数据源；它的文件名字符串成为每条索引条目的 `path` |
| 数据块 | 一个 tar 按 64 MiB 等分后的物理单元，缓存/传输/去重的最小单位，存在对象存储 |
| 索引分片 | 路径索引表的切片，回答"某路径第 i 块对应哪个物理块"，存在对象存储 |
| manifest | 快照清单（manifest.json），记录这次快照由哪几个索引分片组成，存在对象存储 |
| 快照 | CURRENT 指针 + 快照清单 + 清单引用的索引分片 |

## 3. 总体架构与依赖方向

五个包，调用方向如下：

```
                ┌──────────── index ────────────┐
                │ Writer / Catalog / Collector  │   记录块→节点映射、快照、提交、刷新、回收
                └──────┬───────────────┬────────┘
                       │               │
            ┌──────────▼──┐      ┌─────▼──────────┐
            │    cas      │      │  objectstore   │   对 S3 兼容对象存储的抽象（含条件写入）
            │  本地块存储   │      └─────▲──────────┘
            └──────▲──────┘            │
                   │            ┌──────┴──────────┐
            ┌──────┴───────────┐│      fetch       │   下载编排：限流、合并、重试
            │  fetch（下载编排） │└──────▲──────────┘
            └──────▲──────────┘       │
                   │        ┌─────────┴──────────┐
                   │        │  internal/digest   │   xxh3-128 / sha256 封装
                   └───────►└────────────────────┘
```

`index` 管索引，`cas` 管本地块存储，`fetch` 管下载编排，`objectstore` 抽象 S3 兼容存储（条件写在这一层），`internal/digest` 封装 xxh3-128 和 sha256。依赖方向单向无环，这是硬约束：

- `index → cas、objectstore`
- `fetch → objectstore、cas`
- `publish → index、cas、objectstore`，`index` 不反向依赖 `publish`
- `cas → internal/digest`，只碰本地文件系统

`cas` 不依赖 `objectstore`：下载得到的字节流由 `fetch` 喂给 `cas.Put`，本地存储和远端存储因此解耦。

## 5. 核心接口（冻结约定）

本节六个小节的 Go 代码是冻结约定：签名、常量、结构体字段都不能改，要改先回传 BLOCKED。代码注释是行为契约（重点看错误返回值和并发语义），正文只补裁决出处和容易混的点。

### 5.1 objectstore

把 S3 兼容存储收成 6 个方法。`PutIfMatch` 是快照原子提交的关键：它保证"只有一个人能改 CURRENT"。

```go
package objectstore

var (
    ErrNotFound = errors.New("objectstore: object not found")
    ErrConflict = errors.New("objectstore: conditional write conflict")
)

// Store 是对 S3 兼容对象存储的最小抽象。
type Store interface {
    // Get 将对象内容完整写入 w；不存在返回 ErrNotFound。
    Get(ctx context.Context, key string, w io.Writer) error
    // Put 上传对象，返回服务端 ETag。对相同内容 ETag 必须稳定（S3 简单上传语义）。
    Put(ctx context.Context, key string, r io.Reader, size int64) (etag string, err error)
    // Delete 删除对象；对象不存在不算错误。
    Delete(ctx context.Context, key string) error
    // GetETag 返回对象当前 ETag；不存在返回 ErrNotFound。
    GetETag(ctx context.Context, key string) (string, error)
    // PutIfMatch 条件写入：expectedETag 为空串时要求 key 不存在（If-None-Match: *），
    // 否则要求当前 ETag == expectedETag（If-Match）。冲突返回 ErrConflict，不写入。
    PutIfMatch(ctx context.Context, key string, r io.Reader, size int64, expectedETag string) (newETag string, err error)
    // List 返回匹配 prefix 的全部对象键（字典序升序）；无匹配返回空切片（D19）。
    // 供 index.Collector.Sweep 枚举快照对象用。
    List(ctx context.Context, prefix string) ([]string, error)
}

// 构造器（接口冻结）：
func NewMock() *Mock
func NewS3Store(endpoint, accessKey, secretKey, bucket string, secure bool) (*S3Store, error)

// 块键与条件写探测（6.1 §5.12）：
func BlockKey(dataset, path string, chunk int64) string // <dataset>/blocks/<path>#<chunk>
// ProbeConditionalWrite 写临时键后用故意不匹配的 ETag 调 PutIfMatch：
// 后端支持条件写返回 nil；后端忽略前置条件返回 ErrConditionalWriteUnsupported；
// 其他存储错误原样返回。探测对象尽力删除。
func ProbeConditionalWrite(ctx context.Context, s Store) error
```

- ETag 是服务端给对象版本打的标记；S3 简单上传语义下它由内容决定，所以 `Put` 对相同内容必须返回稳定 ETag。
- `PutIfMatch` 就是对象存储上的 compare-and-swap：空串要求 key 不存在，非空要求当前 ETag 相等，冲突报 `ErrConflict` 且不写入。`List` 按字典序返回全部键，供 GC 枚举（D19）。

各 S3 后端对条件写支持度不一，`ProbeConditionalWrite` 负责兜底探测（5.0 §路径索引；裁决见 5.2 D7、Q3）。

Store 之外另有一个可选只读能力 `InfoLister`：`ObjectInfo{Key, Size, LastModified}` 与 `func ListInfo(ctx, s Store, prefix string) ([]ObjectInfo, error)`，`S3Store` 与 `Mock` 都实现，后端缺这个能力时 `ListInfo` 返回 `ErrListInfoUnsupported`。它给孤儿块清理提供对象年龄，`Store` 的 6 个方法不变。

### 5.2 cas

`cas` 管本地磁盘上的块。一个块文件 = 128 字节块头 + 数据，文件名就是内容指纹。下载的数据块流过内存时顺手算 xxh3-128 指纹。按每核约 10GB/s 的量级，算指纹不额外占 I/O，所以指纹能直接当存储键（5.0 §CAS存储层）。

```go
package cas

// 块头（header.go，字节布局见 §6.3）：
const (
    HeaderSize    = 128    // 块头字节数
    FlagHasSHA256 = 1 << 0 // flags bit0：块头含有效 sha256
)

const Magic = "TCBK" // 块头 magic（4 字节）

type Header struct {
    Version   uint16   // = 1
    Flags     uint16   // FlagHasSHA256 置位时 SHA256 字段有效
    BlockSize uint32   // 数据字节数（不含块头）
    XXH3      [16]byte // 数据指纹 = 存储键
    SHA256    [32]byte
}

func ParseHeader(b []byte) (Header, error) // 校验 magic/version/reserved 区；长度不足报错
func (h Header) Encode() [HeaderSize]byte  // 编码为 128 字节（reserved 区置 0）

type Fingerprint [16]byte // xxh3-128，作为存储键

func (f Fingerprint) String() string                    // 32 字符小写 hex
func FingerprintFromHex(s string) (Fingerprint, error)  // 解析 32 字符 hex（长度/字符不符报错）

type VerifyLevel int
const (
    VerifyXXH3        VerifyLevel = iota // 默认：只验 xxh3
    VerifyXXH3SHA256                     // 新写块时同时算 sha256 写入块头，读时双重校验
)

var (
    ErrCorrupt  = errors.New("cas: block verification failed")
    ErrNotFound = errors.New("cas: block not found")
    ErrInUse    = errors.New("cas: block is referenced or being read")
)

type Store struct { /* dir、verify、refcount 表（内部） */ }

func New(dir string, verify VerifyLevel) (*Store, error)

// Put 流式写入：边读边算指纹，写临时文件，完成后 rename 到 blocks/<fp[0:2]hex>/<fp hex>.blk。
// 同指纹并发写安全（rename 原子，最终文件完整）；返回指纹与数据字节数。
// 不做 fsync（丢失代价 = 重拉）。
func (s *Store) Put(ctx context.Context, r io.Reader) (Fingerprint, int64, error)

// Open 打开块并校验：读块头验证 magic/version，流式重算数据 xxh3（及 sha256，按块头
// flags 与 Store.verify 决定）比对；不符返回 ErrCorrupt（调用方负责 Remove 后重拉）。
// 校验通过后返回从数据区起读的句柄。
func (s *Store) Open(fp Fingerprint) (*BlockReader, error)

// Remove 删除块；仍有引用或读者（pin）时返回 ErrInUse。
func (s *Store) Remove(fp Fingerprint) error

// Evict 只删除块的本地副本，供 Agent 层磁盘淘汰用（D28）：refcount 不拦
// （引用是快照级逻辑簿记，与副本是否在本地无关），pin>0 返回 ErrInUse；
// 已不存在返回 ErrNotFound（与 Remove/Sweep 并发安全）。索引条目不受影响，
// 后续读取经 Catalog.Lookup 命中 + Open 得 ErrNotFound 后由 fetch 重下。
func (s *Store) Evict(fp Fingerprint) error

// Acquire/Release 引用计数：Acquire +1（引用计数 = 已提交快照对该 CAS 块的逻辑引用）；
// Release -1，归零后块进入可回收状态。读操作不占引用计数，用 Pin/Unpin 单独管理生命周期。
func (s *Store) Acquire(fp Fingerprint) error
func (s *Store) Release(fp Fingerprint)

// Pin/Unpin 读操作生命周期：Pin 计数 >0 时 Remove 必须返回 ErrInUse。
func (s *Store) Pin(fp Fingerprint) error
func (s *Store) Unpin(fp Fingerprint)

// List 枚举 blocks/ 下全部块指纹（D20）：忽略临时文件与非法文件名；供 GC 枚举用。
func (s *Store) List() ([]Fingerprint, error)

// Quarantine 把 Open 校验失败的坏块物理移入 cas 根下 quarantine/ 目录（与 blocks/ 并列），
// 不再出现在 List() 中。幂等：源块不在 blocks/（已在 quarantine 或从未存在）返回 nil；
// 目标已存在时 rename 原子覆盖。不检查 refs/pins（坏块隔离是正确性动作，引用计数是
// 索引层的逻辑关系，修复后同指纹块回原位、引用不变）；持 s.mu 与 Remove/其他 Quarantine
// 串行。仅真实 I/O 错误报错。
func (s *Store) Quarantine(fp Fingerprint) error

// ListQuarantined 枚举 quarantine/ 下全部块指纹（与 List 同规则：忽略临时文件与非法
// 文件名，按指纹字节序升序，无块返回空切片）。供修复队列与重扫描枚举隔离块用。
func (s *Store) ListQuarantined() ([]Fingerprint, error)

// RemoveQuarantined 删除 quarantine/ 下的块（修复成功后清理）；目标不存在返回 nil
// （同 objectstore.Delete“不存在不算错误”语义）。仅真实 I/O 错误报错。
func (s *Store) RemoveQuarantined(fp Fingerprint) error

// SetOpenObserver 安装实例级 Open 前置观察者：每次 Open（命中或缺失）在调用 os.Open
// 之前以请求指纹触发一次，仅表示"本进程即将读打开该块"；随后打开成败不影响触发。
// 传 nil 清除。观察者不改变 Open 的返回值与错误语义，与并发 Open 数据竞争安全。
func (s *Store) SetOpenObserver(fn func(Fingerprint))

type BlockReader struct { /* 包装 *os.File，从块头之后开始读 */ }
func (r *BlockReader) Read(p []byte) (int, error)
func (r *BlockReader) Close() error
func (r *BlockReader) Size() int64 // 数据字节数（块头 block_size）
```

容易混的四组概念：

- **`Remove` 对 `Evict`**：`Remove` 受引用计数约束；`Evict` 只删本地副本、引用计数不动（D28）。回收管正确性（删不再被引用的旧数据），淘汰管磁盘容量（删仍被引用块的本地副本），两个维度分开（5.0 §CAS存储层补充）。
- **`Acquire/Release` 对 `Pin/Unpin`**：引用计数记"已提交快照对块的逻辑引用"，pin 记"正在读的操作"；pin>0 时 `Remove` 必须报 `ErrInUse`。
- **`Put` 的临时文件叫 `tmp-<random>`**：临时文件写在 `blocks/` 目录下。指纹要读完整个流才算得出来，临时文件名不能带指纹；rename 原子，别的进程永远看不到写了一半的块。
- **`Quarantine` 不看引用计数**：隔离是正确性动作，修复后同指纹块回原位、引用不变（D24–D27）。

### 5.3 fetch

`fetch` 把远端对象变成本地块，同时满足三件事：不压垮网络、不重复下载同一对象、校验失败能自愈。

```go
package fetch

type Options struct {
    MaxInflightBytes int64 // 在途下载字节上限（信号量口径，非 goroutine 数），默认 1 GiB；预铺最多占一半
    MaxConnsPerHost  int   // 单主机连接数上限，默认 64
    MaxTasks         int   // 最大并发下载任务数，默认 8；预铺最多占一半
    MaxRetries       int   // 校验失败重下次数，默认 3
    // OnLocalOpen 在 Put 成功、Open 读回校验之前以块指纹调用一次（可为 nil）。
    // 通用钩子：core 不依赖 Agent 侧类型；实现不得阻塞（调用方通常仅做内存记账）。
    OnLocalOpen func(fp cas.Fingerprint)
}

// Admission 是下载任务在限流层的准入档位：在读是需求读补块与坏块修复——已经有人等在这次
// 下载上；预铺是预取（含显式预热）。排队出队顺序是另一条轴，由 Agent 的 P0~P3 队列决定，
// 与准入档位无关。
type Admission int

const (
    AdmissionReading   Admission = iota // 在读：按全场额度准入，不受预铺额度与让路门约束
    AdmissionSpeculative                // 预铺：受半额额度约束，在读在途时让路
)

var ErrTooManyRetries = errors.New("fetch: verification failed after max retries")

type Fetcher struct { /* objectstore.Store、*cas.Store、limiter、in-flight map（内部） */ }

func New(store objectstore.Store, cs *cas.Store, opts Options) *Fetcher

// MaxInflightBytes 返回实际生效的在途下载字节上限（Options 补齐默认值后）。
func (f *Fetcher) MaxInflightBytes() int64

// Fetch 下载对象（在读准入：需求读补块、坏块修复）：Acquire(expectSize) 字节信号量 → store.Get 流经 cas.Put 落盘 →
// Open 读回校验 → 失败则 Remove 后重试（≤ MaxRetries）→ Release 信号量。
// 相同 key 的并发 Fetch 合并为一次实际下载（in-flight map，等待者共享结果）。
// 返回块指纹。命中检查是调用方职责：先经 index.Catalog.Lookup 取指纹、cas.Open
// 验存在，未命中才调用本方法（对应 docs/2 "缓存命中就不触及数据源"）。
// 簿记契约：Fetch 不做 Acquire；调用方在首次写入时 Acquire 一次即可。Evict（D28）
// 只删本地副本不动引用，故副本被 Evict 后经本方法重下时不得重复 Acquire（D28）。
func (f *Fetcher) Fetch(ctx context.Context, key string, expectSize int64) (cas.Fingerprint, error)

// FetchWithAdmission 与 Fetch 相同，多了准入档位：预铺（预取）受半额任务/字节额度约束，
// 且在读有下载在途时先让路；在读的额度与让路门均不生效。
// 同 key 合并跨档位生效：后到的在读请求若撞上已在途的预铺下载，直接共享该次下载结果，
// 该次下载改按在读口径准入（promote），需求读不必排在让路门后面。
func (f *Fetcher) FetchWithAdmission(ctx context.Context, key string, expectSize int64, adm Admission) (cas.Fingerprint, error)
```

- 限流按在途字节数、不按 goroutine 数：小文件撑爆 goroutine、大文件撑爆内存，字节数是两种情况统一的度量（5.0 §限制并发抓取）。
- 在读/预铺分级：预铺额度固定取全场的一半（任务槽与在途字节各自折半，至少 1），在读始终能拿到另一半；在读有下载在途时预铺暂停接入，预取占不住唯一出口。
- 预铺已开始的下载不取消（数据仍会进缓存）；让路只拦新的预铺接入，故最坏等待是一块下载的收尾时间。
- 让路门只数在读在途、不数合并等待者，否则预铺持有者会被自己的合并等待者挡住；在读合并进来时预铺 owner 立即改按在读口径（`promote`）。
- 相同 key 的并发 `Fetch` 经 in-flight map 合并成一次真实下载，等待者共享结果。
- 命中检查归调用方（`Catalog.Lookup` → `cas.Open` → 未命中才 `Fetch`），缓存命中因此不碰数据源；`Fetch` 自己不 `Acquire`，被 `Evict` 后重下不得重复 `Acquire`（D28）。

四个组件的职责：`Writer.Commit` 把增量 upsert 合并进当前快照、重切分片、条件写 CURRENT（§7.1）；`Catalog` 内存放映射、定时刷新、`atomic.Pointer` 整份换表，`LoadPrefixes` 只加载相关分片（§7.2，D23）；`Collector.Sweep` 删"没人引用、也没人正在读"的对象（§7.3）；`ReaderRegistry` 用 `Declare` 登记读者并刷心跳，GC 把未过期 claim 的 `SnapID` 与 `PreviousSnapID` 都计入保护集合，claim 损坏时 `Sweep` fail-safe 跳过本次块删除（§7.3，登记动机见 5.0 §快照读者登记）。

字段约定：

- `Entry.Chunk` 是块序号，块字节范围 `[chunk*ChunkSize, +Size)`，末块可不足；偏移不落盘，读侧自己乘块大小推导（D4）。
- `Entry.Node` 记录块实际落在哪个节点，v1 保留留空（§10.6）。
- `ShardRef.Key` 是完整对象键，未变更分片跨快照复用首次创建时的键（D18）；`MinPath/MaxPath` 供读侧做前缀范围判定（D22）。
- 条目按 `(path, chunk)` 字典序排序，分片按条目数切，不按哈希切。

### 5.6 logging

日志字段脱敏，`traincache/controller` 与 `traincache/agent` 两个独立 module 共用，所以只依赖标准库。

```go
// Package logging 提供日志字段脱敏，供 controller 与 agent 共用。
package logging

// Redact 返回 s 的副本，其中命中敏感键的取值被替换为 "***"。
func Redact(s string) string

// RedactURL 返回 URL 的安全形式：去掉 userinfo，只保留 scheme://host 与 path，
// 敏感查询参数的值替换为 "***"，丢弃 fragment。解析失败返回 "***"。

// 字符串与 error 值过 Redact；值整体或片段是 http(s) URL 时再过 RedactURL。

```

- 敏感键（小写比较）：`accesskey`、`access_key`、`secretkey`、`secret_key`、`token`、`authorization`、`password`、`secret`、`credential`、`signature`、`expires`、`x-amz-signature`、`x-amz-credential`、`x-amz-security-token`。

- `RedactURL` 用 `net/url` 解析：清空 `User`，保留 scheme/host/path，敏感 query 参数的值换成 `***`（其他参数不动），丢掉 fragment；解析失败返回 `***`。
- `NewRedactingHandler` 覆盖消息、字符串值、`error` 值与 group（递归），`WithAttrs` 预挂的属性同样脱敏；属性名命中敏感键时值整体换成 `***`。构造 logger 时在 `slog.NewJSONHandler` 外包这一层，业务调用点不逐处手写。文本里嵌的 `http(s)` URL 按空白、引号等边界切出后交给 `RedactURL`。
- core 其他包不依赖 logging，logging 也不依赖 core 其他包。归属裁决见 5.2 D32。

## 6. 数据格式

### 6.1 对象存储键布局

所有索引侧对象都在 `dataset/<name>/` 下面，三类键：CURRENT 指针、快照清单、索引分片。

```text
<bucket>/
└── dataset/<name>/
    ├── snapshots/<snapID>/manifest.json
    ├── snapshots/<snapID>/shard-<fp8>.idx      # fp8 = 分片内容 xxh3 前 8 字节 hex
    └── CURRENT                                 # 内容："<snapID> <manifestFP8>"（空格分隔，无换行）
```

数据块对象按源站布局另放：`<数据集名>/blocks/<path>#<chunk>`（裸数据，键函数 `objectstore.BlockKey`，§5.1、§10.5）。本地缓存块布局见 §6.3。

- 快照逻辑上完整，物理上复用旧分片：没变的分片，对象键和内容指纹都不变，不用重传（D6、D18）。
- CURRENT 是唯一入口，改它等于切快照。校验链逐级背书，每一级的指纹由上一级担保：

```text
CURRENT 里的 manifestFP8
 └─背书→ manifest.json
      └─背书→ manifest 中每个索引分片的 ShardRef.Fingerprint
           └─背书→ 每条 Entry.fp
                └─背书→ 数据块内容（落盘时算出的指纹必须等于它）
```

### 6.2 索引分片（shard-<fp8>.idx）

- 格式是 JSON 数组，元素是 `Entry`（§5.4），字段名用全称；`fp` 编码为 32 字符小写 hex。
- 构建规则：条目先按 `(path, chunk)` 字典序排序，再按条目数切分；每片最多 `MaxEntriesPerShard` 条，默认 100_000（6.0 硬上限）。
- 完整性：分片内容的 xxh3-128 写进 manifest 的 `ShardRef.Fingerprint`；读侧下载后重算比对，不一致报 `ErrInvalidShard`。
- 路径范围：首末条目的 Path 写进 `ShardRef.MinPath/MaxPath`，读侧据此跳过无关分片（D22）。
- 索引表放不进 etcd（上限 1.5 MB），所以整表落对象存储（5.0 §路径索引）。

分片为什么选 JSON、体积估算等裁决理由见 5.2 D5。

### 6.3 CAS 块文件（blocks/<fp[0:2]hex>/<fp hex>.blk）

块头统一 128 字节，v1 就是最终格式，不做 64 字节变体（D3）。校验信息写在块头里，不需要额外的校验文件（5.0 §CAS存储层）。字节布局：

```text
offset  size  field
0       4     magic  "TCBK"（0x54 43 42 4B）
4       2     version = 1
6       2     flags   bit0 = 块头含有效 sha256
8       4     block_size   uint32 LE（数据字节数，不含块头）
12      16    xxh3_128     数据指纹 = 存储键 = 文件名
28      32    sha256       flags bit0 置位时有效，否则全 0
60      68    reserved     全 0（对齐到 128B）
128     n     数据
```

- 存储键永远是 xxh3-128，路径不变、去重逻辑不变；开 sha256 只是把校验从"默认单验"升级成"置位后双验"（5.0 §sha256校验）。
- `VerifyXXH3SHA256` 只影响新写入的块：老块 flags bit0=0，读时按自己的 flags 校验，不做全量重算（D13）。
- 隔离块与 `blocks/` 同级、同两级布局：`quarantine/<fp[0:2]hex>/<fp hex>.blk`，不出现在 `List()`，只出现在 `ListQuarantined()`（§5.2、D25）。

### 6.4 manifest.json

```text
{"snapshot_id":"...","created_at":"...","shards":[{"key":"dataset/<name>/snapshots/<snapID>/shard-<fp8>.idx","min_path":"/a/...","max_path":"/b/...","entries":N,"fp":"<完整hex>"}]}
```

manifest 只存引用和范围，真正的条目在分片里。`ShardRef` 各字段含义与复用规则在 §5.4（D18、D22）；`Fingerprint` 存完整 16 字节 hex，文件名只用前 8 字节。

## 7. 关键流程

### 7.1 提交事务（Writer.Commit，对应 6.0 步骤 1–5）

Commit 不改旧数据：新建一套对象，最后用一次条件写把 CURRENT 指过去。

1. **写新块**（发生在 Commit 之前）。调用方经 `fetch.Fetch` 或 `cas.Put` 把新块写进 CAS，然后 `cas.Acquire` 引用 +1。CAS 键是内容指纹，新块天然不覆盖旧块。
2. **写新分片。** 读当前快照 S1 和受影响分片，合并本次 entries，重排、重新切分，先写本地临时文件再 rename；未受影响分片直接复用旧键。
3. **上传对象。** 新分片和新 manifest 用独立键上传。提交前读侧看不到它们——读侧只认 CURRENT。
4. **验证完整性。** 提交前确认四件事：新 manifest 上传成功；引用的分片都在、指纹一致；分片条目数没超上限；引用的新块都已在 CAS 且 `Open` 校验通过。
5. **原子提交。** `PutIfMatch(CURRENT, "<newSnapID> <newManifestFP8>", expectedETag=MD5("<oldSnapID> <oldManifestFP8>"))`。成功则新快照生效；返回 `ErrConflict` 说明别人先提交了，重读最新快照重新合并、构建、提交，最多 `CommitMaxAttempts`（默认 5）次。

写盘原子性（5.0 §注意）由第 2 步的临时文件 + rename 保证，见 §7.4。

### 7.2 读侧刷新（Catalog，对应 6.0 步骤 6）

Catalog 每 `RefreshInterval`（默认 5 秒）读一次 CURRENT。内容没变就跳过；变了就走这条链：下载新 manifest → 逐个下载分片并验证指纹 → 构建新内存映射 → `atomic.Pointer` 一次性切换。加载过程中绝不逐个修改正在服务的旧映射；manifest 和分片都要过完整性校验。

`Start` 在调用方 goroutine 中运行（要后台执行就 `go c.Start(ctx)`），启动即先刷新一次；单轮刷新失败记录错误后继续循环，不影响原子切换语义。

按前缀加载（`LoadPrefixes`，对应 5.0 §索引分片按前缀目录加载）：

- 训练可能只需要某些路径的数据，全量索引分片能到 GB 级，全量加载浪费。manifest 只有 ShardRef 列表、体积小，仍全量下载；省掉的是无关索引分片的下载。
- 用 `ShardRef.MinPath/MaxPath` 对每个 prefix 做 D22 范围判定（公式见 §5.4 注释），只下载、校验、加载相关分片，局部映射原子切换；失败不动旧映射。
- 加载哪些前缀由 Agent 服务决定，库只提供能力（D23）。`LoadPrefixes` 与 `Refresh`/`Start` 二选一，不同时跑后台循环。
- 6.0 附录的两种模式对应：按数据集加载 = 构造时绑定 dataset、走 `Refresh`/`Start`；按路径前缀加载 = 走 `LoadPrefixes`。

### 7.3 回收（Collector.Sweep，对应 6.0 步骤 7 与快照读者登记）

删除范围限定在"窗口外、没人引用、没人正在读"的对象：

- **保留窗口**：CURRENT + 最近 2 个已提交快照（`RetainSnapshots`=3，D14）；"最近 2 个"按 snapID 字典序最大者取。CURRENT 指向的快照永不删除。
- **旧快照和分片**：窗口内仍被在读的 pin 者使用的快照，本次跳过；否则删 manifest，以及其他保留快照不再复用的分片对象。
- **旧数据块**：活块集合 = 保留快照索引可达的指纹 ∪ 读者 pin。只删同时满足"不在活块集合、refcount=0、pin=0"三条的块；有人在用的留到下次。
- 引用计数记录"已提交索引快照对块的逻辑引用"，不统计读操作；读操作生命周期由 pin 单独管（5.0 §CAS存储层注意）。
- **读者登记**：Agent 加载 S2 后写 `dataset/<dataset>/readers/<nodeID>.json`（带心跳时间戳），切快照时更新并保留上一快照宽限期；清理方核对所有登记，"没人声明 + 心跳过期 + 不是 CURRENT"才删。心跳过期就当读者死了，允许删，防止 Agent 崩了旧快照永远留着（5.0 §快照读者登记）。claim 损坏或读取失败时 `Sweep` fail-safe，跳过本次块删除（§5.4；机制取代分布式租约）。

### 7.4 CAS 写入与并发（cas.Store.Put，对应 6.0 写盘原子性）

- 写盘顺序：先写 `blocks/tmp-<random>` 临时文件（块头 + 数据），完成后 `rename()` 到 `blocks/<fp[0:2]hex>/<fp hex>.blk`。别的进程和 goroutine 永远看不到写了一半的块；孤儿临时文件不影响 `Open` 和后续 `Put`。
- 不做逐块 fsync：掉电丢块的代价就是重下（5.0 §注意；D11）。
- 多 goroutine 同时写同一指纹：各写各的临时文件，rename 原子覆盖，最后留下的文件一定完整。指纹等于内容，同指纹内容必相同，xxh3 碰撞概率按 0 处理（D9、D27）。

### 7.5 校验失败重下（fetch.Fetcher.Fetch，对应 6.0 Agent 下载示例）

链路：下载 → `cas.Put` → `cas.Open` 读回校验 → `ErrCorrupt` 就 `cas.Remove` → 重试，最多 `MaxRetries` 次 → 仍失败报 `ErrTooManyRetries`。重试间隔指数退避、100ms 起（5.2 Q6）。

这里的 `Remove` 安全：引用要等 `Fetch` 成功后由上层 `Acquire`，此刻没有引用也没有 pin。

## 9. 验收标准（总闸）

`cd core && go build ./... && go vet ./... && go test ./...` 全绿。单测重点覆盖 5.0 §标准 的四个场景，对应并发、崩溃、去重、损坏四条最容易出错的路径：

1. **多个 goroutine 同时写同一个块**：并发 `Put` 同一份内容 → 最终文件完整、指纹正确、无临时文件泄漏。
2. **写一半进程崩溃**：注入失败点让 `Put` 中途终止，或预置孤儿临时文件 → 重开后同内容 `Put` 完成，`Open` 不受影响。
3. **相同内容去重**：同内容 `Put` 两次 → 指纹相同，磁盘只有一份。
4. **校验失败后重新下载**：篡改块内容 → `Open` 报 `ErrCorrupt`，`Fetch` 自动 `Remove` 重下后恢复。

测试与用例清单在 `5.3 test.md`。

## 10. 多 tar 发布器（publish）

### 10.1 职责与位置

`core/publish` 是写侧编排，对应 6.0 步骤 1 的"写入方"：把一批 tar 源按 `ChunkSize` 切块，写进本地 CAS 和对象存储，生成 `index.Entry` 列表，最后只调一次 `index.Writer.Commit` 原子发布。

它不维护快照、不做读侧刷新、不回收数据：索引合并、分片构建、条件提交归 `index.Writer`。CLI 在 `core/cmd/trainpublish`，只解析参数、装配依赖。依赖方向 `publish → index、cas、objectstore`，`index` 不反向依赖 `publish`（§3）。

### 10.2 包契约（冻结）

```go
package publish

type Source struct {
    Path   string      // tar 文件名，即 Entry.Path；必须不可变
    Reader io.ReaderAt // tar 内容，允许并发按偏移读取
    Size   int64
}

type Options struct {
    Dataset     string
    ChunkSize   int64 // 0 = DefaultChunkSize（64 MiB）
    Concurrency int   // 0 = DefaultConcurrency（4）
}

type Result struct {
    SnapID       string
    Entries      int   // 本次发布的条目数（各 tar 切块数之和）
    Bytes        int64 // 各 Source.Size 之和
    UniqueBlocks int   // 本次观察到的不同内容指纹数（本地 CAS 去重）
}

func Publish(ctx context.Context, store objectstore.Store, cs *cas.Store,
    w *index.Writer, sources []Source, opt Options) (Result, error)
```

- `Source.Path` 取 tar 文件名，即索引路径；同批次内必须唯一，不能含 `#`（块键分隔符）。
- `Options.ChunkSize`/`Concurrency` 传 0 用默认值 64 MiB / 4。
- `Result.Entries` 是本次发布生成的条目数，不是提交后快照的总条目数（Commit 做 upsert 合并）。
- 跨路径内容相同的块，本地 CAS 只存一份，`UniqueBlocks` 按这个口径统计；对象存储仍按各 `Path` 分别保留 `<path>#<chunk>` 键，不跨路径合并。

### 10.3 CLI（trainpublish）

```text
usage: trainpublish --dataset <name> [options] <tar> [<tar>...]
       trainpublish --dataset <name> --check-dataset <path>
```

- 位置参数是 tar，`Path` 取 basename；同批次 `Path` 重复报 `ErrDuplicatePath`。
- 必需参数 `--dataset`；对象存储参数 `--endpoint`、`--access-key`、`--secret-key`、`--bucket`、`--secure`。
- `--chunk-size`（字节，默认 64 MiB）只在空桶首次发布时生效：桶根 `_traincache/format.json` 记录 `{"version":1,"chunkSize":N}`，后续发布读它；显式传不同值失败。改块大小必须清空桶重灌或换桶。
- `--concurrency`（默认 4）。
- `--work-dir` 指定临时目录，`--keep-work-dir` 结束后保留；`--probe-conditional-write` 发布前探测条件写。
- `--check-dataset` 只校验不发布：读桶级声明，比对 DataSet 文件的 `spec.datasetName` 与 `spec.chunkSize`，不一致退出 1。
- 成功打印 `Result` 摘要（snapID / entries / bytes / unique_blocks），失败非零码退出。

### 10.4 多 tar → 单快照

所有 tar 的条目合并成一个 `[]index.Entry`，只调一次 `Writer.Commit`，不按 tar 分批提交。任何一个 tar 或任何一块失败，整次发布失败且不 `Commit`——读侧永远看不到半成品快照。

对应 6.0 附录的上传示例：200 MB tar → 切成 4 块（3×64 MiB + 8 MiB 末块）→ 逐块上传 `<名>/blocks/shard-00000.tar#0`–`#3`、留 4 条 Entry → Entry 排序切索引分片上传 → 新 manifest → CURRENT 条件写入切换。

### 10.5 块键与「先块后 Commit」

- 块键统一由 `objectstore.BlockKey(dataset, path, chunk)` 生成：`<dataset>/blocks/<path>#<chunk>`（§5.1）。`agent/prefetch/pending.go` 与 `agent/rescan/repair.go` 的两份未导出实现改调这个函数，格式知识只维护一处。
- 每块顺序：按 `ReaderAt` 读 `[chunk*ChunkSize, +size)` → `cas.Put` 落本地、拿指纹并校验 → `store.Put(BlockKey, ...)` 上传远端。
- `Commit` 的完整性验证只看本地 CAS（`Open`），不看远端块对象，所以必须先传完全部块再 `Commit`，避免新快照指向远端不存在的块。
- 并发由 `Options.Concurrency` 限制；`Commit` 等所有块成功后只调一次。

### 10.6 Node 保留字段

`index.Entry.Node` 在 v1 固定留空：发布器不填节点信息，JSON 里因 `omitempty` 直接不出现（D31 ③、Q1 现行结论）。取值语义和去重策略等跨节点块放置落地后再定义；在那之前，不要给它赋予发布语义。

### 10.7 失败语义

- 任一块上传失败就不 `Commit`；已上传的远端块留着（孤儿块），不删。
- `Commit` 失败时 `Writer` 只 best-effort 删除本次尝试上传的分片和 manifest，发布器不删远端块对象——宁可多留，不可误删可能被其他快照复用的内容。
- `Path` 不可变：同一 Path 不能对应不同内容，tar 文件名要带版本或哈希（如 `shard-00000-v3-<hash>.tar`）；重复发布同 Path 且内容一致，按 upsert 幂等处理。
- 本地 CAS 是 `Commit` 的校验来源；发布完成后工作目录可以清理。
- 远端孤儿块由 `traincacheds gc --orphan-blocks` 清理：按全部快照重建活块集合，删除不在集合内、且最后修改时间早于 `--orphan-grace`（默认 24h）的块。发布器与 `Collector.Sweep` 不做这件事——前者怕误删仍被旧快照引用的内容，后者只处理快照对象和本地块。

## 11. 数据集管理 CLI（traincacheds）

### 11.1 定位

`trainpublish` 覆盖"增/改"（切块→上传→一次 Commit）；`traincacheds` 补删除、查询、回收触发三个口，是给运维/使用者用的数据集管理平面。

三条边界：

- 一切索引变更只走 `Writer.CommitChanges` 这扇单门——CLI 绕过快照直接改索引对象的路径不存在。
- 数据块删除只走 Collector 回收规则——只有"已提交快照不再引用"的块才进待收集。
- Agent 侧零改动——删除的传播靠已有的 Follow 快照切换，不新增 RPC。

### 11.2 命名规范（D34）

命令名按职责取，不统一前缀。`tc` 这个名字让给 Linux iproute2 的流量控制工具（`/usr/sbin/tc`）——本仓库 bench 装置大量用真 `tc` 限速，撞名必出事。

| 可执行 | 职责 | 说明 |
|---|---|---|
| `traincacheds` | 数据集管理（rm/ls/stat/gc），`core/cmd/traincacheds` | 本节交付 |
| `trainpublish` | 多 tar 发布，`core/cmd/trainpublish` | 独立离线工具 |
| `traincache` | Agent RPC 客户端（prefetch/status），在 agent/cmd | |

### 11.3 命令面

```text
traincacheds rm      <ds> --path p.tar[,…] | --prefix p/  [--dry-run] [--yes]
traincacheds ls      datasets | snapshots <ds> | entries <ds> [--prefix p/] [--limit n]
traincacheds stat    <ds> [--path p.tar]
traincacheds gc      <ds> [--orphan-blocks] [--orphan-grace 24h] [--dry-run] [--yes]
```

- `rm`：`--path` 删指定 tar 的全部块；`--prefix` 目录级批量（读旧快照 → 前缀过滤 → 一次 CommitChanges），这是主要形态（D33）。
- 安全阀：`rm`/`gc` 默认先 dry-run，打印影响的 Entry 条数与字节数；非交互环境实际执行必须带 `--yes`。`CURRENT`、仍被读者 claim 的快照受 §7.3 既有规则保护。
- `ls datasets`：按 `dataset/` 前缀枚举存在 CURRENT 的数据集（`objectstore.List`，D19）。
- `ls entries` / `stat`：复用 `Catalog.List`（D29）与 manifest 的 `ShardRef.Entries`，不新增 core 导出。
- `stat` 两个形态的开销不同：`stat <ds>` 只读 CURRENT + manifest（两次 GET），输出 `dataset snapshot shards entries`；`stat <ds> --path p` 才经 `Catalog.List(p)` 下载相关分片，加输出条目级的 `paths bytes`。条目级总量不在 manifest 里（§6.4），不带 `--path` 就不报，避免"看一眼"的命令悄悄拖全量索引。
- `gc`：手动执行一次 `Collector.Sweep`，与 Agent 30s 周期淘汰循环同款逻辑，纯触发不新建规则；同样默认 dry-run，`--yes` 才执行。
- `gc --orphan-blocks`：在快照回收之外再清远端孤儿块。候选 = 不被任何快照引用、且最后修改时间早于 `--orphan-grace`（默认 24h）的块。宽限期给在途发布留窗口（先传块后 Commit）；任一 manifest 或分片缺失、损坏时整轮放弃删除。
- 配置沿用 `TRAINCACHE_OBJSTORE_*` 环境变量族 + flag 覆盖，与 trainpublish 同名同口径；退出码 0 成功 / 1 运行错误 / 2 参数错误。

四个动词全部站在既有导出面上，唯一的新 core 能力只有 `CommitChanges`。

### 11.4 CommitChanges 契约（冻结）

签名与合并规则见 §5.4。三条语义约定：

1. **删除 = 新快照里不存在**：`commitOnce` 本就读全量旧条目重建分片，删除只是"这次没带上它"——没有 tombstone，没有标记对象。
2. **dels 指向不存在的条目是幂等 no-op**：过滤不命中不算错，与 `Delete`/`Release` 的"不存在不算错误"同族风格（D26）。
3. **puts 与 dels 冲突取 puts**：同一 `(path,chunk)` 既删又放，新值生效——"重写某块"一次提交完成。

删除语义借"全量再物化"的模型白拿，成本只是 API 签名宽了一点。

### 11.5 删除的传播路径

```text
traincacheds rm 提交 S2（不含目标条目）
  → Agent Follow 到 S2，映射中消失        ← 已有机制，零改动
  → 旧快照 → gc（Sweep）回收；远端孤儿块 → gc --orphan-blocks 回收
  → 训练 Pod 读被删 path → Lookup 未命中  ← 语义正确
```

v1 边界：各节点本地 CAS 里被删 path 的残留块副本不主动清理，靠磁盘淘汰自然消退。主动清需要 Agent 按删除事件扫本地块，而误清比滞留危险——旧快照可能仍被其他读者 claim（D33）。

### 11.6 规模边界

`commitOnce` 每次提交读全量旧分片重建（未变更分片复用旧键不重传）。低频批量管理操作没问题；删除/写入一旦变成高频交互，写放大和冲突重试会先出问题。管理平面的账要记在"提交频率"上，不是"命令实现"上。

### 11.7 验收标准

验收命令与判据见 `5.3 test.md` 的数据集管理一节。
