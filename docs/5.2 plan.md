# 缓存核心库实施计划（plan）

核心库按 13 个里程碑落地，每个里程碑有任务清单和验收命令。接口与格式在 `5.1 design.md`（下称 design），裁决在 `5.3 decisions.md`，测试清单在 `5.4 test.md`。

三个词的定义：**里程碑**是带任务清单和验收命令的阶段；**子代理**是只负责一小块编码任务的代理会话；**BLOCKED** 是子代理发现约定行不通时回传的"停下等裁决"状态。白名单的含义见 §0 规则 2。

## 0. 执行方式（固定）

五条规则对所有里程碑生效，目的有两个：不让多个子代理同时改同一个包；不让"子代理自称过了"变成验收结论。

1. **派活**：任务按七项模板下发（`[TASK] [CONTEXT] [INPUT] [WRITE] [DELIVER] [ACCEPT] [FORBID]`），自包含——design §5 签名、§6 格式的原文直接贴进任务，子代理不靠对话历史干活。
2. **白名单**：`[WRITE]` 精确到文件。同一文件同一时间只有一个写入者，白名单外的文件不碰。
3. **约定冻结**：design 的接口签名和数据格式不许私改。走不通就回传 BLOCKED（附理由和证据），主对话裁决、更新 design / decisions 后继续。
4. **验收**：主对话亲自跑验收命令，只认自己跑出来的结果，不采信子代理自报。失败就再派修复子代理（贴报错原文和复现命令），主对话不动代码。
5. **回传格式**：固定七项 `STATUS/FILES/SYMBOLS/TESTS/DECISIONS/BLOCKERS/NEXT`，不夹带大段代码。

## 2. 里程碑 M1：工程骨架 + objectstore

**目标**：把 design 的约定落成能编译的骨架；`objectstore` 完整实现（含条件写入），其余包先只声明接口。先做 objectstore 的原因：它是外部对象存储的唯一入口，接口和错误语义定下来，`cas`、`index` 的测试才有稳定的假后端。

**第 0 步（P0 前置验证）**验证两个外部假设：

1. 依赖可达性：`GOPROXY` 可用（候选 `https://goproxy.cn,direct`），能拉取 `github.com/zeebo/xxh3`、`github.com/minio/minio-go/v7`（环境事实：github.com 本体不可达）。拉不下来按 5.3 Q4 裁决，不继续。
2. S3 条件写入实测：对开发环境对象存储（bench 装置 MinIO、真实 COS/OSS/S3 均可）发一次带 `If-Match` / `If-None-Match: *` 的 `PutObject`（5.3 Q3）。不支持走 Q3 备选方案（乐观写 + 读回校验），objectstore 接口不变。

**任务清单**：

- `core/go.mod`：module `traincache/core`，go 1.26.0，依赖仅上述两个；
- `objectstore/store.go`：`Store` 接口 + `ErrNotFound`/`ErrConflict`（design §5.1 逐字一致）；
- `objectstore/mock.go`：内存 Mock，ETag = md5hex(content)（S3 简单上传语义），`PutIfMatch` 三态（不存在时写 / ETag 匹配时写 / 冲突报 `ErrConflict` 不写入）；
- `objectstore/s3.go`：minio-go 实现全部方法，`PutIfMatch` 用 If-Match/If-None-Match 头；
- `internal/digest/digest.go`：`XXH3_128`/`SHA256`/`NewXXH3`/`NewSHA256` 完整实现；
- 接口骨架：`cas/header.go`、`cas/store.go`、`cas/refcount.go`、`fetch/limiter.go`、`fetch/fetcher.go`、`index/format.go`、`index/writer.go`、`index/catalog.go`、`index/gc.go`，只声明签名 + doc 注释，方法体 `panic("TODO: Mx")` 或返回 `ErrNotImplemented`（design §5.2–5.4 逐字一致）；
- `objectstore/store_test.go` 单测。

**验收**：

```bash
cd core && go build ./... && go vet ./...          # 全绿，无错误
cd core && go test ./objectstore/...               # 全绿
```

判据：① 骨架编译通过；② objectstore 单测覆盖 `PutIfMatch` 三态（不存在→写成功；ETag 匹配→写成功且返回新 ETag；不匹配→`ErrConflict` 且原对象不动）；③ 骨架签名与 design §5 diff 抽查一致；P0 两项结果在 6.3 登记（Q3/Q4）。

## 3. 里程碑 M2：cas 块存储

**目标**：CAS 层完整实现，design §9 四场景单测全绿。

**任务清单**：

1. `cas/header.go`：128B 块头编解码（布局 design §6.3），magic/version 校验，`Header` 类型；
2. `cas/store.go`：`New(dir, verify)`（建 `blocks/`）；`Put` 流式读 → 同步算 xxh3（+可选 sha256）→ 写 `blocks/tmp-<random>` → rename 到 `blocks/<fp[0:2]hex>/<fp hex>.blk`（目录缺则 `MkdirAll`），不 fsync；`Open` 读块头验证 → 流式重算数据指纹比对 → 不符 `ErrCorrupt`，通过返回从块头之后读的 `BlockReader`（`Size()` = block_size）；`Remove` refcount>0 或 pin>0 报 `ErrInUse`，不存在报 `ErrNotFound`；
3. `cas/refcount.go`：`Acquire`/`Release`/`Pin`/`Unpin`（内存表，进程内语义）；
4. 四场景单测（测试名对应 design §9 场景）：`TestConcurrentPutSameBlock`、`TestCrashDuringWrite`（注入失败 + 预置孤儿临时文件两种）、`TestDedup`、`TestVerifyFailure`（篡改数据 1 字节 / 篡改 magic / `VerifyXXH3SHA256` 双校验语义）；
5. `internal/digest/digest_test.go`：四个哈希函数冒烟（M1 未建，M2 验收含 `go test ./internal/...`，白名单内补建）。

**验收**：

```bash
cd core && go test ./cas/... ./internal/... -race   # 全绿
```

判据：① 四场景全过且 `-race` 干净；② `Remove` 在引用/pin 非零时报 `ErrInUse` 有对应测试；③ 导出符号不超出 design §5.2 清单。

## 4. 里程碑 M3：fetch 抓取编排

**目标**：限流下载、指令合并、校验失败重下。

**在途字节**是已开下载、未落盘的字节总量；**信号量**按额度放行，拿不到就等；**in-flight map** 记录正在下载的 key，同 key 后来者直接等前一个的结果。

**任务清单**：

1. `fetch/limiter.go`：字节信号量（`Acquire(n)` 阻塞至在途 ≤ `MaxInflightBytes`，ctx 可取消）、单主机连接数、最大任务数；前台/后台分级（后台额度取一半、前台在途时后台让路）；默认值 design §8；
2. `fetch/fetcher.go`：`New`、`Fetch`（流程 design §7.5）；in-flight map 合并同 key 请求（等待者共享结果与错误）；重试 ≤ `MaxRetries`，退避按 5.3 Q6；
3. 单测（mock objectstore + `t.TempDir()` cas）：`TestInflightByteLimit`、`TestMergeSameKey`（mock 计数实际 `Get` 恰 1 次）、`TestRetryAfterCorrupt`、`TestRetryExhausted`、`TestCtxCancel`（无 goroutine 泄漏）。

**验收**：

```bash
cd core && go test ./fetch/... -race              # 全绿
```

判据：① 五个测试全过；② 重试路径上 `Remove` 发生在 `Open` 校验失败之后（计数断言）。

## 5. 里程碑 M4：index 读写路径

**目标**：分片/manifest/CURRENT 序列化、无冲突提交、Catalog 加载与 Lookup。并发留给 M5。

本节格式定义都在 design：分片是每片 ≤10 万条的小 JSON；manifest 记录快照由哪些分片组成；CURRENT 是指向当前快照的指针对象；ETag 是对象版本标识，条件写靠它判断"我读到的还是不是最新的"；upsert = 键存在就覆盖、不存在就插入。

**任务清单**：

1. `index/format.go`：`Entry`/`ShardRef`/`Manifest` 序列化（JSON，`cas.Fingerprint` 编码 hex，经 `json.Marshaler/Unmarshaler` 或等价手段）；键函数（design §6.1）；CURRENT 内容 `"<snapID> <fp8>"`（空格分隔、无换行）；分片构建：按 `(path, chunk)` 排序 → 按条数切（≤ `MaxEntriesPerShard`）→ 每片算 xxh3 → 文件名 `shard-<fp8>.idx`；
2. `index/writer.go`：`Commit` 无冲突路径——读 CURRENT（`ErrNoCurrent` = 空数据集首次提交，`expectedETag=""`）→ 读 manifest 与受影响分片 → 合并 upsert → 建新分片（未变更分片复用旧键不重传）→ 上传 → 验证（design §7.1 第 4 点）→ `PutIfMatch` 提交；
3. `index/catalog.go`：`Catalog` 构造、`Refresh`（下载 manifest → 逐分片下载验指纹，不符 `ErrInvalidShard` → 建映射 → `atomic.Pointer` 切换）、`Lookup`（未命中 `(Entry{}, false, nil)`；无快照 `ErrNoCurrent`）；
4. 单测：`TestCommitAndLookup`（跨 3 分片，缩小 `MaxEntriesPerShard` 触发）、`TestLookupMiss`、`TestShardFingerprintMismatch`（篡改分片 → `ErrInvalidShard` 且旧映射可用）、`TestFirstCommit`、`TestUpsertAndReuse`（第二次 Commit 只改 1 条 → 未变更分片键不变、变更分片为新键）。

**验收**：

```bash
cd core && go test ./index/...                    # 全绿
```

判据：① 五个测试全过；② 分片对象键与 manifest 指纹字段一致；③ CURRENT 解析格式与 design §6.1 一致。

## 6. 里程碑 M5：index 并发提交 + 后台刷新

**目标**：条件提交冲突重试、并发提交正确性、刷新循环原子性。**原子切换** = 读侧看到的映射要么全是旧快照、要么全是新快照，用 `atomic.Pointer` 一次换完。

**任务清单**：

1. `index/writer.go` 冲突路径：`ErrConflict` → 重读最新快照 → 重新合并构建 → 再提交，上限 `CommitMaxAttempts`（默认 5），耗尽返回含尝试次数的错误；
2. `index/catalog.go`：`Start(ctx)` 后台循环（`RefreshInterval` 默认 5s；ctx 取消退出；刷新失败记录错误、循环继续），启动即先刷新一次（语义登记 design §7.2）；
3. 并发单测（mock 的 `PutIfMatch` 支持 ETag 变化以模拟真实竞争）：`TestConcurrentCommit`（20 goroutine 各自提交不同 entries，全部条目出现在最终快照，无静默丢失）、`TestCommitConflictRetry`（两个 Writer 拿同一 CURRENT，恰一个生效，另一重试后两条数据都在）、`TestRefreshAtomicSwitch`（刷新循环中持续 Lookup，结果永远属于某一个完整快照）、`TestRefreshErrorTolerance`（注入一次分片损坏 → 循环继续、映射保持旧快照，修复后恢复）。

**验收**：

```bash
cd core && go test ./index/... -race              # 全绿，race 干净
```

判据：① 四个测试全过；② `-race` 无告警；③ 冲突重试后无条目丢失。

## 7. 里程碑 M6：GC 回收 + 端到端集成

**目标**：旧快照/分片/块安全回收 + 全链路端到端测试。**活块** = 保留窗口内快照引用可达的块；**孤儿块** = 谁都引用不到、可删的块；保留窗口 = CURRENT + 最近 2 个已提交快照（D14，选择规则 design §7.3）。

**任务清单**：

1. `index/gc.go`：`Collector.Sweep`（design §7.3）——活块集合 = 保留窗口索引可达指纹 ∪ 读者 pin；扫描 `cas` 目录，删"不在活块集合且 refcount=0、pin=0"的块；删窗口外且不被保留快照复用的 manifest 与分片对象（CURRENT 指向的绝不删）；
2. 单测：`TestSweepKeepsLiveBlocks`、`TestSweepRemovesOrphans`、`TestSweepSkipsPinned`、`TestSweepNeverDeletesCurrent`；
3. 端到端集成 `index/integration_test.go`（mock + 临时 cas + fetch 全链路）：fetch 下载落块 → `Commit` → `Refresh` → `Lookup` → `Open` 读回逐字节一致 → 第二次 Commit → 新条目可见、旧条目按窗口处理 → `Sweep` → 并发读（pin 持有）时 Sweep 不删在读块。

**验收（总闸）**：

```bash
cd core && go build ./... && go vet ./... && go test ./... -race   # 全部全绿
```

判据：① 全包通过、`-race` 干净；② 端到端逐字节一致；③ design §9 四场景仍全绿；④ 导出符号与 design §5 逐一核对忠实实现。

## 8. 里程碑 M7：索引分片按前缀目录加载

**背景**：6.0 新增该需求。数据块按需下载，索引却全量加载——训练可能只要 `/train-data` 下某些路径，索引主体涨到 GB 级后全量加载浪费。库提供能力（`LoadPrefixes`），加载哪些前缀归 Agent 服务决定；裁决 D22/D23 见 6.3。

**任务清单**：

1. `index/format.go` / `index/writer.go`：`ShardRef` 增 `MinPath/MaxPath`（json `min_path`/`max_path`），分片构建时填排序后的首末 Path；manifest 编解码同步；
2. `index/catalog.go`：`LoadPrefixes`（语义 design §5.4）：CURRENT → manifest（全量、小）→ D22 范围交叠判定过滤（多前缀取并集，同一分片去重只下载一次）→ 只下载/校验/加载相关分片 → 局部映射 `atomic.Pointer` 切换；空 prefixes = 空映射；含空串 = 全量；失败不动旧映射；
3. 单测 `index/prefix_test.go`（新建）：`TestLoadPrefixes`（mock 计数断言无关分片零下载）、`TestLoadPrefixesRangeOverlap`（边界跨前缀的分片任一前缀命中即加载、只下载一次）、`TestLoadPrefixesEmpty`、`TestLoadPrefixesErrorKeepsOldMapping`；
4. 既有 index 测试（M4–M6）不改动、保持全绿。

**验收**：


## 9. 里程碑 M8：cas 坏块隔离（Quarantine）

**背景**：7.0 要求把校验失败的块标记为坏块（6.1 design §5.7）；Quarantine = 把块从 `blocks/` 挪进 `quarantine/`，不再参与正常读取，也不进 GC 枚举。裁决 D24–D27 见 6.3。Agent 侧修复链（读遇坏块 → Quarantine → 修复队列 → fetch 重下 → Put → 校验通过 → RemoveQuarantined，并发修复复用 single-flight）在 7.1/7.2，不在本里程碑。

**任务清单**：

1. `cas/store.go`：Store 增私有字段 `rootDir`；`New` 时根下 `MkdirAll` `quarantine/`；增常量 `quarantineDirName` 与私有方法 `quarantinePath`；实现 `Quarantine` / `ListQuarantined` / `RemoveQuarantined`（语义 design §5.2）；List 与 ListQuarantined 抽私有 `listBlockDir` 复用，行为不变；

3. `index/gc.go` 零改动：Sweep 经 `cs.List()` 枚举，quarantine 与 blocks/ 并列，天然不进枚举。

**验收**（与 6.2 M0 判据一致）：

```bash

cd core && go test ./... -race -count=1                     # 全绿
```

判据：① 三方法签名与 6.1 design §5.7 逐字一致；② 无清单外新导出符号；③ 既有测试零改动全绿；④ gc.go/go.mod/go.sum 零变化。

## 10. 里程碑 M9：cas.Evict 本地副本淘汰

## 14. 里程碑 M11：多 tar 发布器（core/publish + trainpublish）

**背景**：训练数据以多个 tar 发布。发布器一次把整批 tar 切块上传、只提交一个快照，读侧就不会看到"每传一个 tar 变一次"的中间态。契约冻结于 design §10 与 D31。

**任务清单**：

1. `objectstore/blockkey.go`：导出 `BlockKey(dataset, path, chunk)` = `<dataset>/blocks/<path>#<chunk>`；替换 `agent/prefetch/pending.go`、`agent/rescan/repair.go` 的未导出实现并删重复格式知识；agent 行为不变，补回归断言；
2. `publish/publish.go`：校验（sources 非空、Path 非空且不含 `#`、批内唯一、Size ≥ 0，Options 零值回退）→ 逐源切块（末块可不足），并发上限 `Concurrency`，每块先 `cas.Put` 再 `store.Put(BlockKey, ...)` → 汇总 `[]index.Entry`（Node 留空）→ 全部成功后调**一次** `w.Commit`；任一块失败立即中止且不 `Commit`；`Commit` 失败不删远端块；返回 `Result{SnapID, Entries, Bytes, UniqueBlocks}`；ctx 取消贯穿全程；
3. `cmd/trainpublish/main.go`：接线 design §10.3 的参数（`--dataset` 必需；endpoint/凭证/bucket/`--secure`；`--chunk-size` 默认 64 MiB；`--concurrency`；`--work-dir`/`--keep-work-dir`；`--probe-conditional-write`），打开 tar 构造 `[]publish.Source`，装配 `objectstore.NewS3Store`、`cas.New`、`index.NewWriter` 后调 `Publish`，打印 `Result`，失败非零退出；
4. 单测 `publish/publish_test.go`：`TestPublishMultiTarSingleSnapshot`（CURRENT 条件写恰 1 次）、`TestPublishChunkBoundaries`、`TestPublishBlockBeforeCommit`（顺序断言）、`TestPublishBlockUploadFailure`（无 CURRENT）、`TestPublishCommitFailureKeepsBlocks`、`TestPublishDedupAndResult`、`TestPublishValidation`；
5. CLI 冒烟：缺 `--dataset` 退出码 2；正常参数走到 `Publish`（注入 `run` 函数或本地 mock）。

**验收**：

```bash
cd core && go build ./... && go vet ./... && gofmt -l .     # 全绿、输出为空
cd core && go test ./publish/... ./objectstore/... -race -count=1
cd core && go test ./... -race -count=1                     # 全量回归
```

判据：① 三命令全绿；② 多 tar 只产生一个快照且全部条目可 Lookup；③ 块上传先于 `Commit`（顺序断言）；④ 任一块失败无 CURRENT；⑤ `Commit` 失败后远端块仍在；⑥ `Entry.Node` 恒空；⑦ agent 两处块键输出与 `objectstore.BlockKey` 逐字一致且既有 agent 测试全绿；⑧ go.mod/go.sum 零变化。

## 16. 里程碑 M13：数据集管理（CommitChanges + traincacheds）

**背景**：写侧只有 trainpublish 的"增/改"入口，删除、查询、回收触发没有 CLI。删除借"全量再物化"的提交模型表达为过滤，不需要 tombstone（D33）；命名统一 `traincache` 前缀（D34）。契约冻结于 design §5.4/§11。

**分三小步串行交付**（M13a 先行，纯读零 core 改动）：

1. **M13a 只读命令**：`traincacheds ls datasets|snapshots|entries` + `stat`。复用 `objectstore.List`（D19）、`Catalog.List`（D29）、manifest `ShardRef.Entries`；core 零改动。
2. **M13b CommitChanges**：`index` 新增 `Delete{Path, Chunk}` 与 `Writer.CommitChanges`（design §5.4 逐字一致），`commitOnce` 合并段加过滤，`Commit` 改为薄包装。新单测：删除后新快照不含目标条目且旧快照逐字不变仍可 Lookup / `Chunk=-1` 删整 path / puts 与 dels 冲突取 puts / dels 打空幂等 / 前缀批量与单 path 提交结果一致 / 既有 Commit 用例零改动全绿。
3. **M13c rm + gc**：`traincacheds rm`（dry-run 默认、`--yes` 门槛、输出影响条数与字节数）、`gc`（一次 `Collector.Sweep`，`--dry-run` 只报不删）。

**任务要点**：

- CLI 装配学 trainpublish：`deps` 可注入、mock store 单测不连网、退出码 0/1/2、`TRAINCACHE_OBJSTORE_*` 环境变量族；
- `rm --prefix` 在 CLI 侧展开：读旧快照 → 前缀过滤得 path 列表 → 一次 `CommitChanges`；core 的 `Delete` 保持精确 `(path, chunk)` 粒度；
- `ls datasets`：枚举 `dataset/` 前缀下存在 `<ds>/CURRENT` 的数据集名；
- 本地残留副本不清理（design §11.5 边界），验收不出现"删完后各节点本地块消失"的期望。

**验收**：

```bash
cd core && go build ./... && go vet ./... && gofmt -l .       # 全绿、输出为空
cd core && go test ./index/... -race -count=1                 # CommitChanges 新用例 + 既有用例
cd core && go test ./... -race -count=1                       # 全量回归
```

判据：① 三命令全绿；② `Commit` 行为与 M4/M5 既有用例逐字一致（只许加包装不许改语义）；③ 删除提交后旧快照对象一个不少（不可变原则，mock 计数断言无 DELETE）；④ `Catalog.Refresh` 到 S2 后被删条目 Lookup 未命中；⑤ dry-run 不产生任何写操作；⑥ 新导出符号只有 `Delete` 类型与 `CommitChanges` 方法；⑦ go.mod/go.sum 零变化。
