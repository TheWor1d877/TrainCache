# 日志与可观测性关键决策

## ADR-001 存储选 Loki 而非 Elasticsearch

结论：起步阶段用 Loki 配 Grafana 做日志中心存储，不引入 Elasticsearch。
原因：Loki 只给少量标签建索引、正文压缩存放，查询以组件、任务、节点、原因与请求号为主，标签加结构化元数据就够用，写入成本与运维复杂度都低；Elasticsearch 给全文建倒排索引，存储与集群成本都高，只有出现跨字段任意全文检索的硬需求时才重新评估。

## ADR-002 只做有界关联，不引入分布式 tracing

结论：只做有界关联，给定一个 Pod 用预热任务名加 Pod 序号把控制平面、Agent、DataLoader 三段日志拉出来，不引入 OpenTelemetry 完整 tracing，跨进程主键是任务号、节点与代际。
原因：三段日志跨进程，串不成一条链路；完整 tracing 要给每次请求挂跨进程 traceId 并在三段都接线，改造成本高，对当前排障场景收益有限。

## ADR-003 只写 stdout，Agent 绝不写缓存盘

结论：所有进程只写 stdout 与 stderr，由容器运行时负责轮转、采集器读取收集；Agent 不得把日志写进缓存根目录。
原因：日志写到哪儿影响轮转、采集与磁盘争用，进程自写文件到宿主机、写进缓存盘、只写 stdout 三个候选里选了 stdout；容器运行时原生就管容器日志轮转，采集链路统一；日志与缓存同盘时日志 IO 会和预取争带宽。

## ADR-004 指标标签只放有界维度

结论：标签只放 cluster、namespace、component、level、node、stream 这类有界维度；请求号、Pod 名、任务号与路径一律不进指标标签，也不建 Loki 标签，改放结构化元数据或 JSON 正文，查询时再过滤。
原因：标签都是索引项，取值近乎无限的字段每来一个请求就多一套索引项，进标签会撑爆索引、拖慢查询，只有种类数得清的维度能当标签；告警阈值只从指标取。

## ADR-005 不新造 task 字段做二次抽象

结论：保留 warmup_task 与 task_id 两个字段，保持现有语义，不合并不新造统一的 task。
原因：控制平面用 warmup_task、Agent 与 DataLoader 用 task_id，两者多对一，语义不同，强行合并会丢信息并破坏已冻结的字段语义。

## ADR-006 Warn 与 Error 永不采样

结论：日志超限时先丢 Debug、再丢 Info；Warn 与 Error 永不丢，并计数丢弃条数；必要时临时提高采样率要留审计记录。
原因：Warn 与 Error 是需要人工介入的信号，采样会掩盖稀有但致命的错误，排障时缺样本；永久、IO 与损坏三类错误不得被采样丢弃。

## ADR-007 脱敏实现归属核心库

结论：在核心库里提供脱敏包，给出 `Redact`、`RedactURL` 与 `NewRedactingHandler`；控制平面与 Agent 两端在构造 logger 时把 JSON handler 包一层。
原因：脱敏两端都必须做，但控制平面与 Agent 是互不引用的独立模块，两端各写一份会产生规则漂移；核心库是两端共同依赖，该包无状态且只依赖标准库；规则随核心库版本演进。

## ADR-008 warmup_task 的适用范围

结论：warmup_task 的适用范围定为控制平面与 DataLoader；日志字段中不出现 task；环境变量只作为变量名存在，落日志字段时写 warmup_task。
原因：DataLoader 需要通过 warmup_task 与控制平面关联，否则跨层排障断链；新造 task 字段会破坏已冻结的字段语义。

## ADR-009 Agent 日志封装与控制平面镜像对称

结论：Agent 的日志封装放在 `agent/internal/logging`，导出与控制平面镜像对称的三个入口，跨端共用的脱敏走核心库。
原因：Agent 需要与控制平面对称的日志初始化入口，散落在服务层里初始化不利于统一；Go 的 internal 目录限制跨模块导入，避免这个包被外部依赖。

## ADR-011 指标后端采用 Prometheus

结论：指标后端采用 Prometheus 单实例，与 Loki 同属观测栈的独立 kustomize 根；按 15 秒间隔抓取 controller-manager、agentd、webhook、scheduler 的 `/metrics`，覆盖 traincache 与 kube-system 两个命名空间；Grafana 同时接入两者。
原因：Loki 只承载日志，指标的长期抓取、趋势查询与告警需要专门后端，托管或多副本 Prometheus 在单集群规模下不必要；Prometheus 是 `/metrics` 抓取协议的事实标准且与 Grafana 原生集成；单实例没有高可用，Prometheus 故障期间指标断档，跨集群汇聚要靠远程写或联邦。

## ADR-012 观测栈使用独立 kustomize 根与单独 e2e 脚本

结论：观测栈目录作为独立 kustomize 根，不被主部署清单引用；验收脚本单独提供，不并入主 e2e。
原因：观测栈与业务控制平面的部署生命周期不同，体积与资源开销也远大于主清单，并入主清单会让业务部署背上重依赖；独立根可以单独安装、升级和卸载，单独验收脚本失败不阻塞主链路。代价是要显式 apply 两个根，只部署主清单时没有可观测性。

## ADR-013 指标按暴露路径拆两个抓取 job

结论：第一个 job 抓 controller-manager、agentd、webhook、scheduler 的 `/metrics`；第二个 job 抓 controller-manager 与 scheduler 的 `/metrics/traincache`；scheduler 的项目指标只由第二个 job 承载，第一个 job 对该组件的序列做 drop；agentd 的项目指标在 `/metrics`，只由第一个 job 抓；webhook 没有项目自定义注册表，不进第二个 job。
原因：项目指标与控制平面通用指标暴露在不同路径，统一抓 `/metrics` 覆盖不了 `/metrics/traincache` 这条路径；scheduler 的项目指标要避免与通用 job 重复计数。代价是要维护两个 job 与一条 drop 规则，新增组件时要明确它属于哪个 job。

## ADR-014 动态日志级别走本地端点而非 ConfigMap

结论：动态级别由核心库的进程级级别变量承载，经只绑回环的 `/debug/loglevel` 端点读写，不用 ConfigMap 热加载；端点不鉴权，不进 Service，不加 NetworkPolicy 例外，访问必须经 kubectl port-forward；级别不持久化，进程重启回到环境变量值；每次成功修改写一条 Info 审计日志，字段固定 component、old、new、remote_addr。
原因：调级别是排障时的一次性动作，要的是即时生效和可追溯；ConfigMap 方案需要挂卷、watch、额外 RBAC，还会把运行时状态写回集群对象；端点方案只多一个回环 listener，监听失败只记 Error，不影响业务进程。级别只对当前 Pod 生效，多副本要逐个改。

## ADR-015 网关作为独立 component 复用核心库日志封装

结论：网关不新写日志封装，初始化只调用核心库的脱敏与采样实现，日志 component 固定为 gateway，字段与网关模块自己的日志设计一致；不新增采样规则，也不绕过脱敏。
原因：脱敏、采样、动态级别是三条已冻结的契约，重写会分叉；Agent 侧的薄封装已证明够用，Go 进程共用同一套处理器，调用点不重复实现。component 是日志契约的一部分，枚举一旦随发布固定，新增取值要同时改查询语句与看板，所以 gateway 现在登记。

## ADR-016 checkpoint sidecar 登记为独立 component

结论：checkpoint 旁路进程的日志 component 固定为 checkpointd，进公共字段的 component 枚举；复用核心库的脱敏与采样，不新增采样规则，也不给它单独的 Loki 标签或 Prometheus 指标，Prometheus 不抓它的 `/metrics`。
原因：sidecar 跑在训练 Pod 内，进程一多，日志来源就要能按组件筛；checkpointd 已经是实际取值，枚举不登记就会被采集侧当成未知值丢掉。枚举只增不改，新增取值仍要同步查询语句与看板。
