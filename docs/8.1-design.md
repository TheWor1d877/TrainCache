# 日志与可观测性设计

三层日志共用一个字段契约与一条采集链路：给定一个 Pod，能在中心存储里用预热任务名加 Pod 序号把控制平面、Agent、DataLoader 三段日志一次拉出来。契约先定，日志量后调。

## 三种信号的分工

| 信号 | 适合承载 | 不适合承载 | 落点 |
|---|---|---|---|
| 日志 | 单次决策的上下文、错误原文、高基数字段 | 计数、趋势、告警阈值 | 全部 Go 进程写 stdout 单行 JSON，DataLoader 侧同样走 stdout JSON |
| 指标 | 计数、比率、分位、容量、告警 | 单任务排查、任意维度切片 | 控制平面 `controller/internal/metrics`，Agent `agent/metrics`，各进程在 `/metrics` 暴露，由 Prometheus 抓取 |
| Kubernetes Event | 对象生命周期与面向使用者的原因 | 高频明细、跨进程关联 | 门控放行与降级、默认切分、落点偏离、注入降级 |

一条信息进哪个信号，看它要回答什么问题：要计数、告警或跨 Pod 聚合的进指标；要在 `kubectl describe` 里让用户看到对象为什么不动，进 Event，日志可以再写一份但不能是唯一来源；其余排查上下文进日志。

两条硬规则：告警阈值只从指标取；请求号、Pod 名与任务号不进指标标签，这三个取值近乎无限，进标签会让时间序列数量失控。

## 日志分层

脱敏、采样限流、进程级级别、错误分类与请求身份五样能力放在核心库的日志包里，控制平面与 Agent 都依赖它，谁都不重复实现。

- 核心库 `core/logging` 提供字符串脱敏、URL 脱敏、写出前统一脱敏的 handler、按级别取采样率并折叠重复片段的 handler、进程级级别变量、错误分类函数、请求身份读写函数。
- `controller/internal/logging` 与 `agent/internal/logging` 各自导出三个入口：构造进程 logger、把 logger 放进 context、从 context 取 logger。两者 API 对称，取不到 logger 时回落到 slog 默认 logger。
- 控制平面三个进程在各自的 main 包里初始化 JSON handler，输出写 stderr，带上 component 与 version，级别由 `CONTROLLER_LOG_LEVEL` 做四级校验。
- Agent 在 `cmd/agentd/main.go` 经 `agent/internal/logging` 设置 JSON handler，注入 component、version 与 schema 版本号，错误字段统一为 `err`；Agent 的指标在 `agent/metrics`，共 42 个 metric family。
- 训练侧 DataLoader 由 `agent/hooklib/` 的轻量钩子适配器接入，不替换 PyTorch DataLoader；`bench/` 与 `probes/` 里的训练脚本直接用 PyTorch loader。
- 观测栈在 `controller/deploy/observability/` 这个独立 kustomize 根，含 fluent-bit、Loki、Prometheus、Grafana；验收脚本是 `controller/e2e/observability.sh`，支持 up、verify、down 三个动作。

### 控制平面的日志点

控制平面十七个日志点全部在码，每个点写明触发条件、级别、必带字段与用途：

- warmup 调和入口与出口：每次调和一条，Info，字段 `warmup_task,generation,request_id,duration_ms,result`，是生命周期起点。
- dataset 调和入口与出口：每次调和一条，Info，字段 `dataset,generation,request_id,duration_ms,result`，是数据面校验起点。
- 状态迁移与终态短路：状态或阶段变化时一条，Info，字段 `warmup_task,state,reason`，解释对象为什么不动。
- 规格、快照与存储校验失败：校验返回错误时一条，Warn 或 Error，字段 `dataset,snapshot,reason,err`，把输入问题与依赖问题分开。
- 候选筛选结果：每轮筛选后一条，Info，字段 `warmup_task,nodes,accessible,agent_ready,candidates,reason`，候选为零时的首要线索。
- Agent RPC 成功：下发、更新或取消返回后一条，Info，字段 `warmup_task,task_id,pod,node,generation,rpc`，确认下发是否到达；调用点在 `place.go`。
- Agent RPC 失败：返回错误时一条，Warn 或 Error，上面那组字段加 `err` 与 `err_class`；永久性错误进 Error，可重试错误交调和退避重试。
- 进度轮询：状态或序号变化时一条，Debug，字段 `task_id,node,generation,seq,ready`，看就绪位图推进。
- GWAA 分配变化与未收敛：分配与已下发不同或达到轮次上限时一条，Info 或 Warn，字段 `warmup_task,assign,rounds,actions,unassigned,reason`；assign 是 Pod 到节点列表的对象，形如 `{"p0":["n0","n1"]}`。
- 消费顺序解析与默认切分：显式订单或默认切分时一条，Info，字段 `warmup_task,consume_order_source,reason`，同时发 `ConsumeOrderDefaulted` Event。
- 门控三条件判定：每次评估一条，Info，字段 `state,reason,rates,required,gap,slope`，rates 内含每个 Pod 的就绪数与需求数；判定写在 `logGateDecision`。
- Gate 注入、摘除与降级：webhook 或放行流程里一条，Info 或 Warn，字段 `warmup_task,pod,pod_index,node,request_id,reason`，注入与摘除对称可查。
- Pod 分数注解写入：分数与摘 gate 同一次 patch 时一条，Info 或 Error，字段 `warmup_task,pod,annotation_key,generation,entries`；写入失败的 Pod 保留 gate。
- 评分计算：每个 Pod 一条，Debug，字段 `warmup_task,pod,node,score`，明细默认关闭，消息名是 `pod score detail`。
- 落点偏离检查：已放行的 Pod 不在分配节点上时一条，Warn，字段 `warmup_task,pod,node,actual_node,reason`，同时发 `NodeDeviation` Event。
- webhook 准入：每次创建一条，Info、Warn 或 Debug，字段 `pod,namespace,request_id,reason,duration_ms`，跳过原因枚举齐全。
- scheduler 打分：每个 Pod 对每个节点一条，Debug 或 Warn，字段 `pod,node,annotation_key,score,stale,result`，覆盖缺分、过期与不匹配分支；打分在 `scoreNode`。

### Agent 的日志点

- 启动、装配与退出（`agent/cmd/agentd/main.go`）：进程生命周期里各一条，Info 或 Error，字段 `component,version,node,grpc_addr,metrics_addr`；构造时已注入 component 与 version，启动日志另带节点名与两个监听地址。
- 预热任务受理、窗口更新、取消与结束（`agent/svc/preheat.go`）：收到 RPC 或任务落到终态时一条，Info，字段 `task_id,dataset,generation,state,total,completed,failed`。
- 陈旧代际拒绝（`agent/svc/preheat.go`）：请求代际回退时一条，Warn，字段 `rpc,task_id,generation,current_generation`。
- 逐块下载与校验（`agent/prefetch/prefetcher.go`）：每块开始、成功或失败各一条，Debug，字段 `task_id,dataset,chunk,size,verify,reason,duration_ms`；明细按 1/100 采样，Info 每 60 秒一条汇总。
- 缓存命中、未命中与读 miss（`agent/svc/hooksock.go`、`agent/svc/collector`）：钩子或本地读触发，Debug，字段 `dataset,chunk,reason,phase,source`；指标为主，Info 每 60 秒一条汇总。
- 坏块隔离与修复（`agent/svc/backfill.go`）：遇到损坏错误或后台补块时一条，Warn，字段 `dataset,path,chunk`，失败再加 `err`。
- 订单通道降级与恢复、inotify 溢出（`agent/svc/orders.go`、`agent/svc/collector/heatmap.go`）：环形缓冲停滞或队列满时一条，Warn 或 Info，字段 `readers,mode`，进入降级再带 `stall_threshold`。
- 淘汰与垃圾回收轮次（`agent/evictor/evictor.go`）：每轮结束或触发危险线时一条，Info、Warn 或 Error，字段 `dataset,result,evicted,protected_skipped,usage_ratio`。
- 策略与快照刷新（`agent/svc/follow.go`）：索引切换成功一条 Info，单轮失败一条 Warn，字段 `dataset,result`，成功加 `snapshot`，失败加 `err`；加载失败保持旧映射。
- 钩子收端与帧错误（`agent/svc/hooksock.go`）：收端启动与非法帧各一条，Info 或 Warn，字段 `path,reason,size,type`；正常帧不记。
- 读声明与心跳（`agent/svc/readerheartbeat.go`）：登记失败时一条，Warn，字段 `dataset,pod_uid,reason`。

Agent 高频路径统一按采样规则处理：成功路径降为汇总，失败路径保持 Warn 并带原因；任何采样都不得丢掉永久、IO 与损坏三类错误。

### DataLoader 的日志点

DataLoader 侧由钩子适配器实现，字段、环境变量名与缺失时的降级行为一起冻结为 v1。

- 启动上下文：进程或 worker 启动时一条，Info，字段 `component,warmup_task,pod,pod_index,dataset,generation_at_start,hook_sock,log_schema_version`，建立与 Pod 的关联。
- 数据源选择：每 batch 或每样本组一条，Debug 或汇总 Info，字段 `dataset,source,phase,stage_id`，source 取 cas 或 origin，判断是否绕过缓存。
- miss 与预取命中：缺块或命中时一条，Debug 或采样，字段 `dataset,chunk,reason,prefetch_ready,wait_ms`，reason 取 absent 或 corrupt，归因到 Agent 的预取。
- 单 batch 延迟分位：每 60 秒一条，Info，字段 `dataset,phase,batches,p50_ms,p95_ms,p99_ms,stall_ms`，给出训练侧的真实体感。
- 异常与降级：钩子发送失败、套接字不可用或回源失败时一条，Warn 或 Error，字段 `dataset,reason,err_class,fallback`，钩子故障不阻断训练。
- 退出：正常或异常退出时一条，Info，字段 `dataset,batches,total_wait_ms,unreported_frames`，用于收尾与丢帧核对。

上下文来源：

- webhook 在注入 gate 与注解的同时注入环境变量：任务名用 `TRAINCACHE_TASK`（「命名空间/名字」），Pod 名用 `TRAINCACHE_POD`（「命名空间/名字」），Pod 序号用 `TRAINCACHE_POD_INDEX`。
- 数据集用 `TRAINCACHE_DATASET`（「命名空间/名字」），钩子套接字路径用 `TRAINCACHE_HOOK_SOCK`（默认 `/run/traincache/agent.sock`），启动时刻的代际用 `TRAINCACHE_GENERATION_AT_START`。

环境变量名与日志字段名不是一回事：环境变量 `TRAINCACHE_TASK` 落到日志字段时写 `warmup_task`，日志里不出现 `task`。代际无法通过不可变的环境变量跟随任务更新，Pod 启动时由 webhook 写入启动时刻的代际，日志只记这个启动值。DataLoader 只读环境变量，缺失时记 `context_missing=true`，降级为只有本地日志，不影响训练；不新增读取 Pod 注解的依赖。

验收口径是十六个日志点，控制平面用十五个日志点覆盖：规格校验失败与快照存储校验失败共用一个日志点，其余一一对应；降级与故障恢复由控制平面的门控降级与 Agent 的订单通道降级两条各带入口与出口。控制平面另有状态迁移与终态短路、落点偏离检查两个日志点属于额外补充。

## 公共字段契约

字段契约冻结为 v1：schema 版本号从 1 起只增不改；新增字段允许为空；删字段或改含义要走弃用周期，至少保留一个小版本并新旧双写。级别、采样与限流策略跟字段契约一起冻结为 v1，只增不改。

| 字段 | 类型 | 出现层 | 取值或约束 |
|---|---|---|---|
| `time`、`level`、`msg` | slog 内置 | 全部 | 级别取 DEBUG、INFO、WARN、ERROR，消息是人读文本，也是 CI 断言的查找键 |
| `log_schema_version` | int | 全部 | 整数，从 1 起只增不改 |
| `component` | string | 全部 | 固定枚举：controller-manager、webhook、scheduler、agentd、dataloader、gateway、checkpointd |
| `version` | string | 全部 | 构建版本，启动时写一次 |
| `cluster`、`namespace` | string | 控制平面、Agent | 由采集侧补齐或启动配置注入，Agent 默认只有 node |
| `node` | string | 全部 | Agent 必填，取自节点名环境变量 `NODE_NAME`；控制平面调用 Agent 时必填 |
| `pod`、`pod_index` | string、int | 控制平面、DataLoader | Pod 写「命名空间/名字」；Pod 序号与预热任务绑定 |
| `warmup_task` | string | 控制平面、DataLoader | 写「命名空间/名字」，沿用控制平面现有字段名 |
| `task_id` | string | Agent、DataLoader | Agent 预取任务 ID，与 warmup_task 多对一，不合并 |
| `job` | string | checkpointd | owner Job 名，准入注入，裸 Pod 为空串，是跨链路对账键 |
| `dataset` | string | 全部 | 已做白名单归并，白名单外写 other |
| `snapshot` | string | 控制平面、Agent | 快照 ID，不写完整对象路径 |
| `generation`、`seq` | uint64 | 控制平面、Agent | 预取代际与位图序号，用于判断陈旧 |
| `request_id` | string | 控制平面、Agent | 控制平面格式是「准入 UID/代际/纳秒时间戳」，Agent 从 gRPC metadata 继承 |
| `rpc` | string | 控制平面、Agent | 四个方法名：SubmitPreheat、UpdatePreheat、CancelPreheat、GetPreheatStatus |
| `duration_ms` | int64 | 全部 | 只在操作结束时出现 |
| `result` | string | 全部 | 固定枚举：ok、error、requeue、skipped、stale、degraded |
| `err` | string | 全部 | 错误原文，必须经脱敏，禁止整段堆栈进 Info |
| `err_class` | string | 全部 | 固定枚举：invalid_spec、not_found、unavailable、permanent、corrupt、io、timeout |
| `reason`、`state`、`phase`、`priority` | string | 全部 | 取值来自各模块冻结枚举 |
| `sampled`、`sample_rate` | bool、float | 全部 | 标明这条是否被采样、采样率多少 |

字段 schema 示例（只示公共部分，业务字段另加）：

```json
{
  "time": "2026-10-21T10:00:00.123Z",
  "level": "INFO",
  "msg": "gate evaluated",
  "log_schema_version": 1,
  "component": "controller-manager",
  "version": "v8.3.0",
  "namespace": "train",
  "warmup_task": "train/wt-llm-7b",
  "dataset": "train/llm-7b",
  "node": "gpu-node-12",
  "generation": 7,
  "request_id": "6f1c.../7/1761031200123000000",
  "state": "Hold",
  "reason": "rate_below_required",
  "duration_ms": 12,
  "result": "ok",
  "sampled": false
}
```

命名与兼容规则：

- 固定小写 snake_case；warmup_task 与 task_id 保持现有语义，不新造 task 字段做二次抽象。
- Info 禁止高基数：path、chunk、fp、pod_uid 与完整对象 URL 只在 Debug 出现；task_id 与 request_id 允许进 Info 正文，但不得进指标标签。
- err 与 err_class 必须成对出现，err 给人看，err_class 给聚合与告警。写出前若记录带了 err 而没带 err_class，采样处理器按错误值补一条分类，字符串形式的 err 按 io 兜底。
- 各层特有错误（cas、objectstore、agentclient）在各自包里先映射成七个枚举值，再回退到通用分类；通用分类只认超时与取消，其余一律记为 io。

## 级别与采样

四级的分工：

- Debug：逐块、逐样本、逐节点的明细，默认关闭。例子是 Pod 评分明细、每块下载与校验成功、每 batch 延迟。
- Info：状态迁移、决策结果、周期汇总、任务完成。例子是调和起止、门控判定结果、任务完成、每分钟预取汇总。
- Warn：可恢复的异常、重试、跳过、未收敛、降级。例子是 Agent 不可达、快照刷新失败保持旧映射、分配未收敛、淘汰失败。
- Error：需要人介入。例子是永久拒绝、状态写失败、磁盘超危险线、采集链路自身失败。

预期内的跳过（比如没有预热任务的 Pod）记 Info 或 Warn；节点磁盘到快写满时，一条 Warn 日志与对应指标要同时有。

高频路径必须先聚合再落盘，每块、每帧都写一条 Info 是被禁止的：

- Agent 逐块下载与校验成功不逐块记，每 60 秒一条 Info 汇总，带块数、字节数、失败数与 P50、P99。
- Agent 缓存命中与未命中以指标为主，明细走 Debug，按 1/100 采样。
- 钩子每帧不记 Info，只记格式错误（Warn）与启动，正常帧计数进指标。
- DataLoader 每 60 秒一条 Info 分位汇总，单 batch 明细走 Debug，按 1/100 采样。
- 淘汰与垃圾回收每轮一条 Info，单块走 Debug，按 1/100 采样。
- 控制平面轮询在状态变化时记 Debug，无变化不记。

限流与去重：

- 进程内令牌桶：控制平面默认每秒 100 行、突发 200；Agent 默认每秒 200 行、突发 400。超限先丢 Debug，再丢 Info，Warn 与 Error 永不丢，丢弃条数记 `traincache_log_dropped_total`，标签是 component 与 level。
- 去重窗口：相同的 component、消息、节点、任务号与原因在 60 秒内只出一条，下一个窗口的第一条带上 `suppressed` 计数。去重表键数到 4096 时清理过期键，抑制高频任务号带来的无界增长。
- 采样判断在读 path 与 chunk 之前完成，不先取明细再决定丢不丢。
- 采样率可配：Info 级读 `TRAINCACHE_LOG_SAMPLE_RATE`，默认 1.0；Debug 级读 `TRAINCACHE_LOG_DEBUG_SAMPLE_RATE`，默认 0.01；空值、非数字、NaN 与超出 0 到 1 的值都退回默认，不阻断启动。采样只作用在 Debug 与 Info 上，Warn 与 Error 不采样。采样率在进程启动时读入，改配置要重启进程，采样率本身写进启动日志。
- 令牌桶速率、去重窗口、60 秒汇总窗口与 1/100 采样率是固定值，不开放配置。

## 脱敏红线

以下内容禁止出现在任何日志里：Secret 内容；accessKey、secretKey、token、Authorization 这类凭据名对应的值；查询参数里含 `X-Amz-Signature`、`Signature`、`Expires` 这类字段的 URL；训练样本内容、张量数据与文件正文；Info 级的完整对象存储路径。

- 训练 Pod 不接对象存储也不持凭证，这个边界由日志层的脱敏守住。
- 对象存储端点只记 host；路径即使在 Debug 也只记截断前缀或 `path_hash`。
- 每个 err 落盘前过一层脱敏：字符串与 error 值走字符串脱敏，URL 形态的值与文本里嵌的 URL 再走 URL 脱敏。
- 两端 logger 在构造时统一包一层脱敏 handler，调用点不需要各自处理。消息、字符串值、error 值、分组属性与预挂属性都在写出前过一遍；属性名命中敏感键时整个值被替换。
- 敏感键按小写比较，覆盖凭据名、令牌、口令与 x-amz- 前缀这类对象存储签名键；命中就整体替换成 `***`，键名保留。
- URL 形态的值去掉用户信息与片段，敏感查询参数的值替换成 `***`，其余参数保持原样与原顺序；解析失败返回 `***`。
- 文本里的 URL 在空白、引号或尖括号处截断后单独脱敏。
- 测试用哨兵 Secret 做负向断言，全量日志里不能出现。

## 跨进程关联

跨进程主键是 task_id、node 与 generation 三者，不引入分布式 traceId。给定一个 Pod，用 warmup_task 加 pod_index 就能拉出控制平面、Agent、DataLoader 三段。

request_id 的格式是「准入 UID/代际/纳秒时间戳」，webhook 侧用 admission UID、0 与纳秒时间。

传播走 gRPC metadata 三个键：`x-traincache-request-id`、`x-traincache-task`、`x-traincache-generation`。控制平面客户端注入，Agent 拦截器解析后写进 context logger；键名是运维契约，只能加不能改。

关联链路一共六跳：

- webhook 生成 request_id 并保留在准入日志里。
- Pod 上带 `traincache.io/warmup-task` 与 `traincache.io/pod-index` 两个注解，DataLoader 经环境变量继承。
- 预热任务调和各自生成 request_id，每次外部调用都带。
- gRPC metadata 传请求号、任务号与代际，控制平面注入，Agent 写进 context logger。
- Agent 侧的任务键是 task_id 加 node 加 generation，保持为跨进程主键。
- DataLoader 从环境变量取上下文写进日志公共字段，缺失时记 context_missing=true。

钩子帧里的身份字段是可选的，缺省时按现有行为处理，老版本不填这些字段也能正常工作。

## 采集链路与标签

- 所有进程只写 stdout 与 stderr，不写宿主机文件，容器运行时负责轮转，采集器按容器日志路径读取；Agent 不得把日志写进 `TRAINCACHE_CACHE_ROOT`，日志与缓存同盘时日志 IO 会和预取争带宽。
- 采集器是 fluent-bit，读取容器日志并转发 Loki；内存占用随缓冲与批量参数变化，部署前在目标节点实测。中心存储是 Loki 3.6.9，只给标签建索引、正文压缩存放，查询面板是 Grafana 12.4.13。
- Loki 标签恰为 cluster、namespace、component、level、node、stream 六个且非空；request_id、pod、task_id、path、service_name 均不在标签中；detected_level 是计算字段，不算存储标签。高基数字段放结构化元数据或 JSON 正文，查询时过滤。
- 多租户以 namespace 做逻辑隔离；Loki 多租户可用 X-Scope-OrgID，Grafana 按 namespace 做 RBAC。审计日志走独立管道。
- 指标链路独立于日志链路：Prometheus 单实例，抓取间隔 15 秒，评估间隔 30 秒，覆盖 traincache 与 kube-system 两个命名空间。
- 抓取按暴露路径拆两个 job。第一个抓 controller-manager、agentd、webhook、scheduler 的 `/metrics`，6 个 target 全 up。第二个抓 controller-manager 与 scheduler 的 `/metrics/traincache`，2 个 target 全 up。
- 第一个 job 把 scheduler 的抓取路径重写到项目指标路径后再整体丢弃该组件的序列，因为 kube-scheduler 的通用路径返回 404。项目新增的 `traincache_source_mode` 与 `traincache_gateway_fallback_total` 随同一条路径暴露。
- agentd 的项目指标在 `/metrics` 上，只由第一个 job 抓；webhook 没有项目自定义注册表，不进第二个 job。
- Grafana 把 Prometheus 与 Loki 并列为数据源。指标标签只放有界维度，请求号、Pod 名、任务号与路径不进指标标签。

保留期与容量：

- 保留期默认 720 小时（30 天），级别为 DEBUG 的流保留 168 小时（7 天），通过 Loki 的按流保留配置实现；Event 由 Kubernetes 自身 TTL 管理，中心只保留聚合指标。
- 日原始量按进程数乘每秒行数乘平均行字节乘 86400 估算；压缩后通常是原始量的 10% 到 20%，按 15% 估。100 个节点、每 Agent 稳态每秒 1 行、每行 500 字节的例子是每天约 4.3 GB 原始、约 0.6 GB 压缩；控制平面行数远小于此。Debug 全开或逐块日志会让单节点量级上升 10 到 100 倍，必须依赖采样。

## 运维与动态级别

- 级别由核心库的进程级级别变量承载：进程启动时写入环境变量值，运行中经 HTTP 端点修改，对已构造的 logger 立即生效，进程重启后回到环境变量值；要长期保持低级别就在部署清单里改环境变量。
- 启动级别环境变量：控制平面三个进程读 `CONTROLLER_LOG_LEVEL`，agentd 读 `TRAINCACHE_LOG_LEVEL`；默认都是 info，取值 debug、info、warn、error，大小写不敏感，未知值退化为 info。
- 端点地址环境变量：控制平面三个进程读 `CONTROLLER_DEBUG_ADDR`，agentd 读 `TRAINCACHE_DEBUG_ADDR`；默认都是 127.0.0.1:6060，显式设空字符串关闭端点，配置校验拒绝非回环的地址。
- 端点契约：GET 返回 200 与当前级别；PUT 请求体是 `{"level":"debug"}`，合法值修改进程级别并返回 200 与当前值，非法值返回 400 且不改动；其余方法返回 405 并带 Allow 头。请求体按 1 KiB 截断解析。
- 每次成功修改写一条 Info 审计日志，消息固定为 log level changed，字段固定 component、old、new、remote_addr。端点不鉴权，只能绑回环地址，不进 Service，也不加 NetworkPolicy 例外；监听失败只记 Error，不影响进程的业务功能，进程退出时优雅关闭，最多等 3 秒。
- 日志即接口的变更流程：字段登记在公共字段契约表里，新增字段走 PR 模板勾选，删除或改含义必须双写一个小版本并在 runbook 中标注；日志消息也视为稳定标识，CI 断言按消息查找。
- CI 断言：验收口径的十六个日志点每一个至少一个测试，逐项断言消息、必带字段与级别；控制平面 warmup、webhook、scheduler、dataset 四个业务包各有一份日志断言测试，Agent 端在 `agent/svc/` 有一份；脱敏用哨兵 Secret 做负向断言。日志断言与指标断言都在 CI 里跑，指标名与标签集合被看板和告警引用后只增不改。
- 轮转与磁盘保护：容器运行时配置单文件大小上限（`containerLogMaxSize`）与文件个数上限（`containerLogMaxFiles`）；采集器设置磁盘缓冲上限与背压，压力下先丢 Debug；Agent 与 DataLoader 不自行写文件日志。
- 审计与普通日志分工：Kubernetes audit 记录 API 访问，应用日志只记录业务决策；审计事件只出自 audit 通道，Secret 不进任何业务日志。
- 改级别的操作走 kubectl port-forward 到回环地址，再用 curl 读写端点，级别只对当前 Pod 生效。

## 附录:排障 runbook

五种常见现象的排查顺序是先日志、再指标与事件、最后 Agent 与下游。

### 门控不放行

先查 `gate evaluated` 日志的 `state`、`reason`、`rates`、`required`、`gap`、`slope`，再查 `traincache_controller_gate_tasks{state="hold"}` 与 `traincache_controller_gate_hold_duration_seconds`，以及 `GateReleased` 与 `GateDegraded` 两个 Event，最后查 `GetPreheatStatus` 返回的 `generation`、`seq`、`ready_bitmap` 与 `traincache_controller_preheat_rpc_total`。

判定：`rates` 没到 `required` 是预取未就绪；出现 `gate removal failed` 或 `gate removal incomplete` 是 Pod 打补丁失败；长时间停在 hold 是 Agent 进度问题。

### Agent 不可达

先查 `agent submit failed` 与 `agent update failed` 日志的 `node`、`err`、`err_class`，再查 `traincache_controller_preheat_rpc_total{result="unavailable"}` 与 `traincache_agent_up`，最后查 Agent Pod 的启动与监听日志、节点网络与守护集状态。

判定：`err_class` 是 `permanent` 是请求或代际问题；是 `unavailable` 是网络、Pod 未就绪或 gRPC 端口不通。

### DataLoader 慢

先查 DataLoader 每 60 秒分位日志的 `p99_ms` 与 `stall_ms`，再查 `traincache_read_stall_seconds{phase,cause}`、`traincache_hook_read_miss_total` 与 `traincache_prefetch_lead_blocks`，最后查 `traincache_fetch_requests_total{result,reason}`、`traincache_fetch_inflight_bytes` 与 `traincache_disk_usage_ratio`。

判定：`cause=prefetch_lag` 是预取不够快，`origin_slow` 指向对象存储，`local_slow` 指向本地盘与 CPU；`traincache_prefetch_lead_blocks` 为负说明消费跑在预取前面。

### 落点偏离

先查 `node deviation detected` 日志的 `pod`、`node`、`actual_node` 与 scheduler 的 Debug 打分，再查 `NodeDeviation` Event 与 `traincache_scheduler_score_total{result}`，最后查 Pod 分数注解的条目数与有效期，以及 Pod 实际被调度到的节点。

判定：分数缺失或过期是注解写入或有效期问题；分数正常但落点不同，是调度器其他插件或资源约束。

### 日志量异常与磁盘压力

先查采集器的丢弃计数与 `traincache_log_dropped_total`、Debug 开关记录，再查节点磁盘利用率与 Loki 写入速率，最后查最近是否打开过 Debug 或改过采样率。

处理顺序是先降级别与采样率，再查是否有循环重试在刷日志。
