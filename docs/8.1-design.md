# 日志与可观测性 · Design


## 1. 设计目标与原则

设计目标：三层日志共用一个字段契约与一条采集链路；给定一个 Pod，能在中心存储里用 `warmup_task + pod_index` 把 controller → Agent → DataLoader 三段日志一次拉出来（机制见 §5）。先定契约，再调日志量。


| 信号             | 适合承载                                                         | 不适合承载               | 本项目落点                                                                                                        |
|------------------|------------------------------------------------------------------|--------------------------|-------------------------------------------------------------------------------------------------------------------|
| 日志             | 单次决策上下文、错误原文、高基数字段（path/chunk/fp/request_id） | 计数、趋势、告警阈值     | 全部 Go 进程 stdout JSON；DataLoader 设计为 stdout JSON                                                           |
| 指标             | 计数、比率、分位、容量、告警                                     | 单任务排查、任意维度切片 | 控制平面 `controller/internal/metrics`、Agent `agent/metrics`；各进程 `/metrics` 由 Prometheus 抓取，Grafana 查询 |
| Kubernetes Event | 对象生命周期与面向使用者的原因（`kubectl describe` 可见）        | 高频明细、跨进程关联     | 门控放行/降级、默认切分、落点偏离、注入降级                                                                       |

一条信息该进哪个信号，按这个规则判：要计数、告警、跨 Pod 聚合 → 指标；要让用户在 `kubectl describe` 里看到对象为什么不动 → Event（Info 可以再写一份，但 Info 不能是唯一来源）；其余排查上下文 → 日志。两条硬规则：告警阈值只从指标取；`request_id`/`pod`/`task_id` 不进指标标签，这三个取值近乎无限，进标签会让时间序列数量失控。

## 2. 现状盘点

| 层         | 现状                                                                                                                                                                                                                                                                                                                                                                              |
|------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 控制平面   | `controller/internal/logging` 的 `New/Into/From`；`cmd/{controller-manager,webhook,scheduler}/main.go` 初始化 `JSONHandler(os.Stderr)` 并带 `component/version`；`CONTROLLER_LOG_LEVEL` 四级校验；reconcile 与 webhook 生成 `request_id`；7.1 §9.3 十六点基本落点；`logs_assert_test.go`（warmup/webhook/scheduler/dataset）                                                  |

## 3. 统一日志契约

### 3.1 公共字段

字段契约自 ADR-007~010（条目见 7.2）起冻结为 v1：`log_schema_version` 从 1 起只增不改；新增字段允许为空；删字段或改含义必须走弃用周期，至少保留一个小版本并新旧双写。脱敏统一交给 `core/logging` 的 `Redact` / `RedactURL`（ADR-007），controller 与 Agent 共用同一套实现。两端 `logging.New` 把 JSON handler 包一层 `NewRedactingHandler`。

| 字段                                   | 类型       | 出现层               | 约束                                                                        |
|----------------------------------------|------------|----------------------|-----------------------------------------------------------------------------|
| `time`、`level`、`msg`                 | slog 内置  | 全部                 | `level` 取值 `DEBUG/INFO/WARN/ERROR`                                        |
| `log_schema_version`                   | int        | 全部                 | 从 1 起；只增不改                                                           |
| `component`                            | string     | 全部                 | 固定枚举：`controller-manager/webhook/scheduler/agentd/dataloader/gateway/checkpointd` |
| `version`                              | string     | 全部                 | 构建版本，启动时写一次                                                      |
| `cluster`、`namespace`                 | string     | 控制平面、Agent      | 由采集侧补齐或启动配置注入；Agent 默认只有 `node`                           |
| `node`                                 | string     | 全部                 | Agent 必填（`NODE_NAME`）；控制平面调用 Agent 时必填                        |
| `pod`、`pod_index`                     | string/int | 控制平面、DataLoader | `pod` 用 `<namespace>/<name>`；`pod_index` 与 WarmupTask 绑定               |
| `warmup_task`                          | string     | 控制平面、DataLoader | `<namespace>/<name>`，沿用控制平面现有字段名                                |
| `task_id`                              | string     | Agent、DataLoader    | Agent 预取任务 ID；与 `warmup_task` 是多对一关系，不合并                    |
| `job`                                  | string     | checkpointd          | owner Job 名，准入注入；裸 Pod 为空串，跨链路对账键（10.2 D26）              |
| `dataset`                              | string     | 全部                 | 已做白名单归并；白名单外写 `other`                                          |
| `snapshot`                             | string     | 控制平面、Agent      | 快照 ID；不写完整对象路径                                                   |
| `generation`、`seq`                    | uint64     | 控制平面、Agent      | 预取代际与位图序号；用于判断陈旧                                            |
| `request_id`                           | string     | 控制平面、Agent      | 控制平面格式 `<uid>/<generation>/<unixnano>`；Agent 从 gRPC metadata 继承   |
| `rpc`                                  | string     | 控制平面、Agent      | `SubmitPreheat/UpdatePreheat/CancelPreheat/GetPreheatStatus`                |
| `duration_ms`                          | int64      | 全部                 | 只在操作结束时出现                                                          |
| `result`                               | string     | 全部                 | 固定枚举：`ok/error/requeue/skipped/stale/degraded`                         |
| `err`                                  | string     | 全部                 | 错误原文，必须经脱敏；禁止整段堆栈进 Info                                   |
| `err_class`                            | string     | 全部                 | 固定枚举：`invalid_spec/not_found/unavailable/permanent/corrupt/io/timeout` |
| `reason`、`state`、`phase`、`priority` | string     | 全部                 | 取值来自各模块冻结枚举                                                      |
| `sampled`、`sample_rate`               | bool/float | 全部                 | 被采样时标明，便于估算真实量                                                |

字段 schema 示例（仅示公共部分，业务字段另加）：

```json
{
  "time": "2026-10-21T10:00:00.123Z",
  "level": "INFO",
  "msg": "gate evaluated",
  "log_schema_version": 1,
  "component": "controller-manager",
  "version": "v8.3.0",
  "namespace": "train",
  "warmup_task": "train/wt-llm-7b",
  "dataset": "train/llm-7b",
  "node": "gpu-node-12",
  "generation": 7,
  "request_id": "6f1c.../7/1761031200123000000",
  "state": "Hold",
  "reason": "rate_below_required",
  "duration_ms": 12,
  "result": "ok",
  "sampled": false
}
```

命名与兼容规则：

- 固定小写 snake_case；`warmup_task` 与 `task_id` 保持现有语义，不新造 `task` 字段做二次抽象。
- Info 禁止高基数：`path`、`chunk`、`fp`、`pod_uid`、完整对象 URL 只在 Debug。`task_id`/`request_id` 允许进 Info，因为它们用于关联，但不得进指标标签。
- `err` 与 `err_class` 必须成对出现；`err` 给人看，`err_class` 给聚合与告警。

### 3.2 级别策略

级别、采样与限流策略同样自 ADR-007~010 起冻结为 v1：只增不改；Warn/Error 永不采样（ADR-006），采样只落在 Debug 和 Info 头上。

| 级别  | 语义                                   | 本项目例子                                                  |
|-------|----------------------------------------|-------------------------------------------------------------|
| Debug | 逐块、逐样本、逐节点评分明细；默认关闭 | `pod score detail`、每块下载/校验成功、每 batch 延迟        |
| Info  | 状态迁移、决策结果、周期汇总、任务完成 | reconcile 起止、gate evaluated、任务 DONE、每分钟预取汇总   |
| Warn  | 可恢复异常、重试、跳过、未收敛、降级   | Agent 不可达、快照刷新失败保持旧映射、GWAA 未收敛、淘汰失败 |
| Error | 需人工介入                             | 永久拒绝、状态写失败、磁盘超危险线、采集链路自身失败        |

预期内的跳过（比如没有 WarmupTask 的 Pod）记 Info 或 Warn；节点磁盘到快写满时，一条 Warn 日志和对应指标要同时有。

### 3.3 采样与限流

高频路径必须先聚合再落盘，每块、每帧都写一条 Info 是被禁止的：

| 路径                    | 默认策略                                                       |
|-------------------------|----------------------------------------------------------------|
| Agent 逐块下载/校验成功 | 不逐块记；每 60s 一条 Info 汇总（块数、字节、失败数、P50/P99） |
| Agent 缓存命中/未命中   | 指标为主；命中明细 Debug 且 1/100 采样                         |
| hooksock 每帧           | 不记 Info；只记格式错误（Warn）与启动；正常帧计数进指标        |
| DataLoader 每 batch     | 每 60s 一条 Info 分位汇总；单 batch 明细 Debug 1/100           |
| 淘汰/GC 每块            | 每轮一条 Info；单块 Debug 1/100                                |
| 控制平面轮询            | 状态变化记 Debug；无变化不记                                   |

限流机制：

- 进程内令牌桶：控制平面默认 100 行/秒、突发 200；Agent 默认 200 行/秒、突发 400；超限先丢 Debug，再丢 Info，Warn/Error 永不丢，丢弃计数进 `log_dropped_total`。
- 去重窗口：相同 `(component, event, node, task_id, reason)` 60s 内只出一条，后续在下一窗口带 `suppressed` 计数。
- 先采样后格式化：采样判断在读 `path/chunk` 之前完成。
- 采样配置项：`TRAINCACHE_LOG_SAMPLE_RATE`（Info，默认 1.0）、`TRAINCACHE_LOG_DEBUG_SAMPLE_RATE`（Debug，默认 0.01）。令牌桶速率、去重窗口、60s 汇总窗口、1/100 采样率都是固定值，不可配置。

### 3.4 脱敏红线

以下内容禁止出现在任何日志里：Secret 内容；`accessKey/secretKey/token/Authorization`；带签名的凭据 URL（查询参数里含 `X-Amz-Signature`、`Signature`、`Expires` 等的）；训练样本内容、张量数据、文件正文；完整对象存储路径（Info 级）。

对象存储端点只记 host；路径在 Debug 也只记截断前缀或 `path_hash`。所有 `err` 在落盘前过一层脱敏：字符串与 error 值走 `Redact`，URL 形态的值和文本里嵌的 URL 再走 `RedactURL`。两端 logger 在 `logging.New` 里统一包 `NewRedactingHandler`，调用点无需各自处理。测试用哨兵 Secret 做负向断言，全量日志里不能出现。Agent 已有「训练 Pod 不接对象存储、不持凭证」的边界（6.2 D44），日志层的脱敏守住同一边界。

## 4. 分层日志点

### 4.1 控制平面

| 位置                                        | 触发条件                     | 级别             | 必带字段                                                      | 用途                                               |
|---------------------------------------------|------------------------------|------------------|---------------------------------------------------------------|----------------------------------------------------|
| `warmup/controller.go` reconcile 入口/出口  | 每次 reconcile               | Info             | `warmup_task,generation,request_id,duration_ms,result`        | 生命周期基线                                       |
| `dataset/controller.go` reconcile 入口/出口 | 每次 reconcile               | Info             | `dataset,generation,request_id,duration_ms,result`            | 数据面校验基线                                     |
| 状态迁移/终态短路                           | condition 或 phase 变化      | Info             | `warmup_task,state,reason`                                    | 解释「为何不动」                                     |
| spec/快照/存储校验失败                      | 校验返回错误                 | Warn/Error       | `dataset,snapshot,reason,err`                                 | 输入问题与依赖问题分流                             |
| 候选筛选结果                                | 每轮筛选后                   | Info             | `warmup_task,nodes,accessible,agent_ready,candidates,reason`  | 候选为 0 的首要线索                                |
| Agent RPC 成功                              | Submit/Update/Cancel 返回    | Info             | `warmup_task,task_id,pod,node,generation,rpc`                 | 下发是否到达                                       |
| Agent RPC 失败                              | 返回错误                     | Warn/Error       | 上述 + `err,err_class`                                        | `permanent` 进 Error；可重试错误由 reconcile 退避重试 |
| 进度轮询                                    | 状态或 seq 变化              | Debug            | `task_id,node,generation,seq,ready`                           | 就绪位图推进                                       |
| GWAA 分配变化/未收敛                        | 分配与已下发不同或达轮次上限 | Info/Warn        | `warmup_task,assign,rounds,actions,unassigned,reason`         | 回退与抖动；`assign` 是 `{"p0":["n0","n1"]}` 形式的 Pod→节点列表 |
| 消费顺序解析/默认切分                       | 显式订单或默认切分           | Info             | `warmup_task,consume_order_source,reason`                     | 同时发 `ConsumeOrderDefaulted` Event               |
| 门控三条件判定                              | 每次评估                     | Info             | `state,reason,rates,required,gap,slope`                       | `logGateDecision`；rates 内含每 Pod ready/required |
| Gate 注入/摘除/降级                         | webhook 或放行流程           | Info/Warn        | `warmup_task,pod,pod_index,node,request_id,reason`            | 注入与摘除对称可查                                 |
| Pod 分数注解写入                          | 分数与摘 gate 同一次 patch   | Info/Error       | `warmup_task,pod,annotation_key,generation,entries`           | 写入失败时该 Pod 保留 gate                         |
| 评分计算                                    | 每个 Pod 分数                | Debug            | `warmup_task,pod,node,score`                                  | 明细默认关闭                                       |
| 落点偏离检查                                | 已放行 Pod 不在分配节点      | Warn             | `warmup_task,pod,node,actual_node,reason`                     | 同时发 `NodeDeviation` Event                       |
| webhook 准入                                | 每次 CREATE                  | Info/Warn/Debug  | `pod,namespace,request_id,reason,duration_ms`                 | 跳过原因枚举齐全                                   |
| scheduler 打分                              | 每个 Pod×Node                | Debug/Warn       | `pod,node,annotation_key,score,stale,result`                  | 缺分/过期/不匹配分支                               |

概述：控制平面十七个日志点全部在码，字段与级别按上表执行。

### 4.2 Agent

| 位置                             | 触发条件                 | 级别            | 必带字段                                                  | 用途/现状                                                                                |
|----------------------------------|--------------------------|-----------------|-----------------------------------------------------------|------------------------------------------------------------------------------------------|
| 启动/装配/退出                   | 进程生命周期             | Info/Error      | `component,version,node,grpc_addr,metrics_addr`           | 已在：`logging.New` 注入 `component/version`，启动日志另带 `node/grpc_addr/metrics_addr` |
| preheat 任务受理/更新/取消/结束  | RPC 或完成               | Info            | `task_id,dataset,generation,state,total,completed,failed` | 已在（`svc/preheat.go`）                                                                 |
| 陈旧 generation 拒绝             | RPC 代际回退             | Warn            | `rpc,task_id,generation,current_generation`               | 已在                                                                                     |
| 逐块下载/校验                    | 每块开始/成功/失败       | Debug/汇总 Info | `task_id,dataset,chunk,size,verify,reason,duration_ms`    | 明细走 Debug 1/100 采样，Info 每 60s 一条汇总；已在（`prefetch/prefetcher.go`）            |
| 缓存命中/未命中/read_miss        | 钩子或本地读             | Debug/采样      | `dataset,chunk,reason,phase,source`                       | 指标为主，Info 每 60s 一条汇总；明细走 Debug 1/100 采样；已在（`svc/hooksock.go`、`collector`） |
| 坏块隔离与修复                   | `ErrCorrupt` 或 backfill | Warn            | `dataset,path,chunk`（失败加 `err`）                      | 已在（`svc/backfill.go`）                                                                |
| 订单通道降级/恢复/inotify 溢出 | ring 停滞或队列满        | Warn/Info       | `readers,mode`（进入降级另带 `stall_threshold`）          | 已在（`agent/svc/orders.go`）                                                            |
| GC/淘汰轮次                      | 每轮结束或危险线         | Info/Warn/Error | `dataset,result,evicted,protected_skipped,usage_ratio`    | 已在（`evictor/evictor.go`）                                                             |
| 策略/快照刷新                    | Catalog 切换/单轮失败    | Info/Warn       | `dataset,result`（成功加 `snapshot`，失败加 `err`）       | 切换成功 Info，加载失败 Warn 并保持旧映射；已在（`svc/follow.go`）                       |
| hooksock 收端与帧错误            | 启动、非法帧             | Info/Warn       | `path,reason,size,type`                                   | 已在（`svc/hooksock.go`）；不记正常帧                                                    |

### 4.3 DataLoader（冻结契约）

以下契约由 `agent/hooklib/` 适配器实现。本节字段、env 名与缺失降级行为冻结为 v1；`warmup_task` 的适用范围按 ADR-008 为控制平面 + DataLoader。

| 位置                  | 触发条件                              | 级别            | 必带字段                                                                                                       | 用途               |
|-----------------------|---------------------------------------|-----------------|----------------------------------------------------------------------------------------------------------------|--------------------|
| 启动上下文            | 进程/worker 启动                      | Info            | `component=dataloader,warmup_task,pod,pod_index,dataset,generation_at_start,hook_sock,log_schema_version`      | 建立与 Pod 的关联  |
| 数据源选择            | 每 batch 或每样本组                   | Debug/汇总 Info | `dataset,source=cas\|origin,phase,stage_id`                                                                    | 判断是否绕过缓存   |
| miss 与 prefetch 命中 | 缺块或命中                            | Debug/采样      | `dataset,chunk,reason=absent\|corrupt,prefetch_ready,wait_ms`                                                  | 归因到 Agent 预取  |
| 单 batch 延迟分位     | 每 60s                                | Info            | `dataset,phase,batches,p50_ms,p95_ms,p99_ms,stall_ms`                                                          | 训练侧真实体感     |
| 异常与降级            | 钩子发送失败、socket 不可用、回源失败 | Warn/Error      | `dataset,reason,err_class,fallback`                                                                            | 钩子故障不阻断训练 |
| 退出                  | 正常/异常退出                         | Info            | `dataset,batches,total_wait_ms,unreported_frames`                                                              | 收尾与丢帧核对     |

上下文来源（冻结契约）：

- webhook 在注入 gate/annotation 的同时注入环境变量：`TRAINCACHE_TASK=<ns>/<name>`、`TRAINCACHE_POD=<ns>/<name>`、`TRAINCACHE_POD_INDEX=<n>`、`TRAINCACHE_DATASET=<ns>/<name>`、`TRAINCACHE_HOOK_SOCK=/run/traincache/agent.sock`。
- `TRAINCACHE_TASK` 是环境变量名，其值就是 warmup task 名，落到日志字段时写 `warmup_task`；日志字段中不出现 `task`（ADR-008）。
- `generation` 无法通过不可变 env 跟随 WarmupTask 更新；Pod 启动时由 webhook 写入 `TRAINCACHE_GENERATION_AT_START`，日志只记该启动值。
- 不引入新的 Pod annotation 读取依赖：DataLoader 只读 env，缺失时记 `context_missing=true` 并降级为仅本地日志，不影响训练。

### 4.4 与 7.1 §9.3 十六点的关系

7.1 §9.3 定下的十六个日志点，下表逐条对应（行号被 8.3 等文档引用，不重排）。

| #  | 日志点                    | 状态   | 说明                                   |

| 3  | 快照/存储校验失败         | 已实现 | dataset 控制器                         |

## 5. 关联与传播

目标链路一共六跳，每跳标现状和要做的动作：

| 跳 | 载体                                                                                     | 现状               | 动作                                                   |
|----|------------------------------------------------------------------------------------------|--------------------|--------------------------------------------------------|
| 1  | webhook `request_id`（admission UID/0/nano）                                             | 已实现             | 保留                                                   |
| 2  | Pod `traincache.io/warmup-task`、`traincache.io/pod-index`                               | 已实现（7.1 §6.3） | DataLoader 经 env 继承                                 |
| 3  | WarmupTask reconcile `request_id`                                                        | 已实现             | 每次外部调用都带                                       |
| 4  | gRPC metadata：`x-traincache-request-id`、`x-traincache-task`、`x-traincache-generation` | 已实现             | Controller 客户端注入；Agent 拦截器写入 context logger |
| 5  | Agent 任务键 `task_id + node + generation`                                               | 已实现             | 保持为跨进程主键                                       |
| 6  | DataLoader env → 日志公共字段                                                            | 契约               | 缺失时 `context_missing=true`                          |

跨进程主键是 `task_id + node + generation`（7.1 §9.2 已明确无分布式 traceId）。`request_id` 由 webhook/WarmupTask reconcile 生成，经 gRPC metadata 传给 Agent（第 4 跳）；ADR-002 的「不出进程」指不引入分布式 traceId。不引入 OpenTelemetry（选型理由见 7.2）。三种信号各自承载什么，判据见 §1，字段级清单见 8.0「指标」一节。

## 6. 输出与汇总

日志和指标各走一条链路：

```text
容器 stdout/stderr (JSON)
  -> 节点 DaemonSet 采集（fluent-bit）
  -> Loki 3.6.9（标签索引 + 结构化元数据）
  -> Grafana 12.4.13 查询/看板；告警规则读取指标与少量日志计数

指标链路：
traincache-components: controller-manager(:9412)/metrics、agentd(:9411)/metrics、webhook/metrics、scheduler/metrics
traincache-custom-metrics: controller-manager/metrics/traincache、scheduler/metrics/traincache
  -> Prometheus 单实例（15s 抓取） -> Grafana 查询/看板；告警规则读取 Prometheus 指标
```

链路与标签规范：

- 所有进程只写 stdout，宿主机文件由容器运行时负责轮转，采集器按容器日志路径 tail；Agent 不得把日志写进缓存盘（`TRAINCACHE_CACHE_ROOT`），日志与缓存同盘时，日志 IO 会和预取争带宽。
- 采集器是 fluent-bit：负责 tail 容器日志并转发 Loki；内存占用随缓冲与批量参数变化，部署前在目标节点实测。
- Loki 标签恰为 `cluster`、`namespace`、`component`、`level`、`node`、`stream` 六个且非空；`request_id`、`pod`、`task_id`、`path`、`service_name` 均不在标签中；`detected_level` 是计算字段，不算存储标签。这些高基数字段放 Loki structured metadata 或 JSON 正文，查询时过滤。
- 多租户：以 `namespace` 做逻辑隔离；Loki 多租户可用 `X-Scope-OrgID`，Grafana 按 namespace 做 RBAC。审计日志走独立管道。
- 指标链路独立于日志链路，按暴露路径拆两个抓取 job（决策见 8.2 ADR-013，target 数与验证结果见 8.0「指标」一节）。components job 把 scheduler 的抓取路径重写到 `/metrics/traincache` 后又整体 drop scheduler 的 `/metrics` 序列（kube-scheduler 的 `/metrics` 返回 404），项目指标因此只被 custom job 计一次；agentd 的项目指标在 `/metrics`，新增的 `traincache_source_mode` 与 `traincache_gateway_fallback_total` 随同一路径暴露。Grafana 将 Prometheus 与 Loki 并列为数据源。指标标签只放有界维度，`request_id`、`pod`、`task_id`、`path` 不进指标标签。

保留与容量（容量为数量级）：

- 计算方式：`日原始量 ≈ 进程数 × 每秒行数 × 平均行字节 × 86400`；压缩后通常为原始量的 10%-20%，按 15% 估算。
- 示例：100 个节点、每 Agent 稳态 1 行/秒、每行 500 B -> 约 4.3 GB/日原始、约 0.6 GB/日压缩；控制平面行数远小于此。Debug 全开或逐块日志会让单节点量级上升 10-100 倍，必须依赖采样。
- 保留期：默认 720h（30 天）；`level="DEBUG"` 的流 168h（7 天），通过 Loki `retention_stream` 实现；Event 由 Kubernetes 自身 TTL 管理，中心只保留聚合指标。

存储选型理由见 8.2 ADR-001。

## 7. 管理与维护

- 动态日志级别：级别由 `core/logging` 的进程级 `slog.LevelVar` 承载。进程启动时写入 env 值，运行中经 `/debug/loglevel` 修改，进程重启后回到 env 值；要长期保持低级别就在部署清单里改 env。启动级别 env：`CONTROLLER_LOG_LEVEL`（controller-manager / scheduler / webhook）、`TRAINCACHE_LOG_LEVEL`（agentd），默认都是 `info`，取值 `debug/info/warn/error`，大小写不敏感，未知值退化为 `info`。端点地址 env：`CONTROLLER_DEBUG_ADDR`（三个控制平面进程）、`TRAINCACHE_DEBUG_ADDR`（agentd），默认都是 `127.0.0.1:6060`，显式设空字符串关闭端点。
- `/debug/loglevel` 契约：`GET` 返回 200 与 `{"level":"info"}`；`PUT` 请求体 `{"level":"debug"}`，合法值修改进程级别并返回 200 与当前值，非法值返回 400 且不改动；其余方法返回 405（`Allow: GET, PUT`）。每次成功修改写一条 Info 审计日志，`msg` 固定为 `log level changed`，字段固定 `component`、`old`、`new`、`remote_addr`。端点不鉴权，只能绑回环地址，配置校验拒绝非回环的 `host:port`；端点不进 Service，也不加 NetworkPolicy 例外。端点监听失败只记 Error，不影响进程的业务功能。
- 日志即接口的变更流程：字段登记在本文 §3.1；新增字段走 PR 模板勾选；删除/改义必须双写一个小版本并在 runbook 中标注。日志消息 `msg` 也视为稳定标识，CI 断言按 `msg` 查找。
- CI 断言：7.1 §9.3 的每一行至少一个测试。控制平面已有 `logs_assert_test.go`（warmup/webhook/scheduler/dataset）与 `logging_test.go`；Agent 端已有 `agent/svc/logs_assert_test.go`，逐项断言 `msg + 必带字段 + level`；脱敏用哨兵 Secret 做负向断言。测试清单见 `8.3-test.md`。
- 采样配置：`TRAINCACHE_LOG_SAMPLE_RATE`、`TRAINCACHE_LOG_DEBUG_SAMPLE_RATE`；配置变更需重启或热加载，采样率本身写进启动日志。
- 轮转与磁盘保护：容器运行时配置 `containerLogMaxSize` 与 `containerLogMaxFiles`；采集器设置磁盘缓冲上限与背压，压力下先丢 Debug；Agent 与 DataLoader 不自行写文件日志。
- 审计与普通日志分工：Kubernetes audit 记录 API 访问，应用日志只记录业务决策；审计事件只出自 audit 通道，Secret 不进任何业务日志。

改级别的操作（port-forward、查询与修改命令、生效确认）见 8.4 §四「临时打开 Debug」。
