# 缓存核心库关键决策

## D3 块头只有 128 字节 v1 一种布局

结论：块头固定 128 字节，字段顺序是 magic `TCBK`、version 恒为 1、flags（bit0 表示块头内 sha256 有效）、小端 uint32 的 block_size（不含块头的数据字节数）、16 字节 xxh3_128、32 字节 sha256、68 字节 reserved 全 0，reserved 或版本号不符就判坏块。
原因：同时支持 64 字节变体就要维护两套解析器，而存储键恒为 xxh3-128、去重与是否记 sha256 无关，变体换不来任何收益。

## D4 块按固定大小切分且偏移不落盘

结论：`(path, chunk)` 按 `ChunkSize` 等分，默认 64 MiB、参数可调；索引条目存数据字节数而不存字节偏移，末块允许不足一个块大小。
原因：偏移等于块号乘块大小，读侧自己乘得出来，把同一个数存进索引就要额外保证两份取值一致。

## D5 索引分片是 JSON 数组、单片有条目上限

结论：一个索引分片是条目的 JSON 数组、字段名冻结，条目先按 `(path, chunk)` 字典序排序再按条数切，每片最多 `MaxEntriesPerShard` 条（默认 100_000），超上限即违反契约。
原因：几十万个块的整表远超 etcd 单值 1.5 MB 的上限，必须切片管理；JSON 可读、可调试、构建与合并逻辑简单，而分片存在对象存储上对体积不敏感（十万条约 13 MB）。

## D6 分片对象键含内容指纹

结论：分片对象名取 `shard-<fp8>.idx`，`fp8` 是片内容 xxh3-128 前 8 字节 hex，清单里存完整指纹；内容没变的分片在新快照的清单里继续引用首次创建它的那个对象键。
原因：键由内容决定就把「要不要重传」变成「键名相不相同」，未变更分片物理复用同一个对象，每次提交只传真正变化的那几片；代价是删对象之前必须先读全部保留快照的清单才知道谁还被引用。

## D7 CURRENT 切换只走条件写

结论：CURRENT 的原子提交只走条件写，期望值传空串要求对象不存在（`If-None-Match: *`）、传非空要求当前 ETag 等于它（`If-Match`），ETag 取内容 MD5 的 hex，前置条件不满足就报冲突且不写入。
原因：同一时刻只允许一个提交者改成，条件写是唯一能把这条保证交给对象存储的做法；各后端支持度不一，所以接口面保持不变，支持与否由装配期探测给出结论。

## D8 CURRENT 内容带上清单指纹

结论：CURRENT 的内容是 `"<snapID> <manifestFP8>"`，空格分隔、无换行，`manifestFP8` 是 manifest 内容指纹的前 8 字节 hex。
原因：指针多带一个字段就让校验链从入口闭合，清单损坏当场就能查出来，成本只是一个定长字段。

## D9 引用计数只放内存

结论：`Acquire` 与 `Release` 维护进程内引用计数表、不落盘，回收判据以保留快照可达并上有效读者登记为准，计数只做快速过滤与冗余校验。
原因：持久化计数要解决崩溃一致性，掉电后它与真实快照状态必然对不上；能从快照重算的可达集才是可靠来源。

## D10 两种哈希都用现成实现且只出现在一个包

结论：xxh3-128 用 `github.com/zeebo/xxh3`、sha256 用标准库，两种摘要的一次性计算与流式构造都只由 `internal/digest` 提供，其他包一律调它。
原因：xxh3 抗随机损坏但不抗有意构造，强校验需求由 sha256 档位兜住，两个实现都是社区主流写法，自己重写实现只增加出错面。

## D11 不做逐块 fsync

结论：块发布靠目录内临时文件加一次 rename 保证可见性，`Put` 不对块文件做 fsync。
原因：掉电丢掉的块重拉一次就恢复，逐块 fsync 把写吞吐压到磁盘同步速度上，换来的持久性对一层缓存没有意义。

## D12 单测全部跑在内存后端上

结论：单测用 `objectstore` 的内存实现装配，真实后端的集成测试独立存在、按需运行；内存实现的 ETag 取内容 MD5 的 hex，条件写的比较与写入在同一把锁内完成。
原因：单测要确定性与无网络依赖；而条件写语义成立的前提就是 ETag 等于内容 MD5，mock 不贴住这条就测不出真正的竞争与校验行为。

## D13 校验档位只影响新写的块

结论：档位取 `xxh3`（默认）或 `xxh3+sha256`，是 `cas.New` 的实例参数、进程级取值，只决定新写块是否在块头里记 sha256；读时验什么只看块头 flags。
原因：按 flags 决定读侧校验，档位切换就不动已有块、不触发全量重算；挂实例是因为全进程只有一个 CAS 对象，没有更细的粒度可用。

## D14 快照保留窗口是兜底上限，回收由宿主触发

结论：`RetainSnapshots` 默认 3（CURRENT 加最近 2 个），回收只导出显式的 `Sweep`，库里不放定时器，提交路径不带回收。
原因：真正划定安全边界的是有效读者登记集合，固定保留个数只是上限；定时器放进库会让同一份索引在多个宿主里跑出自相竞争的两套回收。

## D17 Catalog 在构造时绑定单个数据集

结论：`NewCatalog(store, dataset, cfg)` 带数据集参数，`Refresh` 与 `Lookup` 的签名里没有数据集，一个实例只服务一个数据集，换数据集要新建实例。
原因：这两个方法的签名是冻结契约，不加构造参数就得改签名；`Writer` 与 `Collector` 走方法参数传数据集，两套入口并存是签名冻结的结果而不是疏漏。

## D18 分片引用存完整对象键

结论：`ShardRef.Key` 存完整对象键（数据集名、创建它的 snapID 与分片文件名都在内），读侧一律按清单里的 `key` 取对象。
原因：复用分片的对象挂在首次创建它的那个快照目录下，当前快照前缀下并没有它；只存文件名片段就把拼键的责任推给读侧，冷启动直接读不到复用分片。

## D22 分片引用记录路径范围

结论：`ShardRef` 带 `min_path` 与 `max_path`，取片内首末条目的 path，构建分片时必须填。
原因：按前缀加载要先判断哪几片可能含有该前缀的条目，没有范围字段就得把所有分片下载完才知道能丢哪些，前缀加载就省不下流量；清单本来就只是引用列表、体积几十 KB，加两个字段成本极低。

## D23 前缀加载入口的入参是路径前缀

结论：`LoadPrefixes(ctx, prefixes)` 的入参就是路径前缀列表：空列表不加载任何分片、映射为空，含空串元素匹配一切、等于全量，加载失败不动旧映射，与 `Refresh`、`Start` 互斥、宿主二选一。
原因：入参直接是前缀就能在库内做完相关性判定；另一个候选传分片引用列表，调用方得先自己读一遍清单才拿得到它，信息一点也没多。

## D24 坏块物理移走且不检查引用与 pin

结论：`Quarantine` 无条件把 Open 校验失败的块移入隔离目录，与 `Remove` 及其他隔离操作在同一把锁内串行；`ListQuarantined` 沿用 `List` 的枚举规则（字节序升序、空切片返回、忽略临时与非法名）；`RemoveQuarantined` 目标不存在返回 nil。
原因：隔离是正确性动作、引用计数是索引层的逻辑关系，用计数拦住移走就等于继续对外提供坏块；打标记而不移动的话，坏块会继续让读失败、还会留在枚举结果与回收判定里。

## D25 隔离目录与块目录并列

结论：隔离目录是根下与 `blocks/` 并列的 `quarantine/`，同样按指纹前 2 字节分两级，移动用一次 rename 完成。
原因：两个目录同在根下、同一文件系统，一次 rename 就原子可见且不会跨设备失败；并列布局让块枚举与回收天然看不见坏块，回收侧不需要改动。

## D26 隔离与清理按目标状态幂等

结论：`Quarantine` 在源块已不在 `blocks/` 时返回 nil（已在隔离区与从未存在同样处理），目标已存在时 rename 覆盖；`RemoveQuarantined` 目标不存在返回 nil；只有真实 I/O 错误才报错。
原因：修复队列与重扫描并发时会把同一个块反复隔离、反复清理，按目标状态返回让调用方不必判错重试，也与「对象不存在不算错误」这条既有口径一致。

## D27 同指纹重写等价幂等跳过

结论：`Put` 不设「已存在就跳过」分支，一律写完临时文件再 rename 原子覆盖，多协程同时写同一内容各写各的临时文件、最后留下的必为完整块。
原因：指纹等于内容，覆盖写进去的必然与已有内容相同；坏块被移走之后重下的场景里目标位置本来就空着。

## D28 本地副本淘汰单开一个入口

结论：`Evict` 只删块的本地副本：引用计数不拦、pin 大于 0 返回 `ErrInUse`、块不存在返回 `ErrNotFound`，与 `Remove`、`Put` 同锁串行，只动 `blocks/` 下正常块路径，索引条目与引用关系都不受影响。
原因：容量淘汰删的正是仍被快照引用的活块副本，`Remove` 碰到计数大于零就报错、删不动；两个维度共用一个入口就只能靠误删逻辑引用来完成淘汰。

## D31 多 tar 发布单开一个包

结论：`core/publish` 把一批 tar 按块切分、每块先写本地 CAS 再传对象存储、条目排序后只调一次提交发布成一个快照；源的 path 在同批次内唯一、不含 `#`、发布后不可变，条目的 `node` 字段固定不填，任一块失败就取消整轮不提交，提交失败只清理本次上传的分片与清单、不删远端块对象。
原因：写侧编排跨 objectstore、cas、index 三个包，放进任何既有包都会造成反向依赖或依赖环；单快照让读侧只看到发布完成的整体；块上传必须早于提交，因为提交的完整性验证只看本地 CAS；同一条 path 对应不同内容会让索引指向两份数据，所以 tar 文件名要带版本或哈希。

## D32 日志脱敏下沉为共同依赖

结论：`core/logging` 提供字符串脱敏、URL 脱敏与一个包装标准库 slog handler 的构造器，只用标准库，与 core 其他包互不引用，上层两个独立 module 在各自日志装配处包这一层。
原因：agent 与 controller 是两个互不引用的 module、core 是唯一的共同依赖，各写一份就会出现两种脱敏口径和两份维护。

## D33 删除就是新快照不含该条目

结论：`CommitChanges(ctx, dataset, puts, dels)` 是提交的事务主入口，`Commit` 是它传空 dels 的包装；合并规则是先按 dels 过滤旧表再并上 puts、同一 `(path, chunk)` 冲突时 puts 赢、dels 指向不存在的条目是空操作；`Delete` 的 chunk 非负删该 path 的这一块、`-1` 删该 path 全部块，目录级批量由调用方读旧快照展开成 path 列表后一次提交。
原因：每次提交都读全量旧条目重建分片，这个模型里「删除」就是这次没带上它，索引里不出现 tombstone、不可变对象照旧，不需要额外的删除事件通道；代价是写放大与冲突重试随提交频率先到上限。

## D34 命令名按职责取且禁用 tc

结论：命令名不带统一产品前缀、改名不留别名，`traincache`、`traincacheds`、`trainpublish` 各自保留职责名；`tc` 这个名字不能用。
原因：`tc` 是 Linux iproute2 的流量控制工具（`/usr/sbin/tc`），压测装置大量用真 `tc` 做限速，同名会直接歧义。

## D35 本地块副本按节点集合差回收

结论：`Collector.Sweep` 的删除面只有快照对象（清单与分片），不删任何节点的本地块、也不删数据块对象；本地孤儿副本的清理入口是 `index.NewLocalGC` 的 `Sweep(ctx, datasets)`，按节点周期执行，`datasets` 必须是本轮全集，任一数据集索引读不到（确定不存在除外）或损坏就整轮不删任何块。
原因：本地 CAS 是节点级全局、内容寻址，块不按数据集分区，「这个副本还有没有数据集引用它」只能按节点回答，按单个数据集算集合差会把同一节点上其他数据集的副本当孤儿删掉；而凑不出活块集合却照集合差删除，这批块会整批进删除名单，代价是本节点全部回源重下。
