# Controller
## 定义两个CRD，并实现Controller
两个CRD：DataSet与WarmupTask，并且实现他们的子资源（将status与主端点解耦，scale不开）
DataSet: 静态描述数据长什么样子，如何被消费。回答有哪些块、块在哪
WarmupTask: 一次预热的运行时载体，回答给谁预热、分别预热哪些块、分别现在预热到哪里了，现在准备到哪里了
用户只需要创建DataSet与WarmupTask两个CRD即可完成整套预热任务，Controller中没有Job这个概念(这应该不是设计错误)，不需要用户写Job的yaml文件
#### DataSet：登记数据集
这里只描述关键字段，不做完整CRD的yaml文件描述
- 基本字段
group: traincache.io
name: datasets.traincache.io
scope: Namespaced
version: v1alpha1（storage: true）
subresources: 开status
schema: 只描述spec与status的字段结构，k8s使用schema做校验
- 关键语义
1. 数据源: 存储后端endpoint，bucket，数据集名(`dataset/<数据集名>/`这一层)，引用凭证(Secret),当前使用的快照id，哪些节点能访问数据源
2. 块结构: ChunkSize，一个三元组列表`[ (tar分片名称,块数,尾块大小) , ... ]`
3. 元数据: 这是给人或者上层工具看的业务描述，包括：样本数量、数据格式、内容说明、数据版本、来源、用途(默认留空即可，这些内容 只做登记 ，Controller 与 Agent 都不读它做决策)
这里面有spec字段也有status字段，需要自行分辨，此处只描述实现功能
不记录谁引用的Dataset
#### WarmupTask：登记一次预热


这里只描述关键字段，不做完整CRD的yaml文件描述
命名空间：namespaced
1. 预热的DataSet
2. 训练类型(枚举：epoch/shuffle/curriculum/static)，随机种子不进spec，放到DataLoader即可
3. 需要的训练Pod数量，Pod之间的亲和性(默认只看资源都不够，一节点允许多Pod可以改成一节点一Pod)
4. 筛选出来的候选节点列表(详细筛选方法见下面)
5. readinessTable：P×N 就绪表（cij 或比例），分配依据，也是观测入口。(P、N 几十到几百，表是 P×N 个整数，可控)
6. podNodeReadiness:每个 (Pod, 预热节点) 配对一条，每个 Pod 有 preheatFanout 条，至少记录一下内容，podName与PodDetail之间通过podNodeReadiness来关联
   - nodeName
   - podName
   - podDetails（是用户手动填写的，约定每个Pod如何使用资源与资源配置情况）
     - 开始的实际消费顺序是什么initialConsumeOrder（实际Pod消费顺序清单；未指定或指定不全时，按 Pod 数量默认切分），
     - 启动窗口K
     - 需要资源声明
   - readyBlockBitmap：块级就绪位图（只有“落盘 + 校验通过”才置 1）
   - startupWindowReady：窗口内就绪块数
   - startupWindowReadyRate：= startupWindowReady / K（仅用于观测；门控用整数判据 startupWindowReady ≥ floor(阈值 × K)）
   - globalDecayScore：全局衰减就绪度得分（取整，放行快照）
   - lastReportTime：最近上报时间，用于判“进度是否还在涨
7. gateDecision(门控状态机，记录门控状态与放行原因)
8. lastUpdated：最近一次 status 更新时间，用于观测“分数是否还在动”
9. observedGeneration：幂等必备，判断 status 是否已反映最新 spec


###### 候选节点筛选
资源条件：节点剩余 CPU/内存/存储是否够这个训练 Pod 跑。这是 Scheduler Filter 的活，但预热阶段也要粗看——预热本身消耗节点资源（缓存、IO），给一个资源已满的节点预热是浪费。
数据可达性：节点需带有人工维护的 `traincache.io/s3-access=true` 标签；Dataset 可声明可选 selector 进一步收窄。排除拿不到数据的节点。
节点健康状态：NotReady、有污点、正在维护的节点直接排除。

#### DataSet::Controller核心逻辑
- 概述
它是静态数据契约，不是运行时执行者
负责校验数据是否合法，固化块空间，探测入口，确认node节点是否可以访问数据源

- 核心逻辑
1. 接收到一个DataSet声明，先检验数据字段是否完整(如chunkSize>0)，
2. 检查后端格式是否正确，bucket,数据集名,Secret引用正确，三元组列表格式正确等
3. 入口是否能访问： 检查快照指针(不一定就是CURRENT指针，可能任务开始后数据变化)，快照清单是否存在，能否正常访问等
4. 检查节点标签 `traincache.io/s3-access=true`，判断哪些节点可以访问数据源；该标签由用户/集群管理员手工添加到 Node，任何组件不得自动写入
5. 展开块空间，固化编号规则：将以后现推数据块号变成只在DataSet Controller中推一次,新增startChunk字段
```text
totalChunks: 9
blockLayout:
  - shard: shard-000.tar, startChunk: 0, count: 3, lastChunkSize: 50MB
  - shard: shard-001.tar, startChunk: 3, count: 2, lastChunkSize: 30MB
  - shard: shard-002.tar, startChunk: 5, count: 4, lastChunkSize: 50MB
```
6. 写status
7. 触发下游: 如果spec发生变化，通知所有引用他的WarmupTask

- 幂等操作
  控制器重启，事件重放都不能产生重复操作informer的事件可能重复送达，reconcile 逻辑必须做到执⾏几次都结果⼀样

#### WarmupTask::Controller的核心逻辑
- 概述
WarmupTask::Controller是WarmupTask的唯一执行者，监听WarmupTask创建之后的行为
先筛选出值得预热的节点，向这些节点Agent下发块级别的预热任务(gRPC函数调用)
然后持续收集Agent上报的进度，算出各个节点的就绪度
当就绪度达标之后，摘除Pod上面的SchedulingGate，保存此时的分数快照，放行调度，
同时将算好的分数快照暴露给调度器，作为调度器选择节点的一个偏好
它管“数据备好没、能不能放行、哪个节点备得最好”，不管“Pod 最终坐哪”

- 名词声明
就绪度：指数据准备好了多少的度量
窗口内就绪度：只看启动窗口内那部分数据准备好了多少
全局衰减就绪度:看全程数据备好了多少，但按块离起点的距离加权：窗口内权重 1，窗口外指数衰减，衰减到阈值以下不计
全局衰减就绪度 = 窗口内就绪度 + 窗口外就绪度
预热节点集合（下文也称暖节点集合）：某个 Pod 在本次任务中被选中预热的那 preheatFanout 个节点，数量由 preheatFanout 声明，通常多于一个
最终落点：调度器真正把 Pod 放到的那一个节点，正常情况下从该 Pod 的预热节点集合里选出，被抢占时也可能落到集合之外

- 具体逻辑
1. Controller盯着训练Pod的声明，筛选出候选节点，然后使用GWAA算出每个节点需要预热哪些Pod的窗口，以及每个Pod需要预热哪 preheatFanout 个节点
2. 通过gRPC调用向这些节点下发块粒度级别的预热任务
3. 接收Agent的进度汇报，更新 podNodeReadiness（配对级）：
4. 将就绪度填回到CRD的status里面
5. GangScheduling Gate(这不是在Scheduler里面的Permit hook上面的)，持续观察startupWindowReadyRate
6. 当下面三个条件满足其一就放行
   1. 每个 Pod 的预热节点集合中至少有一个节点，其该 Pod 的 startupWindowReady ≥ floor(阈值 × K_i)（例如 K=8、阈值=0.8 时 6 块即可）；预热节点集合就是候选节点里被该 Pod 选中预热的那 preheatFanout 个节点。全部 Pod 满足才放行
   2. 已经有一个pod达标之后，未达标的Pod的提前降级条件必须同时满足“gap > gap_min”和“slope < slope_min”；
   ```text
   gap  = gateThreshold - rate          // 离阈值还差多少
   slope = (rate_now - rate_prev) / (t_now - t_prev)   // 就绪率变化速度，需上报间隔 >= min_interval
   
   if gap > gap_min  &&  slope < slope_min:
   触发提前降级放行
   ```
   3. 超时t_max(降级放行)
7. 放行逻辑
   1. 算出所有Pod的全局衰减就绪度分数:S(node),一会交给Scheduler的就是这个就绪度快照，从这往后预热的不算入分数；S(node) 快照覆盖全部预热节点，Scheduler 在各 Pod 的暖节点集合中选择最终落点
   2. 摘掉Pod的SchedulingGate
   3. 把各预热节点的 S(node) 快照写进对应Node的annotation

- 幂等操作
控制器重启，事件重放都不能产生重复操作informer的事件可能重复送达，reconcile 逻辑必须做到执⾏几次都结果⼀样

#### 就绪度得分逻辑
- 参数
K： 启动窗口大小（前K块权重均为1）
H： 半衰期（多少块后权重掉一半）
C： 截断距离（超过不计分）
- 公式
$$
w(i) =
\begin{cases}
1, & i < K \\
0.5^{\frac{i - K}{H}}, & K \leq i < C \\
0, & i \geq C
\end{cases}
$$
窗口内恒 1 ，窗口外按半衰期指数衰减：每过 H 块，权重减半，超过 C 直接 0，不计
存储的时候将窗口内就绪度与窗口外就绪度分开存储

#### GWAA：贪心窗口亲和分配（Greedy Window Affinity Assignment）
###### 定位
GWAA 是一个纯分配算法模块，只回答一个问题：在候选节点上，每个节点应该预热哪些 Pod 的窗口。
它给每个 Pod 选出 preheatFanout 个预热节点；Pod 的最终落点不在此处决定，由 Scheduler 在放行后的分数快照中选择。
它不涉及门控、放行、调度与兜底，输入输出边界清晰，可独立实现与测试。
###### 输入
Pods（P 个）：每个 Pod 的窗口块集合 windowBlocks，用于标识该 Pod 需要预热的窗口。
Nodes（N 个候选节点）：已通过粗筛（资源余量、数据可达、健康均满足）的节点列表。
就绪表 cij：节点 j 上 Pod i 的窗口已就绪块数或比例，由 Agent 上报增量更新。
preheatFanout：每 Pod 需要预热的节点数，默认 1（与单节点预热的现状兼容），典型值 2。
Pod 间亲和字段：
podAffinity / podAntiAffinity：Pod 间必须同节点 / 不可同节点的约束；
allowMultiPodPerNode：默认 false（一节点一 Pod）；true 时允许多 Pod 同节点，同节点可放数量由亲和约束决定。
###### 约束判定
本模块只处理两类约束，均来自输入字段：
亲和性约束：若 Pod i 与 Pod k 反亲和，则二者不可分配到同一节点；若必须亲和，则须同节点成组分配。
一节点一 Pod / 多 Pod：allowMultiPodPerNode=false 时每节点最多 1 个 Pod；true 时同节点可放多个 Pod，但须满足亲和性约束。本次把该字段正式接线，GWAA 按它判断每个节点还能认领几个 Pod。
资源是否足够已在粗筛保证，模块内不再重复判断。

###### 算法流程
亲和组合并：将“必须同节点”的 Pod 合并为超 Pod，按超 Pod 的窗口集合与就绪表参与分配；分配后组内共享节点。
贪心认领：按各 Pod（或超 Pod）的最大 cij 降序处理，每个 Pod 在候选节点中按 cij 从大到小认领 top-K 可行节点，K 即 preheatFanout；若某个节点因“一节点一 Pod”、反亲和或节点能容纳的 Pod 数已满而不可放，就顺延到下一个可行节点；可行节点不足 K 个时按实际可行数认领。
冲突裁决：多个 Pod 争同一节点且无法全部容纳时，比较各 Pod 的 (cij − 次优 cik) 差值，差值大者（更依赖该节点）保留，其余让步到各自尚未认领的下一个可行节点。
未分配标记：无任何可放节点的 Pod 标记为 unassigned，交上层兜底（回源 / 扩候选）。

###### 输出
`assignment[i]`：Pod i 的 K 个预热节点（节点名列表，按 cij 降序）；可行节点不足 K 个时按实际可行数给出，一个可行节点都没有时标记 unassigned。
preheatSet：全量 (Pod i, 节点 j) 配对集合，覆盖每个 Pod 的 K 个预热节点；未分配的 (Pod, 节点) 组合不预热。
unassignedPods：无可行节点的 Pod 列表，供上层兜底。
输出直接作为“哪个节点预热哪个 Pod 的窗口”的执行依据；最终落点由 Scheduler 在放行后的分数快照里选择，不在 GWAA 输出里。

###### 复杂度
亲和组合并：O(P)
贪心认领：O(P×N×K)
冲突裁决：最坏 O(P×N×K)，实际远小于此
总计 O(P×N×K)，P、N 为几十至几百量级，K 是小常量（默认 1、典型 2），毫秒级，每轮 Poll 重算也够用

## Scheduler
实现`Score`与`NormalizeScore`拓展点
- 编写程序
使用Go语言写一个TrainCacheScore程序，实现ScorePlugin接口，核心方法就是Score()
在里面读取你 Controller 写到 Node annotation 上的分数，做Normalization，并返回（返回的是一个0~100之间的整数）
- 写配置文件
在 KubeSchedulerConfiguration 的 profile 里启用插件，只挂到 score 扩展点：
```yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
   - schedulerName: default-scheduler
     plugins:
        score:
           enabled:
              - name: TrainCacheScore
                weight: x  # 权重值，可根据实际需求调整
```
注意：`KubeSchedulerConfiguration` v1 没有 `normalizeScore` 配置字段（strict decoding 会拒绝）。只要插件实现了 `ScoreExtensions`，framework 会在 score 阶段后自动调用其 `NormalizeScore`，无需也不能在配置里单独启用。

## 接入真实DataLoader
接入真实 DataLoader 不是搭一个假训练循环，而是让真实 tar 分片、真实块语义、真实消费顺序贯穿到测量里。
DataLoader 按 Dataset 固化的 chunkIndex 与 WarmupTask 的初始消费计划组织 sampler，
每个 worker 的读取序列与预热序列对齐；epoch/shuffle/curriculum 通过钩子上报事件给 Agent，触发运行时重预取
存未命中走回源并在打点中区分。打点记录每 step 的 step_time 与 wait_time（并拆出本地命中等待与回源等待），按窗口/切换点/全程聚合。
负载均衡必须在这一步接入：多 worker 的块分配要均衡、worker 序列要与本节点预热对齐、切换后要重新均衡——否则 wait_time 反映的是分配不均和跨节点回源，而非预热收益，后续“启动收益 vs 全程收益”的归因就失效。
