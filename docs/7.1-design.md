# Controller & Scheduler design

Controller 管预热生命周期，Scheduler 管训练 Pod 落点；两者不互调，只经 Pod 注解传分数快照。代码放在独立 Go module `traincache/controller`。

## 定位

四个组件各管一段，串起来是一条从"数据登记"到"Pod 放行"的链路。

| 组件 | 职责 |
|---|---|
| `DataSet` 控制器 | 校验数据契约、固化块编号与布局、解析可达节点、校验快照可访问性；只写 status，不触发预热 |
| `WarmupTask` 控制器 | 唯一执行者：筛候选节点、GWAA 分配、按块下发/更新/取消预热、轮询进度、门控判定、放行时冻结评分并与摘 gate 同一次 patch 写进 Pod 注解 |
| MutatingWebhook | Pod 创建时注入 SchedulingGate、WarmupTask 引用与 Pod 序号注解，是门控链路的前置条件 |
| Scheduler 插件 | 只读 Pod 注解里的节点分数表，实现 `Score` / `NormalizeScore`，返回 0~100 |

`WarmupTask` 控制器管"数据备好没、能不能放行、哪个节点备得最好"；Pod 最终落在哪台机器由 Scheduler 在放行后的分数快照里挑。训练 Pod 经 hostPath 直读本地 CAS，不经过 Controller；数据发布（tar 切块、快照提交）在 `core/publish` 与 `traincache trainpublish` 里完成；运行时重预取（epoch/shuffle/curriculum 切换）在 Agent 的 `PersistentPrefetcher` 里完成，阶段切换永不进入调度路径。

过关标准是完整跑完从提交 `DataSet` + `WarmupTask`、选出预热节点、放行，直到持续预取与阶段切换重预取的全流程训练。

## 架构与依赖方向

controller-manager 管两个 CRD，经 gRPC 调用 Agent 下发预热任务；Webhook 在 Pod 创建时拦截并注入调度门，先于调度器运行；Scheduler 只读 Pod 注解，不反查 Controller。

依赖方向固定为单向、不得反向：`cmd/*` 依赖 `internal/{controller,webhook,scheduler}`；`internal/controller/*` 依赖 `api/v1alpha1` 与 `gwaa`、`gate`、`nodescore`、`agentclient`、`storage`、`config`、`logging`、`metrics`、`scorefmt`；`internal/{nodescore,agentclient,webhook,scheduler}` 依赖 `api/v1alpha1`；`internal/scheduler` 另依赖 `scorefmt`；`internal/agentclient` 依赖 `agent/api/agentpb`；`internal/storage` 依赖 `core/{objectstore,index}`；`api/v1alpha1` 只依赖 `k8s.io/apimachinery`。

禁止 `api` 依赖 `internal`、禁止 `gwaa`/`gate`/`scorefmt` 依赖 k8s 客户端或 core、禁止 `scheduler` 依赖 controller 内部包、禁止 `internal` 依赖 `cmd`：底层不得反向依赖上层，避免小改动牵连大范围。

与已有模块的复用只有三处：校验快照存在性与可访问性用 `core/objectstore` 的 `NewS3Store` 与 `Store.Get`；`core/index` 的 `Manifest`、`ShardRef`、`Entry` 与键布局常量只读复用；`agent/api/agentpb` 的 `PreheatService` 扩展后由 Controller 作 gRPC 客户端调用。

`controller` 加入仓库根 `go.work`；跨 module 引用沿用现有约定：不写 `require traincache/core` / `traincache/agent`，由 workspace 解析。`GOWORK=off` 构建会失败，与现有 agent 依赖 core 的做法一致，不引入 replace。

## CRD 类型

Group `traincache.io`，Version `v1alpha1`。两个 CRD 均 Namespaced，跨对象引用只允许同 namespace。只开 `status` 子资源，不定义 `scale`。`WarmupTaskSpec.podCount` 与 `dataSetRef` 不可变，由 CRD CEL 校验 `self == oldSelf`；Controller 不创建 Job/Pod、不扩缩容、不重建 Pod。用户只需要创建 `DataSet` 与 `WarmupTask` 两个 CRD 就能完成整套预热任务，Controller 里没有 Job 概念，用户不用写 Job 的 yaml。`traincache.io/s3-access` 标签由用户/集群管理员手工维护，任何组件不得写入。

`DataSet` 是静态数据契约，不是运行时执行者，描述数据长什么样、如何被消费——有哪些块、块在哪（endpoint、bucket、数据集名、chunk 大小、shards 列表、可达节点选择器）。`WarmupTask` 是一次预热的运行时载体，回答给谁预热、分别预热哪些块、现在预热到哪里了（引用 DataSet、指明 Pod 集、定义门控与调度策略）。DataSet 不记录被谁引用，WarmupTask 单向引用 DataSet。

### DataSet

`spec` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `endpoint` | string | 存储后端 endpoint |
| `bucket` | string | bucket 名 |
| `datasetName` | string | 数据集名，键前缀是 `dataset/<数据集名>/` |
| `secretRef` | LocalObjectReference | 访问凭证引用 |
| `snapshotID` | string | 当前使用的快照 id；空表示 CURRENT |
| `chunkSize` | int64 | 块字节数 |
| `shards` | ShardSpec 列表 | 块结构三元组 |
| `accessibleNodeSelector` | LabelSelector | 可达节点选择器；未设置时默认 `traincache.io/s3-access=true` |
| `shuffle` | bool | 是否打乱 |
| `metadata` | DataSetMetadata | 业务描述，只做登记，Controller 与 Agent 都不读它做决策 |

`shards` 的每一项：`name` 是 tar 分片名称；`count`（int32）是该分片的块数；`lastChunkSize`（int64）是末块字节数，取值 `0 < v <= chunkSize`。

`metadata` 有六个字段：`sampleCount`（int64，样本数量）、`format`（数据格式）、`description`（内容说明）、`version`（数据版本）、`source`（来源）、`purpose`（用途），默认留空即可；这些内容只做登记，Controller 与 Agent 都不读它做决策。

`status` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `observedGeneration` | int64 | 已反映的 spec 代际 |
| `conditions` | Condition 列表 | 状态条件 |
| `snapshotID` | string | 解析后的具体快照 |
| `totalChunks` | int32 | 块总数 |
| `blockLayout` | BlockLayout 列表 | 分片级块布局 |
| `accessibleNodes` | string 列表 | 选择器的解析结果，升序 |

`blockLayout` 的每一项：`shard` 是分片名；`startChunk`（int32）是该分片首块的全局编号，跨分片累计；`count`（int32）是该分片块数；`lastChunkSize`（int64）是末块字节数。

### WarmupTask

`spec` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `dataSetRef` | LocalObjectReference | 要预热的 DataSet |
| `targetRef` | TargetRef | 训练负载 |
| `podCount` | int32 | 需要的训练 Pod 数量 |
| `preheatFanout` | int32 | 每个 Pod 预热节点数的上限，默认 2，最小 1 |
| `preheatFanoutMin` | int32 | 预热节点数的目标下限，默认 1，最小 1，必须不大于 `preheatFanout` |
| `affinity` | AffinityPolicy | Pod 间亲和策略，仅记录，v1 不参与算法 |
| `trainingType` | TrainingType | 训练类型 |
| `podDetails` | PodDetail 列表 | 每个 Pod 的窗口与资源声明 |
| `gate` | GatePolicy | 门控参数 |
| `score` | ScorePolicy | 评分参数 |
| `candidate` | CandidatePolicy | 候选节点筛选策略 |

`targetRef`：`apiVersion` 是目标 API 版本；`kind` 取值 `Job`、`StatefulSet`、`Pod`；`name` 是目标名字；`podLabelSelector` 可选，按标签筛 Pod。

`podDetails` 的每一项：`index` 是 Pod 序号，取值 `0..podCount-1`，必须连续；`resources` 是需要资源声明；`initialConsumeFiles` 是 tar 分片名列表，全部 Pod 合起来必须恰好覆盖全部分片且每分片出现一次，覆盖不全或重复时整组回退默认均分；`k`（int32）是启动窗口块数，0 或省略表示自动计算。

`gate` 的每一项：`threshold`（float64）是就绪阈值，取值 0~1；`gapMin`（float64）是提前降级的差距下限，取值 0~1；`slopeMin`（float64）是提前降级的斜率上限，单位比例/秒，通常不大于 0；`tMax`（Duration）是门控绝对上限；`minInterval`（Duration）是两次上报采样的最小间隔。

`score` 的每一项：`halfLife`（float64）是半衰期 H，单位块；`cutoff`（int32）是截断距离 C，单位块。K 不在 `score` 里：每 Pod 的 K 来自 `podDetails[].k`，省略时按自动计算口径得出，既是启动窗口也是评分平台段。

`candidate` 的每一项：`requireReady` 是是否要求节点 Ready；`ignoreNoSchedule` 是是否忽略 NoSchedule 污点；`minFreeDiskBytes` 是最小剩余磁盘字节数。

`status` 字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `observedGeneration` | int64 | 已反映的 spec 代际 |
| `conditions` | Condition 列表 | 状态条件 |
| `phase` | WarmupPhase | 任务阶段 |
| `consumeOrderSource` | ConsumeOrderSource | 消费顺序来源，取值 `Spec` 或 `Default` |
| `startedAt` | Time | 首次进入预热的时刻 |
| `candidateNodes` | string 列表 | 候选节点，稳定排序，是就绪表的列头 |
| `readinessTable` | int32 二维数组 | P x N，行是 Pod 序号、列是 `candidateNodes` 顺序，值是窗口就绪块数（计数，非比例） |
| `podNodeReadiness` | PodNodeReadiness 列表 | 每 (Pod, 实际认领节点) 一条 |
| `gateDecision` | GateDecision | 门控状态机 |
| `lastUpdated` | Time | 最近一次 status 更新时间，用于观测分数是否还在动 |

`podNodeReadiness` 的每一项：`podIndex` 是 Pod 序号；`podName` 是 Pod 名字；`nodeName` 是预热节点；`actualNode` 是实际落点，同一 Pod 的各条取同一个值；`readyBlockBitmap`（byte 列表）是该预热节点上报的位图；`startupWindowReady`（int32）是窗口内就绪块数的原始计数，与 `readyInWindow` 由同一次计算赋值；`readyInWindow` 是门控条件①读取的中间结果；`requiredReady` 是 `floor(threshold*K_i)`；`startupWindowReadyRate`（float64）仅观测，不参与门控；`globalDecayScore` 是全局衰减就绪度得分；`state` 是该预热节点的状态，无可行节点时为该 Pod 的汇总态（任一候选 Ready 则 Ready，全部 Failed 则 Failed，否则 Preheating）；`minUnmet` 是该 Pod 实际 Assignment 数量低于 `preheatFanoutMin`，与分配算法的判定同步；`lastReportTime` 是该预热节点最近一次上报。

`podNodeReadiness` 各条目通过 `podIndex`/`podName` 与 `podDetails` 关联：`podDetails` 记录用户声明（消费清单、窗口 K、资源），配对条目记录运行时就绪事实。

`gateDecision` 的每一项：`state` 取值 `Hold`、`Released`、`Degraded`；`reason` 是放行原因；`decidedAt` 是判定时刻；`podRates` 是各 Pod 的速率、差距、斜率列表，每项含 `podIndex`、`rate`（就绪率）、`gap`（离阈值还差多少）、`slope`（就绪率变化速度）。

枚举取值冻结，不得新增或换拼写：

| 枚举 | 取值 | 备注 |
|---|---|---|
| `TrainingType` | `epoch` / `shuffle` / `curriculum` / `static` | 随机种子不进 spec，放在 DataLoader |
| `ConsumeOrderSource` | `Spec` / `Default` | `Default` 表示任一清单含未知分片、全组重复或未恰好覆盖全部分片后整组回退 |
| `WarmupPhase` | `Pending` / `Filtering` / `Preheating` / `Gating` / `Released` / `Degraded` / `Failed` | |
| `GateState` | `Hold` / `Released` / `Degraded` | |
| `PreheatState` | `Preheating` / `Ready` / `Stopped` / `Failed` | |
| `AffinityPolicy` | `Any` / `Pack` / `Spread` | 仅记录，v1 不参与算法 |

### 启动窗口 K_i

`podDetails[].k` 可省略（CRD 下限 0，0 表示省略）。省略时 Controller 按下表算出每个 Pod 的 `K_i`：

| 符号 | 计算 |
|---|---|
| `W_i` | Pod i 实际分到的块数：填文件清单时为所列分片的块数之和；默认均分时为 `[floor(i*T/P), floor((i+1)*T/P))` 的长度 |
| `K_window` | `ceil(startupWindowBytes / chunkSize)` |
| `K_cache` | `floor(cacheCapacityBytes × maxFillFraction / (podCount × chunkSize))`；`cacheCapacityBytes=0` 时不计算 |
| `K_i` | `clamp(min(W_i, K_window, K_cache), 1, W_i)` |

`startupWindowBytes` 默认 536870912（512MiB），`maxFillFraction` 默认 0.125，与 `cacheCapacityBytes` 同在 ConfigMap `traincache-config`。`maxFillFraction` 是自动 K 的缓存预算口径：全部 Pod 的自动 K 总量不超过缓存容量的这个比例，按 `podCount` 均摊；显式 K 超过该预算只发事件，不拒绝。

K 省略时，Controller 把算出的值 patch 回 `spec.podDetails[].k`，立即 `Requeue`，并发 Normal 事件 `KDefaulted`（日志 `startup window K defaulted`）；后续门控与轮询只读 spec 中的持久化值。

用户显式填 K 时有效范围是 `1..W_i`；`K > W_i` 置 `Condition InvalidSpec=False` 并拒绝，不截断、不钳制。`cacheCapacityBytes > 0` 时，全部 Pod 实际请求块数（`min(max(K_i, score.cutoff), W_i)`）合计超过 `cacheCapacityBytes × maxFillFraction` 只发 Warning 事件 `KExceedsFillLimit`，任务照常执行，超出缓存预算的块由回源承担。

预热请求的块数是 `min(max(K_i, score.cutoff), W_i)`，超过消费顺序长度时截断。启动阶段只想预热 `K_i` 块时，`score.cutoff` 不能大于 `K_i`；`cutoff` 调大可以覆盖全程评分，代价是预热块数与耗时增加。

## 控制器

### WarmupTask 驱动与内存态

WarmupTask 控制器是唯一执行者：筛节点、下发块级预热任务、收集进度算就绪度、达标后摘 Pod 的 SchedulingGate 并把分数快照暴露给 Scheduler。两种驱动：`Reconcile` 响应 CR 变更，`Poll` 定时拉 Agent 进度。每个 controller `MaxConcurrentReconciles = 1`，同一 WarmupTask 的 reconcile 串行。内存态仅两项：`rateHistory[taskUID+podIndex][]sample`（保留最近两次、间隔不小于 `minInterval`）与 Agent 客户端池；其余状态一律落 status。重启后全部状态从 CRD 与 Pod 注解重建，rateHistory 为空、门控条件②需重新积累两个采样点。所有时间比较走注入的时钟，门控时序在测试里可驱动，不依赖真实时钟。K 自动计算参数来自 `TRAINCACHE_*` 环境变量，零值回退包内默认值。

### 候选节点筛选

一台 Node 要依次通过全部规则才是候选（先排除后保留）：`Ready=True`；命中 DataSet 的 `accessibleNodes`；无 `NoSchedule/NoExecute` 污点（`ignoreNoSchedule=true` 时只排除 NoExecute）；allocatable 减去已请求资源后满足最大 `podDetails[].resources`；该节点存在 Ready 的 agent Pod。返回节点名升序，作为 `readinessTable` 的列顺序。资源、可达性、健康三项是粗筛口径：预热本身消耗节点资源（缓存、IO），给一个资源已满的节点预热是浪费；数据可达性要求节点带人工维护的 `traincache.io/s3-access=true` 标签，DataSet 可声明可选 selector 进一步收窄；NotReady、有污点、正在维护的节点直接排除。

### GWAA 分配

GWAA（Greedy Window Affinity Assignment）是纯分配算法：在候选节点上给每个 Pod 挑一批预热节点，不读 k8s、不写 status、不记 log，也不涉及门控、放行、调度与兜底。输入是候选节点上每个 Pod 的窗口就绪块数、已停止节点集合、预热节点数的上下限和一个随机源；输出是每个 Pod 的目标集合、实际认领节点、节点到 Pod 的配对表、每个 Pod 的目标数量与异常标记、无可行节点的 Pod 列表、以及算法轮数。

分配单元是普通 Pod 或亲和合并后的超 Pod：必须同节点的 Pod 先合并为超 Pod，单元的最小预热数取各成员的最大值，最大预热数取各成员的最小值，最小值大于最大值时返回冲突错误；单元共享目标集合，组内共享节点。全部按块数计算；输入若为比例，先按该 Pod 的 `K_i` 还原为块数。

目标数量算法对每个分配单元独立执行：

1. `K_i` 是该单元启动窗口的块数；`S_min = ceil(0.25 × K_i)`：最好的节点就绪不足窗口 25% 时，缓存分布无差异。
2. 可行节点按 `c_ij` 降序、节点名升序排序；`best` 是排第一的节点的 `c_ij`。目标集合排序确定，不走随机。
3. `best <= S_min`：判低信号，`band = min(maxFanout, 可行节点数)`，置低信号标记。
4. 否则 `band = min(maxFanout, 满足 c_ij >= 0.5 × best 的节点数)`，至少 1。0.5 是保留线：与最优节点差距过大的节点不进目标集合。
5. `target = clamp(band, minFanout, maxFanout)`，再按可行节点数封顶。
6. `minFanout > band`：置强制补齐标记，按排序强制补到 `target` 以保留暖备份；该标记只表示目标被下限抬高，不保证实际数量达到下限。
7. `minFanout > 可行节点数`：计划阶段置下限未满足标记，`target = 可行节点数`；无可行节点时目标集合为空，进未分配列表。
8. 冲突裁决、top-up、集合外兜底全部结束后，按最终认领结果回算下限未满足标记：实际认领数少于归一后的下限（0 按 1 处理）为真。
9. 每个 Pod 的决策记录目标数量、低信号、强制补齐、下限未满足、集合外兜底五个标记。

在册保留（迟滞）：目标集合定好后、贪心认领前，用本轮进度查询报持有的配对抑制集合翻转；代际与本轮不同的在册任务不算在册，旧任务不占名额。在册节点只要仍可行、未停止且满足保留线——非低信号时 `c_ij >= 0.5 × best`，低信号时视为满足——就留在目标集合里：集合已满时替换集合内排名最低且不在册的节点，集合未满时直接加入，目标数量不变。效果是现配对不会因为别的节点多就绪一块而被换下；换节点只发生在它掉出保留带、被判停止、或 Agent 报未持有（含代际换代、任务被取消）之后，那时按排序自由选择。迟滞不引入随机消耗，判定与顺序仍是确定的。

贪心认领与冲突裁决：每个单元在目标集合内认领；节点能否放多个 Pod 由 `allowMultiPodPerNode` 与亲和约束声明（`podAffinity/podAntiAffinity` 必须同/不可同节点；`allowMultiPodPerNode=false` 一节点一 Pod，true 时同节点可放多个但须满足亲和），本模块按声明判断空位；资源余量已在粗筛保证。多 Pod 争同一节点且放不下时，比较 `c_ij − 次优 c_ik`，差值大者（更依赖该节点）保留，其余让步到集合内未被认领的次优节点；并列（`c_ij` 相同或差值相同）用注入的随机源均匀随机决定。共享分支未启用。每轮结束后被让步单元只能改认未被认领的目标节点；最多 `len(Pods)` 轮，仍未收敛则保留首个贪心结果并记 `slog.Warn("gwaa: 未收敛，保留首个贪心结果")`。

目标集合与执行集合：目标集合表示"允许在哪里预热"，实际认领集合是执行集合；除集合外兜底外实际认领是目标集合的子集，冲突裁决与补齐只在集合内进行；集合内一个都放不下时为免完全未分配，允许集合外兜底 1 个并置集合外兜底标记（始终最多 1 个，不为补足下限把集合外节点扩成多个）；只有无任何可行节点才未分配。节点到 Pod 的配对表覆盖实际认领的配对，未分配的目标节点不进入。冲突或容量限制让实际数量低于下限时照实写 status 并置下限未满足标记。

固定随机种子下可复现；不同种子下输出合法。种子由任务 UID 与 generation 派生，同一代内每轮重算取同一个随机序列：就绪表与停止集合不变，目标集合与实际认领就不变。表一变（块陆续落盘是常态）严格 `c_ij` 排序就会换人，同代的配对连续性由在册保留保证。亲和组合并 O(P)，贪心认领 O(P×N×K)，冲突裁决最坏 O(P×N×K)，总计 O(P×N×K)；K 是小常量（默认 1、典型 2），P、N 为几十至几百量级时为毫秒级，每轮 Poll 后重算也够用。

### 门控判定

Webhook 为 Pod 注入 SchedulingGate，Controller 持续判定能否移除该 gate。放行判据与 status 记录用整数门槛：`required_i` 等于 `floor(threshold × K_i)`；threshold 大于 0 而结果为 0 时取 1，threshold 等于 0 时 `required_i` 为 0（例如 K=8、threshold=0.8 时 required=6）。判定顺序按固定优先级：

1. 条件③超时：`Now - StartedAt >= TMax` 时判 `Degraded`（绝对上限，代表占用资源的机会成本）。
2. 条件①全达标：每个 Pod 的预热节点集合（以实际认领为准）中至少有一个节点，其该 Pod 的就绪块数达到 `required_i`；全部 Pod 满足时判 `Released`。只在预热节点集合内判定，未被选为预热节点的候选节点不参与。
3. 条件②提前降级放行：首个 Pod 达标的时刻非零、`Now` 与该时刻之差不小于 `minInterval`，且每个未达标 Pod 同时满足 `Gap > GapMin` 和 `Slope < SlopeMin` 时判 `Released`。等待价值是减少启动期回源，补齐速率低于消费速率时继续等待边际收益趋零。
4. 都不满足时判 `Hold`。

`gap` 是就绪率离阈值的差距，等于 threshold 减 rate；`slope` 是就绪率的变化速度，等于本轮采样与上轮采样的速率差除以时间差。两者都用连续速率（不取整），避免量化噪声；速率取集合内各节点 `Ready/K_i` 的最大值，仅供观测与条件②；上一次采样时刻为零或间隔小于 `minInterval` 时不参与条件②。

### 评分计算

按 `(pod,node)` 计算，使用该 Pod 的 `K_i`。分数是"窗口内加权就绪比例"，供 Scheduler 打分调权（对消费顺序位置 i，0 起）：

```text
w(i) = 1,                        i < min(K_i, C)
w(i) = 0.5^((i - K_i) / H),      K_i <= i < C
w(i) = 0,                        i >= C
S    = round(100 * Σ(w(i)*ready(i)) / Σw(i))    // Σw(i)=0 时 S=0
```

窗口内的块决定启动速度，给满权重；窗口外按半衰期衰减（每过 H 块权重减半），超过 C 不计。位图缺失的位按 0 计；`K_i >= C` 时平台段截到 C，无衰减段。status 中窗口内就绪度（`startupWindowReady`）与全局衰减得分（`globalDecayScore`）分开存储。

### 落点兜底

分数是调度偏好，Pod 可能落在暖节点集合之外。Controller 监听 Pod 的 `spec.nodeName`：落在实际预热节点集合内时，只回填 `actualNode` 到各条就绪条目；落在集合外时写各条 `actualNode`、发 `Event NodeDeviation`、对实际节点 `Submit` 同一 Pod 的窗口（优先级 P0），不取消原有预热节点，也不重新门控（Pod 已放行）。兜底失败只影响该 Pod 读路径命中率，由 Agent 回源兜底。

## 组件契约

### Webhook 注入

SchedulingGate 只能在 Pod 创建瞬间挂上、之后只能摘下，所以需要 MutatingWebhook。两种条件同时满足才介入：`objectSelector` 匹配 `traincache.io/warmup=enabled`；命名空间内存在 `TargetRef` 命中该 Pod 且 `Ready` 的 WarmupTask。

注入内容幂等，重复调用效果一样：

1. `spec.schedulingGates` 追加 `{"name":"traincache.io/warmup"}`，已存在则跳过。
2. annotation `traincache.io/warmup-task: <namespace>/<name>`。
3. annotation `traincache.io/pod-index: <i>`；`i` 优先取 Pod label `batch.kubernetes.io/job-completion-index`，其次 StatefulSet ordinal（Pod 名最后一个 `-` 后缀），都失败则不注入并记 `Events` 事件 `WarmupTaskMappingFailed`。
4. 给每个容器补齐 DataLoader 契约要求的 6 个环境变量：`TRAINCACHE_TASK`、`TRAINCACHE_POD`、`TRAINCACHE_POD_INDEX`、`TRAINCACHE_DATASET`、`TRAINCACHE_HOOK_SOCK`（默认 `/run/traincache/agent.sock`）、`TRAINCACHE_GENERATION_AT_START`。同名变量已存在时保留原值；Pod 名在准入阶段可能还没生成（generateName 场景），此时跳过 `TRAINCACHE_POD`，训练侧回退到主机名；generation 取准入时的值，之后任务再更新，训练侧日志只能记启动值。除此之外不注入 nodeAffinity、不改资源。

`failurePolicy: Ignore`：注入失败时 Pod 正常创建，Controller 后续 reconcile 检测"带 `warmup=enabled` 但无 task 注解的 Pod"并记 `Condition GateInjectionDegraded`，静默降级，不阻塞训练。

### Scheduler 评分插件

插件名 `TrainCacheScore`，只有一件事：给"Pod 该不该落到这台 Node"打 0~100 分，分数来自 Controller 放行时写进 Pod 注解的节点分数表。

`Score` 经节点信息取节点名（v0.37 的 Score 签名直接传节点信息对象，不再传节点名字符串）。逻辑：读本 Pod 注解 `CONTROLLER_SCORE_ANNOTATION`（默认 `traincache.io/node-scores`），校验 `task` 与 Pod 的 `traincache.io/warmup-task` 一致、`g >= 1`、未过期，取 `s["<节点名>"]`，返回该分数。注解缺失、节点缺项、JSON 损坏、`task` 不匹配、超 TTL，一律返回 0 且不报错；任何错误都不得让 Pod 因插件失败被拒绝调度。`NormalizeScore` 的映射是 `score' = round(score * 100 / max(1, maxScore))`，全 0 时全部返回 0。

`KubeSchedulerConfiguration` 只启用 `score` 扩展点（weight 由配置决定）；v1 没有 `normalizeScore` 配置字段（strict decoding 会拒绝），插件实现 `ScoreExtensions` 后 framework 在 score 阶段后自动调用 `NormalizeScore`，无需也不能单独启用。

### Agent gRPC 客户端

Controller 是 Agent gRPC 的客户端，扩展 `agent/api/agent.proto` 的 `PreheatService`，只使用增量后的消息，不自定义传输格式。客户端池对外提供四个动作：`Submit` 向节点下发块级预热任务、`Update` 更新同一任务号的窗口内容、`Cancel` 取消任务、`Progress` 复用 `GetPreheatStatus` 拉取状态，返回 `{Generation,Seq,ReadyBitmap,Canceled,Completed,Failed,State,UpdatedAt,Total}`。幂等键是 `task_id = "<namespace>/<name>/p<index>"`，每对 `(pod,node)` 一个 task。请求 `chunks` 为该 Pod 消费顺序的前 `min(max(K_i, Cutoff), W_i)` 个块，`chunks` 顺序即位图位序（位 i 对应第 i 项）。控制面一律显式传 `chunks`、不用 prefixes 展开（CLI 的 prefixes 用法保持兼容，但那条路径的位图不参与门控）。

节点地址解析：列出 `app=traincache-agentd` 且 `spec.nodeName` 匹配的 Pod，取 `status.podIP:CONTROLLER_AGENT_PORT`；节点上没有 Agent Pod 时回退到该节点的 `InternalIP`（没有 InternalIP 时用 ExternalIP）加同一端口。解析器给出的是候选列表，Controller 自己取第一个用；候选列表按节点缓存 30s。超时单次 RPC 5s。`Unavailable/DeadlineExceeded` 映射 `ErrAgentUnavailable`（可重试）；`InvalidArgument/FailedPrecondition` 映射 `ErrPermanent`（写 `Condition PreheatRejected=False`，reason=`AgentRejected`）；`NotFound` 映射 `ErrTaskNotFound`，表示该节点当前没有这个 `task_id`——`Cancel` 收到它按幂等空操作成功，分配差异据此判定该配对未提交。

### 地址解析端点

controller-manager 的 metrics 服务器（`CONTROLLER_METRICS_ADDR`，默认 `:9412`）额外承载一个只读端点 `GET /resolve?node=<节点名>`，供 CLI 按节点名找 Agent。响应体是候选地址的 JSON 数组，元素是 `host:port`：

```json
["10.0.0.5:9410", "192.168.1.10:9410"]
```

候选顺序固定：先是该节点上 Agent Pod 的 `status.podIP:<Agent 端口>`，再是该节点的 `InternalIP:<Agent 端口>`（没有 InternalIP 时用 ExternalIP）。Agent 端口取 `CONTROLLER_AGENT_PORT`，默认 9410，与 DaemonSet 的 hostPort 同值。

状态码：缺 `node` 查询参数返回 400；该节点既没有 Agent Pod、节点也没有可用地址返回 404；查询本身失败返回 500。三种失败都带 `{"error":"<说明>"}` 响应体。

端点与 Controller 用的是同一套解析器（`internal/agentclient.Resolver`），候选列表按节点缓存 30s，只读 Node 与 Pod，不写任何对象。端点不做认证，随 metrics 服务器一起暴露在集群内；Service `traincache-controller-manager` 把 9412 端口转给 manager，集群内的 CLI 用 `traincache-controller-manager.traincache.svc:9412` 访问。

### 预热接口增量契约

代际(generation)是任务版本号,Controller 用它防止旧请求覆盖新状态;位图(ready_bitmap)是哪些块已就绪的压缩表示,第 i 位对应 chunks 第 i 项。

proto 在现有 `traincache.agent.v1.PreheatService` 上做最小增量扩展,进度查询复用 `GetPreheatStatus`,不新增 `GetPreheatProgress`。

```proto
message SubmitPreheatRequest {
  // 字段 1..7 保持现状
  uint64 generation = 8;  // 任务代际；0 表示未提供
}

message PreheatStatus {
  // 字段 1..11 保持现状
  uint64 generation = 12;   // 任务代际
  uint64 seq = 13;          // 位图变更序号，单调递增
  bytes ready_bitmap = 14;  // 位 i 对应请求 chunks 第 i 项；1=已落盘且校验通过
  bool canceled = 15;       // 已收到 Cancel 且未被重新 Submit；Cancel 只标记不删除
  uint32 window_blocks = 16;  // 当前窗口块数 = len(chunks)；Controller 据此判定窗口未变化
}

message UpdatePreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;         // 必须 >= Agent 当前代际
  repeated ChunkRef chunks = 4;  // 新的完整块列表，同时定义位序
  PreheatPriority priority = 5;
}

message UpdatePreheatResponse {
  bool accepted = 1;
  string message = 2;
}

message CancelPreheatRequest {
  string task_id = 1;
  string node = 2;
  uint64 generation = 3;
}

message CancelPreheatResponse {
  bool accepted = 1;
}

service PreheatService {
  // 已有
  rpc SubmitPreheat(SubmitPreheatRequest) returns (SubmitPreheatResponse);
  rpc GetPreheatStatus(GetPreheatStatusRequest) returns (PreheatStatus);
  // 新增
  rpc UpdatePreheat(UpdatePreheatRequest) returns (UpdatePreheatResponse);
  rpc CancelPreheat(CancelPreheatRequest) returns (CancelPreheatResponse);
}
```

Agent 侧语义。Controller 每次改任务带更新的 generation,Agent 只接受不旧于当前代际的请求;进度用 seq 比新旧、用位图看具体哪块好了,网络乱序也不会把新状态盖回旧的。

- 任务表以 `task_id` 为键,记录 generation、有序 chunks ref 列表、位图、seq 与状态;`SubmitPreheat` 与 `UpdatePreheat` 均幂等。
- 位序就是请求 chunks 的顺序,位图第 i 位对应当前任务 chunks 第 i 项,仅在 `cas.Put` 落盘且校验通过后置 1,失败位保持 0,位图长度 `ceil(len(chunks)/8)`。
- seq 单调递增,任一位置位或位图重置都使 seq 增加;Controller 用 `(generation, seq)` 判断进度新鲜度。
- `UpdatePreheat` 全量替换 chunks,同时重定义位序并重置旧位图;在途请求不取消,沿用四队列约定;priority 随请求更新。
- `CancelPreheat` 标记任务取消(canceled 为 true,任务仍留在任务表里,幂等),并撤回该任务未完成的下载。撤回的作用点是每块绑定的下载 ctx:任务受理时结一个下载作用域,窗口里的块逐个结上它,取消即取消该作用域,块在下一个 ctx 边界退出,这三处本来 ctx-aware,即准入排队、源站读、写盘。被撤的块按失败计入回调,任务落 ERROR 终态,completed 保留取消前已完成的块数,ready_bitmap 不变。作用域派生自预取管理器自身的 ctx,所以 Agent 关停仍然连带取消;它只在任务出表时释放(drop、TTL 过期、本次取消),DONE 不释放,因为 DONE 后仍可能收到 `UpdatePreheat` 续窗。被撤的块之后若被真实需求读到,按正常读路径重新入队。
- `generation` 低于 Agent 当前代际返回 `FailedPrecondition`;同 generation 的 Cancel 后再 `SubmitPreheat` 视为新任务。
- `GetPreheatStatus` 返回 generation、seq、ready_bitmap 全量位图、canceled 与 window_blocks,由 Controller 主动拉取,Agent 不推送。
- `window_blocks` 等于当前任务 chunks 项数,与 `total_blocks` 口径不同:后者按去重后的唯一块计,前者按窗口位置计。位图长度只区分 `ceil(块数/8)`,同一字节区间内的窗口变化只能靠这个字段发现。
- `ReportService.ReportBlocks` 是 Unimplemented 占位，保留占位不实现，控制面不实现接收端也不用这个通道；理由见 Agent 侧 D67。

## 数据格式

字节层面的约定：字段顺序不影响 JSON 解析，字段名、类型、默认值不得改。

### CRD 状态布局

`readinessTable` 行下标是 `podDetails[].index`，列下标是 `candidateNodes` 顺序；值是该 Pod 在该节点启动窗口内"已落盘且校验通过"的块数，范围 `0..K_i`（每 Pod 用自己的 K）。候选节点粒度的就绪块数只由 `readinessTable` 承载。

`podNodeReadiness` 按 `(podDetails[].index, 预热节点)` 展开，条数是该 Pod 实际认领的节点数：正常在 `[preheatFanoutMin, preheatFanout]` 内，冲突、容量不足或集合外兜底可低于下限（`minUnmet=true`，条数照实），任何情况不超过 `preheatFanout`，总条数不超过 P×preheatFanout；无可行节点的 Pod 只写一条 `nodeName` 为空的汇总记录，`state` 取该 Pod 的汇总态。每条的位图、就绪数、速率与 `lastReportTime` 取该预热节点最近一次上报；`actualNode` 同一 Pod 各条同值。比例一律现算：速率是 `readyInWindow / K_i`，`requiredReady` 按整数门控公式按 Pod 算出后写入各条。体积：P≤64、N≤256、preheatFanout 典型 2 时序列化小于 1 MiB（上限由 `warmup_status_size_test.go` 断言）。

### Pod 分数注解

分数写在训练 Pod 自己的注解上，键由 `CONTROLLER_SCORE_ANNOTATION` 指定（默认 `traincache.io/node-scores`），同一 WarmupTask 的每个 Pod 都带这个键。写分数与摘 scheduling gate 是同一次 Pod patch：Scheduler 看到 Pod 可调度时，该 Pod 对象上一定已经有自己的分数，不存在 Node 与 Pod 两个对象的 watch 到达顺序竞争。

值为单行 JSON，UTF-8，无换行：

```json
{"v":1,"task":"default/train-1","g":12,"t":"2026-10-20T08:00:00Z","s":{"node-a":87,"node-b":73}}
```

| 字段 | 含义 |
|---|---|
| `v` | 格式版本，当前 1 |
| `task` | `<namespace>/<name>`，必须等于 Pod 注解 `traincache.io/warmup-task` |
| `g` | 写入时的 WarmupTask `generation` |
| `t` | RFC3339 UTC 写入时刻；超过 `CONTROLLER_SCORE_TTL`（Controller）或 `SCHEDULER_SCORE_TTL`（Scheduler）视为过期 |
| `s` | 键为预热节点名，值为该 Pod 在该节点的 0~100 整数分数；只含本 Pod 实际认领的节点，缺项按 0 |

每次放行整体替换 `s`，不合并旧条目。Pod 自己的 gate 摘除后不再改写该 Pod 的注解，快照就此冻结；Scheduler 只读本 Pod 的注解，Node 上不写分数。

## 关键流程

### DataSet 校验与块布局

DataSet 是静态数据契约：校验数据、固化块空间、探测入口、确认节点可达。reconcile 依次做七步，先读、再校验、再探测、最后写 status，每次从 spec 全量重算，不依赖上一次结果，重启与事件重放都不产生重复操作。前置条件是 `chunkSize > 0`、`shards` 非空、`count > 0`、`0 < lastChunkSize <= chunkSize`、`0 <= snapshotID`、Secret 存在且含 `accessKey`/`secretKey`。

1. 读取 DataSet；`deletionTimestamp` 非空则直接返回。
2. 校验 spec 字段；失败写 `Condition InvalidSpec=False` 并记事件说明原因，返回 nil。
3. 解析 Secret，构造 `objectstore.Store`；失败写 `Condition StorageUnreachable=False`，返回 error 由 controller-runtime 退避重试。
4. `snapshotID` 为空时读 `CURRENT` 解析具体快照；读 manifest 并校验 `snapshot_id` 一致、`shards` 非空；找不到写 `Condition SnapshotNotFound=False`。
5. 按 spec `shards` 顺序累计 `startChunk`，生成 `blockLayout` 与 `totalChunks`（`totalChunks` 等于各分片 `count` 之和）——全局块号在这里只固化一次，后续预热与门控都按全局块号。
6. 解析可达节点，`snapshotID` 置为解析后的具体值，`accessibleNodes` 升序——默认选 `traincache.io/s3-access=true` 的 Node，`accessibleNodeSelector` 非空时在该标签集合内收窄。有匹配节点时 `Condition Ready=True`；无匹配节点时置 `Condition NoAccessibleNodes=False` 并发事件，返回退避重试（节点标签可能随后补齐），WarmupTask 不得下发。
7. 写 status（带 `observedGeneration`）；spec 变化时通知所有引用它的 WarmupTask（DataSet 不记录被谁引用）。

可重试错误（存储不可达、API 冲突）返回 error 由 controller-runtime 退避；不可重试错误写 `Condition InvalidSpec/StorageUnreachable/SnapshotNotFound=False` 并返回 nil。

### 候选节点筛选与预热下发

WarmupTask reconcile 前六步：

1. 读取 WarmupTask 与 DataSet；DataSet 非 `Ready` 时写 `Condition DataSetNotReady` 并返回。
2. 校验 `podDetails[].index` 覆盖 `0..podCount-1` 且不重复。解析消费清单：任一 Pod 的 `initialConsumeFiles` 为空、含未知分片名，或全组内同一分片出现多次、全部 Pod 合起来未覆盖全部分片时，忽略全部用户值，按默认切分 `T=totalChunks`、Pod i 取 `[floor(i*T/P), floor((i+1)*T/P))` 升序，置 `consumeOrderSource=Default` 并发 `ConsumeOrderDefaulted` 事件；否则为 `Spec`，每个 Pod 的块序是所列分片按列出顺序展开的全局块号。本 Pod 的分片必须一次列全，只列前几个按非法处理。`totalChunks < podCount` 时不存在合法的默认切分，置 `Condition InvalidSpec=False` 并拒绝，不回退。K 的计算、patch 回 spec、显式 K 校验与超预算告警按启动窗口口径执行。
3. 列出 `TargetRef` 匹配的 Pod 与 Node；匹配到 0 个 Pod 时按"Pod 还没建出来"处理，只记 Debug 日志、不置 `Condition PodSetMismatch`；匹配数大于 0 且不等于 `podCount` 时置该条件并发 Warning 事件。两种情形都继续使用已有 Pod，不创建/重建/扩缩容。
4. 执行候选筛选；DataSet 无可达节点时写 `NoAccessibleNodes` 并停止下发；结果为空写 `NoCandidates`，返回退避（节点状态可能变化）。
5. 对每个 `(pod,node)` 调 `Submit`（`chunks` 为该 Pod 消费顺序前 `min(max(K_i, Cutoff), W_i)` 块）。发送失败记 `ErrAgentUnavailable`，节点标记 `Stopped` 下一轮重试；永久拒绝写 `Condition PreheatRejected=False`（reason=`AgentRejected`）发 Warning 事件，该节点不再重试。
6. 进入 `Preheating`，写 `candidateNodes`、`startedAt`（仅首次）。

### 进度拉取与就绪表

`Poll` 每隔 `CONTROLLER_POLL_INTERVAL` 遍历所有处于预热或门控阶段的 task，对实际认领的每个 `(pod,node)` 调进度查询并把 Agent 原始位图翻译成 Controller 侧状态表：按该配对请求的 `chunks` 顺序解码位图，`readyInWindow` 取前 `K_i` 位的置位数，`requiredReady` 按整数门控公式算出，`globalDecayScore` 按评分口径算出。随后更新就绪表与该 Pod 各预热节点的就绪条目，`lastReportTime` 用 Agent 上报时刻、缺失时用本地时钟。低于当前 generation 的响应丢弃并记 Debug；同 generation 下 `seq` 小于已记录值也丢弃。连续 3 次 Agent 不可达将对应预热节点条目置 `Failed`，这只影响门控条件②的斜率计算，不阻塞超时降级。

### 分配与下发差异

每轮 Poll 后用就绪表、已停止节点集合、`preheatFanoutMin` 与 `preheatFanout` 重算分配，门控决策提交（`Released`/`Degraded`）后本代停止重算。分配变化时按差异调用：新增配对 `Submit`/`Update`，移除配对 `Cancel`，未变化配对不重复调用。

差异的"已提交"一侧只认本轮进度查询的回报——Agent 报 `generation` 与 `ready_bitmap` 长度即认定它持有该任务，报 `NotFound` 即认定此处未提交，Agent 无回答的配对本轮不动作；`status` 不参与这个判定。"未变化"的判据是 `generation` 相同且 `window_blocks` 等于本轮窗口块数。宽预热以"没有任何 Agent 报持有"为条件，因此只在首次真正发出去时执行一次。被清理节点记 `prune_reason`（`out_of_target`、`low_signal`、`target_shrink`）。

`Submit`/`Update` 成功后，控制器丢弃该配对在本进程的 `seq` 高水位：Agent 把已取消任务的同名同代际重投当新任务、`seq` 从 1 重启，旧水位留着会把新任务的全部上报判成 `stale` 丢弃，门控从此看不见这个节点的进度。结果只写 status，不写 Node。

放行快照是终态：`status.podNodeReadiness` 的配对与各 Pod 的分数注解在门控决策落库后不再变动，重复的 reconcile（包括从还没看到该次 status patch 的缓存副本起步的那一次）直接短路，不重算分配、不发 `Submit`/`Cancel`、不重写注解；落点兜底照常运行，只回填 `actualNode` 并在实际落点上做 P0 预热。

### 门控与放行

1. 组装门控状态：`AssignedNodes` 取该 Pod 实际预热节点集合（以实际认领为准），`ReadyByNode` 取各预热节点窗口就绪数，速率取集合内 `ReadyByNode[node]/K_i` 最大值；首个 Pod 达标的时刻取自 `Conditions` 中类型 `FirstReady` 的 `LastTransitionTime`——首次出现任一 Pod 在任一预热节点上达标时写入，之后不再更新。
2. 门控判定返回 `Hold` 时不写 Node、不摘 Gate，`RequeueAfter = PollInterval`。
3. 门控仍为 `Hold` 时先做前置放行判断。数据集总字节按 `DataSet.status.blockLayout` 算：每个分片前 `count-1` 块按 `spec.chunkSize` 计，末块按 `lastChunkSize` 计。
   a. 数据集总字节大于 0 且小于 `cacheCapacityBytes / 20`（`cacheCapacityBytes` 未配置时为 0，该条不触发）时放行，原因 `dataset_too_small`；
   b. Agent 上报吞吐大于 `0.8 × TRAINCACHE_GATE_NETWORK_BANDWIDTH`（带宽上限未配置时该条不触发）且数据集总字节小于 5GiB 时放行，原因 `bandwidth_fast_enough`；
   c. 上面两条都没命中时，任一预热节点对某 Pod 上报过非零 ready 块数时放行，原因 `min_progress_any_node`。
   两条跳过条件同时命中时记 `dataset_too_small`。吞吐取候选节点 Agent `/metrics`（9411 端口）里的 `traincache_fetch_bytes_total{result="success"}`，按两次采样的增量除以时间差算，各节点取最大值；带宽上限未配置时不发抓取请求。
4. `Released`/`Degraded` 时，一次 reconcile 内完成两件事：
   a. 逐个 Pod 计算该 Pod 在实际认领各预热节点上的分数（用该 Pod 的 `K_i`），把节点到分数的表与"移除 `traincache.io/warmup` gate"放进同一次 Pod patch。gate 已移除的 Pod 跳过，不重写注解。放行之后继续回填的预热不算入分数——每个 Pod 的分数在它自己的 gate 移除时冻结，generation 不变则不再改写。
   b. 写 `GateDecision{State,Reason,DecidedAt,PodRates}` 与 `Phase=Released/Degraded`。
5. 任一 Pod patch 失败：该 Pod 保留 gate、注解不变（两者同一次写入），本轮不写 `GateDecision`，下一轮重试；已放行的 Pod 不回滚、不重写注解（幂等）。

### 初始化与配置加载

`cmd/controller-manager` 依次做：`config.Load()`、`logging.New()`、`metrics.New()`、`ctrl.NewManager`、注册两个 Reconciler 与 Poll ticker、leader election（可选）、`signal.NotifyContext(SIGINT,SIGTERM)`、`mgr.Start`。`cmd/webhook` 是独立进程，加载同一 `config`，只启动 webhook server。`cmd/scheduler` 走 kube-scheduler 的 `app.WithPlugin` 注册。

### 对象存储校验

对象存储装配按 `secretRef + resourceVersion` 缓存 `objectstore.Store`。校验只读 `<dataset>/CURRENT` 与 `dataset/<name>/snapshots/<id>/manifest.json`，反序列化目标为 `core/index.Manifest`。S3 客户端、重试、校验逻辑全部在 core，Controller 不重复实现。

## DataLoader 接入

接入的标准是让真实 tar 分片、真实块语义、真实消费顺序贯穿到测量里，而不是搭一个假训练循环：DataLoader 按 `DataSet.status.blockLayout` 固化的全局块号与 `WarmupTask` 解析出的初始消费顺序组织 sampler，每个 worker 的读取序列与预热序列对齐。epoch/shuffle/curriculum 阶段切换经钩子向 Agent 上报事件触发运行时重预取，永不进入调度路径。缓存未命中走回源并在打点中区分：打点记录每 step 的 `step_time` 与 `wait_time`（再拆出本地命中等待与回源等待），按窗口、切换点、全程聚合。负载均衡必须同步对齐——多 worker 的块分配均衡、worker 序列与所在节点预热对齐、切换后重新均衡，否则 `wait_time` 反映的是分配不均和跨节点回源而非预热收益，"启动收益 vs 全程收益"的归因失效。块级打点口径由 `docs/6.1-design.md`《钩子 socket 协议》约定。

## 降级与故障

Webhook 未注入时该 Pod 没有 gate，直接调度，不阻塞其他 Pod（`Condition GateInjectionDegraded`）。

节点丢失（Node NotReady）在下轮 reconcile 退出候选集、不再参与分配；已放行 Pod 不回滚、不重新门控，Pod 重调度到别的节点时按落点兜底处理。剔除延迟由集群决定：Node 何时被标记 NotReady 由集群的节点监视器决定，本项目不设 `node-monitor-grace-period`；Controller 在下一轮 reconcile 用 informer 缓存里的新状态重算候选集，未终结的任务按 `CONTROLLER_POLL_INTERVAL`（默认 2s）轮询。候选节点上的 Agent 停机时该节点记为 Stopped，分配只在剩余可行节点上进行。

全部候选被 Agent 永久拒绝时门控不推进，仍由 `TMax` 降级兜底；可达节点为空时既有任务可 `Cancel`，门控同样受 `TMax` 约束。`T < P`（块数少于 Pod 数）属规格错误：置 `Condition InvalidSpec=False` 并拒绝，不进入消费清单回退。

API server 短暂不可用时本轮 reconcile 返回错误且不落盘新 Condition，保留原 phase 与条件；controller-runtime 退避重新排队，恢复后下一轮重算候选集与门控决策。所有降级最终由 `TMax` 超时放行兜底，任务不会永远卡在 Hold。

## 部署与配置

全部环境变量集中在 `internal/config`，校验失败启动即错。

- `CONTROLLER_METRICS_ADDR`，默认 `:9412`，Prometheus 监听地址。
- `CONTROLLER_HEALTH_ADDR`，默认 `:8081`，manager、webhook、scheduler 的 `healthz` 与 `readyz` 监听地址。
- `CONTROLLER_WEBHOOK_ADDR`，默认 `:9443`，webhook server 监听地址，Service 443 转发到这里。
- `CONTROLLER_NAMESPACE`，默认空串，只校验格式并记进启动日志，不改变监听与准入范围。
- `CONTROLLER_AGENT_PORT`，默认 `9410`，Agent gRPC 端口。
- `CONTROLLER_AGENT_TIMEOUT`，默认 `5s`，单次 RPC 超时。
- `CONTROLLER_POLL_INTERVAL`，默认 `2s`，进度拉取周期。
- `CONTROLLER_SCORE_TTL`，默认 `5m`，Pod 分数注解过期时间。
- `SCHEDULER_SCORE_TTL`，默认 `5m`，插件侧过期判断，与 controller 一致。
- `CONTROLLER_SCORE_ANNOTATION`，默认 `traincache.io/node-scores`，Pod 分数注解键，Controller 与 Scheduler 必须同值。
- `CONTROLLER_GATE_NAME`，默认 `traincache.io/warmup`，SchedulingGate 名。
- `CONTROLLER_LEADER_ELECTION`，默认 `false`，是否启用 Lease 选主；多副本同时下发会造成重复 RPC，生产环境建议开启。
- `CONTROLLER_MAX_CHUNKS`，默认 `10000000`，单 DataSet 块数上限。
- `CONTROLLER_LOG_LEVEL`，默认 `info`，取值 `debug`/`info`/`warn`/`error`。
- `CONTROLLER_DEBUG_ADDR`，默认 `127.0.0.1:6060`，`/debug/loglevel` 监听地址，只允许绑定回环地址，留空表示关闭。
- `CHECKPOINT_IMAGE`，默认空串，发布清单里的 checkpointd 镜像取值。
- `TRAINCACHE_CACHE_CAPACITY_BYTES`，默认 `0`，缓存字节上限；`0` 时跳过 `K_cache`。
- `TRAINCACHE_STARTUP_WINDOW_BYTES`，默认 `536870912`，启动窗口字节数，必须大于 0。
- `TRAINCACHE_MAX_FILL_FRACTION`，默认 `0.125`，自动 K 的缓存预算比例，取值必须在 `(0,0.25]`。
- `TRAINCACHE_GATE_NETWORK_BANDWIDTH`，默认 `0`，门控的网络带宽上限（bytes/sec），门控把 Agent 上报吞吐与该值的 0.8 倍比较；0 表示不启用带宽判断，负值使 controller 拒绝启动。

`cacheCapacityBytes`、`startupWindowBytes`、`maxFillFraction`、`gateNetworkBandwidthBytes` 四个 ConfigMap key 由 `traincache-config` 注入为上述 `TRAINCACHE_*` 环境变量，Controller 启动时校验。

## 日志

核心代码的每个关键位置必须记录结构化日志，并随对应功能一起验收；没有日志断言测试的功能不判通过。日志不得改变业务逻辑、接口、数据格式与运行行为。

日志库是标准库 `log/slog`，`JSONHandler(os.Stderr)`，与 agent 一致；`cmd/*/main.go` 各初始化一次，不引入第三方。`internal/logging` 只有三个函数：`New(level) *slog.Logger`、`Into(ctx, l) context.Context`、`From(ctx) *slog.Logger`（缺失时返回 `slog.Default()`）。

每个 reconcile 与 HTTP 请求生成 `request_id`（`<uid>/<generation>/<unixnano>`）放入 context 与所有日志；无分布式 traceId，跨进程关联用 `task_id + node + generation`。

日志字段名固定小写 snake_case，禁止混用；fanout 决策相关字段（`fanout_min`、`fanout_max`、`fanout_target`、`fanout_actual`、`low_signal`、`forced_by_min`、`min_unmet`、`fallback_out_of_target`、`prune_reason`）在每次分配日志里成组出现。

级别划分：Info 记状态迁移、放行、筛选结果、任务完成；Warn 记降级、重试、跳过、未收敛；Error 记 reconcile 返回 error、RPC 永久失败；Debug 记逐块与逐节点的评分明细，默认关闭。

脱敏：禁止记录 Secret 内容、accessKey/secretKey、完整凭据 URL；`path`/`chunk`/`fp` 等高基数维度只进 Debug，Info 聚合到 dataset/task 维度；日志调用不得在锁内做格式化之外的 I/O，`From(ctx)` 缺失时退化为全局 logger，不 panic。

必记日志点：

| 位置 | 级别 | 必带字段 |
|---|---|---|
| 每个 Reconcile 入口与出口 | Info | `component,dataset_or_warmup_task,request_id,generation,duration_ms` |
| spec 校验失败 | Warn | 上述 + `reason,err` |
| 快照与存储校验失败 | Warn/Error | `dataset,snapshot,err` |
| 候选筛选结果 | Info | `warmup_task,pod,node,reason`（汇总计数） |
| gRPC Submit/Update/Cancel | Info | `warmup_task,task_id,pod,node,generation` |
| gRPC 失败 | Warn | 上述 + `err` |
| 进度轮询结果变化 | Debug | `task_id,node,generation,seq,ready` |
| 分配变化或未收敛 | Info/Warn | `warmup_task,assign,rounds,reason` |
| 消费清单解析与默认切分 | Info | `warmup_task,consume_order_source,reason`；默认切分同时发 `ConsumeOrderDefaulted` 事件 |
| 门控判定 | Info | `warmup_task,state,reason,rates,required` |
| Gate 注入与摘除 | Info | `warmup_task,pod,pod_index,node,request_id` |
| Pod 分数注解写入 | Info | `warmup_task,pod,annotation_key,generation,entries` |

## 指标清单

controller-manager 使用独立 Registry，经 `metricsserver.Options.ExtraHandlers` 暴露在 `/metrics/traincache`，内置 `/metrics` 由 controller-runtime 自带；scheduler 是独立进程，自建 Registry 并在 `CONTROLLER_METRICS_ADDR` 暴露同一路径。标签值必须来自固定枚举，禁止 `err.Error()`、Pod/Node/task 名、UID 等无界值。标签集合共 11 个 family：

| Family | 类型 | 标签 |
|---|---|---|
| `traincache_controller_reconcile_total` | Counter | `controller` ∈ `dataset\|warmup\|warmup-degraded`；`result` ∈ `success\|error\|requeue` |
| `traincache_controller_reconcile_duration_seconds` | Histogram | `controller` |
| `traincache_controller_candidate_nodes` | Histogram | `dataset` 取 `<namespace>/<name>` |
| `traincache_controller_preheat_rpc_total` | Counter | `op` ∈ `submit\|update\|cancel`；`result` ∈ `ok\|permanent\|unavailable` |
| `traincache_controller_gate_tasks` | Gauge | `state` ∈ `hold\|released\|degraded` |
| `traincache_controller_gate_hold_duration_seconds` | Histogram | 无 |
| `traincache_controller_agent_poll_total` | Counter | `result` ∈ `ok\|unavailable\|stale\|error` |
| `traincache_controller_pods_per_node` | Histogram | 无 |
| `traincache_controller_gwaa_unassigned_pods` | Gauge | `dataset` |
| `traincache_controller_gwaa_fallback_total` | Counter | 无 |
| `traincache_scheduler_score_total` | Counter | `result` ∈ `ok\|no_task_ref\|invalid_task_ref\|no_annotation\|invalid_value\|task_mismatch\|stale_generation\|expired\|no_node_entry` |

口径约定：`reconcile_total` 的 result 按 err 非空记 error、RequeueAfter 大于 0 记 requeue、否则记 success，duration 用 defer 覆盖所有返回路径；`preheat_rpc_total` 的 permanent 对应 `ErrPermanent`，其余失败记 unavailable；`gate_tasks` 首次门控评估起增减，任务删除或进入终态时减一，重复状态不重复计数；`gate_hold_duration_seconds` 仅在离开 Hold 时观测一次；`agent_poll_total` 的 generation 与 seq 回退被丢弃记 stale、响应解析失败记 error；`pods_per_node` 每次分配计算后按预热配对观测每节点 Pod 数，fanout 接线后该值可大于 1；`gwaa_unassigned_pods` 每次分配后设为未分配 Pod 数；`gwaa_fallback_total` 在分配不收敛、回退到首个贪心结果时加一；`scheduler_score_total` 的 result 是 scheduler 进程取分的固定分支枚举。
