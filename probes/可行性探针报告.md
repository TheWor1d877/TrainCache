## 1. 实验目的与判据

阶段0 第一部分要做的事情,是用一套最小装置把"实验方法论到底成不成立"验证一遍。具体拆成五个探针:

- 探针A:装置能不能造出可信的冷热差异?
- 探针B:stall 指标能不能被稳定地打出来?
- 探针C:stall 是训练全程持续存在的状态,还是只出现在启动预热时的一次性瞬态?
- D 轨勘测:缓存只能覆盖一半工作集(欠配)时,stall 会不会在每个 epoch 里重复出现?
- 消费顺序探针:训练的消费顺序能不能由一组可复现的输入算出来?

后三个探针是 v4 方案(训练全程数据流加速)能不能立住的前提。假如 stall 只是启动瞬态、欠配下 stall 不重复、消费顺序又算不出来,那么"全程加速"这条主线就要塌掉。我们宁可先花两三天把这些问清楚,也不愿意开工三个月之后才发现装置本身不可信。任何一个探针亮红灯,我们都先停下来修装置,修好了再往下走。

**绿灯标准(文档原文)**:

- 探针A:① 冷/热中位延迟差 ≥5×(或中位吞吐差一个数量级);② 两组 bootstrap 95% CI 不重叠;③ 组内变异系数 CV ≤ 15%。冷/热各 ≥7 次取中位数。
- 探针B:① 冷态 stall 占比稳定 >40%;② 热态 stall 占比 <15%;③ 增加 workers 冷态 stall 单调下降。
- 探针C:cold_w4 的窗口A(epoch0 中段)、B(epoch1 切换后)达标,且 cold_w0 的窗口A、B(中位口径)达标,且哨兵 hot_w4 四窗口全部低于阈值。阈值统一取 0.30 × 冷态基准(具体口径见 §3.3)。
- D 轨:前置门(欠配真实生效)通过,且① 相邻 epoch 窗口曲线 r≥0.5 的对数 ≥6/8,② epoch2-9 中位 stall 的 CV ≤30%;报告项③不参与红绿判定。
- 消费顺序探针:7 个验证点全部通过(分片序、分片置换、样本级洗牌、seed 通道、两个 Sampler、端到端重建)。

## 2. 装置与执行:每一步在干什么

### 2.1 总览

```
 ┌────────────────────── host(裸机,32核/30G/双NVMe) ──────────────────────┐
┌────────────┐  http ┌────────┐          ┌────────────────────────────────────────────┐
│ fetch.py   │◄─────►│ docker0│◄────────►│ 源站容器(nginx),tar 只读挂载               │
│ (模拟Agent)│12.5MB/s│ bridge │veth pair│ 容器内 eth0 egress 挂 tc:                  │
│ 有界并发=4 │       └────────┘          │   tbf 100mbit + netem 20ms(源站出站方向)   │
└─────┬──────┘                           └───────────────────┬────────────────────────┘
      │ 冷读:下载落盘                                        │ -v 只读
      ▼                                                      ▼
┌──────────────┐   热读:顺序直读(零网络,verify_isolated.sh 验证)  ┌──────────────┐
│ Agent缓存目录│◄───────────────────────────────────────────────  │ data/tars/   │
│ .cache/agent │  探针B 热态:webdataset 流式读本地 tar            │ 16×128MB tar │
└──────────────┘                                                  └──────┬───────┘
                                                                         │ 探针B 冷态:
```

同一批 tar 分片两处都用:探针A 读字节吞吐,探针B 读解码加打点。这样我们不用维护两套数据,省得再去解释两者之间的差异。

### 2.2 步骤1:合成 2GB 训练数据(`setup/01_synth_data.py`)

**这一步做什么**:生成 16 个 webdataset 风格的 tar 分片,每个分片装 800 张 512×512 的 JPEG,单分片约 126MB,合计 1.97GiB。文档里写过,2026 年训练数据的主流形态是"百 MB 分片 + 确定性 shuffle 流式读取",我们把装置数据也造成这个样子。

**为什么不干脆用纯色块**:纯色块会被 JPEG 压缩得过狠,体积和解码成本都会失真。所以每张图 = 双色渐变底 + 随机圆形/矩形 + 高斯噪声,噪声强度 σ 会自动校准到目标体积 ~160KB/张(实测校准后单张 158KB)。全部随机源都从固定种子(20261006)派生,重跑一遍能得到逐字节一致的数据,结果可以完全复现。

**执行时踩到的问题**:首跑时 numpy 的 `RandomState` 种子超过了 2³² 上限,直接报错;改成取模之后重跑成功,整批合成大约花了 6 分钟。

### 2.3 步骤2:源站(`setup/02_source_up.sh`)

**这一步做什么**:起一个"远程数据源"容器,用 HTTP 字节流对外提供 tar 分片,公开读、不带签名逻辑。按原设计这里本该用容器化的 MinIO(文档层3 规定 kind 集群里用 MinIO 模拟 S3/OSS)。

**降级经过**:MinIO 镜像在所有能访问到的镜像源上都没拉下来——docker hub 直连超时(网络受限,已知)、玄源加速站(回源失败)、DaoCloud(denied)、1ms.run 与 hub.rat.dev(manifest not found)、1panel(denied)、quay.io(unauthorized)、阿里云(仓库不存在)。最后降级成本机已有的 `nginx:latest` 镜像,让它做静态文件服务,tar 目录只读挂到 URL 前缀目录下。

**为什么读路径语义等价**:在这套探针里,MinIO 只承担"远程 HTTP 字节流源"这一个角色(公开读、http 直取,不用 S3 API)。nginx 静态服务在这条读路径上和 MinIO 的公开读行为一致(都是 HTTP GET 字节流);URL 结构 `/train-data/shard-*.tar` 也和 MinIO bucket 前缀一致,下游脚本可以完全复用。后面现勘阶段再按文档部署真 MinIO(镜像到那时另想办法)。

### 2.4 步骤3:tc 限速(`probe_a/tc_setup.sh`)—— 本次执行的核心踩坑

**这一步做什么**:在下载路径上造出"远端网络"的真实代价,把 tbf 令牌桶整形到 100mbit(12.5MB/s),再加 netem 20ms 时延,与文档装置一致(burst≈1s 令牌量)。

**三次踩坑的完整实证过程**(这是本次执行最有价值的发现,已经写进 `design.md` 和长期备忘):

1. **挂 docker0 主设备 → 无效**。首轮冷读 3.5 秒就跑完 2GB(565MB/s),而 tc 计数只涨了 12MB。排查后确认:Linux bridge 的二层转发(br_dev_xmit → veth)不经过桥主设备(docker0)的 egress qdisc。
2. **挂 veth host 侧 root(egress)→ 无效**。tcpdump 证实数据包确实经过了 veth,但 tc 计数一动不动。原因是下载的数据方向是 容器→host(nginx 发响应),在 host 侧 veth 上是 **ingress** 方向,egress qdisc 管不到。排查时还有个额外收获:veth 的匹配不能用 ethtool peer_ifindex(不同 netns 里 ifindex 都是 2,会误匹配到别的容器),要用 `ip -o link show master docker0` 的从属关系来判断。
3. **挂容器 netns 内 eth0 的 egress(源站出站方向)→ 生效**。验证:下载 132MB 实测 11.04s(≈12MB/s),tc 计数涨了 138MB,overlimits 计数也在涨(整形器确实在工作)。

**为什么值得记下来**:这个坑花掉了执行中相当一部分时间,但后面现勘阶段给训练 Pod/Agent 做网络波动实验时还会再碰到它,现在把它实锤并且写成可复用脚本,值回票价。

### 2.5 步骤4/5:冷读与热读(`run_cold.sh` / `run_hot.sh` / `fetch.py`)

**冷读定义**(每轮):`rm -rf` Agent 缓存目录 → `sync` → `echo 3 > /proc/sys/vm/drop_caches`(清全 host 的 page cache,连源站容器进程的也清掉,杜绝"假冷读")→ 走 tc 从源站下载 16 个 tar 到缓存目录。`fetch.py` 模拟层2 Agent 三条抓取指令里的"有界并发"(线程池并发 4、按分片下载、落本地缓存目录)。共 7 轮。

**热读定义**(每轮):数据已经在缓存目录里,顺序直读文件(模拟训练 Pod 的 hostPath 读路径),不 drop_caches(真实训练里的"热"包含 OS page cache)。每轮并行采样 9000 端口的 established 连接数,用来做零网络验证。共 7 轮。

**执行时踩到的问题**:首轮冷读因为 tc 挂点错了,跑出 565MB/s 的作废数据,在 §2.4 修复后清空重跑;另外有一次 results 目录被 root 创建,普通用户写不进去,chown 之后解决,并在 `run.sh` 里加了提示。

### 2.6 步骤6:探针A 判定(`probe_a/judge.py`)

**这一步做什么**:读 7+7 轮的原始 JSON,算出中位耗时/吞吐、百分位 bootstrap 95% CI(2000 次重采样)、组内 CV,再按三条绿灯判据输出。

### 2.7 步骤7/8:探针B 装置与判定(`probe_b/train.py` / `run.sh` / `judge.py`)

**打点口径(主进程视角)**:每步 `t0`=上一步计算结束 → `next(batch)` 到手 `t1` → compute 完成 `t2`。`wait=t1-t0`(DataLoader 等待数据的时间),`step=t2-t0`,`stall=wait/step`。解码在 worker 进程里并行(workers>0 时),主进程的 wait 只含排队与管线补货——这就是文档要求"真 JPEG(真实解码成本)"的意义。

**装置**:webdataset 流式读 tar;冷态从 `http://127.0.0.1:9000/...`(经 tc),热态读本地 tar 目录;workers 0/4/8 三档 × 冷热 = 六组,每组 60 步(warmup 10 步不计);compute = 单线程 1024² matmul × 8(校准后,见下);batch=32(≈5MB/批)。

**compute 量级的两次校准(如实记录)**:

1. 首跑发现 1024² matmul 被多核 BLAS 跑成了 ~3ms,stall 对 wait 的微小变化特别敏感(热态 wait 0.6ms 和 13ms 的差别就把 stall 从 17% 推到 81%),装置的判别力很差。限成单线程后 ~25ms,热态仍然 ~35%,压不到 15%。
2. 改成单线程 ×8 次 ≈200ms/步。这是在"模拟真实 step 的 compute 量级"和"判据灵敏度"之间选的一个落点——相对真实模型它仍是"极小矩阵乘"(文档允许),同时又让 stall 有判别力。

**判定口径与实测机制的对应**(详述见 §4.2):条件1 判 w0 无管线档(冷态),条件2 判 w4/w8 至少一档(热态),条件3 按 mean 口径(时间加权)判单调。这些口径不是预先定的,全部来自本次实测的 wait 结构数据。

### 2.8 探针C 与 D 轨:多 epoch 全程测量装置

探针C 和 D 轨共用同一套装置,代码放在 `probe_c`:`train_multi_epoch.py`(打点核心)、`run_c.sh`(探针C 四组执行)、`judge_c.py`(探针C 判定)、`judge_track_d.py`(D 轨判定)。

**探针C 的装置参数**:

| 项                       | 值                                                                                          |
|--------------------------|---------------------------------------------------------------------------------------------|
| epoch 数 × 每 epoch 步数 | 3 × 400(batch 32,每 epoch 一遍全量 12800 样本)                                              |
| warmup                   | 仅 epoch0 前 10 步(计入步号、标记排除)                                                      |
| seed                     | 基种子 20261013;epoch e 有效种子 = 基种子 + e                                               |
| 分片置换                 | `random.Random(seed+epoch)` 生成 0..15 置换,显式 URL 列表(`shardshuffle=False`,读序=列表序) |
| 样本级洗牌               | `.shuffle(100, seed=seed+epoch)`(有效种子 = 传入值,由 probe_d 验证点3 实测)                 |
| 打点口径                 | wait = t1-t0、step = t2-t0、stall = wait/step;compute = 单线程 1024² matmul × 8             |
| 四组                     | cold_w4 → cold_w0 → cold_w8 → hot_w4                                                        |
| 网络                     | 冷组 tc 恒 100mbit + 20ms;热组读本地 tar                                                    |

**冷态规则**:只在每组开跑前做一次组前冷态(清 Agent 缓存目录 + sync + drop_caches);epoch 之间绝不清缓存、不重启容器、也不 drop_caches——epoch 切换后 stall 会不会回升,恰恰是我们这次要测的东西;组间只 sleep 5 秒。每个 epoch 都要重建 loader(webdataset pipeline 的 worker 内副本没法换 seed),重建耗时单独记进 `loader_build_s`(约 0.2ms,父进程侧)。

**D 轨的装置参数**:复用 `train_multi_epoch.py`(和探针C 行为语义相同,只走 CLI 传参:10 epoch / seed=20261014 / workers=4 / 每 epoch 400 步);tc 恒 100mbit+20ms;同样只在开跑前冷态一次,epoch 之间不清缓存、不重启。

**欠配怎么造的**:我们把 nginx 源站容器用 cgroup 限制到 1GiB,让它只能缓存住一半工作集。命令是 `docker update --memory=1073741824 --memory-swap=1073741824 traincache-source`,之后核对 HostConfig.Memory/MemorySwap(memory-swap=memory 表示禁用 swap,免得换页把欠配掩盖掉)。页缓存由 nginx 容器(读 tar)持有,cgroup 的 file 行就是它的缓存占用。

**内存采样与恢复**:后台每 2 秒读一次源站容器 cgroup v2 的 memory.current 和 memory.stat 的 file 行,写进 `mem_track_d_w4.jsonl`(meta/采样/final 三类行,这次共 903 点)。收尾时脚本请求 `--memory 0 --memory-swap 0`,但本机 docker 29 把 0 当成"不变更"(零值语义),脚本检测到后回退成 128GiB(≈4× 宿主内存)等效恢复并记档(final 行 `limit_restored`)。容器不重建就没法真正归零,而这套装置禁止重建。

**装置备注(如实记录)**:

- 本机 sudo 没有 NOPASSWD、也没有 tty:脚本先试 `sudo -n`,不可用就回退到带 NET_ADMIN 的 docker 容器(在源站 netns 内执行同一条 tc 命令)和特权 docker 容器(drop_caches、清 root 属主的缓存目录),`via=docker` 与 qdisc 全文都留档在每组 environment 里;
- 解释器固定 `/usr/bin/python3.12` 的历史口径已于 2026-10-25 失效:本机现在没有 `/usr/bin/python3.12`,系统 python3 是 3.14,`~/.local/lib/python3.12/site-packages` 也不存在了。探针产物按当时的解释器记录,不改写;要重跑 D 轨需先重建解释器与 numpy/torch/webdataset 依赖,现状对账见 `docs/4 bench装置说明.md` §7 第 17/19 条。下文保留原始记录:
- 解释器固定 `/usr/bin/python3.12`(webdataset 1.0.2 / torch 2.14.1+cpu 装在用户级 site-packages;系统原有的 PIL 是 python3.14 构建的,对 3.12 不可用,我们补装了 pillow 12.3.0 cp312 到 `~/.local/lib/python3.12/site-packages`);
- 结果写进 `results/probe_c/c_cold_w0|c_cold_w4|c_cold_w8|c_hot_w4.json`(per_step/per_epoch/environment)、`env_<组名>.json`、`verdict.json`。

### 2.9 消费顺序探针装置

代码在 `probe_d`:`verify_wds.py`(验证点 1-4,webdataset 1.0.2)、`verify_torch.py`(验证点 5-6,torch 2.14.1+cpu)、`reconstruct.py`(验证点 7,不经框架、只凭 tar 文件名 + 源码语义独立复现)、`judge.py`(按序跑三个脚本并汇总)。全部单进程跑(num_workers=0),数据用同一批合成 16 分片,总耗时 6.63s;输出 `wds_results.json`/`torch_results.json`/`reconstruct_results.json`/`verdict.json`。

## 4. 结果分析

### 4.1 探针A:冷热差是稳定、可复现、且悬殊的

- **817× 的差距远超 5× 判据**。冷读被 tbf 整形钉在 11.4MB/s(100mbit 理论值 12.5MB/s,扣掉 20ms 时延与 TCP 开销之后的实际值);热读是 NVMe page cache 直读(~9.3GB/s)。
- **冷读 7 轮极差只有 46ms(CV≈0)**。原因是 tbf 令牌桶整形本身是确定性的:每轮数据量一样(2GB)、限速器状态在每轮之间被 drop_caches 和固定起始条件重置,波动只来自 TCP 慢启动的微小差异。热读 CV 0.4% 同样稳。两组 CI 自然不重叠。
- **红灯排查清单逐条验证过**:tc 计数在涨(overlimits 24959)、热读零网络(连接峰值 0)、盘不是瓶颈(9.3GB/s 远高于限速)、也没有假冷读(每轮 drop_caches 全清)。

**结论:装置能造出可信的冷热差异,而且重复测量高度稳定。**

### 4.2 探针B:stall 指标打得出,而且数据揭示了三个机制

**机制1:无管线档(w0)直接暴露数据源速度。** 冷 w0 每步 wait 318ms(网络下载 5MB/批 + 主进程内解码),stall 71.7%,数据加载确实是瓶颈;热 w0 wait 177ms(只剩本地读+解码),stall 58.1% 仍然偏高,因为解码发生在主进程(w0 没有并行管线),这是装置结构使然。真实训练一定会开 workers,所以条件1/2 分别按无管线/有管线档来判。

**机制2:管线化之后,冷热差异转移到 wait 尾部。** w4/w8 的中位 wait 都落在 ~12-14ms 的 DataLoader 基座上(预取队列缓冲把数据源差异抹平了),但冷态的 p90 wait 是 ~0.9-1.0s(每 4-8 批撞一次 100mbit 共享带宽的网络排队),热态 p90 只有 ~13ms(本地读没有排队)。这就是"块级就绪度"问题在数据加载上的第一个可见签名:共享瓶颈会把等待集中成周期性的长尾。

**机制3:条件③的单调下降,是真实 I/O 饥饿的证据。** mean 口径下 70.4% → 27.3% → 17.6%:w0→w4 的大降来自管线并行化(真实的 I/O 等待被预取吸收掉了),w4→w8 的缓降来自带宽已经饱和(共享 100mbit,再加工人也没用)。这正是文档想看到的证据:我们测到的是真实的 I/O 饥饿,不是打点带来的噪声。如果只是打点噪声,w0→w4 这一段本不该有变化。

### 4.3 装置 artifact 与真实机制的区分(诚实性说明)

- ~12-14ms 的 DataLoader 基座 wait 是本装置的固定开销(多 worker 队列与批次传递造成的),不是数据源属性;它决定热态 stall 的"地板"约为 wait/(wait+compute)。compute 校准到 200ms 后,地板 ≈6%。
- compute 量级是我们自己设的装置参数,不属于测量对象:3ms 时装置失去判别力,200ms 是"极小 compute 替身"与判据灵敏度之间的落点。换机器或换数据时,得照 design.md 的旋钮重新校准。
- 合成 JPEG 的像素内容不真实(解码成本是真实的);这对 stall 打点没有影响。现勘阶段如果要对齐公开基线,可以换数据源,不用动装置骨架。

### 4.4 源站降级对结论的影响

MinIO 换成 nginx,改掉的是"对象存储语义"(S3 API、元数据层),但探针只测 HTTP 字节流读路径上的冷热差与 stall,而这条路径上两者等价。这个差异我们如实记录,后面现勘阶段会用真 MinIO 部署复核(镜像问题到那时另行解决)。

### 4.5 探针C:全程 data stall 是持续状态

- **切换窗口高于中段,就是回升的签名**:cold_w4 的 B、C(30.0%、40.0%)高于 A、D(24.1%、19.5%);cold_w8 方向一致(B=35.0% > D=12.0%,C=20.0% > A=12.8%)。每组只在开跑前冷态一次,epoch 之间没有任何清缓存或重启,epoch1/2 切换后的窗口还是回升了——新一轮读取(新 seed 重排)一上来就重新表现为长尾等待。
- **stall 是持续状态,不只在启动时出现**:如果 stall 只出现在启动预热阶段,cold_w4 的 epoch0 中段(A)本该回落到接近热态的水平;实测 A=24.1%,比 hot 的 0.0% 高出 24.1 个百分点,而且三个 epoch 的中位/均值 stall 几乎不变(见表),cold_w0 全程中位 ≈71%。也就是说,一次性启动预热撑不起全程。
- **口径来自实测**:有管线档的中位 stall 对冷态不敏感(cold_w4 中位 8.0% ≈ hot_w4 8.1%),冷态信号只在 wait≥0.5s 的尾部,所以窗口指标取尾占比;w0 无管线档仍然用中位数。hot_w4 四窗口全 0.0%(哨兵过),说明装置对"信号"和"污染"有判别力。
- **诚实性说明**:tc 恒限速(100mbit+20ms)下每个字节都受限,本探针绿灯的实质是确认"stall 是一种持续状态,不只在启动时出现";它不测量任何缓存机制能带来多大的回升幅度(收益量属于 bench 阶段)。

### 4.6 D 轨:欠配下 stall 逐 epoch 重复

- **重复形态确认**:8 个相邻对里 7 对 r≥0.5(中位 r≈0.61),逐 epoch 中位 stall 几乎不变(CV 0.8%),每 epoch 用时 179-180s(≈2GB@100mbit 满速)——欠配之下,每个 epoch 的读取都要重新经历一半工作集的 miss,stall 形态逐 epoch 重复出现,既不消失也不发散。
- **欠配真实,而且没被人为掩盖**:file 峰值达到上限的 96.8%,稳态占用 0.954-0.967GiB(903 点里有 860 点 ≥0.9GiB),epoch 边界没见回落(因为没清缓存);final 行 memory.events 显示 `max` 计数 52221(触顶分配重试留下的痕迹),但 oom_kill=0,memory-swap=memory 让欠配没法被换页掩盖。
- **报告项③为什么降级**:恒定限速下 median stall 对冷态不敏感(全 epoch 中位 8.1%-8.3%),epoch0 的冷态差异被链路瓶颈掩盖,实测比值 0.99 低于旧阈值 1.2——这和探针B 已经确立的机制一致(w4 冷态签名只在 wait 尾部、中位 stall 对冷态不敏感)。所以我们只报告数值,另外补记"epoch1 首窗切换峰值"当作切换瞬间冷读集中的证据:epoch1 首窗 0.536 是各 epoch 首窗里最高的,首窗 tail 占比(30%-35%)也高于中段(见窗口曲线)。
- **诚实性说明**:本轨是"勘测"性质——判据①②只回答"形态是否重复",不回答"缓存机制能省多少"(收益量在 bench 阶段测);报告项③因为装置瓶颈降级,原始数值全部留档可复查。

### 4.7 消费顺序:输入可构造,几处 seed 语义要当心

- **OrderSource 的输入可以构造**:分片置换(`detshuffle`/`SimpleShardList`/`MultiShardSample` 三选一)和样本级洗牌(`.shuffle(buffer, seed)`)都由 (分片列表, seed, epoch) 决定;`reconstruct.py` 只凭这个三元组加上 tar 文件名(不经框架运行)就复现了 400 步消费序列,和框架采集逐位一致。
- **实测到的 seed 语义(如实记录)**:(a) `.shuffle(100, seed=S)` 不带 epoch 项——同一个 S 的所有轮次序列完全相同,OrderSource 如果要求样本级顺序随 epoch 变化,就得把 epoch 显式混进 seed;(b) `detshuffle` 的有效种子 = S + epoch(首迭 = S+0、第 k 次 run 的 epoch=k-1),任务书里说的"首迭有效种子 = S+1"在这套安装(1.0.2)里没复现;(c) `shardshuffle=True` 缺省 seed 非确定,必须显式注入 `seed=` 或 `WDS_SEED` 才能复现;(d) `RandomSampler` 的显式 generator 有状态,复用同一个对象而不重建会得到不同序列,必须每个 epoch 重建或重播种。
- **局限(明确留待 bench)**:`num_workers>0` 时 worker 的切分模型(`split_by_worker` 交错)和到达时序语义还没覆盖——主进程看到的顺序取决于 prefetch 与 worker 时序,要重建得另加 worker 切分模型;这个差异作为 bench 阶段的输入假设记录下来。
