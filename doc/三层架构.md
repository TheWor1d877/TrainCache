## 层1 k8s control plane
#### 资源预热
定义两种新资源: DataSet与Preheat Job的CRD
一个Controller(reconcile)负责对比资源与期望状态,进行调谐这些CRD资源

manifest(用啦声明资源或者软件包的元数据)引用子集,明确需要预热哪些块
Controller向节点上面的Agent下达命令去预热某些块
Agent将块预热完毕之后通过`Dataset.status`反馈给Controller

#### 门控机制
使用SchedulingGate ⻔控: Job 创建时，Controller 往 Pod 上挂一个 gate（traincache.io/preheat-pending）。只要 gate 在，K8s 调度器就不调度这个 Pod，Pod 一直 Pending。
就绪度(Job子集 readyRatio)：Controller 检查"Job 要的那个子集，在候选节点上备好了多少比例"。
门控用 readyRatio 决定"放不放行"

- 候选节点数量是一个实验变量，不是固定值：必须要让调度器有的选还要考虑多Job共享场景,需要研究这笔网络的浪费究竟是否值得


#### 打分机制
门控机制筛选出一系列候选节点,通过Schedule Score Plugin给候选节点进行打分
直接读取本地缓存中读取各个节点的readyRatio,不走网络

打分逻辑: score(node) = 该节点对这个 Job 子集的 readyRatio（次要因子：空闲磁盘、在途预热负载）
- 打分是在门控放行之后开始的,而门控放行的条件是"至少有一个节点的 readyRatio ≥ 阈值"。触发之后Pod开始调度，调度器跑 Score Plugin 时读当前快照，选最高分。在大多数实际情况下，先到阈值的节点会赢，因为调度器延迟窗口窄、readyRatio 增速递减。但机制上不保证——如果后到的节点在调度器窗口内反超，或者先到的节点有次因子扣分（比如磁盘满、在途负载重），后到的也能赢。
  
   
## 层2 节点层
#### 缓存Agent DeamonSet
Agent以DeamonSet的形式部署，每个节点一个
Agent 的职责：接收 Controller 的预热指令，去源站下载数据，落到本地盘，回报进度。
Agent的抓取指令: 
1. 有界并发(按照字节与信号量来限制在途的字节数)
2. 多个相同指令合并
3. 设置缓存,缓存命中就不触及数据源

#### 训练Pod:真正跑训练任务的Pod
训练 Pod 通过 hostPath 只读挂载 Agent 下载数据的目录（/var/cache/traincache/）。
训练 Pod 直接读本地盘，不经过 Agent。这就是"preheat 模型"——读路径零额外延迟。

#### 可选: 分布式缓存组
如果 node1 需要一块数据，node2 已经有了，node1 从 node2 拉，而不是从源站拉
uiceFS 社区版（CE）没有分布式缓存组，只有单机缓存。
EE 缓存组语义：JuiceFS 企业版（EE）有分布式缓存组
我们可以在 CE 基线上，用 Go 自研组件复现 EE 的缓存组语义
