### 5.3 把 MinIO 数据导入 JuiceFS 文件系统(新步骤,10 分钟)

**在干什么**:JuiceFS 有自己的元数据层(redis),对象存储里的**裸对象不会被
JuiceFS 文件系统自动看到**——裸 S3 对象和 JuiceFS 文件是两个概念。本步骤起一个
临时 Pod,用 mount 镜像里的 `juicefs sync` 把 MinIO 裸对象导入 JuiceFS 文件系统。
**注意两点(都是实测踩坑后的结论)**:
- Fluid 的 PVC 是只读的,挂载后写不进去 → 目标不用挂载点,改用 `jfs://` 协议
  直写(官方推荐,绕过 FUSE;`jfs://` 后面跟环境变量名,值为 redis 元数据 URL);
- MinIO 是路径式寻址,源 URI 必须写 `minio://AK:SK@endpoint/bucket`
  (endpoint 在前,bucket 在路径第一段),写成 s3 的 bucket.endpoint 风格会解析错乱。
- 该镜像的客户端(ce-v1.3.0)已移除 `juicefs import` 命令,必须用 `juicefs sync`。

```bash
kubectl apply -f import-pod.yaml
kubectl logs -f jfs-import
# 预期:sync 进度输出(16 个对象、约 2GB),末尾 "=== 导入完成 ===" +
#       juicefs ls 列出 16 个 shard-*.tar
kubectl get pod jfs-import
# 预期:STATUS=Completed(restartPolicy=Never,完成即退出)
```

**留下**:`kubectl logs jfs-import > evidence/import-pod.log`

**集群侧复核(确认 16 个 tar 真的进了 JuiceFS 文件系统,而不只是 sync 自己说成功)**:

```bash
# 用 Fluid 已建好的只读 PVC 起一个验证 Pod 读(读是允许的,只读 PVC 只禁止写):
kubectl run jfs-verify --image=busybox:latest --restart=Never --rm -it \
  --overrides='{"spec":{"volumes":[{"name":"jfsdemo","persistentVolumeClaim":{"claimName":"jfsdemo"}}],"containers":[{"name":"v","image":"busybox:latest","volumeMounts":[{"name":"jfsdemo","mountPath":"/data"}]}]}}' \
  -- ls -la /data
# 预期:列出 16 个 shard-*.tar,总大小约 2GB(可加 du -sh /data 再看)
```

**为什么不可省**:不导入则 JuiceFS 文件系统为空 → DataLoad 预热 0 字节(缺口三
"预热成本"无数据可测)→ 训练 Pod 读空目录 → 后面所有完成判据失效。

**若 sync 报错**:把完整报错贴给我(常见两类:URI 解析错——对照上面两点检查;
凭证/元数据错——检查 jfs-secret 与 redis Service 名)。

### 5.4 创建 DataLoad(手动预热)并抓时序(10 分钟)

**在干什么**:DataLoad 是**独立、手动创建的 CRD**(这正是对手机制的关键观察点:
它和调度决策没有任何联动)。它跑一个 loader Job 执行 `juicefs warmup`,把
JuiceFS 数据块从 MinIO 拉到 loader Pod 所在节点的本地缓存。**注意:DataLoad
只创建一个 loader Pod,k8s 把它调度到某一个节点;缓存是"本地行为",Pod 在哪个
节点,缓存就落在哪个节点**——记下这个节点,后面看训练 Pod 是否被调度到它上面。

**先不要创建训练 Pod**,单独观察 DataLoad 生命周期:

```bash
date +%T   # 记录 T0(预热开始)
kubectl apply -f dataload.yaml
kubectl get dataload jfs-load -w   # 观察 PHASE 变化,Ctrl-C 退出
kubectl get pods -o wide | grep loader   # loader Pod 落在哪个节点?记下来!
kubectl logs -f <loader-pod>       # 看 warmup 过程日志
kubectl get dataload jfs-load      # 直到 PHASE=Complete
date +%T   # 记录 T1(预热完成)
```

**留下**:`kubectl get dataload jfs-load > evidence/dataload-status.txt`;
`kubectl logs <loader-pod> > evidence/loader.log`;
把 T0/T1、loader 落点节点、warmup 耗时写进 `evidence/timeline-notes.txt`。
