# P1 对手现勘报告(Fluid / JuiceFS 机制现勘)

- 日期:2026-10-09
- 环境:kind 集群 `traincache`(3 节点,k8s **v1.37.0**;kindest/node:v1.28.15 节点镜像)
- 全部证据归档:`../survey/evidence`(本报告每条判断均标注对应证据文件)
- 版本:**开源 Fluid 1.1.0-alpha.9**(镜像 1.1.0-36f0467,helm chart fluid-1.1.0-alpha.9)、**JuiceFS CE 1.3.0**(客户端 1.3.0+2025-07-03.30190ca1)、JuiceFS CSI v0.32.0(本地镜像)、MinIO latest、redis 7-alpine

## 0. 摘要与闸门判定

现勘验证了两个问题,结论如下:

1. **Fluid 是否真的没做"预热—调度"联动?** 成立,且比 P1 笔记的预期更强:开源 Fluid 1.1.0-alpha.9 在 JuiceFSRuntime 上**连 webhook 粗粒度注入都消失了**(实测注入前后 diff 为零,见 §2.2),预热(DataLoad)与调度(Pod 创建即被调度,时间戳同秒)完全独立。
2. **JuiceFS 社区版的能力边界?** 确认:CE 只有本地缓存;分布式缓存组、IORPC、RDMA 均为企业版(5.2/5.3+)能力,且有官方文档佐证。

**闸门判定:缺口成立 → 核心1 按"闭环"叙事推进**(P1 现勘闸门 ①)。

## 2. 官方 demo 与证据抓取(动作2)

### 2.1 链路与数据导入

Dataset `jfsdemo` + JuiceFSRuntime(同名绑定)→ format(元数据进 redis,数据块落 MinIO)→ **数据导入**(裸对象→JuiceFS 文件系统)→ DataLoad(warmup)→ 训练 Pod。

导入方式(踩坑后定稿):`juicefs sync` 以 `jfs://` 协议直写文件系统,源 URI 为路径式 `minio://AK:SK@endpoint/bucket`。该镜像客户端(ce-v1.3.0)已移除 `juicefs import` 命令;Fluid 的 PVC 只读,挂载写不可行。

### 2.2 发现一:webhook 注入前后 diff 为零

dry-run(绕过 webhook)与实际创建(经过 webhook)的 Pod spec 对比(`evidence/pod-before-injection.yaml` vs `pod-after-injection.yaml`):

| 观察项 | 结果 |
|---|---|
| FUSE sidecar 容器注入 | **无**——容器列表只有用户的 busybox。FUSE 由 Fluid CSI(node plugin)+ `jfsdemo-fuse` Pod(每节点一个)在 kubelet 层完成挂载,Pod 内只见普通 volumeMount |
| nodeAffinity / nodeSelector 注入 | **无**——P1 笔记描述的"webhook 注入亲和"在此版本+Runtime 组合下不复现 |
| 其他注入 | 仅 k8s 默认字段(serviceaccount projected volume、默认 tolerations) |

而 `JuiceFSRuntime.status` 里 Fluid 维护着 `cacheAffinity`(`evidence/runtime-status.txt`):
worker 节点被打上 `fluid.io/f-default-jfsdemo=true` 标签,亲和策略为 `preferredDuringSchedulingIgnoredDuringExecution`(weight 100),**required 项为空,且未注入到任何 Pod**。

**解读**:Fluid 1.1 把 JuiceFS 访问全面 CSI 化后,传统 webhook sidecar 注入路径不再使用;缓存亲和退化为 runtime status 里的"软偏好+节点标签",既不强制也不自动。这与 P1 笔记的外部事实"粗粒度二进制+事后注入"相比,注入环节已弱化,但"二进制(有无缓存 worker)而非块级进度"的粒度问题依旧。

### 2.3 发现二:Pod 不等 DataLoad(时序证据)

`evidence/timeline-notes.txt`(全部同一秒,来自 `kubectl get pod -o jsonpath`):

| 时刻(UTC) | 事件 |
|---|---|
| 08:33:39 | train-demo creationTimestamp |
| 08:33:39 | PodScheduled 条件生效 |
| 08:33:39 | startTime(容器启动) |

Pod 从创建到被调度到 `traincache-worker` 到启动,**同一秒完成,零等待**。DataLoad 是之后手动创建的独立资源(10:00 与 16:26 各运行一次),**没有任何机制让 Pod 等待预热完成**——"先被调度、再等数据"的 P1 论断成立(且在本装置上数据已在文件系统里,连"等数据"都由 FUSE 冷读承担,调度器一无所知)。

### 2.4 发现三:两次 warmup 的结果差异与 3.9G 污染事件

DataLoad 的 loader Job 在 worker Pod 里执行 `juicefs warmup <worker挂载点>`,两次运行结果不同:

| 时间(UTC) | warmup 结果 | 证据 |
|---|---|---|
| 02:00:12(10:00 CST) | **0 files (0 B)** | `evidence/loader-jfs-load.log`、`dataload-timing.txt` |
| 08:26:55(16:26 CST) | **548 files (3.9 GiB)** | 执行时终端日志(用户记录) |

10:00 那次 warmup 为 0 files,但同一脚本里 `ls` 挂载点能看到 shard-00000/00001.tar——两次差异的机制与 worker 生命周期相关(jfsdemo-worker-0 于 12:38 重启,16:26 的 warmup 在重启后的 worker 上成功),**结论按实记录:warmup 行为依赖 worker 挂载状态,失败时 DataLoad 仍会以 Complete 结束**(10:00 那次 DataLoad PHASE=Complete、DURATION 6s,`evidence/dataload-status.txt`)。

**3.9G 污染事件(装置侧教训,如实记录)**:导入时源 URI 拼重(`train-data//train-data/`)导致 sync 把 JuiceFS 自己的数据块对象镜像进了文件系统本身,文件系统 = 16 tar(1.97GiB)+ `traincache-demo/chunks/` 垃圾镜像(1.97GiB)≈ 3.9G(`evidence/import-pod.log`)。这直接导致 warmup 3.9GiB 超过 3Gi 缓存配额、热读被 LRU 淘汰打折——**恰好是"预热成本无人记账"的装置侧缩影:多拉 2 倍数据,系统毫无提示**。垃圾目录的清理见 §6 遗留事项。

### 2.5 训练 Pod 读数据(端到端成立)

`evidence/train-pod.log`:经 Fluid 挂载的 `/data` 可见 16 个 shard-*.tar,`du -sh` 3.9G(含垃圾),读 tar 前 1MB 成功——Fluid 链路端到端可用。

## 3. 独立 JuiceFS CE 对照组与 warmup 基线(动作4)

不经过 Fluid,用挂载镜像直接裸挂载同一文件系统(`../survey/manifests/jfs-standalone.yaml`),装置与结果(`evidence/standalone-baseline.txt`):

| 项 | 记录 |
|---|---|
| 客户端版本 | juicefs **1.3.0**+2025-07-03.30190ca1 |
| 挂载参数 | `metaurl=redis://redis.default.svc.cluster.local:6379/0`,`--cache-dir /cache --cache-size 3072`(本地缓存模式) |
| 冷读(缓存空,首读 1.97GiB 有效数据) | **1037 ms**(≈1.9 GB/s,kind 集群内网直连 MinIO) |
| warmup | 548 files(3.9 GiB,含垃圾镜像),**1193 ms** |
| 热读(重读) | **354 ms**(≈5.6 GB/s,本地缓存命中) |
| 缓存占用 | 2.9G(3.9GiB 数据超出 3GiB 配额,LRU 已淘汰部分) |

**基线解读**:① 冷热差 2.9×——本装置无 tc 限速,集群内网过快,冷读已接近内存速度,冷热差被压缩(探针阶段在限速装置下是 817×);② warmup 本身开销极小(秒级"通知式"拉取),真正的成本在缓存容量与重复预热字节;③ 该数字为"含污染数据"的基线,清理后需重测(见 §6)。

## 4. 能力边界表(动作3,四方对比)

每条判断附版本号与证据来源(实测/CRD/官方文档):

| 能力 | 开源 Fluid(实测 1.1.0-alpha.9,镜像 36f0467) | ACK ack-fluid(阿里云文档,版本标注) | JuiceFS CE(实测 1.3.0) | JuiceFS EE(文档,5.2/5.3+) |
|---|---|---|---|---|
| 预热与调度联动 | **无**:webhook 注入 diff 为零(实测);Pod 创建即调度(实测同秒);DataLoad 独立手动 | 缓存亲和感知调度(调度器与缓存引擎交互);多级亲和调度 v1.0.5+;FUSE 客户端亲和调度语义 v1.0.7+ | 无(无调度概念) | 无(无调度概念) |
| 预热机制 | DataLoad CRD 含 `schedule`、`target[].replicas` 字段(CRD 实证,`/tmp/fluid/crds/data.fluid.io_dataloads.yaml`);warmup 实测可用 | 定时 DataLoad(Once/Cron,v1.0.2+);target 可配副本数;预热资源限额 v1.0.6+;定时回收 v1.0.5+ | `juicefs warmup` 命令(实测) | 同命令,配合缓存组语义 |
| 块级进度/就绪度门控 | **无**(无 SchedulingGate、无块级就绪概念) | 未见(亲和调度仍为"有无缓存"级) | 无 | 无 |
| 缓存亲和注入 | status.cacheAffinity(preferred weight 100,required 空,**未注入 Pod**,实测) | Serverless 场景 FUSE Sidecar 注入(文档);标准集群走 CSI | — | — |
| 分布式缓存组 | 无 | — | **无(仅本地缓存)** | **有**:一致性哈希缓存组、IORPC(5.2+)、RDMA(5.3+,Beta) |
| 加速运行时 | 开源 Runtime(Alluxio/JuiceFS/Jindo/Thin 等) | 阿里云自研 JindoRuntime、EFCRuntime;ECI 本地盘缓存 v1.0.2+ | — | — |

**对照结论**:
1. "预热—调度"联动在**四方中没有任何一方做到块级**;ACK 做得最接近(亲和感知调度),但仍是"节点有无缓存"的粗粒度,且为商业版,不含块级进度门控与按 Job 子集预热。
2. 开源 Fluid 的注入行为比 P1 笔记预期更弱(CSI 化后 webhook 零注入)——TrainCache 的闭环设计("Job 即将调度→按需块级预热→SchedulingGate 门控→超时降级")在此对比下是**真空地带**,不是重复造轮子。

## 5. 缺口判定(P1 三个"缝")与叙事方向

| 缝 | 判定 | 现勘证据 |
|---|---|---|
| ① 预热与调度不闭环 | **成立,且强化** | 注入 diff 为零;Pod 不等 DataLoad;ACK 仅有粗粒度亲和(文档) |
| ② 就绪度粒度错配 | **成立** | cacheAffinity 为二进制(节点有无 worker),无"该 Job 要读的分片就绪比例"概念 |
| ③ 预热成本无人记账 | **成立** | 3.9G 污染事件:多拉 2 倍字节,系统零提示;warmup 超配额静默 LRU |

**闸门判定:缺口被证据确认 → 核心1 按"闭环"叙事推进,不带假设开工。**
